## Why it matters

On GKE, you describe the app in Kubernetes manifests: a Deployment runs the Pods, and a Service, Gateway, or Ingress exposes them. The developer chooses the update strategy, the source of configuration and secrets, and the identity that Pods use. The developer also chooses how a release moves between environments. The exam tests these manifests, the `kubectl` rollout commands, and the choices that Google recommends.

## Key points

- Autopilot is the recommended cluster mode for most production use cases ([Deploy an app to a GKE cluster](https://docs.cloud.google.com/kubernetes-engine/docs/deploy-app-cluster)).
- You use Google Cloud tools to manage the cluster and `kubectl` for tasks inside the cluster ([Deploying workloads](https://docs.cloud.google.com/kubernetes-engine/docs/get-started/deploy-workloads)).
- A Deployment runs uniform, non-unique Pods for a stateless app. A stateful app uses a StatefulSet, which gives each Pod a unique identity ([Deploying a stateless Linux application](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/stateless-apps)).
- A rollout starts only when the Pod template (`.spec.template`) changes. Scaling a Deployment does not start a rollout ([Deployments | Kubernetes](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/)).
- `kubectl rollout undo` returns a Deployment to the previous revision, or to a revision that you name. It works for an update in progress or a completed update ([Deploying a stateless Linux application](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/stateless-apps)).
- A Service gives a group of Pods a stable IP address that lasts for the life of the Service. ClusterIP is the default type ([Understand Kubernetes Services](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/service)).
- A LoadBalancer Service creates a passthrough Network Load Balancer, not an Application Load Balancer ([About LoadBalancer Services](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/service-load-balancer)).
- GKE Ingress is in maintenance mode. Google recommends the GKE Gateway API ([GKE Ingress for Application Load Balancers](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/ingress)).
- Workload Identity Federation for GKE (formerly GKE Workload Identity) is the recommended way for workloads to call Google Cloud APIs. It is always on in Autopilot ([About Workload Identity Federation for GKE](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/workload-identity), [Authenticate to Google Cloud APIs from GKE workloads](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/workload-identity), [Make IAM for GKE easier to use with Workload Identity Federation | Google Cloud Blog](https://cloud.google.com/blog/products/identity-security/make-iam-for-gke-easier-to-use-with-workload-identity-federation)).
- Nodes pull images as the node service account. By default, this is the Compute Engine default service account ([Deploying to Google Kubernetes Engine](https://docs.cloud.google.com/artifact-registry/docs/integrate-gke)).
- If you do not set resource requests, Autopilot applies default values. Google recommends that you set requests for each container ([Resource requests in Autopilot](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/autopilot-resource-requests)).
- Cloud Deploy delivers a release to a series of targets in a promotion sequence ([Overview of Cloud Deploy](https://docs.cloud.google.com/deploy/docs/overview)).

## Deployments and rolling updates

A Deployment holds the desired state: the number of Pods, the image version, and the Pod labels. You change the app by changing the Pod specification ([Deploying a stateless Linux application](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/stateless-apps)).

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 3
  selector:
    matchLabels:
      run: my-app
  template:
    metadata:
      labels:
        run: my-app
    spec:
      containers:
      - name: hello-app
        image: us-docker.pkg.dev/google-samples/containers/gke/hello-app:1.0
```

Source: [Deploying a stateless Linux application](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/stateless-apps).

The fields below control a rollout. Questions often give a scenario and ask which field to change:

| Field | Default | What it controls |
|---|---|---|
| `spec.replicas` | 1 | The number of Pods. Do not set it when a HorizontalPodAutoscaler manages the Deployment |
| `spec.strategy.type` | `RollingUpdate` | `Recreate` stops all existing Pods before it creates new ones |
| `rollingUpdate.maxUnavailable` | 25% | Pods that can be unavailable during the update. A percentage rounds down |
| `rollingUpdate.maxSurge` | 25% | Pods above `replicas` during the update. A percentage rounds up. It cannot be 0 if `maxUnavailable` is 0 |
| `minReadySeconds` | 0 | How long a new Pod must be ready, without a crash, before it counts as available |
| `progressDeadlineSeconds` | 600 | How long the controller waits before it reports `ProgressDeadlineExceeded` |
| `revisionHistoryLimit` | 10 | How many old ReplicaSets stay for rollback. With 0, you cannot undo a rollout |

Sources: [Deployments | Kubernetes](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/).

| Task | Command |
|---|---|
| Create or update from a manifest | `kubectl apply -f DEPLOYMENT_FILE` |
| Change the image | `kubectl set image deployment nginx nginx=nginx:1.9.1` |
| Watch a rollout | `kubectl rollout status deployment/nginx-deployment` |
| List revisions | `kubectl rollout history deployment/nginx-deployment` |
| Roll back | `kubectl rollout undo deployment my-deployment --to-revision=3` |
| Scale by hand | `kubectl scale deployment DEPLOYMENT_NAME --replicas NUMBER_OF_REPLICAS` |

Sources: [Deploying a stateless Linux application](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/stateless-apps), [Deployments | Kubernetes](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/).

Some rollout rules are not obvious:

- `kubectl apply` can update a resource only if you created it with `kubectl apply` or `kubectl create --save-config` ([Deploying a stateless Linux application](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/stateless-apps)).
- A rollback restores only the Pod template. Scaling does not create a revision ([Deployments | Kubernetes](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/)).
- The `kubernetes.io/change-cause` annotation fills the `CHANGE-CAUSE` column of the history. The `--record` flag is deprecated ([Deployments | Kubernetes](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/)).
- If the new Pods fail, for example because the image cannot be pulled, the controller stops the bad rollout. It stops scaling up the new ReplicaSet. The result depends on the `maxUnavailable` setting ([Deployments | Kubernetes](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/)). Readiness comes from probes, which [Kubernetes health checks](note:3.2-health-checks) explains.

GKE also supports patterns such as recreate, rolling update, and blue-green ([Best practices for continuous integration and delivery to Google Kubernetes Engine](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/best-practices-continuous-integration-delivery-kubernetes)). For canary and weighted rollouts, see [Traffic splitting](note:1.1-traffic-splitting).

## Expose the app: Services, Gateway, and Ingress

Pod IP addresses change when Pods come and go. A Service gives clients one stable address and balances requests across its Pods ([Understand Kubernetes Services](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/service)).

| Need | Use | What GKE creates |
|---|---|---|
| Calls from other Pods in the cluster | ClusterIP Service (default) | A stable internal IP address |
| Layer 4 access from outside the VPC network | LoadBalancer Service with `loadBalancerClass: "networking.gke.io/l4-regional-external"` | A regional external passthrough Network Load Balancer |
| Layer 4 access from inside the VPC network | LoadBalancer Service with `loadBalancerClass: "networking.gke.io/l4-regional-internal"` | An internal passthrough Network Load Balancer |
| HTTP(S) routing by host, path, or header | Gateway and HTTPRoute | An Application Load Balancer of the GatewayClass type |
| An existing Ingress setup | Ingress (maintenance mode) | A classic Application Load Balancer, or an internal Application Load Balancer |

Sources: [Understand Kubernetes Services](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/service), [About LoadBalancer Services](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/service-load-balancer), [About Gateway API](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/gateway-api), [GKE Ingress for Application Load Balancers](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/ingress).

The `loadBalancerClass` field needs GKE 1.33.1-gke.1779000 or later, and you cannot change it after you create the Service. A LoadBalancer Service without this field or the related annotations creates a target pool-based load balancer. Google does not recommend that type ([About LoadBalancer Services](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/service-load-balancer)). The quickstart creates a LoadBalancer Service with one command:

```bash
kubectl expose deployment hello-server \
    --type LoadBalancer \
    --port 80 \
    --target-port 8080
```

Source: [Deploy an app to a GKE cluster](https://docs.cloud.google.com/kubernetes-engine/docs/deploy-app-cluster).

### Gateway API

The Gateway API is role-oriented. A GatewayClass is a cluster-scoped template for a Layer 7 load balancer. A cluster operator creates a Gateway from a GatewayClass. Application developers attach HTTPRoutes to it. It also supports header matching and traffic weighting without custom annotations ([About Gateway API](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/gateway-api)).

| GatewayClass | Load balancer |
|---|---|
| `gke-l7-global-external-managed` | Global external Application Load Balancer (recommended over `gke-l7-gxlb`) |
| `gke-l7-regional-external-managed` | Regional external Application Load Balancer |
| `gke-l7-rilb` | Internal Application Load Balancer |
| `gke-l7-gxlb` | Classic Application Load Balancer |

Sources: [About Gateway API](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/gateway-api).

This internal Gateway listens on port 80. The HTTPRoute sends `/de` to one Service and all other requests to another:

```yaml
kind: Gateway
apiVersion: gateway.networking.k8s.io/v1
metadata:
   name: internal-http
spec:
  gatewayClassName: gke-l7-rilb
  listeners:
  - name: http
    protocol: HTTP
    port: 80
---
kind: HTTPRoute
apiVersion: gateway.networking.k8s.io/v1
metadata:
  name: store
spec:
  parentRefs:
  - kind: Gateway
    name: internal-http
  hostnames:
  - "store.example.com"
  rules:
  - matches:
    - path:
        value: /de
    backendRefs:
    - name: store-german
      port: 8080
  - backendRefs:
    - name: store-v1
      port: 8080
```

Source: [Deploying Gateways](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/deploying-gateways).

Gateway rules that the exam can test:

- Gateway works only on VPC-native clusters. It is always on in Autopilot. On Standard, add `--gateway-api=standard` to the cluster ([Deploying Gateways](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/deploying-gateways)).
- The cluster must have the `HttpLoadBalancing` add-on enabled. This add-on is enabled by default ([Deploying Gateways](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/deploying-gateways), [About LoadBalancer Services](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/service-load-balancer)).
- Regional and cross-region GatewayClasses need a proxy-only subnet ([Deploying Gateways](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/deploying-gateways)).
- You configure a Gateway with Policy resources, such as HealthCheckPolicy and GCPBackendPolicy. FrontendConfig and BackendConfig do not work with a Gateway ([Deploying Gateways](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/deploying-gateways), [About Gateway API](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/gateway-api)).
- A GCPBackendPolicy sets how the backend services of the load balancer send traffic to the endpoints. It is similar to a BackendConfig for an Ingress. It replaced `LbPolicy`, which is still supported but gets no new attributes ([About Gateway API](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/gateway-api)).
- An HTTPRoute that refers to a Service in another namespace needs a ReferenceGrant in that namespace ([About Gateway API](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/gateway-api)).

To choose a load balancer type, see [Load balancing](note:1.1-load-balancing). Load balancer health checks are in [Kubernetes health checks](note:3.2-health-checks).

## Configuration and secrets

Keep configuration out of the image, and keep secrets out of plain configuration. The store that you choose controls who can read the data and when Pods see a change:

| Data | Store | How Pods read it | What to know |
|---|---|---|---|
| Settings that are not secret | ConfigMap | Environment variables, command arguments, or files in a volume | No secrecy or encryption. A mounted file updates eventually. An environment variable needs a Pod restart |
| Secrets in the cluster | Kubernetes Secret | Environment variables or files in a volume | GKE encrypts Secrets at rest by default. Application-layer secrets encryption adds your own Cloud KMS key |
| Secrets outside the cluster | Secret Manager, through the Secret Manager add-on | Files in a CSI volume | Access is controlled by IAM, not by in-cluster RBAC |

Sources: [ConfigMaps | Kubernetes](https://kubernetes.io/docs/concepts/configuration/configmap/), [Secrets | Kubernetes](https://kubernetes.io/docs/concepts/configuration/secret/), [Encrypt secrets at the application layer](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/encrypting-secrets), [Access secrets stored outside GKE clusters using client libraries](https://docs.cloud.google.com/kubernetes-engine/docs/tutorials/workload-identity-secrets).

Anyone who can create a Pod in a namespace can read every Secret in that namespace ([Secrets | Kubernetes](https://kubernetes.io/docs/concepts/configuration/secret/)). Secrets that you store outside the cluster have a lower risk of unauthorized access if an attack occurs ([Access secrets stored outside GKE clusters using client libraries](https://docs.cloud.google.com/kubernetes-engine/docs/tutorials/workload-identity-secrets)).

The Secret Manager add-on mounts Secret Manager secrets as files in Pods. It is based on the open source Secrets Store CSI Driver and works on Standard and Autopilot clusters. It does not support the Sync as Kubernetes Secret feature. To copy secrets into Kubernetes Secrets, use the secret synchronization feature of Secret Manager ([Use Secret Manager add-on with Google Kubernetes Engine](https://docs.cloud.google.com/secret-manager/docs/secret-manager-managed-csi-component)).

You enable the add-on with `--enable-secret-manager`, and you grant `roles/secretmanager.secretAccessor` to the Kubernetes ServiceAccount of the Pod. Then a `SecretProviderClass` lists the secrets, and a CSI volume mounts them:

```yaml
apiVersion: secrets-store.csi.x-k8s.io/v1
kind: SecretProviderClass
metadata:
  name: SECRET_PROVIDER_CLASS_NAME
spec:
  provider: gke
  parameters:
    secrets: |
      - resourceName: "projects/PROJECT_ID/secrets/SECRET_NAME/versions/SECRET_VERSION"
        path: "FILENAME.txt"
---
# Part of the Pod spec
spec:
  serviceAccountName: KSA_NAME
  containers:
  - image: IMAGE_NAME
    name: POD_NAME
    volumeMounts:
      - mountPath: "/var/secrets"
        name: mysecret
  volumes:
  - name: mysecret
    csi:
      driver: secrets-store-gke.csi.k8s.io
      readOnly: true
      volumeAttributes:
        secretProviderClass: SECRET_PROVIDER_CLASS_NAME
```

Source: [Use Secret Manager add-on with Google Kubernetes Engine](https://docs.cloud.google.com/secret-manager/docs/secret-manager-managed-csi-component).

Automatic rotation of mounted secrets is optional. Turn it on with `--enable-secret-manager-rotation`, and set `--secret-manager-rotation-interval`. The add-on then pushes updated secrets to the Pods periodically, and the app gets them without a restart ([Use Secret Manager add-on with Google Kubernetes Engine](https://docs.cloud.google.com/secret-manager/docs/secret-manager-managed-csi-component)).

For Secret Manager versions and rotation, see [Secrets and keys](note:1.2-secrets-and-keys).

## Workload Identity Federation for GKE

Workload Identity Federation for GKE lets a Pod call Google Cloud APIs as its Kubernetes ServiceAccount. You grant IAM roles to that ServiceAccount, so you need no service account key files. Each app can have its own identity ([About Workload Identity Federation for GKE](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/workload-identity)).

1. Create a Kubernetes ServiceAccount, or use an existing one. A Pod without a ServiceAccount gets the `default` ServiceAccount of its namespace ([Authenticate to Google Cloud APIs from GKE workloads](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/workload-identity)).
2. Grant IAM roles to the principal identifier of that ServiceAccount ([Authenticate to Google Cloud APIs from GKE workloads](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/workload-identity)).
3. Set `serviceAccountName` in the Pod spec, as in the add-on sample above ([Use Secret Manager add-on with Google Kubernetes Engine](https://docs.cloud.google.com/secret-manager/docs/secret-manager-managed-csi-component)).

```bash
kubectl create serviceaccount KSA_NAME \
    --namespace NAMESPACE
gcloud projects add-iam-policy-binding projects/PROJECT_ID \
    --role=roles/container.clusterViewer \
    --member=principal://iam.googleapis.com/projects/PROJECT_NUMBER/locations/global/workloadIdentityPools/PROJECT_ID.svc.id.goog/subject/ns/NAMESPACE/sa/KSA_NAME \
    --condition=None
```

Source: [Authenticate to Google Cloud APIs from GKE workloads](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/workload-identity).

Enabling the feature on a cluster grants no IAM permissions ([About Workload Identity Federation for GKE](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/workload-identity)). Google recommends IAM principal identifiers. Some APIs have limits on this federated identity. For those APIs, link the Kubernetes ServiceAccount to an IAM service account instead. That method needs both a `roles/iam.workloadIdentityUser` grant and the `iam.gke.io/gcp-service-account` annotation ([Authenticate to Google Cloud APIs from GKE workloads](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/workload-identity)). For Application Default Credentials, see [Authenticating to Google Cloud](note:1.2-authenticating-to-google-cloud).

## Images, resource requests, and namespaces

**Images.** An Artifact Registry image path has the form `LOCATION-docker.pkg.dev/PROJECT-ID/REPOSITORY/IMAGE:TAG`. Nodes pull images as the node service account. If your organization blocks the automatic Editor grant, give that account Artifact Registry Reader. For a repository in another project, grant the role to the node service account ([Deploying to Google Kubernetes Engine](https://docs.cloud.google.com/artifact-registry/docs/integrate-gke)). If you do not give an image version, the `latest` tag applies ([Deploy an app to a GKE cluster](https://docs.cloud.google.com/kubernetes-engine/docs/deploy-app-cluster)). In production, use specific immutable tags or SHA digests ([Troubleshoot CrashLoopBackOff events](https://docs.cloud.google.com/kubernetes-engine/docs/troubleshooting/crashloopbackoff-events)).

**Resource requests on Autopilot.** Autopilot uses your requests to configure nodes, and it enforces a minimum and a maximum for each compute class ([Resource requests in Autopilot](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/autopilot-resource-requests)):

| Your Pod spec | What Autopilot does |
|---|---|
| No requests | Applies defaults. For the general-purpose class: 0.5 vCPU, 2 GiB of memory, and 1 GiB of ephemeral storage |
| Requests below the minimum | Raises the requests to the allowed range |
| Requests above the maximum | Rejects the workload with an error |
| Requests set, no limits | Pods can burst on clusters that support bursting. On other clusters, limits equal requests |
| Limits set, no requests | Sets requests equal to limits |

Sources: [Resource requests in Autopilot](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/autopilot-resource-requests).

For sizing and cost, see [Resources and cost](note:1.1-resources-and-cost).

**Namespaces.** In an enterprise cluster, each team usually gets its own namespace. Policies are usually scoped by namespace. They restrict API access, resource usage, and what containers can do ([Cluster multi-tenancy](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/multitenancy-overview)).

## Delivery with Cloud Deploy

Cloud Deploy moves one release through a series of targets, for example `dev` and then `prod` ([Overview of Cloud Deploy](https://docs.cloud.google.com/deploy/docs/overview)).

| Term | Meaning |
|---|---|
| Delivery pipeline | A YAML file with the promotion sequence of targets |
| Target | One environment, for example a GKE cluster |
| Release | The rendered manifests and the exact images to deploy |
| Rollout | The deploy of a release to one target. A new release creates the first rollout |
| Promotion | A rollout of the same release to the next target |
| Approval | `requireApproval` on a target holds promotion until someone approves |
| Rollback | A new rollout of the last successfully deployed release |

Sources: [Overview of Cloud Deploy](https://docs.cloud.google.com/deploy/docs/overview).

Cloud Deploy uses Skaffold to render and deploy. It deploys to GKE and Cloud Run ([Overview of Cloud Deploy](https://docs.cloud.google.com/deploy/docs/overview)).

```yaml
apiVersion: deploy.cloud.google.com/v1
kind: DeliveryPipeline
metadata:
  name: my-gke-demo-app-1
serialPipeline:
  stages:
  - targetId: qsdev
  - targetId: qsprod
---
apiVersion: deploy.cloud.google.com/v1
kind: Target
metadata:
  name: qsdev
gke:
  cluster: projects/PROJECT_ID/locations/us-central1/clusters/quickstart-cluster-qsdev
```

Source: [Deploy an app to GKE using Cloud Deploy](https://docs.cloud.google.com/deploy/docs/deploy-app-gke).

Register the pipeline with `gcloud deploy apply --file=clouddeploy.yaml`. Then create a release with `gcloud deploy releases create`. Google recommends templated manifests and SHA-qualified image names in the `--images` flag ([Deploy an app to GKE using Cloud Deploy](https://docs.cloud.google.com/deploy/docs/deploy-app-gke)).

Build the image once and promote it through the environments. A rebuild can add untested changes to production. Google also recommends separate clusters for each environment ([Best practices for continuous integration and delivery to Google Kubernetes Engine](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/best-practices-continuous-integration-delivery-kubernetes)). For the build side, see [Cloud Build and Artifact Registry](note:2.2-cloud-build-artifact-registry).

## AWS mapping

| AWS | Google Cloud | Difference that matters |
|---|---|---|
| Amazon EKS | GKE | Autopilot is the recommended mode for most production use cases |
| AWS Fargate with Amazon EKS | GKE Autopilot | Autopilot applies default requests and rejects requests above the maximum |
| Elastic Load Balancing | Cloud Load Balancing through a Service, a Gateway, or an Ingress | A LoadBalancer Service is a passthrough load balancer. Use a Gateway for HTTP(S) routing |
| Amazon ECR | Artifact Registry | Nodes pull images as the node service account |
| AWS Secrets Manager | Secret Manager and its GKE add-on | The add-on mounts secrets as files. IAM controls access |
| AWS CodePipeline, AWS CodeDeploy | Cloud Deploy | A rollback is a new rollout of the last successful release |

## Exam traps

- **"Scale the Deployment to start a new rollout."** Only a change to the Pod template starts a rollout ([Deployments | Kubernetes](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/)).
- **"A rollback also restores the old replica count."** A rollback restores only the Pod template ([Deployments | Kubernetes](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/)).
- **A LoadBalancer Service for path-based HTTP routing.** It creates a passthrough Network Load Balancer. Use a Gateway and an HTTPRoute ([About LoadBalancer Services](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/service-load-balancer), [About Gateway API](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/gateway-api)).
- **A new design on GKE Ingress.** Ingress gets only bug fixes. Google recommends the Gateway API ([GKE Ingress for Application Load Balancers](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/ingress)).
- **Image pull fails from another project.** Grant Artifact Registry access to the node service account, not to the Pod's ServiceAccount ([Deploying to Google Kubernetes Engine](https://docs.cloud.google.com/artifact-registry/docs/integrate-gke)).
- **A password in a ConfigMap.** A ConfigMap gives no secrecy or encryption ([ConfigMaps | Kubernetes](https://kubernetes.io/docs/concepts/configuration/configmap/)).
- **"The Pod sees the new ConfigMap value."** Values in environment variables change only after a Pod restart ([ConfigMaps | Kubernetes](https://kubernetes.io/docs/concepts/configuration/configmap/)).
- **A service account key stored in a Kubernetes Secret.** Use Workload Identity Federation for GKE instead of key files ([About Workload Identity Federation for GKE](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/workload-identity)).
- **"Enabling Workload Identity Federation gives the Pods access."** It grants no permissions. You must grant IAM roles ([About Workload Identity Federation for GKE](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/workload-identity)).
- **Large requests on Autopilot.** Requests above the maximum make Autopilot reject the workload ([Resource requests in Autopilot](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/autopilot-resource-requests)).
- **A new build for each environment.** Build once and promote the same image ([Best practices for continuous integration and delivery to Google Kubernetes Engine](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/best-practices-continuous-integration-delivery-kubernetes)).
