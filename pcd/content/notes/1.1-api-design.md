## Why it matters

Google designs its own Cloud APIs with one set of rules: the API Improvement Proposals (AIPs). The exam expects you to design your APIs in the same way, with resources, standard methods, clear errors, and safe retries. You also choose between REST and gRPC. Then you configure Cloud Run or GKE so that gRPC traffic stays on HTTP/2 from the client to the container.

## Key points

- The API design guide is the guide that Google follows for Cloud APIs. It applies to REST and RPC APIs, and its sections now point to the AIPs ([API design guide](https://docs.cloud.google.com/apis/design)).
- Resource-oriented design models an API as named resources (nouns) in a hierarchy, with a small number of standard methods (verbs) ([AIP-121](https://google.aip.dev/121)).
- An API that is identical to the database schema is an anti-pattern, because it couples the API to the storage system ([AIP-121](https://google.aip.dev/121)).
- Prefer standard methods. A custom method uses a normal HTTP verb (usually `POST`) and puts the custom verb in the URI after a colon ([AIP-121](https://google.aip.dev/121), [AIP-136](https://google.aip.dev/136)).
- An update uses `PATCH` with a field mask. Google APIs generally do not support `PUT` ([AIP-134](https://google.aip.dev/134)).
- Every error returns `google.rpc.Status` with a canonical code. Every error response includes an `ErrorInfo` with a machine-readable `reason` ([AIP-193](https://google.aip.dev/193)).
- A `request_id` field makes a request idempotent. The server detects a duplicate request and returns the response of the first request ([AIP-155](https://google.aip.dev/155)).
- A method that can take a long time returns a `google.longrunning.Operation`. A good rule of thumb for "a long time" is 10 seconds ([AIP-151](https://google.aip.dev/151)).
- gRPC sends protocol buffers over HTTP/2. Many gRPC features, such as streaming and metadata, need HTTP/2 ([Using gRPC](https://docs.cloud.google.com/run/docs/triggering/grpc)).
- Cloud Run downgrades HTTP/2 requests to HTTP/1 before they reach the container, except native gRPC traffic. For end-to-end HTTP/2, set `--use-http2` and serve `h2c` in the container ([Use HTTP/2 for services](https://docs.cloud.google.com/run/docs/configuring/http2)).
- gRPC through an Application Load Balancer needs HTTP/2 from end to end. Set the backend service protocol to `HTTP2` or `H2C` ([External Application Load Balancer overview](https://docs.cloud.google.com/load-balancing/docs/https)).
- API Gateway accepts API definitions in OpenAPI 2.0, OpenAPI 3.0.x, and OpenAPI 3.1.x ([OpenAPI overview](https://docs.cloud.google.com/api-gateway/docs/openapi-overview)).

## Resource-oriented design

Design the resources first and the methods last. AIP-121 gives this order: the resources, the relationships between them, the schema of each resource, and then the methods ([AIP-121](https://google.aip.dev/121)).

A resource name is a path of collection IDs and resource IDs, for example `publishers/123/books/les-miserables`. Collection IDs are plural and use `camelCase`. The first field of a resource is `name`, and it holds this name ([AIP-122](https://google.aip.dev/122)).

The resource URI includes the major version, for example `https://library.googleapis.com/v1/publishers/123/books/les-miserables`. The full resource name (`//library.googleapis.com/publishers/123/books/les-miserables`) has no version, because the resource continues to exist across major versions ([AIP-122](https://google.aip.dev/122)). [Versioning, exposing, and securing APIs on Cloud Run](note:3.1-api-versioning-and-exposure) explains version changes.

### Standard methods and their HTTP mapping

| Method | HTTP mapping | Request body | Rules to remember |
|---|---|---|---|
| Get | `GET /v1/{name=publishers/*/books/*}` | None | Every resource supports Get, so that clients can check the state after a change |
| List | `GET /v1/{parent=publishers/*}/books` | None | Every resource supports List, except a singleton resource |
| Create | `POST /v1/{parent=publishers/*}/books` | The resource | A duplicate resource name gives `ALREADY_EXISTS` |
| Update | `PATCH /v1/{book.name=publishers/*/books/*}` | The resource | `update_mask` lists the fields to change. The value `*` replaces the full resource |
| Delete | `DELETE /v1/{name=publishers/*/books/*}` | None | A missing resource gives `NOT_FOUND`. With `allow_missing`, the request succeeds and does nothing |
| Custom | `POST /v1/{name=publishers/*/books/*}:archive` | `*` | Use `GET` to read data. Use `POST` when the method changes data |

Sources: [AIP-121](https://google.aip.dev/121), [AIP-131](https://google.aip.dev/131), [AIP-132](https://google.aip.dev/132), [AIP-133](https://google.aip.dev/133), [AIP-134](https://google.aip.dev/134), [AIP-135](https://google.aip.dev/135), [AIP-136](https://google.aip.dev/136).

Choose a method type in this order: standard methods, batch or aggregate methods, custom methods, and streaming methods. Standard methods work in the most clients: declarative tools, CLIs, UIs, and SDKs ([AIP-130](https://google.aip.dev/130)).

Google APIs use `PATCH` and not `PUT`. Google adds fields to stable APIs over time, and a new field breaks a client that sends `PUT` with the full resource ([AIP-134](https://google.aip.dev/134)).

Names use correct American English and a small, consistent vocabulary. Method names use `VerbNoun` in UpperCamelCase, for example `CreateBook` ([AIP-190](https://google.aip.dev/190)). A custom method name must not include `Async`. Use the suffix `LongRunning` for a long-running variant of a method ([AIP-136](https://google.aip.dev/136)).

### One definition for gRPC and REST

Google defines an API once, in protocol buffers, and maps each RPC to an HTTP method with the `google.api.http` annotation. Clients can then call the same method with gRPC or with JSON over HTTP. This is HTTP/JSON transcoding ([AIP-127](https://google.aip.dev/127)).

```proto
rpc CreateBook(CreateBookRequest) returns (Book) {
  option (google.api.http) = {
    post: "/v1/{parent=publishers/*}/books"
    body: "book"
  };
}
```

Source: [AIP-127](https://google.aip.dev/127).

Every RPC must have an HTTP definition, except a bidirectional streaming RPC. HTTP/1.1 cannot carry bidirectional streaming, so offer another method that does not need it ([AIP-127](https://google.aip.dev/127)). Fields that are not in the URI path or the body become query parameters. JSON clients use `camelCase` field names ([AIP-127](https://google.aip.dev/127)).

API Gateway and the Extensible Service Proxy (ESP) of Cloud Endpoints can do the transcoding for you ([gRPC overview for API Gateway](https://docs.cloud.google.com/api-gateway/docs/grpc-overview), [Transcoding HTTP/JSON to gRPC](https://docs.cloud.google.com/endpoints/docs/grpc/transcoding)).

## Errors

Return errors in one standard format, so that clients write code against codes and not against text.

| Part | What it holds | Rule |
|---|---|---|
| `Status.code` | A canonical code, for example `NOT_FOUND` or `RESOURCE_EXHAUSTED` | Clients branch on the code |
| `Status.message` | An English message for developers | Do not parse it. The text can change |
| `ErrorInfo` in `details` | `reason` (for example `RESOURCE_AVAILABILITY`), `domain`, and `metadata` | Required in every error response |
| `LocalizedMessage` in `details` | A message in the user's locale, or a better message than `Status.message` | Optional (a service may add it) |

Sources: [AIP-193](https://google.aip.dev/193), [Best practices for the Compute Engine API](https://docs.cloud.google.com/compute/docs/api/best-practices).

Check permission before you check that a resource exists. A caller without permission gets `PERMISSION_DENIED` (403), even when the resource does not exist. A caller with permission gets `NOT_FOUND` (404) for a missing resource ([AIP-193](https://google.aip.dev/193)).

Do not return partial errors from a normal method. A bulk method that needs partial failure puts the failure details in the metadata of a long-running operation ([AIP-193](https://google.aip.dev/193)). Over HTTP/1.1 with JSON, the error body has `code` (the HTTP status), `message`, `status`, and `details` ([AIP-193](https://google.aip.dev/193)).

Which errors a client retries, and how long it waits, is in [Efficient and resilient API calls](note:4.2-efficient-api-calls).

## Idempotency and long-running operations

Networks fail. A client that gets no response does not know if the server did the work. Design the API so that a retry is safe.

| Need | Pattern | Source |
|---|---|---|
| Safe retry of a Create or a custom method | Add a `request_id` (a UUID). The server returns the earlier response for a duplicate ID | [AIP-155](https://google.aip.dev/155) |
| Safe retry of a Delete | `allow_missing` turns a delete of a missing resource into a no-op | [AIP-135](https://google.aip.dev/135) |
| No lost update | Send the `etag` that you read. A mismatch gives `ABORTED` | [AIP-154](https://google.aip.dev/154), [AIP-135](https://google.aip.dev/135) |
| Work that takes more than about 10 seconds | Return a `google.longrunning.Operation` and implement the `Operations` service | [AIP-151](https://google.aip.dev/151) |

Sources: [AIP-155](https://google.aip.dev/155), [AIP-135](https://google.aip.dev/135), [AIP-154](https://google.aip.dev/154), [AIP-151](https://google.aip.dev/151).

A long-running method declares its response type and metadata type in the `operation_info` annotation. While a create or delete operation runs, Get and List should show the resource with a state that says it is not usable. An error during the operation goes in `Operation.error`. A resource that does not allow parallel operations returns `ABORTED` for a second operation ([AIP-151](https://google.aip.dev/151)).

Google's own APIs work in the same way. A Compute Engine request that changes a resource returns HTTP `200` when the server accepts it. The `200` does not mean that the operation is done or that it succeeded. Call the `wait` method of the operation (`zoneOperations.wait`, `regionOperations.wait`, or `globalOperations.wait`) in a retry loop with exponential backoff. Do not poll with short intervals, because each request uses rate quota ([Best practices for the Compute Engine API](https://docs.cloud.google.com/compute/docs/api/best-practices)).

## REST or gRPC

| Use | When | Do not use when |
|---|---|---|
| REST with JSON | Browsers, partners, and other public clients call the API. Most public APIs follow REST conventions | You need streaming or the lowest CPU cost per call |
| gRPC | Internal microservices call each other, the load is high, or you need streaming | Browser clients call the service directly and nothing transcodes |
| gRPC with transcoding | You need gRPC for internal callers and JSON for external callers | The JSON request or response body is larger than 1 MB on API Gateway |

Sources: [AIP-127](https://google.aip.dev/127), [Using gRPC](https://docs.cloud.google.com/run/docs/triggering/grpc), [gRPC overview for API Gateway](https://docs.cloud.google.com/api-gateway/docs/grpc-overview).

gRPC uses protocol buffers, which the Cloud Run docs say are up to seven times faster than REST calls ([Using gRPC](https://docs.cloud.google.com/run/docs/triggering/grpc)). For Google's own APIs, gRPC can increase throughput per CPU by as much as a factor of 10 compared to the JSON REST API ([Client libraries and Cloud APIs explained](https://docs.cloud.google.com/apis/docs/client-libraries-explained)).

## gRPC on Cloud Run

Cloud Run supports all gRPC types, streaming and unary ([Using gRPC](https://docs.cloud.google.com/run/docs/triggering/grpc)). Do these steps:

1. Define the messages and the service in a proto file, and compile it. Cloud Run needs nothing special in the proto file.
2. Make the server listen on the port in the `PORT` environment variable.
3. Make the server accept HTTP/2 cleartext (`h2c`). The Google frontend ends TLS and sends `h2c` to the container. Test locally with `curl -i --http2-prior-knowledge http://localhost:PORT`.
4. Deploy with end-to-end HTTP/2. Google recommends it for gRPC, and streaming needs it.
5. Connect the client to the service URL (or a mapped custom domain) on port 443.

Sources: [Using gRPC](https://docs.cloud.google.com/run/docs/triggering/grpc), [Use HTTP/2 for services](https://docs.cloud.google.com/run/docs/configuring/http2).

```bash
gcloud run deploy --image IMAGE_URL --use-http2
gcloud run services update SERVICE --use-http2
```

Source: [Use HTTP/2 for services](https://docs.cloud.google.com/run/docs/configuring/http2).

In service YAML, the same setting is a container port with the name `h2c` ([Use HTTP/2 for services](https://docs.cloud.google.com/run/docs/configuring/http2)).

Know how Cloud Run handles gRPC connections:

- The client connection ends at the Google load balancer, not at your instance. `KeepAlive` settings affect only the connection to the load balancer ([Using gRPC](https://docs.cloud.google.com/run/docs/triggering/grpc)).
- At scale-in, the load balancer sends `GOAWAY` to instances that shut down. The client does not see the change ([Using gRPC](https://docs.cloud.google.com/run/docs/triggering/grpc)).
- Each stream counts once against the maximum concurrent requests of an instance ([Using gRPC](https://docs.cloud.google.com/run/docs/triggering/grpc)).
- An HTTP/1 server has a 32 MiB request size limit. An HTTP/2 server has no request size limit. A client connection carries at most 100 concurrent HTTP/2 streams ([Cloud Run quotas and limits](https://docs.cloud.google.com/run/quotas)).

A private gRPC service needs an ID token in the `authorization` metadata. The audience is the service URL without a port. The token expires after 1 hour, so reuse it ([Using gRPC](https://docs.cloud.google.com/run/docs/triggering/grpc)). The docs sample is in Go:

```go
// audience: the Cloud Run service URL without a port number.
tokenSource, err := idtoken.NewTokenSource(ctx, audience)
if err != nil {
	return nil, fmt.Errorf("idtoken.NewTokenSource: %w", err)
}
token, err := tokenSource.Token()
if err != nil {
	return nil, fmt.Errorf("TokenSource.Token: %w", err)
}
// Add token to gRPC Request.
ctx = grpcMetadata.AppendToOutgoingContext(ctx, "authorization", "Bearer "+token.AccessToken)
client := pb.NewPingServiceClient(conn)
return client.Send(ctx, p)
```

Source: [Using gRPC](https://docs.cloud.google.com/run/docs/triggering/grpc).

Service-to-service identity is in [Secure service-to-service communication](note:1.2-service-to-service).

## gRPC on GKE

A GKE Ingress load balancer uses unencrypted HTTP/1.1 to the Pods by default. gRPC needs HTTP/2 between the load balancer and the Pods ([Secure traffic for GKE Ingress](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/secure-traffic-management), [External Application Load Balancer overview](https://docs.cloud.google.com/load-balancing/docs/https)).

| Option | How to get HTTP/2 to the Pods | Note |
|---|---|---|
| GKE Ingress | Annotation `cloud.google.com/app-protocols` with the value `HTTP2` for the named port | The Pods must serve TLS. The Service is `NodePort`, or `ClusterIP` with container-native load balancing |
| GKE Gateway | Field `ports[].appProtocol` on the Service: `HTTP2`, or `kubernetes.io/h2c` for cleartext | The Gateway controller does not support the deprecated `networking.gke.io/app-protocol` annotation |
| Envoy behind a passthrough Network Load Balancer | Envoy ends TLS and routes each RPC to the Pods | The load balancer passes TCP connections. Envoy balances per RPC, not per connection |
| Cloud Service Mesh proxyless gRPC | The gRPC library gets endpoints and policy from the control plane through xDS | No sidecar proxy |

Sources: [Secure traffic for GKE Ingress](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/secure-traffic-management), [Secure a Gateway](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/secure-gateway), [Using Envoy Proxy to load-balance gRPC services on GKE](https://docs.cloud.google.com/kubernetes-engine/docs/tutorials/exposing-grpc-services-on-gke-using-envoy-proxy), [Cloud Service Mesh with proxyless gRPC services overview](https://docs.cloud.google.com/service-mesh/docs/service-routing/proxyless-overview).

```yaml
apiVersion: v1
kind: Service
metadata:
  name: my-http2-service
  annotations:
    cloud.google.com/app-protocols: '{"my-port":"HTTP2"}'
spec:
  type: NodePort
  selector:
    app: my-app
  ports:
  - name: my-port
    protocol: TCP
    port: 443
    targetPort: 8443
```

Source: [Secure traffic for GKE Ingress](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/secure-traffic-management).

Clients can send gRPC to the load balancer only over TLS. The load balancer does not accept gRPC over `h2c` from clients ([External Application Load Balancer overview](https://docs.cloud.google.com/load-balancing/docs/https)). Toward a backend, the load balancer uses at most 100 concurrent streams per connection ([External Application Load Balancer overview](https://docs.cloud.google.com/load-balancing/docs/https)).

The load balancer does not show gRPC errors. If the gRPC endpoint returns an error, the load balancer logs and monitoring data report `200 OK` ([External Application Load Balancer overview](https://docs.cloud.google.com/load-balancing/docs/https)). Measure gRPC errors in the application. [Instrumenting code](note:4.3-instrumentation) shows how. [Choosing a load balancer and session affinity](note:1.1-load-balancing) compares the load balancer types.

## OpenAPI specifications

An OpenAPI document describes a REST API. From it, you can generate reference documentation, client libraries, and server stubs ([OpenAPI overview](https://docs.cloud.google.com/api-gateway/docs/openapi-overview)). API Gateway uses the OpenAPI document as its configuration, with `x-google-*` extensions for the backend, authentication, and quotas (Beta). [API management with Apigee and API Gateway](note:1.1-api-management) explains these extensions.

For a gRPC API on API Gateway, you give a service configuration with the proto descriptor. The service configuration sets authentication, the HTTP mappings for transcoding, and other settings ([gRPC overview for API Gateway](https://docs.cloud.google.com/api-gateway/docs/grpc-overview)). API Gateway supports gRPC backends only on Cloud Run, and it does not support payload compression ([gRPC overview for API Gateway](https://docs.cloud.google.com/api-gateway/docs/grpc-overview)).

Pagination, partial responses, and batch methods are in [Efficient and resilient API calls](note:4.2-efficient-api-calls).

| AWS | Google Cloud | Difference that matters |
|---|---|---|
| Amazon API Gateway | API Gateway, or Apigee | API Gateway takes OpenAPI 2.0 or 3.x documents. It sends gRPC only to Cloud Run backends |
| AWS App Mesh | Cloud Service Mesh | Proxyless gRPC clients get mesh configuration through xDS, with no sidecar |

## Exam traps

- **`PUT` for an update.** Google APIs use `PATCH` with an `update_mask`. A new resource field breaks `PUT` clients ([AIP-134](https://google.aip.dev/134)).
- **An API that copies the database tables.** AIP-121 calls this an anti-pattern ([AIP-121](https://google.aip.dev/121)).
- **A retry of a Create with no request ID.** Without a `request_id`, a retried Create is not idempotent ([AIP-155](https://google.aip.dev/155)).
- **Error handling that parses the message text.** Use the canonical code and `ErrorInfo.reason`. Messages can change without notice ([Best practices for the Compute Engine API](https://docs.cloud.google.com/compute/docs/api/best-practices), [AIP-193](https://google.aip.dev/193)).
- **An HTTP `200` from a Compute Engine change means that the work is done.** It means only that the server accepted the request. Use the operation's `wait` method ([Best practices for the Compute Engine API](https://docs.cloud.google.com/compute/docs/api/best-practices)).
- **Streaming gRPC on Cloud Run without `--use-http2`.** Streaming needs end-to-end HTTP/2 ([Using gRPC](https://docs.cloud.google.com/run/docs/triggering/grpc)).
- **TLS in the Cloud Run container for HTTP/2.** The Google frontend ends TLS. The container must accept `h2c` ([Use HTTP/2 for services](https://docs.cloud.google.com/run/docs/configuring/http2)).
- **A gRPC client that connects to port 8080 of the Cloud Run URL.** Clients connect on port 443 ([Using gRPC](https://docs.cloud.google.com/run/docs/triggering/grpc)).
- **A passthrough Network Load Balancer to spread gRPC calls across Pods.** It passes TCP connections. Envoy, an L7 proxy, balances each RPC ([Using Envoy Proxy to load-balance gRPC services on GKE](https://docs.cloud.google.com/kubernetes-engine/docs/tutorials/exposing-grpc-services-on-gke-using-envoy-proxy)).
- **Load balancer logs to count gRPC errors.** They report `200 OK` for gRPC errors ([External Application Load Balancer overview](https://docs.cloud.google.com/load-balancing/docs/https)).
- **Large JSON bodies through API Gateway transcoding.** Bodies over one megabyte can give `500 Internal Server Error` ([gRPC overview for API Gateway](https://docs.cloud.google.com/api-gateway/docs/grpc-overview)).
