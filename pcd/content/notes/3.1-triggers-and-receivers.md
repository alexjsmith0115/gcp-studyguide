## Why it matters

A Cloud Run service or function receives events as HTTP POST requests from an Eventarc trigger or a Pub/Sub push subscription. The developer chooses the route, gives the trigger an identity with the correct roles, and writes a receiver that returns the correct status code. The exam tests the IAM setup, the retry and acknowledgment defaults, and receiver code that is safe for duplicates. Many errors are silent: the trigger is active, but the events fail.

## Key points

- If a direct event exists for a source, use it instead of a Cloud Audit Logs event. Direct events have lower latency, typed formats, and no audit log cost ([Event routes](https://docs.cloud.google.com/eventarc/standard/docs/run/event-routing-options)).
- The Eventarc destination service must be in the same project as the trigger. It can be in another region, and it receives POST requests at `/` ([Create triggers with Eventarc](https://docs.cloud.google.com/run/docs/triggering/trigger-with-events)).
- Give each trigger a user-managed service account. Without one, the trigger uses the Compute Engine default service account ([Create triggers with Eventarc](https://docs.cloud.google.com/run/docs/triggering/trigger-with-events)).
- Without `roles/run.invoker`, a trigger to an authenticated service is active, but every event fails with an authentication error ([Roles and permissions for Cloud Run targets](https://docs.cloud.google.com/eventarc/docs/roles-permissions)).
- The Pub/Sub subscription behind an Eventarc trigger has a 10-second acknowledgment deadline by default. Google recommends 600 seconds ([Create triggers with Eventarc](https://docs.cloud.google.com/run/docs/triggering/trigger-with-events)).
- A trigger that you create from the Cloud Run page of the console makes one delivery attempt. gcloud, Terraform, and the Eventarc page enable retries by default ([Retry events](https://docs.cloud.google.com/eventarc/docs/retry-events)).
- A push endpoint acknowledges with HTTP 102, 200, 201, 202, or 204. Any other code, including 400, is a negative acknowledgment ([Push subscriptions](https://docs.cloud.google.com/pubsub/docs/push)).
- Cloud Run verifies the Pub/Sub OIDC token itself. You only grant `roles/run.invoker` to the push service account ([Authentication for push subscriptions](https://docs.cloud.google.com/pubsub/docs/authenticate-push-subscriptions)).
- With internal ingress, a service still receives Eventarc and Pub/Sub requests from the same project or VPC Service Controls perimeter, through the `run.app` URL ([Restrict network endpoint ingress for Cloud Run services and instances](https://docs.cloud.google.com/run/docs/securing/ingress)).

## Choose the event route

| Route | Use it when | Format at the receiver |
|---|---|---|
| Eventarc direct event | Eventarc supports a direct event for the source, for example `google.cloud.storage.object.v1.finalized` | CloudEvent with typed data |
| Eventarc Cloud Audit Logs event | No direct event exists, and the service writes audit logs | CloudEvent with the audit log entry |
| Eventarc Pub/Sub event | Your application publishes to a topic, and you want the CloudEvents format, for example for several sources | CloudEvent that contains the Pub/Sub message |
| Pub/Sub push subscription | A direct Pub/Sub integration without Eventarc | Pub/Sub JSON envelope |

Sources: [Event routes](https://docs.cloud.google.com/eventarc/standard/docs/run/event-routing-options), [CloudEvents format - HTTP protocol binding](https://docs.cloud.google.com/eventarc/docs/cloudevents).

When a service supports both audit logs and Pub/Sub, choose the source that has the data you need. For example, Cloud Build sends build status in Pub/Sub messages, and build creation in audit logs ([Event routes](https://docs.cloud.google.com/eventarc/standard/docs/run/event-routing-options)). For the product choice, see [the asynchronous integration page](note:1.1-async-events).

## Eventarc triggers for Cloud Run

Source: [Route Cloud Storage events to Cloud Run](https://docs.cloud.google.com/eventarc/standard/docs/run/route-trigger-cloud-storage).

```bash
gcloud eventarc triggers create helloworld-trigger \
    --location=us-central1 \
    --destination-run-service=helloworld-events \
    --destination-run-region=us-central1 \
    --event-filters="type=google.cloud.storage.object.v1.finalized" \
    --event-filters="bucket=my-bucket" \
    --service-account=${SERVICE_ACCOUNT_NAME}@${PROJECT_ID}.iam.gserviceaccount.com
```

Filter rules ([Create triggers with Eventarc](https://docs.cloud.google.com/run/docs/triggering/trigger-with-events), [Route Cloud Storage events to Cloud Run](https://docs.cloud.google.com/eventarc/standard/docs/run/route-trigger-cloud-storage)):

- The `type` filter is required. A Cloud Storage trigger also requires the `bucket` filter. You cannot change the `type` after you create the trigger.
- An event must match all filters. Filters use exact matches, with no wildcards or regular expressions.
- `--event-filters-path-pattern` matches resource paths, for example in the audit log `resourceName`. It is in Preview ([Understand path patterns](https://docs.cloud.google.com/eventarc/docs/path-patterns)).
- `--destination-run-path` sends events to a path other than `/`.
- A new trigger can take up to 2 minutes to start to deliver events.

### Trigger location

The source location sets the trigger location ([Understand Eventarc locations](https://docs.cloud.google.com/eventarc/docs/understand-locations)):

| Event source | Allowed trigger locations | Rule |
|---|---|---|
| Cloud Storage direct event | Single, dual, or multi-region. Not global | Must match the bucket location. The bucket must be in the trigger's project |
| Cloud Audit Logs | Single region or global. Not dual or multi-region | A global trigger matches all regions. You cannot filter by bucket |
| Pub/Sub | Single region only | Topics are global, but the trigger needs a region |

Sources: [Understand Eventarc locations](https://docs.cloud.google.com/eventarc/docs/understand-locations), [Route Cloud Storage events to Cloud Run](https://docs.cloud.google.com/eventarc/standard/docs/run/route-trigger-cloud-storage).

Identical triggers in several regions on one topic create several subscriptions. Each region then processes every message, which gives duplicates ([Understand Eventarc locations](https://docs.cloud.google.com/eventarc/docs/understand-locations)). To avoid the duplicates, the docs use one trigger in one region that points to a global external Application Load Balancer. The load balancer routes the events to the services in each region ([Understand Eventarc locations](https://docs.cloud.google.com/eventarc/docs/understand-locations)).

### The trigger service account and its roles

| Principal | Role | Why |
|---|---|---|
| The person who creates the trigger | `roles/eventarc.admin` and `roles/iam.serviceAccountUser` | Manage triggers and attach the service account |
| Trigger service account | `roles/eventarc.eventReceiver` on the project | Receive events. Not needed for direct Pub/Sub events |
| Trigger service account | `roles/run.invoker` on the service | Call an authenticated Cloud Run service |
| Cloud Storage service agent | `roles/pubsub.publisher` | Publish Cloud Storage events to the transport topic |
| Pub/Sub service agent | `roles/iam.serviceAccountTokenCreator` | Only if the agent was enabled on or before April 8, 2021 |

Sources: [Roles and permissions for Cloud Run targets](https://docs.cloud.google.com/eventarc/docs/roles-permissions), [Route Cloud Storage events to Cloud Run](https://docs.cloud.google.com/eventarc/standard/docs/run/route-trigger-cloud-storage).

Do not use the default service account. It is automatically granted the basic Editor role, which is highly privileged ([Roles and permissions for Cloud Run targets](https://docs.cloud.google.com/eventarc/docs/roles-permissions)). See [least privilege for service accounts](note:1.2-service-accounts-least-privilege).

### Retries, acknowledgment deadline, and dead-letter topics

Eventarc Standard delivers through a Pub/Sub subscription. Its ID starts with `eventarc-REGION-`. By default, retries use exponential backoff from 10 to 600 seconds, and Eventarc keeps an event for 24 hours. After that, Eventarc discards the event, unless the subscription has a dead-letter topic ([Retry events](https://docs.cloud.google.com/eventarc/docs/retry-events)).

| Setting | Default | Change it with |
|---|---|---|
| Delivery attempts | Retries on, except from the console Cloud Run page | `--max-retry-attempts=1` for one attempt (the only valid value) |
| Acknowledgment deadline | 10 seconds | `gcloud pubsub subscriptions update SUB --ack-deadline=600` |
| Retry backoff | 10 to 600 seconds | `--min-retry-delay` and `--max-retry-delay` on the subscription. Set both |
| Dead-letter topic | None | A dead-letter topic on the subscription, not on the topic |

Sources: [Retry events](https://docs.cloud.google.com/eventarc/docs/retry-events), [Create triggers with Eventarc](https://docs.cloud.google.com/run/docs/triggering/trigger-with-events).

Google recommends no retries while you develop and test, to prevent runaway retries. In production, enable retries and add a dead-letter topic ([Retry events](https://docs.cloud.google.com/eventarc/docs/retry-events)). For a function, retries are a setting of the Eventarc trigger, not of the function ([Configure event-driven function retries](https://docs.cloud.google.com/run/docs/tips/function-retries)).

Source: [Create triggers with Eventarc](https://docs.cloud.google.com/run/docs/triggering/trigger-with-events).

```bash
SUBSCRIPTION_ID=$(gcloud eventarc triggers describe "$TRIGGER_NAME" --location $LOCATION --format json | jq -r '.transport.pubsub.subscription')
gcloud pubsub subscriptions update "$SUBSCRIPTION_ID" --ack-deadline=600
```

## Pub/Sub push subscriptions to Cloud Run

Set up a push subscription to a private Cloud Run service ([Use Pub/Sub with Cloud Run tutorial](https://docs.cloud.google.com/run/docs/tutorials/pubsub)):

1. Deploy the service with `--no-allow-unauthenticated`.
2. Create a service account for the subscription identity.
3. Grant that service account `roles/run.invoker` on the service.
4. If the project was created on or before April 8, 2021, grant `roles/iam.serviceAccountTokenCreator` to the Pub/Sub service agent.
5. Create the push subscription with the service account.

Source: [Use Pub/Sub with Cloud Run tutorial](https://docs.cloud.google.com/run/docs/tutorials/pubsub).

```bash
gcloud run services add-iam-policy-binding pubsub-tutorial \
--member=serviceAccount:cloud-run-pubsub-invoker@PROJECT_ID.iam.gserviceaccount.com \
--role=roles/run.invoker

gcloud pubsub subscriptions create myRunSubscription --topic myRunTopic \
--ack-deadline=600 \
--push-endpoint=SERVICE-URL/ \
--push-auth-service-account=cloud-run-pubsub-invoker@PROJECT_ID.iam.gserviceaccount.com
```

IAM changes can take several minutes. Until then, the service logs show HTTP 403 errors ([Use Pub/Sub with Cloud Run tutorial](https://docs.cloud.google.com/run/docs/tutorials/pubsub)).

### OIDC token and audience

With authentication enabled, Pub/Sub signs a JWT for the push service account and sends it in the `Authorization` header. The token has the `email` and `aud` claims, and it can be up to an hour old ([Authentication for push subscriptions](https://docs.cloud.google.com/pubsub/docs/authenticate-push-subscriptions)).

| Item | Rule |
|---|---|
| Push service account | The subscription creator needs `iam.serviceAccounts.actAs` on it |
| Pub/Sub service agent | Needs `iam.serviceAccounts.getOpenIdToken` (Service Account Token Creator) to sign tokens |
| Audience | `--push-auth-token-audience`. Optional, a case-insensitive string that the receiver checks |
| Cloud Run receiver | Cloud Run checks the token and the invoker permission. No code needed |
| Other receivers | Verify the signature, and check that `email` and `aud` match the subscription |

Sources: [Authentication for push subscriptions](https://docs.cloud.google.com/pubsub/docs/authenticate-push-subscriptions), [Create push subscriptions](https://docs.cloud.google.com/pubsub/docs/create-push-subscription), [Use Pub/Sub with Cloud Run tutorial](https://docs.cloud.google.com/run/docs/tutorials/pubsub).

### Acknowledgment, retry, and backoff

| Response | Result |
|---|---|
| 102, 200, 201, 202, or 204 | Acknowledged |
| Any other code, for example 400 or 500 | Negative acknowledgment. Pub/Sub resends the message |
| No response before the acknowledgment deadline | Pub/Sub resends the message |

Sources: [Push subscriptions](https://docs.cloud.google.com/pubsub/docs/push), [Use Pub/Sub with Cloud Run tutorial](https://docs.cloud.google.com/run/docs/tutorials/pubsub).

Other push rules ([Push subscriptions](https://docs.cloud.google.com/pubsub/docs/push)):

- You cannot extend the acknowledgment deadline of one push message. Set the deadline on the subscription.
- Many negative acknowledgments start a push backoff: Pub/Sub pauses delivery for 100 milliseconds to 60 seconds. You cannot turn it off, and it applies to the whole subscription.
- The push backoff and the retry policy work together. The delay is the larger of the two.
- To pause delivery, change the subscription to pull. To resume, set the endpoint URL again.

Pub/Sub retries a message that always fails until the message expires. Add a dead-letter topic and a maximum number of delivery attempts. The push body then has a `deliveryAttempt` field ([Dead-letter topics](https://docs.cloud.google.com/pubsub/docs/dead-letter-topics)). For the dead-letter IAM setup, see [the messaging page](note:4.1-messaging).

## Cloud Storage notifications

Cloud Storage reports object changes in two ways:

| | Eventarc Cloud Storage trigger | Pub/Sub notifications |
|---|---|---|
| Setup | `gcloud eventarc triggers create` with `type` and `bucket` filters | `gcloud storage buckets notifications create gs://BUCKET --topic=TOPIC` |
| Receiver gets | CloudEvent, for example `google.cloud.storage.object.v1.finalized` | Pub/Sub message with attributes such as `eventType`, `bucketId`, `objectId` |
| Event names | `finalized`, `deleted`, `archived`, `metadataUpdated` | `OBJECT_FINALIZE`, `OBJECT_DELETE`, `OBJECT_ARCHIVE`, `OBJECT_METADATA_UPDATE` |
| Consumers | One destination for each trigger | Any subscription type on the topic |

Sources: [Route Cloud Storage events to Cloud Run](https://docs.cloud.google.com/eventarc/standard/docs/run/route-trigger-cloud-storage), [Configure Pub/Sub notifications for Cloud Storage](https://docs.cloud.google.com/storage/docs/reporting-changes), [Pub/Sub notifications for Cloud Storage](https://docs.cloud.google.com/storage/docs/pubsub-notifications).

Facts for both ([Pub/Sub notifications for Cloud Storage](https://docs.cloud.google.com/storage/docs/pubsub-notifications), [Configure Pub/Sub notifications for Cloud Storage](https://docs.cloud.google.com/storage/docs/reporting-changes)):

- The Cloud Storage service agent needs `roles/pubsub.publisher` on the topic.
- A bucket allows up to 10 notification configurations for each event type. An Eventarc Cloud Storage trigger uses one of them.
- One object change can give several messages with different IDs. Notifications are not in order.
- To change an object because of a notification, use generation and metageneration preconditions.
- Replacing an object gives two events: `OBJECT_FINALIZE` for the new object, and `OBJECT_ARCHIVE` or `OBJECT_DELETE` for the old one.

## Write the event receiver

### Parse a CloudEvent

The CloudEvents SDK turns the HTTP request into a CloudEvent object. It exists for C#, Go, Java, JavaScript, Python, and Ruby. The receiver must return a 2xx code; the router resends the event for any other code ([Develop event receivers](https://docs.cloud.google.com/eventarc/standard/docs/run/event-receivers)).

Source: [Develop event receivers](https://docs.cloud.google.com/eventarc/standard/docs/run/event-receivers).

```python
@app.route("/", methods=["POST"])
def index():
    # Create a CloudEvent object from the incoming request
    event = from_http(request.headers, request.data)
    # Gets the GCS bucket name from the CloudEvent
    bucket = event.get("subject")
    return (f"Detected change in Cloud Storage bucket: {bucket}", 200)
```

### Parse a push message

A wrapped push request has a JSON body. The `message.data` field is base64-encoded ([Push subscriptions](https://docs.cloud.google.com/pubsub/docs/push)).

Source: [Use Pub/Sub with Cloud Run tutorial](https://docs.cloud.google.com/run/docs/tutorials/pubsub).

```python
@app.route("/", methods=["POST"])
def index():
    envelope = request.get_json()
    if not isinstance(envelope, dict) or "message" not in envelope:
        return "Bad Request: invalid Pub/Sub message format", 400
    pubsub_message = envelope["message"]
    name = "World"
    if isinstance(pubsub_message, dict) and "data" in pubsub_message:
        name = base64.b64decode(pubsub_message["data"]).decode("utf-8").strip()
    print(f"Hello {name}!")
    return ("", 204)
```

This sample returns 400 for a bad message, so Pub/Sub retries the message. A dead-letter topic stops these retries ([Push subscriptions](https://docs.cloud.google.com/pubsub/docs/push), [Dead-letter topics](https://docs.cloud.google.com/pubsub/docs/dead-letter-topics)).

### Use the Functions Framework

Cloud Run functions (formerly Cloud Functions) require the Functions Framework. It unmarshals CloudEvents and starts a local development server for tests. An event-driven function uses `@functions_framework.cloud_event` ([Write Cloud Run functions](https://docs.cloud.google.com/run/docs/write-functions)). Every event-driven function uses an Eventarc trigger, and one function binds to only one trigger ([Cloud Run function triggers](https://docs.cloud.google.com/run/docs/function-triggers)).

With retries on, a function that raises an exception gets the event again. Set an end condition so that an event cannot loop forever ([Configure event-driven function retries](https://docs.cloud.google.com/run/docs/tips/function-retries)):

Source: [Configure event-driven function retries](https://docs.cloud.google.com/run/docs/tips/function-retries).

```python
@functions_framework.cloud_event
def avoid_infinite_retries(cloud_event):
    timestamp = cloud_event["time"]
    event_time = parser.parse(timestamp)
    event_age = (datetime.now(timezone.utc) - event_time).total_seconds()
    event_age_ms = event_age * 1000

    # Ignore events that are too old
    max_age_ms = 10000
    if event_age_ms > max_age_ms:
        print("Dropped {} (age {}ms)".format(cloud_event["id"], event_age_ms))
        return "Timeout"

    print("Processed {} (age {}ms)".format(cloud_event["id"], event_age_ms))
    return  # To retry the execution, raise an exception here
```

Use retries for transient errors, for example a timeout to a flaky endpoint. Remove permanent errors, such as bugs, with tests before you enable retries ([Configure event-driven function retries](https://docs.cloud.google.com/run/docs/tips/function-retries)). Finish all background work before the function returns, or the work might not complete ([Write Cloud Run functions](https://docs.cloud.google.com/run/docs/write-functions)).

### Acknowledge fast and handle duplicates

Process a message before you acknowledge it. Pub/Sub does not redeliver an acknowledged message, so a failure after the acknowledgment loses the work ([Best practices to subscribe to a Pub/Sub topic](https://docs.cloud.google.com/pubsub/docs/subscribe-best-practices)). To reduce redeliveries, process and acknowledge messages as quickly as possible ([Best practices to subscribe to a Pub/Sub topic](https://docs.cloud.google.com/pubsub/docs/subscribe-best-practices)).

Duplicates still occur, so make the receiver idempotent. Use the event ID as the idempotency key, and record the IDs that you processed ([Retry events](https://docs.cloud.google.com/eventarc/docs/retry-events)). Cloud Run logs show the event ID and source in the labels `run.googleapis.com/cloud_event_id` and `run.googleapis.com/cloud_event_source` ([Create triggers with Eventarc](https://docs.cloud.google.com/run/docs/triggering/trigger-with-events)).

### Timeouts compared with acknowledgment deadlines

| Limit | Value | Effect |
|---|---|---|
| Cloud Run request timeout | 5 minutes by default, up to 60 minutes | For Eventarc, push, and Cloud Scheduler requests, the caller's timeout also applies |
| Eventarc trigger subscription | 10 seconds by default, up to 600 seconds | A slower handler gets the same event again |
| Push subscription acknowledgment deadline | Up to 600 seconds. Push processing is limited to 10 minutes | A handler that answers after the deadline causes a redelivery |
| Cloud Tasks HTTP handler | 10 minutes by default, up to 30 minutes | Use it for longer HTTP work |

Sources: [Configure request timeout for services](https://docs.cloud.google.com/run/docs/configuring/request-timeout), [Create triggers with Eventarc](https://docs.cloud.google.com/run/docs/triggering/trigger-with-events), [Subscription properties](https://docs.cloud.google.com/pubsub/docs/subscription-properties), [Choosing Pub/Sub or Cloud Tasks](https://docs.cloud.google.com/pubsub/docs/choosing-pubsub-or-cloud-tasks), [Push subscriptions](https://docs.cloud.google.com/pubsub/docs/push).

A long Cloud Run timeout does not help a push receiver: Pub/Sub resends the message when its deadline expires. A pull subscriber can extend its deadline, so long processing fits pull better ([Choose a subscription type](https://docs.cloud.google.com/pubsub/docs/subscriber)).

## Secure the receiver

1. Deploy the receiver with authentication required (`--no-allow-unauthenticated`). Pub/Sub sends an OIDC token, and Cloud Run checks it ([Use Pub/Sub with Cloud Run tutorial](https://docs.cloud.google.com/run/docs/tutorials/pubsub)). An Eventarc trigger uses its service account as the identity ([Create triggers with Eventarc](https://docs.cloud.google.com/run/docs/triggering/trigger-with-events)).
2. Grant `roles/run.invoker` on the service only to the trigger or push service account ([Roles and permissions for Cloud Run targets](https://docs.cloud.google.com/eventarc/docs/roles-permissions)).
3. Set ingress to `internal` with `gcloud run services update SERVICE --ingress internal`. Eventarc, Pub/Sub, Cloud Scheduler, Cloud Tasks, and Workflows in the same project or perimeter still reach the `run.app` URL ([Restrict network endpoint ingress for Cloud Run services and instances](https://docs.cloud.google.com/run/docs/securing/ingress)).
4. With VPC Service Controls, a new push subscription can only target a Cloud Run `run.app` URL or a Workflows execution. Custom domains do not work ([Create push subscriptions](https://docs.cloud.google.com/pubsub/docs/create-push-subscription)).

Service-to-service authentication in general is on [the service-to-service page](note:1.2-service-to-service).

## Exam traps

- **A trigger that is active but delivers nothing.** The trigger service account lacks `roles/run.invoker` on the service ([Roles and permissions for Cloud Run targets](https://docs.cloud.google.com/eventarc/docs/roles-permissions)).
- **Duplicate executions from a slow function.** The trigger subscription keeps its 10-second deadline. Set 600 seconds ([Create triggers with Eventarc](https://docs.cloud.google.com/run/docs/triggering/trigger-with-events)).
- **"Retries are on, because the default is on."** A trigger from the console Cloud Run page makes one attempt ([Retry events](https://docs.cloud.google.com/eventarc/docs/retry-events)).
- **HTTP 400 to drop a bad push message.** Any code except 102, 200, 201, 202, and 204 is a negative acknowledgment. Use a dead-letter topic ([Push subscriptions](https://docs.cloud.google.com/pubsub/docs/push)).
- **`--allow-unauthenticated` so that Pub/Sub can reach the service.** Keep the service private and grant `roles/run.invoker` to the push service account ([Use Pub/Sub with Cloud Run tutorial](https://docs.cloud.google.com/run/docs/tutorials/pubsub)).
- **Token validation code in a Cloud Run receiver.** Cloud Run checks the Pub/Sub token itself ([Use Pub/Sub with Cloud Run tutorial](https://docs.cloud.google.com/run/docs/tutorials/pubsub)).
- **A Cloud Audit Logs trigger for a Cloud Storage bucket.** Use the direct event, which can filter by bucket ([Event routes](https://docs.cloud.google.com/eventarc/standard/docs/run/event-routing-options), [Understand Eventarc locations](https://docs.cloud.google.com/eventarc/docs/understand-locations)).
- **A Cloud Storage trigger in another location than the bucket, or a global one.** The locations must match ([Understand Eventarc locations](https://docs.cloud.google.com/eventarc/docs/understand-locations)).
- **A destination service in another project.** The service must be in the trigger's project ([Create triggers with Eventarc](https://docs.cloud.google.com/run/docs/triggering/trigger-with-events)).
- **A changed event type on a trigger.** You cannot change the `type` filter. Create a new trigger ([Create triggers with Eventarc](https://docs.cloud.google.com/run/docs/triggering/trigger-with-events)).
- **A 30-minute request timeout for a push receiver.** The push deadline is at most 600 seconds ([Subscription properties](https://docs.cloud.google.com/pubsub/docs/subscription-properties)).
