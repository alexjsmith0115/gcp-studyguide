## Why it matters

A developer decides where each password, API key, and encryption key lives, how the app reads it, and how it changes. Secret Manager stores secret values, and Cloud Key Management Service (Cloud KMS) keeps encryption keys that no one can export. Workload Identity Federation removes the need for service account keys. The exam tests which service fits each credential, how Cloud Run and GKE read secrets, how rotation works, and which IAM role each identity needs.

## Key points

- A secret is a global resource that holds metadata and secret versions. Each version stores the secret data. You can pin versions to workloads, add aliases, and disable or destroy versions ([Secret Manager overview](https://docs.cloud.google.com/secret-manager/docs/overview)).
- Grant the Secret Manager Secret Accessor role (`roles/secretmanager.secretAccessor`) on one secret, not on the project. The Owner role can read secret values. The Editor and Viewer roles cannot ([Access control with IAM](https://docs.cloud.google.com/secret-manager/docs/access-control)).
- In production, reference a version number, not the `latest` alias. A bad new version behind `latest` can cause a service-wide outage ([Secret Manager best practices](https://docs.cloud.google.com/secret-manager/docs/best-practices), [About rotation schedules](https://docs.cloud.google.com/secret-manager/docs/rotation-recommendations)).
- A rotation schedule only sends a `SECRET_ROTATE` message to Pub/Sub. Your own subscriber creates the new credential and adds the new version ([Create rotation schedules in Secret Manager](https://docs.cloud.google.com/secret-manager/docs/secret-rotation)).
- Cloud Run reads a secret in an environment variable once, when the instance starts. Cloud Run reads a secret in a mounted volume each time the app reads the file ([Configure secrets for services](https://docs.cloud.google.com/run/docs/configuring/services/secrets)).
- On GKE, the Secret Manager add-on mounts secrets as files in Pods. It authenticates with Workload Identity Federation for GKE (formerly GKE Workload Identity) ([Use Secret Manager add-on with Google Kubernetes Engine](https://docs.cloud.google.com/secret-manager/docs/secret-manager-managed-csi-component), [Make IAM for GKE easier to use with Workload Identity Federation](https://cloud.google.com/blog/products/identity-security/make-iam-for-gke-easier-to-use-with-workload-identity-federation)).
- Cloud KMS key rotation creates a new key version. It does not re-encrypt existing data, and it does not disable old versions ([Key rotation](https://docs.cloud.google.com/kms/docs/key-rotation)). Automatic rotation makes the new version primary ([REST Resource: projects.locations.keyRings.cryptoKeys](https://docs.cloud.google.com/kms/docs/reference/rest/v1/projects.locations.keyRings.cryptoKeys)). A version that you create with the API is not primary until you set it ([Rotate a key](https://docs.cloud.google.com/kms/docs/rotate-key)).
- In envelope encryption, a local data encryption key (DEK) encrypts the data, and a key encryption key (KEK) in Cloud KMS wraps the DEK. The KEK never leaves Cloud KMS ([Envelope encryption](https://docs.cloud.google.com/kms/docs/envelope-encryption)).
- With customer-managed encryption keys (CMEK), the service agent of the Google Cloud service uses your key. The user who creates the resource does not need a role on the key ([Customer-managed encryption keys (CMEK)](https://docs.cloud.google.com/kms/docs/cmek)).
- Workload Identity Federation gives workloads on AWS, Azure, on premises, or in a deployment pipeline access to Google Cloud without a service account key ([Workload Identity Federation](https://docs.cloud.google.com/iam/docs/workload-identity-federation)).

## Where each credential belongs

| Need | Use | Why |
|---|---|---|
| A password, API key, or certificate that the app reads | Secret Manager | Versions, IAM on each secret, and rotation schedules |
| Encrypt app data with a key that no one can read | Cloud KMS with envelope encryption | No one can view or export the key material |
| Control the key that protects data in a Google Cloud service | CMEK, created by you or by Cloud KMS Autokey | You control the location, rotation, access, and destruction of the key |
| Code on Google Cloud calls Google APIs | The attached service account, through the metadata server | No secret to store |
| Code on AWS, Azure, on premises, or in a pipeline calls Google APIs | Workload Identity Federation | No service account key |
| App settings that are not secret, such as feature flags | Parameter Manager, an extension of Secret Manager | Parameters can reference secrets |

Sources: [Secret Manager overview](https://docs.cloud.google.com/secret-manager/docs/overview), [Secret Manager best practices](https://docs.cloud.google.com/secret-manager/docs/best-practices), [Customer-managed encryption keys (CMEK)](https://docs.cloud.google.com/kms/docs/cmek), [Workload Identity Federation](https://docs.cloud.google.com/iam/docs/workload-identity-federation).

## Secret Manager: versions and access

A version holds an immutable payload. Versions are numbered in order, and the `latest` alias points to the most recently added version ([About rotation schedules](https://docs.cloud.google.com/secret-manager/docs/rotation-recommendations)). Secret Manager encrypts all data at rest with AES-256 and in transit with TLS. You can add CMEK ([Secret Manager overview](https://docs.cloud.google.com/secret-manager/docs/overview)).

| Action on a version | Result | Can you undo it? |
|---|---|---|
| Disable | No one can access the version | Yes. Enable the version again |
| Destroy | Secret Manager discards the secret data | No. By default, destruction is immediate and permanent |
| Destroy, with delayed destruction set on the secret | The version is disabled and scheduled for destruction | Yes, during the delay |

Sources: [Disable a secret version](https://docs.cloud.google.com/secret-manager/docs/disable-secret-version), [Destroy a secret version](https://docs.cloud.google.com/secret-manager/docs/destroy-secret-version), [Delay destruction of secret versions](https://docs.cloud.google.com/secret-manager/docs/delay-destruction-of-secret-versions).

Disable a version before you destroy it. Then wait, for example a week, to find dependencies that still use it. Do not set an expiration on production secrets, because expiration deletes the secret irreversibly ([Secret Manager best practices](https://docs.cloud.google.com/secret-manager/docs/best-practices)).

| Role | What it allows | Use it for |
|---|---|---|
| Secret Manager Secret Accessor (`roles/secretmanager.secretAccessor`) | Read the payload | The identity of the app that uses the secret |
| Secret Manager Secret Version Adder (`roles/secretmanager.secretVersionAdder`) | Add versions. It cannot read them | A rotation process that only writes new values |
| Secret Manager Secret Version Manager (`roles/secretmanager.secretVersionManager`) | Add, enable, disable, and destroy versions. It cannot read them | Version lifecycle management |

Sources: [Access control with IAM](https://docs.cloud.google.com/secret-manager/docs/access-control), [About rotation schedules](https://docs.cloud.google.com/secret-manager/docs/rotation-recommendations).

- Grant roles at the lowest level, the secret. When one project holds secrets for many services, use bindings on each secret or IAM Conditions ([Secret Manager best practices](https://docs.cloud.google.com/secret-manager/docs/best-practices)).
- On Compute Engine and GKE, the instance or node needs the `cloud-platform` OAuth scope ([Access control with IAM](https://docs.cloud.google.com/secret-manager/docs/access-control)).
- To see who read a secret, enable Data Access audit logs for `AccessSecretVersion` ([Secret Manager best practices](https://docs.cloud.google.com/secret-manager/docs/best-practices)). Event notifications do not help, because `Get`, `List`, and `Access` calls do not publish messages ([Set up notifications on a secret](https://docs.cloud.google.com/secret-manager/docs/event-notifications)).

Google recommends that code calls the Secret Manager API through a client library. Secrets in files can leak through directory traversal attacks. Secrets in environment variables can leak through debug endpoints or dependencies that log the environment. Serverless integrations are an accepted exception ([Secret Manager best practices](https://docs.cloud.google.com/secret-manager/docs/best-practices)).

```python
from google.cloud import secretmanager
import google_crc32c


def access_secret_version(project_id: str, secret_id: str, version_id: str) -> str:
    """version_id is a version number, such as "5", or an alias."""
    client = secretmanager.SecretManagerServiceClient()
    name = f"projects/{project_id}/secrets/{secret_id}/versions/{version_id}"
    response = client.access_secret_version(request={"name": name})

    # Verify the payload checksum.
    crc32c = google_crc32c.Checksum()
    crc32c.update(response.payload.data)
    if response.payload.data_crc32c != int(crc32c.hexdigest(), 16):
        raise ValueError("Data corruption detected.")

    # Do not print or log the payload in production.
    return response.payload.data.decode("UTF-8")
```

Source: [Access a secret version](https://docs.cloud.google.com/secret-manager/docs/access-secret-version) (adapted to return the payload).

The client library uses Application Default Credentials, so the code contains no credential. See [Authenticating to Google Cloud](note:1.2-authenticating-to-google-cloud).

## Pinned versions, rotation, and notifications

How the app binds to a version decides how a new version reaches production:

| Approach | How it works | Risk |
|---|---|---|
| Resolve at release (recommended) | At rotation time, resolve `latest` to a full version name. Store it, for example in Git, and deploy it with the app | Low. You roll out gradually and roll back with your release process |
| Resolve at startup | The app reads `latest` when it starts | After a bad version, new instances fail to start when instances restart or scale up |
| Resolve continuously | The app polls `latest` and uses a new value at once | An immediate, service-wide outage, because there is no gradual adoption |

Source: [About rotation schedules](https://docs.cloud.google.com/secret-manager/docs/rotation-recommendations).

**Rotation schedules.** You set `next_rotation_time`, an optional `rotation_period`, and at least one Pub/Sub topic on the secret. At `next_rotation_time`, Secret Manager sends `SECRET_ROTATE` to the topics. Secret Manager retries a failed delivery for up to seven days ([Create rotation schedules in Secret Manager](https://docs.cloud.google.com/secret-manager/docs/secret-rotation)).

```bash
gcloud secrets create SECRET_ID \
  --replication-policy "automatic" \
  --next-rotation-time="NEXT_ROTATION_TIME" \
  --rotation-period="ROTATION_PERIOD" \
  --topics="FULL_TOPIC_NAME"
```

Source: [Create rotation schedules in Secret Manager](https://docs.cloud.google.com/secret-manager/docs/secret-rotation).

**The rotation process.** In the docs example, a Cloud Run service receives the message and does these steps ([About rotation schedules](https://docs.cloud.google.com/secret-manager/docs/rotation-recommendations)):

1. Create a new credential in the external system, for example the database. Keep the current credential valid.
2. Add the new credential as a new secret version, for example with `roles/secretmanager.secretVersionAdder`. Do not use the default service account.
3. Roll out the new version to the workloads.
4. Disable the old version and make sure that nothing breaks. Then remove the old credential from the external system and destroy the old version.

The service must be reentrant, with retries and limits on concurrency and instances. Labels can save the rotation state, and etags detect concurrent changes ([About rotation schedules](https://docs.cloud.google.com/secret-manager/docs/rotation-recommendations)).

**Cloud SQL credentials.** Automatic rotation of Cloud SQL secrets (Preview) generates the password, updates the instance, and adds the version for you. It works only for regional secrets of the type `Cloud SQL DB credentials` ([Automatic rotation of Cloud SQL secrets](https://docs.cloud.google.com/secret-manager/regional-secrets/autorotation-of-cloudsql-secrets-rs)).

**Notifications.** Secret Manager publishes a message to the Pub/Sub topics of the secret for each change, for example `SECRET_VERSION_ADD`, `SECRET_VERSION_DISABLE`, and `SECRET_ROTATE`. Create the Secret Manager service agent with `gcloud beta services identity create`, and grant it `roles/pubsub.publisher` on each topic ([Set up notifications on a secret](https://docs.cloud.google.com/secret-manager/docs/event-notifications)).

## Replication and regional secrets

You choose the storage locations of a secret when you create it. You cannot change them later. Replication is synchronous and strongly consistent ([Choose a secret replication policy](https://docs.cloud.google.com/secret-manager/docs/choosing-replication)).

| | Automatic replication | User-managed replication | Regional secret |
|---|---|---|---|
| Where the data is stored | Multiple regions that Google chooses | The regions that you choose | One location that you choose |
| Endpoint | Global | Global | Regional, for example `secretmanager.LOCATION.rep.googleapis.com` |
| Access from other regions | Yes | Yes | No |
| Cloud Run support | Yes | Yes | No |
| Use it when | Default. Most workloads | Replicas must be in specific regions | Strict data residency rules |

Sources: [Choose a secret replication policy](https://docs.cloud.google.com/secret-manager/docs/choosing-replication), [Compare global and regional service](https://docs.cloud.google.com/secret-manager/regional-secrets/global-regionalized-service-comparison), [Create a regional secret](https://docs.cloud.google.com/secret-manager/regional-secrets/create-regional-secret), [Configure secrets for services](https://docs.cloud.google.com/run/docs/configuring/services/secrets).

- Automatic replication is billed as one location, and it needs `global` allowed by the `gcp.resourceLocations` constraint. User-managed replication is billed for each location ([Choose a secret replication policy](https://docs.cloud.google.com/secret-manager/docs/choosing-replication)).
- With user-managed replication, an outage in one selected region makes create and update calls fail ([Choose a secret replication policy](https://docs.cloud.google.com/secret-manager/docs/choosing-replication)).
- A regional secret keeps its data in its location at rest, in use, and in transit ([About data residency and regional secrets](https://docs.cloud.google.com/secret-manager/regional-secrets/data-residency)). Since June 2026, the location can be a multi-region, such as `us` or `eu` ([Secret Manager release notes](https://docs.cloud.google.com/secret-manager/docs/release-notes)).

## Using secrets in Cloud Run

| | Environment variable | Mounted volume |
|---|---|---|
| When Cloud Run reads the value | Once, before the instance starts | Each time the app reads the file |
| Version to reference | A pinned version number | `latest` works, and rotation reaches running instances |
| If Cloud Run cannot read the secret | The instance does not start | The file read fails at runtime |
| `gcloud` flag | `--update-secrets=ENV_VAR_NAME=SECRET_NAME:VERSION` | `--update-secrets=PATH=SECRET_NAME:VERSION` |

Source: [Configure secrets for services](https://docs.cloud.google.com/run/docs/configuring/services/secrets).

A volume with `latest` gets a new version without a redeploy. But this is the "resolve continuously" approach: a bad version reaches all instances at once ([Configure secrets for services](https://docs.cloud.google.com/run/docs/configuring/services/secrets), [About rotation schedules](https://docs.cloud.google.com/secret-manager/docs/rotation-recommendations)).

```bash
# Mount the secret as a file. PATH is the mount path and the file name.
gcloud run deploy SERVICE --image IMAGE_URL \
  --update-secrets=PATH=SECRET_NAME:VERSION

# Expose the secret as an environment variable.
gcloud run deploy SERVICE --image IMAGE_URL \
  --update-secrets=ENV_VAR_NAME=SECRET_NAME:VERSION
```

Source: [Configure secrets for services](https://docs.cloud.google.com/run/docs/configuring/services/secrets).

Rules for Cloud Run ([Configure secrets for services](https://docs.cloud.google.com/run/docs/configuring/services/secrets)):

- The service identity needs `roles/secretmanager.secretAccessor`. Cloud Run checks this permission when you deploy.
- For a secret in another project, use `projects/PROJECT_NUMBER/secrets/SECRET_NAME`.
- A mount hides the files that already exist in the mount directory. Mount into a new directory.
- Cloud Run does not support regional secrets.

For the full deploy flow, see [Deploying to Cloud Run from source code](note:3.1-deploy-from-source).

## Using secrets in GKE

| Option | How the Pod gets the secret | Notes |
|---|---|---|
| Secret Manager add-on (recommended) | A CSI volume mounts secrets as in-memory files | Needs Workload Identity Federation for GKE. Supports global and regional secrets. Optional auto-rotation, at least every 120 seconds |
| Secret synchronization | GKE copies secrets into Kubernetes Secret objects | For apps that already read Kubernetes Secrets. Google says that the add-on is more secure |
| Client library | The app calls the Secret Manager API | The general recommendation for code |

Sources: [Use Secret Manager add-on with Google Kubernetes Engine](https://docs.cloud.google.com/secret-manager/docs/secret-manager-managed-csi-component), [Synchronize secrets to Kubernetes Secrets](https://docs.cloud.google.com/secret-manager/docs/sync-k8-secrets), [Secret Manager best practices](https://docs.cloud.google.com/secret-manager/docs/best-practices).

A `SecretProviderClass` lists the secrets to mount and their file names:

```yaml
apiVersion: secrets-store.csi.x-k8s.io/v1
kind: SecretProviderClass
metadata:
  name: SECRET_PROVIDER_CLASS_NAME
spec:
  provider: gke
  parameters:
    secrets: |
      - resourceName: "projects/PROJECT_ID/secrets/SECRET_NAME/versions/SECRET_VERSION"
        path: "FILENAME.txt"
```

Source: [Use Secret Manager add-on with Google Kubernetes Engine](https://docs.cloud.google.com/secret-manager/docs/secret-manager-managed-csi-component).

The Pod uses a `csi` volume with the driver `secrets-store-gke.csi.k8s.io` and this class. Grant `roles/secretmanager.secretAccessor` on the secret to the principal identifier of the Pod's Kubernetes ServiceAccount ([Use Secret Manager add-on with Google Kubernetes Engine](https://docs.cloud.google.com/secret-manager/docs/secret-manager-managed-csi-component)).

**Kubernetes Secrets at rest.** GKE encrypts Secrets at rest by default. Application-layer secrets encryption adds envelope encryption with a KEK that you manage in Cloud KMS. The Kubernetes Engine Service Agent needs access to the key. Keep the key in the same location as the cluster ([Encrypt secrets at the application layer](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/encrypting-secrets)).

## Cloud KMS: key rings, keys, and versions

| Resource | What it is | Rules |
|---|---|---|
| Key ring | A group of keys in one location | You cannot move it to another location. No cost |
| Key | A named object with key versions and metadata | You set IAM here. The purpose and protection level are fixed at creation |
| Key version | The key material, numbered from 1 | No one can view or export it. It costs money in every state except destroyed |

Source: [Cloud KMS resources](https://docs.cloud.google.com/kms/docs/resource-hierarchy).

- A symmetric key has a primary version, which Cloud KMS uses to encrypt by default. Access to a key gives access to all its enabled versions ([Cloud KMS resources](https://docs.cloud.google.com/kms/docs/resource-hierarchy)).
- To encrypt or decrypt, grant `roles/cloudkms.cryptoKeyEncrypter`, `roles/cloudkms.cryptoKeyDecrypter`, or `roles/cloudkms.cryptoKeyEncrypterDecrypter` on the key. The Cloud KMS Admin role (`roles/cloudkms.admin`) cannot encrypt or decrypt ([Encrypting and decrypting data with a symmetric key](https://docs.cloud.google.com/kms/docs/encrypt-decrypt)).
- A destroyed version is first scheduled for destruction, by default for 30 days. You can restore it during that time ([Key version states](https://docs.cloud.google.com/kms/docs/key-states)).
- Destruction removes the key material. Deletion removes a destroyed version, an empty key, or an empty key ring from all lists ([Delete Cloud KMS resources](https://docs.cloud.google.com/kms/docs/delete-kms-resources)). Deletion of keys and key rings became GA in 2026 ([Cloud KMS release notes](https://docs.cloud.google.com/kms/docs/release-notes)). The Cloud KMS resources page still says that you cannot delete a key ring ([Cloud KMS resources](https://docs.cloud.google.com/kms/docs/resource-hierarchy)).

**Automatic rotation.** Google recommends automatic rotation on a schedule for symmetric keys, for example every 90 days. Cloud KMS does not rotate asymmetric keys automatically ([Key rotation](https://docs.cloud.google.com/kms/docs/key-rotation)).
```bash
gcloud kms keys create KEY_NAME \
    --keyring KEY_RING \
    --location LOCATION \
    --purpose "encryption" \
    --rotation-period ROTATION_PERIOD \
    --next-rotation-time NEXT_ROTATION_TIME
```

Source: [Rotate a key](https://docs.cloud.google.com/kms/docs/rotate-key).

Existing data stays encrypted with the old versions, and those versions stay enabled and billed. To retire an old version, re-encrypt the data, then destroy the version. If you destroy a version that is still in use, you can lose data permanently ([Key rotation](https://docs.cloud.google.com/kms/docs/key-rotation)).

## Envelope encryption and CMEK

Cloud KMS `Encrypt` and `Decrypt` accept at most 64 KiB of data, because Cloud KMS is designed to manage KEKs. For larger data, use envelope encryption ([Envelope encryption](https://docs.cloud.google.com/kms/docs/envelope-encryption)):

1. Generate a new DEK locally for each write. Use AES-256 in Galois Counter Mode (GCM).
2. Encrypt the data locally with the DEK.
3. Call Cloud KMS to encrypt (wrap) the DEK with the KEK.
4. Store the encrypted data and the wrapped DEK. Never store a plaintext DEK.

To decrypt, Cloud KMS unwraps the DEK, and your code decrypts the data locally ([Envelope encryption](https://docs.cloud.google.com/kms/docs/envelope-encryption)). The Tink library does all these steps and returns one ciphertext with the encrypted data and the wrapped DEK ([Client-side encryption with Tink and Cloud KMS](https://docs.cloud.google.com/kms/docs/client-side-encryption)).

**CMEK.** A service with a CMEK integration does server-side envelope encryption with a key that you control ([Customer-managed encryption keys (CMEK)](https://docs.cloud.google.com/kms/docs/cmek)).

| | Google default encryption | CMEK |
|---|---|---|
| Key owner | Google | You |
| Who encrypts and decrypts | The service | The service agent, with your key |
| Control of key rotation | No | Yes |
| Logs of access to the key | No | Yes |

Source: [Customer-managed encryption keys (CMEK)](https://docs.cloud.google.com/kms/docs/cmek).

- Grant the service agent `roles/cloudkms.cryptoKeyEncrypterDecrypter` on the key. The principal that creates or views the resource does not need this role ([Customer-managed encryption keys (CMEK)](https://docs.cloud.google.com/kms/docs/cmek)).
- If the key is disabled or destroyed, requests for the resource fail. Destroying the key makes the data unrecoverable (crypto-shredding) ([Customer-managed encryption keys (CMEK)](https://docs.cloud.google.com/kms/docs/cmek), [Delete Cloud KMS resources](https://docs.cloud.google.com/kms/docs/delete-kms-resources)).
- Cloud KMS Autokey creates key rings and keys when you create a resource, and it grants the service agent its roles. Google recommends Autokey when its keys meet your requirements. Its modes are dedicated-project key storage (formerly centralized key management) and same-project key storage (formerly delegated key management) ([Customer-managed encryption keys (CMEK)](https://docs.cloud.google.com/kms/docs/cmek)).
- Organization policy constraints can require CMEK ([Customer-managed encryption keys (CMEK)](https://docs.cloud.google.com/kms/docs/cmek)). See [Data retention and organization policies](note:1.2-retention-and-org-policy).

## Removing service account keys

A leaked service account key works without 2-step verification, so attackers can value it more than a leaked password ([Best practices for managing service account keys](https://docs.cloud.google.com/iam/docs/best-practices-for-managing-service-account-keys)). Use the alternatives. [Authenticating to Google Cloud](note:1.2-authenticating-to-google-cloud) gives the setup details.

- **On Google Cloud.** Attach a service account. Client libraries get credentials from the metadata server. On GKE, use Workload Identity Federation for GKE ([Secret Manager best practices](https://docs.cloud.google.com/secret-manager/docs/best-practices)).
- **Outside Google Cloud.** Use Workload Identity Federation. The workload exchanges its own credential, for example from AWS, Azure, GitHub, or an OIDC or SAML 2.0 provider, for a short-lived token ([Workload Identity Federation](https://docs.cloud.google.com/iam/docs/workload-identity-federation)).
- **Deployment pipelines.** GitHub, GitLab SaaS, and HCP Terraform use one issuer for all customers. Add an attribute condition that accepts only tokens from your organization ([Configure Workload Identity Federation with deployment pipelines](https://docs.cloud.google.com/iam/docs/workload-identity-federation-with-deployment-pipelines)).

If you must use a key:

- Do not store it in Secret Manager. An app that can read Secret Manager already has an identity that Google Cloud recognizes. It can use that identity instead ([Best practices for managing service account keys](https://docs.cloud.google.com/iam/docs/best-practices-for-managing-service-account-keys)).
- Block key creation with an organization policy. Allow exceptions only for projects that cannot use an alternative ([Best practices for managing service account keys](https://docs.cloud.google.com/iam/docs/best-practices-for-managing-service-account-keys)).
- Set the constraint `iam.serviceAccountKeyExposureResponse` to `DISABLE_KEY`. Google Cloud then disables leaked keys that it detects, but it does not guarantee detection ([Best practices for managing service account keys](https://docs.cloud.google.com/iam/docs/best-practices-for-managing-service-account-keys), [Organization policy constraints](https://docs.cloud.google.com/organization-policy/reference/org-policy-constraints)).

## Never put secrets in code, images, or plain environment variables

| Place | Risk | Do this instead |
|---|---|---|
| Source code and Git history | Attackers scan public repositories. A private repository can become public. Git keeps a permanent record | Secret Manager. If you committed a key, delete the key in IAM. Removing it from the repository is not enough |
| Binaries and container images | Anyone who can access the binary can extract an embedded key | Keep credentials out of the artifact. Artifact Analysis can detect some secrets in images (Preview) |
| Plain environment variables | Debug endpoints and dependencies that log the environment can leak them | A Secret Manager reference in Cloud Run, or a client library call |
| Desktop and mobile apps | Users can extract a key from the app binary | Users sign in with their own credentials, for example through the OAuth consent flow |

Sources: [Best practices for managing service account keys](https://docs.cloud.google.com/iam/docs/best-practices-for-managing-service-account-keys), [Secret Manager best practices](https://docs.cloud.google.com/secret-manager/docs/best-practices), [Scan for secrets](https://docs.cloud.google.com/artifact-analysis/docs/secret-scanning), [Configure environment variables for services](https://docs.cloud.google.com/run/docs/configuring/services/environment-variables).

In Cloud Build, declare each secret in `availableSecrets` and list it in `secretEnv` of the steps that use it. Steps can refer to secrets only in `args` ([Use secrets from Secret Manager](https://docs.cloud.google.com/build/docs/securing-builds/use-secrets)). See [Integration tests in Cloud Build](note:2.3-integration-tests-cloud-build).

|---|---|---|

## Exam traps

- **A service account key in Secret Manager for an app on Google Cloud.** Use the identity of the app instead ([Best practices for managing service account keys](https://docs.cloud.google.com/iam/docs/best-practices-for-managing-service-account-keys)).
- **A rotation schedule that "rotates" the secret.** It only sends `SECRET_ROTATE`. Your subscriber adds the version ([Create rotation schedules in Secret Manager](https://docs.cloud.google.com/secret-manager/docs/secret-rotation)).
- **`latest` in a Cloud Run environment variable to get new versions.** Cloud Run reads environment variables only at instance startup ([Configure secrets for services](https://docs.cloud.google.com/run/docs/configuring/services/secrets)).
- **A regional secret for a Cloud Run service.** Cloud Run does not support regional secrets ([Configure secrets for services](https://docs.cloud.google.com/run/docs/configuring/services/secrets)).
- **User-managed replication for strict data residency.** The secret stays accessible from other regions. Use a regional secret ([Compare global and regional service](https://docs.cloud.google.com/secret-manager/regional-secrets/global-regionalized-service-comparison)).
- **The Editor role so that the app can read a secret.** Editor cannot read payloads. Grant Secret Accessor on the secret ([Access control with IAM](https://docs.cloud.google.com/secret-manager/docs/access-control)).
- **Pub/Sub notifications to audit secret reads.** Access calls do not publish messages. Use Data Access audit logs ([Set up notifications on a secret](https://docs.cloud.google.com/secret-manager/docs/event-notifications)).
- **`roles/cloudkms.admin` for an app that encrypts data.** The admin role cannot encrypt or decrypt ([Encrypting and decrypting data with a symmetric key](https://docs.cloud.google.com/kms/docs/encrypt-decrypt)).
- **The Encrypter/Decrypter role for the user who creates a CMEK resource.** The service agent needs it ([Customer-managed encryption keys (CMEK)](https://docs.cloud.google.com/kms/docs/cmek)).
- **Key rotation to re-encrypt data or retire old versions.** Rotation does neither ([Key rotation](https://docs.cloud.google.com/kms/docs/key-rotation)).
- **A large file sent to the Cloud KMS `Encrypt` method.** The limit is 64 KiB. Use envelope encryption ([Envelope encryption](https://docs.cloud.google.com/kms/docs/envelope-encryption)).
