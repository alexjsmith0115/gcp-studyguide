## Why it matters

You set the CPU, memory, concurrency, and scaling limits of each workload, and these settings decide its latency, its stability, and its bill. The exam tests Cloud Run billing settings, minimum and maximum instances, GKE requests and limits, Autopilot request rules, and Compute Engine discounts. Many questions give a cost or performance symptom and ask which one setting to change.

## Key points

- **Cloud Run sizes.** An instance gets 1 vCPU and 512 MiB of memory by default. The maximum is 8 vCPU and 32 GiB, and each CPU value allows a fixed memory range. A GPU service is an exception: an NVIDIA RTX PRO 6000 GPU needs at least 20 CPU and 80 GiB ([Configure CPU limits for services](https://docs.cloud.google.com/run/docs/configuring/services/cpu), [Configure memory limits for services](https://docs.cloud.google.com/run/docs/configuring/services/memory-limits), [GPU support for services](https://docs.cloud.google.com/run/docs/configuring/services/gpu)).
- **Concurrency.** One Cloud Run instance takes up to 1,000 requests at the same time. The default is 80 times the vCPU count (gcloud CLI or Terraform, at creation) or 80 (console). Google says that you should use the default ([Maximum concurrent requests for services](https://docs.cloud.google.com/run/docs/about-concurrency)).
- **Two billing settings.** Request-based billing (formerly "CPU only allocated during request processing") is the default. Instance-based billing (formerly "CPU always allocated") charges for the whole instance lifetime and gives CPU outside requests ([Billing settings for services](https://docs.cloud.google.com/run/docs/configuring/billing-settings)).
- **Minimum instances** keep instances warm to reduce cold starts, and you pay for them while they are idle. Google recommends a committed use discount for this predictable charge ([Set minimum instances for services](https://docs.cloud.google.com/run/docs/configuring/min-instances)).
- **Maximum instances** limit cost and the number of connections to a backing service, such as a database. The default is 100 instances per revision ([Set maximum instances for services](https://docs.cloud.google.com/run/docs/configuring/max-instances)).
- **Startup CPU boost** gives extra CPU during startup and for 10 seconds after, and you pay for the boosted CPU ([Configure CPU limits for services](https://docs.cloud.google.com/run/docs/configuring/services/cpu)).
- **GKE requests and limits.** Set the memory request equal to the memory limit. Set the CPU request to the minimum that the app needs, with no CPU limit ([Best practices for running cost-optimized Kubernetes applications on GKE](https://docs.cloud.google.com/architecture/best-practices-for-running-cost-effective-kubernetes-applications-on-gke)).
- **Autopilot bills Pod requests.** Autopilot raises a request below the minimum and rejects a request above the maximum. Set requests explicitly, because the defaults might not fit ([Resource requests in Autopilot](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/autopilot-resource-requests), [Google Kubernetes Engine pricing](https://cloud.google.com/kubernetes-engine/pricing)).
- **Compute Engine machine types.** The general-purpose family has the best price-performance ratio, and the E2 series has the lowest cost. Custom machine types cost 5% more than equal predefined types ([Machine families resource and comparison guide](https://docs.cloud.google.com/compute/docs/machine-resource)).
- **Spot VMs** (the latest version of preemptible VMs) cost up to 91% less. Compute Engine can preempt them at any time, and no SLA covers them ([Spot VMs](https://docs.cloud.google.com/compute/docs/instances/spot)).
- **Committed use discounts (CUDs).** Compute flexible commitments cover Compute Engine, GKE, and Cloud Run. Flexible Savings Plans give spend-based discounts across products, for example for generative AI models. Resource-based CUDs are for Compute Engine only, in one region ([Committed use discounts](https://docs.cloud.google.com/docs/cuds)).
- **Labels for cost.** Google Cloud forwards labels to the billing system, so you can break down charges by label and query them in the BigQuery billing export ([Labels overview](https://docs.cloud.google.com/resource-manager/docs/labels-overview)).

## Cloud Run: CPU and memory

Each vCPU value allows a range of memory:

| vCPU | Memory |
|---|---|
| 0.08 | Up to 512 MiB |
| 0.5 | Up to 1 GiB |
| 1 | Up to 4 GiB |
| 2 | Up to 8 GiB |
| 4 | 2 to 16 GiB |
| 6 | 4 to 24 GiB |
| 8 | 4 to 32 GiB |

Sources: [Configure CPU limits for services](https://docs.cloud.google.com/run/docs/configuring/services/cpu), [Configure memory limits for services](https://docs.cloud.google.com/run/docs/configuring/services/memory-limits).

- **Less than 1 vCPU** needs a concurrency of 1, request-based billing, and the first generation execution environment ([Configure CPU limits for services](https://docs.cloud.google.com/run/docs/configuring/services/cpu)).
- **More than 1 vCPU:** check the threading model of the app first. A single-threaded app might fully use only one vCPU ([Configure CPU limits for services](https://docs.cloud.google.com/run/docs/configuring/services/cpu)).
- **Memory holds three things:** the executable, the memory that the process allocates, and the files that the app writes to the file system. The image size does not change the memory that the instance gets ([Configure memory limits for services](https://docs.cloud.google.com/run/docs/configuring/services/memory-limits)).
- **Over the limit.** Cloud Run terminates an instance that exceeds its memory limit, and all its requests in progress fail with HTTP 500 ([Container runtime contract](https://docs.cloud.google.com/run/docs/container-contract)).
- **Right size from metrics.** Start from a baseline, load test, and watch the CPU and memory metrics in Cloud Monitoring. Reduce the CPU if utilization stays low under peak load. Increase it if latency is high ([Configure CPU limits for services](https://docs.cloud.google.com/run/docs/configuring/services/cpu), [Configure memory limits for services](https://docs.cloud.google.com/run/docs/configuring/services/memory-limits)).

## Cloud Run: concurrency

Concurrency is the maximum number of requests that one instance processes at the same time. A higher value lets fewer instances serve the same load, so the cost goes down, but the code must handle parallel requests safely ([Maximum concurrent requests for services](https://docs.cloud.google.com/run/docs/about-concurrency)).

| Situation | Concurrency setting |
|---|---|
| Most apps | Keep the default |
| The code cannot process parallel requests, or it uses global state that two requests cannot share | 1 |
| Each request uses most of the CPU or memory of the instance | 1 |
| A single-threaded app on several vCPUs (chosen for memory) does not scale on CPU | Lower the value, so that request count drives scaling |
| A deployment from source code | Start low, for example 8, then increase |
| Python 3.8 or later | Set a `THREADS` environment variable equal to the concurrency |

Source: [Maximum concurrent requests for services](https://docs.cloud.google.com/run/docs/about-concurrency).

A concurrency of 1 hurts scaling, because a traffic spike needs many new instances ([Maximum concurrent requests for services](https://docs.cloud.google.com/run/docs/about-concurrency)). The single-threaded case is a "vCPU hotspot". One vCPU is busy and the others are idle, so the average CPU stays low and CPU-based scaling does not start.

## Cloud Run: billing settings

| | Request-based billing (default) | Instance-based billing |
|---|---|---|
| Former name | CPU only allocated during request processing | CPU always allocated |
| CPU | Only during request processing | For the whole instance lifetime |
| Charges | While instances process requests, start, and shut down, plus a per-request fee | For the whole instance lifetime, with no per-request fee |
| Traffic pattern | Sporadic, bursty, or spiky | Steady, slowly varying |
| Background work after the response | Not supported: no CPU outside requests | Supported, for example OpenTelemetry agents or goroutines |
| gcloud flag | `--cpu-throttling` | `--no-cpu-throttling` |

Sources: [Billing settings for services](https://docs.cloud.google.com/run/docs/configuring/billing-settings), [What is Cloud Run](https://docs.cloud.google.com/run/docs/overview/what-is-cloud-run).

More rules about billing settings:

- Recommender looks at the last month of traffic. It recommends instance-based billing when that costs less ([Billing settings for services](https://docs.cloud.google.com/run/docs/configuring/billing-settings)).
- All Cloud Run jobs use instance-based billing ([Billing settings for services](https://docs.cloud.google.com/run/docs/configuring/billing-settings)). GPU services also require instance-based billing ([GPU support for services](https://docs.cloud.google.com/run/docs/configuring/services/gpu)).
- Instance-based billing does not stop autoscaling. An instance never stays idle for more than 15 minutes after a request unless minimum instances keep it ([Billing settings for services](https://docs.cloud.google.com/run/docs/configuring/billing-settings)).
- For asynchronous work, also consider Cloud Tasks, which retries failed tasks ([Billing settings for services](https://docs.cloud.google.com/run/docs/configuring/billing-settings)). See [Orchestrating services with Workflows, Cloud Tasks, and Cloud Scheduler](note:1.1-orchestration).
- Budget spend caps (Preview) pause all Cloud Run workloads in the project when spend reaches the cap. Services then return `5xx` errors ([Billing settings for services](https://docs.cloud.google.com/run/docs/configuring/billing-settings)).

## Cloud Run: minimum and maximum instances

| | Minimum instances | Maximum instances |
|---|---|---|
| Purpose | Fewer cold starts and lower latency | A cost limit, and a limit on connections to a backend |
| Default | None; the service scales to zero | 100 per revision |
| Cost | Idle instances bill at a lower rate (request-based) or the full rate (instance-based) | A cost-safety limit |
| Google guidance | At least 3 for high availability; buy a CUD for the predictable charge | Start with 3 to protect the budget; set it at service level |
| Guarantee | Best effort; instances can restart at any time | Cloud Run can exceed it for a short time during spikes |

Sources: [Set minimum instances for services](https://docs.cloud.google.com/run/docs/configuring/min-instances), [Set maximum instances for services](https://docs.cloud.google.com/run/docs/configuring/max-instances), [What is Cloud Run](https://docs.cloud.google.com/run/docs/overview/what-is-cloud-run).

Set both limits at the service level. Service-level values apply at once, with no new revision. Revision-level minimum instances start every revision that is in the traffic split or has a traffic tag, and you pay for those idle instances. Revision-level scaling is available only for services that had it configured before ([Set minimum instances for services](https://docs.cloud.google.com/run/docs/configuring/min-instances)). For tags and traffic splits, see [Traffic splitting: gradual rollouts, rollbacks, and A/B tests](note:1.1-traffic-splitting).

This deploy command sets the size, the concurrency, the scaling limits, the startup boost, and cost labels in one step:

```bash
gcloud run deploy SERVICE \
  --image IMAGE_URL \
  --cpu 2 \
  --memory 4Gi \
  --concurrency 80 \
  --min 1 \
  --max 10 \
  --cpu-boost \
  --labels team=checkout,env=prod
```

Source: [gcloud run deploy](https://docs.cloud.google.com/sdk/gcloud/reference/run/deploy).

## Cloud Run: startup CPU boost

Startup CPU boost adds CPU while the instance starts and for 10 seconds after it starts. Cloud Run charges for the boosted CPU for that time ([Configure CPU limits for services](https://docs.cloud.google.com/run/docs/configuring/services/cpu)). The gcloud CLI turns it on by default for a new service when you do not set the flag ([gcloud run deploy](https://docs.cloud.google.com/sdk/gcloud/reference/run/deploy)).

| CPU limit | Boosted CPU |
|---|---|
| 0 to 1 | 2 |
| 2 | 4 |
| 4, 6, or 8 | 8 |

Source: [Configure CPU limits for services](https://docs.cloud.google.com/run/docs/configuring/services/cpu).

Other ways to cut startup time are minimum instances, fewer dependencies, global variables that later requests reuse, and lazy initialization of rarely used objects ([General development tips](https://docs.cloud.google.com/run/docs/tips/general)).

## GKE Standard: requests and limits

The scheduler places a Pod by its requests. A limit caps what the container can use. Google's cost guide gives one pattern ([Best practices for running cost-optimized Kubernetes applications on GKE](https://docs.cloud.google.com/architecture/best-practices-for-running-cost-effective-kubernetes-applications-on-gke)):

- **Memory:** request equal to limit. Memory cannot be compressed, so when a node runs out of memory, Kubernetes must take Pods down. The equal values prevent this.
- **CPU:** request the minimum that the app needs for its SLOs, and set no CPU limit. When CPU is short, Kubernetes throttles Pods down to their requests.

```yaml
resources:
  requests:
    memory: "128Mi"
    cpu: "250m"
  limits:
    memory: "128Mi"
```

Source: [Best practices for running cost-optimized Kubernetes applications on GKE](https://docs.cloud.google.com/architecture/best-practices-for-running-cost-effective-kubernetes-applications-on-gke).

To find the right values, run the Vertical Pod Autoscaler (VPA) in recommendation mode in a production-like environment. To find containers with no requests or limits, look at the insights of subtype `REQUEST_OR_LIMIT_NOT_SET` ([Best practices for running cost-optimized Kubernetes applications on GKE](https://docs.cloud.google.com/architecture/best-practices-for-running-cost-effective-kubernetes-applications-on-gke)). The Horizontal Pod Autoscaler also uses the requests; see [Scaling on GKE: Horizontal Pod Autoscaler attributes and metrics](note:3.2-autoscaling).

## GKE Autopilot: resource requests and compute classes

Autopilot bills general-purpose Pods by their resource requests. Pods that select specific hardware, such as GPUs or a machine series, use node-based billing plus an Autopilot premium ([Google Kubernetes Engine pricing](https://cloud.google.com/kubernetes-engine/pricing)). So on Autopilot, the request is the price.

| What you set | What Autopilot does |
|---|---|
| No requests | Applies defaults: 0.5 vCPU and 2 GiB for the general-purpose platform, Balanced, and Scale-Out |
| A request below the minimum | Raises it to the minimum |
| A request above the maximum | Rejects the workload with an error |
| A CPU:memory ratio outside the allowed range | Raises the smaller resource |
| A limit and no request | Sets the request equal to the limit |
| A request lower than the limit | Lets the Pod burst up to the limit, if the cluster supports bursting |

Source: [Resource requests in Autopilot](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/autopilot-resource-requests).

The general-purpose platform allows a CPU:memory ratio between 1:1 and 1:6.5, up to 30 vCPU and 110 GiB. Google recommends that you set requests for each container, and in most cases set limits equal to requests ([Resource requests in Autopilot](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/autopilot-resource-requests)).

A compute class selects other hardware. `Balanced` gives more CPU and memory than the default platform. `Scale-Out` turns off simultaneous multithreading, so one vCPU is one physical core, on Arm or x86. You can also define custom ComputeClasses ([About Balanced and Scale-Out ComputeClasses in Autopilot clusters](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/balanced-scale-out-autopilot)). Select one class with a node selector:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: helloweb
spec:
  selector:
    matchLabels:
      app: hello
  template:
    metadata:
      labels:
        app: hello
    spec:
      nodeSelector:
        cloud.google.com/compute-class: Scale-Out
      containers:
      - name: hello-app
        image: us-docker.pkg.dev/google-samples/containers/gke/hello-app:1.0
        resources:
          requests:
            cpu: "250m"
            memory: "1Gi"
```

Source: [About Balanced and Scale-Out ComputeClasses in Autopilot clusters](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/balanced-scale-out-autopilot).

For fault-tolerant work, request Spot Pods with the node selector `cloud.google.com/gke-spot: "true"`. GKE can evict Spot Pods at any time, with a grace period of at most 15 seconds ([Run fault-tolerant workloads at lower costs in Spot Pods](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/autopilot-spot-pods)).

## Compute Engine: machine types and discounts

| Machine family | Use for |
|---|---|
| General-purpose | Most workloads; best price-performance ratio |
| Compute-optimized | HPC and compute-intensive work; high performance per core |
| Memory-optimized | Memory-intensive work; up to 12 TB of memory |
| Storage-optimized | Low core use with high storage density |
| Network-optimized | High network bandwidth and packet processing |
| Accelerator-optimized | GPU or TPU workloads, such as ML and HPC |

Source: [Machine families resource and comparison guide](https://docs.cloud.google.com/compute/docs/machine-resource).

- **Custom machine types** match vCPU and memory to the workload, so you avoid paying for unused resources. They cost 5% more than equal predefined types. Extended memory gives more memory per vCPU, up to the series limit ([Machine families resource and comparison guide](https://docs.cloud.google.com/compute/docs/machine-resource), [Optimize resource usage](https://docs.cloud.google.com/architecture/framework/cost-optimization/optimize-resource-usage)).
- **Shared-core types** (`e2-micro`, `e2-small`, `e2-medium`) share a physical core and fit small apps ([Machine families resource and comparison guide](https://docs.cloud.google.com/compute/docs/machine-resource)).
- **Rightsizing recommendations** use the last 8 days of metrics and are free. They are not available for GKE nodes or VMs with GPUs or TPUs. They use 60-second averages, so they miss short spikes ([Apply machine type recommendations to VM instances](https://docs.cloud.google.com/compute/docs/instances/apply-machine-type-recommendations-for-instances)).

| Discount | How you get it | Applies to | Watch for |
|---|---|---|---|
| Spot VMs | Choose the Spot provisioning model | Compute Engine VMs and GKE nodes | Preemption at any time, a shutdown period of up to 30 seconds, no SLA |
| Compute flexible commitment (spend-based CUD) | Commit to an hourly spend | Compute Engine, GKE, and Cloud Run | Spend above the commitment bills at on-demand rates |
| Flexible Savings Plan (spend-based) | Commit to a monthly spend | Eligible workloads across products, for example generative AI models | Measured over a monthly window; spend above the commitment bills at on-demand rates |
| Resource-based CUD | Commit to vCPU, memory, GPUs, or Local SSD in a region | Compute Engine only | Region-specific |
| Sustained use discount (SUD) | Automatic, for use above 25% of the month | N1, N2, N2D, C2, M1, M2 VMs from Compute Engine or GKE | Not for usage that a CUD covers; up to 30% |

Sources: [Spot VMs](https://docs.cloud.google.com/compute/docs/instances/spot), [Committed use discounts](https://docs.cloud.google.com/docs/cuds), [Sustained use discounts](https://docs.cloud.google.com/compute/docs/sustained-use-discounts), [Best practices for running cost-optimized Kubernetes applications on GKE](https://docs.cloud.google.com/architecture/best-practices-for-running-cost-effective-kubernetes-applications-on-gke).

For a GKE commitment, look at your minimum usage, for example at night, and commit to that amount ([Best practices for running cost-optimized Kubernetes applications on GKE](https://docs.cloud.google.com/architecture/best-practices-for-running-cost-effective-kubernetes-applications-on-gke)). The service-specific CUDs for Cloud Run and GKE Autopilot are no longer for sale; buy Compute flexible commitments instead ([Committed use discounts](https://docs.cloud.google.com/docs/cuds)).

On GKE, use Spot VMs for batch or fault-tolerant jobs only. Keep a node pool without Spot VMs, so that a node is always available ([Best practices for running cost-optimized Kubernetes applications on GKE](https://docs.cloud.google.com/architecture/best-practices-for-running-cost-effective-kubernetes-applications-on-gke)).

## Cost attribution with labels

A label is a key-value pair on a resource. Billing reports and the BigQuery billing export carry the labels, so you can group charges by team, service, or environment. A resource can have up to 64 labels, and keys use lowercase letters. Do not put sensitive data in labels. Labels cannot set conditions on policies; tags can ([Labels overview](https://docs.cloud.google.com/resource-manager/docs/labels-overview)).

| Platform | How labels reach the bill |
|---|---|
| Cloud Run | Billing and Logging receive only labels in `spec.template.metadata.labels` (YAML) or under `template` (Terraform). The console and the gcloud CLI set both places. A label change creates a new revision |
| GKE Standard | GKE cost allocation adds the cluster name, the namespace, and Pod labels to the detailed billing export. It uses resource requests, not actual use, and does not backfill old data |
| Compute Engine and Cloud Storage | Labels on the VM or bucket, for example `costcenter`, `service`, and `environment` |

Sources: [Configure labels for services](https://docs.cloud.google.com/run/docs/configuring/services/labels), [Get key spending insights for your GKE resource allocation and cluster costs](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/cost-allocations), [Labels overview](https://docs.cloud.google.com/resource-manager/docs/labels-overview).

Google recommends GKE cost allocation instead of the older GKE usage metering ([Understanding cluster resource usage](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/cluster-usage-metering)).

## Other cost levers

- **Region.** Prices differ by region. Choose the lowest-cost region that still gives acceptable latency, and include the cost to move data between regions ([Best practices for running cost-optimized Kubernetes applications on GKE](https://docs.cloud.google.com/architecture/best-practices-for-running-cost-effective-kubernetes-applications-on-gke)). See [Regions, zones, latency, and replication for failover](note:1.1-regions-and-replication).
- **Same-region traffic.** Cloud Run has no charge for data transfer to Google Cloud resources in the same region ([Cloud Run pricing](https://cloud.google.com/run/pricing)).
- **Workload type.** Google suggests Spot VMs for non-critical work and Cloud Run or Cloud Run functions for event-driven work. In development, limit VM run time or stop VMs that you do not use ([Optimize resource usage](https://docs.cloud.google.com/architecture/framework/cost-optimization/optimize-resource-usage)).
- **Guardrails.** Organization policies can limit the locations and products that teams use ([Optimize resource usage](https://docs.cloud.google.com/architecture/framework/cost-optimization/optimize-resource-usage)).

## Exam traps

- **Minimum instances to protect a database.** Minimum instances keep instances warm. Maximum instances limit connections to a backend ([Set maximum instances for services](https://docs.cloud.google.com/run/docs/configuring/max-instances)).
- **Background threads with request-based billing.** CPU is allocated only during requests. Use instance-based billing for work after the response ([Billing settings for services](https://docs.cloud.google.com/run/docs/configuring/billing-settings)).
- **Concurrency 1 "to be safe".** It needs many more instances and slows scaling. Use it only when requests cannot share an instance ([Maximum concurrent requests for services](https://docs.cloud.google.com/run/docs/about-concurrency)).
- **More vCPUs for a single-threaded app.** It cannot use them, and CPU-based scaling can stall. Lower the concurrency instead ([Maximum concurrent requests for services](https://docs.cloud.google.com/run/docs/about-concurrency)).
- **Revision-level minimum instances with traffic tags.** Every tagged revision keeps idle instances that you pay for. Use service-level minimum instances ([Set minimum instances for services](https://docs.cloud.google.com/run/docs/configuring/min-instances)).
- **A memory limit above the memory request on GKE.** Kubernetes can remove the Pod when the node runs out of memory. Set the request equal to the limit ([Best practices for running cost-optimized Kubernetes applications on GKE](https://docs.cloud.google.com/architecture/best-practices-for-running-cost-effective-kubernetes-applications-on-gke)).
- **A tiny request on Autopilot to save money.** Autopilot raises it to the minimum and bills the raised value ([Resource requests in Autopilot](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/autopilot-resource-requests), [Google Kubernetes Engine pricing](https://cloud.google.com/kubernetes-engine/pricing)).
- **Labels only in the service `metadata`.** Billing does not see them. Put them in `spec.template.metadata.labels` ([Configure labels for services](https://docs.cloud.google.com/run/docs/configuring/services/labels)).
- **Spot VMs for a stateful serving tier.** Spot VMs can stop at any time and have no SLA ([Spot VMs](https://docs.cloud.google.com/compute/docs/instances/spot)).
- **Sustained use discounts on top of a CUD.** SUDs do not apply to usage that a CUD covers, and E2 is not an eligible series ([Sustained use discounts](https://docs.cloud.google.com/compute/docs/sustained-use-discounts)).
- **Rightsizing recommendations for GKE nodes.** Compute Engine does not make them for GKE VMs. Use VPA recommendations instead ([Apply machine type recommendations to VM instances](https://docs.cloud.google.com/compute/docs/instances/apply-machine-type-recommendations-for-instances), [Best practices for running cost-optimized Kubernetes applications on GKE](https://docs.cloud.google.com/architecture/best-practices-for-running-cost-effective-kubernetes-applications-on-gke)).
