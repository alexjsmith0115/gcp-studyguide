## Why it matters

Most Pub/Sub code is short, but its settings decide throughput, cost, and how many duplicates you get. The developer sets batching and flow control on the publisher, handles the publish result, and chooses how subscribers acknowledge, extend, and filter messages. The exam tests the client library patterns that Google recommends and the defaults that cause redeliveries and lost messages.

## Key points

- The Pub/Sub client libraries publish asynchronously. `publish()` returns a future that resolves to the message ID ([Publish messages to topics](https://docs.cloud.google.com/pubsub/docs/publisher)).
- The client libraries batch messages by default. In Python, the defaults are 100 messages, 1 MB, or 10 ms, whichever comes first ([Batch messaging](https://docs.cloud.google.com/pubsub/docs/batch-messaging)).
- A message is at most 10 MB of data, with up to 100 attributes ([Pub/Sub quotas and limits](https://docs.cloud.google.com/pubsub/quotas)).
- A publish retry after a lost response can give two identical messages with different message IDs ([Retry requests](https://docs.cloud.google.com/pubsub/docs/retry-requests)).
- For most subscribers, Google recommends the high-level client library with the StreamingPull API and asynchronous processing ([Pull subscriptions](https://docs.cloud.google.com/pubsub/docs/pull)).
- The high-level client libraries extend the acknowledgment deadline of an unacknowledged message, by default for up to an hour ([Extend ack time with lease management](https://docs.cloud.google.com/pubsub/docs/lease-management)).
- Process a message before you acknowledge it. Pub/Sub does not redeliver an acknowledged message ([Best practices to subscribe to a Pub/Sub topic](https://docs.cloud.google.com/pubsub/docs/subscribe-best-practices)).
- A subscription filter uses message attributes, not data. You cannot change the filter after you create the subscription ([Filter messages from a subscription](https://docs.cloud.google.com/pubsub/docs/subscription-message-filter)).
- A schema on a topic makes Pub/Sub reject a message that does not conform. Pub/Sub supports Apache Avro and Protocol Buffer schemas ([Schema overview](https://docs.cloud.google.com/pubsub/docs/schemas)).
- Seek to a snapshot or to a time replays or purges the messages of a subscription ([Replay and purge messages with seek](https://docs.cloud.google.com/pubsub/docs/replay-overview)).

## Publish messages

A message must have at least one of these: data, an ordering key, or attributes. Pub/Sub adds a message ID and a publish time. The publisher needs `roles/pubsub.publisher` on the topic ([Publish messages to topics](https://docs.cloud.google.com/pubsub/docs/publisher)).

| Limit | Value |
|---|---|
| Message data | 10 MB |
| Attributes for each message | 100 |
| Attribute key size | 256 bytes |
| Attribute value size | 1,024 bytes |
| One publish request | 10 MB or 1,000 messages |
| Ordering key throughput | 1 MBps for each key |

Sources: [Pub/Sub quotas and limits](https://docs.cloud.google.com/pubsub/quotas), [Batch messaging](https://docs.cloud.google.com/pubsub/docs/batch-messaging), [Order messages](https://docs.cloud.google.com/pubsub/docs/ordering).

In Python, attributes are keyword arguments to `publish()`. Data must be a bytestring ([Publish messages to topics](https://docs.cloud.google.com/pubsub/docs/publisher)).

Source: [Publish messages to topics](https://docs.cloud.google.com/pubsub/docs/publisher).

```python
from google.cloud import pubsub_v1

publisher = pubsub_v1.PublisherClient()
topic_path = publisher.topic_path(project_id, topic_id)

data = "Message number 1".encode("utf-8")
# Add two attributes, origin and username, to the message
future = publisher.publish(
    topic_path, data, origin="python-sample", username="gcp"
)
print(future.result())
```

Handle each future asynchronously. For a failed publish, Google gives these options ([Best practices to publish to a Pub/Sub topic](https://docs.cloud.google.com/pubsub/docs/publish-best-practices)):

- Log the error, if your use case does not need every message.
- Retry after a transient error, such as `DEADLINE_EXCEEDED`.
- Store the message to publish it later, after an error that needs a person to act, such as `NOT_FOUND` or `PERMISSION_DENIED`.
- Send the error back to the upstream service that gave you the message.

Before you publish, attach a subscription or enable topic retention. Otherwise Pub/Sub does not keep the messages ([Best practices to publish to a Pub/Sub topic](https://docs.cloud.google.com/pubsub/docs/publish-best-practices)).

### Batching

Batching trades latency for throughput and cost. The client sends a batch when it reaches any one threshold ([Best practices to publish to a Pub/Sub topic](https://docs.cloud.google.com/pubsub/docs/publish-best-practices)).

Source: [Batch messaging](https://docs.cloud.google.com/pubsub/docs/batch-messaging).

```python
batch_settings = pubsub_v1.types.BatchSettings(
    max_messages=10,  # default 100
    max_bytes=1024,  # default 1 MB
    max_latency=1,  # default 10 ms
)
publisher = pubsub_v1.PublisherClient(batch_settings)
```

Set `max_messages` to 1 to turn off batching. For cost, Pub/Sub counts each request as at least 1,000 bytes, even when the messages are smaller ([Batch messaging](https://docs.cloud.google.com/pubsub/docs/batch-messaging)).

### Publisher flow control

A publisher can create requests faster than it can send them. The requests then wait in memory until they fail with `DEADLINE_EXCEEDED`. Publisher flow control limits the outstanding messages and bytes ([Flow control](https://docs.cloud.google.com/pubsub/docs/flow-control-messages)).

Source: [Flow control](https://docs.cloud.google.com/pubsub/docs/flow-control-messages).

```python
from google.cloud.pubsub_v1.types import (
    LimitExceededBehavior,
    PublisherOptions,
    PublishFlowControl,
)

flow_control_settings = PublishFlowControl(
    message_limit=100,  # 100 messages
    byte_limit=10 * 1024 * 1024,  # 10 MiB
    limit_exceeded_behavior=LimitExceededBehavior.BLOCK,
)
publisher = pubsub_v1.PublisherClient(
    publisher_options=PublisherOptions(flow_control=flow_control_settings)
)
```

Flow control is for temporary spikes. For a lasting overload, add publisher client instances ([Flow control](https://docs.cloud.google.com/pubsub/docs/flow-control-messages)).

### Retry settings

The client library retries transient errors itself. You can change the initial timeout, the retry delay, and the total timeout. In Python, you pass an `api_core.retry.Retry` object to `publish()`. The library defaults are an initial delay of 0.1 seconds, a maximum delay of 60 seconds, and a total deadline of 60 seconds ([Retry requests](https://docs.cloud.google.com/pubsub/docs/retry-requests)). Change the retry settings only if the defaults are not sufficient ([Best practices to publish to a Pub/Sub topic](https://docs.cloud.google.com/pubsub/docs/publish-best-practices)).

A retry can make a duplicate. When the publish succeeds but the response does not arrive, the library publishes again, and the subscriber gets two identical messages with different message IDs ([Retry requests](https://docs.cloud.google.com/pubsub/docs/retry-requests)). Subscribers must handle this, even with exactly-once delivery ([Exactly-once delivery](https://docs.cloud.google.com/pubsub/docs/exactly-once-delivery)).

### Ordering keys

To publish in order, enable message ordering on the publisher. Use a locational endpoint, so that all messages for a key go to one region ([Publish messages to topics](https://docs.cloud.google.com/pubsub/docs/publisher), [Best practices to publish to a Pub/Sub topic](https://docs.cloud.google.com/pubsub/docs/publish-best-practices)). If a publish with an ordering key fails, the library fails the later messages for that key. Call `resume_publish` to continue ([Retry requests](https://docs.cloud.google.com/pubsub/docs/retry-requests)).

Source: [Retry requests](https://docs.cloud.google.com/pubsub/docs/retry-requests).

```python
publisher_options = pubsub_v1.types.PublisherOptions(enable_message_ordering=True)
# Sending messages to the same region ensures they are received in order
client_options = {"api_endpoint": "us-east1-pubsub.googleapis.com:443"}
publisher = pubsub_v1.PublisherClient(
    publisher_options=publisher_options, client_options=client_options
)
topic_path = publisher.topic_path(project_id, topic_id)

future = publisher.publish(topic_path, data=data, ordering_key=ordering_key)
try:
    print(future.result())
except RuntimeError:
    # Resume publish on an ordering key that has had unrecoverable errors.
    publisher.resume_publish(topic_path, ordering_key)
```

For a message with an ordering key, the client library retries the request repeatedly, independent of the retry settings ([Best practices to publish to a Pub/Sub topic](https://docs.cloud.google.com/pubsub/docs/publish-best-practices)). Retries can still change the order that the subscriber sees, for example 1, 1, 2, 3 ([Retry requests](https://docs.cloud.google.com/pubsub/docs/retry-requests)). The subscription must also have message ordering enabled ([Order messages](https://docs.cloud.google.com/pubsub/docs/ordering)).

## Subscribe to messages

### Push or pull

| Choose | When |
|---|---|
| Pull with the high-level client library (StreamingPull) | Most cases. Large volume, high efficiency, or no public HTTPS endpoint |
| Push | The subscriber cannot import the client library or make outgoing requests, or one endpoint serves many subscriptions |
| Unary Pull API | You need strict control of the message count or client memory, or the subscriber is a proxy |

Sources: [Pull subscriptions](https://docs.cloud.google.com/pubsub/docs/pull), [Best practices to subscribe to a Pub/Sub topic](https://docs.cloud.google.com/pubsub/docs/subscribe-best-practices), [Choose a subscription type](https://docs.cloud.google.com/pubsub/docs/subscriber).

With the unary Pull API, an empty response does not mean that the subscription has no messages ([Pull subscriptions](https://docs.cloud.google.com/pubsub/docs/pull)). The low-level library does not give you lease management, ordered delivery, exactly-once delivery, or flow control; you must write them yourself ([Pull subscriptions](https://docs.cloud.google.com/pubsub/docs/pull)). Push receivers on Cloud Run are on [the triggers and receivers page](note:3.1-triggers-and-receivers).

### StreamingPull with flow control

Subscriber flow control limits the outstanding messages and bytes. When the client reaches a limit, it stops pulling until it acknowledges or negatively acknowledges messages ([Handle transient spikes with flow control](https://docs.cloud.google.com/pubsub/docs/flow-control)).

Source: [Handle transient spikes with flow control](https://docs.cloud.google.com/pubsub/docs/flow-control).

```python
from concurrent.futures import TimeoutError
from google.cloud import pubsub_v1

subscriber = pubsub_v1.SubscriberClient()
subscription_path = subscriber.subscription_path(project_id, subscription_id)

def callback(message: pubsub_v1.subscriber.message.Message) -> None:
    print(f"Received {message.data!r}.")
    message.ack()

# Limit the subscriber to only have ten outstanding messages at a time.
flow_control = pubsub_v1.types.FlowControl(max_messages=10)

streaming_pull_future = subscriber.subscribe(
    subscription_path, callback=callback, flow_control=flow_control
)
with subscriber:
    try:
        streaming_pull_future.result(timeout=timeout)
    except TimeoutError:
        streaming_pull_future.cancel()  # Trigger the shutdown.
        streaming_pull_future.result()  # Block until the shutdown is complete.
```

For a lasting overload, add subscriber instances ([Handle transient spikes with flow control](https://docs.cloud.google.com/pubsub/docs/flow-control)). On Cloud Run, a worker pool can run a pull subscriber for an always-on workload ([What is Cloud Run](https://docs.cloud.google.com/run/docs/overview/what-is-cloud-run)). See [the platform choice page](note:1.1-platform-choice).

### Acknowledgment deadlines and lease management

| Setting | Where | Value |
|---|---|---|
| Acknowledgment deadline | Subscription | 10 seconds by default, 10 to 600 seconds |
| Maximum extension period | Client library | Up to an hour by default |
| Length of each extension | Client library (Python, Go, Java) | The 99th percentile of acknowledgment delay |
| Minimum and maximum extension | Client library | Limits for each `modifyAckDeadline` request |

Sources: [Subscription properties](https://docs.cloud.google.com/pubsub/docs/subscription-properties), [Extend ack time with lease management](https://docs.cloud.google.com/pubsub/docs/lease-management).

A low subscription deadline gives more duplicates. A high deadline delays the redelivery of failed messages. Lease management avoids this choice, because the client extends the deadline for each message ([Extend ack time with lease management](https://docs.cloud.google.com/pubsub/docs/lease-management)). Pub/Sub does not guarantee the deadline unless exactly-once delivery is enabled ([Extend ack time with lease management](https://docs.cloud.google.com/pubsub/docs/lease-management)).

A negative acknowledgment (nack) makes Pub/Sub redeliver the message immediately, unless a retry policy sets a delay. A `modifyAckDeadline` request with a deadline of 0 is also a nack ([Overview of the Pub/Sub service](https://docs.cloud.google.com/pubsub/docs/pubsub-basics)). Nack a message that the subscriber cannot process now, so that Pub/Sub does not lose it ([Overview of the Pub/Sub service](https://docs.cloud.google.com/pubsub/docs/pubsub-basics)).

If many messages always come back, the subscribers are overloaded or acknowledge too late. For pull, tune flow control or lease management. For push, increase the acknowledgment deadline ([Best practices to subscribe to a Pub/Sub topic](https://docs.cloud.google.com/pubsub/docs/subscribe-best-practices)).

### Exactly-once delivery

Source: [Exactly-once delivery](https://docs.cloud.google.com/pubsub/docs/exactly-once-delivery).

```bash
gcloud pubsub subscriptions create SUBSCRIPTION_ID \
  --topic=TOPIC_ID \
  --enable-exactly-once-delivery
```

Rules for the subscriber code ([Exactly-once delivery](https://docs.cloud.google.com/pubsub/docs/exactly-once-delivery)):

- Use the "acknowledgment with response" interface of the client library. A successful acknowledgment means no redelivery. Without this interface, failed acknowledgments cause silent redeliveries.
- Set a high minimum lease extension. The maximum is 600 seconds.
- An acknowledgment with an expired ID fails with `INVALID_ARGUMENT`.
- If you do not set an acknowledgment deadline when you create the subscription, the default is 60 seconds, not 10.
- For high throughput, use StreamingPull.

Exactly-once delivery works only for pull subscriptions and only inside one region ([Exactly-once delivery](https://docs.cloud.google.com/pubsub/docs/exactly-once-delivery)). For the trade-offs, see [the asynchronous integration page](note:1.1-async-events).

### Filters

Source: [Filter messages from a subscription](https://docs.cloud.google.com/pubsub/docs/subscription-message-filter).

```bash
gcloud pubsub subscriptions create SUBSCRIPTION_ID \
  --topic=TOPIC_ID \
  --message-filter='FILTER'
```

A filter is an expression on attributes, for example `attributes.name = "com"`, `attributes:name`, or `hasPrefix(attributes.name, "co")`, combined with `AND`, `OR`, and `NOT` ([Filter messages from a subscription](https://docs.cloud.google.com/pubsub/docs/subscription-message-filter)). Pub/Sub automatically acknowledges the messages that do not match. You pay no outbound fees for them, but you pay delivery fees ([Filter messages from a subscription](https://docs.cloud.google.com/pubsub/docs/subscription-message-filter)).

To change a filter ([Filter messages from a subscription](https://docs.cloud.google.com/pubsub/docs/subscription-message-filter)):

1. Take a snapshot of the old subscription.
2. Create a new subscription with the new filter.
3. Seek the new subscription to the snapshot.
4. Move the subscribers to the new subscription, and delete the old one.

## Dead-letter topics and retry policies

Source: [Dead-letter topics](https://docs.cloud.google.com/pubsub/docs/dead-letter-topics).

```bash
gcloud pubsub subscriptions create subscription-id \
  --topic=topic-id \
  --dead-letter-topic=dead-letter-topic-name \
  [--max-delivery-attempts=max-delivery-attempts] \
  [--dead-letter-topic-project=dead-letter-topic-project]

PUBSUB_SERVICE_ACCOUNT="service-project-number@gcp-sa-pubsub.iam.gserviceaccount.com"
gcloud pubsub topics add-iam-policy-binding dead-letter-topic-name \
  --member="serviceAccount:$PUBSUB_SERVICE_ACCOUNT"\
  --role="roles/pubsub.publisher"
gcloud pubsub subscriptions add-iam-policy-binding subscription-id \
  --member="serviceAccount:$PUBSUB_SERVICE_ACCOUNT"\
  --role="roles/pubsub.subscriber"
```

The Pub/Sub service agent needs both roles. Pub/Sub counts delivery attempts only when the dead-letter topic and its IAM roles are correct ([Dead-letter topics](https://docs.cloud.google.com/pubsub/docs/dead-letter-topics)). A pull message has the `delivery_attempt` field, and a push message has `deliveryAttempt` ([Dead-letter topics](https://docs.cloud.google.com/pubsub/docs/dead-letter-topics)). Attach a subscription to the dead-letter topic to read the forwarded messages ([Dead-letter topics](https://docs.cloud.google.com/pubsub/docs/dead-letter-topics)).

The retry policy sets the delay before a redelivery ([Subscription properties](https://docs.cloud.google.com/pubsub/docs/subscription-properties)):

| Policy | Behavior |
|---|---|
| Retry immediately (default) | Pub/Sub resends when the deadline expires or the subscriber sends a nack |
| Retry after exponential backoff delay | A minimum delay (default 10 seconds) and a maximum delay (default and limit 600 seconds) |

Sources: [Subscription properties](https://docs.cloud.google.com/pubsub/docs/subscription-properties).

Set the backoff with `gcloud pubsub subscriptions update SUBSCRIPTION_ID --min-retry-delay=MIN_RETRY_DELAY --max-retry-delay=MAX_RETRY_DELAY` ([Retry events](https://docs.cloud.google.com/eventarc/docs/retry-events)).

## Seek, snapshots, and replay

Sources: [Replay and purge messages with seek](https://docs.cloud.google.com/pubsub/docs/replay-overview), [Configure message retention for a subscription](https://docs.cloud.google.com/pubsub/docs/subscription-message-retention).

```bash
gcloud pubsub subscriptions update SUBSCRIPTION_ID \
  --message-retention-duration=1d \
  --retain-acked-messages

gcloud pubsub snapshots create \
    --project=PROJECT_ID \
    --subscription=SUBSCRIPTION_ID \
    SNAPSHOT_ID

gcloud pubsub subscriptions seek SUBSCRIPTION_ID --time=TIME
gcloud pubsub subscriptions seek SUBSCRIPTION_ID --snapshot=SNAPSHOT_ID
```

Facts about seek ([Replay and purge messages with seek](https://docs.cloud.google.com/pubsub/docs/replay-overview)):

- Seek to a past time needs retained acknowledged messages or topic retention. Seek to a snapshot needs no retention setting.
- A snapshot expires 7 days minus the age of the oldest unacknowledged message.
- Seek is eventually consistent. It can take up to a minute to take full effect.
- With a dead-letter topic, seek sets the delivery attempts to 0.
- With exactly-once delivery, acknowledgments for deliveries from before the seek fail.

A common use: create a snapshot before you deploy new subscriber code. If the code has a bug, seek back to the snapshot ([Replay and purge messages with seek](https://docs.cloud.google.com/pubsub/docs/replay-overview)).

## Schemas

A schema is a contract between publishers and subscribers that Pub/Sub enforces. Pub/Sub supports Apache Avro 1.11 and Protocol Buffers (proto2 and proto3) ([Schema overview](https://docs.cloud.google.com/pubsub/docs/schemas)). When you attach a schema to a topic, you choose the `JSON` or `BINARY` message encoding. You can also limit the schema revisions that the topic accepts ([Associate a schema with a topic](https://docs.cloud.google.com/pubsub/docs/associate-schema-topic)).

Source: [Associate a schema with a topic](https://docs.cloud.google.com/pubsub/docs/associate-schema-topic).

```bash
gcloud pubsub topics create TOPIC_ID \
        --message-encoding=ENCODING_TYPE \
        --schema=SCHEMA_ID \
        --first-revision-id=FIRST_REVISION_ID \
        --last-revision-id=LAST_REVISION_ID
```

Pub/Sub does not publish a message that does not conform to the schema ([Schema overview](https://docs.cloud.google.com/pubsub/docs/schemas)). For local tests without a real topic, see [the emulators page](note:2.1-emulators).

## AWS mapping

| AWS | Google Cloud | Difference that matters |
|---|---|---|
| Amazon Kinesis Data Streams | Pub/Sub | Pub/Sub leases individual messages, not partitions. The client library extends each lease, and you acknowledge each message |
| Amazon MQ | Pub/Sub | Pub/Sub has dead-letter topics and filters, as messaging middleware does. But filters use attributes only and cannot change |

Sources: [Compare AWS and Azure services to Google Cloud](https://docs.cloud.google.com/docs/get-started/aws-azure-gcp-service-comparison), [What is Pub/Sub?](https://docs.cloud.google.com/pubsub/docs/overview), [Extend ack time with lease management](https://docs.cloud.google.com/pubsub/docs/lease-management), [Filter messages from a subscription](https://docs.cloud.google.com/pubsub/docs/subscription-message-filter).

## Exam traps

- **Publish in a loop and ignore the futures.** Handle each future. Use publisher flow control to stop `DEADLINE_EXCEEDED` errors in a burst ([Best practices to publish to a Pub/Sub topic](https://docs.cloud.google.com/pubsub/docs/publish-best-practices), [Flow control](https://docs.cloud.google.com/pubsub/docs/flow-control-messages)).
- **A 20 MB message.** The data of one message is limited to 10 MB ([Pub/Sub quotas and limits](https://docs.cloud.google.com/pubsub/quotas)).
- **Acknowledge first, then process.** A failure after the acknowledgment loses the message ([Best practices to subscribe to a Pub/Sub topic](https://docs.cloud.google.com/pubsub/docs/subscribe-best-practices)).
- **A 600-second subscription deadline for a slow pull subscriber.** The client library already extends leases. Tune lease management and flow control ([Extend ack time with lease management](https://docs.cloud.google.com/pubsub/docs/lease-management)).
- **Unary Pull for throughput.** Use StreamingPull through the high-level library ([Pull subscriptions](https://docs.cloud.google.com/pubsub/docs/pull)).
- **A filter on a field in the message data.** Filters use attributes only ([Filter messages from a subscription](https://docs.cloud.google.com/pubsub/docs/subscription-message-filter)).
- **An update to the filter of a subscription.** It is immutable. Use a snapshot, a new subscription, and seek ([Filter messages from a subscription](https://docs.cloud.google.com/pubsub/docs/subscription-message-filter)).
- **An ordering key without a locational endpoint, or without `resume_publish`.** Google recommends both for ordered publishing ([Best practices to publish to a Pub/Sub topic](https://docs.cloud.google.com/pubsub/docs/publish-best-practices)).
- **A dead-letter topic that never receives messages.** The Pub/Sub service agent lacks the publisher or subscriber role ([Dead-letter topics](https://docs.cloud.google.com/pubsub/docs/dead-letter-topics)).
- **Seek to last week without retention.** Seek to a past time needs retained acknowledged messages or topic retention ([Replay and purge messages with seek](https://docs.cloud.google.com/pubsub/docs/replay-overview)).
