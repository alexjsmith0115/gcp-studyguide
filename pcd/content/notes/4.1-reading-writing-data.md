## Why it matters

Each data service has its own read and write calls, and the wrong call causes lost updates, duplicate rows, slow scans, or extra cost. The exam shows a requirement or a code fragment and asks for the correct pattern. Examples are a resumable upload with a precondition, a Firestore transaction, and a Spanner read-only transaction. Others are a Bigtable row range and the BigQuery Storage Read API.

## Key points

- Use a single-request upload for a small object. A resumable upload suits most applications and is more reliable for large files ([Object uploads](https://docs.cloud.google.com/storage/docs/uploads)).
- An upload with the same name replaces the object. A generation precondition of `0` creates the object only if no live version exists ([Object uploads](https://docs.cloud.google.com/storage/docs/uploads), [Request preconditions](https://docs.cloud.google.com/storage/docs/request-preconditions)).
- A Cloud Storage request with a failed precondition returns `412 Precondition Failed` ([Request preconditions](https://docs.cloud.google.com/storage/docs/request-preconditions)).
- A Firestore transaction does all reads before its writes. The library runs the function again if a concurrent edit occurs ([Transactions and batched writes](https://docs.cloud.google.com/firestore/native/docs/manage-data/transactions)).
- A Firestore batched write is atomic and needs no reads ([Transactions and batched writes](https://docs.cloud.google.com/firestore/native/docs/manage-data/transactions)).
- In Firestore Standard edition, every query uses an index. A query with an equality filter and a range filter on different fields needs a manual index (formerly composite index) ([Query and filter data](https://docs.cloud.google.com/firestore/native/docs/query-data/queries), [Standard edition index overview](https://docs.cloud.google.com/firestore/native/docs/standard-index-overview)).
- In Spanner, use a read-only transaction or a single read for reads. Use a locking read-write transaction only when you must write ([Transactions overview](https://docs.cloud.google.com/spanner/docs/transactions)).
- Spanner partitioned DML runs large `UPDATE` and `DELETE` statements without transaction limits. It has no commit or rollback ([Partitioned DML](https://docs.cloud.google.com/spanner/docs/dml-partitioned)).
- Do not mix DML and mutations in one Spanner transaction ([Compare DML and mutations](https://docs.cloud.google.com/spanner/docs/dml-versus-mutations)).
- Restrict each Bigtable read to row keys or row ranges. A filter without a row range scans the full table ([Reads](https://docs.cloud.google.com/bigtable/docs/reads), [Use filters](https://docs.cloud.google.com/bigtable/docs/using-filters)).
- In a Bigtable batch write, each row entry is atomic, but the batch as a whole is not ([Writes](https://docs.cloud.google.com/bigtable/docs/writes)).
- For large BigQuery reads, use the Storage Read API. It reads in parallel streams with column projection and row filters ([Use the BigQuery Storage Read API to read table data](https://docs.cloud.google.com/bigquery/docs/reference/storage)).

## Cloud Storage: choose an upload type

Choose the upload type by object size, network reliability, and tool support ([Object uploads](https://docs.cloud.google.com/storage/docs/uploads)). For the uploads that browsers send with signed URLs, see [Signed URLs](note:1.3-signed-urls).

| Upload type | How it works | Use when |
|---|---|---|
| Single-request | One request sends all data. The JSON API multipart form also sends the metadata | You can afford to restart the full upload if the connection fails |
| Resumable | A request starts a session, and the data goes to the session URI | Most cases, and large files. It costs one extra HTTP request |
| XML API multipart | Parts upload in parallel and are joined by the final request. Compatible with Amazon S3 multipart uploads | S3-compatible code, or parallel parts |
| Parallel composite | Up to 32 chunks upload as temporary objects, and a compose request joins them | Large files, for example from the gcloud CLI. Not with retention policies |
| Streaming | Data uploads without a file, with an unknown size | Output of another process |

Sources: [Object uploads](https://docs.cloud.google.com/storage/docs/uploads), [Resumable uploads](https://docs.cloud.google.com/storage/docs/resumable-uploads), [XML API multipart uploads](https://docs.cloud.google.com/storage/docs/multipart-uploads), [Parallel composite uploads](https://docs.cloud.google.com/storage/docs/parallel-composite-uploads), [Streaming uploads](https://docs.cloud.google.com/storage/docs/streaming-uploads).

The size limit for a single-request upload depends on the time you can lose. With 30 seconds of tolerance at 8 Mbps, the limit is about 30 MB. At 500 Mbps within a region, it is almost 2 GB ([Object uploads](https://docs.cloud.google.com/storage/docs/uploads)). The Python library uses a resumable upload for objects larger than 8 MiB. To always use a resumable upload, use `Blob.open(mode='w')` or `BlobWriter`. A chunk size must be a multiple of 256 KiB ([Resumable uploads](https://docs.cloud.google.com/storage/docs/resumable-uploads)).

```python
storage_client = storage.Client()
bucket = storage_client.bucket(bucket_name)
blob = bucket.blob(destination_blob_name)

# For a destination object that does not yet exist, set the
# if_generation_match precondition to 0.
generation_match_precondition = 0
blob.upload_from_filename(
    source_file_name, if_generation_match=generation_match_precondition
)
```

Source: [Upload objects from a file system](https://docs.cloud.google.com/storage/docs/uploading-objects).

Know the costs of the parallel methods:

- Unfinished XML API multipart parts stay in the bucket and you pay for them. Use Object Lifecycle Management to remove them. Multipart uploads support no preconditions and no MD5 hash ([XML API multipart uploads](https://docs.cloud.google.com/storage/docs/multipart-uploads)).
- A parallel composite upload creates temporary objects. They can cause early deletion fees and soft delete costs. Do not use it with a retention policy. With default object holds, you must release the hold on each temporary object before you can delete it. The final object has only a CRC32C hash ([Parallel composite uploads](https://docs.cloud.google.com/storage/docs/parallel-composite-uploads)).
- With the XML API, prefer XML API multipart uploads to parallel composite uploads ([Parallel composite uploads](https://docs.cloud.google.com/storage/docs/parallel-composite-uploads)).

## Cloud Storage: preconditions

Preconditions stop race conditions in uploads, deletes, and metadata updates. Two processes can change the same object, or a retry can send the same request twice ([Request preconditions](https://docs.cloud.google.com/storage/docs/request-preconditions)).

| Precondition | The request proceeds if | Else |
|---|---|---|
| `ifGenerationMatch` (`x-goog-if-generation-match`) | The object generation matches. `0` means that no live object with that name exists | `412` |
| `ifMetagenerationMatch` (`x-goog-if-metageneration-match`) | The metadata generation matches | `412` |
| `ifMetagenerationNotMatch` | The metadata generation does not match | `304` |

Source: [Request preconditions](https://docs.cloud.google.com/storage/docs/request-preconditions).

Prefer generation and metageneration preconditions to ETags. With a metageneration precondition, also add a generation precondition ([Request preconditions](https://docs.cloud.google.com/storage/docs/request-preconditions)). To update an object safely, first read its generation, then send the write with that generation. This extra metadata request adds latency ([Request preconditions](https://docs.cloud.google.com/storage/docs/request-preconditions)). A precondition also makes an upload safe to retry. This matters because the Python library retries uploads (Objects: insert) by default ([Retry strategy](https://docs.cloud.google.com/storage/docs/retry-strategy)).

## Cloud Storage: downloads and range reads

You can read an object into memory or as a stream, or download it to a file. To resume a failed download, request the remaining bytes with a `Range` header. Sliced downloads get several byte ranges in parallel ([Object reads and downloads](https://docs.cloud.google.com/storage/docs/reads-and-downloads)). In Python, `download_to_filename` takes `start` and `end` byte offsets ([Download objects](https://docs.cloud.google.com/storage/docs/downloading-objects)).

Know two details. `Bucket.blob()` makes no request, but `Bucket.get_blob()` reads the metadata. A checksum validates only a full object, not a byte range ([Download objects](https://docs.cloud.google.com/storage/docs/downloading-objects)).

## Firestore: reads, queries, and indexes

A query filters documents in a collection with `where`. The operators are `<`, `<=`, `==`, `>`, `>=`, `!=`, `array-contains`, `array-contains-any`, `in`, and `not-in` ([Query and filter data](https://docs.cloud.google.com/firestore/native/docs/query-data/queries)).

```python
docs = (
    db.collection("cities")
    .where(filter=FieldFilter("capital", "==", True))
    .stream()
)
for doc in docs:
    print(f"{doc.id} => {doc.to_dict()}")
```

Source: [Query and filter data](https://docs.cloud.google.com/firestore/native/docs/query-data/queries).

Know these query rules ([Query and filter data](https://docs.cloud.google.com/firestore/native/docs/query-data/queries)):

- `!=` and `not-in` do not return documents that lack the field. `orderBy` also drops documents that lack the field.
- `in` takes up to 30 values. In Standard edition, `not-in` takes up to 10 values, and a query can have one `!=` or `not-in`.
- An equality filter combined with a range filter on another field needs a manual index. So does a collection group query.
- If an index is missing, the query fails with an error message that contains a link to create the index.

In Standard edition, automatic indexes (formerly single-field indexes) and manual indexes (formerly composite indexes) back every query. Query performance depends on the size of the result set, not on the size of the database ([Standard edition index overview](https://docs.cloud.google.com/firestore/native/docs/standard-index-overview)). Enterprise edition can run queries without an index ([Firestore editions overview](https://docs.cloud.google.com/firestore/native/docs/editions-overview)). For index design, see [NoSQL schema design](note:1.3-nosql-schema).

To page through results, use query cursors such as `startAt()` and `startAfter()` ([Paginate data with query cursors](https://docs.cloud.google.com/firestore/native/docs/query-data/query-cursors)). Do not use offsets. Firestore still reads the skipped documents, and you pay for those reads ([Firestore best practices](https://docs.cloud.google.com/firestore/native/docs/best-practices)).

A real-time listener gets the current contents first, and then an update after each change. In Python, call `on_snapshot` with a callback ([Get real-time updates](https://docs.cloud.google.com/firestore/native/docs/query-data/listen)). Detach a listener when you no longer need it. After an error, a listener gets no more events ([Get real-time updates](https://docs.cloud.google.com/firestore/native/docs/query-data/listen)). The PHP client library does not support real-time listeners ([Get real-time updates](https://docs.cloud.google.com/firestore/native/docs/query-data/listen)).

## Firestore: transactions and batched writes

Both operations are atomic, and both can change several documents ([Transactions and batched writes](https://docs.cloud.google.com/firestore/native/docs/manage-data/transactions)).

| | Transaction | Batched write |
|---|---|---|
| Reads | Yes. All reads come before the writes | No |
| On a concurrent change | The library runs the function again | Not applicable |
| Use when | A write depends on the current value | You write a known set of documents |

Source: [Transactions and batched writes](https://docs.cloud.google.com/firestore/native/docs/manage-data/transactions).

```python
transaction = db.transaction()
city_ref = db.collection("cities").document("SF")

@firestore.transactional
def update_in_transaction(transaction, city_ref):
    snapshot = city_ref.get(transaction=transaction)
    transaction.update(city_ref, {"population": snapshot.get("population") + 1})

update_in_transaction(transaction, city_ref)

batch = db.batch()
batch.set(db.collection("cities").document("NYC"), {"name": "New York City"})
batch.update(db.collection("cities").document("SF"), {"population": 1000000})
batch.delete(db.collection("cities").document("DEN"))
batch.commit()
```

Source: [Transactions and batched writes](https://docs.cloud.google.com/firestore/native/docs/manage-data/transactions).

Know these transaction rules ([Transactions and batched writes](https://docs.cloud.google.com/firestore/native/docs/manage-data/transactions)):

- The function can run more than once. It must not change app state.
- A transaction fails when the client is offline.
- A transaction fails if it exceeds the 10 MiB request size, 270 seconds, or 60 seconds of idle time. A failed transaction rolls back automatically.

Repeated conflicts end with the error "ABORTED: Too much contention". The concurrency mode decides when Firestore checks for conflicts. The default is pessimistic for Standard edition and optimistic for Enterprise edition ([Data contention in transactions](https://docs.cloud.google.com/firestore/native/docs/transaction-data-contention)). The mobile and web SDKs always use optimistic concurrency ([Data contention in transactions](https://docs.cloud.google.com/firestore/native/docs/transaction-data-contention)). Keep transactions small. To write a large number of documents, use a bulk writer instead of a batched write ([Firestore best practices](https://docs.cloud.google.com/firestore/native/docs/best-practices)).

## Spanner: transactions, DML, and mutations

| Type | Locks | Use when |
|---|---|---|
| Read-write | Yes, with the default serializable isolation | Reads and writes that must be atomic. The client library retries aborted transactions |
| Read-only | No | Several reads that must see the same timestamp. Can run on any replica |
| Single read | No | One read, outside a transaction |
| Partitioned DML | Only rows that match the `WHERE` clause | Large `UPDATE` or `DELETE` statements that must be idempotent |
| Batch write | Not atomic across mutation groups | Many writes that do not need one atomic transaction |

Sources: [Transactions overview](https://docs.cloud.google.com/spanner/docs/transactions), [Partitioned DML](https://docs.cloud.google.com/spanner/docs/dml-partitioned), [Modify data using batch write](https://docs.cloud.google.com/spanner/docs/batch-write).

You define the body of a transaction as a function. The client library runs the function again until the transaction commits or hits an error that it cannot retry. In Python, an exception in the function rolls back the transaction ([Transactions overview](https://docs.cloud.google.com/spanner/docs/transactions)).

```python
def update_albums(transaction):
    row_ct = transaction.execute_update(
        "UPDATE Albums "
        "SET MarketingBudget = MarketingBudget * 2 "
        "WHERE SingerId = 1 and AlbumId = 1"
    )

database.run_in_transaction(update_albums)

with database.snapshot(multi_use=True) as snapshot:  # read-only transaction
    results = snapshot.execute_sql("SELECT SingerId, AlbumId, AlbumTitle FROM Albums")

row_ct = database.execute_partitioned_dml(
    "UPDATE Albums SET MarketingBudget = 100000 WHERE SingerId > 1"
)
```

Sources: [Insert, update, and delete data using DML](https://docs.cloud.google.com/spanner/docs/dml-tasks), [Transactions overview](https://docs.cloud.google.com/spanner/docs/transactions).

Keep read-write transactions short. Long-held locks increase contention, deadlocks, and aborts ([Transactions overview](https://docs.cloud.google.com/spanner/docs/transactions)). Strong reads are the default. For stale reads and their trade-offs, see [Consistency and replication](note:1.3-consistency-and-replication).

You write data in a read-write transaction with DML statements or with mutations ([Compare DML and mutations](https://docs.cloud.google.com/spanner/docs/dml-versus-mutations)):

| Feature | DML | Mutations |
|---|---|---|
| Read your own writes in the transaction | Yes | No. Spanner applies them at commit |
| Constraint checks | After each statement | At commit |
| Insert or ignore | Supported | Not supported |

Source: [Compare DML and mutations](https://docs.cloud.google.com/spanner/docs/dml-versus-mutations).

Do not mix DML and mutations in one transaction. Spanner runs the DML statements before the mutations, and mutations are not visible until the commit ([Compare DML and mutations](https://docs.cloud.google.com/spanner/docs/dml-versus-mutations)). Partitioned DML has no commit or rollback. If you cancel it, partitions that already ran stay changed ([Partitioned DML](https://docs.cloud.google.com/spanner/docs/dml-partitioned)). Spanner can run a statement more than once on a partition, so the statement must be idempotent ([Partitioned DML](https://docs.cloud.google.com/spanner/docs/dml-partitioned)). Batch write has no replay protection, so make those writes idempotent too ([Modify data using batch write](https://docs.cloud.google.com/spanner/docs/batch-write)).

## Bigtable: reads and writes

Every Bigtable read uses `ReadRows`. Rows come back in row key order, and each row read is atomic ([Reads](https://docs.cloud.google.com/bigtable/docs/reads)). A scan by row range or row key prefix is the most common read. Restrict the row set as much as you can ([Reads](https://docs.cloud.google.com/bigtable/docs/reads)).

```python
row_set = RowSet()
row_set.add_row_range_from_keys(
    start_key=b"phone#4c410523#20190501", end_key=b"phone#4c410523#201906201"
)
rows = table.read_rows(row_set=row_set)

rows = table.read_rows(filter_=row_filters.CellsColumnLimitFilter(2))
```

Sources: [Read examples](https://docs.cloud.google.com/bigtable/docs/reading-data), [Use filters](https://docs.cloud.google.com/bigtable/docs/using-filters).

Filters select the cells to return, for example the latest cells in each column. A filter reduces network data, but it uses more CPU and makes the read slower. Use filters for efficiency, not for latency ([Reads](https://docs.cloud.google.com/bigtable/docs/reads)). A row key regex starts a full table scan, unless the regex begins with a literal prefix ([Use filters](https://docs.cloud.google.com/bigtable/docs/using-filters)). For high-throughput read jobs that must not affect serving traffic, use Data Boost, a serverless compute service for reads ([Reads](https://docs.cloud.google.com/bigtable/docs/reads)).

| Write request | Atomic | Use when | Do not use when |
|---|---|---|---|
| `MutateRow` (simple write) | Yes, for one row | Several changes to one row | High throughput for many rows |
| `MutateRows` (batch write) | Each row entry, not the batch | Many rows with similar row keys | Rows far apart in the key space |
| `CheckAndMutateRow` (conditional write) | Yes | Write only if a filter matches | Multi-cluster routing |
| `ReadModifyWriteRow` (append or increment) | Yes | Append to a value | Multi-cluster routing. It is never retried |

Source: [Writes](https://docs.cloud.google.com/bigtable/docs/writes).

The client libraries retry simple writes and batch writes. A batch write retries the entries that failed, until all succeed or the deadline passes ([Writes](https://docs.cloud.google.com/bigtable/docs/writes)). For counters, use aggregate cells with `AddToCell` instead of `ReadModifyWriteRow` ([Writes](https://docs.cloud.google.com/bigtable/docs/writes)).

```python
with MutationsBatcher(table=table) as batcher:
    rows = [
        table.direct_row("tablet#a0b81f74#20190501"),
        table.direct_row("tablet#a0b81f74#20190502"),
    ]
    rows[0].set_cell(column_family_id, "connected_wifi", 1, timestamp)
    rows[1].set_cell(column_family_id, "connected_wifi", 1, timestamp)
    batcher.mutate_rows(rows)
```

Source: [Write examples](https://docs.cloud.google.com/bigtable/docs/writing-data).

## BigQuery: query results and the Storage Read API

To run a query, the caller needs BigQuery Job User on the project and BigQuery Data Viewer on the tables ([Run a query](https://docs.cloud.google.com/bigquery/docs/running-queries)). `query_and_wait` runs the query and returns a row iterator ([Run a query](https://docs.cloud.google.com/bigquery/docs/running-queries)). The client library fetches the next page as you iterate ([Using pagination with the BigQuery API](https://docs.cloud.google.com/bigquery/docs/paging-results)).

```python
from google.cloud import bigquery

client = bigquery.Client()
query = """
    SELECT name, SUM(number) as total_people
    FROM `bigquery-public-data.usa_names.usa_1910_2013`
    WHERE state = 'TX'
    GROUP BY name, state
    ORDER BY total_people DESC
    LIMIT 20
"""
rows = client.query_and_wait(query)  # Make an API request.
for row in rows:
    print("name={}, count={}".format(row[0], row["total_people"]))
```

Source: [Run a query](https://docs.cloud.google.com/bigquery/docs/running-queries).

Know these rules for query results:

- BigQuery writes query results to a temporary table by default, or to a permanent table that you name ([Run a query](https://docs.cloud.google.com/bigquery/docs/running-queries)).
- Set `max_results` or `page_size` to limit the rows in each request ([Using pagination with the BigQuery API](https://docs.cloud.google.com/bigquery/docs/paging-results)).
- For a stateless web app, return the page token to the client, and pass it back for the next page ([Using pagination with the BigQuery API](https://docs.cloud.google.com/bigquery/docs/paging-results)).
- For short queries, optional job creation mode returns results without a job, which can lower latency ([Run a query](https://docs.cloud.google.com/bigquery/docs/running-queries)).

The `tabledata.list` and `jobs.getQueryResults` methods return pages of rows, and suit small result sets. The Storage Read API sends binary data over RPC, so several consumers can read in parallel ([Use the BigQuery Storage Read API to read table data](https://docs.cloud.google.com/bigquery/docs/reference/storage)).

| Feature | Storage Read API behavior |
|---|---|
| Multiple streams | Each stream reads a separate set of rows. To read all data, read every stream |
| Column projection | The session returns only the columns that you select |
| Row filtering | Simple filter predicates run on the server |
| Snapshot consistency | All streams read one point in time |
| Format | Apache Avro or Apache Arrow |
| Session expiration | At least 6 hours after creation |
| Limits | No direct reads of logical views, materialized views, or external tables |

Source: [Use the BigQuery Storage Read API to read table data](https://docs.cloud.google.com/bigquery/docs/reference/storage).

```python
from google.cloud.bigquery_storage import BigQueryReadClient, types

client = BigQueryReadClient()
requested_session = types.ReadSession()
requested_session.table = "projects/bigquery-public-data/datasets/usa_names/tables/usa_1910_current"
requested_session.data_format = types.DataFormat.AVRO
requested_session.read_options.selected_fields = ["name", "number", "state"]
requested_session.read_options.row_restriction = 'state = "WA"'

session = client.create_read_session(
    parent="projects/{}".format(project_id),
    read_session=requested_session,
    max_stream_count=1,
)
reader = client.read_rows(session.streams[0].name)
rows = reader.rows(session)
```

Source: [BigQuery Storage API Client Libraries](https://docs.cloud.google.com/bigquery/docs/reference/storage/libraries).

The caller needs Read Session User (`roles/bigquery.readSessionUser`) on the project ([Use the BigQuery Storage Read API to read table data](https://docs.cloud.google.com/bigquery/docs/reference/storage)). You often do not call the API yourself. In Python, `to_dataframe` and `to_arrow` create a Storage Read API client by default. They need the `google-cloud-bigquery-storage` library, and the Storage Read API is billable ([Class RowIterator](https://docs.cloud.google.com/python/docs/reference/bigquery/latest/google.cloud.bigquery.table.RowIterator)). For writes to BigQuery, see [BigQuery writes](note:1.3-bigquery-writes).

## Exam traps

- **Two workers overwrite the same object.** Read the generation, then write with `if_generation_match`. Use `0` when the object must not exist ([Request preconditions](https://docs.cloud.google.com/storage/docs/request-preconditions)).
- **Preconditions with an XML API multipart upload.** They are not supported, and the request fails ([Request preconditions](https://docs.cloud.google.com/storage/docs/request-preconditions)).
- **Parallel composite uploads to a bucket with a retention policy.** The temporary objects cannot be deleted until they meet the retention period. Do not use them there ([Parallel composite uploads](https://docs.cloud.google.com/storage/docs/parallel-composite-uploads)).
- **A Firestore transaction that sends an email or changes a global variable.** The function can run more than once ([Transactions and batched writes](https://docs.cloud.google.com/firestore/native/docs/manage-data/transactions)).
- **A transaction for writes that need no reads.** Use a batched write, or a bulk writer for many documents ([Transactions and batched writes](https://docs.cloud.google.com/firestore/native/docs/manage-data/transactions), [Firestore best practices](https://docs.cloud.google.com/firestore/native/docs/best-practices)).
- **A `!=` query that should also return documents without the field.** Firestore excludes them ([Query and filter data](https://docs.cloud.google.com/firestore/native/docs/query-data/queries)).
- **Offsets for deep pagination.** Firestore reads and bills the skipped documents. Use cursors ([Firestore best practices](https://docs.cloud.google.com/firestore/native/docs/best-practices)).
- **A Spanner read-write transaction for a report with several reads.** Use a read-only transaction. It takes no locks ([Transactions overview](https://docs.cloud.google.com/spanner/docs/transactions)).
- **A DML statement that should see an earlier mutation in the same transaction.** Spanner applies mutations at commit, after the DML ([Compare DML and mutations](https://docs.cloud.google.com/spanner/docs/dml-versus-mutations)).
- **Partitioned DML for an all-or-nothing change.** It has no rollback ([Partitioned DML](https://docs.cloud.google.com/spanner/docs/dml-partitioned)).
- **A Bigtable `MutateRows` batch as an atomic unit.** Only each row entry is atomic ([Writes](https://docs.cloud.google.com/bigtable/docs/writes)).
- **A Bigtable read with only a filter.** It scans the full table. Add a row key or row range ([Use filters](https://docs.cloud.google.com/bigtable/docs/using-filters)).
- **`ReadModifyWriteRow` with multi-cluster routing, or for high-rate counters.** Do not use it there. Use `AddToCell` for counters ([Writes](https://docs.cloud.google.com/bigtable/docs/writes)).
- **The Storage Read API on a view.** It cannot read views. Query the view, then read the result table ([Use the BigQuery Storage Read API to read table data](https://docs.cloud.google.com/bigquery/docs/reference/storage)).
