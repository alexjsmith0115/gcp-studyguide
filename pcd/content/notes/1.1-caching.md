## Why it matters

A cache cuts latency and database load, but each cache layer has a different scope and a different way to become stale. A developer decides what to cache, where to cache it, and for how long. The exam tests the Memorystore product for a scenario and the cache-aside pattern with TTLs. It also tests the network path from Cloud Run to Memorystore, and the Cloud CDN settings.

## Key points

- Memorystore offers Valkey, Redis Cluster, Redis, and Memcached. Memorystore for Memcached is deprecated and shuts down on January 31, 2029. Google recommends migration to Memorystore for Valkey ([Memorystore for Memcached release notes](https://docs.cloud.google.com/memorystore/docs/memcached/release-notes)).
- Memorystore for Valkey and Memorystore for Redis Cluster scale without downtime and offer a 99.99% SLA ([Memorystore](https://cloud.google.com/memorystore)).
- In the cache-aside pattern, the app checks the cache first. It queries the database only if the value is absent or expired ([Caching data with Memorystore](https://docs.cloud.google.com/appengine/docs/standard/using-memorystore)).
- The default eviction policy is `volatile-lru`. Set TTLs on the keys that you want to expire, or Redis has no keys to evict ([Memory management best practices](https://docs.cloud.google.com/memorystore/docs/redis/memory-management-best-practices)).
- Memorystore for Redis instances use private IP addresses, so Cloud Run reaches them through the VPC network. Google recommends Direct VPC egress over a VPC connector ([Memorystore for Redis overview](https://docs.cloud.google.com/memorystore/docs/redis/memorystore-for-redis-overview), [Connect to a Redis instance from a Cloud Run service](https://docs.cloud.google.com/memorystore/docs/redis/connect-redis-instance-cloud-run)).
- For high availability, provision at least one replica for each shard. During an unplanned failover, acknowledged writes can be lost, because replication is asynchronous ([High availability and replicas](https://docs.cloud.google.com/memorystore/docs/valkey/ha-and-replicas)).
- A value in the memory of one Cloud Run instance does not help other instances. You cannot assume that a client returns to the same instance ([General development tips](https://docs.cloud.google.com/run/docs/tips/general), [Set session affinity for services](https://docs.cloud.google.com/run/docs/configuring/session-affinity)).
- Cloud CDN works only with two types of Application Load Balancer (formerly HTTP(S) Load Balancing): global external and classic ([Cloud CDN overview](https://docs.cloud.google.com/cdn/docs/overview), [Cloud Load Balancing release notes](https://docs.cloud.google.com/load-balancing/docs/release-notes)).
- The default cache mode, `CACHE_ALL_STATIC`, caches static content types without headers. HTML and JSON responses need an explicit `Cache-Control` header ([Caching overview](https://docs.cloud.google.com/cdn/docs/caching)).
- Google recommends versioned URLs as the default way to update cached content. Use invalidation sparingly, as a last resort ([Content delivery best practices](https://docs.cloud.google.com/cdn/docs/best-practices)).

## Where to cache

| Cache layer | Who shares it | Use it for | Limits |
|---|---|---|---|
| Memory of one instance (a global variable) | Requests on that instance only | Clients and objects that are expensive to create | Each instance has its own copy. A new instance starts empty |
| Memorystore | All instances that connect through the VPC network | Query results, session data, API responses, leaderboards | Reached through the VPC network, not the internet |
| Cloud CDN | All users that the same edge cache serves | Static files and public responses | `GET` responses only. Needs the global external or classic Application Load Balancer |
| Browser cache | One user | Static files | Cloud CDN invalidation does not clear it |

Sources: [General development tips](https://docs.cloud.google.com/run/docs/tips/general), [Memorystore for Redis overview](https://docs.cloud.google.com/memorystore/docs/redis/memorystore-for-redis-overview), [Caching overview](https://docs.cloud.google.com/cdn/docs/caching), [Cache invalidation overview](https://docs.cloud.google.com/cdn/docs/cache-invalidation-overview).

### Why an in-memory cache on each instance is not shared

Cloud Run reuses instances, so a value in a global variable can serve later requests on the same instance. But you cannot assume that state is kept between requests, and you cannot know if a request reaches a warm instance ([General development tips](https://docs.cloud.google.com/run/docs/tips/general)). Each instance has its own memory. Two instances can return different cached values, and a new instance starts with an empty cache. Even with session affinity, a client does not always return to the same instance ([Set session affinity for services](https://docs.cloud.google.com/run/docs/configuring/session-affinity)).

Use the instance memory for objects such as a database client or a parsed configuration. Put data that all instances must see in Memorystore or in the database. Load balancer session affinity can raise the hit rate of per-instance caches, because it sends a client to the same backend ([Backend services overview](https://docs.cloud.google.com/load-balancing/docs/backend-service)). On GKE Gateway, the `RING_HASH` algorithm keeps most requests on the same Pods when Pods are added or removed. Google recommends it for services that are sensitive to cache misses ([Configure Gateway resources using Policies](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/configure-gateway-resources)). Affinity is best effort, so treat a per-instance cache as an optimization only. The [load balancing page](note:1.1-load-balancing) covers session affinity.

## Choosing a Memorystore product

| Product | Structure | Availability and scaling | Persistence |
|---|---|---|---|
| Memorystore for Valkey | Cluster Mode Enabled (one or more shards) or Cluster Mode Disabled (one shard). 0 to 5 replicas for each shard | Replicas in other zones, 99.99% SLA, scaling without downtime | AOF or RDB, not both |
| Memorystore for Redis Cluster | Shards with 0 to 5 replicas each. Based on Redis 7.x | Replicas in other zones, 99.99% SLA, scaling without downtime | AOF or RDB, not both |
| Memorystore for Redis, Basic Tier | One node, up to 300 GB | No replication and no automatic failover | RDB snapshots only |
| Memorystore for Redis, Standard Tier | A primary with replication across zones, and up to 5 read replicas | Automatic failover, 99.9% SLA. Scaling causes downtime of less than a minute | RDB snapshots only |
| Memorystore for Memcached (deprecated) | Keys divided across nodes | Keys are not replicated | — |

Sources: [Memorystore for Valkey overview](https://docs.cloud.google.com/memorystore/docs/valkey/product-overview), [Memorystore](https://cloud.google.com/memorystore), [Persistence overview (Valkey)](https://docs.cloud.google.com/memorystore/docs/valkey/persistence-overview), [Memorystore for Redis Cluster overview](https://docs.cloud.google.com/memorystore/docs/cluster/memorystore-for-redis-cluster-overview), [Persistence overview (Redis Cluster)](https://docs.cloud.google.com/memorystore/docs/cluster/persistence-overview), [Memorystore for Redis overview](https://docs.cloud.google.com/memorystore/docs/redis/memorystore-for-redis-overview), [Memorystore for Memcached overview](https://docs.cloud.google.com/memorystore/docs/memcached/memcached-overview).

How to choose:

- **High availability and scaling without downtime:** Memorystore for Valkey or Memorystore for Redis Cluster ([Memorystore](https://cloud.google.com/memorystore)). Valkey also offers cross-region replication: secondary instances serve reads in other regions and give redundancy for a regional outage ([Memorystore for Valkey FAQ](https://docs.cloud.google.com/memorystore/docs/valkey/faq)).
- **One Redis node is enough:** Memorystore for Redis, up to 300 GB. Use the Standard Tier for production, because the Basic Tier has no failover ([Memorystore for Redis overview](https://docs.cloud.google.com/memorystore/docs/redis/memorystore-for-redis-overview)).
- **Memcached workload:** migrate to Memorystore for Valkey, as Google recommends. You can't create Memcached instances in new projects after February 1, 2027 ([Memorystore for Memcached release notes](https://docs.cloud.google.com/memorystore/docs/memcached/release-notes)). The migration changes the client library, for example to valkey-py, and the commands ([Migrate from Memorystore for Memcached to Memorystore for Valkey](https://docs.cloud.google.com/memorystore/docs/memcached/deprecation/migrate-to-valkey)).

In Cluster Mode Enabled, the client connects to a discovery endpoint. In Cluster Mode Disabled, the client writes to the primary endpoint and reads from the reader endpoint, which spreads reads across replicas ([Memorystore for Valkey overview](https://docs.cloud.google.com/memorystore/docs/valkey/product-overview)). Reads from replicas add throughput, but the data can be stale ([High availability and replicas](https://docs.cloud.google.com/memorystore/docs/valkey/ha-and-replicas)).

## Caching patterns

### Cache-aside

Cache-aside works in three steps ([Caching data with Memorystore](https://docs.cloud.google.com/appengine/docs/standard/using-memorystore)):

1. The app reads the key from the cache.
2. On a hit, the app returns the cached value.
3. On a miss, the app reads the database, writes the value to the cache with a TTL, and returns the value.

```python
import json
import os

import redis

redis_client = redis.Redis(
    host=os.environ.get("REDISHOST", "localhost"),
    port=int(os.environ.get("REDISPORT", 6379)),
    decode_responses=True,
)

def get_product(product_id):
    key = f"product:{product_id}"
    cached = redis_client.get(key)            # 1. Check the cache
    if cached is not None:
        return json.loads(cached)             # 2. Cache hit
    product = load_product_from_db(product_id)  # 3. Cache miss: read the database
    redis_client.set(key, json.dumps(product), ex=300)  # TTL in seconds
    return product
```

Sources: [Connect to a Redis instance from a Cloud Run service](https://docs.cloud.google.com/memorystore/docs/redis/connect-redis-instance-cloud-run), [Client library code samples](https://docs.cloud.google.com/memorystore/docs/valkey/client-library-code-samples), [Migrate from Memorystore for Memcached to Memorystore for Valkey](https://docs.cloud.google.com/memorystore/docs/memcached/deprecation/migrate-to-valkey).

Create the client once, in global scope, so that later requests on the instance reuse it ([General development tips](https://docs.cloud.google.com/run/docs/tips/general)). Start with a connection pool of one connection for each node ([Best practices for Memorystore for Valkey](https://docs.cloud.google.com/memorystore/docs/valkey/general-best-practices)).

### Write strategies

| Strategy | How it writes | Use it when |
|---|---|---|
| Cache-aside | The app reads from the cache and fills it from the database on a miss | Reads are frequent, and results do not need to be current at once |
| Write-through | The app writes to the cache and the database at the same time (synchronously) | You want more cache hits and fewer database reads |
| Write-back (write-behind) | The app writes to the cache first. The database update happens later (asynchronously) | The app is write-heavy, and the database is slow |

Sources: [Caching data with Memorystore](https://docs.cloud.google.com/appengine/docs/standard/using-memorystore), [Develop energy-efficient software](https://docs.cloud.google.com/architecture/framework/sustainability/energy-efficient-software).

### TTLs and eviction

Eviction policies such as TTL, least recently used (LRU), and least frequently used (LFU) remove stale or unused data ([Develop energy-efficient software](https://docs.cloud.google.com/architecture/framework/sustainability/energy-efficient-software)). Know these Memorystore rules:

- The default policy is `volatile-lru`. It evicts only keys that have a TTL. Without TTLs, Redis has no keys to evict ([Memory management best practices](https://docs.cloud.google.com/memorystore/docs/redis/memory-management-best-practices)).
- Eviction runs in the background. A high write rate can outpace eviction and cause an out-of-memory condition ([Memory management best practices](https://docs.cloud.google.com/memorystore/docs/redis/memory-management-best-practices)).
- With the `noeviction` policy, Memorystore for Valkey returns an error when memory is full ([Memorystore for Valkey FAQ](https://docs.cloud.google.com/memorystore/docs/valkey/faq)).
- Monitor the cache hit ratio. For Valkey, use the `total_keyspace_hits_count` and `total_keyspace_misses_count` metrics ([Memorystore for Valkey FAQ](https://docs.cloud.google.com/memorystore/docs/valkey/faq)).

### Design for cache failure

Design the app so that it keeps working when the cache fails. Cache misses and short cache outages must not stop reads from the database. Retry with exponential backoff and a time limit ([Best practices (Memcached)](https://docs.cloud.google.com/memorystore/docs/memcached/best-practices)). Add jitter to the backoff, so that clients do not reconnect all at the same time ([Best practices for Memorystore for Valkey](https://docs.cloud.google.com/memorystore/docs/valkey/general-best-practices)). If the loss of a cached value breaks a user session, store the value in the database too ([Caching data with Memorystore](https://docs.cloud.google.com/appengine/docs/standard/using-memorystore)). Memorystore has no emulator. For local tests, run a local Redis instance ([Caching data with Memorystore](https://docs.cloud.google.com/appengine/docs/standard/using-memorystore)).

## Connecting from Cloud Run and GKE

Memorystore for Redis instances have private IP addresses. Only apps in the same authorized VPC network can connect ([Memorystore for Redis overview](https://docs.cloud.google.com/memorystore/docs/redis/memorystore-for-redis-overview)). Memorystore for Valkey and Memorystore for Redis Cluster are available with Private Service Connect ([Memorystore](https://cloud.google.com/memorystore)). For Valkey, a network administrator creates a service connection policy with the `gcp-memorystore` service class ([Networking (Valkey)](https://docs.cloud.google.com/memorystore/docs/valkey/networking)).

| Client | How it connects |
|---|---|
| Cloud Run | For Memorystore for Redis: Direct VPC egress (recommended) or a Serverless VPC Access connector. Direct VPC egress has lower latency, higher throughput, and lower cost, and it needs no connector instances |
| GKE | Directly, from a cluster on the authorized network. The private services access connect mode needs a VPC-native cluster |
| Compute Engine | Directly, with no connector |

Sources: [Connect to a Redis instance from a Cloud Run service](https://docs.cloud.google.com/memorystore/docs/redis/connect-redis-instance-cloud-run), [Compare Direct VPC egress and VPC connectors](https://docs.cloud.google.com/run/docs/configuring/connecting-vpc), [Connect to a Redis instance from a Google Kubernetes Engine cluster](https://docs.cloud.google.com/memorystore/docs/redis/connect-redis-instance-gke), [Supported environments (Valkey)](https://docs.cloud.google.com/memorystore/docs/valkey/supported-environments).

The Memorystore for Valkey docs differ: they list a Serverless VPC Access connector as a requirement for Cloud Run ([Supported environments (Valkey)](https://docs.cloud.google.com/memorystore/docs/valkey/supported-environments)).

```bash
gcloud run deploy \
  --image REPO_REGION-docker.pkg.dev/PROJECT_ID/REPO_ID/visit-counter:v1 \
  --allow-unauthenticated \
  --region REGION \
  --network NETWORK \
  --subnet SUBNET \
```

In this sample, `REGION` is the region of the Redis instance, and `NETWORK` is its authorized network. The subnet must be `/26` or larger. The [service-to-service page](note:1.2-service-to-service) covers Direct VPC egress in detail.

## High availability and persistence

High availability and persistence protect against different failures. Google recommends both ([Persistence overview (Valkey)](https://docs.cloud.google.com/memorystore/docs/valkey/persistence-overview)).

- **High availability:** at least one replica for each shard. Memorystore puts the replicas in other zones and fails over automatically. An unplanned failover takes tens of seconds ([High availability and replicas](https://docs.cloud.google.com/memorystore/docs/valkey/ha-and-replicas)).
- **AOF persistence:** writes data every second or on every write. Choose it when durability is the priority ([Persistence overview (Valkey)](https://docs.cloud.google.com/memorystore/docs/valkey/persistence-overview)).
- **RDB persistence:** takes periodic snapshots. Choose it when performance is the priority and some staleness on recovery is acceptable ([Persistence overview (Valkey)](https://docs.cloud.google.com/memorystore/docs/valkey/persistence-overview)).

Memorystore for Redis supports RDB snapshots but not AOF ([Memorystore for Redis overview](https://docs.cloud.google.com/memorystore/docs/redis/memorystore-for-redis-overview)). The [replication page](note:1.1-regions-and-replication) covers zonal and regional failover models.

## Cloud CDN

Cloud CDN caches responses at Google edge locations. You enable it on a backend service or backend bucket of a global external or classic Application Load Balancer. Backends can be Compute Engine, GKE Ingress, GKE Gateway, or Cloud Storage buckets ([Cloud CDN overview](https://docs.cloud.google.com/cdn/docs/overview)). Backend services with Cloud Run, Cloud Run functions (formerly Cloud Functions), API Gateway, and App Engine backends also support Cloud CDN ([Set up a global external Application Load Balancer with Cloud Run, App Engine, or Cloud Run functions](https://docs.cloud.google.com/load-balancing/docs/https/setup-global-ext-https-serverless), [Compare Cloud Run functions](https://docs.cloud.google.com/run/docs/functions/comparison)). Caching is reactive: a cache stores an object only after a request for it passes through that cache. You cannot preload the caches ([Cloud CDN overview](https://docs.cloud.google.com/cdn/docs/overview)).

### Cache modes

| Cache mode | Behavior | Use it when |
|---|---|---|
| `CACHE_ALL_STATIC` (default) | Caches static types (CSS, JavaScript, fonts, images, video, audio, PDF) with no headers. Other responses need valid cache directives | Most sites |
| `USE_ORIGIN_HEADERS` | Caches only responses with valid cache directives | The origin sets `Cache-Control` for each response |
| `FORCE_CACHE_ALL` | Caches all successful responses and ignores `Cache-Control` and `Expires` | The backend serves only public content. Do not use it for per-user content |

Source: [Caching overview](https://docs.cloud.google.com/cdn/docs/caching).

### Cache-Control headers

The app controls caching with response headers. Cloud CDN caches only responses to `GET` requests ([Caching overview](https://docs.cloud.google.com/cdn/docs/caching)).

| Response header | Cloud CDN behavior |
|---|---|
| `Cache-Control: public, max-age=259200` | Cloud CDN and browsers cache the response for 72 hours |
| `s-maxage=N` | Cloud CDN uses `s-maxage` instead of `max-age`. Browsers ignore it |
| `no-cache` | Cloud CDN caches the response but revalidates it with the origin before each use |
| `private` | Cloud CDN does not cache it. Browsers can cache it |
| `no-store` | No cache stores it |
| `CDN-Cache-Control` | Cloud CDN uses it and ignores `Cache-Control` |
| `stale-while-revalidate=N` | Cloud CDN serves the stale copy for up to N seconds while it revalidates |
| `Set-Cookie` | Cloud CDN does not cache the response |

Sources: [Caching overview](https://docs.cloud.google.com/cdn/docs/caching), [Content delivery best practices](https://docs.cloud.google.com/cdn/docs/best-practices).

`FORCE_CACHE_ALL` overrides `no-store`, `private`, and `no-cache`, but not a `Vary` header. A `Vary` header with a value outside the allowed list prevents caching. If the request has an `Authorization` header, Cloud CDN caches the response only if it has `public`, `must-revalidate`, or `s-maxage`. `FORCE_CACHE_ALL` removes this check ([Caching overview](https://docs.cloud.google.com/cdn/docs/caching)).

### TTLs

The default client TTL and default TTL are 3,600 seconds, and the default maximum TTL is 86,400 seconds. Cloud CDN treats an expiration time over 30 days as 30 days ([Caching overview](https://docs.cloud.google.com/cdn/docs/caching)). Set `--default-ttl=0` to make Cloud CDN revalidate each response at the origin. With `USE_ORIGIN_HEADERS`, you cannot set a default TTL ([Change TTL settings and overrides](https://docs.cloud.google.com/cdn/docs/using-ttl-overrides)). A cache entry can be evicted before it expires, and an entry with no access for 30 days is evicted ([Caching overview](https://docs.cloud.google.com/cdn/docs/caching)).

### Cache keys

For a backend service, the default cache key is the full request URI: protocol, host, path, and query string. For a backend bucket, the key omits the protocol and host. You can omit the protocol, the host, or the query string, or include or exclude named query parameters. A backend bucket supports only an include list. You can also add request headers to the key, and named cookies on a backend service ([Caching overview](https://docs.cloud.google.com/cdn/docs/caching)). Custom cache keys stop Cloud CDN from splitting one object into many cache entries, which raises the cache hit ratio ([Content delivery best practices](https://docs.cloud.google.com/cdn/docs/best-practices)).

### Updating cached content

Google recommends versioned URLs as the default, because versioning is free. Add a version to the URL, for example `file.ext?v=100`, `file_v100.ext`, or `/v100/file.ext`, and use a long expiration time ([Content delivery best practices](https://docs.cloud.google.com/cdn/docs/best-practices)). For a backend bucket, add the version parameter to the query string include list. By default, a backend bucket key includes only query parameters that Cloud Storage knows ([Caching overview](https://docs.cloud.google.com/cdn/docs/caching)). Google also recommends that you upload each new version with a unique file name, such as `file_v2.css`, and not update existing files. A query parameter such as `file.css?v=2` does not stop Cloud CDN from caching a partly uploaded file ([Content delivery best practices](https://docs.cloud.google.com/cdn/docs/best-practices)). Invalidation is for exceptional cases, such as content that you must remove for legal reasons ([Content delivery best practices](https://docs.cloud.google.com/cdn/docs/best-practices)). Invalidation has these limits ([Cache invalidation overview](https://docs.cloud.google.com/cdn/docs/cache-invalidation-overview)):

- You can send up to 500 invalidation requests per minute. Each request takes effect in about 10 seconds.
- A path can end with `*` to match a prefix. You cannot invalidate one query string variant of a path.
- Invalidation does not clear browser caches or third-party caches.

```bash
# Turn on Cloud CDN for the backend service
gcloud compute backend-services update BACKEND_SERVICE_NAME \
    --enable-cdn --global

# Set the cache mode
gcloud compute backend-services update BACKEND_SERVICE_NAME \
    --cache-mode=CACHE_ALL_STATIC

# Invalidate one object (exceptional cases only)
gcloud compute url-maps invalidate-cdn-cache URL_MAP_NAME \
    --path "/images/file.jpg"
```

Sources: [Set up a global external Application Load Balancer with Cloud Run, App Engine, or Cloud Run functions](https://docs.cloud.google.com/load-balancing/docs/https/setup-global-ext-https-serverless), [Change cache modes](https://docs.cloud.google.com/cdn/docs/using-cache-modes), [Invalidate cached content](https://docs.cloud.google.com/cdn/docs/invalidating-cached-content).

### Cloud CDN with IAP and GKE

IAP and Cloud CDN cannot be on the same backend service ([Serverless network endpoint groups overview](https://docs.cloud.google.com/load-balancing/docs/negs/serverless-neg-concepts)). On GKE Gateway, set cache keys and TTLs for each path with a `GCPHTTPFilter` in the `HTTPRoute`. Cloud CDN and IAP do not work on the same route ([Content delivery best practices](https://docs.cloud.google.com/cdn/docs/best-practices)). With GKE Ingress, configure Cloud CDN in a `BackendConfig`. One `BackendConfig` cannot enable both IAP and Cloud CDN ([Ingress configuration](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/ingress-configuration)). Google recommends Cloud Armor together with Cloud CDN ([Content delivery best practices](https://docs.cloud.google.com/cdn/docs/best-practices)). Do not sign URLs that give access to private, per-user information. A response to a signed URL can be cached whatever its `Cache-Control` header says ([Caching overview](https://docs.cloud.google.com/cdn/docs/caching)). The [signed URLs page](note:1.3-signed-urls) covers access to private objects.

## Exam traps

- **Cache keys with no TTL under `volatile-lru`.** Redis has no keys to evict, and memory fills up. Set TTLs ([Memory management best practices](https://docs.cloud.google.com/memorystore/docs/redis/memory-management-best-practices)).
- **A global variable as a cache that all Cloud Run instances share.** Each instance has its own memory. Use Memorystore ([General development tips](https://docs.cloud.google.com/run/docs/tips/general)).
- **Session affinity to keep a per-instance cache correct.** Affinity is best effort. Keep the source of truth in a shared store ([Set session affinity for services](https://docs.cloud.google.com/run/docs/configuring/session-affinity)).
- **Memorystore for Memcached in a new design.** It is deprecated. Use Memorystore for Valkey ([Memorystore for Memcached release notes](https://docs.cloud.google.com/memorystore/docs/memcached/release-notes)).
- **A Serverless VPC Access connector as the first choice from Cloud Run to Memorystore for Redis.** Google recommends Direct VPC egress ([Connect to a Redis instance from a Cloud Run service](https://docs.cloud.google.com/memorystore/docs/redis/connect-redis-instance-cloud-run)).
- **The Basic Tier of Memorystore for Redis for production.** It has no replication and no automatic failover ([Memorystore for Redis overview](https://docs.cloud.google.com/memorystore/docs/redis/memorystore-for-redis-overview)).
- **No data loss on failover.** Replication is asynchronous, so a failover can lose acknowledged writes ([High availability and replicas](https://docs.cloud.google.com/memorystore/docs/valkey/ha-and-replicas)).
- **AOF persistence on Memorystore for Redis.** It supports RDB snapshots only. Valkey and Redis Cluster support AOF ([Memorystore for Redis overview](https://docs.cloud.google.com/memorystore/docs/redis/memorystore-for-redis-overview), [Persistence overview (Valkey)](https://docs.cloud.google.com/memorystore/docs/valkey/persistence-overview)).
- **An app that fails when the cache is down.** Fall back to the database, and retry the cache with exponential backoff ([Best practices (Memcached)](https://docs.cloud.google.com/memorystore/docs/memcached/best-practices)).
- **HTML or JSON responses with no `Cache-Control` header.** `CACHE_ALL_STATIC` does not cache them ([Caching overview](https://docs.cloud.google.com/cdn/docs/caching)).
- **`FORCE_CACHE_ALL` on a backend that serves per-user content.** Cloud CDN caches the private responses ([Caching overview](https://docs.cloud.google.com/cdn/docs/caching)).
- **Invalidation after every deploy.** It is rate limited and does not clear browser caches. Use versioned URLs ([Content delivery best practices](https://docs.cloud.google.com/cdn/docs/best-practices), [Cache invalidation overview](https://docs.cloud.google.com/cdn/docs/cache-invalidation-overview)).
- **`?v=2` cache busting on a backend bucket with the default cache key.** The default key ignores unknown query parameters. Add the parameter to the include list, or change the file name ([Caching overview](https://docs.cloud.google.com/cdn/docs/caching)).
- **Cloud CDN and IAP on the same backend service.** This is not supported ([Serverless network endpoint groups overview](https://docs.cloud.google.com/load-balancing/docs/negs/serverless-neg-concepts)).
- **Cloud CDN on a regional external Application Load Balancer.** Cloud CDN needs the global external or classic load balancer ([Cloud CDN overview](https://docs.cloud.google.com/cdn/docs/overview)).
