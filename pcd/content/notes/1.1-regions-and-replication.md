## Why it matters

Each Google Cloud resource is zonal, regional, multi-regional, or global. This location scope decides which outage stops the resource, and which failover you must build yourself. The exam gives an availability, latency, or recovery requirement and asks for the configuration with the least effort that meets it. Know which services move between zones automatically, and which need your design for a region outage.

## Key points

- **A zone is a single failure domain.** A region has three or more zones. To protect an app against zone failures, deploy it across several zones ([Geography and regions](https://docs.cloud.google.com/docs/geography-and-regions)).
- **More locations give a higher availability target.** The infrastructure target is 99.9% for a zonal deployment, 99.99% for a regional one, and 99.999% for a multi-regional or global one ([Comparative analysis of Google Cloud deployment archetypes](https://docs.cloud.google.com/architecture/deployment-archetypes/comparison)).
- **Cloud Run is regional.** It spreads instances across the zones of a region and moves traffic away from a failed zone. It never sends traffic to another region ([Architecting disaster recovery for cloud infrastructure outages](https://docs.cloud.google.com/architecture/disaster-recovery)).
- **Use regional GKE clusters for production.** A regional cluster has control plane replicas in several zones. Autopilot clusters are always regional. You cannot change a cluster between zonal and regional after creation ([About cluster configuration choices](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/configuration-overview)).
- **Compute Engine VMs are zonal.** A regional managed instance group (MIG) spreads identical VMs across zones. Google recommends regional MIGs over zonal MIGs ([About regional MIGs](https://docs.cloud.google.com/compute/docs/instance-groups/regional-migs)).
- **Cloud SQL high availability (HA) protects against a zone outage only.** The standby instance is in a second zone of the same region. For a region outage, add a cross-region read replica ([Architecting disaster recovery for cloud infrastructure outages](https://docs.cloud.google.com/architecture/disaster-recovery)).
- **Multi-region databases continue after the loss of a region.** Spanner dual-region and multi-region configurations (Enterprise Plus edition) and Firestore multi-region locations replicate synchronously across regions ([Architecting disaster recovery for cloud infrastructure outages](https://docs.cloud.google.com/architecture/disaster-recovery), [Regional, dual-region, and multi-region configurations](https://docs.cloud.google.com/spanner/docs/instance-configurations)).
- **Dual-region and multi-region buckets fail over automatically.** You do not change storage paths. New objects reach the second region asynchronously ([Bucket locations](https://docs.cloud.google.com/storage/docs/locations)).
- **Region choice affects latency.** Put compute near users and near its data. A global load balancer has one anycast IP address and sends each user to the closest region with available capacity ([Best practices for Compute Engine regions selection](https://docs.cloud.google.com/solutions/best-practices-compute-engine-region-selection), [Cloud Load Balancing overview](https://docs.cloud.google.com/load-balancing/docs/load-balancing-overview)).
- **RTO and RPO set the design.** The recovery time objective (RTO) is the maximum time that the app can be offline. The recovery point objective (RPO) is the maximum time period in which data can be lost. Smaller values cost more ([Disaster recovery planning guide](https://docs.cloud.google.com/architecture/dr-scenarios-planning-guide)).

## Location scopes

| Scope | Effect of an outage | Examples |
|---|---|---|
| Zonal | A zone outage can stop the resource | Compute Engine VMs, zonal disks, the control plane of a zonal GKE cluster |
| Regional | The resource continues in the other zones. A region outage stops it | Cloud Run services, regional MIGs, regional GKE clusters, Cloud SQL HA instances, regional buckets, subnets |
| Multi-regional | The resource continues after the loss of one region, with a trade-off in latency or consistency | Spanner dual-region and multi-region, Firestore multi-region, dual-region and multi-region buckets |
| Global | Resources in any region can use it | VPC networks, firewall rules, images, snapshots, global external IP addresses, Pub/Sub topics |

Sources: [Global, regional, and zonal resources](https://docs.cloud.google.com/compute/docs/regions-zones/global-regional-zonal-resources), [Geography and regions](https://docs.cloud.google.com/docs/geography-and-regions), [Architecting disaster recovery for cloud infrastructure outages](https://docs.cloud.google.com/architecture/disaster-recovery), [About cluster configuration choices](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/configuration-overview).

A location scope is not a deployment design. A VM is zonal, but VMs in several zones of a region give a regional deployment ([Google Cloud deployment archetypes](https://docs.cloud.google.com/architecture/deployment-archetypes)). Communication inside a region is usually cheaper and faster than communication between regions ([Regions and zones](https://docs.cloud.google.com/compute/docs/regions-zones)).

### Choosing how many zones and regions

| Deployment | Availability target | RTO for a zone outage | RTO for a region outage | Cost | Use for |
|---|---|---|---|---|---|
| Zonal | 99.9% | Hours or days | Hours or days | Low | Development and test, license-restricted software |
| Regional | 99.99% | Near zero | Hours or days | Medium | Highly available apps for users in one area, data residency |
| Multi-regional | 99.999% | Near zero | Near zero | High | Users in several areas, low user latency |
| Global | 99.999% | Near zero | Near zero | Medium | Users worldwide, with global resources |

Sources: [Google Cloud deployment archetypes](https://docs.cloud.google.com/architecture/deployment-archetypes), [Comparative analysis of Google Cloud deployment archetypes](https://docs.cloud.google.com/architecture/deployment-archetypes/comparison).

A near-zero RTO needs synchronous data replication ([Comparative analysis of Google Cloud deployment archetypes](https://docs.cloud.google.com/architecture/deployment-archetypes/comparison)).

## Zone and region outages by service

| Service | Location choice | Zone outage | Region outage |
|---|---|---|---|
| Compute Engine | VM: one zone. MIG: one zone, or several zones of a region | The VM stops. A regional MIG serves from the other zones | Run a regional MIG in each region |
| GKE | Autopilot: regional. Standard: zonal or regional | Regional cluster: the control plane and the other zones continue | Run a regional cluster in each region, with Multi Cluster Ingress or a multi-cluster Gateway |
| Cloud Run | One region. A multi-region service deploys a copy to each listed region | Automatic | Deploy to several regions behind a global external Application Load Balancer |
| Cloud SQL | Standalone instance (one zone) or HA instance (two zones) | HA: automatic failover in about 60 seconds. Standalone: manual recovery | Promote a cross-region read replica manually |
| AlloyDB | HA primary instance with nodes in two zones | Automatic failover | Promote a secondary cluster in another region |
| Spanner | Regional, dual-region, or multi-region | Automatic | Dual-region and multi-region: automatic. Regional: copy backups to another region |
| Firestore | Regional or multi-region. You cannot change it later | Automatic | Only a multi-region location continues |
| Bigtable | Clusters in up to 8 regions, one cluster per zone | Multi-cluster routing: automatic | Multi-cluster routing: automatic, but recent writes can be missing |
| Cloud Storage | Zone (Rapid Bucket), region, dual-region, or multi-region | Region, dual-region, and multi-region: automatic | Dual-region and multi-region: automatic. Regional bucket: offline |
| Memorystore for Valkey | HA instance: replicas in other zones | Automatic failover in tens of seconds | Switch over to, or detach, a secondary instance in another region |
| Memorystore for Redis | Basic Tier: one node. Standard Tier: replication across zones | Basic Tier: full cache flush. Standard Tier: automatic failover | Restore an export from a bucket in another region |

Sources: [Architecting disaster recovery for cloud infrastructure outages](https://docs.cloud.google.com/architecture/disaster-recovery), [About regional MIGs](https://docs.cloud.google.com/compute/docs/instance-groups/regional-migs), [About cluster configuration choices](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/configuration-overview), [About high availability](https://docs.cloud.google.com/sql/docs/postgres/high-availability), [Cross-region replication overview](https://docs.cloud.google.com/alloydb/docs/cross-region-replication/about-cross-region-replication), [Regional, dual-region, and multi-region configurations](https://docs.cloud.google.com/spanner/docs/instance-configurations), [Firestore locations](https://docs.cloud.google.com/firestore/native/docs/locations), [Bigtable replication overview](https://docs.cloud.google.com/bigtable/docs/replication-overview), [Bucket locations](https://docs.cloud.google.com/storage/docs/locations), [High availability and replicas](https://docs.cloud.google.com/memorystore/docs/valkey/ha-and-replicas), [About cross-region replication](https://docs.cloud.google.com/memorystore/docs/valkey/about-cross-region-replication), [Redis tier capabilities](https://docs.cloud.google.com/memorystore/docs/redis/redis-tiers).

## Zonal failover: mostly automatic

Regional resources fail over between zones with no action from you. For zonal resources, you build the redundancy yourself. Put VMs in several zones, use a load balancer that routes away from an unhealthy zone, and replicate disks to a second zone ([Architecting disaster recovery for cloud infrastructure outages](https://docs.cloud.google.com/architecture/disaster-recovery)).

- **Cloud Run.** You configure nothing. The scheduler in each zone knows the load in the other zones and keeps extra capacity for a zone failure ([Architecting disaster recovery for cloud infrastructure outages](https://docs.cloud.google.com/architecture/disaster-recovery)). For GPUs, you can turn off zonal redundancy for a lower cost. Failover is then best effort ([GPU support for services](https://docs.cloud.google.com/run/docs/configuring/services/gpu)).
- **GKE.** In a regional cluster, a zone outage does not affect the control plane or the nodes in the other zones. Autopilot rebalances the nodes automatically. In Standard, you rebalance manually or with the cluster autoscaler ([Regional clusters](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/regional-clusters)). In a zonal cluster, workloads run during a control plane outage, but you cannot change the cluster ([About cluster configuration choices](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/configuration-overview)).
- **Disks.** Regional Persistent Disk and Hyperdisk Balanced High Availability replicate synchronously to a second zone. After a zone outage, you force-attach the disk to a VM in the other zone. These disks cost double per byte ([Build HA services using synchronously replicated disks](https://docs.cloud.google.com/compute/docs/disks/high-availability-regional-persistent-disk), [Architecting disaster recovery for cloud infrastructure outages](https://docs.cloud.google.com/architecture/disaster-recovery)).
- **Cloud SQL.** An HA failover takes about 60 seconds, and clients reconnect to the same IP address. An HA instance costs twice as much as a standalone instance. Cloud SQL does not recover a standalone instance from a zone outage automatically ([About high availability](https://docs.cloud.google.com/sql/docs/postgres/high-availability)).
- **Memorystore.** Valkey HA instances and the Redis Standard Tier fail over to a replica automatically, but they can lose acknowledged writes ([High availability and replicas](https://docs.cloud.google.com/memorystore/docs/valkey/ha-and-replicas), [High availability for Memorystore for Redis](https://docs.cloud.google.com/memorystore/docs/redis/high-availability-for-memorystore-for-redis)). See the [caching page](note:1.1-caching).

To add HA to an existing Cloud SQL instance, patch its availability type. The change restarts the instance. Then trigger a failover to see how your app reacts.

Source: [Enable and disable high availability](https://docs.cloud.google.com/sql/docs/postgres/configure-ha).

```bash
gcloud sql instances patch INSTANCE_NAME \
  --availability-type REGIONAL

gcloud sql instances failover PRIMARY_INSTANCE_NAME
```

### Overprovision for the loss of a zone

After a zone outage, a regional MIG serves from the instances in the remaining zones. It does not add instances there unless you set up autoscaling. So Google strongly recommends overprovisioning: the remaining zones must still meet your minimum capacity ([About regional MIGs](https://docs.cloud.google.com/compute/docs/instance-groups/regional-migs)).

| Zones in the MIG | Extra instances | Group size, compared to the need |
|---|---|---|
| 2 | +100% | 200% |
| 3 (the default) | +50% | 150% |
| 4 | +33% | 133% |

Source: [About regional MIGs](https://docs.cloud.google.com/compute/docs/instance-groups/regional-migs).

For example, an app that needs 20 VMs gets a regional MIG of 30 VMs in three zones. If one zone fails, 20 VMs remain. You choose the zones when you create the group, and you cannot change them later ([About regional MIGs](https://docs.cloud.google.com/compute/docs/instance-groups/regional-migs)).

Source: [Create a MIG with VMs in multiple zones in a region](https://docs.cloud.google.com/compute/docs/instance-groups/distributing-instances-with-regional-instance-groups).

```bash
gcloud compute instance-groups managed create example-rmig \
    --template projects/my-project/regions/us-east1/instanceTemplates/1234567890 \
    --size 30 \
    --region us-east1
```

The same rule applies to GKE Standard with the cluster autoscaler. For a three-zone cluster at 150%, set a maximum of six nodes per zone, not four. If one zone fails, the cluster scales to 12 nodes in the other zones ([Regional clusters](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/regional-clusters)).

## Regional failover: you design it

A regional service stops when its region has an outage. For example, Cloud Run becomes available again only when the outage ends ([Architecting disaster recovery for cloud infrastructure outages](https://docs.cloud.google.com/architecture/disaster-recovery)). To continue serving, you need four parts:

1. **Compute in a second region.** Deploy the Cloud Run service to several regions. Or run a regional GKE cluster or a regional MIG in each region ([Architecting disaster recovery for cloud infrastructure outages](https://docs.cloud.google.com/architecture/disaster-recovery)).
2. **One entry point.** Use a global external Application Load Balancer for public traffic, or a cross-region internal Application Load Balancer for private traffic ([Automate cross-region failover with Cloud Run service health](https://docs.cloud.google.com/run/docs/configuring/configure-service-health)). See the [load balancing page](note:1.1-load-balancing).
3. **A health signal** that tells the load balancer that a region is unhealthy.
4. **Data in the second region.** Use a multi-region database or bucket, or replicate the data yourself ([Geography and regions](https://docs.cloud.google.com/docs/geography-and-regions)).

Test the region failover regularly ([Architecting disaster recovery for cloud infrastructure outages](https://docs.cloud.google.com/architecture/disaster-recovery)).

### Cloud Run in several regions

The `--regions` flag of `gcloud run deploy` deploys one multi-region service to a list of regions. Then you add a serverless NEG for each region to a global load balancer ([Serve traffic from multiple regions](https://docs.cloud.google.com/run/docs/multiple-regions)).

Source: [Automate cross-region failover with Cloud Run service health](https://docs.cloud.google.com/run/docs/configuring/configure-service-health).

```bash
gcloud run deploy SERVICE \
  --source=. \
  --regions=us-west1,europe-west1 \
  --min=10 \
  --readiness-probe httpGet.path="/are_you_ready"
```

The load balancer alone does not move traffic away from a region that is unresponsive or returns errors ([Serve traffic from multiple regions](https://docs.cloud.google.com/run/docs/multiple-regions)). Cloud Run service health adds this function, with these rules ([Automate cross-region failover with Cloud Run service health](https://docs.cloud.google.com/run/docs/configuring/configure-service-health)):

- A regional service is healthy when 60% or more of its instances pass their readiness probes.
- The load balancer moves traffic away from an unhealthy region. After recovery, it moves traffic back gradually.
- Each region needs at least one minimum instance. Failover needs services in at least two regions.
- The load balancer treats a revision without probes as healthy.

Other points for multi-region Cloud Run ([Serve traffic from multiple regions](https://docs.cloud.google.com/run/docs/multiple-regions)):

- The minimum instances value applies in each region. Two regions with `--min=10` keep 20 instances.
- Outlier detection is another option. It finds unhealthy services from their HTTP error rate.
- A client cannot know which region gets its request. For an authenticated service, configure a custom audience.

### GKE and Compute Engine in several regions

For GKE, create a regional cluster in each region. Multi Cluster Ingress or a multi-cluster Gateway configures one load balancer for the clusters from a config cluster ([Multi Cluster Ingress](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/multi-cluster-ingress), [About multi-cluster Gateways](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/multi-cluster-gateways)). Both APIs are GA ([Choose your multi-cluster load balancing API for GKE](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/choose-mc-lb-api)). Use a regional cluster as the config cluster. If a zonal config cluster is in a failed zone, you must fail over manually ([Architecting disaster recovery for cloud infrastructure outages](https://docs.cloud.google.com/architecture/disaster-recovery)).

For stateless apps on Compute Engine, run a regional MIG in each region behind a global load balancer ([Architecting disaster recovery for cloud infrastructure outages](https://docs.cloud.google.com/architecture/disaster-recovery)).

### Data failover between regions

| Data | Failover to another region | Data at risk |
|---|---|---|
| Spanner multi-region | Automatic. The leaders move to the second read-write region | None |
| Spanner dual-region | Automatic, in up to 45 minutes. A manual failover usually completes within one minute, but then you must fail back manually | None (zero RPO) |
| Firestore multi-region | Automatic | None |
| Dual-region or multi-region bucket | Automatic | New objects not yet copied. Turbo replication (dual-region only) targets 15 minutes |
| Bigtable with multi-cluster routing | Automatic | Writes not yet replicated |
| Cloud SQL | You promote a cross-region read replica and redirect the app to it | Transactions that did not reach the replica |
| AlloyDB | You promote a secondary cluster | Transactions that did not reach the secondary cluster |
| Disks with Asynchronous Replication | You stop replication, attach the secondary disks to VMs in the second region, and change the network addresses | Writes not yet replicated |
| Memorystore for Valkey | You switch over to, or detach, a secondary instance | Writes not yet replicated |

Sources: [Regional, dual-region, and multi-region configurations](https://docs.cloud.google.com/spanner/docs/instance-configurations), [Architecting disaster recovery for cloud infrastructure outages](https://docs.cloud.google.com/architecture/disaster-recovery), [Bucket locations](https://docs.cloud.google.com/storage/docs/locations), [About Asynchronous Replication](https://docs.cloud.google.com/compute/docs/disks/async-pd/about), [Cross-region replication overview](https://docs.cloud.google.com/alloydb/docs/cross-region-replication/about-cross-region-replication), [About cross-region replication](https://docs.cloud.google.com/memorystore/docs/valkey/about-cross-region-replication).

## Latency and region choice

Choose the regions early. It is difficult, and sometimes costly, to move a live app and its data to another region. Compare latency, price, colocation with other services, machine-type availability, regional quotas, and the carbon-free energy percentage. Prices differ by region, and data that you sync between regions has transfer charges ([Best practices for Compute Engine regions selection](https://docs.cloud.google.com/solutions/best-practices-compute-engine-region-selection)).

User latency has four parts. They are the last mile, the path to the Google edge, the path from the edge to the region, and the app. Region choice changes only the path to the region. To estimate it, allow 1 ms of round-trip time for each 100 km. The network path is usually 1.5 to 2 times the map distance ([Best practices for Compute Engine regions selection](https://docs.cloud.google.com/solutions/best-practices-compute-engine-region-selection)).

| Deployment pattern | Use when | Trade-off |
|---|---|---|
| One region | Most mobile apps and apps that are not latency-critical. Add Cloud CDN and TLS termination at the edge | The simplest design |
| Frontend in several regions, backend in one region | Most requests need few calls to the backend, for example with a cache or asynchronous writes | No data sync between regions |
| Frontend and backend in several regions | Every request must complete locally | You replicate all data to all regions, for example with Spanner multi-region |
| Parallel apps in several regions | Each user belongs to one site, for example a country domain or the region of a SaaS account | Only a small part of the data is shared |

Source: [Best practices for Compute Engine regions selection](https://docs.cloud.google.com/solutions/best-practices-compute-engine-region-selection).

Ways to lower latency:

- **Premium Tier** is the default network tier. Traffic enters Google's network at the point of presence (PoP) closest to the user. Standard Tier traffic enters near the region and costs less. Global load balancers and Cloud CDN need Premium Tier ([Network Service Tiers overview](https://docs.cloud.google.com/network-tiers/docs/overview)).
- **A global load balancer** ends TCP and TLS sessions at the edge. This lowers latency also for an app in one region ([Best practices for Compute Engine regions selection](https://docs.cloud.google.com/solutions/best-practices-compute-engine-region-selection)).
- **A cache** for backend answers helps when the frontend and backend are in different regions ([Best practices for Compute Engine regions selection](https://docs.cloud.google.com/solutions/best-practices-compute-engine-region-selection)). See the [caching page](note:1.1-caching).
- **Data placement.** A Firestore regional location has lower write latency than a multi-region location ([Firestore locations](https://docs.cloud.google.com/firestore/native/docs/locations)). In Spanner, put the default leader region near most of the write traffic ([Regional, dual-region, and multi-region configurations](https://docs.cloud.google.com/spanner/docs/instance-configurations)). Keep data in the same region as the compute that reads it ([Bucket locations](https://docs.cloud.google.com/storage/docs/locations)).
- **One region for a global user base:** choose a US region. The US connects to most other regions, and traffic between Europe and Asia goes through the US ([Best practices for Compute Engine regions selection](https://docs.cloud.google.com/solutions/best-practices-compute-engine-region-selection)).

## RTO, RPO, and DR patterns

Disaster recovery (DR) planning starts with an RTO and an RPO for each app. Smaller values cost more and add complexity ([Disaster recovery planning guide](https://docs.cloud.google.com/architecture/dr-scenarios-planning-guide)). The pattern shows how fast the app recovers:

| Pattern | Example on Google Cloud | Recovery |
|---|---|---|
| Cold | A MIG with a target size of one. A startup script creates the disk from the newest snapshot | The MIG recreates a failed VM. After a zone failure, you create a MIG in another zone manually. The RPO is the time since the last snapshot |
| Warm | A static site in Cloud Storage on standby | When the app fails, you point Cloud DNS to the static site |
| Hot | A regional MIG behind a global load balancer, with Cloud SQL | Failover is automatic. You do nothing |

Source: [Disaster recovery scenarios for applications](https://docs.cloud.google.com/architecture/dr-scenarios-for-applications).

One app can use several patterns. In an online store, the purchase path needs a hot pattern, and the order email can use a warm or cold pattern ([Disaster recovery scenarios for applications](https://docs.cloud.google.com/architecture/dr-scenarios-for-applications)). To check a design, ask what happens when a zone or a region has an outage of 1, 5, 10, or 30 minutes ([Architecting disaster recovery for cloud infrastructure outages](https://docs.cloud.google.com/architecture/disaster-recovery)).

## Exam traps

- **Cloud SQL HA for a region outage.** The primary and standby instances are in one region. Add a cross-region read replica, and promote it in a region outage ([Architecting disaster recovery for cloud infrastructure outages](https://docs.cloud.google.com/architecture/disaster-recovery)).
- **"Cloud Run fails over to another region."** It does not. Deploy the service to several regions behind a global external Application Load Balancer ([Architecting disaster recovery for cloud infrastructure outages](https://docs.cloud.google.com/architecture/disaster-recovery), [Serve traffic from multiple regions](https://docs.cloud.google.com/run/docs/multiple-regions)).
- **A multi-region Cloud Run setup with no health signal.** Without service health or outlier detection, the load balancer keeps sending traffic to a region that returns errors ([Serve traffic from multiple regions](https://docs.cloud.google.com/run/docs/multiple-regions)).
- **Service health with zero minimum instances.** Service health needs at least one minimum instance in each region ([Automate cross-region failover with Cloud Run service health](https://docs.cloud.google.com/run/docs/configuring/configure-service-health)).
- **A zonal GKE cluster for production.** A control plane outage blocks all cluster changes, and you cannot convert the cluster to regional later ([About cluster configuration choices](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/configuration-overview)).
- **A regional MIG sized for normal load.** After a zone outage, the MIG adds no instances without autoscaling. Overprovision by 50% for three zones ([About regional MIGs](https://docs.cloud.google.com/compute/docs/instance-groups/regional-migs)).
- **A BigQuery multi-region for DR.** BigQuery stores multi-region data in one region. For cross-region redundancy, use managed disaster recovery. BigQuery plans to stop using the term "multi-region" and to list `US` and `EU` as single regions, with no change to data residency ([BigQuery locations](https://docs.cloud.google.com/bigquery/docs/locations)).
- **The Multi-Regional storage class.** It is a legacy storage class. Choose a dual-region or multi-region location with Standard storage ([Storage classes](https://docs.cloud.google.com/storage/docs/storage-classes)).
- **Turbo replication on a multi-region bucket.** Turbo replication is available only for dual-region buckets ([Data availability and durability](https://docs.cloud.google.com/storage/docs/availability-durability)).
- **Waiting for the automatic Spanner dual-region failover.** It can take up to 45 minutes. For a shorter RTO, monitor quorum health and fail over manually ([Regional, dual-region, and multi-region configurations](https://docs.cloud.google.com/spanner/docs/instance-configurations)).
- **A DR region to lower latency.** A backup region is not in the serving path, so user latency does not change ([Best practices for Compute Engine regions selection](https://docs.cloud.google.com/solutions/best-practices-compute-engine-region-selection)).
