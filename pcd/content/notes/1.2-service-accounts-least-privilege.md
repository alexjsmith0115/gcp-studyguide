## Why it matters

Every workload runs as an identity, and on Google Cloud that identity is usually a service account. The developer decides which service account each service uses, which roles it gets, and on which resource. The exam tests the risk of default service accounts and the difference between attaching and impersonating a service account. It also tests the three role types and the tools that find and remove excess access.

## Key points

- A service account is both a principal and a resource. As a principal, it gets roles on resources. As a resource, other principals get roles on it, for example the permission to attach it ([Service accounts overview](https://docs.cloud.google.com/iam/docs/service-account-overview)).
- There are two types: user-managed service accounts and service agents. Default service accounts are user-managed service accounts that some services create. Google creates and manages service agents ([Types of service accounts](https://docs.cloud.google.com/iam/docs/service-account-types)).
- The Compute Engine and App Engine default service accounts can get the Editor role on the project. The `iam.automaticIamGrantsForDefaultServiceAccounts` constraint stops this grant, and it is enforced by default in organizations created after May 3, 2024 ([Types of service accounts](https://docs.cloud.google.com/iam/docs/service-account-types)).
- Create a dedicated service account for each application, and do not use default service accounts ([Best practices for using service accounts securely](https://docs.cloud.google.com/iam/docs/best-practices-service-accounts)).
- Service Account User (`roles/iam.serviceAccountUser`) lets a principal attach a service account to a resource. Service Account Token Creator (`roles/iam.serviceAccountTokenCreator`) lets a principal create short-lived credentials, which is impersonation ([Roles for service account authentication](https://docs.cloud.google.com/iam/docs/service-account-permissions)).
- Prefer predefined roles. Use a custom role when every predefined role with the permission also grants too much. Do not grant basic roles in production unless there is no alternative ([Choose which type of role to use](https://docs.cloud.google.com/iam/docs/choose-role-type)).
- Grant roles at the smallest scope, for example the Pub/Sub Publisher role on one topic instead of on the project ([Use IAM securely](https://docs.cloud.google.com/iam/docs/using-iam-securely)).
- IAM Conditions add a CEL expression to a role binding, for example an expiry time or a resource name prefix ([Overview of IAM Conditions](https://docs.cloud.google.com/iam/docs/conditions-overview)).
- Role recommendations compare the permissions of a principal with the permissions that it used in the last 90 days. They suggest how to remove or replace a role ([Overview of role recommendations](https://docs.cloud.google.com/policy-intelligence/docs/role-recommendations-overview)).
- Do not revoke the roles that Google grants to service agents, unless a role recommendation suggests it ([Types of service accounts](https://docs.cloud.google.com/iam/docs/service-account-types)).

## Service account types

| Type | Who creates and manages it | Example email | What to do |
|---|---|---|---|
| User-managed | You | `SERVICE_ACCOUNT_NAME@PROJECT_ID.iam.gserviceaccount.com` | Create one for each application. Grant only the roles that it needs |
| Default (user-managed) | Created when you enable or use some services. You manage it | `PROJECT_NUMBER-compute@developer.gserviceaccount.com`, `PROJECT_ID@appspot.gserviceaccount.com` | Avoid it. It can have the Editor role |
| Service agent | Google creates and manages it. It is not in your project | The Cloud Run service agent ends in `@serverless-robot-prod.iam.gserviceaccount.com` | Some need roles from you so that the service works. Do not revoke its roles |

Sources: [Types of service accounts](https://docs.cloud.google.com/iam/docs/service-account-types), [Introduction to service identity](https://docs.cloud.google.com/run/docs/securing/service-identity), [Deploy container images to Cloud Run services](https://docs.cloud.google.com/run/docs/deploying).

Lifecycle facts ([Service accounts overview](https://docs.cloud.google.com/iam/docs/service-account-overview)):

- A service account stays in the project where you create it. You cannot move it to a different project.
- Service account insights show which service accounts did not authenticate in the past 90 days. Disable a service account before you delete it, so that you can enable it again if something still uses it.
- Role bindings use the unique ID of a service account, not its email address. If you delete a service account and create a new one with the same name, the old bindings do not apply to the new one. Resources are also not attached to it.
- The `iam.disableServiceAccountCreation` organization policy constraint blocks the creation of service accounts.

## Default service accounts and their broad roles

Some services create a default service account when you enable their API. The default service account can get the Editor role, which can read and change all resources in the project. Google Cloud services do not need this grant, because they use service agents, not default service accounts, to access your resources ([Best practices for using service accounts securely](https://docs.cloud.google.com/iam/docs/best-practices-service-accounts)).

Where default service accounts appear:

- **Cloud Run.** If you do not specify a service account, Cloud Run uses the Compute Engine default service account as the service identity ([Introduction to service identity](https://docs.cloud.google.com/run/docs/securing/service-identity)).
- **Compute Engine.** A VM without a specified service account can use the default service account. A role that you grant to the default service account applies to every VM that runs as it ([Best practices for using service accounts securely](https://docs.cloud.google.com/iam/docs/best-practices-service-accounts), [Change the attached service account](https://docs.cloud.google.com/compute/docs/instances/change-service-account)).
- **GKE nodes.** By default, GKE uses the Compute Engine default service account as the node service account. Create a custom node service account with at least the Kubernetes Engine Default Node Service Account role (`roles/container.defaultNodeServiceAccount`) ([About service accounts in GKE](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/service-accounts)).

How to reduce the risk:

1. Enforce `iam.automaticIamGrantsForDefaultServiceAccounts` on the organization or folder. It does not remove the Editor role from existing default service accounts ([Best practices for using service accounts securely](https://docs.cloud.google.com/iam/docs/best-practices-service-accounts)). For the other constraints that new organizations enforce, see [Data retention and organization policies](note:1.2-retention-and-org-policy).
2. If a default service account already has Editor, replace it with less permissive roles. Use role recommendations and Policy Simulator to check the effect first ([Types of service accounts](https://docs.cloud.google.com/iam/docs/service-account-types)).
3. Attach a dedicated user-managed service account to each new workload.

## One dedicated service account per service

Sharing one service account across applications causes three problems ([Best practices for using service accounts securely](https://docs.cloud.google.com/iam/docs/best-practices-service-accounts)):

- When you retire one application, it might not be clear if the service account is still necessary.
- The access needs of the applications grow apart, so the shared account gets access to more and more resources.
- Cloud Audit Logs show the service account, not the application. You might not be able to trace an action to the correct application.

Google's checklist says the same: treat each component of the application as a separate trust boundary, with its own service account ([Use IAM securely](https://docs.cloud.google.com/iam/docs/using-iam-securely)).

| Runtime | How to attach the service account | Facts to know |
|---|---|---|
| Cloud Run | `--service-account` on `gcloud run deploy` or `gcloud run services update`, or `serviceAccountName` in the service YAML | A service that calls no Google Cloud APIs needs no roles on its service identity |
| GKE Pods | Workload Identity Federation for GKE (Workload Identity in the console): grant roles to the Kubernetes ServiceAccount | The node service account is separate. GKE uses it for system tasks such as logging, monitoring, and image pulls |
| Compute Engine VM | `--service-account` and `--scopes` on `gcloud compute instances create` | One service account per VM. To change it, stop the VM first |

Sources: [Configure service identity for services](https://docs.cloud.google.com/run/docs/configuring/services/service-identity), [About Workload Identity Federation for GKE](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/workload-identity), [Authenticate to Google Cloud APIs from GKE workloads](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/workload-identity), [About service accounts in GKE](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/service-accounts), [Service accounts (Compute Engine)](https://docs.cloud.google.com/compute/docs/access/service-accounts), [Change the attached service account](https://docs.cloud.google.com/compute/docs/instances/change-service-account).

```bash
# Create a dedicated service account
gcloud iam service-accounts create SERVICE_ACCOUNT_NAME

# Let a deployer attach it (Service Account User on this one service account)
gcloud iam service-accounts add-iam-policy-binding \
    SERVICE_ACCOUNT_NAME@PROJECT_ID.iam.gserviceaccount.com \
    --member="user:USER_EMAIL" --role=roles/iam.serviceAccountUser

# Attach it to a Cloud Run service
gcloud run deploy --image IMAGE_URL --service-account SERVICE_ACCOUNT

# Attach it to a VM, with the cloud-platform scope and IAM roles for control
gcloud compute instances create VM_NAME \
    --service-account=SERVICE_ACCOUNT_EMAIL \
    --scopes=https://www.googleapis.com/auth/cloud-platform
```

Sources: [Set up ADC for a resource with an attached service account](https://docs.cloud.google.com/docs/authentication/set-up-adc-attached-service-account), [Configure service identity for services](https://docs.cloud.google.com/run/docs/configuring/services/service-identity), [Create a VM that uses a user-managed service account](https://docs.cloud.google.com/compute/docs/access/create-enable-service-accounts-for-instances).

Do not rely on access scopes to limit a VM. Scopes are coarse: a read-only Cloud Storage scope cannot limit access to one bucket. Use a dedicated service account with fine-grained allow policies instead ([Best practices for using service accounts securely](https://docs.cloud.google.com/iam/docs/best-practices-service-accounts)). For how code gets the credentials of the attached service account, see [Authenticating code to Google Cloud](note:1.2-authenticating-to-google-cloud).

## Act as compared with impersonate

Two different roles control who can use a service account ([Roles for service account authentication](https://docs.cloud.google.com/iam/docs/service-account-permissions)):

| Role | Main permissions | What the principal can do |
|---|---|---|
| Service Account User (`roles/iam.serviceAccountUser`) | `iam.serviceAccounts.actAs` | Attach the service account to a resource. Code on the resource then runs as the service account. It cannot create short-lived credentials or use `--impersonate-service-account` |
| Service Account Token Creator (`roles/iam.serviceAccountTokenCreator`) | `getAccessToken`, `getOpenIdToken`, `implicitDelegation`, `signBlob`, `signJwt` | Create access tokens and ID tokens, sign blobs and JWTs, and use `--impersonate-service-account` |
| Service Account OpenID Connect Identity Token Creator (`roles/iam.serviceAccountOpenIdTokenCreator`) | `getOpenIdToken` | Create ID tokens only |
| Workload Identity User (`roles/iam.workloadIdentityUser`) | `getAccessToken`, `getOpenIdToken` | Impersonate service accounts from GKE workloads |

Source: [Roles for service account authentication](https://docs.cloud.google.com/iam/docs/service-account-permissions).

**Deploying needs act as.** To attach a service account, you need `iam.serviceAccounts.actAs` and permission to create the resource ([Roles for service account authentication](https://docs.cloud.google.com/iam/docs/service-account-permissions)). A Cloud Run deployer needs Cloud Run Developer (`roles/run.developer`) on the service and Service Account User on the service identity. The deployer also needs Artifact Registry Reader on the image repository. If the service identity is in a different project, the deployer also needs Token Creator on it ([Deploy container images to Cloud Run services](https://docs.cloud.google.com/run/docs/deploying)).

**Signing needs Token Creator.** `signBlob` signs any payload, such as a Cloud Storage signed URL, with the Google-managed private key of the service account. Google holds this key and never exposes it ([Roles for service account authentication](https://docs.cloud.google.com/iam/docs/service-account-permissions)). See [Signed URLs](note:1.3-signed-urls).

**Both roles can raise privileges.** A user who can impersonate or attach a service account gets its access. The permissions that allow this include `actAs`, `getAccessToken`, `getOpenIdToken`, `implicitDelegation`, `signBlob`, `signJwt`, `iam.serviceAccountKeys.create`, `deploymentmanager.deployments.create`, and `cloudbuild.builds.create`. Owner, Editor, Service Account User, Token Creator, Service Account Admin, Workload Identity User, and Cloud Build Editor contain some of them ([Best practices for using service accounts securely](https://docs.cloud.google.com/iam/docs/best-practices-service-accounts)). So:

- Grant these roles on one service account, not on the project or folder. Token Creator on a project lets the user impersonate every service account in it ([Best practices for using service accounts securely](https://docs.cloud.google.com/iam/docs/best-practices-service-accounts)).
- Do not let users impersonate a service account that has more access than they have, unless you want temporary elevation ([Best practices for using service accounts securely](https://docs.cloud.google.com/iam/docs/best-practices-service-accounts)).
- Any code on a VM can get a token for the attached service account from the metadata server. Do not run code from less protected sources on a resource with a privileged service account ([Best practices for using service accounts securely](https://docs.cloud.google.com/iam/docs/best-practices-service-accounts)).

## Basic, predefined, and custom roles

A permission has the format `SERVICE.RESOURCE.VERB`, and a role is a set of permissions ([Roles overview](https://docs.cloud.google.com/iam/docs/roles-overview)).

| Role type | Maintained by | Use it when | Limits and facts |
|---|---|---|---|
| Basic: legacy Owner, Editor, Viewer; Admin, Writer, Reader (Preview) | Google | No alternative exists, or in development and test environments | Thousands of permissions. No conditions on legacy basic roles. You cannot grant Admin, Writer, or Reader in the console |
| Predefined, for example `roles/pubsub.publisher` | Google, which updates them when it adds features | The default choice | Each role lists the lowest-level resource where you can grant it |
| Custom | You. New Google permissions are not added | Every predefined role with the permission has extra permissions, or a role recommendation suggests a custom role | Only at organization or project level, not folder. 300 per organization and 300 per project. Up to 3,000 permissions |

Sources: [Roles overview](https://docs.cloud.google.com/iam/docs/roles-overview), [Choose which type of role to use](https://docs.cloud.google.com/iam/docs/choose-role-type), [Access control with Identity and Access Management](https://docs.cloud.google.com/pubsub/docs/access-control).

More custom role facts ([Roles overview](https://docs.cloud.google.com/iam/docs/roles-overview)):

- You can grant a custom role only in the project or organization where you created it.
- Some permissions work only together. To update an allow policy, you need `getIamPolicy` and `setIamPolicy`. Start from a similar predefined role.
- After you delete a custom role, you cannot reuse its ID until the 44-day deletion process ends.
- A principal who can edit custom roles can add any permission to them. Give this ability to few people.

The legacy basic roles were once called primitive roles ([Roles overview](https://docs.cloud.google.com/iam/docs/roles-overview)). Owner can access and change almost all resources, including allow policies. To let someone manage allow policies without access to all resources, grant Project IAM Admin or Folder IAM Admin ([Use IAM securely](https://docs.cloud.google.com/iam/docs/using-iam-securely)).

## Granting on the smallest resource

Allow policies are inherited. A role on a project applies to every resource in it. For example, a user who can administer VMs on the project can administer every VM in it. The allow policy on each VM does not change this ([Use IAM securely](https://docs.cloud.google.com/iam/docs/using-iam-securely)). So grant each role on the lowest resource that the task needs:

| Task | Too broad | Least privilege |
|---|---|---|
| A service publishes to one topic | Pub/Sub Editor on the project | Pub/Sub Publisher on the topic |
| A service reads objects from one bucket | Storage Object Viewer on the project | Storage Object Viewer on the bucket, or a condition on the object name prefix |
| A developer deploys one Cloud Run service | Service Account User on the project | Service Account User on the service identity only |
| A user needs temporary access to fix a production issue | A permanent role | A conditional binding that expires |

Sources: [Use IAM securely](https://docs.cloud.google.com/iam/docs/using-iam-securely), [Access control with Identity and Access Management](https://docs.cloud.google.com/pubsub/docs/access-control), [Overview of IAM Conditions](https://docs.cloud.google.com/iam/docs/conditions-overview), [Best practices for using service accounts securely](https://docs.cloud.google.com/iam/docs/best-practices-service-accounts).

Also grant the most limited predefined role that meets the need ([Use IAM securely](https://docs.cloud.google.com/iam/docs/using-iam-securely)). For example, Storage Object Creator (`roles/storage.objectCreator`) lets a principal create objects, but not view, delete, or overwrite them. Storage Object Admin (`roles/storage.objectAdmin`) gives full control of objects, including listing, viewing, and deleting them ([IAM roles for Cloud Storage](https://docs.cloud.google.com/storage/docs/access-control/iam-roles)).

Grant roles to groups instead of individual users when possible, because it is easier to change group membership than allow policies ([Use IAM securely](https://docs.cloud.google.com/iam/docs/using-iam-securely)).

## IAM Conditions

A condition limits a role binding with a Common Expression Language (CEL) expression. It has a title, an optional description, and the expression ([Overview of IAM Conditions](https://docs.cloud.google.com/iam/docs/conditions-overview)). Expressions can use:

- **Resource attributes:** the resource type, name, service, and tags.
- **Request attributes:** the date and time. With IAP, also the access level, the URL host and path, and the destination IP address and port.

Source: [Overview of IAM Conditions](https://docs.cloud.google.com/iam/docs/conditions-overview).

```json
{
  "bindings": [
    {
      "role": "roles/storage.objectViewer",
      "members": ["serviceAccount:SERVICE_ACCOUNT_NAME@PROJECT_ID.iam.gserviceaccount.com"],
      "condition": {
        "title": "site_assets_until_2027",
        "description": "Objects in one bucket only, until 2027-01-01",
        "expression": "resource.type == 'storage.googleapis.com/Object' && resource.name.startsWith('projects/_/buckets/exampleco-site-assets/') && request.time < timestamp('2027-01-01T00:00:00Z')"
      }
    }
  ],
  "version": 3
}
```

Sources: [Overview of IAM Conditions](https://docs.cloud.google.com/iam/docs/conditions-overview), [Manage conditional role bindings](https://docs.cloud.google.com/iam/docs/managing-conditional-role-bindings).

An allow policy with conditions uses version 3. The gcloud CLI sets the version when you add a condition. In the console, the Expiring Access condition type builds a time limit for you ([Manage conditional role bindings](https://docs.cloud.google.com/iam/docs/managing-conditional-role-bindings)).

Limits that the exam tests ([Overview of IAM Conditions](https://docs.cloud.google.com/iam/docs/conditions-overview)):

- You cannot add conditions to legacy basic roles, or to grants to `allUsers` or `allAuthenticatedUsers`.
- A conditional binding does not override a binding of the same role without a condition. The principal keeps the role.
- A Cloud Storage bucket needs uniform bucket-level access for conditions in its allow policy.
- As a best practice, use 100 or fewer conditional role bindings in one allow policy.

## Find and remove excess access

**Role recommendations.** The IAM recommender compares each principal's permissions with the permissions that it used in the last 90 days. It also uses machine learning to find permissions that the principal is likely to need in the future. A recommendation suggests that you revoke a role or replace it. The replacement can be one or more predefined roles, an existing custom role, or a new project-level custom role. Except for service agents, a recommendation never increases access. It covers only IAM, not ACLs or Kubernetes RBAC. The default minimum observation period is 90 days, and for project-level recommendations you can set 30 or 60 days ([Overview of role recommendations](https://docs.cloud.google.com/policy-intelligence/docs/role-recommendations-overview)).

**Lateral movement insights.** They identify roles that let a service account in one project impersonate a service account in another project ([Overview of role recommendations](https://docs.cloud.google.com/policy-intelligence/docs/role-recommendations-overview)).

**Dedicated service accounts on Cloud Run.** Recommender also suggests dedicated service accounts with the minimum permissions for Cloud Run services ([Configure service identity for services](https://docs.cloud.google.com/run/docs/configuring/services/service-identity)).

## Service agents

Service agents are service accounts that Google creates and manages, so that a service can act on your behalf. They are not in your project's list of service accounts. The IAM page in the console hides their grants until you select **Include Google-provided role grants**. Many project-level service agents get their roles automatically, and these role names usually end in `serviceAgent` ([Types of service accounts](https://docs.cloud.google.com/iam/docs/service-account-types)).

Rules:

- Do not revoke service agent roles unless a role recommendation suggests it. Otherwise some services stop working ([Types of service accounts](https://docs.cloud.google.com/iam/docs/service-account-types)).
- If you ask Google Cloud to create a service agent before you use the service, the service agent gets no roles automatically. You must grant them ([Types of service accounts](https://docs.cloud.google.com/iam/docs/service-account-types)).
- Only user-managed service accounts can be attached to a VM. You cannot attach a service agent ([Service accounts (Compute Engine)](https://docs.cloud.google.com/compute/docs/access/service-accounts)).
- Some setups need a grant to a service agent:

| Scenario | Grant |
|---|---|
| Cloud Run deploys an image from another project | Artifact Registry Reader, in the image's project, to the Cloud Run service agent (`...@serverless-robot-prod.iam.gserviceaccount.com`) |
| IAP on a Cloud Run service | `roles/run.invoker` to the IAP service agent, `service-PROJECT_NUMBER@gcp-sa-iap.iam.gserviceaccount.com` |
| Attach a service account to a resource in another project | Token Creator on the service account, to the service agent of the service that owns the resource. Also, in the service account's project, do not enforce `iam.disableCrossProjectServiceAccountUsage`, which is enforced by default |

Sources: [Deploy container images to Cloud Run services](https://docs.cloud.google.com/run/docs/deploying), [Configure IAP for Cloud Run](https://docs.cloud.google.com/run/docs/securing/identity-aware-proxy-cloud-run), [Attach service accounts to resources](https://docs.cloud.google.com/iam/docs/attach-service-accounts).

## Exam traps

- **Editor on the service account "so that it works".** Grant predefined roles for the task. Basic roles do not belong in production ([Choose which type of role to use](https://docs.cloud.google.com/iam/docs/choose-role-type)).
- **Service Account User for `--impersonate-service-account`.** That flag needs Token Creator ([Roles for service account authentication](https://docs.cloud.google.com/iam/docs/service-account-permissions)).
- **Token Creator or Service Account User on the whole project.** The user can then use every service account in the project ([Best practices for using service accounts securely](https://docs.cloud.google.com/iam/docs/best-practices-service-accounts)).
- **The default grants constraint to clean up old projects.** It does not remove Editor from existing default service accounts ([Best practices for using service accounts securely](https://docs.cloud.google.com/iam/docs/best-practices-service-accounts)).
- **A new service account with the old name.** Old bindings do not apply, because they use the unique ID ([Service accounts overview](https://docs.cloud.google.com/iam/docs/service-account-overview)).
- **A custom role on a folder.** Custom roles exist only at organization or project level ([Roles overview](https://docs.cloud.google.com/iam/docs/roles-overview)).
- **A condition on an Editor grant.** Legacy basic roles do not accept conditions ([Overview of IAM Conditions](https://docs.cloud.google.com/iam/docs/conditions-overview)).
- **A conditional binding to limit a role that the principal already has without a condition.** It has no effect ([Overview of IAM Conditions](https://docs.cloud.google.com/iam/docs/conditions-overview)).
- **Revoking service agent roles to tighten security.** Services stop working ([Types of service accounts](https://docs.cloud.google.com/iam/docs/service-account-types)).
- **A Cloud Run deploy that cannot pull an image from another project.** Grant the Cloud Run service agent Artifact Registry Reader there ([Deploy container images to Cloud Run services](https://docs.cloud.google.com/run/docs/deploying)).
- **Access scopes as the least-privilege control.** They are coarse. Use a dedicated service account and fine-grained roles ([Best practices for using service accounts securely](https://docs.cloud.google.com/iam/docs/best-practices-service-accounts)).
- **Cloud Build Editor as a harmless role.** `cloudbuild.builds.create` can give a user the access of a service account ([Best practices for using service accounts securely](https://docs.cloud.google.com/iam/docs/best-practices-service-accounts)).
