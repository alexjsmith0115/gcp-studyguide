## Why it matters

Cloud Run can build your source code into a container image and deploy it with one command. The developer decides how to build the image, which identities to use, and which settings, secrets, and access rules apply. The exam tests what `gcloud run deploy --source` does and when to build the image in a separate step. It also tests the deploy flags that keep a service secure.

## Key points

- `gcloud run deploy SERVICE --source .` uses Cloud Build and Google Cloud's buildpacks to build an image from your code. You do not need Docker on your machine, and you do not run `gcloud builds submit` ([Deploy services from source code](https://docs.cloud.google.com/run/docs/deploying-source-code)).
- If the source directory has a Dockerfile, Cloud Build uses it. If not, buildpacks detect the language and build the image on a secure base image that Google manages ([Deploy services from source code](https://docs.cloud.google.com/run/docs/deploying-source-code)).
- Source deploy stores the image in an Artifact Registry repository named `cloud-run-source-deploy`. If the repository does not exist in the region, the command creates it ([Deploy services from source code](https://docs.cloud.google.com/run/docs/deploying-source-code)).
- The deployer needs Cloud Run Source Developer and Service Usage Consumer on the project, and Service Account User on the service identity. The build service account needs Cloud Run Builder (`roles/run.builder`) ([Deploy services from source code](https://docs.cloud.google.com/run/docs/deploying-source-code)).
- A change to the revision settings creates a new revision, and revisions are immutable. After a source deploy, the new revision serves 100% of traffic ([Deploy container images to Cloud Run services](https://docs.cloud.google.com/run/docs/deploying), [Deploy services from source code](https://docs.cloud.google.com/run/docs/deploying-source-code)).
- A Cloud Run function (formerly Cloud Functions 2nd gen) is a Cloud Run service that is deployed from source code. You deploy it with `gcloud run deploy --function` ([Compare Cloud Run functions](https://docs.cloud.google.com/run/docs/functions/comparison), [Deploy a Cloud Run function](https://docs.cloud.google.com/run/docs/deploy-functions)).
- Automatic base image updates let Google patch the operating system and language runtime of a running service. You do not rebuild or redeploy, and Cloud Run does not create a new revision ([Configure automatic base image updates](https://docs.cloud.google.com/run/docs/configuring/services/automatic-base-image-updates)).
- `--set-env-vars` deletes the variables that are not in the new list. `--update-env-vars` changes only the variables that you name ([Configure environment variables for services](https://docs.cloud.google.com/run/docs/configuring/services/environment-variables)).
- Do not keep secrets in environment variables. Store them in Secret Manager and reference them with `--update-secrets` ([Configure environment variables for services](https://docs.cloud.google.com/run/docs/configuring/services/environment-variables), [Configure secrets for services](https://docs.cloud.google.com/run/docs/configuring/services/secrets)).
- `--no-allow-unauthenticated` keeps the service private. If you omit both access flags, `gcloud` asks you to confirm during the deploy ([Deploy container images to Cloud Run services](https://docs.cloud.google.com/run/docs/deploying)).
- Google recommends automatic deploys from a Git repository. This stops deploys of unversioned local changes ([Deploy services from source code](https://docs.cloud.google.com/run/docs/deploying-source-code)).

## What a source deploy does

One command does the build, the push, and the deploy. The steps are:

1. `gcloud` uploads the source directory. It skips the files in `.gcloudignore`. If that file does not exist, `gcloud` generates one from `.gitignore` ([gcloud run deploy](https://docs.cloud.google.com/sdk/gcloud/reference/run/deploy)).
2. The source goes to a Cloud Storage bucket. Cloud Build builds the image and pushes it to the registry ([Set build worker pools (source deploy)](https://docs.cloud.google.com/run/docs/configuring/services/build-worker-pools)).
3. Cloud Run imports the image and creates a revision. Cloud Run does not pull the image again when a new instance starts ([Deploy container images to Cloud Run services](https://docs.cloud.google.com/run/docs/deploying)).
4. Cloud Run starts one instance and waits for its startup probe to pass. If this deployment health check fails, Cloud Run marks the revision unhealthy and sends no traffic to it ([Deploy services from source code](https://docs.cloud.google.com/run/docs/deploying-source-code)).

The Python quickstart enables two APIs and then deploys the current folder. The command asks for the service name and the region. It also asks to create the repository and to allow public access:

```bash
gcloud services enable run.googleapis.com cloudbuild.googleapis.com
gcloud run deploy --source .
```

Source: [Quickstart: Build and deploy a Python (Flask) web app to Cloud Run](https://docs.cloud.google.com/run/docs/quickstarts/build-and-deploy/deploy-python-service).

## Choose how to build the image

Source deploy is a convenience feature. It does not give full control of the build. For more control, build the image with Cloud Build and deploy it with `gcloud run deploy --image` ([Deploy services from source code](https://docs.cloud.google.com/run/docs/deploying-source-code)).

| Option | Use it when | Do not use it when |
|---|---|---|
| `--source` with a Dockerfile | You want to define the image yourself, or your language is not in the buildpacks list | You need full control of the build steps |
| `--source` with buildpacks (no Dockerfile) | The app uses a supported language: Go, Node.js, Python, Java, .NET, Ruby, or PHP | Your language or OS configuration is not in `gcr.io/buildpacks/builder:latest` |
| `--source --no-build` (Preview) | You want the fastest deploy of a service on a supported runtime | You deploy a job, you need a Dockerfile, or the archive is larger than 250 MiB |
| Build first, then `--image` | A CI/CD pipeline builds, tests, and deploys. YAML or Terraform refers to an image URL | You only want a quick deploy from your workstation |

Sources: [Deploy services from source code](https://docs.cloud.google.com/run/docs/deploying-source-code), [Build sources to containers](https://docs.cloud.google.com/run/docs/building/containers).

The deploy without build (Preview) skips Cloud Build. You upload an archive, and Cloud Run runs it on a base image. The source must include all its dependencies, so you install them locally first ([Deploy services from source code](https://docs.cloud.google.com/run/docs/deploying-source-code)).

```bash
pip3 install -r requirements.txt --target=./vendor
gcloud beta run deploy helloworld \
  --source . \
  --region=REGION \
  --no-build \
  --base-image=python314 \
  --command=python \
  --args=main.py \
  --set-env-vars PYTHONPATH=./vendor
```

Source: [Deploy services from source code](https://docs.cloud.google.com/run/docs/deploying-source-code).

Buildpacks have one side effect that the docs call out. They set the Last Modified date of source files to January 1, 1980. This can affect browser caching of static files. If it affects your app, Google recommends that you disable the `etag` and `Last-Modified` headers in the app ([Deploy services from source code](https://docs.cloud.google.com/run/docs/deploying-source-code)). For the build pipeline itself, see [Cloud Build and Artifact Registry](note:2.2-cloud-build-artifact-registry).

### Python with buildpacks

The Python buildpack picks the Python version from a `.python-version` file or the `GOOGLE_PYTHON_VERSION` variable. If you set both, `GOOGLE_PYTHON_VERSION` wins ([Build a Python application](https://docs.cloud.google.com/docs/buildpacks/python)).

The start command (entrypoint) for a Cloud Run source deploy depends on the Python version:

| Python version | Default entrypoint |
|---|---|
| 3.12 and earlier | `gunicorn -b :8080 main:app` |
| 3.13 and later | Set from the server or framework in `requirements.txt`, in this order: `gunicorn`, `uvicorn`, `fastapi[standard]`, `gradio`, `streamlit`, `google-adk`. With none of these, Gunicorn is the default |

Sources: [Build a Python application](https://docs.cloud.google.com/docs/buildpacks/python).

To change the start command, add a `Procfile`, for example `web: gunicorn --bind :$PORT --workers 1 --threads 8 --timeout 0 main:app`. You can also set `GOOGLE_ENTRYPOINT` with `--set-build-env-vars` ([Build a Python application](https://docs.cloud.google.com/docs/buildpacks/python)). Build environment variables work only with `--source`, not with `--image`. Do not put secrets in them. `--set-build-env-vars` replaces all existing build environment variables, and `--update-build-env-vars` keeps the variables that you do not name ([Set build environment variables (source deploy)](https://docs.cloud.google.com/run/docs/configuring/services/build-environment-variables)).

### The build identity

Cloud Build uses the Compute Engine default service account to build your source, unless you choose another account. That account needs Cloud Run Builder on the project. The `iam.automaticIamGrantsForDefaultServiceAccounts` constraint stops the automatic Editor grant to default service accounts. It is on by default for organizations created after May 3, 2024 ([Deploy services from source code](https://docs.cloud.google.com/run/docs/deploying-source-code)).

For least privilege, Google recommends your own build service account. Set it with `--build-service-account`, which works only for source deploys ([Set build service account (source deploy)](https://docs.cloud.google.com/run/docs/configuring/services/build-service-account)). Cloud Build has unlimited internet access during the build by default. Inside a VPC Service Controls perimeter, use a private pool with `--build-worker-pool` ([Set build worker pools (source deploy)](https://docs.cloud.google.com/run/docs/configuring/services/build-worker-pools)).

## Deploy functions from source

A function is source code that the Functions Framework runs. You define an entry point and a signature type: HTTP or CloudEvents. For Python, the file must be `main.py`, and `requirements.txt` must include `functions-framework==3.*` ([Write Cloud Run functions](https://docs.cloud.google.com/run/docs/write-functions)).

```python
import functions_framework

# Register an HTTP function with the Functions Framework
@functions_framework.http
def my_http_function(request):
  # Your code here

  # Return an HTTP response
  return 'OK'
```

Source: [Write Cloud Run functions](https://docs.cloud.google.com/run/docs/write-functions).

Deploy it with `gcloud run deploy` and the `--function` flag. The entry point is `my_http_function`, and the base image is a runtime ID such as `python314`:

```bash
gcloud run deploy FUNCTION \
       --source . \
       --function FUNCTION_ENTRYPOINT \
       --base-image BASE_IMAGE \
       --region REGION
```

Source: [Deploy a Cloud Run function](https://docs.cloud.google.com/run/docs/deploy-functions).

Facts about functions that the exam can test:

- Add `--allow-unauthenticated` only for a public HTTP function, for example a webhook. Omit it for an event-triggered function ([Deploy a Cloud Run function](https://docs.cloud.google.com/run/docs/deploy-functions)).
- You add Eventarc triggers after the deploy. Google strongly recommends that you change the Eventarc retry policy and add a Pub/Sub dead-letter topic ([Deploy a Cloud Run function](https://docs.cloud.google.com/run/docs/deploy-functions)). Trigger design belongs to [Triggers and event receivers](note:3.1-triggers-and-receivers).
- The Cloud Run Admin API is the recommended API. You cannot use the Cloud Functions API to change a function that the Cloud Run Admin API created. `gcloud functions deploy` remains for backward compatibility ([Compare Cloud Run functions](https://docs.cloud.google.com/run/docs/functions/comparison), [Deploy a Cloud Run function](https://docs.cloud.google.com/run/docs/deploy-functions)).
- Cloud Run functions store images only in Artifact Registry. The comparison page lists Container Registry for Cloud Run functions (1st gen), formerly Cloud Functions (1st gen). Container Registry shut down on March 18, 2025, and you cannot write images to it ([Compare Cloud Run functions](https://docs.cloud.google.com/run/docs/functions/comparison), [Transition from Container Registry](https://docs.cloud.google.com/artifact-registry/docs/transition/transition-from-gcr)).

## Automatic base image updates

Automatic base image updates move the operating system and language runtime patches out of your release cycle. Google tests each new runtime image and rolls it out with zero downtime. Without automatic updates, a service gets security fixes only when you deploy it again ([Configure automatic base image updates](https://docs.cloud.google.com/run/docs/configuring/services/automatic-base-image-updates), [Deploy services from source code](https://docs.cloud.google.com/run/docs/deploying-source-code)).

| Topic | What the docs say |
|---|---|
| Default | On for functions that you deploy with `gcloud functions`, the Cloud Functions v2 API, or `gcloud run` with the function and base image flags |
| Base image | Only Google Cloud's buildpacks base images are supported |
| App image | It must not contain the OS layers. Deploy from source (recommended), or copy the app onto a `scratch` image in a multi-stage Dockerfile |
| Compiled languages | Go and Java apps can need a rebuild to get language-level fixes |
| Turn off | `--no-automatic-updates` |
| Runtime support | You must upgrade to a newer runtime before your runtime reaches end of support |

Sources: [Configure automatic base image updates](https://docs.cloud.google.com/run/docs/configuring/services/automatic-base-image-updates), [gcloud run deploy](https://docs.cloud.google.com/sdk/gcloud/reference/run/deploy), [Supported language runtimes and base images](https://docs.cloud.google.com/run/docs/configuring/services/runtime-base-images).

```bash
gcloud run deploy \
    --source . \
    --base-image nodejs24 \
    --automatic-updates
```

Source: [Configure automatic base image updates](https://docs.cloud.google.com/run/docs/configuring/services/automatic-base-image-updates).

## Configuration and security at deploy time

Each deploy can set the configuration, the secrets, the runtime identity, and the access rules. A change to the revision settings creates a new revision ([Deploy container images to Cloud Run services](https://docs.cloud.google.com/run/docs/deploying)). A service-level setting applies without a new revision, for example `gcloud run services update SERVICE --min` or `--max` ([Set minimum instances for services](https://docs.cloud.google.com/run/docs/configuring/min-instances), [Set maximum instances for services](https://docs.cloud.google.com/run/docs/configuring/max-instances)).

| Setting | Flags | What to know |
|---|---|---|
| Environment variables | `--update-env-vars`, `--set-env-vars`, `--env-vars-file` | `--set-env-vars` and `--env-vars-file` remove all existing variables before they add the new ones. A service value overrides a Dockerfile `ENV` value |
| Secrets | `--update-secrets=ENV_VAR_NAME=SECRET_NAME:VERSION` or `PATH=SECRET_NAME:VERSION` | `--set-secrets` clears the existing secrets. The service identity needs Secret Manager Secret Accessor |
| Service identity | `--service-account` | Use a user-managed service account. The deployer needs Service Account User on it |
| Private access | `--no-allow-unauthenticated` | Cloud Run enforces the Invoker IAM check by default |
| Public access | `--no-invoker-iam-check` (recommended) or `--allow-unauthenticated` | `--allow-unauthenticated` grants Cloud Run Invoker to `allUsers`. Disable the IAM check instead when domain restricted sharing applies |

Sources: [Configure environment variables for services](https://docs.cloud.google.com/run/docs/configuring/services/environment-variables), [gcloud run deploy](https://docs.cloud.google.com/sdk/gcloud/reference/run/deploy), [Configure secrets for services](https://docs.cloud.google.com/run/docs/configuring/services/secrets), [Configure service identity for services](https://docs.cloud.google.com/run/docs/configuring/services/service-identity), [Introduction to service identity](https://docs.cloud.google.com/run/docs/securing/service-identity), [Deploy container images to Cloud Run services](https://docs.cloud.google.com/run/docs/deploying), [Allowing public (unauthenticated) access](https://docs.cloud.google.com/run/docs/authenticating/public).

How you expose a secret controls when the service sees a new version:

- **Volume.** Cloud Run reads the latest value from Secret Manager each time the app reads the file. This works well with secret rotation ([Configure secrets for services](https://docs.cloud.google.com/run/docs/configuring/services/secrets)).
- **Environment variable.** Cloud Run reads the value when the instance starts. Google recommends that you pin a version instead of `latest`. If Cloud Run cannot read the secret, the instance does not start ([Configure secrets for services](https://docs.cloud.google.com/run/docs/configuring/services/secrets)).

If you do not set a service account, Cloud Run uses the Compute Engine default service account. Google recommends a user-managed service account with the minimum roles instead ([Introduction to service identity](https://docs.cloud.google.com/run/docs/securing/service-identity)). Never set `GOOGLE_APPLICATION_CREDENTIALS` on a Cloud Run service that uses its service identity ([Configure environment variables for services](https://docs.cloud.google.com/run/docs/configuring/services/environment-variables)). For role design, see [Service accounts and least privilege](note:1.2-service-accounts-least-privilege). For Secret Manager itself, see [Secrets and keys](note:1.2-secrets-and-keys).

### Service YAML and `gcloud run services replace`

A YAML file keeps the whole service specification in version control. Export the current service, change `spec.template`, and replace the service ([Deploy container images to Cloud Run services](https://docs.cloud.google.com/run/docs/deploying)):

```bash
gcloud run services describe SERVICE --format export > service.yaml
gcloud run services replace service.yaml
```

Source: [Deploy container images to Cloud Run services](https://docs.cloud.google.com/run/docs/deploying).

The minimum YAML uses the Knative format and names an image:

```yaml
apiVersion: serving.knative.dev/v1
kind: Service
metadata:
  name: SERVICE
spec:
  template:
    spec:
      containers:
      - image: IMAGE
```

Source: [Deploy container images to Cloud Run services](https://docs.cloud.google.com/run/docs/deploying).

`replace` overwrites the whole service configuration. A change that someone made in the console or with `gcloud` is lost at the next `replace`. If you manage a service with YAML, make all changes in the YAML ([Deploy container images to Cloud Run services](https://docs.cloud.google.com/run/docs/deploying)).

## Continuous deployment from a Git repository

The Cloud Run console can connect a Git repository to a service. Cloud Run then uses a Cloud Build trigger to build and deploy on each push to a branch ([Continuously deploy from a repository](https://docs.cloud.google.com/run/docs/continuous-deployment)).

| Choice | Use it for |
|---|---|
| Cloud Build | Continuous deployment from GitHub, through the Cloud Build GitHub app |
| Developer Connect | Continuous deployment from GitHub, GitLab, or Bitbucket. It needs the Developer Connect API |
| Cloud Deploy | A continuous delivery pipeline that deploys to several environments |

Sources: [Continuously deploy from a repository](https://docs.cloud.google.com/run/docs/continuous-deployment).

The repository needs a Dockerfile, or code in a language that buildpacks support ([Continuously deploy from a repository](https://docs.cloud.google.com/run/docs/continuous-deployment)). To control how the new revision gets traffic, see [Traffic splitting](note:1.1-traffic-splitting).

## Jobs, worker pools, and Compose

Source deploy also works for other Cloud Run resources:

| Resource | Command | What to know |
|---|---|---|
| Job | `gcloud run jobs deploy JOB --source .` | Builds the image, uploads it to Artifact Registry, and deploys the job |
| Worker pool | `gcloud run worker-pools deploy WORKER_POOL` | Without `--image`, the command deploys from source. A worker pool has no URL and no autoscaling |
| Compose file | `gcloud run compose up compose.yaml` | Deploys one service with several containers. Google calls it ideal for development and recommends Terraform for production |

Sources: [Build and create a Python job in Cloud Run](https://docs.cloud.google.com/run/docs/quickstarts/jobs/build-create-python), [gcloud run jobs deploy](https://docs.cloud.google.com/sdk/gcloud/reference/run/jobs/deploy), [Deploy worker pools to Cloud Run](https://docs.cloud.google.com/run/docs/deploy-worker-pools), [Deploy services using Compose](https://docs.cloud.google.com/run/docs/deploy-run-compose).

A successful worker pool deploy does not mean that a health check ran. Configure startup and liveness probes, and check them in the logs ([Deploy worker pools to Cloud Run](https://docs.cloud.google.com/run/docs/deploy-worker-pools)).

## Exam traps

- **"Build with Docker and push the image first."** A source deploy needs no local Docker and no `gcloud builds submit` ([Deploy services from source code](https://docs.cloud.google.com/run/docs/deploying-source-code)).
- **"Source deploy gives full control of the build."** It does not. Build with Cloud Build and deploy with `--image` when you need control ([Deploy services from source code](https://docs.cloud.google.com/run/docs/deploying-source-code)).
- **`--set-env-vars` to add one variable.** It deletes the other variables. Use `--update-env-vars` ([Configure environment variables for services](https://docs.cloud.google.com/run/docs/configuring/services/environment-variables)).
- **A secret in an environment variable with version `latest`.** The value is read only at instance startup. Pin a version, or mount the secret as a volume for rotation ([Configure secrets for services](https://docs.cloud.google.com/run/docs/configuring/services/secrets)).
- **A key file in `GOOGLE_APPLICATION_CREDENTIALS`.** Use a user-managed service account as the service identity ([Introduction to service identity](https://docs.cloud.google.com/run/docs/securing/service-identity)).
- **`--allow-unauthenticated` on an event-triggered function.** Omit it. Use it only for a public HTTP function ([Deploy a Cloud Run function](https://docs.cloud.google.com/run/docs/deploy-functions)).
- **"Security patches arrive by themselves."** Without automatic base image updates, fixes apply only when you redeploy ([Deploy services from source code](https://docs.cloud.google.com/run/docs/deploying-source-code)).
- **YAML and console changes mixed.** `gcloud run services replace` overwrites console and `gcloud` changes ([Deploy container images to Cloud Run services](https://docs.cloud.google.com/run/docs/deploying)).
- **`--image` together with `--source`.** The value must be an Artifact Registry Docker repository, and the image name must equal the service name ([gcloud run deploy](https://docs.cloud.google.com/sdk/gcloud/reference/run/deploy)).
- **"The default build account already has the roles it needs."** In organizations created after May 3, 2024, default service accounts do not get Editor. Grant Cloud Run Builder to the build service account ([Deploy services from source code](https://docs.cloud.google.com/run/docs/deploying-source-code)).
