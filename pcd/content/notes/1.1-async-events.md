## Why it matters

Asynchronous integration lets a service hand off work and continue without a wait for the result. The developer chooses the product (Pub/Sub, Eventarc, or Cloud Tasks), the subscription type, and the delivery settings. The exam tests these choices and the defaults behind them: at-least-once delivery, duplicates, ordering, retention, and dead-letter topics. Many wrong answers assume a guarantee that the product does not give.

## Key points

- Pub/Sub is an asynchronous messaging service. It decouples the services that produce messages from the services that process them ([What is Pub/Sub?](https://docs.cloud.google.com/pubsub/docs/overview)).
- Each subscription gets a copy of every message. The subscribers on one subscription share the messages of that subscription ([Overview of the Pub/Sub service](https://docs.cloud.google.com/pubsub/docs/pubsub-basics)).
- The default delivery is at-least-once, with no ordering guarantee. Pub/Sub can redeliver a message even after a successful acknowledgment, so the subscriber must be idempotent ([Subscription overview](https://docs.cloud.google.com/pubsub/docs/subscription-overview)).
- Only pull subscriptions support exactly-once delivery. Push and export subscriptions do not ([Exactly-once delivery](https://docs.cloud.google.com/pubsub/docs/exactly-once-delivery)).
- An ordering key gives order inside the key, not across the topic. You must enable message ordering on the subscription ([Order messages](https://docs.cloud.google.com/pubsub/docs/ordering)).
- A subscription keeps an unacknowledged message for 7 days by default. Topic retention is not enabled by default ([Subscription properties](https://docs.cloud.google.com/pubsub/docs/subscription-properties), [Topic properties](https://docs.cloud.google.com/pubsub/docs/topic-properties)).
- You configure a dead-letter topic on the subscription, not on the topic ([Dead-letter topics](https://docs.cloud.google.com/pubsub/docs/dead-letter-topics)).
- Eventarc Standard routes events from a provider to a destination with triggers. Eventarc Advanced adds a central bus, many-to-many routing, and transformation ([Eventarc overview](https://docs.cloud.google.com/eventarc/docs/overview)).
- Eventarc delivers each event as an HTTP request in the CloudEvents format ([CloudEvents format - HTTP protocol binding](https://docs.cloud.google.com/eventarc/docs/cloudevents)).
- Pub/Sub uses implicit invocation: the publisher does not know the subscribers. Cloud Tasks uses explicit invocation: the producer names the endpoint for each task ([Choosing Pub/Sub or Cloud Tasks](https://docs.cloud.google.com/pubsub/docs/choosing-pubsub-or-cloud-tasks)).

## Why integrate asynchronously

In an event-driven architecture, producers send events to a router, and the router fans them out to consumers. The producers, the router, and the consumers deploy, update, and scale independently ([Event-driven architectures](https://docs.cloud.google.com/eventarc/docs/event-driven-architectures)).

| Benefit | What it gives you |
|---|---|
| Decoupling | You add or remove producers and consumers without a change to the other services. Each service can use a different language and framework |
| Buffering | Pub/Sub keeps an unacknowledged message and delivers it again until the retention period ends. A consumer that is down gets the backlog when it comes back |
| Fan-out | The router sends one event to many consumers. Each consumer processes the event in parallel, in its own way |
| Parallel work | Pub/Sub distributes many tasks among many workers, for example image or email jobs |
| Resiliency | When one service fails, the other services continue. You can replay past events |
| Less polling | Consumers receive pushed events, so they do not poll for changes |

Sources: [Event-driven architectures](https://docs.cloud.google.com/eventarc/docs/event-driven-architectures), [What is Pub/Sub?](https://docs.cloud.google.com/pubsub/docs/overview), [Overview of the Pub/Sub service](https://docs.cloud.google.com/pubsub/docs/pubsub-basics).

Asynchronous design also has costs. The docs list these questions before you choose it ([Event-driven architectures](https://docs.cloud.google.com/eventarc/docs/event-driven-architectures)):

- Is the event source durable? You need a durable source if you must process every event.
- How do you track the flow? You track an event flow with monitoring, not with static code analysis.
- Do you rebuild state from events? Then you must deduplicate and order them.

The caller does not get the result of asynchronous work. For example, the Cloud Tasks docs say that Cloud Tasks is not suitable for interactive applications where a user waits for the result ([Understand Cloud Tasks](https://docs.cloud.google.com/tasks/docs/dual-overview)).

## Pub/Sub topics and subscriptions

A publisher sends a message to a topic. A subscription belongs to one topic and makes the messages available to subscribers. A subscriber acknowledges each message after it processes it ([Overview of the Pub/Sub service](https://docs.cloud.google.com/pubsub/docs/pubsub-basics)).

The model gives three patterns ([Overview of the Pub/Sub service](https://docs.cloud.google.com/pubsub/docs/pubsub-basics)):

- **Fan-out.** One topic has several subscriptions. Each subscription gets every message.
- **Load balancing.** Several subscribers use one subscription. Pub/Sub shares the messages among them.
- **Fan-in.** Several publishers send to one topic.

Pub/Sub leases individual messages to subscribers. It does not use partitions, so the number of partitions does not limit the number of consumers ([What is Pub/Sub?](https://docs.cloud.google.com/pubsub/docs/overview)).

### Subscription types

| Type | How it delivers | Use it when |
|---|---|---|
| Pull | The subscriber client requests messages from Pub/Sub | The volume is large (GBs per second), throughput is critical, or the subscriber has no public HTTPS endpoint |
| Push | Pub/Sub sends each message as an HTTP request to an HTTPS endpoint | One webhook processes several topics, the subscriber is a Cloud Run function or an App Engine standard app, or the subscriber cannot use credentials and the client library |
| BigQuery | Pub/Sub writes each message to a BigQuery table | You store messages in BigQuery with no extra processing |
| Cloud Storage | Pub/Sub writes messages to files in a bucket | You store messages in Cloud Storage with no extra processing |
| Bigtable (Preview) | Pub/Sub writes messages to a Bigtable table | You store messages in Bigtable with no extra processing |

Sources: [Choose a subscription type](https://docs.cloud.google.com/pubsub/docs/subscriber), [Subscription overview](https://docs.cloud.google.com/pubsub/docs/subscription-overview).

Facts that decide between pull and push ([Choose a subscription type](https://docs.cloud.google.com/pubsub/docs/subscriber)):

- With pull, the subscriber controls the rate. It can extend the acknowledgment deadline, so processing can take a long time.
- With push, the Pub/Sub server does the flow control. Push delivers one message per request.
- A push endpoint must be an HTTPS server on the public web, with a certificate that is not self-signed.
- An export subscription needs no Dataflow job when the data needs no processing. Use Dataflow when Single Message Transforms (SMTs) cannot do the transformation.

On Cloud Run, a service receives push requests. A pull subscriber can run in a worker pool, which has no URL ([What is Cloud Run](https://docs.cloud.google.com/run/docs/overview/what-is-cloud-run)). See [the platform choice page](note:1.1-platform-choice) for worker pools and [the BigQuery writes page](note:1.3-bigquery-writes) for BigQuery subscriptions.

A subscription receives only the messages that arrive after you create it ([Subscription overview](https://docs.cloud.google.com/pubsub/docs/subscription-overview)). If a topic has no subscription, Pub/Sub does not keep the messages that you publish to it. Attach a subscription or enable topic retention before you publish ([Best practices to publish to a Pub/Sub topic](https://docs.cloud.google.com/pubsub/docs/publish-best-practices)).

## Delivery guarantees

| Guarantee | Subscription types | What you must do |
|---|---|---|
| At-least-once (default) | All types | Make the subscriber idempotent. Expect a rare duplicate, also after a successful acknowledgment |
| Exactly-once | Pull only, including StreamingPull | Enable it on the subscription. Check the result of each acknowledgment in the client library |

Sources: [Subscription overview](https://docs.cloud.google.com/pubsub/docs/subscription-overview), [Exactly-once delivery](https://docs.cloud.google.com/pubsub/docs/exactly-once-delivery).

Exactly-once delivery has limits ([Exactly-once delivery](https://docs.cloud.google.com/pubsub/docs/exactly-once-delivery)):

- The guarantee applies only when the subscribers connect to one region. Subscribers in several regions can get duplicates. A locational endpoint keeps a client on one region.
- A publisher retry can store the same data twice. The two copies have different message IDs, so the subscription delivers both.
- The publish-to-subscribe latency is significantly higher than for a regular subscription.
- With ordering, client throughput is limited to the order of thousands of messages per second.
- Push cannot support it. The push endpoint does not know if Pub/Sub received its response.

Google's advice for most applications: a rare duplicate is normal. Use exactly-once delivery only when the application cannot accept any duplicate ([Best practices to subscribe to a Pub/Sub topic](https://docs.cloud.google.com/pubsub/docs/subscribe-best-practices)).

## Ordering keys

Message ordering delivers the messages that have the same ordering key in the order that they were published. Messages with different keys have no order between them ([Order messages](https://docs.cloud.google.com/pubsub/docs/ordering)).

To get ordered delivery ([Order messages](https://docs.cloud.google.com/pubsub/docs/ordering)):

1. Set the same ordering key on all related messages.
2. Publish all messages with that key in the same region. Subscribers can connect to any region.
3. Enable message ordering on the subscription. You cannot change this property after you create the subscription.

Ordering has costs ([Order messages](https://docs.cloud.google.com/pubsub/docs/ordering)):

- Each ordering key accepts up to 1 MBps of publish throughput.
- Ordered delivery decreases publish availability and increases latency.
- A redelivery of one message also redelivers all later messages for that key, even acknowledged ones.
- Unacknowledged messages for one key can delay the messages for other keys. A dead-letter topic stops this indefinite hold, but it might not keep the order.
- A push subscription sends only one outstanding message for each key at a time.
- Do not enable ordering on a subscription that Dataflow reads.

Eventarc has no first-in-first-out guarantee in either edition ([Eventarc overview](https://docs.cloud.google.com/eventarc/docs/overview)).

## Retention, replay, and dead-letter topics

| Setting | Resource | Default | Range |
|---|---|---|---|
| Message retention duration | Subscription | 7 days | 10 minutes to 31 days |
| Retain acknowledged messages | Subscription | Off | Uses the retention duration |
| Message retention | Topic | Not enabled | 10 minutes to 31 days |
| Expiration period | Subscription | 31 days of inactivity | At least 1 day, or never |
| Acknowledgment deadline | Subscription | 10 seconds | 10 to 600 seconds |

Sources: [Subscription properties](https://docs.cloud.google.com/pubsub/docs/subscription-properties), [Configure message retention for a subscription](https://docs.cloud.google.com/pubsub/docs/subscription-message-retention), [Topic properties](https://docs.cloud.google.com/pubsub/docs/topic-properties).

By default, a topic discards a message when all attached subscriptions acknowledge it. Topic retention lets a subscription replay acknowledged messages. It also lets a new subscription replay messages from before it existed ([Create a topic](https://docs.cloud.google.com/pubsub/docs/create-topic)).

You replay or purge messages with seek ([Replay and purge messages with seek](https://docs.cloud.google.com/pubsub/docs/replay-overview)):

| Seek target | Effect | Setup |
|---|---|---|
| A time in the past | Replays messages from that time | Topic retention, or retained acknowledged messages on the subscription |
| A time in the future | Purges the backlog | None |
| A snapshot | Restores the acknowledgment state at the snapshot time | Create the snapshot first, for example before you deploy new subscriber code |

Sources: [Replay and purge messages with seek](https://docs.cloud.google.com/pubsub/docs/replay-overview).

A snapshot lasts at most 7 days ([Replay and purge messages with seek](https://docs.cloud.google.com/pubsub/docs/replay-overview)). The exact gcloud commands are on [the messaging page](note:4.1-messaging).

A dead-letter topic (also known as a dead-letter queue) receives the messages that subscribers cannot acknowledge ([Dead-letter topics](https://docs.cloud.google.com/pubsub/docs/dead-letter-topics)):

- After the maximum number of delivery attempts, Pub/Sub forwards the message. The default is 5, and the range is 5 to 100. The count is approximate.
- Pub/Sub wraps the original message and adds attributes that identify the source subscription.
- The Pub/Sub service agent needs the Pub/Sub Publisher role on the dead-letter topic and the Pub/Sub Subscriber role on the source subscription.
- The dead-letter topic must be a different topic from the source topic. Attach a subscription to it to receive the forwarded messages.

The retry policy of a subscription is "Retry immediately" by default. The other choice is exponential backoff, between a minimum and a maximum delay of up to 600 seconds ([Subscription properties](https://docs.cloud.google.com/pubsub/docs/subscription-properties)).

## Eventarc Standard and Eventarc Advanced

Eventarc routes events from sources to destinations and manages delivery, security, and error handling. It has two editions with the same data model ([Eventarc overview](https://docs.cloud.google.com/eventarc/docs/overview)).

| Feature | Eventarc Standard | Eventarc Advanced |
|---|---|---|
| Routing | A trigger routes events from a provider to one destination | A bus receives events. An enrollment matches events with a CEL expression and sends them to a pipeline. A pipeline delivers to one destination |
| Routing scope | Provider to destination | Many providers to many destinations |
| Filters | Event type and specific attributes | Any event attribute |
| Transformation | No | Yes, with CEL expressions |
| Cross-project delivery | No | Yes |
| Dead-letter queue | Yes, through a Pub/Sub dead-letter topic | No |
| Event size | 512 KB maximum | 1 MB maximum |
| Location | Regional or global | Regional |
| Limits | 500 triggers per project per region | One bus and 100 pipelines per project per region |
| Destinations | Cloud Run services and functions, Workflows, GKE services (Preview), internal HTTP endpoints in a VPC network (Preview) | Cloud Run services, jobs, and functions, Workflows, Pub/Sub topics, internal HTTP endpoints in a VPC network, and other buses |

Sources: [Eventarc overview](https://docs.cloud.google.com/eventarc/docs/overview), [Eventarc Standard overview](https://docs.cloud.google.com/eventarc/standard/docs/overview), [Eventarc Advanced overview](https://docs.cloud.google.com/eventarc/advanced/docs/overview).

Google recommends Eventarc Standard when an application only delivers events from a provider to a destination. Eventarc Advanced is for complex eventing needs, for example many teams across projects ([Eventarc overview](https://docs.cloud.google.com/eventarc/docs/overview)). Eventarc Advanced became generally available on August 1, 2025. Publishing from multiple projects is in Preview ([Eventarc release notes](https://docs.cloud.google.com/eventarc/docs/release-notes)).

Eventarc Standard gets Google events in two ways: directly from the source, or through Cloud Audit Logs entries. It also accepts messages from a Pub/Sub topic, and third-party events (Preview). It uses Pub/Sub as the transport and delivers through Pub/Sub push subscriptions ([Eventarc Standard overview](https://docs.cloud.google.com/eventarc/standard/docs/overview)).

| Event source | Example filter | Note |
|---|---|---|
| Direct event | `type=google.cloud.storage.object.v1.finalized` | Comes directly from the service |
| Cloud Audit Logs | `type=google.cloud.audit.log.v1.written`, with `serviceName` and `methodName` | Delivered in under a minute |
| Pub/Sub | `type=google.cloud.pubsub.topic.v1.messagePublished` | Uses an existing topic or a topic that Eventarc creates. Delivered in seconds |

Sources: [Eventarc Standard overview](https://docs.cloud.google.com/eventarc/standard/docs/overview).

Every event-driven Cloud Run function (formerly Cloud Functions) uses an Eventarc trigger ([Eventarc Standard overview](https://docs.cloud.google.com/eventarc/standard/docs/overview)). Trigger setup, roles, and locations are on [the triggers and receivers page](note:3.1-triggers-and-receivers).

## CloudEvents

CloudEvents is a CNCF specification that describes event data in a common way. Eventarc sends each event as an HTTP POST request to the root path (`/`) of the receiver ([CloudEvents format - HTTP protocol binding](https://docs.cloud.google.com/eventarc/docs/cloudevents)). It uses binary content mode: the event attributes are HTTP headers, and the event data is the body ([Eventarc Advanced overview](https://docs.cloud.google.com/eventarc/advanced/docs/overview)).

Source: [CloudEvents format - HTTP protocol binding](https://docs.cloud.google.com/eventarc/docs/cloudevents).

```text
ce-specversion: 1.0
ce-type: google.cloud.pubsub.topic.v1.messagePublished
ce-source: //pubsub.googleapis.com/TOPIC
ce-id: MESSAGE_ID
ce-time: PUBLISH_TIME
Content-Type: application/json; charset=utf-8
```

The `ce-type` header tells the receiver what happened. The `ce-source` and `ce-id` pair identifies the event. Two events with the same pair are duplicates ([Retry events](https://docs.cloud.google.com/eventarc/docs/retry-events)). A Workflows destination gets the event as a JSON runtime argument, not as HTTP headers ([Eventarc Advanced overview](https://docs.cloud.google.com/eventarc/advanced/docs/overview)).

## Idempotent consumers

Every product in this page can deliver the same event more than once. An idempotent handler gives the same result when it processes an event twice.

| Cause of a duplicate | What it means for the handler |
|---|---|
| Pub/Sub at-least-once delivery | A message can arrive again, also after a successful acknowledgment |
| A publisher retry after a lost response | Two copies have different message IDs. A check on the message ID does not catch them |
| Cloud Storage notifications | One object change can give several messages with different IDs |
| Eventarc retries | The same `source` and `id` pair can arrive again |
| Cloud Tasks and Cloud Scheduler | Both deliver at least once |

Sources: [Subscription overview](https://docs.cloud.google.com/pubsub/docs/subscription-overview), [Retry requests](https://docs.cloud.google.com/pubsub/docs/retry-requests), [Pub/Sub notifications for Cloud Storage](https://docs.cloud.google.com/storage/docs/pubsub-notifications), [Retry events](https://docs.cloud.google.com/eventarc/docs/retry-events), [Understand Cloud Tasks](https://docs.cloud.google.com/tasks/docs/dual-overview), [About Cloud Scheduler](https://docs.cloud.google.com/scheduler/docs/overview).

The Eventarc docs give these rules for an idempotent handler ([Retry events](https://docs.cloud.google.com/eventarc/docs/retry-events)):

1. When an external API accepts an idempotency key, send the event ID as the key.
2. Make sure that a mutation can happen more than once with the same outcome.
3. Query the database state in a transaction before you change it.
4. Record each processed event ID outside the service, and skip an ID that you already processed.
5. Make all side effects idempotent, or clean up duplicates out of band with a separate process.

Idempotency makes retries safe. Google recommends that you combine idempotency with retries ([Retry events](https://docs.cloud.google.com/eventarc/docs/retry-events)).

## Choose Pub/Sub, Eventarc, or Cloud Tasks

Cloud Tasks is for a producer that must defer or control the execution of a specific webhook. Pub/Sub is for general event ingestion and distribution, where the producer gives up some control ([Choosing Pub/Sub or Cloud Tasks](https://docs.cloud.google.com/pubsub/docs/choosing-pubsub-or-cloud-tasks)).

| Requirement | Choose | Reason |
|---|---|---|
| Several consumers get each message, and the producer does not know them | Pub/Sub | Implicit invocation and several subscriptions for each message |
| Call one specific endpoint later, at a controlled rate | Cloud Tasks | Explicit invocation and queue rate controls |
| Deliver at a set time in the future | Cloud Tasks | Scheduled delivery. Pub/Sub has none |
| Deduplicate when you create the work | Cloud Tasks | Task names deduplicate. Pub/Sub does not |
| Consumers pull work through an API | Pub/Sub | Cloud Tasks has no pull |
| A message is larger than 1 MB | Pub/Sub | 10 MB maximum. A task is 1 MB maximum |
| A push handler runs longer than 10 minutes | Cloud Tasks | An HTTP target can run for up to 30 minutes |
| React to a change in a Google Cloud service and deliver CloudEvents to Cloud Run or Workflows | Eventarc Standard | Triggers with filters on more than 130 Google providers |
| A central bus for many teams and projects, with transformation | Eventarc Advanced | Bus, enrollments, and pipelines |
| Existing Kafka workloads, or portability across clouds | Managed Service for Apache Kafka | Kafka APIs with minimal code changes |

Sources: [Choosing Pub/Sub or Cloud Tasks](https://docs.cloud.google.com/pubsub/docs/choosing-pubsub-or-cloud-tasks), [Eventarc overview](https://docs.cloud.google.com/eventarc/docs/overview), [Eventarc Standard overview](https://docs.cloud.google.com/eventarc/standard/docs/overview), [Choose Pub/Sub or Cloud Managed Service for Apache Kafka](https://docs.cloud.google.com/pubsub/docs/choose-pubsub-kafka).

For new workloads, Google recommends Pub/Sub over Managed Service for Apache Kafka because it is easier to use ([Choose Pub/Sub or Cloud Managed Service for Apache Kafka](https://docs.cloud.google.com/pubsub/docs/choose-pubsub-kafka)). Pub/Sub Lite is deprecated, and Google turns it down on January 31, 2027 ([Choose Pub/Sub or Pub/Sub Lite](https://docs.cloud.google.com/pubsub/docs/choosing-pubsub-or-lite)). Pub/Sub is for service-to-service traffic. For messages between a mobile or web app and a service, the docs point to Firebase products ([What is Pub/Sub?](https://docs.cloud.google.com/pubsub/docs/overview)).

Workflows, Cloud Tasks queues, and Cloud Scheduler jobs are on [the orchestration page](note:1.1-orchestration).

## Exam traps

- **Exactly-once delivery on a push subscription.** Only pull subscriptions support it ([Exactly-once delivery](https://docs.cloud.google.com/pubsub/docs/exactly-once-delivery)).
- **"Exactly-once, so the handler needs no idempotency."** Publisher retries can still create copies with different message IDs ([Exactly-once delivery](https://docs.cloud.google.com/pubsub/docs/exactly-once-delivery)).
- **A dead-letter topic on the topic.** It is a property of the subscription ([Dead-letter topics](https://docs.cloud.google.com/pubsub/docs/dead-letter-topics)).
- **A dead-letter topic with no subscription.** Pub/Sub does not keep messages on a topic without a subscription. Attach one to the dead-letter topic ([Best practices to publish to a Pub/Sub topic](https://docs.cloud.google.com/pubsub/docs/publish-best-practices), [Dead-letter topics](https://docs.cloud.google.com/pubsub/docs/dead-letter-topics)).
- **A new subscription to read last week's messages.** A subscription gets only messages published after it exists. Use topic retention and seek ([Subscription overview](https://docs.cloud.google.com/pubsub/docs/subscription-overview), [Create a topic](https://docs.cloud.google.com/pubsub/docs/create-topic)).
- **Ordering keys for a total order of the topic.** Order applies only inside one key ([Order messages](https://docs.cloud.google.com/pubsub/docs/ordering)).
- **Ordering turned on for an existing subscription.** You cannot change the ordering property after you create the subscription ([Order messages](https://docs.cloud.google.com/pubsub/docs/ordering)).
- **Pub/Sub to call one API at a set time or a fixed rate.** That is explicit invocation. Use Cloud Tasks ([Choosing Pub/Sub or Cloud Tasks](https://docs.cloud.google.com/pubsub/docs/choosing-pubsub-or-cloud-tasks)).
- **Eventarc for strict event order.** Neither edition has a first-in-first-out guarantee ([Eventarc overview](https://docs.cloud.google.com/eventarc/docs/overview)).
- **Eventarc Advanced for a simple route from one source to one service.** Google recommends Eventarc Standard for that case ([Eventarc overview](https://docs.cloud.google.com/eventarc/docs/overview)).
- **Pub/Sub Lite for a new design.** It is deprecated and turns down on January 31, 2027 ([Choose Pub/Sub or Pub/Sub Lite](https://docs.cloud.google.com/pubsub/docs/choosing-pubsub-or-lite)).
