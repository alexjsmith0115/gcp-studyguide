## Why it matters

Spanner and AlloyDB both use SQL, but a schema habit from a single-server database can fail on Spanner. Spanner spreads rows across servers by primary key range, so the key design decides whether writes spread out or go to one server. AlloyDB keeps standard PostgreSQL schemas, so the decisions are index types, partitions, and the columnar engine. The exam shows DDL or a key, and asks for the change that removes a hotspot or speeds up a query.

## Key points

- Spanner (formerly Cloud Spanner) divides data among servers by key ranges. A primary key that starts with an increasing value, such as a timestamp or a sequence number, sends all inserts to one server ([Schemas overview](https://docs.cloud.google.com/spanner/docs/schema-and-data-model), [Schema design best practices](https://docs.cloud.google.com/spanner/docs/schema-design), [Your Google Cloud database options, explained](https://cloud.google.com/blog/topics/developers-practitioners/your-google-cloud-database-options-explained)).
- For new applications, Spanner recommends UUID version 4 primary keys. If the app needs integer keys, use a bit-reversed sequence ([Primary key default values management](https://docs.cloud.google.com/spanner/docs/primary-key-default-value)).
- Interleaving stores child rows with their parent row. The child primary key starts with the parent primary key, and interleaving is permanent ([Schemas overview](https://docs.cloud.google.com/spanner/docs/schema-and-data-model)).
- Foreign keys are more general than interleaving, but they do not store the tables together. Google recommends interleaving or foreign keys for a relationship, not both ([Schemas overview](https://docs.cloud.google.com/spanner/docs/schema-and-data-model), [Foreign keys](https://docs.cloud.google.com/spanner/docs/foreign-keys/overview)).
- A secondary index can store extra columns with `STORING` (GoogleSQL) or `INCLUDE` (PostgreSQL), so a query does not join back to the base table ([Secondary indexes](https://docs.cloud.google.com/spanner/docs/secondary-indexes)).
- A commit timestamp column records the commit time of each transaction. As the first key part of a table or an index, it creates a hotspot ([Commit timestamps in GoogleSQL-dialect databases](https://docs.cloud.google.com/spanner/docs/commit-timestamp)).
- Spanner changes a schema with no downtime. Index backfills and data validation run in the background and can take hours ([Make schema updates](https://docs.cloud.google.com/spanner/docs/schema-updates)).
- AlloyDB for PostgreSQL is PostgreSQL-compatible, so standard PostgreSQL clients and tools work. An index advisor recommends new indexes from the query workload ([AlloyDB overview](https://docs.cloud.google.com/alloydb/docs/overview), [Use the index advisor](https://docs.cloud.google.com/alloydb/docs/use-index-advisor)).
- The AlloyDB columnar engine keeps selected columns in memory in a column format. It speeds up scans, joins, and aggregates ([About the AlloyDB columnar engine](https://docs.cloud.google.com/alloydb/docs/columnar-engine/about)).
- AlloyDB separates compute from storage and stores up to 128 TiB per cluster. A Cloud SQL instance is a VM with a persistent disk and stores up to 64 TB ([AlloyDB overview](https://docs.cloud.google.com/alloydb/docs/overview), [AlloyDB quotas and limits](https://docs.cloud.google.com/alloydb/quotas), [Cloud SQL overview](https://docs.cloud.google.com/sql/docs/introduction), [Cloud SQL quotas and limits](https://docs.cloud.google.com/sql/docs/quotas)).

## Spanner: primary keys that spread writes

Spanner stores rows in primary key order and divides them into splits. A split is a range of contiguous rows, and Spanner assigns splits to servers ([Schemas overview](https://docs.cloud.google.com/spanner/docs/schema-and-data-model)). If the first key part always increases, every insert goes to the last split, and its server becomes a hotspot. A change of the sort order does not help, because the inserts then go to the top of the table ([Schema design best practices](https://docs.cloud.google.com/spanner/docs/schema-design)).

| Technique | Key example | Use when |
|---|---|---|
| UUID version 4 | `LogEntryId UUID DEFAULT (NEW_UUID())` | A new app needs a surrogate key. This is the recommended choice |
| Bit-reversed sequence | `INT64 GENERATED BY DEFAULT AS IDENTITY (BIT_REVERSED_POSITIVE)` | The app needs integer keys |
| Swap the key order | `PRIMARY KEY (UserId, LastAccess)` | A high-cardinality column, such as a user ID, can come first |
| Hash shard prefix | `PRIMARY KEY (ShardId, LastAccess, UserId)`, where `ShardId` is a hash modulo N | No natural key spreads the writes. Set N to the expected node count |

Sources: [Schema design best practices](https://docs.cloud.google.com/spanner/docs/schema-design), [Primary key default values management](https://docs.cloud.google.com/spanner/docs/primary-key-default-value).

```sql
-- Recommended for new apps: a random UUID version 4 key
CREATE TABLE Fans (
  FanId UUID DEFAULT (NEW_UUID()),
  Name STRING(MAX),
) PRIMARY KEY (FanId);

-- When the app needs INT64 keys: bit-reversed values spread over the key space
CREATE TABLE Singers (
  SingerId INT64 GENERATED BY DEFAULT AS IDENTITY (BIT_REVERSED_POSITIVE),
  Name STRING(MAX),
  Rank INT64
) PRIMARY KEY (SingerId);
```

Source: [Primary key default values management](https://docs.cloud.google.com/spanner/docs/primary-key-default-value).

Rules that the exam tests:

- **UUID version.** Do not use version 1 UUIDs. They put the timestamp in the high-order bits ([Schema design best practices](https://docs.cloud.google.com/spanner/docs/schema-design)).
- **No monotonic generator.** Spanner cannot generate monotonic values. `AUTO_INCREMENT` (GoogleSQL) and `SERIAL` (PostgreSQL) are aliases for `IDENTITY` columns, and they need the database option `default_sequence_kind`. If a migrated app needs new monotonic keys, use a composite key ([Primary key default values management](https://docs.cloud.google.com/spanner/docs/primary-key-default-value)).
- **Keys are fixed.** You cannot add or remove a key column of an existing table ([Schemas overview](https://docs.cloud.google.com/spanner/docs/schema-and-data-model)).
- **Newest first.** To read the latest events first, declare the timestamp key part `DESC`, for example `PRIMARY KEY (UserId, LastAccess DESC)` ([Schema design best practices](https://docs.cloud.google.com/spanner/docs/schema-design)).
- **Multi-tenancy.** Put all tenants in one table with a `CustomerId` first key column. A database for each tenant can reach the limits on databases, tables, and indexes. New tables and non-interleaved indexes can take a long time to add ([Schemas overview](https://docs.cloud.google.com/spanner/docs/schema-and-data-model), [Schema update best practices](https://docs.cloud.google.com/spanner/docs/schema-updates-best-practices)).

## Spanner: interleaved tables or foreign keys

Interleaving declares data locality: Spanner stores the child rows of a parent row next to that row. This effectively pre-joins the tables, so a join by primary key stays local ([Schemas overview](https://docs.cloud.google.com/spanner/docs/schema-and-data-model), [Foreign keys](https://docs.cloud.google.com/spanner/docs/foreign-keys/overview)).

```sql
CREATE TABLE Singers (
 SingerId   INT64 NOT NULL PRIMARY KEY,
 FirstName  STRING(1024),
 LastName   STRING(1024),
 );

CREATE TABLE Albums (
 SingerId     INT64 NOT NULL,
 AlbumId      INT64 NOT NULL,
 AlbumTitle   STRING(MAX),
 ) PRIMARY KEY (SingerId, AlbumId),
INTERLEAVE IN PARENT Singers ON DELETE CASCADE;
```

Source: [Schemas overview](https://docs.cloud.google.com/spanner/docs/schema-and-data-model).

| | Interleaving | Enforced foreign key |
|---|---|---|
| Stores parent and child rows together | Yes | No |
| Can use non-primary-key columns | No | Yes |
| Number of parents | 0 or 1 | 0 to N |
| Cascade delete | Yes | Yes |
| Can be removed | No, unless you delete the child table | Yes |

Source: [Foreign keys](https://docs.cloud.google.com/spanner/docs/foreign-keys/overview).

- **Enforcement.** With `INTERLEAVE IN PARENT`, the parent row must exist before its child rows. `INTERLEAVE IN` keeps the same layout without this rule ([Schemas overview](https://docs.cloud.google.com/spanner/docs/schema-and-data-model)).
- **Depth.** A hierarchy of interleaved tables can be seven levels deep ([Schemas overview](https://docs.cloud.google.com/spanner/docs/schema-and-data-model)).
- **Large cascades.** A transaction fails above 80,000 mutations. Large cascading deletes work with `INTERLEAVE IN PARENT`, but not with foreign keys. With foreign keys, delete the child rows first ([Foreign keys](https://docs.cloud.google.com/spanner/docs/foreign-keys/overview)).
- **Informational foreign keys.** A `NOT ENFORCED` foreign key (GoogleSQL only) tells the query optimizer about the model, but Spanner does not check writes. Start with enforced foreign keys ([Foreign keys](https://docs.cloud.google.com/spanner/docs/foreign-keys/overview)).

## Spanner: secondary indexes

Spanner indexes each primary key automatically. A secondary index stores the key columns of the base table, the indexed columns, and the `STORING` columns ([Secondary indexes](https://docs.cloud.google.com/spanner/docs/secondary-indexes)).

| | Interleaved index | Global index (default) |
|---|---|---|
| Storage | With the parent row, in the same split | In a separate table that splits independently |
| Key rule | The parent primary key is a prefix of the index key | None |
| Write cost | Low: updates usually stay in one split | Higher: updates often need distributed transactions |
| Best for | Queries for one parent, for example the photos of one user | Searches across the database, for example a user by email |

Source: [Secondary indexes](https://docs.cloud.google.com/spanner/docs/secondary-indexes).

```sql
-- Covering index: the query reads MarketingBudget from the index, with no join
CREATE INDEX AlbumsByAlbumTitle2 ON Albums(AlbumTitle) STORING (MarketingBudget);

-- A timestamp index is safe when it is interleaved under the user row
CREATE NULL_FILTERED INDEX UsersByLastAccess
ON Users(UserId, LastAccess),
INTERLEAVE IN Users;
```

Sources: [Secondary indexes](https://docs.cloud.google.com/spanner/docs/secondary-indexes), [Schema design best practices](https://docs.cloud.google.com/spanner/docs/schema-design).

- **Increasing index keys.** Spanner implements an index as a table. A global index on an increasing column, such as `LastAccess`, creates the same hotspot as a key. Interleave the index, or add a shard column ([Schema design best practices](https://docs.cloud.google.com/spanner/docs/schema-design)).
- **Sparse columns.** A `NULL_FILTERED` index leaves out `NULL` values, so it is smaller and costs less to maintain ([Secondary indexes](https://docs.cloud.google.com/spanner/docs/secondary-indexes)).
- **Index choice.** SQL queries select indexes automatically, but Google advises a `FORCE_INDEX` hint for critical queries. The read API never selects an index: you name it, and it must hold every column that the read returns ([Secondary indexes](https://docs.cloud.google.com/spanner/docs/secondary-indexes)).

## Spanner: commit timestamps

Set `allow_commit_timestamp=true` on a `TIMESTAMP` column. Then write `PENDING_COMMIT_TIMESTAMP()` in DML, or the `spanner.commit_timestamp()` placeholder in a mutation. Spanner stores the commit time, which comes from TrueTime ([Commit timestamps in GoogleSQL-dialect databases](https://docs.cloud.google.com/spanner/docs/commit-timestamp)).

```sql
CREATE TABLE Documents (
  UserId     INT64 NOT NULL,
  DocumentId INT64 NOT NULL,
  Contents   STRING(MAX) NOT NULL,
) PRIMARY KEY (UserId, DocumentId);

CREATE TABLE DocumentHistory (
  UserId     INT64 NOT NULL,
  DocumentId INT64 NOT NULL,
  Ts         TIMESTAMP NOT NULL OPTIONS (allow_commit_timestamp=true),
  Delta      STRING(MAX),
) PRIMARY KEY (UserId, DocumentId, Ts),
  INTERLEAVE IN PARENT Documents ON DELETE NO ACTION;
```

Source: [Commit timestamps in GoogleSQL-dialect databases](https://docs.cloud.google.com/spanner/docs/commit-timestamp).

- **Changelog.** Insert the history row in the same transaction as the change. The commit timestamps put the entries in order. To keep the history after a document is deleted, do not interleave the tables ([Commit timestamps in GoogleSQL-dialect databases](https://docs.cloud.google.com/spanner/docs/commit-timestamp)).
- **Not unique.** Transactions that write to non-overlapping sets of fields can get the same timestamp ([Commit timestamps in GoogleSQL-dialect databases](https://docs.cloud.google.com/spanner/docs/commit-timestamp)).
- **Hotspots.** A commit timestamp as the first key part of a table or an index creates a hotspot, even at low write rates ([Commit timestamps in GoogleSQL-dialect databases](https://docs.cloud.google.com/spanner/docs/commit-timestamp)).
- **Client code.** For transactions, DML, and mutations in the client libraries, see [Reading and writing data with the client libraries](note:4.1-reading-writing-data).

## Spanner: schema changes and dialects

Reads and writes continue while Spanner applies a schema change as a long-running operation ([Make schema updates](https://docs.cloud.google.com/spanner/docs/schema-updates)).

| Change | Typical time |
|---|---|
| `CREATE TABLE`, `ADD COLUMN`, `DROP INDEX` | Minutes |
| `CREATE INDEX` on an existing table | Minutes to hours, because of the backfill |
| `CREATE INDEX` in the same batch as its `CREATE TABLE` | Minutes |
| `ALTER COLUMN` that needs validation, for example `NOT NULL` | Minutes to hours |

Source: [Make schema updates](https://docs.cloud.google.com/spanner/docs/schema-updates).

Best practices from [Schema update best practices](https://docs.cloud.google.com/spanner/docs/schema-updates-best-practices):

1. Put a new table and its indexes in one batch, so that Spanner does not backfill the indexes.
2. Create no more than about 3 indexes that need a backfill each day. A batch can hold at most 10 statements that need a backfill or validation.
3. Do not use tools that apply long series of upgrade and downgrade changes on each deployment. Too many schema versions make Spanner throttle updates.
4. Check the existing data first. For example, a statement that adds `NOT NULL` to a column with `NULL` values fails. The earlier statements of the batch stay applied.

**Dialect.** You select GoogleSQL or the PostgreSQL interface when you create each database. The PostgreSQL interface does not support PostgreSQL extensions, user-defined data types, or user-defined stored procedures. A PostgreSQL app usually needs some rework, for example of its primary keys ([PostgreSQL interface](https://docs.cloud.google.com/spanner/docs/postgresql-interface)).

## AlloyDB: indexes and partitions

AlloyDB is fully PostgreSQL-compatible, so it uses standard PostgreSQL schemas ([AlloyDB overview](https://docs.cloud.google.com/alloydb/docs/overview)). Choose the index type for the query pattern:

| Index type | Use for |
|---|---|
| B-tree (default) | Equality and range queries, primary keys, foreign keys, and unique constraints. Also partial and function-based indexes |
| HASH | Equality only, on one column |
| GIN or GiST | Full-text search, arrays, and `jsonb` key-value pairs |
| BRIN | Large insert-only tables with an ordered column, such as an increasing ID or a timestamp |
| HNSW, IVFFlat, or ScaNN | Vector similarity search. ScaNN suits very large datasets |

Source: [AlloyDB database indexing strategies](https://docs.cloud.google.com/alloydb/docs/reference/indexing-strategies).

- **Covering indexes.** `INCLUDE` adds a column to an index without indexing it, so the query can skip the table ([AlloyDB database indexing strategies](https://docs.cloud.google.com/alloydb/docs/reference/indexing-strategies)).
- **Sort order.** An index on the filter and `ORDER BY` columns, for example `(product_id, id DESC)`, can remove a sort step ([AlloyDB database indexing strategies](https://docs.cloud.google.com/alloydb/docs/reference/indexing-strategies)).
- **Index advisor.** It analyzes tracked queries and lists `CREATE INDEX` statements in the `google_db_advisor_recommended_indexes` view ([Use the index advisor](https://docs.cloud.google.com/alloydb/docs/use-index-advisor)).

**Partitions.** For time series data, partition a table by range on a date column. At the end of the retention period, drop the old partitions. In a busy database, detach a partition with `CONCURRENTLY` to reduce locks ([Dynamically drop partitions within cloud databases](https://cloud.google.com/blog/products/databases/dynamically-drop-partitions-within-cloud-databases/)). The `pg_partman` extension creates and manages time-based and serial-based partition sets ([Supported database extensions](https://docs.cloud.google.com/alloydb/docs/reference/extensions)).

```sql
CREATE TABLE sales (id int, p_name text, amount int, sale_date date)
  PARTITION BY RANGE (sale_date);
CREATE TABLE sales_2022_01 PARTITION OF sales
  FOR VALUES FROM ('2022-01-01') TO ('2022-02-01');
```

Source: [Dynamically drop partitions within cloud databases](https://cloud.google.com/blog/products/databases/dynamically-drop-partitions-within-cloud-databases/).

## AlloyDB: the columnar engine

The columnar engine adds a column store for selected columns, and a query planner and execution engine that use it ([About the AlloyDB columnar engine](https://docs.cloud.google.com/alloydb/docs/columnar-engine/about)).

- **Where it runs.** On the primary instance, a read pool instance, or both. By default, it uses 30% of the instance memory ([About the AlloyDB columnar engine](https://docs.cloud.google.com/alloydb/docs/columnar-engine/about)).
- **Setup.** You turn on the engine once, with a restart. Then auto-columnarization adds columns from the workload, or you add columns yourself ([About the AlloyDB columnar engine](https://docs.cloud.google.com/alloydb/docs/columnar-engine/about)).
- **Best queries.** Selective filters on a few columns of a large table, and `SUM`, `MIN`, `MAX`, `AVG`, and `COUNT` aggregates ([About the AlloyDB columnar engine](https://docs.cloud.google.com/alloydb/docs/columnar-engine/about)).
- **Limits.** Frequent updates invalidate column data. For an indexed column, the optimizer can choose the row store. A partitioned table needs each leaf partition in the column store ([About the AlloyDB columnar engine](https://docs.cloud.google.com/alloydb/docs/columnar-engine/about)).

| Storage limit | 64 TB | 128 TiB per cluster |

## Exam traps

- **A timestamp or a sequence as the first Spanner key part.** All inserts go to one split. Use a UUID version 4, a bit-reversed sequence, a swapped key order, or a shard prefix ([Schema design best practices](https://docs.cloud.google.com/spanner/docs/schema-design)).
- **A change of the timestamp sort order to fix the hotspot.** The inserts then go to the top of the table, which is still one server ([Schema design best practices](https://docs.cloud.google.com/spanner/docs/schema-design)).
- **UUID version 1.** It stores the timestamp in the high-order bits ([Schema design best practices](https://docs.cloud.google.com/spanner/docs/schema-design)).
- **A global index on an increasing column, such as `LastAccess`.** Interleave the index, or add a shard column ([Schema design best practices](https://docs.cloud.google.com/spanner/docs/schema-design)).
- **A commit timestamp as the first key part.** It creates a hotspot even at low write rates ([Commit timestamps in GoogleSQL-dialect databases](https://docs.cloud.google.com/spanner/docs/commit-timestamp)).
- **Interleaving and a foreign key for the same relationship.** Use one of them ([Foreign keys](https://docs.cloud.google.com/spanner/docs/foreign-keys/overview)).
- **A plan to remove interleaving or change the key later.** Interleaving is permanent, and key columns cannot change. You must create a new table and migrate the data ([Schemas overview](https://docs.cloud.google.com/spanner/docs/schema-and-data-model)).
- **A foreign key cascade that deletes millions of rows.** It can pass the 80,000 mutation limit. Use `INTERLEAVE IN PARENT` with `ON DELETE CASCADE` ([Foreign keys](https://docs.cloud.google.com/spanner/docs/foreign-keys/overview)).
- **A migration tool that runs many DDL changes on each deployment.** Too many schema versions make Spanner throttle updates. Batch the DDL ([Schema update best practices](https://docs.cloud.google.com/spanner/docs/schema-updates-best-practices)).
- **Indexes added one at a time after a new table.** Put them in the same batch as `CREATE TABLE`, so no backfill runs ([Schema update best practices](https://docs.cloud.google.com/spanner/docs/schema-updates-best-practices)).
- **The columnar engine for columns that change all the time.** Frequent updates invalidate column data ([About the AlloyDB columnar engine](https://docs.cloud.google.com/alloydb/docs/columnar-engine/about)).
- **AlloyDB for a MySQL or SQL Server app.** AlloyDB is PostgreSQL-compatible only. Cloud SQL runs all three engines ([AlloyDB overview](https://docs.cloud.google.com/alloydb/docs/overview), [Cloud SQL overview](https://docs.cloud.google.com/sql/docs/introduction)).
