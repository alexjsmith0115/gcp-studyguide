## Why it matters

Your app often must let a person download or upload one object, but that person has no Google account. A signed URL gives time-limited access to one object, and your app logic decides who gets the URL. The exam tests when a signed URL is the correct tool and how to sign it without a service account key. It also tests browser uploads and how long a URL stays valid.

## Key points

- A signed URL gives anyone who has it time-limited access to one Cloud Storage resource. The person does not need an account ([Signed URLs](https://docs.cloud.google.com/storage/docs/access-control/signed-urls)).
- Signed URLs work only with XML API endpoints. Uploads and downloads are the most common uses ([Signed URLs](https://docs.cloud.google.com/storage/docs/access-control/signed-urls)).
- Use the V4 signing process. A V4 signed URL is valid for at most 604,800 seconds (7 days) ([Signed URLs](https://docs.cloud.google.com/storage/docs/access-control/signed-urls), [Signatures](https://docs.cloud.google.com/storage/docs/authentication/signatures)).
- The signing account must have permission for the request that the URL makes. Usually this account is a service account ([Signed URLs](https://docs.cloud.google.com/storage/docs/access-control/signed-urls)).
- Sign with the IAM `signBlob` method, not with a downloaded private key. The gcloud CLI and most client libraries can use `signBlob` ([Signatures](https://docs.cloud.google.com/storage/docs/authentication/signatures)).
- To sign with `signBlob`, the caller needs the Service Account Token Creator role, and the project needs the Service Account Credentials API ([V4 signing process with Cloud Storage tools](https://docs.cloud.google.com/storage/docs/access-control/signing-urls-with-helpers)).
- `gcloud storage sign-url --impersonate-service-account` allows at most 12 hours, because the system-managed key that signs the URL may not stay valid longer ([gcloud storage sign-url](https://docs.cloud.google.com/sdk/gcloud/reference/storage/sign-url)).
- HTML forms do not support signed URLs. Use a signed policy document, which also controls the size and content type of the upload ([Upload an object with HTML forms](https://docs.cloud.google.com/storage/docs/xml-api/post-object-forms), [Overview of access control](https://docs.cloud.google.com/storage/docs/access-control)).
- A browser upload to a signed URL needs a CORS configuration on the bucket. XML API endpoints allow CORS only from that configuration ([Cross-origin resource sharing (CORS)](https://docs.cloud.google.com/storage/docs/cross-origin)).
- A signed URL works until it expires or until the key that signed it rotates ([Signed URLs](https://docs.cloud.google.com/storage/docs/access-control/signed-urls)).
- Public access prevention does not block signed URLs ([Public access prevention](https://docs.cloud.google.com/storage/docs/public-access-prevention)).

## Choose how to give access to objects

Start from the identity of the user. If the user has a Google identity, use IAM. If the user has no account and your app decides access, use a signed URL or a signed policy document. Cloud Storage recommends signed URLs for users without accounts, and recommends against publicly writable buckets ([Best practices for Cloud Storage](https://docs.cloud.google.com/storage/docs/best-practices)).

| Requirement | Use | Notes |
|---|---|---|
| Users or service accounts with Google identities need continued access | IAM roles, with uniform bucket-level access | IAM is the recommended access control. Uniform bucket-level access turns off ACLs |
| Anyone on the internet can read the data, with no time limit | Public access (`allUsers`) | Anyone who knows the URI can read the object while it is public. Public access prevention blocks it |
| A user without an account downloads or uploads one object for a short time | Signed URL | Read, write, or delete access to one resource until the URL expires |
| A web form uploads a file, and you must limit the size or content type | Signed policy document | HTML forms do not support signed URLs |
| Users of a mobile or web app that uses the Firebase SDKs for Cloud Storage | Firebase Security Rules | Attribute-based rules, for example on object size |
| Serve content from a private bucket only through Cloud CDN or a load balancer | Private bucket access | The bucket stays private, and you need no signed URLs |
| Time-limited access to cached content through Cloud CDN | Cloud CDN signed URLs or signed cookies | Cloud CDN checks the signature with a key that you add to the backend |

Sources: [Overview of access control](https://docs.cloud.google.com/storage/docs/access-control), [Signed URLs](https://docs.cloud.google.com/storage/docs/access-control/signed-urls), [Make data public](https://docs.cloud.google.com/storage/docs/access-control/making-data-public), [Upload an object with HTML forms](https://docs.cloud.google.com/storage/docs/xml-api/post-object-forms), [Content access control](https://docs.cloud.google.com/cdn/docs/authenticate-content).

Do not use a signed URL to copy, compose, or delete objects, or to edit metadata. The component that creates the URL should make that request itself ([Signed URLs](https://docs.cloud.google.com/storage/docs/access-control/signed-urls)). Signed URLs add to IAM. For example, IAM can give a few people access to the bucket, and a signed URL can give other people one object ([Overview of access control](https://docs.cloud.google.com/storage/docs/access-control)).

Cloud CDN has its own signed URLs. You create a key on the backend bucket or backend service, and Cloud CDN checks the signature. These URLs allow only `GET`, `HEAD`, `OPTIONS`, and `TRACE`. Use signed cookies when you must sign tens or hundreds of URLs for each user, for example video segments ([Content access control](https://docs.cloud.google.com/cdn/docs/authenticate-content)).

## How a V4 signed URL works

A signed URL is an XML API URL with authentication data in its query string ([Signed URLs](https://docs.cloud.google.com/storage/docs/access-control/signed-urls)). A V4 URL has these query string parameters:

| Parameter | Content |
|---|---|
| `X-Goog-Algorithm` | The signing algorithm, for example `GOOG4-RSA-SHA256` |
| `X-Goog-Credential` | Data about the credentials that signed the URL |
| `X-Goog-Date` | The time when the URL becomes usable |
| `X-Goog-Expires` | Seconds from `X-Goog-Date` until the URL expires. The maximum is 604800 (7 days) |
| `X-Goog-SignedHeaders` | Headers that every request with the URL must include |
| `X-Goog-Signature` | The signature |

Source: [Signed URLs](https://docs.cloud.google.com/storage/docs/access-control/signed-urls).

Know these rules:

- Cloud Storage processes a signed request with the authority of the signing account ([Signatures](https://docs.cloud.google.com/storage/docs/authentication/signatures)). That account must have permission for the request ([Signed URLs](https://docs.cloud.google.com/storage/docs/access-control/signed-urls)).
- Use V4. The docs call V2 legacy and recommend V4 ([V2 signing process](https://docs.cloud.google.com/storage/docs/access-control/signed-urls-v2)).
- The signature covers the query string. A request that adds an unsigned query parameter fails ([V4 signing process with Cloud Storage tools](https://docs.cloud.google.com/storage/docs/access-control/signing-urls-with-helpers)).
- A request must send each signed header with the signed value. If you sign an upload with a content type, the client must send that `Content-Type` ([Class Blob](https://docs.cloud.google.com/python/docs/reference/storage/latest/google.cloud.storage.blob.Blob)).
- A user account can sign only with an HMAC key, in your own program. The Cloud Storage tools do not support HMAC credentials for signed URLs ([Signed URLs](https://docs.cloud.google.com/storage/docs/access-control/signed-urls), [V4 signing process with Cloud Storage tools](https://docs.cloud.google.com/storage/docs/access-control/signing-urls-with-helpers)).
- In most cases, the Cloud Storage tools are faster and easier than your own signing program ([V4 signing process with your own program](https://docs.cloud.google.com/storage/docs/access-control/signing-urls-manually)).

## Sign without a service account key

Use the IAM `signBlob` method. It signs with the system-managed private key of the service account ([Create short-lived credentials for a service account](https://docs.cloud.google.com/iam/docs/create-short-lived-credentials-direct)). Google keeps that key, and you cannot get it ([Service account credentials](https://docs.cloud.google.com/iam/docs/service-account-creds)). Local signing with an RSA library needs a downloaded service account key, and the docs discourage it ([Signatures](https://docs.cloud.google.com/storage/docs/authentication/signatures)). For more on keys, see [Secrets and keys](note:1.2-secrets-and-keys).

Set up keyless signing in this order ([V4 signing process with Cloud Storage tools](https://docs.cloud.google.com/storage/docs/access-control/signing-urls-with-helpers)):

1. Enable the Service Account Credentials API.
2. Give the signing service account a Cloud Storage role for the request. Use Storage Object Viewer (`roles/storage.objectViewer`) for downloads only.
3. For uploads that never overwrite an object, use Storage Object Creator (`roles/storage.objectCreator`). For uploads that can overwrite, use Storage Object User (`roles/storage.objectUser`).
4. Give the caller Service Account Token Creator (`roles/iam.serviceAccountTokenCreator`). For user credentials, grant it on the signing service account.
5. If code runs as an attached service account and signs as itself, make that service account the principal. The Cloud Storage page grants the role on the project that contains the service account.

IAM best practices advise against a project-level grant. Token Creator on a project lets the principal impersonate every service account in the project. Instead, manage access for each service account ([Best practices for using service accounts securely](https://docs.cloud.google.com/iam/docs/best-practices-service-accounts)). So in step 5, grant the role on the signing service account only.

From the command line, impersonate the signing service account:

```bash
# Download URL, valid for 10 minutes
gcloud storage sign-url gs://BUCKET_NAME/OBJECT_NAME \
    --impersonate-service-account=SERVICE_ACCOUNT_EMAIL \
    --duration=10m

# Upload URL: the client must send the same Content-Type header
gcloud storage sign-url gs://BUCKET_NAME/OBJECT_NAME \
    --impersonate-service-account=SERVICE_ACCOUNT_EMAIL \
    --http-verb=PUT --duration=1h \
    --headers=content-type=CONTENT_TYPE
```

Source: [V4 signing process with Cloud Storage tools](https://docs.cloud.google.com/storage/docs/access-control/signing-urls-with-helpers).

`gcloud storage sign-url` signs as the service account in `--impersonate-service-account`, or as a service account that gcloud authenticates as directly. Otherwise, it needs a service account key. The default duration is 1 hour. With impersonation, the maximum is 12 hours, because the system-managed key may not stay valid longer. The 7-day maximum applies only to a private key file or an account that you activated with `gcloud auth activate-service-account` ([gcloud storage sign-url](https://docs.cloud.google.com/sdk/gcloud/reference/storage/sign-url)).

By default, `gcloud storage sign-url` reads the bucket metadata to find the region of the bucket ([gcloud storage sign-url](https://docs.cloud.google.com/sdk/gcloud/reference/storage/sign-url)). With impersonation, gcloud sends all API requests as the impersonated service account ([gcloud](https://docs.cloud.google.com/sdk/gcloud/reference)). Storage Object Viewer, Storage Object Creator, and Storage Object User do not include `storage.buckets.get` ([IAM roles for Cloud Storage](https://docs.cloud.google.com/storage/docs/access-control/iam-roles)). So if the signing service account has only these roles, also pass `--region` with the bucket location.

In code, most client libraries can sign with `signBlob` ([Signatures](https://docs.cloud.google.com/storage/docs/authentication/signatures)). The Python docs sample passes no signing account, and it needs a service account key file ([V4 signing process with Cloud Storage tools](https://docs.cloud.google.com/storage/docs/access-control/signing-urls-with-helpers)). Called like that on Compute Engine, `generate_signed_url` cannot sign with the attached service account. The Class Blob page warns about this and suggests a key file. To sign without a key, also pass `service_account_email` and `access_token` to `generate_signed_url` ([Class Blob](https://docs.cloud.google.com/python/docs/reference/storage/latest/google.cloud.storage.blob.Blob)). The access token comes from Application Default Credentials (ADC):

```python
import datetime
import os

import google.auth
import google.auth.transport.requests
from google.cloud import storage

storage_client = storage.Client()  # create once and reuse

def signed_download_url(bucket_name, blob_name):
    credentials, _ = google.auth.default(
        scopes=["https://www.googleapis.com/auth/cloud-platform"])
    credentials.refresh(google.auth.transport.requests.Request())
    blob = storage_client.bucket(bucket_name).blob(blob_name)
    return blob.generate_signed_url(
        version="v4",
        expiration=datetime.timedelta(minutes=15),
        method="GET",
        service_account_email=os.environ["SIGNER_EMAIL"],
        access_token=credentials.token,
    )
```

Sources: [Class Blob](https://docs.cloud.google.com/python/docs/reference/storage/latest/google.cloud.storage.blob.Blob), [V4 signing process with Cloud Storage tools](https://docs.cloud.google.com/storage/docs/access-control/signing-urls-with-helpers), [OpenAI compatibility](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/start/openai).

## Upload with a signed URL

For a single-request upload, sign a `PUT` URL and include the content type. In Python, pass `method="PUT"` and `content_type` to `generate_signed_url`. The client must then send the same `Content-Type` header ([V4 signing process with Cloud Storage tools](https://docs.cloud.google.com/storage/docs/access-control/signing-urls-with-helpers)). The docs test the URL like this:

```bash
curl -X PUT -H 'Content-Type: application/octet-stream' \
    --upload-file my-file 'SIGNED_URL'
```

Source: [V4 signing process with Cloud Storage tools](https://docs.cloud.google.com/storage/docs/access-control/signing-urls-with-helpers).

For large files, use a resumable upload. The client sends one request to start a session, and then sends the data to the session URI ([Resumable uploads](https://docs.cloud.google.com/storage/docs/resumable-uploads)). You can start the session in two ways:

| Option | How it works | When to use it |
|---|---|---|
| The server starts the session | Your server sends the initial `POST` with its own credentials. It gives the session URI to the client, and the client uploads the data | Most cases. You need no signed URL, because the session URI acts as an authentication token |
| The client starts the session with a signed URL | You sign a `POST` URL that requires the header `x-goog-resumable:start`. The client sends the initial `POST` | The client is far from the server. A session is pinned to the region of the initial request |

Sources: [Signed URLs](https://docs.cloud.google.com/storage/docs/access-control/signed-urls), [Resumable uploads](https://docs.cloud.google.com/storage/docs/resumable-uploads), [gcloud storage sign-url](https://docs.cloud.google.com/sdk/gcloud/reference/storage/sign-url).

Know these rules for resumable sessions:

- Anyone who has the session URI can upload data. Send it to the client over HTTPS only ([Signed URLs](https://docs.cloud.google.com/storage/docs/access-control/signed-urls)).
- For a browser upload, include the client's `Origin` header in the request that starts the session. Without it, the browser's cross-origin requests fail ([Resumable uploads](https://docs.cloud.google.com/storage/docs/resumable-uploads)).
- A URL that starts a session must sign the `x-goog-resumable:start` header. If the request does not send it, signature validation fails ([gcloud storage sign-url](https://docs.cloud.google.com/sdk/gcloud/reference/storage/sign-url)).
- A session expires after one week ([Resumable uploads](https://docs.cloud.google.com/storage/docs/resumable-uploads)).

For upload types and preconditions in code, see [Reading and writing data](note:4.1-reading-writing-data).

## Signed policy documents for HTML forms

HTML forms do not support signed URLs. A form uploads with the XML API POST Object request, and a signed policy document authorizes the upload ([Upload an object with HTML forms](https://docs.cloud.google.com/storage/docs/xml-api/post-object-forms)). A policy document gives more control over size, content type, and other upload properties than a signed URL ([Overview of access control](https://docs.cloud.google.com/storage/docs/access-control)).

A policy document is a JSON document with an `expiration` and a list of `conditions`. Each form field needs a condition, except `x-goog-signature`, `file`, and `policy`. The `bucket` condition is always required ([Signatures](https://docs.cloud.google.com/storage/docs/authentication/signatures)).

| Condition type | Example | Meaning |
|---|---|---|
| Exact match | `{"bucket": "travel-maps"}` or `["eq", "$Content-Type", "image/jpeg"]` | The field must have this value |
| Starts with | `["starts-with", "$key", ""]` | The field must start with this value. An empty value allows any value |
| Content length range | `["content-length-range", 0, 1000000]` | The file size in bytes must be in this range |

Source: [Signatures](https://docs.cloud.google.com/storage/docs/authentication/signatures).

The client library builds and signs the policy. It returns the form URL and the hidden fields:

```python
import datetime
from google.cloud import storage

def generate_signed_post_policy_v4(bucket_name, blob_name):
    storage_client = storage.Client()
    policy = storage_client.generate_signed_post_policy_v4(
        bucket_name,
        blob_name,
        expiration=datetime.timedelta(minutes=10),
        fields={"x-goog-meta-test": "data"},
    )
    form = f"<form action='{policy['url']}' method='POST' enctype='multipart/form-data'>\n"
    # Include all fields returned in the HTML form as they're required
    for key, value in policy["fields"].items():
        form += f"  <input name='{key}' value='{value}' type='hidden'/>\n"
    form += "  <input type='file' name='file'/><br />\n"
    form += "  <input type='submit' value='Upload File' /><br />\n</form>"
    return form
```

Source: [Upload an object with HTML forms](https://docs.cloud.google.com/storage/docs/xml-api/post-object-forms).

Know these form rules ([Upload an object with HTML forms](https://docs.cloud.google.com/storage/docs/xml-api/post-object-forms)):

- The form uses `method="post"` and `enctype="multipart/form-data"`. The action is the bucket URL.
- The `key` field is the object name. It can contain `${filename}`.
- The `file` field must be the last field. One form uploads one object.
- An upload replaces an object with the same name.
- A form without a `policy` field sends an anonymous request.
- `success_action_redirect` sends the user to a URL after the upload. `success_action_status` sets the status code, and the default is 204.

## CORS for browser uploads

A browser upload to a signed URL is a cross-origin request. Signed URLs work only with XML API endpoints, and XML API endpoints allow CORS only from the bucket's CORS configuration. JSON API endpoints always allow CORS ([Signed URLs](https://docs.cloud.google.com/storage/docs/access-control/signed-urls), [Cross-origin resource sharing (CORS)](https://docs.cloud.google.com/storage/docs/cross-origin)). So set a CORS configuration on the bucket before a browser uploads.

A `PUT` request always triggers a preflight request ([CORS configuration examples](https://docs.cloud.google.com/storage/docs/cors-configurations)). Cloud Storage compares the method and headers with the configuration. If they do not match, the browser does not send the upload ([Cross-origin resource sharing (CORS)](https://docs.cloud.google.com/storage/docs/cross-origin)). This configuration allows direct uploads from one site:

```json
{
  "cors": [
    {
      "origin": ["https://www.example.com"],
      "method": ["PUT", "POST"],
      "responseHeader": ["Content-Type", "x-goog-resumable"],
      "maxAgeSeconds": 3600
    }
  ]
}
```

```bash
gcloud storage buckets update gs://BUCKET_NAME --cors-file=CORS_CONFIG_FILE
```

Sources: [CORS configuration examples](https://docs.cloud.google.com/storage/docs/cors-configurations), [Cross-origin resource sharing (CORS)](https://docs.cloud.google.com/storage/docs/cross-origin), [Set up and view CORS configurations](https://docs.cloud.google.com/storage/docs/using-cors).

Know these CORS rules ([Cross-origin resource sharing (CORS)](https://docs.cloud.google.com/storage/docs/cross-origin)):

- The `*` origin helps for tests. In most cases, list only your own origins.
- `maxAgeSeconds` sets how long the browser keeps the preflight result. The default is 3600.
- The XML API does not support CORS credentials, for example cookies.
- The `storage.cloud.google.com` endpoint does not allow CORS requests.

## Limit and revoke access

Plan for misuse before you share a URL. A signed URL works until it expires or until the key that signed it rotates, and anyone who has the URL can use it ([Signed URLs](https://docs.cloud.google.com/storage/docs/access-control/signed-urls)). Use these controls:

- Set a short expiration. `gcloud storage sign-url` uses 1 hour by default ([gcloud storage sign-url](https://docs.cloud.google.com/sdk/gcloud/reference/storage/sign-url)).
- Give the signing service account only the role that the URLs need. Grant the minimum permission for the task ([V4 signing process with Cloud Storage tools](https://docs.cloud.google.com/storage/docs/access-control/signing-urls-with-helpers), [Overview of access control](https://docs.cloud.google.com/storage/docs/access-control)).
- To stop uploads from overwriting objects, sign with Storage Object Creator. Overwrite needs `storage.objects.delete` ([V4 signing process with Cloud Storage tools](https://docs.cloud.google.com/storage/docs/access-control/signing-urls-with-helpers)).
- Sign the HTTP method and the headers that the request must send ([Class Blob](https://docs.cloud.google.com/python/docs/reference/storage/latest/google.cloud.storage.blob.Blob)).

How access ends early depends on how you signed:

| Signed with | How access ends before expiration |
|---|---|
| A service account key (not recommended) | Rotate the key that signed the URL |
| `signBlob` and the system-managed key | Google rotates the key regularly. So `gcloud storage sign-url` limits these URLs to 12 hours |
| A Cloud CDN signed request key | Delete the key from the backend. Cloud CDN then stops honoring URLs that the key signed |

Sources: [Signed URLs](https://docs.cloud.google.com/storage/docs/access-control/signed-urls), [Service account credentials](https://docs.cloud.google.com/iam/docs/service-account-creds), [gcloud storage sign-url](https://docs.cloud.google.com/sdk/gcloud/reference/storage/sign-url), [Use signed URLs](https://docs.cloud.google.com/cdn/docs/using-signed-urls).

For Cloud CDN, rotate keys regularly: delete the oldest key, then add a new key. Set each URL to expire as soon as possible ([Use signed URLs](https://docs.cloud.google.com/cdn/docs/using-signed-urls), [Content access control](https://docs.cloud.google.com/cdn/docs/authenticate-content)).

## AWS mapping

| AWS | Google Cloud | Difference that matters |
|---|---|---|
| Amazon S3 presigned URLs | Cloud Storage signed URLs | XML API endpoints only. Sign with `signBlob` through impersonation, not with a key. gcloud then allows at most 12 hours |
| S3-compatible requests signed with HMAC keys | Cloud Storage HMAC keys with the XML API | The Cloud Storage tools do not create signed URLs from HMAC keys |
| Amazon CloudFront signed URLs and signed cookies | Cloud CDN signed URLs and signed cookies | You add the signing key to the backend bucket or backend service. Only `GET`, `HEAD`, `OPTIONS`, and `TRACE` |

Sources: [Migrate from Amazon S3 to Cloud Storage](https://docs.cloud.google.com/architecture/migrate-amazon-s3-to-cloud-storage), [Compare AWS and Azure services to Google Cloud](https://docs.cloud.google.com/docs/get-started/aws-azure-gcp-service-comparison), [Simple migration from Amazon S3](https://docs.cloud.google.com/storage/docs/aws-simple-migration), [V4 signing process with Cloud Storage tools](https://docs.cloud.google.com/storage/docs/access-control/signing-urls-with-helpers), [gcloud storage sign-url](https://docs.cloud.google.com/sdk/gcloud/reference/storage/sign-url), [Content access control](https://docs.cloud.google.com/cdn/docs/authenticate-content).

## Exam traps

- **A public bucket so that customers without accounts can download a file.** Use a signed URL. Cloud Storage recommends signed URLs for users without accounts ([Best practices for Cloud Storage](https://docs.cloud.google.com/storage/docs/best-practices)).
- **Public access prevention blocks signed URLs.** It does not. Signed URLs get access through scoped service account permissions ([Public access prevention](https://docs.cloud.google.com/storage/docs/public-access-prevention)).
- **A service account key file to sign URLs on Cloud Run or Compute Engine.** Sign with `signBlob`. Local signing needs a downloaded private key, and the docs discourage it ([Signatures](https://docs.cloud.google.com/storage/docs/authentication/signatures)).
- **Only a Cloud Storage role for keyless signing.** The caller also needs Service Account Token Creator, and the Service Account Credentials API must be on ([V4 signing process with Cloud Storage tools](https://docs.cloud.google.com/storage/docs/access-control/signing-urls-with-helpers)).
- **A 7-day URL from `gcloud storage sign-url --impersonate-service-account`.** The maximum is 12 hours. Seven days needs a private key file ([gcloud storage sign-url](https://docs.cloud.google.com/sdk/gcloud/reference/storage/sign-url)).
- **A signed URL in the action of an HTML form.** Forms do not support signed URLs. Use a signed policy document ([Upload an object with HTML forms](https://docs.cloud.google.com/storage/docs/xml-api/post-object-forms)).
- **A browser upload that fails with a CORS error.** Add a CORS configuration to the bucket. XML API endpoints use only that configuration ([Cross-origin resource sharing (CORS)](https://docs.cloud.google.com/storage/docs/cross-origin)).
- **A server that starts a browser's resumable upload without the `Origin` header.** The browser's requests then fail. Send the client's origin in the request that starts the session ([Resumable uploads](https://docs.cloud.google.com/storage/docs/resumable-uploads)).
- **A signed URL for each chunk of a resumable upload.** After the first request, the client uses the session URI, not a signed URL ([Signed URLs](https://docs.cloud.google.com/storage/docs/access-control/signed-urls)).
- **A signed URL so that a client can copy or delete objects.** The server should make that request itself ([Signed URLs](https://docs.cloud.google.com/storage/docs/access-control/signed-urls)).
- **Many signed URLs per user for video segments behind Cloud CDN.** Use Cloud CDN signed cookies ([Content access control](https://docs.cloud.google.com/cdn/docs/authenticate-content)).
