## Why it matters

Your code needs credentials to call Google APIs, Cloud Run services, and databases. You decide where the code gets them. The choices are your user account, an attached service account, Workload Identity Federation, and, as the last choice, a service account key. The exam tests the search order of Application Default Credentials (ADC), the token type for each target, and the database connectors. It also tests how to remove keys from workloads outside Google Cloud and on GKE.

## Key points

- ADC is the strategy that the authentication libraries use to find credentials. It checks the `GOOGLE_APPLICATION_CREDENTIALS` environment variable, then the local file from `gcloud auth application-default login`, then the attached service account ([How Application Default Credentials works](https://docs.cloud.google.com/docs/authentication/application-default-credentials)).
- For production code on Google Cloud, attach a user-managed service account. Google lists this method as the most secure way to use a service account ([Authentication for Google Cloud APIs and services](https://docs.cloud.google.com/docs/authentication)).
- On a workstation, use your user credentials or impersonate a service account. Use a key only as the last choice ([Set up ADC for a local development environment](https://docs.cloud.google.com/docs/authentication/set-up-adc-local-dev-environment), [Use service account impersonation](https://docs.cloud.google.com/docs/authentication/use-service-account-impersonation)).
- Access tokens call Google APIs. ID tokens call Cloud Run, Cloud Run functions, apps behind IAP, and API Gateway. An ID token cannot call a Google API ([Token types](https://docs.cloud.google.com/docs/authentication/token-types), [Get an ID token](https://docs.cloud.google.com/docs/authentication/get-id-token)).
- IAM is the primary authorization control. On a Compute Engine VM, the access scopes must also allow the request ([Authentication for Google Cloud APIs and services](https://docs.cloud.google.com/docs/authentication), [Service accounts (Compute Engine)](https://docs.cloud.google.com/compute/docs/access/service-accounts)).
- The Cloud SQL Language Connectors and the Cloud SQL Auth Proxy authorize connections with IAM and encrypt the traffic. They do not create a network path ([Cloud SQL Language Connectors overview](https://docs.cloud.google.com/sql/docs/postgres/language-connectors), [About the Cloud SQL Auth Proxy](https://docs.cloud.google.com/sql/docs/postgres/sql-proxy)).
- Automatic IAM database authentication replaces the database password with a short-lived OAuth 2.0 access token that the connector refreshes ([IAM authentication](https://docs.cloud.google.com/sql/docs/postgres/iam-authentication)).
- Workload Identity Federation gives workloads on AWS, on Azure, on premises, or in deployment pipelines access to Google Cloud without a service account key ([Workload Identity Federation](https://docs.cloud.google.com/iam/docs/workload-identity-federation)).
- Workload Identity Federation for GKE is the recommended way for GKE workloads to access Google Cloud services. The console still calls it Workload Identity ([About Workload Identity Federation for GKE](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/workload-identity), [Authenticate to Google Cloud APIs from GKE workloads](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/workload-identity)).

## Choose how your code gets credentials

Start with the place where the code runs ([Authentication for Google Cloud APIs and services](https://docs.cloud.google.com/docs/authentication)):

| Where the code runs | Credential | How ADC finds it |
|---|---|---|
| Workstation | Your user account | Local ADC file |
| Workstation, and the code must act as a service account | Impersonation of the service account | Local ADC file created with `--impersonate-service-account` |
| Cloud Shell | The account that you signed in with | Automatic. You cannot configure ADC there with gcloud |
| Compute Engine, Cloud Run, Cloud Run functions, App Engine | An attached user-managed service account | Metadata server |
| GKE | Workload Identity Federation for GKE | GKE metadata server |
| AWS, Azure, on premises, deployment pipeline | Workload Identity Federation | Credential configuration file in `GOOGLE_APPLICATION_CREDENTIALS` |
| Outside Google Cloud, and the identity provider does not support federation | A service account key (last choice) | Key file in `GOOGLE_APPLICATION_CREDENTIALS` |

Sources: [Authentication for Google Cloud APIs and services](https://docs.cloud.google.com/docs/authentication), [How Application Default Credentials works](https://docs.cloud.google.com/docs/authentication/application-default-credentials), [Set up ADC for a cloud-based development environment](https://docs.cloud.google.com/docs/authentication/set-up-adc-cloud-dev-environment), [Set up ADC for on-premises or another cloud provider](https://docs.cloud.google.com/docs/authentication/set-up-adc-on-premises), [About Workload Identity Federation for GKE](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/workload-identity).

Google orders the service account methods from most secure to least secure ([Authentication for Google Cloud APIs and services](https://docs.cloud.google.com/docs/authentication)):

1. An attached user-managed service account.
2. Impersonation by another service account.
3. Workload Identity Federation.
4. The default service account.
5. A service account key.

The default service account is highly privileged by default ([Authentication for Google Cloud APIs and services](https://docs.cloud.google.com/docs/authentication)). An organization policy can block key creation (see [Retention and organization policies](note:1.2-retention-and-org-policy)). For keys and secrets, see [Secrets, credentials, and keys](note:1.2-secrets-and-keys).

Except for API keys, Google APIs do not accept credentials directly. Your application must get a token and send it to the API ([Authentication for Google Cloud APIs and services](https://docs.cloud.google.com/docs/authentication)). A Cloud Client Library does this with ADC, so the code has no credential logic:

```python
from google.cloud import storage

# No credentials in the code: the client library finds them with ADC.
storage_client = storage.Client(project=project_id)
for bucket in storage_client.list_buckets():
    print(bucket.name)
```

Source: [Authenticate with client libraries](https://docs.cloud.google.com/docs/authentication/client-libraries).

## How ADC finds credentials

ADC checks these locations in this order ([How Application Default Credentials works](https://docs.cloud.google.com/docs/authentication/application-default-credentials)):

1. The `GOOGLE_APPLICATION_CREDENTIALS` environment variable. It points to a credential configuration file for Workload Identity Federation or Workforce Identity Federation, or to a service account key (not recommended).
2. The local ADC file: `$HOME/.config/gcloud/application_default_credentials.json` on Linux and macOS, `%APPDATA%\gcloud\application_default_credentials.json` on Windows.
3. The attached service account, from the metadata server.

The order does not show which location is best ([How Application Default Credentials works](https://docs.cloud.google.com/docs/authentication/application-default-credentials)). It shows which credential wins:

- The environment variable wins over all other credentials, also over Workload Identity Federation for GKE ([Troubleshoot your ADC setup](https://docs.cloud.google.com/docs/authentication/troubleshoot-adc)).
- On Cloud Run, never set `GOOGLE_APPLICATION_CREDENTIALS`. Configure a user-managed service account ([Introduction to service identity](https://docs.cloud.google.com/run/docs/securing/service-identity)).
- An API key in the request wins over ADC ([Troubleshoot your ADC setup](https://docs.cloud.google.com/docs/authentication/troubleshoot-adc)).

**gcloud credentials are not ADC credentials.** `gcloud auth login` sets the credentials for gcloud commands. `gcloud auth application-default login` sets the credentials for your code. The gcloud CLI itself does not use ADC ([Troubleshoot your ADC setup](https://docs.cloud.google.com/docs/authentication/troubleshoot-adc), [Set up Application Default Credentials](https://docs.cloud.google.com/docs/authentication/provide-credentials-adc)). Do not use `gcloud auth login` for automated workloads on remote systems with persistent storage ([Authenticate for the gcloud CLI](https://docs.cloud.google.com/sdk/docs/authenticate)). See also [Developer tools](note:2.1-developer-tools).

**Quota project.** With user credentials, some APIs need a quota project, for example `gcloud auth application-default set-quota-project PROJECT_ID`. You need the `serviceusage.services.use` permission on that project ([Troubleshoot your ADC setup](https://docs.cloud.google.com/docs/authentication/troubleshoot-adc)). See [Calling Google Cloud APIs](note:4.2-calling-google-apis).

## Local development: user credentials or impersonation

User credentials are the best option on a workstation. The local ADC file contains your refresh token, so revoke it with `gcloud auth application-default revoke` when you no longer need it. The file belongs to your user account, not to a gcloud configuration ([Set up ADC for a local development environment](https://docs.cloud.google.com/docs/authentication/set-up-adc-local-dev-environment)).

Impersonate a service account to test with the permissions of the production workload. Impersonation is more secure than a key: it needs an authenticated caller, and its credentials do not persist ([Use service account impersonation](https://docs.cloud.google.com/docs/authentication/use-service-account-impersonation)). The setup:

1. Enable the Service Account Credentials API.
2. Get the Service Account Token Creator role (`roles/iam.serviceAccountTokenCreator`) on the service account. You need it even in your own project, and even with the Owner role.
3. Use the `--impersonate-service-account` flag, or make impersonation the default for gcloud.

Sources: [Use service account impersonation](https://docs.cloud.google.com/docs/authentication/use-service-account-impersonation), [Authenticate with REST](https://docs.cloud.google.com/docs/authentication/rest).

```bash
# ADC file with your user credentials
gcloud auth application-default login

# ADC file that impersonates a service account
gcloud auth application-default login --impersonate-service-account SERVICE_ACCT_EMAIL

# gcloud commands impersonate the service account by default
gcloud config set auth/impersonate_service_account SERVICE_ACCT_EMAIL
```

Sources: [Set up ADC for a local development environment](https://docs.cloud.google.com/docs/authentication/set-up-adc-local-dev-environment), [Use service account impersonation](https://docs.cloud.google.com/docs/authentication/use-service-account-impersonation).

Impersonation is similar to `AssumeRole` in AWS Security Token Service. Most audit logs show both the caller and the service account. Authentication with a key shows only the service account ([Service account impersonation](https://docs.cloud.google.com/iam/docs/service-account-impersonation)).

## Access tokens and ID tokens

The target of the request decides the token type ([Token types](https://docs.cloud.google.com/docs/authentication/token-types), [Get an ID token](https://docs.cloud.google.com/docs/authentication/get-id-token)):

| | Access token | ID token |
|---|---|---|
| Calls | Google APIs, for example Cloud Storage or Pub/Sub | Cloud Run, Cloud Run functions, apps behind IAP, APIs on API Gateway or Cloud Endpoints |
| Format | Opaque | JWT, signed but not encrypted |
| What limits it | OAuth 2.0 scopes and the IAM roles of the principal | The `aud` claim: the Cloud Run service URL or a custom audience. For IAP, usually the OAuth client ID |
| Lifetime | 1 hour by default. Service account tokens: 5 minutes to 12 hours | 1 hour at most |
| Revocable | User tokens: yes. Service account tokens: no | No |
| Metadata server path | `.../service-accounts/default/token` | `.../service-accounts/default/identity?audience=AUDIENCE` |
| gcloud, for development | `gcloud auth print-access-token` | `gcloud auth print-identity-token` |

Sources: [Token types](https://docs.cloud.google.com/docs/authentication/token-types), [Get an ID token](https://docs.cloud.google.com/docs/authentication/get-id-token), [Introduction to service identity](https://docs.cloud.google.com/run/docs/securing/service-identity), [Authenticate with REST](https://docs.cloud.google.com/docs/authentication/rest), [Programmatic authentication](https://docs.cloud.google.com/iap/docs/authentication-howto).

On Google Cloud, the metadata server gives ID tokens for the attached service account, not for user credentials. Set the audience to the URL of the receiving service:

```python
import google.auth.transport.requests
from google.auth import compute_engine


def idtoken_from_metadata_server(url: str) -> str:
    request = google.auth.transport.requests.Request()
    credentials = compute_engine.IDTokenCredentials(
        request=request, target_audience=url, use_metadata_identity_endpoint=True
    )
    credentials.refresh(request)
    return credentials.token  # send as "Authorization: Bearer TOKEN"
```

Source: [Get an ID token](https://docs.cloud.google.com/docs/authentication/get-id-token).

Other ways to get an ID token ([Get an ID token](https://docs.cloud.google.com/docs/authentication/get-id-token)):

- **Connecting services.** Cloud Scheduler, Cloud Tasks, Pub/Sub push subscriptions, and Workflows can add an ID token with the correct audience.
- **Impersonation.** Grant `roles/run.invoker` to a privilege-bearing service account. Grant the caller the Service Account OpenID Connect Identity Token Creator role (`roles/iam.serviceAccountOpenIdTokenCreator`) on it. Impersonation should always involve two principals: the caller and the privilege-bearing service account. Self-impersonation to create tokens is a security vulnerability, because the service account can refresh its access token indefinitely.
- **Development.** `gcloud auth print-identity-token` works only for Cloud Run and Cloud Run functions.

The gcloud ID token has no audience claim, so someone can replay it. In production, use service account ID tokens with an audience ([Authenticate developers](https://docs.cloud.google.com/run/docs/authenticating/developers)). For the full pattern between Cloud Run services, see [Secure service-to-service communication](note:1.2-service-to-service).

## Scopes and IAM

IAM controls which principal can do what on which resource. A scope limits what an access token can do. The `https://www.googleapis.com/auth/cloud-platform` scope covers all Google Cloud services. A narrower scope reduces risk where tokens can leak, for example in mobile apps ([Authentication for Google Cloud APIs and services](https://docs.cloud.google.com/docs/authentication)).

On Compute Engine, access scopes are the legacy method to limit a VM. Both the access scopes and the IAM roles must allow the request:

| VM access scope | IAM role on the service account | Can the app write Cloud Storage objects? |
|---|---|---|
| `cloud-platform` | `roles/storage.objectAdmin` | Yes |
| `cloud-platform` | `roles/storage.objectViewer` | No. IAM blocks it |
| `devstorage.read_only` | `roles/storage.objectAdmin` | No. The scope blocks it |

Source: [Service accounts (Compute Engine)](https://docs.cloud.google.com/compute/docs/access/service-accounts).

Best practice: set the `cloud-platform` scope and control access with IAM roles. Access scopes do not apply to gRPC calls ([Service accounts (Compute Engine)](https://docs.cloud.google.com/compute/docs/access/service-accounts)). A local ADC file with user credentials also uses `cloud-platform` by default. For APIs outside Google Cloud, such as Google Drive, add `--scopes` with your own OAuth client ID or an impersonated service account ([How Application Default Credentials works](https://docs.cloud.google.com/docs/authentication/application-default-credentials)).

## Cloud SQL and AlloyDB: Auth Proxy, Language Connectors, and IAM database authentication

The proxies and connectors handle authentication and encryption, not routing. They authorize with IAM, encrypt the traffic, and remove the need to manage SSL certificates or authorized networks. They use the network path that already exists ([About the Cloud SQL Auth Proxy](https://docs.cloud.google.com/sql/docs/postgres/sql-proxy), [Cloud SQL Language Connectors overview](https://docs.cloud.google.com/sql/docs/postgres/language-connectors), [AlloyDB Language Connectors overview](https://docs.cloud.google.com/alloydb/docs/language-connectors-overview)).

| | Cloud SQL Auth Proxy | Cloud SQL Language Connectors | AlloyDB Auth Proxy | AlloyDB Language Connectors |
|---|---|---|---|---|
| Form | A separate process | A library: Java, Python, Go, Node.js | A separate process | A library: Java, Python, Go |
| Encryption | TLS 1.3 | TLS with a temporary certificate | mTLS 1.3 | mTLS with TLS 1.3 |
| IAM role to connect | Cloud SQL Client (`roles/cloudsql.client`) | Cloud SQL Client | `roles/alloydb.client` and `roles/serviceusage.serviceUsageConsumer` | The same two roles |
| Automatic IAM database authentication | `--auto-iam-authn` | `enable_iam_auth=True` (Python) | Supported | Supported, not the default |

Sources: [About the Cloud SQL Auth Proxy](https://docs.cloud.google.com/sql/docs/postgres/sql-proxy), [Cloud SQL Language Connectors overview](https://docs.cloud.google.com/sql/docs/postgres/language-connectors), [Roles and permissions](https://docs.cloud.google.com/sql/docs/postgres/roles-and-permissions), [Log in using IAM database authentication](https://docs.cloud.google.com/sql/docs/postgres/iam-logins), [About the AlloyDB Auth Proxy](https://docs.cloud.google.com/alloydb/docs/auth-proxy/overview), [AlloyDB Language Connectors overview](https://docs.cloud.google.com/alloydb/docs/language-connectors-overview), [Connect using the AlloyDB Language Connectors](https://docs.cloud.google.com/alloydb/docs/connect-language-connectors).

Choose between them ([About the Cloud SQL Auth Proxy](https://docs.cloud.google.com/sql/docs/postgres/sql-proxy), [About the AlloyDB Auth Proxy](https://docs.cloud.google.com/alloydb/docs/auth-proxy/overview), [Cloud SQL Language Connectors overview](https://docs.cloud.google.com/sql/docs/postgres/language-connectors)):

- **Language Connector** when your language has one. The Cloud SQL docs say to use the Java, Python, or Go connector instead of the proxy.
- **Auth Proxy** for other languages. Run it on the same machine as the workload, because the link from the app to the proxy is not encrypted. It does not pool connections. Allow egress on ports 443 and 3307 (Cloud SQL) or 443 and 5433 (AlloyDB).
- **Connector enforcement** to make Cloud SQL reject direct connections.

The Cloud SQL Language Connectors and the AlloyDB Auth Proxy find credentials with ADC ([Connect using Cloud SQL Language Connectors](https://docs.cloud.google.com/sql/docs/postgres/connect-connectors), [About the AlloyDB Auth Proxy](https://docs.cloud.google.com/alloydb/docs/auth-proxy/overview)). For network paths and pool sizing, see [Connecting to datastores](note:4.1-datastore-connections).

**IAM database authentication** logs in with a temporary OAuth 2.0 access token instead of a password, and it requires SSL ([IAM authentication](https://docs.cloud.google.com/sql/docs/postgres/iam-authentication)). Rules for Cloud SQL:

- In automatic mode, the connector gets and refreshes the token. In manual mode, you pass the token as the password, and new logins fail after one hour. Use automatic mode for connection pools ([IAM authentication](https://docs.cloud.google.com/sql/docs/postgres/iam-authentication)).
- The instance needs the `cloudsql.iam_authentication` flag. The console sets it by default. The flag does not stop existing non-IAM users from logging in with passwords. To reject direct connections, use connector enforcement ([IAM authentication](https://docs.cloud.google.com/sql/docs/postgres/iam-authentication), [Connect using Cloud SQL Language Connectors](https://docs.cloud.google.com/sql/docs/postgres/connect-connectors)).
- The principal needs Cloud SQL Instance User (`roles/cloudsql.instanceUser`) to log in and Cloud SQL Client to connect. The principal that starts the connector must be the principal that logs in ([Log in using IAM database authentication](https://docs.cloud.google.com/sql/docs/postgres/iam-logins)).
- A service account's database user name is its email without `.gserviceaccount.com`. A new IAM database user has no database privileges until you grant them, for example with `GRANT` ([Log in using IAM database authentication](https://docs.cloud.google.com/sql/docs/postgres/iam-logins)).
- Proxy v1 (`cloud_sql_proxy`, `--enable_iam_login`) is old. Use v2 (`cloud-sql-proxy`, `--auto-iam-authn`) ([Log in using IAM database authentication](https://docs.cloud.google.com/sql/docs/postgres/iam-logins)).

```python
from google.cloud.sql.connector import Connector, IPTypes
import pg8000
import sqlalchemy

connector = Connector(refresh_strategy="LAZY")


def getconn() -> pg8000.dbapi.Connection:
    return connector.connect(
        "PROJECT:REGION:INSTANCE",      # instance connection name
        "pg8000",
        user="SA_NAME@PROJECT_ID.iam",  # service account email without .gserviceaccount.com
        db="DB_NAME",
        enable_iam_auth=True,           # automatic IAM database authentication
        ip_type=IPTypes.PRIVATE,
    )


pool = sqlalchemy.create_engine("postgresql+pg8000://", creator=getconn)
```

Source: [Log in using IAM database authentication](https://docs.cloud.google.com/sql/docs/postgres/iam-logins).

AlloyDB differs: IAM authentication is disabled by default. Set the `alloydb.iam_authentication` flag to `on`, and grant `roles/alloydb.databaseUser` and `roles/serviceusage.serviceUsageConsumer` ([Manage IAM authentication](https://docs.cloud.google.com/alloydb/docs/database-users/manage-iam-auth)).

## Workload Identity Federation for external workloads

Workload Identity Federation follows the OAuth 2.0 token exchange specification. The workload sends a credential from its identity provider to the Security Token Service and gets a federated token back ([Workload Identity Federation](https://docs.cloud.google.com/iam/docs/workload-identity-federation)). Use it when the app has ambient credentials, such as an EC2 instance profile, an Azure managed identity, or a GitHub Actions ID token ([Best practices for using Workload Identity Federation](https://docs.cloud.google.com/iam/docs/best-practices-for-using-workload-identity-federation)).

- **Workload identity pool.** A group of external identities. Google recommends one pool for each environment, such as development, staging, and production ([Workload Identity Federation](https://docs.cloud.google.com/iam/docs/workload-identity-federation)).
- **Provider.** The relationship with one identity provider. Its attribute mapping must set `google.subject`. Its attribute condition, a CEL expression, accepts or rejects each credential ([Workload Identity Federation](https://docs.cloud.google.com/iam/docs/workload-identity-federation), [Configure Workload Identity Federation with deployment pipelines](https://docs.cloud.google.com/iam/docs/workload-identity-federation-with-deployment-pipelines)).
- **Credential configuration file.** It tells the library where to get the external credential, which provider to use, and which service account to impersonate, if any. It has no private key and is not confidential. Point `GOOGLE_APPLICATION_CREDENTIALS` at it ([Configure Workload Identity Federation with AWS or Azure VMs](https://docs.cloud.google.com/iam/docs/workload-identity-federation-with-other-clouds)).

| Option | What you grant | When to use it |
|---|---|---|
| Direct resource access (recommended) | A role on the resource to a `principal://` or `principalSet://` identifier | The default choice |
| Service account impersonation | Workload Identity User (`roles/iam.workloadIdentityUser`) on a service account | An API has limits with direct access |

Sources: [Workload Identity Federation](https://docs.cloud.google.com/iam/docs/workload-identity-federation), [Configure Workload Identity Federation with AWS or Azure VMs](https://docs.cloud.google.com/iam/docs/workload-identity-federation-with-other-clouds).

Principal identifiers use the project number, not the project ID, for example `principal://iam.googleapis.com/projects/PROJECT_NUMBER/locations/global/workloadIdentityPools/POOL_ID/subject/SUBJECT`. A grant to all identities in a pool is a risk. Limit access with attributes and conditions ([Workload Identity Federation](https://docs.cloud.google.com/iam/docs/workload-identity-federation)).

**GitHub Actions.** GitHub, GitLab SaaS, and HCP Terraform use one issuer URL for all organizations. You must add an attribute condition for your organization, for example `assertion.repository_owner=='ORGANIZATION'`. Prefer the numeric `*_id` claims, because someone can claim a deleted repository or organization name ([Configure Workload Identity Federation with deployment pipelines](https://docs.cloud.google.com/iam/docs/workload-identity-federation-with-deployment-pipelines)). Keep pools and providers in a dedicated project ([Best practices for using Workload Identity Federation](https://docs.cloud.google.com/iam/docs/best-practices-for-using-workload-identity-federation)).

```yaml
jobs:
  build:
    permissions:
      id-token: write   # lets the job get a GitHub ID token
      contents: read
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - id: 'auth'
        uses: 'google-github-actions/auth@v1'
        with:
          create_credentials_file: true
          workload_identity_provider: 'projects/PROJECT_NUMBER/locations/global/workloadIdentityPools/POOL_ID/providers/PROVIDER_ID'
          service_account: 'SERVICE_ACCOUNT_EMAIL'  # omit for direct resource access
```

Source: [Configure Workload Identity Federation with deployment pipelines](https://docs.cloud.google.com/iam/docs/workload-identity-federation-with-deployment-pipelines).

## Workload Identity Federation for GKE

Each Kubernetes workload gets its own identity for Google Cloud APIs. Google manages the pool, `PROJECT_ID.svc.id.goog`, and its provider ([About Workload Identity Federation for GKE](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/workload-identity), [Authenticate to Google Cloud APIs from GKE workloads](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/workload-identity)). How it works:

1. ADC in the Pod asks the metadata server for a token. Client library code needs no change.
2. The GKE metadata server on the node intercepts the request. It gets a Kubernetes ServiceAccount token, a JWT that the API server signs.
3. It exchanges this JWT with the Security Token Service for a short-lived federated access token.

Sources: [About Workload Identity Federation for GKE](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/workload-identity), [Authenticate to Google Cloud APIs from GKE workloads](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/workload-identity).

Setup ([Authenticate to Google Cloud APIs from GKE workloads](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/workload-identity)):

- **Autopilot:** always on.
- **Standard:** `gcloud container clusters update CLUSTER_NAME --location=LOCATION --workload-pool=PROJECT_ID.svc.id.goog`. Existing node pools do not change. Update them with `--workload-metadata=GKE_METADATA`, or create new node pools.
- **Access (best practice):** grant IAM roles to the principal identifier of the Kubernetes ServiceAccount.

```bash
gcloud storage buckets add-iam-policy-binding gs://BUCKET \
    --role=roles/storage.objectViewer \
    --member=principal://iam.googleapis.com/projects/PROJECT_NUMBER/locations/global/workloadIdentityPools/PROJECT_ID.svc.id.goog/subject/ns/NAMESPACE/sa/KSA_NAME \
    --condition=None
```

Source: [Authenticate to Google Cloud APIs from GKE workloads](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/workload-identity).

If an API has limits with federated identities, link the Kubernetes ServiceAccount to an IAM service account. Grant `roles/iam.workloadIdentityUser` on the IAM service account to `serviceAccount:PROJECT_ID.svc.id.goog[NAMESPACE/KSA_NAME]`, and annotate the Kubernetes ServiceAccount with `iam.gke.io/gcp-service-account=IAM_SA_EMAIL`. You need both ([Authenticate to Google Cloud APIs from GKE workloads](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/workload-identity)).

Behavior that the exam tests ([About Workload Identity Federation for GKE](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/workload-identity)):

- Enabling the feature grants no IAM permissions.
- **Identity sameness.** All clusters in a project share one pool. The same namespace and Kubernetes ServiceAccount name in any of them get the same access. Conditional IAM policies can limit this access to specific clusters. Put untrusted clusters in other projects, or use distinct namespace names.
- The node service account, not the workload, pulls container images.
- Pods with `hostNetwork: true` do not use the feature.

See also [GKE deployments](note:3.2-gke-deployments) and [Service accounts, IAM roles, and least privilege](note:1.2-service-accounts-least-privilege).

## AWS mapping

| AWS | Google Cloud | Difference that matters |
|---|---|---|
| AWS STS `AssumeRole` | Service account impersonation | The caller needs Token Creator, also as project Owner |
| SDK default credential chain † | Application Default Credentials | The environment variable wins, also on GKE |

## Exam traps

- **`gcloud auth login` to give credentials to local code.** Code uses ADC. Run `gcloud auth application-default login` ([Troubleshoot your ADC setup](https://docs.cloud.google.com/docs/authentication/troubleshoot-adc)).
- **A key file in `GOOGLE_APPLICATION_CREDENTIALS` on Cloud Run or GKE.** It overrides the attached service account and Workload Identity Federation for GKE ([Troubleshoot your ADC setup](https://docs.cloud.google.com/docs/authentication/troubleshoot-adc), [Introduction to service identity](https://docs.cloud.google.com/run/docs/securing/service-identity)).
- **"The project Owner can impersonate any service account."** Owners also need `iam.serviceAccounts.getAccessToken` from Token Creator ([Authenticate with REST](https://docs.cloud.google.com/docs/authentication/rest)).
- **An access token to call a private Cloud Run service.** Cloud Run needs an ID token ([Authentication and authorization use cases](https://docs.cloud.google.com/docs/authentication/use-cases)).
- **An ID token to call a Google API.** ID tokens cannot call Google APIs or get access tokens ([Token types](https://docs.cloud.google.com/docs/authentication/token-types)).
- **`gcloud auth print-identity-token` in production.** It is for development, and the token has no audience ([Authenticate developers](https://docs.cloud.google.com/run/docs/authenticating/developers)).
- **A broader IAM role for a VM that cannot write to Cloud Storage.** Check the access scope first. A read-only scope blocks writes ([Service accounts (Compute Engine)](https://docs.cloud.google.com/compute/docs/access/service-accounts)).
- **The Cloud SQL Auth Proxy to reach a private IP from another network.** The proxy does not create a network path ([About the Cloud SQL Auth Proxy](https://docs.cloud.google.com/sql/docs/postgres/sql-proxy)).
- **Only Cloud SQL Client for IAM database login.** Login also needs Cloud SQL Instance User, and the user needs database privileges ([Log in using IAM database authentication](https://docs.cloud.google.com/sql/docs/postgres/iam-logins)).
- **Manual IAM database authentication in a connection pool.** Tokens expire after one hour ([IAM authentication](https://docs.cloud.google.com/sql/docs/postgres/iam-authentication)).
- **A GitHub provider without an attribute condition.** Tokens from other organizations share the issuer ([Configure Workload Identity Federation with deployment pipelines](https://docs.cloud.google.com/iam/docs/workload-identity-federation-with-deployment-pipelines)).
- **An untrusted cluster in the same project.** Identity sameness gives it the access of matching namespaces ([About Workload Identity Federation for GKE](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/workload-identity)).
