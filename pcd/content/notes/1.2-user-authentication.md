## Why it matters

An app must know who its user is, and sometimes it must act on the user's data in a Google API. For sign-in to your own app, Google Cloud gives you Identity Platform and Firebase Authentication. For Google Accounts and user consent, it gives you OAuth 2.0 and OpenID Connect. For internal apps, it gives you Identity-Aware Proxy (IAP). The exam tests which option fits customers or employees, how a backend validates a JWT, and how the OAuth 2.0 authorization code flow works.

## Key points

- Identity Platform is a customer identity and access management (CIAM) platform. It supports email and password, phone, social providers, SAML, OIDC, and custom sign-in ([Authentication and authorization use cases](https://docs.cloud.google.com/docs/authentication/use-cases)).
- Firebase Authentication uses Identity Platform as its backend. Identity Platform adds multi-factor authentication (MFA), blocking functions, SAML and OIDC providers, multi-tenancy, IAP integration, and an SLA. The upgrade needs no app change ([Differences between Identity Platform and Firebase Authentication](https://docs.cloud.google.com/identity-platform/docs/product-comparison), [Authentication and authorization use cases](https://docs.cloud.google.com/docs/authentication/use-cases)).
- After sign-in, the client sends an ID token to your backend. The backend verifies the token before it trusts the user ID in it ([Identity Platform users in projects](https://docs.cloud.google.com/identity-platform/docs/concepts-manage-users), [Verify ID Tokens](https://firebase.google.com/docs/auth/admin/verify-id-tokens)).
- For end users of a Cloud Run service, use Identity Platform: deploy the service publicly and verify the ID token in your code. For internal users, use IAP ([Authenticating users](https://docs.cloud.google.com/run/docs/authenticating/end-users)).
- To validate a Google-signed ID token, check the signature, the issuer (`iss`), the audience (`aud`), and the expiry (`exp`) ([OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect)).
- OAuth 2.0 lets your app call Google APIs for a user after the user gives consent. Web server apps use the authorization code flow. `access_type=offline` adds a refresh token ([Using OAuth 2.0 for Web Server Applications](https://developers.google.com/identity/protocols/oauth2/web-server)).
- You configure the consent screen in the Google Auth Platform. The audience is Internal (users in your organization) or External (any Google Account) ([Get started with the Google Auth Platform](https://support.google.com/cloud/answer/15544987), [Manage App Audience](https://support.google.com/cloud/answer/15549945)).
- IAP can sign in customers through Identity Platform. Then IAM does not control access: the app filters on the claims in the IAP JWT ([External identities](https://docs.cloud.google.com/iap/docs/external-identities)).
- API Gateway and the Apigee VerifyJWT policy can validate JWTs before a request reaches the backend ([Using Firebase to authenticate users](https://docs.cloud.google.com/api-gateway/docs/authenticating-users-firebase), [VerifyJWT policy](https://docs.cloud.google.com/apigee/docs/api-platform/reference/policies/verify-jwt-policy)).

## Choose a user authentication option

Start with who the users are and what the app must do for them:

| Users and need | Use | Why |
|---|---|---|
| Consumers who sign in on many platforms | Firebase Authentication | Consumer apps. It has a subset of the Identity Platform features |
| Customers or business customers who need SAML or OIDC, MFA, tenants, or an SLA | Identity Platform | Enterprise SaaS apps and enterprise identity providers |
| Users with Google Accounts on mobile or web | Sign In With Google (Google Identity Services) | Built on OAuth 2.0 and OpenID Connect |
| Employees and partners on an internal web app | IAP | IAP authenticates before the request reaches your app. IAM roles control access |
| The app reads or changes the user's data in a Google API, such as Drive | OAuth 2.0 authorization (three-legged OAuth) | The user gives consent to scopes |

Sources: [Authentication and authorization use cases](https://docs.cloud.google.com/docs/authentication/use-cases), [Differences between Identity Platform and Firebase Authentication](https://docs.cloud.google.com/identity-platform/docs/product-comparison), [Authenticating users](https://docs.cloud.google.com/run/docs/authenticating/end-users), [Workforce Identity Federation](https://docs.cloud.google.com/iam/docs/workforce-identity-federation).

End users usually have no IAM permission on your project or Cloud Run service ([Authenticating users](https://docs.cloud.google.com/run/docs/authenticating/end-users)). So for customers, your app checks identity itself, or a gateway checks it for you. IAM is for your own principals: employees, partners, and service accounts.

## Identity Platform and Firebase Authentication

Identity Platform is the backend of Firebase Authentication with Identity Platform, and the SDKs still use Firebase names for backward compatibility ([Differences between Identity Platform and Firebase Authentication](https://docs.cloud.google.com/identity-platform/docs/product-comparison)):

| Feature | Identity Platform | Firebase Authentication |
|---|---|---|
| Email, phone, social, and custom sign-in | Yes | Yes |
| Multi-factor authentication | Yes | No |
| Blocking functions | Yes | No |
| SAML and OIDC providers | Yes | No |
| Multi-tenancy | Yes | No |
| IAP integration | Yes | No |
| Enterprise SLA | 99.95% uptime | No |

Source: [Differences between Identity Platform and Firebase Authentication](https://docs.cloud.google.com/identity-platform/docs/product-comparison).

**Sign-in methods.** Users sign in with email and password, with Google, Facebook, Twitter, or GitHub, with a phone number and an SMS code, or anonymously. With custom authentication, your server exchanges tokens from your existing sign-in system for Identity Platform tokens ([Authentication](https://docs.cloud.google.com/identity-platform/docs/concepts-authentication)).

**Token types.** Know the three kinds ([Identity Platform users in projects](https://docs.cloud.google.com/identity-platform/docs/concepts-manage-users)):

- **Identity Platform ID tokens.** Signed JWTs that identify the user in the project. You send these to your backend.
- **Identity provider tokens.** Tokens from Google, Facebook, and other providers, often OAuth 2.0 access tokens. The client exchanges them for Identity Platform credentials.
- **Custom tokens.** JWTs that your server signs with a service account private key. The Admin SDK verification method is for ID tokens, not custom tokens ([Verify ID Tokens](https://firebase.google.com/docs/auth/admin/verify-id-tokens)).

**Multi-factor authentication.** The web guide adds SMS as the second factor. MFA requires verified email addresses, so that an attacker cannot register an email address that they do not own and lock out the owner. In a tenant, set `tenantId` on the `Auth` instance ([Adding multi-factor authentication to your web app](https://docs.cloud.google.com/identity-platform/docs/web/mfa)).

**Multi-tenancy.** A tenant is a silo of users and configuration inside one project. Each tenant has its own users, identity providers, IAM configuration, and quota. Tenants are most common in business-to-business (B2B) apps. Tenants cannot have their own blocking function ([Identity Platform multi-tenancy](https://docs.cloud.google.com/identity-platform/docs/multi-tenancy)).

**Blocking functions** run your Cloud Run functions code during sign-up and sign-in ([Customize the authentication flow using blocking functions](https://docs.cloud.google.com/identity-platform/docs/blocking-functions)):

- `beforeCreate` runs before Identity Platform saves a new user. `beforeSignIn` runs after the credentials are verified and before the ID token goes to the client.
- The function must respond within seven seconds, or the sign-in fails. Responses other than `200` go to the client app.
- The functions apply to all users in the project, also users in tenants. Anonymous and custom authentication do not support them.
- If you delete the function, also unregister the trigger. If you do not, no user can sign in.

The Firebase Admin SDK is the server-side tool: it manages users, creates custom tokens, verifies ID tokens, and sets custom claims for roles ([Introduction to the Admin Auth API](https://docs.cloud.google.com/identity-platform/docs/concepts-admin-auth-api)).

## Verifying ID tokens in a backend

The pattern for a Cloud Run backend ([Authenticating users](https://docs.cloud.google.com/run/docs/authenticating/end-users), [End user authentication for Cloud Run tutorial](https://docs.cloud.google.com/run/docs/tutorials/identity-platform)):

1. The web or mobile app signs the user in with the client SDK and gets an ID token.
2. The app sends the token in the `Authorization: Bearer ID_TOKEN` header.
3. The Cloud Run service allows unauthenticated invocations, so that any user can reach it. The code verifies the token and uses the user ID from it.

```python
from functools import wraps

import firebase_admin.auth
from flask import Response, request


def jwt_authenticated(func):
    @wraps(func)
    def decorated_function(*args, **kwargs):
        header = request.headers.get("Authorization", None)  # "Bearer ID_TOKEN"
        if not header:
            return Response(status=401)
        token = header.split(" ")[1]
        try:
            # Checks format, signature, and expiry. check_revoked=True also
            # asks the authentication backend if the session was revoked.
            decoded_token = firebase_admin.auth.verify_id_token(token, check_revoked=True)
        except Exception as e:
            return Response(status=403, response=f"Error with authentication: {e}")
        request.uid = decoded_token["uid"]
        return func(*args, **kwargs)

    return decorated_function
```

Sources: [End user authentication for Cloud Run tutorial](https://docs.cloud.google.com/run/docs/tutorials/identity-platform), [Manage User Sessions](https://firebase.google.com/docs/auth/admin/manage-sessions).

JWT validation always checks the same things: a signature from the issuer's public keys, the issuer, the audience, and the time claims. The values differ by token:

| Check | Identity Platform or Firebase ID token | Google ID token (Sign In With Google, OIDC) | IAP JWT |
|---|---|---|---|
| Where it arrives | `Authorization: Bearer` from your client | From the OAuth 2.0 flow, or a `POST` from Google Identity Services | `x-goog-iap-jwt-assertion` header |
| Signature | `RS256`, keys at `https://www.googleapis.com/robot/v1/metadata/x509/securetoken@system.gserviceaccount.com` | Keys at the `jwks_uri` of the Discovery document | `ES256`, keys at `https://www.gstatic.com/iap/verify/public_key` |
| `iss` | `https://securetoken.google.com/PROJECT_ID` | `https://accounts.google.com` or `accounts.google.com` | `https://cloud.google.com/iap` |
| `aud` | Your project ID | Your OAuth client ID | The resource, for Cloud Run `/projects/PROJECT_NUMBER/locations/REGION/services/SERVICE_NAME` |
| Time | `exp` in the future, `iat` and `auth_time` in the past | `exp` not passed | `exp` in the future, `iat` in the past, 30 seconds of skew |
| User ID | `sub`, which is the `uid` | `sub` | `sub` and `email` |

Sources: [Verify ID Tokens](https://firebase.google.com/docs/auth/admin/verify-id-tokens), [OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect), [Verify the Google ID token on your server side](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token), [Securing your app with signed headers](https://docs.cloud.google.com/iap/docs/signed-headers-howto).

Rules that the exam tests:

- **Use a library.** `verify_id_token` in the Firebase Admin SDK checks the format, expiry, and signature. `verify_oauth2_token` in `google.oauth2.id_token` checks the signature, `aud`, and `exp` of a Google ID token. You must check `hd` yourself when you limit access to the members of one Google Workspace or Cloud organization domain ([Verify ID Tokens](https://firebase.google.com/docs/auth/admin/verify-id-tokens), [Verify the Google ID token on your server side](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token)).
- **Revocation needs an extra call.** ID tokens are stateless JWTs that last one hour. `verify_id_token` does not check revocation. `check_revoked=True` asks the backend, at the cost of one network round trip ([Manage User Sessions](https://firebase.google.com/docs/auth/admin/manage-sessions)).
- **Sessions are long.** A refresh token gets new ID tokens. It ends when the user is deleted or disabled, or after a major account change such as a new password. The Admin SDK can revoke refresh tokens, for example after a device is stolen ([Manage User Sessions](https://firebase.google.com/docs/auth/admin/manage-sessions)).
- **Cache the keys, do not call `tokeninfo`.** The `tokeninfo` endpoint is for debugging. In production, validate locally with cached public keys ([OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect)).
- **Identify users by `sub`.** A Google Account can have different email addresses over time ([Verify the Google ID token on your server side](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token)).

## OAuth 2.0 for user authorization

Use OAuth 2.0 user authorization when your app needs a user's data, for example in Google Drive or Google Calendar. For server-to-server calls, use a service account, which needs no OAuth client ID and no user consent. Do not deploy user credentials on servers for long-running jobs. A session control policy can end them, and the server cannot sign the user in again ([Using OAuth 2.0 to Access Google APIs](https://developers.google.com/identity/protocols/oauth2)).

The authorization code flow for a web server app ([Using OAuth 2.0 for Web Server Applications](https://developers.google.com/identity/protocols/oauth2/web-server), [Manage OAuth Clients](https://support.google.com/cloud/answer/15549257)):

1. Create a Web application client on the Google Auth Platform Clients page. Add the authorized redirect URIs. The console shows the client secret only once, so store it in a secure place such as Secret Manager.
2. Redirect the browser to `https://accounts.google.com/o/oauth2/v2/auth` with the parameters in the next table.
3. Google signs the user in and shows the consent screen.
4. Google redirects to your redirect URI with a `code` and your `state` value. Check that `state` matches.
5. Exchange the code at `https://oauth2.googleapis.com/token` for an access token, and also a refresh token if you asked for offline access.
6. Send the access token in the `Authorization` header. Do not put it in the URL query, because URLs can end up in logs ([Using OAuth 2.0 to Access Google APIs](https://developers.google.com/identity/protocols/oauth2)).

| Parameter | What it does |
|---|---|
| `client_id` | Identifies your OAuth client |
| `redirect_uri` | Must exactly match an authorized redirect URI, including scheme, case, and trailing slash. Else: `redirect_uri_mismatch` |
| `response_type=code` | Asks for an authorization code |
| `scope` | The access that the user is asked to grant. Fewer scopes make consent more likely |
| `access_type=offline` | Returns a refresh token the first time that you exchange a code |
| `state` | Your random value that comes back unchanged. It protects against cross-site request forgery (CSRF) |
| `include_granted_scopes=true` | Incremental authorization: the new token also covers scopes granted before |
| `prompt=consent` | Shows the consent screen again |

Source: [Using OAuth 2.0 for Web Server Applications](https://developers.google.com/identity/protocols/oauth2/web-server).

```python
import google_auth_oauthlib.flow

flow = google_auth_oauthlib.flow.Flow.from_client_secrets_file(
    'client_secret.json',
    scopes=['https://www.googleapis.com/auth/drive.metadata.readonly'])
# Must exactly match an authorized redirect URI of the OAuth client.
flow.redirect_uri = 'https://www.example.com/oauth2callback'
authorization_url, state = flow.authorization_url(
    access_type='offline',          # also return a refresh token
    include_granted_scopes='true')  # incremental authorization
# Save state in the session and redirect the browser to authorization_url.
# In the callback, build the flow again with state=state, then call
# flow.fetch_token(authorization_response=flask.request.url).
```

Source: [Using OAuth 2.0 for Web Server Applications](https://developers.google.com/identity/protocols/oauth2/web-server).

Ask for scopes when the user needs the feature, not all at the start. The user can grant fewer scopes than you request, so check the granted scopes ([Using OAuth 2.0 to Access Google APIs](https://developers.google.com/identity/protocols/oauth2)).

**Consent screen settings.** The Google Auth Platform holds the app information that users see on the consent screen, for example the app name and user support email ([Get started with the Google Auth Platform](https://support.google.com/cloud/answer/15544987)). Its Audience page sets who can authorize the app ([Manage App Audience](https://support.google.com/cloud/answer/15549945)):

| Setting | Effect |
|---|---|
| Internal user type | Only users in your Google Cloud organization. Other users get an `org_internal` error |
| External user type | Any user with a Google Account |
| Testing status | Up to 100 test users. Their authorizations and refresh tokens expire after seven days, unless the app asks only for name, email, and profile scopes |
| In production status | Any user. Sensitive or restricted scopes need verification, or users see an unverified app warning |

Source: [Manage App Audience](https://support.google.com/cloud/answer/15549945).

**Refresh tokens.** Store them in secure long-term storage. A refresh token can stop working, for example when the user revokes access or when nobody uses it for six months. When a session control policy ends the session, the call fails with `invalid_grant` and the subtype `invalid_rapt`. There is a limit of 100 refresh tokens per Google Account per OAuth client ID. A new token past the limit invalidates the oldest one without warning ([Using OAuth 2.0 to Access Google APIs](https://developers.google.com/identity/protocols/oauth2)).

## IAP for workforce users compared with Identity Platform for customers

IAP and Identity Platform answer different questions. IAP decides who can reach an app. Identity Platform signs users in to your app ([Identity-Aware Proxy overview](https://docs.cloud.google.com/iap/docs/concepts-overview), [Authentication and authorization use cases](https://docs.cloud.google.com/docs/authentication/use-cases)).

| | IAP with Google Accounts or Workforce Identity Federation | Identity Platform in your app | IAP with Identity Platform (external identities) |
|---|---|---|---|
| Users | Employees and partners | Customers | Users of an external identity system that you cannot move to Google Accounts |
| Where sign-in happens | At IAP, before the app | In your app, with the client SDK | At IAP, with Identity Platform, before the app |
| Access control | The IAP-secured Web App User role (`roles/iap.httpsResourceAccessor`) | Your code, for example with custom claims | Not IAM. The app checks the claims in the IAP JWT |
| Programmatic access | Google identities only, with an ID token for the IAP audience, or a service account JWT | The ID token in the `Authorization` header | Service accounts only, with a service account JWT |

Sources: [Identity-Aware Proxy overview](https://docs.cloud.google.com/iap/docs/concepts-overview), [External identities](https://docs.cloud.google.com/iap/docs/external-identities), [Programmatic authentication](https://docs.cloud.google.com/iap/docs/authentication-howto), [Introduction to the Admin Auth API](https://docs.cloud.google.com/identity-platform/docs/concepts-admin-auth-api), [Configure IAP for Cloud Run](https://docs.cloud.google.com/run/docs/securing/identity-aware-proxy-cloud-run), [Workforce Identity Federation](https://docs.cloud.google.com/iam/docs/workforce-identity-federation).

Facts that decide scenario questions:

- **One tenant per IAP resource.** Identity Platform tokens without a tenant are valid for the whole project. A user could sign in to one IAP resource and use the token on another. A tenant for each resource prevents this ([External identities](https://docs.cloud.google.com/iap/docs/external-identities)).
- **CORS preflight.** For preflighted CORS requests to an authenticated Cloud Run service, Google recommends IAP over IAM authentication. IAP can allow the unauthenticated `OPTIONS` request ([Authenticating users](https://docs.cloud.google.com/run/docs/authenticating/end-users)).
- **Default OAuth client.** With the Google-managed OAuth client, users have no programmatic access, but service accounts can use self-signed JWTs ([Programmatic authentication](https://docs.cloud.google.com/iap/docs/authentication-howto)).
- **Scope of protection.** IAP does not protect against activity inside the project, such as calls from another service in the same project ([Authentication and authorization use cases](https://docs.cloud.google.com/docs/authentication/use-cases)).

For IAP setup on Cloud Run and JWT verification code, see [Protecting apps and finding vulnerabilities](note:1.2-protect-and-scan).

## JWT validation at API Gateway and Apigee

A gateway can validate the JWT so that your backend code does not. API Gateway (the exam guide says Cloud API Gateway) validates the token with the JSON Web Key Set (JWKS) of the issuer. It caches the JWKS for five minutes. The JWT must contain `iss`, `sub`, `aud`, `iat`, and `exp` ([Using Firebase to authenticate users](https://docs.cloud.google.com/api-gateway/docs/authenticating-users-firebase)).

```yaml
# OpenAPI 2.0 API config for Firebase or Identity Platform ID tokens
securityDefinitions:
  firebase:
    authorizationUrl: ""
    flow: "implicit"
    type: "oauth2"
    x-google-issuer: "https://securetoken.google.com/PROJECT_ID"
    x-google-jwks_uri: "https://www.googleapis.com/service_accounts/v1/metadata/x509/securetoken@system.gserviceaccount.com"
    x-google-audiences: "PROJECT_ID"
security:
  - firebase: []
```

Source: [Using Firebase to authenticate users](https://docs.cloud.google.com/api-gateway/docs/authenticating-users-firebase).

API Gateway sends the JWT payload to the backend in the `X-Apigateway-Api-Userinfo` header, base64url-encoded. Google recommends this header. When the config uses `x-google-backend`, API Gateway replaces the original `Authorization` header ([Using Firebase to authenticate users](https://docs.cloud.google.com/api-gateway/docs/authenticating-users-firebase)).

In Apigee, the VerifyJWT policy verifies the signature with a key or a JWKS URI, then checks the expiry and not-before times. It can also check the subject, issuer, audience, and other claims. It puts the claims into flow variables for later policies. If verification fails, processing stops and the client gets an error ([VerifyJWT policy](https://docs.cloud.google.com/apigee/docs/api-platform/reference/policies/verify-jwt-policy)).

To choose between the gateways, see [API management](note:1.1-api-management). For how to expose Cloud Run APIs, see [API versioning and exposure](note:3.1-api-versioning-and-exposure).

## Exam traps

- **IAM roles for public customers.** End users usually have no IAM permissions on your project. Use Identity Platform and verify the ID token in code ([Authenticating users](https://docs.cloud.google.com/run/docs/authenticating/end-users)).
- **Identity Platform on a Cloud Run service that requires authentication.** The docs deploy the service with unauthenticated access and verify the token in code ([End user authentication for Cloud Run tutorial](https://docs.cloud.google.com/run/docs/tutorials/identity-platform)).
- **Firebase Authentication for SAML sign-in, MFA, or tenants.** These features need Identity Platform ([Differences between Identity Platform and Firebase Authentication](https://docs.cloud.google.com/identity-platform/docs/product-comparison)).
- **Trusting the claims of a decoded JWT.** Validate the signature, `iss`, `aud`, and `exp` before you use any claim ([OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect)).
- **The email address as the user key.** Use `sub` ([Verify the Google ID token on your server side](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token)).
- **Only `verify_id_token` after you revoke a user's sessions.** It does not check revocation. Use `check_revoked=True` ([Manage User Sessions](https://firebase.google.com/docs/auth/admin/manage-sessions)).
- **No refresh token.** Set `access_type=offline` ([Using OAuth 2.0 for Web Server Applications](https://developers.google.com/identity/protocols/oauth2/web-server)).
- **Refresh tokens that stop after seven days.** The app is External and in Testing status ([Manage App Audience](https://support.google.com/cloud/answer/15549945)).
- **`org_internal` error.** The app is Internal, and the user is outside the organization ([Manage App Audience](https://support.google.com/cloud/answer/15549945)).
- **User credentials for a server-to-server job.** Use a service account. A job that reads the data of each user, such as Drive files, uses the refresh token of that user (`access_type=offline`) ([Using OAuth 2.0 to Access Google APIs](https://developers.google.com/identity/protocols/oauth2), [Using OAuth 2.0 for Web Server Applications](https://developers.google.com/identity/protocols/oauth2/web-server)).
- **Programmatic access to IAP for Identity Platform users.** IAP supports only Google identities for this ([Programmatic authentication](https://docs.cloud.google.com/iap/docs/authentication-howto)).
- **A deleted blocking function that is still registered.** No user can sign in ([Customize the authentication flow using blocking functions](https://docs.cloud.google.com/identity-platform/docs/blocking-functions)).
