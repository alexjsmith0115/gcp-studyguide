## Why it matters

A developer chooses where to write and run code: a local IDE, Cloud Shell, or Cloud Workstations. The developer also chooses how each tool gets credentials. The exam tests gcloud configurations, `gcloud auth login` versus `gcloud auth application-default login`, and service account impersonation. It also tests the limits of Cloud Shell, the parts of Cloud Workstations, and the purpose of Cloud Code and Gemini Cloud Assist.

## Key points

- A gcloud configuration is a named set of gcloud CLI properties, for example the project and the account. Only one configuration is active at a time, and `--configuration` selects another one for a single command ([Managing gcloud CLI configurations](https://docs.cloud.google.com/sdk/docs/configurations)).
- `gcloud auth login` gives credentials to the gcloud CLI only. Code that uses the Cloud Client Libraries gets credentials from Application Default Credentials (ADC) ([Authenticate for the gcloud CLI](https://docs.cloud.google.com/sdk/docs/authenticate)).
- `gcloud auth application-default login` puts your user credentials in a local ADC file. The ADC file belongs to your user account, not to a gcloud configuration ([Set up ADC for a local development environment](https://docs.cloud.google.com/docs/authentication/set-up-adc-local-dev-environment)).
- To act as a service account without a key, use impersonation. You need the Service Account Token Creator role (`roles/iam.serviceAccountTokenCreator`) on the service account ([Authenticate for the gcloud CLI](https://docs.cloud.google.com/sdk/docs/authenticate)).
- In scripts, use `--format` and `--filter` for predictable output and `--quiet` to turn off prompts. The gcloud CLI does not support parallel commands ([Scripting gcloud CLI commands](https://docs.cloud.google.com/sdk/docs/scripting-gcloud)).
- Cloud Shell runs on a VM that Google owns. Your files persist between sessions only in the 5 GB `$HOME` directory ([How Cloud Shell works](https://docs.cloud.google.com/shell/docs/how-cloud-shell-works)).
- Cloud Shell is for interactive use. It has a weekly quota of 50 hours, and it ends non-interactive sessions after 40 minutes ([Quotas and limits](https://docs.cloud.google.com/shell/docs/quotas-limits)).
- Cloud Code is an extension for VS Code and JetBrains IDEs, and it is built into the Cloud Shell Editor. It supports GKE and Cloud Run development, Secret Manager, and the Cloud APIs ([Cloud Code overview](https://docs.cloud.google.com/code/docs/vscode/overview)).
- Cloud Workstations runs each workstation on a Compute Engine VM in your project. A workstation configuration is the template, and a workstation cluster sets the region and VPC network ([Cloud Workstations overview](https://docs.cloud.google.com/workstations/docs/overview)).
- Gemini Cloud Assist (Preview) is an AI assistant in the Google Cloud console. Do not enable it for projects with data residency or customer-managed encryption key (CMEK) requirements ([Gemini Cloud Assist overview](https://docs.cloud.google.com/cloud-assist/overview), [Set up Gemini Cloud Assist](https://docs.cloud.google.com/cloud-assist/set-up-gemini)).
- The console shows the gcloud command and the REST request for an action under **Equivalent code** ([Google Cloud console](https://docs.cloud.google.com/compute/docs/console)).

## The gcloud CLI and the other Cloud SDK tools

The Google Cloud SDK includes command-line tools, client libraries, and IDE extensions ([Google Cloud SDK documentation](https://docs.cloud.google.com/sdk/docs)). The Google Cloud CLI installs the command-line tools as components, and components add command groups.

| Tool or component | What it does | Installed by default |
|---|---|---|
| `gcloud` | The main CLI. The default component has only GA commands | Yes |
| `bq` | BigQuery command-line tool | Yes |
| `gsutil` | Legacy Cloud Storage tool. Use `gcloud storage` commands instead | Yes |
| `alpha`, `beta`, `preview` | Commands at those release levels | No |
| `kubectl` | Kubernetes command-line tool | No |
| `cbt` | Bigtable command-line tool | No |
| Emulators (`pubsub-emulator`, `cloud-spanner-emulator`, and others) | Local copies of services | No |

Source: [Managing gcloud CLI components](https://docs.cloud.google.com/sdk/docs/components).

Install a component with `gcloud components install COMPONENT_ID`. If you installed the gcloud CLI with a package manager such as `apt` or `yum`, the component manager is off. Install components with the package manager instead ([Managing gcloud CLI components](https://docs.cloud.google.com/sdk/docs/components)). [Emulating Google Cloud services](note:2.1-emulators) covers the emulators.

### Configurations

Use one configuration for each project or account, and switch between them. The gcloud CLI starts with a configuration named `default`.

```bash
gcloud config configurations create dev
gcloud config configurations activate dev
gcloud config set project PROJECT_ID
gcloud config configurations list
gcloud auth list --configuration=prod
```

Source: [Managing gcloud CLI configurations](https://docs.cloud.google.com/sdk/docs/configurations).

The environment variable `CLOUDSDK_ACTIVE_CONFIG_NAME` selects the configuration for all commands in a terminal. You can also set one property with a variable named `CLOUDSDK_SECTION_NAME_PROPERTY_NAME`, for example `CLOUDSDK_CORE_PROJECT`. In Cloud Shell, gcloud preferences are kept only for the current tab and do not persist across sessions ([Managing gcloud CLI configurations](https://docs.cloud.google.com/sdk/docs/configurations)).

## Two sets of credentials: the gcloud CLI and ADC

The gcloud CLI and your application code use different credentials. A common exam scenario asks why code fails after `gcloud auth login` succeeded.

| Command | Who uses the credential | Use it when |
|---|---|---|
| `gcloud auth login` | The gcloud CLI | You run gcloud commands as yourself |
| `gcloud auth application-default login` | Client libraries, through ADC | You run your code locally as yourself |
| `gcloud auth application-default login --impersonate-service-account SA_EMAIL` | Client libraries, as the service account | You test your code with the permissions of a service account |
| `--impersonate-service-account=SA_EMAIL` on a gcloud command | The gcloud CLI, as the service account | You run one gcloud command as a service account |
| None (metadata server) | The gcloud CLI and ADC on Compute Engine, Cloud Run, and Cloud Build | The code runs on Google Cloud with an attached service account |

Sources: [Authenticate for the gcloud CLI](https://docs.cloud.google.com/sdk/docs/authenticate), [Set up ADC for a local development environment](https://docs.cloud.google.com/docs/authentication/set-up-adc-local-dev-environment).

Both login commands store credentials on disk. Anyone with access to your file system can use them. Do not use `gcloud auth login` for automated workloads on remote systems with persistent storage. Revoke a local ADC file that you no longer need with `gcloud auth application-default revoke` ([Authenticate for the gcloud CLI](https://docs.cloud.google.com/sdk/docs/authenticate), [Set up ADC for a local development environment](https://docs.cloud.google.com/docs/authentication/set-up-adc-local-dev-environment)).

In Cloud Shell, you do not run either login command. Cloud Shell asks you to authorize the first time a tool needs credentials ([Authenticate for the gcloud CLI](https://docs.cloud.google.com/sdk/docs/authenticate), [How Cloud Shell works](https://docs.cloud.google.com/shell/docs/how-cloud-shell-works)).

To impersonate a service account for all gcloud commands, set a property in the active configuration. Impersonation needs the Service Account Credentials API in the project:

```bash
gcloud config set auth/impersonate_service_account SERVICE_ACCOUNT_EMAIL
gcloud config unset auth/impersonate_service_account
```

Source: [Authenticate for the gcloud CLI](https://docs.cloud.google.com/sdk/docs/authenticate).

For a person who needs more access for a short time, Google recommends Privileged Access Manager instead of impersonation ([Authenticate for the gcloud CLI](https://docs.cloud.google.com/sdk/docs/authenticate)). [Authenticating code to Google Cloud](note:1.2-authenticating-to-google-cloud) explains the ADC search order and Workload Identity Federation.

### Scripting

A script must not depend on interactive prompts or on the table layout of the output. Use these flags:

```bash
gcloud projects list --format="json" \
  --filter="labels.env=test AND labels.version=alpha"
gcloud info --format='value(config.account)'
gcloud config set disable_prompts true
```

Source: [Scripting gcloud CLI commands](https://docs.cloud.google.com/sdk/docs/scripting-gcloud).

`--format` accepts formats such as `json`, `yaml`, `csv`, `table`, and `value`. `--quiet` (or `-q`) turns off prompts for one command and uses the default answers ([Scripting gcloud CLI commands](https://docs.cloud.google.com/sdk/docs/scripting-gcloud)).

## Cloud Shell

Cloud Shell gives you a terminal and an editor in the browser, with the gcloud CLI and other tools installed. Its limits decide when it is the correct choice.

| Fact | Detail |
|---|---|
| Where it runs | A Compute Engine VM that Google owns. The VM is not in any of your projects |
| Lifetime | One VM for each user and session. After a period of inactivity, the session ends and the VM is discarded |
| Persistent storage | 5 GB in `$HOME`, for each user, across projects. You cannot make it larger |
| Storage deletion | Cloud Shell deletes `$HOME` if you do not use Cloud Shell for 120 days |
| Software outside `$HOME` | Lost when the VM ends |
| Usage limits | 50 hours each week. Non-interactive sessions end after 40 minutes. All sessions end after 12 hours |
| Project | `GOOGLE_CLOUD_PROJECT` is set to the active project in the console |
| Ephemeral mode | Starts faster, but nothing persists when the session ends |
| Editor | The Cloud Shell Editor is based on Code OSS and includes Cloud Code. You cannot install custom extensions |

Sources: [How Cloud Shell works](https://docs.cloud.google.com/shell/docs/how-cloud-shell-works), [Quotas and limits](https://docs.cloud.google.com/shell/docs/quotas-limits), [Cloud Shell Editor interface overview](https://docs.cloud.google.com/shell/docs/editor-overview).

Open a file in the editor with `cloudshell edit FILE`, or go to `ide.cloud.google.com`. When you need more storage, more control of the environment, or no weekly limit, the Cloud Shell docs point you to Cloud Workstations ([Cloud Shell Editor interface overview](https://docs.cloud.google.com/shell/docs/editor-overview), [How Cloud Shell works](https://docs.cloud.google.com/shell/docs/how-cloud-shell-works), [Quotas and limits](https://docs.cloud.google.com/shell/docs/quotas-limits)).

## Cloud Code

Cloud Code is an IDE extension for applications that run on GKE and Cloud Run. You can install it in VS Code and in IntelliJ and other JetBrains IDEs. It is available by default in the Cloud Shell Editor.

| Feature | What it does |
|---|---|
| Kubernetes development | Builds, deploys, and debugs Kubernetes applications. A `skaffold.yaml` file describes the build and the deployment |
| Cloud Run development | Deploys services, and runs and debugs a service locally in the Cloud Run emulator |
| Container images | Builds images from source with Google Cloud's buildpacks, without a Dockerfile |
| Secret Manager | Creates, views, and updates secrets from the IDE |
| Cloud APIs | Browses APIs, enables services, and installs client libraries |
| Compute Engine | Browses VMs, opens a terminal to a VM, and copies files |
| Apigee | Tests API proxies in the Apigee Emulator |

Sources: [Cloud Code overview](https://docs.cloud.google.com/code/docs/vscode/overview), [Get started with Cloud Code for VS Code for Kubernetes](https://docs.cloud.google.com/code/docs/vscode/get-started-k8s).

Cloud Code can install kubectl, Skaffold, and minikube for you. The setting `cloudcode.autoDependencies` controls this. Docker is optional if you build only with Cloud Build or Jib. When you sign in to the gcloud CLI from Cloud Code, Cloud Code also updates your ADC ([Install the Cloud Code for VS Code extension](https://docs.cloud.google.com/code/docs/vscode/install)).

Gemini Code Assist is now a separate plugin from Cloud Code. The Gemini Code Assist extension installs with Cloud Code by default, but the Standard and Enterprise editions are not enabled automatically ([Cloud Code overview](https://docs.cloud.google.com/code/docs/vscode/overview), [Install the Cloud Code for VS Code extension](https://docs.cloud.google.com/code/docs/vscode/install)). [AI coding assistants, context, and MCP servers](note:2.1-ai-assisted-development) covers Gemini Code Assist.

## Cloud Workstations

Cloud Workstations gives each developer a managed development environment that runs in your project and your VPC network. Administrators define the environment once, and developers create workstations from it.

| Resource | What it is |
|---|---|
| Workstation cluster | A group of workstations in one region and one VPC network. Google manages its controller and gateway. It is not a GKE cluster |
| Workstation configuration | The template: machine type, persistent storage, container image, IDE, timeouts, and the service account |
| Workstation | One developer environment. It runs on a Compute Engine VM in your project, with a persistent disk for `/home` |

Sources: [Cloud Workstations overview](https://docs.cloud.google.com/workstations/docs/overview), [Cloud Workstations architecture](https://docs.cloud.google.com/workstations/docs/architecture).

Developers connect from a browser IDE, from a local VS Code or JetBrains IDE, or with SSH. When a session ends, Cloud Workstations deletes the VM and keeps the persistent disk. A configuration change applies to each workstation the next time that workstation starts ([Cloud Workstations overview](https://docs.cloud.google.com/workstations/docs/overview), [Cloud Workstations architecture](https://docs.cloud.google.com/workstations/docs/architecture)).

| Setting | What to know |
|---|---|
| Idle timeout | Shuts down an idle workstation. Network requests and IDE activity reset it. The console default for auto-sleep is after 2 hours of inactivity |
| Running timeout | Stops a workstation after a set time, so that workstations pick up configuration changes |
| Quick start pool | Keeps VMs ready with the image already pulled. Enable it for faster startup, or disable it for lower cost. The default pool size is 1 |
| Custom container image | Extend a base image, such as `.../predefined/code-oss:latest`. Rebuild it when the base image changes, and scan it with Artifact Analysis |
| Startup scripts | Files in `/etc/workstation-startup.d/` run at each start. Changes to `/home` in the Dockerfile are lost, because the persistent disk mounts over `/home` |
| No public IP addresses | You must set up Private Google Access or Cloud NAT on your network |
| Private cluster | The gateway is reachable only from inside your network. VPC Service Controls requires a private cluster and no public IP addresses |

Sources: [Cloud Workstations architecture](https://docs.cloud.google.com/workstations/docs/architecture), [Cloud Workstations overview](https://docs.cloud.google.com/workstations/docs/overview), [Create a workstation configuration](https://docs.cloud.google.com/workstations/docs/create-configuration), [Customize container images](https://docs.cloud.google.com/workstations/docs/customize-container-images), [Configure VPC Service Controls and private clusters](https://docs.cloud.google.com/workstations/docs/configure-vpc-service-controls-private-clusters).

A long background job does not reset the idle timeout. Run `/google/scripts/keep_alive.sh` from the base image to keep the workstation running ([Cloud Workstations architecture](https://docs.cloud.google.com/workstations/docs/architecture)).

## Choose a development environment

| Use | When |
|---|---|
| Local IDE with Cloud Code and the gcloud CLI | You want your own machine and tools, and local emulators |
| Cloud Shell | You need a quick terminal with tools and credentials ready, for interactive work only |
| Cloud Workstations | You need a standard, secured environment in your VPC network, with more storage and no weekly limit |

Sources: [Cloud Code overview](https://docs.cloud.google.com/code/docs/vscode/overview), [Quotas and limits](https://docs.cloud.google.com/shell/docs/quotas-limits), [Cloud Workstations overview](https://docs.cloud.google.com/workstations/docs/overview).

## Gemini Cloud Assist (Preview)

Gemini Cloud Assist is an AI assistant that works in the Google Cloud console. You open its panel from the console toolbar and write prompts in natural language. There is no cost for the panel while it is in Preview ([Use Gemini Cloud Assist in the Google Cloud console](https://docs.cloud.google.com/cloud-assist/chat-panel)).

| Area | What it does |
|---|---|
| Design and build | Generates gcloud commands, `kubectl` manifests, and Terraform code. Helps you select IAM roles |
| Support and troubleshooting | Investigations of logs, metrics, and configuration. Questions about Artifact Analysis vulnerabilities. Natural language in Google Cloud Observability |
| Optimize | Cost and resource usage recommendations |

Source: [Gemini Cloud Assist overview](https://docs.cloud.google.com/cloud-assist/overview).

To set it up, enable `geminicloudassist.googleapis.com` and grant `roles/geminicloudassist.user` and `roles/cloudasset.viewer`. Gemini Cloud Assist can store data in any Google Cloud data center ([Set up Gemini Cloud Assist](https://docs.cloud.google.com/cloud-assist/set-up-gemini)). Validate all output before you use it. For resource questions, the panel gives an equivalent query that you can run to check the result ([Gemini Cloud Assist overview](https://docs.cloud.google.com/cloud-assist/overview), [Use Gemini Cloud Assist in the Google Cloud console](https://docs.cloud.google.com/cloud-assist/chat-panel)).

Since April 10, 2026, only users with a Premium Support contract, or with access through their account team, can create and run investigations ([Troubleshoot issues with Gemini Cloud Assist investigations](https://docs.cloud.google.com/cloud-assist/investigations)). [Finding and fixing issues](note:4.3-troubleshooting) teaches AI-assisted troubleshooting.

## Google Cloud console features for developers

The console is useful when you learn a task or check a resource. When you create a resource in the console, **Equivalent code** shows the gcloud command and the REST request for the same action. Copy them into scripts ([Google Cloud console](https://docs.cloud.google.com/compute/docs/console)). You can also open Cloud Shell from the console, and Cloud Shell sets `GOOGLE_CLOUD_PROJECT` to the console project ([How Cloud Shell works](https://docs.cloud.google.com/shell/docs/how-cloud-shell-works)).

## Exam traps

- **"I ran `gcloud auth login`, so my code can call the API."** Client libraries use ADC. Run `gcloud auth application-default login` ([Authenticate for the gcloud CLI](https://docs.cloud.google.com/sdk/docs/authenticate)).
- **"I switched the gcloud configuration, so my code uses the other account."** The local ADC file does not change with the configuration ([Set up ADC for a local development environment](https://docs.cloud.google.com/docs/authentication/set-up-adc-local-dev-environment)).
- **A downloaded service account key for local tests.** Use your user account, or impersonate the service account with ADC ([Set up ADC for a local development environment](https://docs.cloud.google.com/docs/authentication/set-up-adc-local-dev-environment)).
- **Impersonation without Token Creator.** The caller needs `iam.serviceAccounts.getAccessToken`, which `roles/iam.serviceAccountTokenCreator` contains ([Authenticate for the gcloud CLI](https://docs.cloud.google.com/sdk/docs/authenticate)).
- **Software installed outside `$HOME` in Cloud Shell.** It is lost when the VM ends ([How Cloud Shell works](https://docs.cloud.google.com/shell/docs/how-cloud-shell-works)).
- **Cloud Shell for a long batch job.** Non-interactive sessions end after 40 minutes ([Quotas and limits](https://docs.cloud.google.com/shell/docs/quotas-limits)).
- **"The workstation picks up the new configuration now."** A configuration change applies at the next start of each workstation ([Cloud Workstations overview](https://docs.cloud.google.com/workstations/docs/overview)).
- **Tools added to `/home` in the custom image Dockerfile.** The persistent home disk mounts over `/home` and hides them. Use a startup script ([Customize container images](https://docs.cloud.google.com/workstations/docs/customize-container-images)).
- **`gsutil` in a new script.** It is a legacy tool. Use `gcloud storage` ([Managing gcloud CLI components](https://docs.cloud.google.com/sdk/docs/components)).
