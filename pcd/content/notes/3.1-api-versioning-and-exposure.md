## Why it matters

An API on Cloud Run changes over time, and clients must keep working while it changes. A developer decides what is a compatible change, where the version number goes, and how clients test a new version before it gets traffic. The developer also decides how clients reach the service (`run.app` URL, load balancer, API Gateway, or Apigee) and how each caller proves its identity. The exam tests the Google-recommended choice for each of these decisions.

## Key points

- A Google API puts its major version first in the URI path, for example `/v1/...`. Google APIs do not expose minor or patch versions ([AIP-185](https://google.aip.dev/185)).
- A compatible change stays in the same major version. Adding a required field, or removing or renaming a field, is a breaking change ([AIP-180](https://google.aip.dev/180)).
- A stable component must not get breaking changes. For a breaking change, create a new major version and deprecate the old one ([AIP-181](https://google.aip.dev/181)).
- In Apigee, a proxy revision is an internal configuration number. It is not the API version, and apps never see it ([Understanding APIs and API proxies](https://docs.cloud.google.com/apigee/docs/api-platform/fundamentals/understanding-apis-and-api-proxies)).
- An Apigee base path routes requests to a proxy. It must be unique within an environment ([API proxy configuration reference](https://docs.cloud.google.com/apigee/docs/api-platform/reference/api-proxy-configuration-reference)).
- Cloud Run ingress settings (`all`, `internal`, `internal-and-cloud-load-balancing`) control which network paths reach the service. IAM still applies on every path ([Restrict network endpoint ingress for Cloud Run](https://docs.cloud.google.com/run/docs/securing/ingress)).
- Google recommends a global external Application Load Balancer for a custom domain. Cloud Run domain mapping is in Preview and is not recommended for production ([Mapping custom domains](https://docs.cloud.google.com/run/docs/mapping-custom-domains)).
- Cloud Run services are private by default. Only principals with the Cloud Run Invoker role (or Owner, Editor, or Cloud Run Admin) can call them ([Authentication overview](https://docs.cloud.google.com/run/docs/authenticating/overview)).
- Use Identity-Aware Proxy (IAP) for internal users and Identity Platform for end users ([Authenticating users](https://docs.cloud.google.com/run/docs/authenticating/end-users)).
- A standard API key associates a request with a project. It does not identify a principal, so no IAM check is possible ([Manage API keys](https://docs.cloud.google.com/docs/authentication/api-keys)).
- A revision tag gives a new revision its own URL. Deploy with `--no-traffic --tag`, test the tag URL, then move traffic ([Rollbacks, gradual rollouts, and traffic migration](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration)).

## Version the API

Google's rules for versions are in AIP-185 and AIP-180. Every API has a major version number. For REST, the major version is the first part of the URI path. Clients get compatible changes in place, without a migration ([AIP-185](https://google.aip.dev/185)).

| Change | Compatible in the same major version? |
|---|---|
| Add a method, a message, or an optional field | Yes. Old clients must get the same behavior as before |
| Add a value to an enum that is used only in requests | Yes |
| Add a required field to a request or a resource | No |
| Remove or rename a field, method, or enum value (a rename is a remove and an add) | No |
| Change the type of a field, even to a wire-compatible type | No |
| Change a default value, or how a default value is serialized | No |
| Change a resource name or the set of valid names | No. A resource name must not change, even across major versions |
| Add pagination to a List method that returned all items | No, if the default page size is smaller than what clients got before |

Source: [AIP-180](https://google.aip.dev/180).

Run old and new major versions at the same time for a transition period. Deprecate the old version with a clear notice before you shut it down. A new major version must not depend on the previous one ([AIP-185](https://google.aip.dev/185)).

| Stability level | Version name | Rule |
|---|---|---|
| Alpha | `v1alpha` | Breaking changes are allowed and expected |
| Beta | `v1beta` | A superset of stable. Breaking changes only after a deprecation period. A good time to promote to stable is 90 days |
| Stable | `v1` | No breaking changes. A breaking change needs `v2` |

Sources: [AIP-185](https://google.aip.dev/185), [AIP-181](https://google.aip.dev/181).

AIP-185 recommends channel-based versioning, as in the table. The older release-based pattern uses names such as `v1beta1` and `v1beta2`. For beta functionality, Google recommends 180 days between deprecation and removal ([AIP-185](https://google.aip.dev/185)).

Some Google APIs use interface-based versioning. The client sends a date version, such as `2025-09-04`, in the `X-Goog-Api-Version` header or the `$apiVersion` query parameter ([AIP-185](https://google.aip.dev/185)).

## Versions and revisions in Apigee

Keep two numbers apart. The API version (`v1`, `v2`) is the public contract. The proxy revision is an internal, sequential number for one configuration of the proxy ([Understanding APIs and API proxies](https://docs.cloud.google.com/apigee/docs/api-platform/fundamentals/understanding-apis-and-api-proxies)).

| Apigee concept | What it does for versions |
|---|---|
| Proxy revision | You save each change as a new revision. To undo a change, deploy an earlier revision |
| Environment | A proxy must be deployed to an environment (for example `test` or `prod`) before clients can call it. You promote a tested revision from `test` to `prod` |
| Environment group | Holds the hostnames. An environment must be in at least one group before it gets traffic |
| Base path | The first part of the request path. It routes the request to a proxy and must be unique within an environment |
| Conditional RouteRule | Sends requests from one proxy to different backends, for example to support backend versions |
| API product | Bundles proxies and resource paths. Apps get keys for API products, so the product controls which apps can call which proxy |

Sources: [Understanding APIs and API proxies](https://docs.cloud.google.com/apigee/docs/api-platform/fundamentals/understanding-apis-and-api-proxies), [About environments and environment groups](https://docs.cloud.google.com/apigee/docs/api-platform/fundamentals/environments-overview), [API proxy configuration reference](https://docs.cloud.google.com/apigee/docs/api-platform/reference/api-proxy-configuration-reference), [Introduction to API products](https://docs.cloud.google.com/apigee/docs/api-platform/publish/what-api-product).

The base path and AIP-185 work together. AIP-185 puts the major version first in the path, and Apigee routes each base path to one proxy. So a base path that starts with `/v1` and a base path that starts with `/v2` send the two major versions to two proxies, which can run side by side ([AIP-185](https://google.aip.dev/185), [API proxy configuration reference](https://docs.cloud.google.com/apigee/docs/api-platform/reference/api-proxy-configuration-reference)). A conditional RouteRule in one proxy can instead choose the backend at runtime:

```xml
<ProxyEndpoint name="default">
  <HTTPProxyConnection>
    <BasePath>/weather</BasePath>
  </HTTPProxyConnection>
  <RouteRule name="MyRoute">
    <Condition>request.header.routeTo = "TargetEndpoint1"</Condition>
    <TargetEndpoint>TargetEndpoint1</TargetEndpoint>
  </RouteRule>
  <RouteRule name="default">
    <URL>http://api.mycompany.com/v2</URL>
  </RouteRule>
</ProxyEndpoint>
```

Source: [API proxy configuration reference](https://docs.cloud.google.com/apigee/docs/api-platform/reference/api-proxy-configuration-reference).

Know these deployment rules:

- You cannot change a deployed revision. Save the change as a new revision and deploy that ([Deploying an API proxy](https://docs.cloud.google.com/apigee/docs/api-platform/deploy/ui-deploy-new)).
- A new revision with the same base path, deployed to the same environment, replaces the previous revision. With the Apigee API, set `override=true` to deploy the new revision fully before the old one is undeployed ([Deploying an API proxy](https://docs.cloud.google.com/apigee/docs/api-platform/deploy/ui-deploy-new)).
- Do not deploy one proxy to two environments in the same environment group. The behavior is undefined ([Deploying an API proxy](https://docs.cloud.google.com/apigee/docs/api-platform/deploy/ui-deploy-new)).
- If you save a proxy with the base path of another proxy, Apigee undeploys the proxy that you saved ([Creating an API proxy](https://docs.cloud.google.com/apigee/docs/api-platform/develop/ui-create-proxy)).
- Use TargetServer resources instead of fixed backend URLs, so that the same revision works in each environment ([Best practices for API proxy design and development with Apigee](https://docs.cloud.google.com/apigee/docs/api-platform/fundamentals/best-practices-api-proxy-design-and-development)).

## Expose a Cloud Run API

A Cloud Run service has three network entry paths: the default `run.app` URL, a domain mapping, and Application Load Balancers. The ingress setting applies to all of them ([Restrict network endpoint ingress for Cloud Run](https://docs.cloud.google.com/run/docs/securing/ingress)).

| Ingress setting | Who can reach the service | Use it when |
|---|---|---|
| `all` (default) | Everyone, including direct internet requests to `run.app` | The `run.app` URL is the public entry point |
| `internal-and-cloud-load-balancing` | Internal sources and external Application Load Balancers. Direct internet requests to `run.app` fail | Internet traffic must go through the load balancer for Cloud Armor, Cloud CDN, or IAP on the load balancer |
| `internal` | Internal Application Load Balancers, the same project's VPC networks, Shared VPC, VPC Service Controls perimeters, and listed Google services | Only internal callers use the API |

Source: [Restrict network endpoint ingress for Cloud Run](https://docs.cloud.google.com/run/docs/securing/ingress).

```bash
gcloud run deploy SERVICE --image IMAGE_URL --ingress internal-and-cloud-load-balancing
gcloud run services update SERVICE --no-default-url
```

Source: [Restrict network endpoint ingress for Cloud Run](https://docs.cloud.google.com/run/docs/securing/ingress).

The `internal` setting accepts these Google services when they use the `run.app` URL from the same project or perimeter: Cloud Scheduler, Cloud Tasks, Dialogflow CX, Eventarc, Gemini Enterprise, Pub/Sub, synthetic monitors, Workflows, and BigQuery ([Restrict network endpoint ingress for Cloud Run](https://docs.cloud.google.com/run/docs/securing/ingress)). API Gateway and Apigee are not on that list. Protect their backends with IAM, as the next sections show.

`--no-default-url` turns off the `run.app` URL. Then only load balancers and domain mappings reach the service. Services that call the `run.app` URL, such as Cloud Scheduler, Cloud Tasks, Eventarc, Pub/Sub, and Workflows, stop working ([Restrict network endpoint ingress for Cloud Run](https://docs.cloud.google.com/run/docs/securing/ingress)).

### Choose the front door

| Front door | Use it when | Key configuration |
|---|---|---|
| `run.app` URL | A simple API with no custom domain | Ingress `all`. IAM or a public setting controls access |
| Global external Application Load Balancer | A custom domain, your own TLS certificate, path routing, Cloud CDN, or Cloud Armor | Recommended for custom domains. Ingress `internal-and-cloud-load-balancing` |
| API Gateway | API keys, JWT checks, and per-minute quotas (Beta) in front of serverless backends | Keep the service private. Give the gateway's service account the Cloud Run Invoker role |
| Apigee | Partner APIs, API products, analytics, or many policies | The TargetEndpoint calls Cloud Run with a `<GoogleIDToken>` |
| Cloud Run domain mapping | Tests only | Preview. Not production-ready because of latency issues |

Sources: [Mapping custom domains](https://docs.cloud.google.com/run/docs/mapping-custom-domains), [Restrict network endpoint ingress for Cloud Run](https://docs.cloud.google.com/run/docs/securing/ingress), [Securing backend services](https://docs.cloud.google.com/api-gateway/docs/securing-backend-services), [OpenAPI 2.0 extensions in API Gateway](https://docs.cloud.google.com/api-gateway/docs/oasv2-extensions), [API proxy configuration reference](https://docs.cloud.google.com/apigee/docs/api-platform/reference/api-proxy-configuration-reference).

[API management with Apigee and API Gateway](note:1.1-api-management) compares API Gateway and Apigee. [Choosing a load balancer and session affinity](note:1.1-load-balancing) explains the load balancer setup.

## Secure the API

Pick the mechanism by the type of caller.

| Caller | Mechanism | Where the check happens |
|---|---|---|
| Another service, API Gateway, or Apigee | ID token for a service account with the Cloud Run Invoker role | Cloud Run IAM |
| Employees and other internal users | IAP | IAP on the Cloud Run service |
| End users who sign up in your app | Identity Platform ID token in `Authorization: Bearer ID_TOKEN` | Your code verifies the token. The service is public |
| Apps of partners and other developers | API key, OAuth 2.0 access token, or JWT | API Gateway, or an Apigee policy (VerifyAPIKey, OAuthV2, VerifyJWT) |

Sources: [Authentication overview](https://docs.cloud.google.com/run/docs/authenticating/overview), [Authenticating users](https://docs.cloud.google.com/run/docs/authenticating/end-users), [Securing backend services](https://docs.cloud.google.com/api-gateway/docs/securing-backend-services), [Using JWT to authenticate users](https://docs.cloud.google.com/api-gateway/docs/authenticating-users-jwt), [OAuthV2 policy](https://docs.cloud.google.com/apigee/docs/api-platform/reference/policies/oauthv2-policy).

### IAP for internal users

Google recommends that you enable IAP on the Cloud Run service itself. Then IAP protects every ingress path, including the `run.app` URL and load balancers ([Configure IAP for Cloud Run](https://docs.cloud.google.com/run/docs/securing/identity-aware-proxy-cloud-run)).

```bash
gcloud run deploy SERVICE_NAME \
  --region=REGION \
  --image=IMAGE_URL \
  --no-allow-unauthenticated \
  --iap
gcloud run services add-iam-policy-binding SERVICE_NAME \
  --region=REGION \
  --member=serviceAccount:service-PROJECT_NUMBER@gcp-sa-iap.iam.gserviceaccount.com \
  --role=roles/run.invoker
```

Source: [Configure IAP for Cloud Run](https://docs.cloud.google.com/run/docs/securing/identity-aware-proxy-cloud-run).

You cannot configure IAP on both the load balancer and the Cloud Run service. IAP replaces the caller's identity, so callers such as Pub/Sub that use their own authentication can fail ([Configure IAP for Cloud Run](https://docs.cloud.google.com/run/docs/securing/identity-aware-proxy-cloud-run)). For CORS preflight requests to an authenticated service, use IAP and allow unauthenticated `OPTIONS` requests ([Authenticating users](https://docs.cloud.google.com/run/docs/authenticating/end-users)).

### End users and public APIs

For end users, a public web or mobile app signs the user in with Identity Platform (or Firebase Authentication). The app sends the user's ID token to the Cloud Run service. Deploy the service publicly and verify the ID token in your code ([Authenticating users](https://docs.cloud.google.com/run/docs/authenticating/end-users)).

To make a service public, Google recommends that you disable the Invoker IAM check with `--no-invoker-iam-check`. This works when an organization policy restricts domain sharing. The other way is to grant the Cloud Run Invoker role to `allUsers` ([Allowing public (unauthenticated) access](https://docs.cloud.google.com/run/docs/authenticating/public)). [Authenticating end users](note:1.2-user-authentication) explains Identity Platform and OAuth 2.0.

### API keys compared to tokens

| | API key | OAuth 2.0 access token or JWT |
|---|---|---|
| Identifies | A project (API Gateway) or a registered app (Apigee) | A user or a service account |
| Lifetime | Valid until you delete it. Rotate keys from time to time to limit the impact of a leaked key | Short-lived. A JWT has an expiry claim |
| IAM check | Not possible with a standard key | Possible when the token is for a Google identity |
| Use for | Quotas, billing, and app identification | Access to user data and sensitive operations |

Sources: [Manage API keys](https://docs.cloud.google.com/docs/authentication/api-keys), [Use API keys](https://docs.cloud.google.com/api-gateway/docs/authenticate-api-keys), [VerifyAPIKey policy](https://docs.cloud.google.com/apigee/docs/api-platform/reference/policies/verify-api-key-policy), [VerifyJWT policy](https://docs.cloud.google.com/apigee/docs/api-platform/reference/policies/verify-jwt-policy).

An API key goes with every request, so it is less secure than a short-lived token. Do not use only API keys when calls carry sensitive data ([Use API keys](https://docs.cloud.google.com/api-gateway/docs/authenticate-api-keys)). [Secure service-to-service communication](note:1.2-service-to-service) explains ID tokens between services.

## Test a new API version with revision tags

A revision tag gives one revision its own URL, so you can test it before it gets any traffic. Google gives this sequence ([Rollbacks, gradual rollouts, and traffic migration](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration)):

1. Run integration tests on the container during development.
2. Deploy to a staging project with no traffic, and test the tagged revision.
3. Deploy to production with no traffic, and test the tagged revision.
4. Move traffic to the tagged revision.

```bash
gcloud run deploy myservice --image IMAGE_URL --no-traffic --tag TAG_NAME
# Test https://TAG_NAME---myservice-abcdef.a.run.app, then move traffic:
gcloud run services update-traffic myservice --to-tags TAG_NAME=TRAFFIC_PERCENT
gcloud run services update-traffic myservice --to-latest
```

Source: [Rollbacks, gradual rollouts, and traffic migration](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration).

Know these rules:

- After you split traffic, all later deployments keep that split. Use `--to-latest` to send all traffic to the latest revision again ([Rollbacks, gradual rollouts, and traffic migration](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration)).
- Minimum instances set at the revision level also start for tagged revisions, and you pay for them. Use service-level minimum instances, or remove tags that you no longer need ([Rollbacks, gradual rollouts, and traffic migration](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration)).
- To test a tag through API Gateway, use the tag URL in `address` and set `jwt_audience` to `https://SERVICE_HOSTNAME`. Without it, the ID token audience is the tag URL ([Getting started with API Gateway and Cloud Run](https://docs.cloud.google.com/api-gateway/docs/get-started-cloud-run)).

[Traffic splitting: gradual rollouts, rollbacks, and A/B tests](note:1.1-traffic-splitting) covers gradual rollouts. [Deploying to Cloud Run from source code](note:3.1-deploy-from-source) covers revisions.

## AWS mapping

| AWS | Google Cloud | Difference that matters |
|---|---|---|
| Amazon API Gateway | Apigee | A proxy revision is not an API version, and apps never see it |
| Amazon Cognito | Identity Platform | Cloud Run does not check Identity Platform tokens for you. Deploy the service publicly and verify the ID token in code |
| AWS Application Load Balancer with Cognito and Verified Access | Identity-Aware Proxy (IAP) | Enable IAP on the Cloud Run service itself. It then covers every ingress path |
| AWS App Runner | Cloud Run | A revision tag gives a test URL to a revision that gets no traffic |

Sources: [Compare AWS and Azure services to Google Cloud](https://docs.cloud.google.com/docs/get-started/aws-azure-gcp-service-comparison), [Understanding APIs and API proxies](https://docs.cloud.google.com/apigee/docs/api-platform/fundamentals/understanding-apis-and-api-proxies), [Authenticating users](https://docs.cloud.google.com/run/docs/authenticating/end-users), [Configure IAP for Cloud Run](https://docs.cloud.google.com/run/docs/securing/identity-aware-proxy-cloud-run), [Rollbacks, gradual rollouts, and traffic migration](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration).

## Exam traps

- **A version such as `v1.1` in the path.** Google APIs expose only the major version ([AIP-185](https://google.aip.dev/185)).
- **A new required field in `v1`.** That is a breaking change. Make the field optional or create `v2` ([AIP-180](https://google.aip.dev/180)).
- **A field rename in the same major version.** A rename is a remove and an add. Add the new field and keep the old one ([AIP-180](https://google.aip.dev/180)).
- **An Apigee proxy revision as the API version.** Revisions are internal and invisible to apps ([Understanding APIs and API proxies](https://docs.cloud.google.com/apigee/docs/api-platform/fundamentals/understanding-apis-and-api-proxies)).
- **Two proxies with the same base path in one environment.** The base path must be unique ([API proxy configuration reference](https://docs.cloud.google.com/apigee/docs/api-platform/reference/api-proxy-configuration-reference)).
- **Ingress `internal-and-cloud-load-balancing` as the only access control.** IAM still applies. A public site behind the load balancer also needs public access or IAP ([Restrict network endpoint ingress for Cloud Run](https://docs.cloud.google.com/run/docs/securing/ingress)).
- **Cloud Run domain mapping for a production custom domain.** It is Preview and not production-ready. Use a global external Application Load Balancer ([Mapping custom domains](https://docs.cloud.google.com/run/docs/mapping-custom-domains)).
- **IAP on both the load balancer and the Cloud Run service.** You cannot configure both ([Configure IAP for Cloud Run](https://docs.cloud.google.com/run/docs/securing/identity-aware-proxy-cloud-run)).
- **IAP for consumer sign-up.** IAP is for internal users. Use Identity Platform for end users ([Authenticating users](https://docs.cloud.google.com/run/docs/authenticating/end-users)).
- **An API key to authorize access to user data.** A standard key identifies no principal ([Manage API keys](https://docs.cloud.google.com/docs/authentication/api-keys)).
- **A new revision that gets traffic before tests.** Deploy with `--no-traffic --tag` and test the tag URL first ([Rollbacks, gradual rollouts, and traffic migration](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration)).
