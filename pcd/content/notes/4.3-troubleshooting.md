## Why it matters

When a service fails, the developer must find the cause and fix it. Exam questions give a symptom and ask for the correct tool or fix. The symptom can be an HTTP status code, a Pod status, or a log message. This page maps symptoms to the Google Cloud Observability (formerly Stackdriver) tools and to the documented fixes for Cloud Run and GKE.

## Key points

- Use the Logs Explorer to troubleshoot and explore. Use Observability Analytics (formerly Log Analytics) to aggregate log data with SQL or to join log and trace data. The Logs Explorer does not support aggregate operations ([Analyze logs using Logs Explorer and Observability Analytics](https://docs.cloud.google.com/logging/docs/log-analytics), [Logging release notes](https://docs.cloud.google.com/logging/docs/release-notes)).
- In the Logging query language, `NOT` has the highest precedence, then `OR`, then `AND`. Lowercase `and`, `or`, and `not` are search terms, not operators ([Logging query language](https://docs.cloud.google.com/logging/docs/view/logging-query-language)).
- If Cloud Run reports "Container failed to start", check the port. The container must listen on the port in the `PORT` environment variable, and on `0.0.0.0`, not `127.0.0.1` ([Troubleshoot Cloud Run issues](https://docs.cloud.google.com/run/docs/troubleshooting)).
- On Cloud Run, HTTP 429 with "no available instance" means that the service reached its maximum instances. HTTP 500 with the same message means that Cloud Run could not scale fast enough ([Troubleshoot Cloud Run issues](https://docs.cloud.google.com/run/docs/troubleshooting)).
- A GKE Pod in `CrashLoopBackOff` already has a node and its image. Look at the container: the exit code, the logs of the previous container, memory, and probes ([Troubleshoot CrashLoopBackOff events](https://docs.cloud.google.com/kubernetes-engine/docs/troubleshooting/crashloopbackoff-events)).
- The kubelet pulls images from Artifact Registry with the service account of the node VM, not with Workload Identity Federation for GKE ([Troubleshoot image pulls](https://docs.cloud.google.com/kubernetes-engine/docs/troubleshooting/image-pulls)).
- Error Reporting groups error events from log entries that contain a stack trace, and from the Error Reporting API and client libraries. It cannot analyze log entries in log buckets that use CMEK ([Error Reporting overview](https://docs.cloud.google.com/error-reporting/docs/grouping-errors), [Collect error data by using Error Reporting](https://docs.cloud.google.com/error-reporting/docs/setup)).
- A Resolved error group changes back to Open when the error occurs again. A Muted error group does not record new events ([Manage error groups](https://docs.cloud.google.com/error-reporting/docs/managing-errors)).
- Gemini Cloud Assist investigations (Preview) look at logs, metrics, and configurations to find probable root causes ([Troubleshoot issues with Gemini Cloud Assist investigations](https://docs.cloud.google.com/cloud-assist/investigations)).
- Since April 10, 2026, only users with a Premium Support contract, or with access from their account team, can create or run investigations ([Troubleshoot issues with Gemini Cloud Assist investigations](https://docs.cloud.google.com/cloud-assist/investigations)).

## Which tool answers which question

| Question | Tool |
|---|---|

| How many errors per hour, for each version? | Observability Analytics (SQL) |
| How did a metric change, for example after a deployment? | Metrics Explorer and dashboards |
| Which exceptions are new, and how often do they occur? | Error Reporting |
| Which service or call in the request path is slow? | Trace Explorer |
| Which function uses the most CPU or memory? | Cloud Profiler |

## Logs Explorer and the Logging query language

The Logs Explorer, the Cloud Logging API, and the Google Cloud CLI use the same query language. A log entry that belongs to an error group has a menu that opens the error group ([Analyze logs using Logs Explorer and Observability Analytics](https://docs.cloud.google.com/logging/docs/log-analytics)).

Rules of the query language ([Logging query language](https://docs.cloud.google.com/logging/docs/view/logging-query-language)):

- **Operators.** `AND`, `OR`, and `NOT` must be in uppercase. You can omit `AND`, and you can write `-` for `NOT`. Log views support only `AND` and `NOT`.
- **Parentheses.** When you combine `AND` and `OR`, use parentheses. Without them, the precedence can give an unexpected result.
- **Case.** String comparisons ignore letter case. Regular expressions and logical operators do not.
- **Speed.** Query indexed fields: `resource.type`, `resource.labels.*`, `logName`, `severity`, `timestamp`, `insertId`, `operation.id`, `trace`, `httpRequest.status`, `labels.*`, and `split.uid`. A global restriction (a value without a field) can be slow, and the `:` substring operator does not use the indexes. Use the `SEARCH` function instead.
- **Log names.** Use the full, URL-encoded log name, for example `cloudaudit.googleapis.com%2Factivity`. A short name such as `activity` matches nothing.

```text
"a" OR NOT "b" AND NOT "c" OR "d"
("a" OR (NOT "b")) AND ((NOT "c") OR "d")
```

Source: [Logging query language](https://docs.cloud.google.com/logging/docs/view/logging-query-language). The two expressions are equivalent.

You can also read logs from the command line:

```bash
gcloud run services logs read SERVICE --limit=10 --project PROJECT-ID
gcloud logging read "resource.type=cloud_run_revision AND resource.labels.service_name=SERVICE" --project PROJECT-ID --limit 10
```

Source: [Logging and viewing logs in Cloud Run](https://docs.cloud.google.com/run/docs/logging).

## Observability Analytics

Observability Analytics runs SQL queries that group and aggregate log data. It can also join log data with trace data ([Analyze logs using Logs Explorer and Observability Analytics](https://docs.cloud.google.com/logging/docs/log-analytics)).

```sql
SELECT
  -- Count the number of log entries for each severity.
  severity, COUNT(*) AS count
FROM
  `PROJECT_ID.LOCATION.BUCKET_ID.LOG_VIEW_ID`
WHERE
  severity IS NOT NULL
GROUP BY severity
ORDER BY severity
LIMIT 100
```

Source: [Sample SQL queries](https://docs.cloud.google.com/logging/docs/analyze/examples).

- **Upgrade the log bucket first.** The bucket must be at the project level, and unlocked unless it is `_Required`. Older entries become available after a backfill that can take several days ([Analyze logs using Logs Explorer and Observability Analytics](https://docs.cloud.google.com/logging/docs/log-analytics)). Since March 12, 2026, you must ask Cloud Customer Care to start the backfill ([Logging release notes](https://docs.cloud.google.com/logging/docs/release-notes)).
- **Analyze results.** This Logs Explorer button opens Observability Analytics. It appears only when the log bucket is upgraded ([View and analyze log entries](https://docs.cloud.google.com/logging/docs/view/logs-explorer-interface)).
- **Linked BigQuery dataset.** It gives BigQuery read access to the log bucket without BigQuery ingestion or storage costs. BigQuery analysis charges apply to the queries ([Analyze logs using Logs Explorer and Observability Analytics](https://docs.cloud.google.com/logging/docs/log-analytics)).
- **Duplicates.** Observability Analytics does not remove duplicate entries. The Logs Explorer does ([Analyze logs using Logs Explorer and Observability Analytics](https://docs.cloud.google.com/logging/docs/log-analytics)).

## Metrics Explorer, dashboards, and alerts

- **Metrics Explorer** makes temporary charts. To keep a chart, save it to a custom dashboard. Dashboards can show log data, metric data, trace data, and alerts ([Create charts with Metrics Explorer](https://docs.cloud.google.com/monitoring/charts/metrics-explorer)).
- **Cloud Run metrics** include request count, request latencies, container instance count, container startup latency, and CPU and memory utilization. The metric charts of a Cloud Run service show deployment events ([Monitor Health and Performance](https://docs.cloud.google.com/run/docs/monitoring)).
- **Short spikes.** A short increase in traffic or processing time can be visible only at a 10-second resolution ([Troubleshoot Cloud Run issues](https://docs.cloud.google.com/run/docs/troubleshooting)).
- **Alerts.** A log-based alerting policy notifies you when a message appears in your logs. A metric-based policy watches time series ([Alerting overview](https://docs.cloud.google.com/monitoring/alerts)).

## Cloud Run failures

| Symptom | Likely cause | Fix |
|---|---|---|
| Deployment: "Container failed to start. Failed to start and then listen on the port defined by the PORT environment variable." | Wrong port, listens on `127.0.0.1`, or the image is not for 64-bit Linux | Listen on `PORT` and `0.0.0.0`. Run the image locally. If you build on an ARM computer, build with Cloud Build instead. Read the `stdout` and `stderr` logs |
| Deployment: "Google Cloud Run Service Agent must have permission to read the image" | The image is in another project | In the registry project, grant Artifact Registry Reader to the Cloud Run service agent |
| HTTP 500: "The request failed because the instance could not start successfully." | Often, no access to a Secret Manager secret | Grant Secret Manager Secret Accessor to the service account. Check the secret path and the egress to `secretmanager.googleapis.com`. Log the startup steps |
| HTTP 429: "no available instance" | The service reached its maximum instances | Check the container instance count metric. Raise the maximum instances, or the quota |
| HTTP 500: "no available instance" | A traffic spike, a long cold start, or a long request time | Exponential backoff and retries in the client. Minimum instances for cold starts, at a higher cost |
| HTTP 500 or 503: "using too much memory and was terminated" | Memory limit exceeded. Files in the local file system use memory | Check the `varlog/system` log. Raise the memory limit |
| HTTP 503: "probably has reached its maximum container instance limit", with high CPU | Too many concurrent requests for each instance | Raise the maximum instances, or lower the concurrency |
| HTTP 504: "reached the maximum request timeout" | Long requests, or a dead connection that the app reuses | Increase the request timeout. Add logging and tracing. Open new connections after a reset |
| HTTP 404 that is not in the request logs | The ingress setting blocked the request, or the `run.app` URL is disabled | Check the ingress setting. Check the VPC Service Controls audit logs |
| HTTP 401 or 403 | 401: not an ID token, or the wrong audience. 403: no `run.routes.invoke` permission | Send an ID token with the correct `aud`. Grant Cloud Run Invoker (`roles/run.invoker`) |
| High latency with low CPU utilization | A single-threaded app on several vCPUs | Use 1 vCPU, or lower the maximum concurrency |

Sources: [Troubleshoot Cloud Run issues](https://docs.cloud.google.com/run/docs/troubleshooting), [Deploy container images to Cloud Run services](https://docs.cloud.google.com/run/docs/deploying).

```text
resource.type="cloud_run_revision"
log_name="projects/PROJECT_ID/logs/run.googleapis.com%2Frequests"
httpRequest.status=404
```

Source: [Troubleshoot Cloud Run issues](https://docs.cloud.google.com/run/docs/troubleshooting). When ingress blocks a request, this query finds nothing, because the request did not reach the container.

- **Why an instance started.** Cloud Run writes `Starting new instance. Reason: REASON - DESCRIPTION` to the `varlog/system` log. The reasons are `MANUAL_OR_CUSTOMER_MIN_INSTANCE`, `AUTOSCALING`, and `DEPLOYMENT_ROLLOUT` ([Logging and viewing logs in Cloud Run](https://docs.cloud.google.com/run/docs/logging)).
- **Crashes cause cold starts.** If an error crashes the application process, a new instance must start ([Aggregate, analyze, and view errors](https://docs.cloud.google.com/run/docs/error-reporting)).
- **Out of memory in the app.** An application-level out-of-memory error does not always stop the instance. Requests can then stay open until they reach the request timeout ([Troubleshoot Cloud Run issues](https://docs.cloud.google.com/run/docs/troubleshooting)).

How to size instances and reduce cold starts is in [Sizing resources and controlling cost](note:1.1-resources-and-cost). Retries with backoff are in [Efficient and resilient API calls](note:4.2-efficient-api-calls).

## GKE: CrashLoopBackOff and ImagePullBackOff

```bash
kubectl describe pod POD_NAME -n NAMESPACE_NAME
kubectl logs POD_NAME --previous
```

Source: [Troubleshoot CrashLoopBackOff events](https://docs.cloud.google.com/kubernetes-engine/docs/troubleshooting/crashloopbackoff-events).

| Status or finding | Meaning | Fix |
|---|---|---|
| `CrashLoopBackOff` | The container starts and exits again and again. The delay grows (10s, 20s, 40s) up to five minutes | Read the exit code under `Last State`, and the logs of the previous container |
| `Last State: Terminated`, `Reason: OOMKilled` | The container tried to use more than its memory limit (`resources.limits.memory`) | Raise the memory limit, add replicas, or fix a memory leak |
| Liveness probe failures | After three failures (the default), the kubelet restarts the container | Review the probe configuration |
| Exit code `0` | The process ended. For example, a worker stops when its queue is empty, or a `ConfigMap` is missing | Use a Job for work that ends, or fix the configuration |
| Non-zero exit code | Bad configuration, a wrong entry point or command (often exit code `128`), a changed `:latest` image, or a failed dependency | Fix the command and settings. Use immutable tags or digests |
| `ImagePullBackOff` | The kubelet cannot pull the image. It retries with a delay of up to five minutes | Read the pull error in the Pod events |
| Pull error 403 Forbidden | The node pool service account, or the service account of the `imagePullSecret`, cannot read the repository | Grant Artifact Registry Reader (`roles/artifactregistry.reader`) |
| Pull error 401 Unauthorized | The node service account is disabled, or the node has the wrong access scope | Enable the account, or recreate the node pool with the correct scope |
| Image not found, or wrong architecture | The name or tag is wrong, or the image does not match the CPU of the node | Fix the image reference. Build for the node architecture |

Sources: [Troubleshoot CrashLoopBackOff events](https://docs.cloud.google.com/kubernetes-engine/docs/troubleshooting/crashloopbackoff-events), [Troubleshoot OOM events](https://docs.cloud.google.com/kubernetes-engine/docs/troubleshooting/oom-events), [Troubleshoot image pulls](https://docs.cloud.google.com/kubernetes-engine/docs/troubleshooting/image-pulls).

```text
resource.type="k8s_node"
log_id("kubelet")
jsonPayload.MESSAGE:"failed liveness probe, will be restarted"
resource.labels.cluster_name="CLUSTER_NAME"
```

Source: [Troubleshoot CrashLoopBackOff events](https://docs.cloud.google.com/kubernetes-engine/docs/troubleshooting/crashloopbackoff-events). This query finds restarts caused by liveness probes. Probe design is in [Kubernetes health checks](note:3.2-health-checks).

- **Keep the evidence.** GKE removes container logs when their Pod is removed, and removes cluster events after one hour. Cloud Logging keeps the logs that GKE sends to it ([About GKE logs](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/about-logs)).
- **Container Registry.** Container Registry was shut down on March 18, 2025. Use Artifact Registry ([Troubleshoot image pulls](https://docs.cloud.google.com/kubernetes-engine/docs/troubleshooting/image-pulls)).

## Error Reporting

| Way in | How | Notes |
|---|---|---|
| Automatic log collection | Error Reporting reads log entries. For example, Cloud Run sends exceptions on `stderr` to Cloud Logging | The log bucket must not use CMEK, and must be in the source project or the project that the logs were routed to |
| Client library | Your code reports errors, for example with `report_exception()` | Works when log buckets use CMEK. Needs Error Reporting Writer (`roles/errorreporting.writer`) |
| Error Reporting API | Call `report` with a `ReportedErrorEvent` | Required for API key authentication. The calls write log entries, which can cost Logging ingestion |

Sources: [Collect error data by using Error Reporting](https://docs.cloud.google.com/error-reporting/docs/setup), [Instrument Python apps for Error Reporting](https://docs.cloud.google.com/error-reporting/docs/setup/python), [Format a log entry to report error events](https://docs.cloud.google.com/error-reporting/docs/formatting-error-messages).

```python
from google.cloud import error_reporting

client = error_reporting.Client()
try:
    raise Exception("Something went wrong")
except Exception:
    client.report_exception()
```

Source: [Instrument Python apps for Error Reporting](https://docs.cloud.google.com/error-reporting/docs/setup/python).

### Log entries that Error Reporting captures

- **Stack trace and severity on Cloud Run.** For Cloud Run and Cloud Run functions, Error Reporting creates an error event from a log entry that contains a stack trace. The severity of the entry must be not set, or at least `ERROR` ([Instrument Python apps for Error Reporting](https://docs.cloud.google.com/error-reporting/docs/setup/python)).
- **Where the stack trace goes.** Use a multi-line `textPayload`, or a `message`, `stack_trace`, or `exception` field in `jsonPayload`. The evaluation order is `stack_trace`, `exception`, then `message` ([Format a log entry to report error events](https://docs.cloud.google.com/error-reporting/docs/formatting-error-messages)).
- **A message without a stack trace.** Set `@type`, as shown in the next block. If `@type` is not set, Cloud Logging looks for a `serviceContext` field to decide whether the payload is a `ReportedErrorEvent` ([Format a log entry to report error events](https://docs.cloud.google.com/error-reporting/docs/formatting-error-messages)).

```json
"jsonPayload": {
  "@type": "type.googleapis.com/google.devtools.clouderrorreporting.v1beta1.ReportedErrorEvent",
  "message": "Text message"
},
```

Source: [Format a log entry to report error events](https://docs.cloud.google.com/error-reporting/docs/formatting-error-messages).

### Grouping, status, and notifications

- **Grouping.** Events with a stack trace are grouped by exception type and the five topmost frames of the innermost exception. Events with only a message are grouped by the first three literal tokens of the message and, if present, the function name. Frames that you do not own, such as library frames, are ignored ([Error Reporting overview](https://docs.cloud.google.com/error-reporting/docs/grouping-errors)).
- **Cloud Run errors.** "Memory limit exceeded" and "No instances available" errors also appear automatically. The Cloud Run console shows them on the **Observability** > **Errors** tab ([Aggregate, analyze, and view errors](https://docs.cloud.google.com/run/docs/error-reporting)).
- **From an error to its logs.** In **Recent samples**, **View Logs** opens the Logs Explorer with a filter such as `errorGroups.id="ERROR_GROUP_ID"` ([View and filter error groups](https://docs.cloud.google.com/error-reporting/docs/viewing-errors)). You cannot use this field in sink filters, log-based metrics, or log-based alerts ([LogEntry](https://docs.cloud.google.com/logging/docs/reference/v2/rest/v2/LogEntry)).

| Resolution status | Meaning |
|---|---|
| Open | The default for every new error group |
| Acknowledged | Someone is triaging the error |
| Resolved | Fixed. If the error occurs again, the status changes back to Open |
| Muted | Hidden. New events are not recorded, and nobody is notified |

Source: [Manage error groups](https://docs.cloud.google.com/error-reporting/docs/managing-errors).

Error Reporting sends a notification for a new error that it cannot group with existing errors. It also sends one for an error in a Resolved group (a regression). It uses Cloud Monitoring notification channels: email, mobile, Slack, and webhooks. To configure notifications, you need the Error Reporting User role ([Configure and manage notifications](https://docs.cloud.google.com/error-reporting/docs/notifications)).

## Slow code: Cloud Trace or Cloud Profiler

| Symptom | Tool | What it shows |
|---|---|---|
| Some requests are slow, and you do not know which service or call is slow | Cloud Trace | The latency of each span of a request, as a waterfall graph |
| The service uses too much CPU or memory under normal load | Cloud Profiler | The functions that use the most CPU time or memory, from production data |
| High latency on Cloud Run, but low CPU utilization | Cloud Run settings | A possible cause is a single-threaded app on several vCPUs |

Sources: [Using distributed tracing](https://docs.cloud.google.com/run/docs/trace), [Cloud Profiler overview](https://docs.cloud.google.com/profiler/docs/about-profiler), [Troubleshoot Cloud Run issues](https://docs.cloud.google.com/run/docs/troubleshooting).

- **Profile data** is kept for 30 days. You can download profiles to keep them longer ([Cloud Profiler overview](https://docs.cloud.google.com/profiler/docs/about-profiler)).
- **Exemplars.** An exemplar can link a metric measurement to a trace, so that you can correlate metric data and trace data ([Instrument for Cloud Trace](https://docs.cloud.google.com/trace/docs/setup)).

## AI-assisted observability

Gemini Cloud Assist is in Preview. It lets you explore metrics, logs, alerts, and errors with natural language. Validate all of its output before you use it ([Gemini Cloud Assist overview](https://docs.cloud.google.com/cloud-assist/overview)).

| Need | Feature | Notes |
|---|---|---|
| Explain one log entry | **Investigate log** in the Logs Explorer | Sends only the text of the entry. For `ERROR` or higher, it can list causes and fixes |
| Troubleshooting help for an error group | Gemini on the Error Group Details page | Available when Gemini is enabled in the project |
| Find the root cause across logs, metrics, and configuration | An investigation | Gives observations, hypotheses, and next steps |
| Start an analysis when an alert fires | Proactive alert investigations | You configure alerting policies to start Gemini Cloud Assist automatically. It gives a preliminary root-cause analysis |
| Use the same agents from an IDE or a CLI | MCP support | For example, from Gemini CLI or Claude Code |

Sources: [View and analyze log entries](https://docs.cloud.google.com/logging/docs/view/logs-explorer-interface), [View and filter error groups](https://docs.cloud.google.com/error-reporting/docs/viewing-errors), [Troubleshoot issues with Gemini Cloud Assist investigations](https://docs.cloud.google.com/cloud-assist/investigations), [Gemini Cloud Assist overview](https://docs.cloud.google.com/cloud-assist/overview).

Facts about investigations:

- **Inputs.** Enter a time range, the issue (paste the exact error message), and the resources. An accurate start time gives better results ([Create a Gemini Cloud Assist investigation](https://docs.cloud.google.com/cloud-assist/create-investigation)).
- **Results.** A recap, hypotheses with next steps, and findings. For some hypotheses, **Generate plan** creates steps with `gcloud` commands or Kubernetes manifests. You review the plan and then click **Run** ([Create a Gemini Cloud Assist investigation](https://docs.cloud.google.com/cloud-assist/create-investigation)).
- **Start points.** The Investigations page, the Logs Explorer (entries of severity Warning or higher), alerts that have a resource label, the Cloud Assist chat, Cloud Hub, and product pages ([Troubleshoot issues with Gemini Cloud Assist investigations](https://docs.cloud.google.com/cloud-assist/investigations)).
- **Access.** You need the Investigation Creator role (`roles/geminicloudassist.investigationCreator`). The investigation uses your credentials, so it sees only what you can see ([Create a Gemini Cloud Assist investigation](https://docs.cloud.google.com/cloud-assist/create-investigation)).
- **Limits.** One investigation covers one project or one App Hub application. Its OAuth token is never used to change data. Its data can be stored in any Google Cloud data center, so do not use it for data with residency requirements. Two runs can give different results ([Troubleshoot issues with Gemini Cloud Assist investigations](https://docs.cloud.google.com/cloud-assist/investigations)).
- **Application code.** For Cloud Run, an investigation can trace a root cause from infrastructure signals to application code ([Gemini Cloud Assist overview](https://docs.cloud.google.com/cloud-assist/overview)).

Setup of Gemini Cloud Assist is in [Developer tools](note:2.1-developer-tools). MCP servers and coding agents are in [AI coding assistants, context, and MCP servers](note:2.1-ai-assisted-development).

## Exam traps

- **A count of errors per hour in the Logs Explorer.** It does not aggregate. Use Observability Analytics ([Analyze logs using Logs Explorer and Observability Analytics](https://docs.cloud.google.com/logging/docs/log-analytics)).
- **`a OR b AND c` read as "a, or b and c".** `OR` has a higher precedence than `AND`. The query means "(a or b) and c" ([Logging query language](https://docs.cloud.google.com/logging/docs/view/logging-query-language)).
- **A 404 that the request logs do not show.** The ingress setting or a disabled `run.app` URL stopped the request before the container ([Troubleshoot Cloud Run issues](https://docs.cloud.google.com/run/docs/troubleshooting)).
- **More memory to fix HTTP 429.** HTTP 429 "no available instance" needs more maximum instances or quota ([Troubleshoot Cloud Run issues](https://docs.cloud.google.com/run/docs/troubleshooting)).
- **An error message without a stack trace that never reaches Error Reporting.** Add a stack trace, or set `@type` to the `ReportedErrorEvent` type ([Format a log entry to report error events](https://docs.cloud.google.com/error-reporting/docs/formatting-error-messages)).
- **A stack trace logged at `WARNING` on Cloud Run.** For Cloud Run and Cloud Run functions, Error Reporting needs a severity that is not set or is at least `ERROR` ([Instrument Python apps for Error Reporting](https://docs.cloud.google.com/error-reporting/docs/setup/python)).
- **Log buckets with CMEK.** Error Reporting cannot read them. Use the client library ([Instrument Python apps for Error Reporting](https://docs.cloud.google.com/error-reporting/docs/setup/python)).
- **Muted instead of Resolved.** Muted stops recording and notifications. A Resolved group reopens when the error comes back, and this regression can send a notification ([Manage error groups](https://docs.cloud.google.com/error-reporting/docs/managing-errors), [Configure and manage notifications](https://docs.cloud.google.com/error-reporting/docs/notifications)).
- **Artifact Registry Reader granted to the Kubernetes service account for an image pull.** The kubelet uses the node service account ([Troubleshoot image pulls](https://docs.cloud.google.com/kubernetes-engine/docs/troubleshooting/image-pulls)).
- **A Deployment for a worker that exits with code `0`.** Use a Job for work that ends ([Troubleshoot CrashLoopBackOff events](https://docs.cloud.google.com/kubernetes-engine/docs/troubleshooting/crashloopbackoff-events)).
- **`kubectl logs` without `--previous`.** The new container can be too new to have the crash logs ([Troubleshoot CrashLoopBackOff events](https://docs.cloud.google.com/kubernetes-engine/docs/troubleshooting/crashloopbackoff-events)).
- **An investigation for data with residency requirements.** Investigation data can be stored in any data center ([Troubleshoot issues with Gemini Cloud Assist investigations](https://docs.cloud.google.com/cloud-assist/investigations)).
