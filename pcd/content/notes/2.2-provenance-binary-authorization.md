## Why it matters

Build provenance records where, how, and from what source an image was built. Binary Authorization checks signed attestations at deploy time and blocks images that did not pass the steps you require. The exam tests how to make Cloud Build produce provenance and how to allow only images that Cloud Build built. It also tests how to write a policy and how to roll out enforcement on Cloud Run and GKE without an outage.

## Key points

- Build provenance is verifiable metadata about a build: image digests, source locations, build arguments, and build duration. Cloud Build provenance meets SLSA level 3 ([Generate and validate build provenance](https://docs.cloud.google.com/build/docs/securing-builds/generate-validate-build-provenance)).
- Cloud Build generates provenance only for artifacts in Artifact Registry. A container image gets provenance only when the `images` field pushes it, not an explicit `docker push` step ([Generate and validate build provenance](https://docs.cloud.google.com/build/docs/securing-builds/generate-validate-build-provenance)).
- `options.requestedVerifyOption: VERIFIED` turns on provenance generation. The build succeeds only if Cloud Build generates the provenance ([Generate and validate build provenance](https://docs.cloud.google.com/build/docs/securing-builds/generate-validate-build-provenance)).
- Binary Authorization is a deploy-time control for GKE, Cloud Run, Cloud Service Mesh (formerly Anthos Service Mesh and Traffic Director), and Google Distributed Cloud ([Binary Authorization overview](https://docs.cloud.google.com/binary-authorization/docs/overview)).
- Each project has exactly one policy, in the project where the deployment platform runs. A rule has an evaluation mode and an enforcement mode ([Binary Authorization concepts](https://docs.cloud.google.com/binary-authorization/docs/key-concepts)).
- An attestation is a signature over an image digest. An attestor holds the public key that verifies it ([Binary Authorization concepts](https://docs.cloud.google.com/binary-authorization/docs/key-concepts)).
- Cloud Build signs attestations at build time. To deploy only images that Cloud Build built, require the `built-by-cloud-build` attestor ([Securing image deployments to Cloud Run and Google Kubernetes Engine](https://docs.cloud.google.com/build/docs/securing-builds/secure-deployments-to-run-gke)).
- Dry-run mode (`DRYRUN_AUDIT_LOG_ONLY`) allows every image and writes violations to Cloud Audit Logs ([Enable dry-run mode](https://docs.cloud.google.com/binary-authorization/docs/enabling-dry-run)).
- Breakglass deploys a blocked image in an emergency and always writes an audit log entry ([Use breakglass (GKE, Distributed Cloud)](https://docs.cloud.google.com/binary-authorization/docs/using-breakglass), [Use breakglass (Cloud Run)](https://docs.cloud.google.com/binary-authorization/docs/run/using-breakglass-cloud-run)).
- Continuous validation with check-based platform policies (Preview) checks running GKE Pods at least every 24 hours. It logs violations but does not stop Pods ([Continuous validation overview](https://docs.cloud.google.com/binary-authorization/docs/overview-cv)).

## SLSA and Cloud Build provenance

SLSA (Supply-chain Levels for Software Artifacts) is a framework of build maturity levels. Each level adds requirements to the level below it:

| SLSA level | Added requirements |
|---|---|
| 1 | Automated builds. Build provenance is available to the consumers of the artifact |
| 2 | A build service, not developer environments. The build service generates the provenance and signs it, so consumers can verify it |
| 3 | The provenance includes the entry point of the build definition and all build parameters under user control |

Source: [Safeguard builds](https://docs.cloud.google.com/software-supply-chain-security/docs/safeguard-builds).

Cloud Build can generate SLSA level 3 provenance for container images. It also sets up a new virtual machine for every build and destroys it after the build ([Safeguard builds](https://docs.cloud.google.com/software-supply-chain-security/docs/safeguard-builds)).

### Request provenance

```yaml
steps:
- name: 'gcr.io/cloud-builders/docker'
  args: ['build', '-t', 'LOCATION-docker.pkg.dev/PROJECT_ID/REPOSITORY/IMAGE', '.']
images: ['LOCATION-docker.pkg.dev/PROJECT_ID/REPOSITORY/IMAGE']
options:
  requestedVerifyOption: VERIFIED
```

Source: [Generate and validate build provenance](https://docs.cloud.google.com/build/docs/securing-builds/generate-validate-build-provenance).

The `images` field is necessary. With only a `docker push` step, Cloud Build generates neither provenance nor the Binary Authorization attestation ([Generate and validate build provenance](https://docs.cloud.google.com/build/docs/securing-builds/generate-validate-build-provenance), [Securing image deployments to Cloud Run and Google Kubernetes Engine](https://docs.cloud.google.com/build/docs/securing-builds/secure-deployments-to-run-gke)). Builds in a private pool generate attestations only when you set `requestedVerifyOption: VERIFIED` ([Securing image deployments to Cloud Run and Google Kubernetes Engine](https://docs.cloud.google.com/build/docs/securing-builds/secure-deployments-to-run-gke)).

### Where provenance is stored and how to view it

Artifact Analysis (formerly Container Analysis) stores metadata for images as notes and occurrences ([Artifact Analysis overview](https://docs.cloud.google.com/artifact-analysis/docs/artifact-analysis)). The provenance output shows an occurrence of kind `BUILD` for the image digest. Provenance is a repository attachment. Cleanup policies do not delete it, but deleting the image deletes it. To use provenance, enable the Cloud Build, Container Analysis, and Artifact Registry APIs ([Generate and validate build provenance](https://docs.cloud.google.com/build/docs/securing-builds/generate-validate-build-provenance)).

| Task | How |
|---|---|
| View in the console | The **Security insights** panel on the Build History page. It shows the SLSA build level, vulnerabilities in build artifacts, and provenance |
| View with gcloud | `gcloud artifacts docker images describe IMAGE@sha256:HASH --show-provenance` |
| Validate | The open source SLSA verifier with the source URI and the builder ID `https://cloudbuild.googleapis.com/GoogleHostedWorker`. Or get the public key from Cloud KMS and check the signature with `openssl` |
| Non-container artifacts | Go, Java (Maven), Python, and Node.js (npm) builds that upload to Artifact Registry also get provenance. Find it with `gcloud container analysis occurrences list` and a filter for the build ID |

Sources: [Generate and validate build provenance](https://docs.cloud.google.com/build/docs/securing-builds/generate-validate-build-provenance), [Software supply chain security](https://docs.cloud.google.com/software-supply-chain-security/docs/overview).

In the documented example, the provenance records the build config path, the Git ref, the system substitutions such as `COMMIT_SHA` and `TRIGGER_NAME`, and the trigger. The `resolvedDependencies` field lists the source commit and the digests of the builder images. With SLSA version 0.1 provenance, Binary Authorization policies can verify the DSSE signature (`provenanceSigner`) ([Generate and validate build provenance](https://docs.cloud.google.com/build/docs/securing-builds/generate-validate-build-provenance)). The signatures identify the build service. To also record which service account started the build, sign the image with cosign and a user-specified service account ([Build container images](https://docs.cloud.google.com/build/docs/building/build-containers)).

## Binary Authorization policy model

| Term | Meaning |
|---|---|
| Policy | The project-singleton set of rules and exempt images. Configure it in the project where GKE or Cloud Run runs |
| Default rule (`defaultAdmissionRule`) | Applies to every deployment that no specific rule matches |
| Specific rule | GKE and other Kubernetes platforms only: a rule for a cluster, a Kubernetes namespace, or a Kubernetes service account. Cloud Run supports only the default rule |
| Evaluation mode | `ALWAYS_ALLOW`, `ALWAYS_DENY`, or `REQUIRE_ATTESTATION` |
| Enforcement mode | `ENFORCED_BLOCK_AND_AUDIT_LOG`, or `DRYRUN_AUDIT_LOG_ONLY` |
| Attestation | A signed statement that an image digest completed a required process. Stored as an Artifact Analysis occurrence |
| Signer | A person or process that signs the digest with a private key |
| Attestor | A resource with an Artifact Analysis note and the public key that verifies attestations at deploy time |
| Exempt images | `admissionWhitelistPatterns`: image paths that are always allowed |

Sources: [Binary Authorization concepts](https://docs.cloud.google.com/binary-authorization/docs/key-concepts), [Policy YAML reference](https://docs.cloud.google.com/binary-authorization/docs/policy-yaml-reference).

You edit a policy as YAML. Export it with `gcloud container binauthz policy export > /tmp/policy.yaml`, change it, and import it with `gcloud container binauthz policy import /tmp/policy.yaml`. This policy needs the Cloud Build attestation everywhere, and a second attestation for one production cluster:

```yaml
name: projects/PROJECT_ID/policy
globalPolicyEvaluationMode: ENABLE
defaultAdmissionRule:
  evaluationMode: REQUIRE_ATTESTATION
  enforcementMode: ENFORCED_BLOCK_AND_AUDIT_LOG
  requireAttestationsBy:
  - projects/PROJECT_ID/attestors/built-by-cloud-build
clusterAdmissionRules:
  us-east1-a.prod-cluster:
    evaluationMode: REQUIRE_ATTESTATION
    enforcementMode: ENFORCED_BLOCK_AND_AUDIT_LOG
    requireAttestationsBy:
    - projects/PROJECT_ID/attestors/built-by-cloud-build
    - projects/PROJECT_ID/attestors/prod-qualified
```

Sources: [Policy YAML reference](https://docs.cloud.google.com/binary-authorization/docs/policy-yaml-reference), [Securing image deployments to Cloud Run and Google Kubernetes Engine](https://docs.cloud.google.com/build/docs/securing-builds/secure-deployments-to-run-gke).

Rules that the exam uses ([Policy YAML reference](https://docs.cloud.google.com/binary-authorization/docs/policy-yaml-reference)):

- **A specific rule replaces the default rule.** For a deployment to `prod-cluster`, Binary Authorization does not consider the default rule. A cluster rule must list every attestor it needs.
- **System images.** `globalPolicyEvaluationMode: ENABLE` is the default and is recommended. It trusts the Google-maintained images that GKE needs. With `DISABLE`, you must list those paths yourself.
- **Wildcards.** `*` matches one directory and `**` matches subdirectories. A pattern such as `gcr.io/my-project**` also matches images in another project, for example `my-project-exploit`.
- **Changes take effect in a few minutes** ([Enable dry-run mode](https://docs.cloud.google.com/binary-authorization/docs/enabling-dry-run)).

Attestations are for a digest, not a tag. GKE with Binary Authorization does not allow tag-based deployment ([About container image digests](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/about-container-images)). For digests, see [Building containers with Cloud Build and storing them in Artifact Registry](note:2.2-cloud-build-artifact-registry).

## Allow only images that Cloud Build built

Cloud Build creates the `built-by-cloud-build` attestor the first time you run a build in a project. Add `projects/PROJECT_ID/attestors/built-by-cloud-build` to `requireAttestationsBy`, where `PROJECT_ID` is the project that runs Cloud Build ([Securing image deployments to Cloud Run and Google Kubernetes Engine](https://docs.cloud.google.com/build/docs/securing-builds/secure-deployments-to-run-gke)). Limits of this attestor ([Securing image deployments to Cloud Run and Google Kubernetes Engine](https://docs.cloud.google.com/build/docs/securing-builds/secure-deployments-to-run-gke)):

1. Cloud Build and Binary Authorization must be in the same project. For another deployment project, configure IAM for a multi-project setup and refer to the Cloud Build project.
2. Push with the `images` field. An explicit `docker push` step gives no attestation.
3. Use separate build config files for the build and the deployment. Cloud Build creates the attestation only after the build pipeline completes successfully.
4. In a private pool, set `requestedVerifyOption: VERIFIED`.

## Custom attestors and attestations

Use your own attestor when a stage other than the build must approve the image. For example, a QA representative creates an attestation after a manual check ([Binary Authorization overview](https://docs.cloud.google.com/binary-authorization/docs/overview), [Binary Authorization concepts](https://docs.cloud.google.com/binary-authorization/docs/key-concepts)).

1. Create one Artifact Analysis note for the attestor. Each attestation is an occurrence of this note ([Create attestors using the gcloud CLI](https://docs.cloud.google.com/binary-authorization/docs/creating-attestors-cli)).
2. Create a key pair. Binary Authorization supports PKIX keys, which include post-quantum (PQC) algorithms, and PGP keys. PKIX keys can be local, external, or in Cloud KMS ([Binary Authorization concepts](https://docs.cloud.google.com/binary-authorization/docs/key-concepts)).
3. Create the attestor with `gcloud container binauthz attestors create`, and add the public key with `gcloud container binauthz attestors public-keys add` ([Create attestors using the gcloud CLI](https://docs.cloud.google.com/binary-authorization/docs/creating-attestors-cli)).
4. If the attestor and the deployment are in different projects, grant the deployer project's service account the Attestor Verifier role (`roles/binaryauthorization.attestorsVerifier`) on the attestor ([Create attestors using the gcloud CLI](https://docs.cloud.google.com/binary-authorization/docs/creating-attestors-cli)).
5. Create the attestation for `IMAGE@DIGEST`. The signer needs the Notes Attacher role on the note and the Occurrences Editor role on the attestation project ([Create attestations](https://docs.cloud.google.com/binary-authorization/docs/making-attestations)).

For step 5, there are two commands ([Create attestations](https://docs.cloud.google.com/binary-authorization/docs/making-attestations)):

- **Local key.** Sign the payload yourself, for example with `openssl`. Then run `gcloud container binauthz attestations create --signature-file=FILE --public-key-id=ID`.
- **Cloud KMS key.** Run `gcloud beta container binauthz attestations sign-and-create` with the key version. This command is in `gcloud beta` only.

Add `--validate` to either command. It checks that the attestor in your policy can verify the attestation. In Cloud Build, a community build step (`binauthz-attestation`) signs with Cloud KMS. Its service account needs the Attestor Viewer, Cloud KMS CryptoKey Signer/Verifier, and Notes Attacher roles ([Create a Binary Authorization attestation in a Cloud Build pipeline](https://docs.cloud.google.com/binary-authorization/docs/cloud-build)).

For separation of duties, Google recommends three projects. The deployer project holds the policy and the clusters. The attestor project holds the attestors and keys. The attestation project holds the attestations ([Create attestors using the gcloud CLI](https://docs.cloud.google.com/binary-authorization/docs/creating-attestors-cli), [Configure a multi-project setup](https://docs.cloud.google.com/binary-authorization/docs/multi-project-setup-cli)).

## Enforcement on Cloud Run and GKE

| | Cloud Run | GKE |
|---|---|---|
| Turn on | `gcloud run deploy SERVICE --image=IMAGE --binary-authorization=default`, or `gcloud run services update` and `gcloud run jobs update` with the same flag | `gcloud container clusters update NAME --zone ZONE --binauthz-evaluation-mode=PROJECT_SINGLETON_POLICY_ENFORCE` (or `--region` for a regional cluster) |
| Rules | Default rule only | Default rule and specific rules |
| When an image is blocked | The new revision fails with "uses an unauthorized container image". The service keeps serving the earlier healthy revision | `kubectl` returns `Forbidden: image policy webhook backend denied one or more images` |
| Breakglass | `gcloud run services update SERVICE --breakglass=JUSTIFICATION` | Pod label `image-policy.k8s.io/break-glass: "true"` |

Sources: [Enable Binary Authorization for Cloud Run](https://docs.cloud.google.com/binary-authorization/docs/run/enabling-binauthz-cloud-run), [Enable enforcement on an existing cluster](https://docs.cloud.google.com/binary-authorization/docs/enable-cluster), [Binary Authorization concepts](https://docs.cloud.google.com/binary-authorization/docs/key-concepts), [Use breakglass (GKE, Distributed Cloud)](https://docs.cloud.google.com/binary-authorization/docs/using-breakglass), [Use breakglass (Cloud Run)](https://docs.cloud.google.com/binary-authorization/docs/run/using-breakglass-cloud-run).

- **Cloud Run checks every update.** A change that affects traffic triggers enforcement on each revision that receives traffic. On an existing service, you might need to deploy a revision or update traffic before enforcement starts ([Enable Binary Authorization for Cloud Run](https://docs.cloud.google.com/binary-authorization/docs/run/enabling-binauthz-cloud-run)).
- **Require it on Cloud Run.** Cloud Run developers can turn Binary Authorization off. To prevent this, set the organization policy `run.allowedBinaryAuthorizationPolicies` to the value `default` on the organization, a folder, or a project ([Enable Binary Authorization for Cloud Run](https://docs.cloud.google.com/binary-authorization/docs/run/enabling-binauthz-cloud-run), [Require Binary Authorization for Cloud Run](https://docs.cloud.google.com/binary-authorization/docs/run/requiring-binauthz-cloud-run)).
- **Cloud Run functions (formerly Cloud Functions).** To deploy functions, the policy must exempt the repository that holds the function images. Use `REGION-docker.pkg.dev/PROJECT_ID/cloud-run-source-deploy/**` for `gcloud run deploy`, or `.../gcf-artifacts/**` for `gcloud functions deploy` ([Use Binary Authorization](https://docs.cloud.google.com/run/docs/securing/binary-authorization)).
- **Breakglass for one deployment.** The `--breakglass` justification applies to one operation. The next update or deploy command clears it automatically ([gcloud run services update](https://docs.cloud.google.com/sdk/gcloud/reference/run/services/update)).
- **Breakglass annotation.** Do not add the `run.googleapis.com/binary-authorization-breakglass` annotation to the service YAML. Then all later deployments bypass enforcement ([Use breakglass (Cloud Run)](https://docs.cloud.google.com/binary-authorization/docs/run/using-breakglass-cloud-run)).

## Roll out enforcement safely

1. Write the policy with `enforcementMode: DRYRUN_AUDIT_LOG_ONLY`. All images still deploy ([Enable dry-run mode](https://docs.cloud.google.com/binary-authorization/docs/enabling-dry-run)).
2. Deploy and read the dry-run events in Cloud Audit Logs. Find the images that the policy would block, and take corrective action ([Enable dry-run mode](https://docs.cloud.google.com/binary-authorization/docs/enabling-dry-run)).
3. Change to `ENFORCED_BLOCK_AND_AUDIT_LOG`. Most production rules use this mode ([Binary Authorization concepts](https://docs.cloud.google.com/binary-authorization/docs/key-concepts)).
4. Use breakglass only for emergencies, and alert on breakglass events in Cloud Audit Logs ([Use breakglass (GKE, Distributed Cloud)](https://docs.cloud.google.com/binary-authorization/docs/using-breakglass)).

For an organization policy that requires Binary Authorization on Cloud Run, Google also recommends dry-run mode first if services are running ([Require Binary Authorization for Cloud Run](https://docs.cloud.google.com/binary-authorization/docs/run/requiring-binauthz-cloud-run)).

## Continuous validation (Preview)

Enforcement checks an image once, at deploy time. After a policy update, Pods that already run continue to run. Continuous validation (CV) closes this gap on GKE ([Continuous validation overview](https://docs.cloud.google.com/binary-authorization/docs/overview-cv)):

- CV uses check-based **platform policies**, which are separate from the project-singleton policy. Platform policies only monitor, and GKE is the only platform. Use a project-singleton policy to enforce and a matching platform policy to monitor.
- CV reviews the images of running Pods at least every 24 hours and writes violations to Cloud Logging. CV also logs Pods that breakglass or dry run allowed.
- CV does not terminate Pods and does not support image tags, except in exempt images.

| Check | Logs a Pod when |
|---|---|
| Simple signing attestation | An image has no valid attestation. Use the same note and key as the attestor |
| SLSA | The image was not built by a trusted builder (Cloud Build only) from a config in a trusted source repository |
| Vulnerability | Artifact Analysis finds vulnerabilities above a severity, or a blocked CVE, also after deployment |
| Image freshness | The image was uploaded more than `maxUploadAgeDays` ago |
| Sigstore signature | The image has no valid Sigstore signature |
| Trusted directory | The image is in a repository path that the policy does not list |
| Always deny | Always, for example for a set of Pods that you want to see in the logs |

Source: [Continuous validation overview](https://docs.cloud.google.com/binary-authorization/docs/overview-cv).

A project-singleton policy needs a valid attestation from every attestor in the rule. The simple signing attestation check passes with an attestation from any key in any authenticator. To match a rule with several attestors, configure one attestation check for each attestor ([Continuous validation overview](https://docs.cloud.google.com/binary-authorization/docs/overview-cv)).

To keep enforcement and add CV on a cluster, use `--binauthz-evaluation-mode=POLICY_BINDINGS_AND_PROJECT_SINGLETON_POLICY_ENFORCE`. The value `POLICY_BINDINGS` alone turns off an existing enforcement policy ([Enable enforcement on an existing cluster](https://docs.cloud.google.com/binary-authorization/docs/enable-cluster)). In the gcloud reference, the GA `gcloud container clusters update` command accepts only `disabled` and `project-singleton-policy-enforce`. The two CV values are in `gcloud beta container clusters update` ([gcloud container clusters update](https://docs.cloud.google.com/sdk/gcloud/reference/container/clusters/update), [gcloud beta container clusters update](https://docs.cloud.google.com/sdk/gcloud/reference/beta/container/clusters/update)). For vulnerability findings and fixes, see [Protecting apps and finding vulnerabilities](note:1.2-protect-and-scan).

## Exam traps

- **No provenance or attestation after a `docker push` step.** Push with the `images` field ([Generate and validate build provenance](https://docs.cloud.google.com/build/docs/securing-builds/generate-validate-build-provenance)).
- **One `cloudbuild.yaml` that builds and then deploys under a `built-by-cloud-build` policy.** The attestation exists only after the build completes. Use separate build and deploy configs ([Securing image deployments to Cloud Run and Google Kubernetes Engine](https://docs.cloud.google.com/build/docs/securing-builds/secure-deployments-to-run-gke)).
- **A private pool build with no attestation.** Add `requestedVerifyOption: VERIFIED` ([Securing image deployments to Cloud Run and Google Kubernetes Engine](https://docs.cloud.google.com/build/docs/securing-builds/secure-deployments-to-run-gke)).
- **Deploying by tag to GKE with Binary Authorization.** Deploy by digest ([About container image digests](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/about-container-images)).
- **Dry run on the default rule, with the expectation that it blocks images.** Dry run allows every image and only writes logs ([Enable dry-run mode](https://docs.cloud.google.com/binary-authorization/docs/enabling-dry-run)).
- **A cluster-specific rule that lists only the QA attestor.** The default rule no longer applies to that cluster, so the build attestor check is lost ([Policy YAML reference](https://docs.cloud.google.com/binary-authorization/docs/policy-yaml-reference)).
- **A namespace rule for Cloud Run.** Cloud Run supports only the default rule ([Binary Authorization concepts](https://docs.cloud.google.com/binary-authorization/docs/key-concepts)).
- **Binary Authorization turned on for each Cloud Run service, with the expectation that it stays on.** Developers can turn it off. Require it with the `run.allowedBinaryAuthorizationPolicies` organization policy ([Enable Binary Authorization for Cloud Run](https://docs.cloud.google.com/binary-authorization/docs/run/enabling-binauthz-cloud-run)).
- **Expecting a stricter policy to stop running Pods.** Enforcement is at deploy time. CV logs violations but does not terminate Pods ([Continuous validation overview](https://docs.cloud.google.com/binary-authorization/docs/overview-cv)).
- **Setting `POLICY_BINDINGS` to add CV.** It turns off enforcement. Use `POLICY_BINDINGS_AND_PROJECT_SINGLETON_POLICY_ENFORCE` ([Enable enforcement on an existing cluster](https://docs.cloud.google.com/binary-authorization/docs/enable-cluster)).
