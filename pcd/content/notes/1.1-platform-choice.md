## Why it matters

The first design decision for a new workload is where it runs. Google recommends that you consider serverless first, so Cloud Run is the default choice and GKE Autopilot is the next choice ([Select a managed container runtime environment](https://docs.cloud.google.com/architecture/select-managed-container-runtime-environment)). The exam gives a list of requirements and asks for the platform with the least operations work that meets all of them. Find the one requirement that removes Cloud Run, for example a Kubernetes API, a privileged container, a specific OS, or a protocol other than HTTP.

## Key points

- **Serverless first.** "Unless you specifically want or need Kubernetes, we recommend that you consider serverless first as your target runtime environment." If the workload does not fit serverless, Google recommends GKE Autopilot ([Select a managed container runtime environment](https://docs.cloud.google.com/architecture/select-managed-container-runtime-environment)).
- **The Cloud Run fit test.** A Cloud Run service must meet four criteria. It serves HTTP, HTTP/2, WebSockets, or gRPC, or it runs to completion. It needs no persistent local file system. It works with many instances at the same time. It needs no more than 8 CPU and 32 GiB of memory per instance. If the app fails a criterion, look at GKE ([Is my app a good fit for a Cloud Run service?](https://docs.cloud.google.com/run/docs/fit-for-run)).
- **Four Cloud Run resource types.** A service answers HTTP requests at a stable endpoint. A job runs tasks to completion. A worker pool runs always-on background work, such as Kafka or Pub/Sub consumers. An instance is a singleton for long-lived work (Preview) ([What is Cloud Run](https://docs.cloud.google.com/run/docs/overview/what-is-cloud-run), [Deployment options and resource model](https://docs.cloud.google.com/run/docs/resource-model)).
- **Cloud Run functions** (formerly Cloud Functions 2nd gen) is a Cloud Run service that you deploy from function source code. The original product is now Cloud Run functions (1st gen) ([Compare Cloud Run functions](https://docs.cloud.google.com/run/docs/functions/comparison)).
- **Autopilot is the recommended GKE mode.** Use Autopilot for most workloads. Use Standard only when the app needs privileges or configuration that Autopilot does not allow ([About GKE modes of operation](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/choose-cluster-mode)).
- **Kubernetes dependency means GKE.** An app that calls Kubernetes APIs, uses custom resources, or deploys with Helm needs Autopilot, because Cloud Run does not support Kubernetes ([Select a managed container runtime environment](https://docs.cloud.google.com/architecture/select-managed-container-runtime-environment)).
- **Compute Engine is for full OS control.** Use it to migrate a legacy app with specific licensing, OS, kernel, or networking requirements. Examples are a Windows app and SAP HANA ([Where should I run my stuff?](https://cloud.google.com/blog/topics/developers-practitioners/where-should-i-run-my-stuff-choosing-google-cloud-compute-option)).
- **Different price models.** Cloud Run charges per use, rounded up to the nearest 100 ms. GKE charges a fee per cluster per hour in both modes, plus the compute ([GKE and Cloud Run](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/gke-and-cloud-run), [Google Kubernetes Engine pricing](https://cloud.google.com/kubernetes-engine/pricing)).
- **One image, two platforms.** The same container image runs on Cloud Run and on GKE with no change. Cloud Deploy delivers to both, and a load balancer can split traffic across both ([GKE and Cloud Run](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/gke-and-cloud-run)).
- **App Engine is not for new apps.** Google recommends Cloud Run as the preferred alternative to App Engine for new Google Cloud users ([Choose an App Engine environment](https://docs.cloud.google.com/appengine/docs/the-appengine-environments)).

## The decision order

Google puts the runtimes in two groups. The most-managed group is Cloud Run (which includes functions) and GKE Autopilot. The least-managed group is GKE Standard and Compute Engine, where you manage the VMs ([Select a managed container runtime environment](https://docs.cloud.google.com/architecture/select-managed-container-runtime-environment)). Go down this list and stop at the first platform that meets every requirement:

1. **Cloud Run.** The workload passes the fit test, and nothing in it needs Kubernetes.
2. **GKE Autopilot.** The workload needs Kubernetes, a persistent disk, Arm CPUs, vertical scaling, or Pods that run for days. Or it needs more CPU and memory than one Cloud Run instance gives.
3. **GKE Standard.** The workload needs a configuration that Autopilot blocks, for example privileged Pods or Windows Server containers.
4. **Compute Engine.** The workload needs a specific OS, kernel, or license, or it cannot run in a container.

Sources: [Select a managed container runtime environment](https://docs.cloud.google.com/architecture/select-managed-container-runtime-environment), [About GKE modes of operation](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/choose-cluster-mode), [Windows Server containers on GKE](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/windows-server-gke), [Where should I run my stuff?](https://cloud.google.com/blog/topics/developers-practitioners/where-should-i-run-my-stuff-choosing-google-cloud-compute-option).

Organizational factors also count. Google lists the IT strategy, the existing tools (for example Argo CD, Gatekeeper, or Helm), the team's Kubernetes skills, and the operations model. A team with no Kubernetes skills gets more from Cloud Run, which has no cluster to create and no control plane upgrades to manage ([Select a managed container runtime environment](https://docs.cloud.google.com/architecture/select-managed-container-runtime-environment), [What is Cloud Run](https://docs.cloud.google.com/run/docs/overview/what-is-cloud-run)).

## Platforms side by side

| | Cloud Run | GKE Autopilot | GKE Standard | Compute Engine |
|---|---|---|---|---|
| You manage | The container and its settings | Pods; Google manages the nodes | Nodes, node pools, and Pods | The VM, the OS, and all software |
| Billing | Per use, rounded up to 100 ms; scale to zero | Cluster fee plus Pod resource requests | Cluster fee plus the node VMs | The VM resources that you provision |
| Inbound protocols | HTTP, HTTP/2, WebSockets, gRPC (services) | HTTP and other protocols, through Kubernetes Services | HTTP and other protocols, through Kubernetes Services | HTTP and other protocols; you choose the software |
| Local storage | In-memory file system; network file systems by volume mounts | Persistent Disk volumes | Persistent Disk volumes | Persistent Disk, Hyperdisk, Local SSD |
| CPU architecture | x86 only | x86 and Arm | x86 and Arm | x86 and Arm |
| Privileged containers | No | No | Yes | Not applicable |
| Accelerators | GPUs, with limits | GPUs and TPUs | GPUs and TPUs | GPUs (accelerator-optimized machine series) |
| Horizontal scaling | Usually faster than Autopilot: zero to over 10,000 instances in about 10 seconds in a demo | GKE adds nodes for new Pods; extra spare capacity costs more | You plan node pool capacity and configure node scaling | Autoscaling for stateless managed instance groups |

Sources: [Select a managed container runtime environment](https://docs.cloud.google.com/architecture/select-managed-container-runtime-environment), [GKE and Cloud Run](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/gke-and-cloud-run), [Google Kubernetes Engine pricing](https://cloud.google.com/kubernetes-engine/pricing), [GKE Autopilot overview](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/autopilot-overview), [About GKE modes of operation](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/choose-cluster-mode), [Arm workloads on GKE](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/arm-on-gke), [Arm VMs on Compute](https://docs.cloud.google.com/compute/docs/instances/arm-on-compute), [About TPUs in GKE](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/tpus), [Compute Engine overview](https://docs.cloud.google.com/compute/docs/overview), [Choose a Compute Engine deployment strategy for your workload](https://docs.cloud.google.com/compute/docs/choose-compute-deployment-option), [Container runtime contract](https://docs.cloud.google.com/run/docs/container-contract), [Where should I run my stuff?](https://cloud.google.com/blog/topics/developers-practitioners/where-should-i-run-my-stuff-choosing-google-cloud-compute-option).

Google sums up the split for each platform. GKE is best for complex microservices, stateful apps, custom infrastructure or network configuration, and deep Kubernetes control. Cloud Run is best for event-driven apps, stateless web services, APIs, batch jobs, and work that benefits from pay-per-use pricing ([GKE and Cloud Run](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/gke-and-cloud-run)).

## Choosing the Cloud Run resource type

Pick the resource type from how the work starts and how long it runs.

| | Service | Job | Worker pool | Function |
|---|---|---|---|---|
| Use for | Websites, APIs, microservices, event receivers | Scripts, data processing, migrations, scheduled work | Pull consumers for Kafka, Pub/Sub, or RabbitMQ | Single-purpose, event-driven code |
| Started by | HTTP or gRPC requests, Eventarc events | Manual execution, Cloud Scheduler, Workflows | Always on | HTTP requests or events |
| Endpoint | Stable `run.app` URL | No public endpoint | None; private IP ingress through Direct VPC | `run.app` URL |
| Scaling | Automatic on requests, or manual | Number of tasks; tasks can run in parallel | Manual instance count, or autoscaling with external metrics | Same as a service |
| Time limit | Request timeout, up to 60 minutes | Task timeout, up to 168 hours (7 days) | None; it runs until you stop it | Up to 60 minutes for HTTP functions |
| Billing | Request-based or instance-based | Per execution duration | Per instance duration | Same as a service |

Sources: [Deployment options and resource model](https://docs.cloud.google.com/run/docs/resource-model), [What is Cloud Run](https://docs.cloud.google.com/run/docs/overview/what-is-cloud-run), [Configure request timeout for services](https://docs.cloud.google.com/run/docs/configuring/request-timeout), [Set task timeout for jobs](https://docs.cloud.google.com/run/docs/configuring/task-timeout), [Deploy worker pools to Cloud Run](https://docs.cloud.google.com/run/docs/deploy-worker-pools), [Compare Cloud Run functions](https://docs.cloud.google.com/run/docs/functions/comparison).

Points that the exam tests about each type:

- **Services.** A service scales to 1,000 instances, or more with a quota increase. Use the maximum instances setting to protect costs or a downstream system ([What is Cloud Run](https://docs.cloud.google.com/run/docs/overview/what-is-cloud-run)). A request that runs longer than 15 minutes needs retries and idempotent code, because the connection can break ([Configure request timeout for services](https://docs.cloud.google.com/run/docs/configuring/request-timeout)).
- **Jobs.** A job execution succeeds only when all its tasks succeed. Cloud Run retries a failed task up to the `maxRetries` value. By default, up to 100 tasks run in parallel; lower this value to protect a database ([Deployment options and resource model](https://docs.cloud.google.com/run/docs/resource-model)). Google recommends retries for all jobs, and especially for long tasks, because a long task is more likely to fail. During a maintenance event, Cloud Run moves running tasks to another machine, and outbound VPC connections break ([Set task timeout for jobs](https://docs.cloud.google.com/run/docs/configuring/task-timeout)).
- **Worker pools.** A worker pool has no URL and no request-based autoscaling. Its container does not have to listen on a port ([Deployment options and resource model](https://docs.cloud.google.com/run/docs/resource-model)). With Direct VPC ingress, the container must listen for TCP connections on the port that the image exposes or that `PORT` sets. Only resources in the VPC network can connect to the worker pool ([Container runtime contract](https://docs.cloud.google.com/run/docs/container-contract)). If you set the minimum instances to 0, the worker pool does not start ([What is Cloud Run](https://docs.cloud.google.com/run/docs/overview/what-is-cloud-run)).
- **Functions.** Cloud Run builds the function into a container and deploys it as a service. So the function gets service features such as Direct VPC, GPUs, and volume mounts. Create new functions with the Cloud Run Admin API, which Google recommends ([Compare Cloud Run functions](https://docs.cloud.google.com/run/docs/functions/comparison)).

| | Cloud Run functions | Cloud Run functions (1st gen) |
|---|---|---|
| Former name | Cloud Functions (2nd gen) | Cloud Functions (1st gen) |
| Request timeout | Up to 60 minutes (HTTP); up to 9 minutes (event-driven, created with the Cloud Functions v2 API) | Up to 9 minutes |
| Instance size | Up to 16 GiB with 4 vCPU | Up to 8 GB with 2 vCPU |
| Concurrency | Up to 1,000 requests per instance | 1 request per instance |
| Traffic splitting | Supported | Not supported |

Source: [Compare Cloud Run functions](https://docs.cloud.google.com/run/docs/functions/comparison).

## When the answer is GKE

The select guide lists the technical reasons to leave Cloud Run for GKE Autopilot ([Select a managed container runtime environment](https://docs.cloud.google.com/architecture/select-managed-container-runtime-environment)):

- **Control.** Autopilot gives more settings inside the Pod, for example quality of service, lifecycle handlers, and process namespace sharing. Cloud Run supports only a subset of the Pod API.
- **Networking between services.** Autopilot gives namespaces, network policies, cluster DNS, and the Gateway API. Use it for many services with complex traffic rules between them.
- **State.** Autopilot supports Kubernetes volumes on Persistent Disk, so it can run a self-managed database. Cloud Run has an in-memory file system that uses the instance memory.
- **Run time.** Autopilot Pods can run for up to seven days when you protect them from eviction. Use Autopilot for long-lived work and for batch tasks that exceed the Cloud Run task timeout.
- **Hardware.** Autopilot supports Arm nodes, GPUs, and TPUs, and larger CPU and memory requests than Cloud Run. Cloud Run supports GPUs with limits and no Arm.
- **Vertical scaling.** An app that cannot scale by adding instances fits Autopilot. Autopilot can change the CPU and memory of a workload without more instances.
- **Multi-tenancy.** Complex tenant structures need Kubernetes role-based access control (RBAC).

Kubernetes also answers the protocol question. A Kubernetes Service of type `LoadBalancer` on Autopilot creates a regional external passthrough Network Load Balancer, for example for a public email server ([GKE Autopilot overview](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/autopilot-overview)). For load balancer choices, see [Choosing a load balancer and session affinity](note:1.1-load-balancing).

### Autopilot or Standard

| Use Autopilot when | Use Standard when |
|---|---|
| You want Google to manage nodes, scaling, and security settings | The workload needs privileged Pods or node settings that Autopilot blocks |
| You want to pay for Pod resource requests, not for nodes | You run Windows Server containers |
| You want an SLA that covers the control plane and the Pod compute | You need direct control over node pools and node scaling |

Sources: [About GKE modes of operation](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/choose-cluster-mode), [GKE Autopilot overview](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/autopilot-overview), [Google Kubernetes Engine pricing](https://cloud.google.com/kubernetes-engine/pricing), [Windows Server containers on GKE](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/windows-server-gke).

Standard clusters can also run Autopilot workloads. You select Autopilot mode for a workload with a compute class ([About GKE modes of operation](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/choose-cluster-mode)). For Deployment and Service details, see [Deploying containerized applications to GKE](note:3.2-gke-deployments).

### When not to split an app across GKE and Cloud Run

Google lists three cases where a mix of both platforms is a poor fit ([GKE and Cloud Run](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/gke-and-cloud-run)):

- Tightly coupled microservices with frequent, low-latency calls. Network calls between the platforms add overhead.
- Legacy apps with libraries or configurations that Cloud Run does not support.
- A tight budget with a steady, predictable load. The GKE price per node can cost less than Cloud Run pay-per-use pricing.

## When the answer is Compute Engine

Compute Engine gives you VMs on Google infrastructure. You choose Linux or Windows images, predefined or custom machine types, and Hyperdisk, Persistent Disk, or Local SSD storage ([Compute Engine overview](https://docs.cloud.google.com/compute/docs/overview)). Choose it when the OS, the kernel, or a software license is a requirement. Google's examples are Windows-based apps, genomics processing, and SAP HANA ([Where should I run my stuff?](https://cloud.google.com/blog/topics/developers-practitioners/where-should-i-run-my-stuff-choosing-google-cloud-compute-option)). That 2021 post uses old names such as Cloud Functions and Anthos.

For a group of identical VMs, use a managed instance group (MIG). Use a regional MIG when the app must keep running during a zone failure ([Choose a Compute Engine deployment strategy for your workload](https://docs.cloud.google.com/compute/docs/choose-compute-deployment-option)). For zone and region failover, see [Regions, zones, latency, and replication for failover](note:1.1-regions-and-replication).

## Long-running, stateful, and non-HTTP work

| Requirement | Use | Reason |
|---|---|---|
| A stateless HTTP API with spiky traffic | Cloud Run service | Scales out fast and to zero |
| Work after the HTTP response returns | Cloud Run with instance-based billing, or Cloud Tasks | Request-based billing gives CPU only during requests |
| A request that runs more than 60 minutes | A Cloud Run job, or GKE | The request timeout maximum is 60 minutes |
| A batch task of up to 7 days | Cloud Run job | The task timeout maximum is 168 hours |
| A continuous Kafka or Pub/Sub pull consumer | Cloud Run worker pool | No endpoint and no request-based scaling |
| A self-managed database on a persistent disk | GKE Autopilot | Cloud Run has no persistent local file system |
| A public TCP or UDP server, for example email | GKE (`LoadBalancer` Service) or Compute Engine | Cloud Run services accept only HTTP-family protocols |
| Kubernetes APIs, custom resources, or Helm | GKE Autopilot | Cloud Run does not support Kubernetes |
| GPU inference that scales to zero | Cloud Run service with a GPU | One GPU per instance; instance-based billing is required |
| A specific OS, kernel, or license | Compute Engine | You control the full VM |

## App Engine

App Engine runs apps in the standard environment and the flexible environment. For new Google Cloud users, Google recommends Cloud Run as the preferred alternative to App Engine. Google also recommends that you evaluate Cloud Run for new projects, and that you use Cloud Run to modernize existing apps ([Choose an App Engine environment](https://docs.cloud.google.com/appengine/docs/the-appengine-environments)). Treat App Engine as an option only for an app that already runs there.

An AWS habit to drop: Lambda provisions one instance for each concurrent request. A Cloud Run instance serves many requests at the same time, and the requests share its CPU and memory, which you pay for once. Lambda behavior equals a Cloud Run concurrency of 1. Cloud Run also accepts gRPC connections, which Lambda does not support ([Migrate from AWS Lambda to Cloud Run](https://docs.cloud.google.com/architecture/migrate-aws-lambda-to-cloudrun)).

## Exam traps

- **GKE for a plain stateless API.** If nothing needs Kubernetes, the Google answer is Cloud Run. Kubernetes adds complexity ([Select a managed container runtime environment](https://docs.cloud.google.com/architecture/select-managed-container-runtime-environment)).
- **GKE Standard as the default.** Autopilot is the recommended mode. Choose Standard only for a configuration that Autopilot blocks ([About GKE modes of operation](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/choose-cluster-mode)).
- **A public TCP server on Cloud Run.** Cloud Run services accept HTTP, HTTP/2, WebSockets, and gRPC only. A worker pool accepts only private traffic through Direct VPC ([Is my app a good fit for a Cloud Run service?](https://docs.cloud.google.com/run/docs/fit-for-run), [Deployment options and resource model](https://docs.cloud.google.com/run/docs/resource-model)).
- **Files that must survive a restart on Cloud Run.** The file system is in memory and disposable. Write the data to Cloud Storage or to a network file system ([What is Cloud Run](https://docs.cloud.google.com/run/docs/overview/what-is-cloud-run)).
- **An Arm image on Cloud Run.** Cloud Run does not support Arm. Use Autopilot ([Select a managed container runtime environment](https://docs.cloud.google.com/architecture/select-managed-container-runtime-environment)).
- **Windows containers on Autopilot.** Windows Server containers need a Standard cluster ([Windows Server containers on GKE](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/windows-server-gke)).
- **A two-hour HTTP request.** The maximum request timeout is 60 minutes. Use a Cloud Run job, where a task can run for up to 168 hours ([Configure request timeout for services](https://docs.cloud.google.com/run/docs/configuring/request-timeout), [Set task timeout for jobs](https://docs.cloud.google.com/run/docs/configuring/task-timeout)).
- **A Cloud Run job for an HTTP endpoint.** Jobs have no public endpoint and get no inbound traffic. They run tasks to completion ([Deployment options and resource model](https://docs.cloud.google.com/run/docs/resource-model)).
- **App Engine for a new app.** Google recommends Cloud Run for new users ([Choose an App Engine environment](https://docs.cloud.google.com/appengine/docs/the-appengine-environments)).
- **"Cloud Functions" in an older question.** The current name is Cloud Run functions, and the function is a Cloud Run service ([Compare Cloud Run functions](https://docs.cloud.google.com/run/docs/functions/comparison)).
