## Why it matters

A pipeline must stop a bad change before users see it. In Cloud Build, each test is a build step, and a failed step stops the build before the deploy steps run. The exam tests how to order test steps and how to give tests their dependencies and secrets. It also tests how to check a new Cloud Run revision before it gets traffic, and how to run tests on pull requests.

## Key points

- A build config can fetch dependencies and run unit tests, static analysis, and integration tests before it creates artifacts ([Overview of Cloud Build](https://docs.cloud.google.com/build/docs/overview)).
- Each build step runs as a container. By default, the steps run one after another on the same machine ([Build configuration file schema](https://docs.cloud.google.com/build/docs/build-config-file-schema)).
- A step without `waitFor` waits until all earlier steps complete successfully. `waitFor: ['-']` starts a step when the build starts ([Configuring the order of build steps](https://docs.cloud.google.com/build/docs/configuring-builds/configure-build-step-order)).
- When a step fails, the build status is `FAILURE`. Running steps become `CANCELLED`, and steps that did not start stay `QUEUED` ([View build results](https://docs.cloud.google.com/build/docs/view-build-results)).
- If a step has `allowFailure: true`, a failure of that step does not fail the build ([Build configuration file schema](https://docs.cloud.google.com/build/docs/build-config-file-schema)).
- Cloud Build attaches each step's container to a local Docker network named `cloudbuild` ([Build configuration file schema](https://docs.cloud.google.com/build/docs/build-config-file-schema)).
- The `artifacts.objects` field uploads files, such as JUnit XML test reports, to Cloud Storage after all build steps succeed ([Build configuration file schema](https://docs.cloud.google.com/build/docs/build-config-file-schema), [Build and test Python applications](https://docs.cloud.google.com/build/docs/building/build-python)).
- A build reads Secret Manager secrets through `availableSecrets` and the `secretEnv` field of a step. The build service account needs the Secret Manager Secret Accessor role ([Use secrets from Secret Manager](https://docs.cloud.google.com/build/docs/securing-builds/use-secrets)).
- `gcloud run deploy --no-traffic --tag TAG` creates a revision that serves no traffic and has its own URL for tests ([Rollbacks, gradual rollouts, and traffic migration](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration)).
- To get ID tokens in a build, use a user-specified service account. Cloud Build does not generate ID tokens with the default service account ([Authorize service-to-service access](https://docs.cloud.google.com/build/docs/securing-builds/authorize-service-to-service-access)).
- A pull request trigger can wait for an owner or collaborator to comment `/gcbrun` before it runs a build ([Building repositories from GitHub](https://docs.cloud.google.com/build/docs/automating-builds/github/build-repos-from-github)).
- Cloud Deploy can run your test containers after a deployment. If the verification fails, the rollout fails ([Verify your deployment](https://docs.cloud.google.com/deploy/docs/verify-deployment)).

## Order the test steps

Steps run serially by default. Give a step an `id`, and list that `id` in the `waitFor` field of a later step. A step starts only after every step in its `waitFor` list completes successfully. Steps that depend on the same steps run at the same time ([Configuring the order of build steps](https://docs.cloud.google.com/build/docs/configuring-builds/configure-build-step-order)).

In this example, the Go steps run the tests in order. The `fetch-resources` step starts at the same time as the first Go step. The `docker` step starts only after the install step and the copy step finish:

```yaml
steps:
- name: 'gcr.io/cloud-builders/go'
  args: ['generate']
- name: 'gcr.io/cloud-builders/go'
  args: ['test', './...']
- name: 'gcr.io/cloud-builders/go'
  args: ['install', 'mytarget']
  id: 'go-install'
- name: 'gcr.io/cloud-builders/gcloud'
  args: ['storage', 'cp', '-r', './somefiles', 'gs://my-resource-bucket/somefiles']
  waitFor: ['-']  # The '-' indicates that this step begins immediately.
  id: 'fetch-resources'
- name: 'gcr.io/cloud-builders/docker'
  args: ['build', '-t', 'gcr.io/$PROJECT_ID/mytarget', '.']
  waitFor: ['go-install', 'fetch-resources']
```

Source: [Configuring the order of build steps](https://docs.cloud.google.com/build/docs/configuring-builds/configure-build-step-order).

The example tags the image with a Container Registry path. Container Registry is shut down, so use an Artifact Registry path for new images ([Transition from Container Registry](https://docs.cloud.google.com/artifact-registry/docs/transition/transition-from-gcr)).

Fields that control a test step:

| Field | What it does |
|---|---|
| `id` and `waitFor` | Set the order. A step waits for every `id` in its `waitFor` list. You must define an `id` before you use it in `waitFor` |
| `waitFor: ['-']` | Starts the step when the build starts |
| `allowFailure: true` | The build succeeds even if this step fails. If all steps have it and all fail, the build status is still successful |
| `allowExitCodes` | The build ignores a failure of this step only for the listed exit codes, up to 255. It takes precedence over `allowFailure` |
| Step `timeout` | A time limit for one step. It must not be more than the build timeout |
| Build `timeout` | The default is 60 minutes and the maximum is 24 hours. When the time ends, the build status is `TIMEOUT` |

Sources: [Configuring the order of build steps](https://docs.cloud.google.com/build/docs/configuring-builds/configure-build-step-order), [Build configuration file schema](https://docs.cloud.google.com/build/docs/build-config-file-schema).

A failed or timed-out step fails the build. Steps that succeeded before the failure are `SUCCESS`. Steps that were running are `CANCELLED`. Steps that did not start stay `QUEUED`. A step that fails with a permitted exit code is marked as failed, but the build is `SUCCESS` ([View build results](https://docs.cloud.google.com/build/docs/view-build-results)). Because of this, a test step with no `allowFailure` and no `allowExitCodes` stops every deploy step that waits for it. In the API, a failed build or step has the status `FAILURE` ([REST Resource: projects.builds](https://docs.cloud.google.com/build/docs/api/reference/rest/v1/projects.builds)).

## Run the tests and keep the report

The language guides put the unit tests in a step before the build step. The Python guide writes a JUnit XML report and uploads it to Cloud Storage:

```yaml
steps:
- name: python
  entrypoint: python
  args: ['-m', 'pip', 'install', 'build', 'pytest', 'Flask', '--user']
- name: 'python'
  entrypoint: 'python'
  args: ['-m', 'pytest', '--junitxml=${SHORT_SHA}_test_log.xml']
- name: 'python'
  entrypoint: 'python'
  args: ['-m', 'build']
artifacts:
  objects:
    location: 'gs://${_BUCKET_NAME}/'
    paths:
    - '${SHORT_SHA}_test_log.xml'
```

Source: [Build and test Python applications](https://docs.cloud.google.com/build/docs/building/build-python).

- **Installed modules.** The `--user` flag of `pip install` lets later build steps use the modules that the install step installs ([Build and test Python applications](https://docs.cloud.google.com/build/docs/building/build-python)).
- **Permissions.** Grant the build service account the Storage Object Creator role on the bucket ([Build and test Python applications](https://docs.cloud.google.com/build/docs/building/build-python)).
- **Upload time.** Cloud Build uploads `artifacts` only after all build steps succeed. Then it writes a manifest at `LOCATION/artifacts-$BUILD_ID.json` ([Build configuration file schema](https://docs.cloud.google.com/build/docs/build-config-file-schema), [Storing build artifacts in Cloud Storage](https://docs.cloud.google.com/build/docs/building/store-artifacts-in-cloud-storage)). For a failed build, read the log of the failed step on the build details page ([View build results](https://docs.cloud.google.com/build/docs/view-build-results)).
- **File names.** An upload replaces an object with the same name, unless the bucket has Object Versioning ([Storing build artifacts in Cloud Storage](https://docs.cloud.google.com/build/docs/building/store-artifacts-in-cloud-storage)). Triggers set `$SHORT_SHA`, but `gcloud builds submit` does not ([Build and test Go applications](https://docs.cloud.google.com/build/docs/building/build-go)).
- **Other languages.** Node.js runs `npm test`. Java runs `mvn test`, and `mvn package` runs the tests again unless you add `-Dmaven.test.skip=true` ([Build and test Node.js applications](https://docs.cloud.google.com/build/docs/building/build-nodejs), [Build and test Java applications](https://docs.cloud.google.com/build/docs/building/build-java)).
- **Several runtime versions.** Make the image version a substitution, for example `node:$_NODE_VERSION`. Then create one trigger for each version ([Build and test Node.js applications](https://docs.cloud.google.com/build/docs/building/build-nodejs)).

For unit tests that an AI assistant writes, see [Writing unit tests with AI coding assistants](note:2.3-unit-tests-with-ai).

## Dependencies for integration tests

An integration test calls a real dependency, such as a database or an emulator. The docs describe these ways to provide one in a build:

| Dependency | How the docs run it | Notes |
|---|---|---|
| Firebase emulators: Firestore, Realtime Database, Pub/Sub, Functions, Hosting | `firebase emulators:exec SCRIPT` | Starts the emulators, runs the script, and stops the emulators. The Firebase docs call it more appropriate for continuous integration |
| Spanner emulator | The container image `gcr.io/cloud-spanner-emulator/emulator` | Port 9010 for gRPC and port 9020 for REST |
| Several containers together | The community `docker-compose` builder, which runs integration tests on Docker images | No prebuilt image. You build it from the community repository. Cloud Build does not maintain it |
| A Cloud SQL test instance with public IP | The Cloud SQL Auth Proxy, started in the background in the same step as the test command | The build service account needs the Cloud SQL Client role |
| A Cloud SQL test instance with private IP | A direct TCP connection to the private IP address and port, without the Cloud SQL Auth Proxy | Run the build in a private pool that is in the VPC network of the instance |

Sources: [Install, configure and integrate Local Emulator Suite](https://firebase.google.com/docs/emulator-suite/install_and_configure), [Emulate Spanner locally](https://docs.cloud.google.com/spanner/docs/emulator), [Cloud builders](https://docs.cloud.google.com/build/docs/cloud-builders), [Connect from Cloud Build](https://docs.cloud.google.com/sql/docs/postgres/connect-build).

Every step's container joins the `cloudbuild` network, which also hosts Application Default Credentials. If a step starts nested Docker containers, add `--network=cloudbuild` so that they can use those credentials ([Build configuration file schema](https://docs.cloud.google.com/build/docs/build-config-file-schema)). Files in `/workspace` stay available to later steps ([Build configuration file schema](https://docs.cloud.google.com/build/docs/build-config-file-schema)). For emulator start commands and environment variables, see [Emulating Google Cloud services for local development and unit tests](note:2.1-emulators).

In the Cloud SQL sample, an earlier step saves the proxy binary to `/workspace`. The `migrate` step starts the proxy in the background and then runs its command. Put your test command where the sample runs `migrate.py`:

```yaml
- id: migrate
  waitFor: ['install-proxy']
  name: YOUR_CONTAINER_IMAGE_NAME
  entrypoint: sh
  env:
  - "DATABASE_NAME=${_DATABASE_NAME}"
  - "DATABASE_USER=${_DATABASE_USER}"
  - "DATABASE_PORT=${_DATABASE_PORT}"
  - "INSTANCE_CONNECTION_NAME=${_INSTANCE_CONNECTION_NAME}"
  secretEnv:
  - DATABASE_PASS
  args:
  - "-c"
  - |
    /workspace/cloud-sql-proxy ${_INSTANCE_CONNECTION_NAME} --port ${_DATABASE_PORT} & sleep 2;
    # Cloud SQL Proxy is now up and running, add your own logic below to connect
    python migrate.py # For example
availableSecrets:
  secretManager:
  - versionName: projects/$PROJECT_ID/secrets/${_DATABASE_PASSWORD_KEY}/versions/latest
    env: "DATABASE_PASS"
```

Source: [Connect from Cloud Build](https://docs.cloud.google.com/sql/docs/postgres/connect-build).

## Test a new Cloud Run revision before it gets traffic

The Cloud Run docs give this sequence. Run integration tests during development. Deploy to a staging project with no traffic, and test the tagged revision. Then deploy to production with no traffic, test the tagged revision again, and migrate traffic ([Rollbacks, gradual rollouts, and traffic migration](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration)).

```bash
gcloud run deploy myservice --image IMAGE_URL --no-traffic --tag TAG_NAME
gcloud run services update-traffic myservice --to-tags TAG_NAME=TRAFFIC_PERCENT
gcloud run services update-traffic SERVICE --remove-tags TAG_NAME
```

Source: [Rollbacks, gradual rollouts, and traffic migration](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration).

1. **Deploy.** The tag name must be lowercase. The test URL starts with the tag, for example `https://green---myservice-abcdef.a.run.app` ([Rollbacks, gradual rollouts, and traffic migration](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration)).
2. **Test.** A later build step sends requests to the tag URL. If a test fails, the build fails, and the traffic step does not run ([View build results](https://docs.cloud.google.com/build/docs/view-build-results)).
3. **Promote.** Send traffic to the tag, all at once or in percentages. Remove the tag when you no longer need it ([Rollbacks, gradual rollouts, and traffic migration](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration)).

For a private service, the build must send an ID token:

- Run the build as a user-specified service account. Grant it the Service Account OpenID Connect Identity Token Creator role (`roles/iam.serviceAccountOpenIdTokenCreator`) ([Authorize service-to-service access](https://docs.cloud.google.com/build/docs/securing-builds/authorize-service-to-service-access)).
- Grant that service account the Cloud Run Invoker role (`roles/run.invoker`) on the service ([Authenticating service-to-service](https://docs.cloud.google.com/run/docs/authenticating/service-to-service)).
- Set the token audience to the URL of the service, not the tag URL. Without a custom audience, the audience must stay the service URL, also for requests to a traffic tag ([Authenticating service-to-service](https://docs.cloud.google.com/run/docs/authenticating/service-to-service)).

```yaml
steps:
- name: 'gcr.io/cloud-builders/gcloud'
  script: 'gcloud auth print-identity-token --audiences ${_TOKEN_AUDIENCE} > /workspace/identity_token.txt'
  env:
  - _TOKEN_AUDIENCE=${_TOKEN_AUDIENCE}
service_account: '$_SERVICE_ACCOUNT'
substitutions:
  _TOKEN_AUDIENCE: 'TOKEN_AUDIENCE'
  _SERVICE_ACCOUNT_ID: 'SERVICE_ACCOUNT_ID'
  _SERVICE_ACCOUNT: 'projects/${PROJECT_ID}/serviceAccounts/${_SERVICE_ACCOUNT_ID}'
logsBucket: 'LOGS_BUCKET_LOCATION'
options:
  logging: GCS_ONLY
  dynamic_substitutions: true
```

Source: [Authorize service-to-service access](https://docs.cloud.google.com/build/docs/securing-builds/authorize-service-to-service-access).

A build with a user-specified service account cannot use the Google-owned log bucket. Set `logging: CLOUD_LOGGING_ONLY`, or set `logging: GCS_ONLY` and a `logsBucket` in your project ([Configure user-specified service accounts](https://docs.cloud.google.com/build/docs/securing-builds/configure-user-specified-service-accounts)). The test step reads the token from `/workspace` and sends it in the `Authorization: Bearer` header ([Authenticating service-to-service](https://docs.cloud.google.com/run/docs/authenticating/service-to-service)). For traffic splits and gradual rollouts, see [Traffic splitting: gradual rollouts, rollbacks, and A/B tests](note:1.1-traffic-splitting). For ID tokens between services, see [Secure service-to-service communication](note:1.2-service-to-service).

## Secrets in builds

Store passwords and API keys in Secret Manager, and let the build read them at run time ([Use secrets from Secret Manager](https://docs.cloud.google.com/build/docs/securing-builds/use-secrets)):

```yaml
steps:
- name: python:slim
  entrypoint: python
  args: ['main.py']
  secretEnv: ['MYSECRET']
availableSecrets:
  secretManager:
  - versionName: projects/$PROJECT_ID/secrets/mySecret/versions/latest
    env: 'MYSECRET'
```

Source: [Use secrets from Secret Manager](https://docs.cloud.google.com/build/docs/securing-builds/use-secrets).

- **Grant access to the secret.** Give the build service account the Secret Manager Secret Accessor role on the secret ([Use secrets from Secret Manager](https://docs.cloud.google.com/build/docs/securing-builds/use-secrets)).
- **Use the variable in a step.** List it in `secretEnv`. To use it in `args`, set `entrypoint: 'bash'`, pass `-c`, and write the variable with `$$`, for example `$$PASSWORD`. You can refer to secrets only in the `args` field ([Use secrets from Secret Manager](https://docs.cloud.google.com/build/docs/securing-builds/use-secrets)).
- **Binary secrets.** For a secret that is not UTF-8, a step runs `gcloud secrets versions access` and writes the value to a file ([Use secrets from Secret Manager](https://docs.cloud.google.com/build/docs/securing-builds/use-secrets)).
- **Avoid Cloud KMS in the config.** `availableSecrets.inline` with Cloud KMS exposes sensitive data in the build config file. Google strongly recommends Secret Manager instead. Use `availableSecrets`, not the older `secrets` field ([Build configuration file schema](https://docs.cloud.google.com/build/docs/build-config-file-schema)).
- **Legacy service account risk.** A trigger can run as the legacy Cloud Build service account. Then any user who can run that trigger can use its secret access ([Use secrets from Secret Manager](https://docs.cloud.google.com/build/docs/securing-builds/use-secrets)).

For secret versions, rotation, and Cloud KMS, see [Secrets, credentials, and keys](note:1.2-secrets-and-keys).

## Pull request triggers

A GitHub trigger with the **Pull request** event starts a build on commits to a pull request ([Building repositories from GitHub](https://docs.cloud.google.com/build/docs/automating-builds/github/build-repos-from-github)):

```bash
gcloud builds triggers create github --name="my-trigger" \
  --repository=projects/my-project/locations/us-central1/connections/my-conn/repositories/my-repo \
  --pull-request-pattern="^master$" --build-config="cloudbuild.yaml" --region=us-central1
```

Source: [gcloud builds triggers create github](https://docs.cloud.google.com/sdk/gcloud/reference/builds/triggers/create/github).

- **Branch pattern.** `--pull-request-pattern` is an RE2 search on the base branch, the branch that the pull request merges into. The pattern `foo` also matches `foobar` and `barfoo` ([gcloud builds triggers create github](https://docs.cloud.google.com/sdk/gcloud/reference/builds/triggers/create/github)).
- **Comment control.** `COMMENTS_ENABLED` (the gcloud default) needs a `/gcbrun` comment from an owner or collaborator for every pull request. `COMMENTS_ENABLED_FOR_EXTERNAL_CONTRIBUTORS_ONLY` needs it only for outside contributors. `COMMENTS_DISABLED` builds every pull request ([gcloud builds triggers create github](https://docs.cloud.google.com/sdk/gcloud/reference/builds/triggers/create/github)).
- **Untrusted code.** Any user with read access can open a pull request that runs a build with the changed code. For public repositories, Google recommends manual approvals ([Building repositories from GitHub](https://docs.cloud.google.com/build/docs/automating-builds/github/build-repos-from-github)). With `--require-approval`, a user with the Cloud Build Approver role must approve each build ([Gate builds on approval](https://docs.cloud.google.com/build/docs/securing-builds/gate-builds-on-approval)).
- **Results on GitHub.** You see the build result in the **Checks** tab of the repository. Build logs go to GitHub only if the trigger sends them. A required status check can use the trigger name ([Building repositories from GitHub](https://docs.cloud.google.com/build/docs/automating-builds/github/build-repos-from-github)).
- **Closed pull requests.** When you close the pull request, Cloud Build cancels its running builds. A merge does not cancel them ([Building repositories from GitHub](https://docs.cloud.google.com/build/docs/automating-builds/github/build-repos-from-github)).
- **Substitutions.** Pull request builds get `$_HEAD_BRANCH`, `$_BASE_BRANCH`, `$_HEAD_REPO_URL`, and `$_PR_NUMBER` ([Substituting variable values](https://docs.cloud.google.com/build/docs/configuring-builds/substitute-variable-values)).

For trigger types and the trigger service account, see [Building containers with Cloud Build and storing them in Artifact Registry](note:2.2-cloud-build-artifact-registry).

## Verification after deployment with Cloud Deploy

Cloud Deploy can run your test containers on a target after each deployment. Add a `verify` stanza to the stage of the delivery pipeline ([Verify your deployment](https://docs.cloud.google.com/deploy/docs/verify-deployment)):

```yaml
apiVersion: deploy.cloud.google.com/v1
kind: DeliveryPipeline
metadata:
 name: my-demo-app
serialPipeline:
 stages:
 - targetId: dev
   profiles: []
   strategy:
     standard:
       verify:
         tasks:
         - type: container
           image: "VERIFY_IMAGE"
           command: [COMMANDS_TO_RUN]
           args: [LIST_OF_ARGS]
```

Source: [Verify your deployment](https://docs.cloud.google.com/deploy/docs/verify-deployment).

- **Result.** Exit code `0` means success, and any other exit code means failure. If there are several containers, all must succeed. A failed verification fails the rollout ([Verify your deployment](https://docs.cloud.google.com/deploy/docs/verify-deployment)).
- **Where it runs.** By default, verification runs in the Cloud Deploy execution environment. For GKE, you can run it on the application cluster through `skaffold.yaml`. For Cloud Run, it runs only in the execution environment ([Verify your deployment](https://docs.cloud.google.com/deploy/docs/verify-deployment)).
- **Inputs.** Verify jobs get environment variables such as `CLOUD_RUN_SERVICE_URLS` and `CLOUD_RUN_REVISION` ([Verify your deployment](https://docs.cloud.google.com/deploy/docs/verify-deployment)).
- **After a failure.** You can retry the job with `gcloud deploy rollouts retry-job`, ignore it, or terminate a running verify job ([Verify your deployment](https://docs.cloud.google.com/deploy/docs/verify-deployment)).

| AWS | Google Cloud | Difference that matters |
|---|---|---|
| AWS CodeBuild | Cloud Build | Each test is a container step in `cloudbuild.yaml`. A failed step stops the steps that wait for it |
| AWS CodePipeline, AWS CodeDeploy | Cloud Deploy | A `verify` stanza runs your test containers after deployment, and a failed verification fails the rollout |
| AWS Secrets Manager | Secret Manager | A build reads secrets through `availableSecrets` and `secretEnv` |

Sources: [Compare AWS and Azure services to Google Cloud](https://docs.cloud.google.com/docs/get-started/aws-azure-gcp-service-comparison), [Verify your deployment](https://docs.cloud.google.com/deploy/docs/verify-deployment), [Use secrets from Secret Manager](https://docs.cloud.google.com/build/docs/securing-builds/use-secrets).

## Exam traps

- **`allowFailure: true` on a test step.** The build then succeeds when the tests fail, and the deploy steps run ([Build configuration file schema](https://docs.cloud.google.com/build/docs/build-config-file-schema)).
- **`waitFor: ['-']` on an integration test step.** The step starts when the build starts, before the setup steps finish ([Configuring the order of build steps](https://docs.cloud.google.com/build/docs/configuring-builds/configure-build-step-order)).
- **Expecting `artifacts` to upload the report of a failed test run.** Cloud Build uploads artifacts only after all steps succeed ([Build configuration file schema](https://docs.cloud.google.com/build/docs/build-config-file-schema)).
- **A report named with `$SHORT_SHA` from `gcloud builds submit`.** Only triggers set `$SHORT_SHA` ([Build and test Go applications](https://docs.cloud.google.com/build/docs/building/build-go)).
- **Calling a private tagged revision from a build that runs as the default service account.** Cloud Build cannot generate ID tokens with it ([Authorize service-to-service access](https://docs.cloud.google.com/build/docs/securing-builds/authorize-service-to-service-access)).
- **The tag URL as the token audience.** Use the service URL or a custom audience ([Authenticating service-to-service](https://docs.cloud.google.com/run/docs/authenticating/service-to-service)).
- **`$PASSWORD` in `args`.** Write `$$PASSWORD` with a bash entrypoint, and list the variable in `secretEnv` ([Use secrets from Secret Manager](https://docs.cloud.google.com/build/docs/securing-builds/use-secrets)).
- **`--pull-request-pattern=main`.** It also matches `main-old`, because the pattern is a search. Use `^main$` ([gcloud builds triggers create github](https://docs.cloud.google.com/sdk/gcloud/reference/builds/triggers/create/github)).
- **Comment control off on a public repository.** Any user with read access can then run code in your build ([Building repositories from GitHub](https://docs.cloud.google.com/build/docs/automating-builds/github/build-repos-from-github)).
- **Tests against a private IP Cloud SQL instance in the default pool.** Use a private pool in the same VPC network, and connect over TCP without the proxy ([Connect from Cloud Build](https://docs.cloud.google.com/sql/docs/postgres/connect-build)).
- **Cloud Deploy verification on the Cloud Run service itself.** Only GKE can run verify containers on the application cluster ([Verify your deployment](https://docs.cloud.google.com/deploy/docs/verify-deployment)).
