## Why it matters

GKE has several autoscalers, and each one changes a different thing. The Horizontal Pod Autoscaler (HPA) changes the number of Pods, vertical Pod autoscaling changes Pod requests, and the cluster autoscaler or Autopilot changes node capacity. The developer chooses the metric, the target, the replica range, and how fast the HPA scales. The exam tests which autoscaler fits a scenario, why the HPA needs resource requests, and how to scale on a queue backlog.

## Key points

- The HPA changes the number of Pods based on CPU or memory use, custom metrics, or external metrics. It does not change the number of nodes ([Horizontal Pod autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/horizontalpodautoscaler)).
- A utilization target is a percentage of the Pod's requests. If a container has no request for that resource, the HPA takes no action for that metric ([Horizontal Pod autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/horizontalpodautoscaler)).
- The HPA calculates `desiredReplicas = ceil[currentReplicas × currentMetricValue / desiredMetricValue]` ([Horizontal Pod Autoscaling | Kubernetes](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/)).
- With several metrics, the HPA calculates a replica count for each metric and uses the largest one ([Horizontal Pod autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/horizontalpodautoscaler)).
- The HPA ignores changes within a 10% tolerance. In GKE, the scale-down stabilization window is 300 seconds by default ([Horizontal Pod autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/horizontalpodautoscaler)).
- Use the `autoscaling/v2` API. The `autoscaling/v1` API is still supported, but Google no longer recommends it. It does not support scaling to and from zero ([Configuring horizontal Pod autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/horizontal-pod-autoscaling)).
- An external metric comes from outside the cluster. For example, you can scale on any Cloud Monitoring metric, such as a Pub/Sub backlog ([About autoscaling workloads based on metrics](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/custom-and-external-metrics)).
- Google recommends Managed Service for Prometheus to create and manage custom metrics ([About autoscaling workloads based on metrics](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/custom-and-external-metrics)).
- Do not use the HPA and vertical Pod autoscaling together on CPU or memory ([Horizontal Pod autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/horizontalpodautoscaler)).
- The cluster autoscaler adds nodes when Pods cannot be scheduled. It decides from Pod requests, not from actual use ([About GKE cluster autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/cluster-autoscaler)).
- In Autopilot, GKE provisions nodes for the Pods that the HPA adds ([GKE Autopilot overview](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/autopilot-overview)).
- In GKE 1.37 or later, the HPA can scale a workload to zero replicas. It needs at least one External or Object metric, because GKE cannot collect CPU or memory metrics from zero Pods ([Scale GKE workloads to and from zero using HPA](https://docs.cloud.google.com/kubernetes-engine/docs/tutorials/scale-to-from-zero-hpa)).

## Which autoscaler changes what

| Autoscaler | What it changes | What drives it | Use it for |
|---|---|---|---|
| Horizontal Pod Autoscaler | The number of Pods | CPU or memory, custom metrics, external metrics | Load that changes, including sudden spikes |
| Vertical Pod autoscaling | CPU and memory requests and limits | Historical usage | Right-sizing of long-running workloads with steady use |
| Multidimensional Pod autoscaling (Beta) | The number of Pods (on CPU) and memory requests | A CPU target and memory usage | Horizontal and vertical scaling at the same time |
| Cluster autoscaler (Standard) | Nodes in a node pool, between a minimum and a maximum | Requests of Pods that cannot be scheduled | Node capacity for new Pods |
| Autopilot | Nodes and node resources | The Pods in the cluster | Node capacity that Google manages |

Sources: [Horizontal Pod autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/horizontalpodautoscaler), [Vertical Pod autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/verticalpodautoscaler), [Configure multidimensional Pod autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/multidimensional-pod-autoscaling), [About GKE cluster autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/cluster-autoscaler), [GKE Autopilot overview](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/autopilot-overview).

The HPA works best for stateless workers that start fast and shut down gracefully ([Best practices for running cost-optimized Kubernetes applications on GKE](https://docs.cloud.google.com/architecture/best-practices-for-running-cost-effective-kubernetes-applications-on-gke)). For workload sizing in general, see [Resources and cost](note:1.1-resources-and-cost).

## The HPA manifest

The HPA needs requests in the Deployment for a utilization target. Without requests, you can scale only on an absolute value, such as millicores of CPU ([Configuring horizontal Pod autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/horizontal-pod-autoscaling)). The Deployment in the GKE sample sets a CPU request:

```yaml
    spec:
      containers:
      - name: nginx
        image: nginx:1.7.9
        resources:
          # You must specify requests for CPU to autoscale
          # based on CPU utilization
          requests:
            cpu: "250m"
```

Source: [Configuring horizontal Pod autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/horizontal-pod-autoscaling).

This HPA keeps the average CPU utilization near 50% of the request, with 1 to 10 replicas:

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: nginx
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: nginx
  minReplicas: 1
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 50
```

Source: [Configuring horizontal Pod autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/horizontal-pod-autoscaling).

For average CPU only, one command creates the same object: `kubectl autoscale deployment nginx --cpu-percent=50 --min=1 --max=10` ([Configuring horizontal Pod autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/horizontal-pod-autoscaling)).

| Field | What to know |
|---|---|
| `scaleTargetRef` | Point it at the Deployment, not at the ReplicaSet behind it. You cannot autoscale a DaemonSet |
| `minReplicas`, `maxReplicas` | The replica range. `minReplicas: 0` needs GKE 1.37 or later |
| `metrics[].type` | `Resource` (CPU or memory), `Pods` (a custom metric for each Pod), `Object` (a metric of another object, such as a Service), or `External` |
| `target.type` | `Utilization` is a percentage of requests. `AverageValue` is an average across the Pods |
| `behavior` | Scale-up and scale-down policies and stabilization windows. It needs the `v2` API |

Sources: [Horizontal Pod autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/horizontalpodautoscaler), [Configuring horizontal Pod autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/horizontal-pod-autoscaling), [Horizontal Pod Autoscaling | Kubernetes](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/).

Rules that questions can test:

- The HPA manages the `replicas` field of the Deployment, also during a rolling update ([Horizontal Pod Autoscaling | Kubernetes](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/)).
- Remove `spec.replicas` from the Deployment manifest when an HPA is on. If you keep it, each `kubectl apply` sets the Pod count back to that value ([Horizontal Pod Autoscaling | Kubernetes](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/)).
- When you delete an HPA, the replica count stays the same. The Deployment does not go back to its earlier size ([Configuring horizontal Pod autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/horizontal-pod-autoscaling)).
- Use `kubectl get hpa` and `kubectl describe hpa HPA_NAME` to see the HPA state and events ([Horizontal Pod autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/horizontalpodautoscaler), [Configuring horizontal Pod autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/horizontal-pod-autoscaling)).

## The scaling algorithm

The HPA is a control loop. By default, it runs every 15 seconds ([Horizontal Pod Autoscaling | Kubernetes](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/)). On each run, it compares the current metric value with the target:

`desiredReplicas = ceil[currentReplicas × currentMetricValue / desiredMetricValue]`

If the current value is `200m` and the target is `100m`, the replica count doubles. If the current value is `50m`, the count halves. If the ratio is within the tolerance (0.1 by default) of 1.0, the HPA does nothing ([Horizontal Pod Autoscaling | Kubernetes](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/)). For example, 4 replicas at 80% average CPU utilization with a 50% target give ceil(4 × 80 / 50) = ceil(6.4) = 7 replicas.

The algorithm is careful with incomplete data ([Horizontal Pod Autoscaling | Kubernetes](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/)):

- For a Pod with missing metrics, the HPA assumes 100% of the target on a scale-down and 0% on a scale-up. This makes the change smaller.
- For Pods that are not yet ready, the HPA assumes 0% use when it scales up.
- If a Pod uses much CPU at startup, configure a startup probe that passes only after the spike. Or make the readiness probe report ready only after the spike. See [Kubernetes health checks](note:3.2-health-checks).

With several metrics, the HPA uses the largest result. If a metric is not available, the HPA can still scale up, but it does not scale down ([Horizontal Pod autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/horizontalpodautoscaler)).

**Choose a target with a buffer.** Google's example sets 70% CPU utilization, which leaves a 30% buffer while new Pods start. Make the buffer large enough to handle requests for two or three minutes of a spike. New nodes and CPU throttling add delay ([Best practices for running cost-optimized Kubernetes applications on GKE](https://docs.cloud.google.com/architecture/best-practices-for-running-cost-effective-kubernetes-applications-on-gke)).

## Behavior: how fast the HPA scales

The `behavior` field sets separate rules for scale-up and scale-down. These are the default values:

```yaml
behavior:
  scaleDown:
    stabilizationWindowSeconds: 300
    policies:
    - type: Percent
      value: 100
      periodSeconds: 15
  scaleUp:
    stabilizationWindowSeconds: 0
    policies:
    - type: Percent
      value: 100
      periodSeconds: 15
    - type: Pods
      value: 4
      periodSeconds: 15
    selectPolicy: Max
```

Source: [Horizontal Pod Autoscaling | Kubernetes](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/).

| Setting | What it does |
|---|---|
| `policies` | Limit the change in one period: a number of Pods (`Pods`) or a percentage of current replicas (`Percent`). `periodSeconds` can be up to 1800 |
| `selectPolicy` | `Max` (default) uses the policy that allows the largest change. `Min` uses the smallest. `Disabled` stops scaling in that direction |
| `stabilizationWindowSeconds` | For scale-down, the HPA uses the highest recommendation in the window. This stops the replica count from moving up and down too often |
| `tolerance` | Ignores metric changes below the value that you set. Without it, the cluster default of 10% applies. The field is stable from Kubernetes 1.37 |

Sources: [Horizontal Pod Autoscaling | Kubernetes](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/).

With the defaults, a scale-up happens at once. The HPA can add 4 Pods or 100% of the current Pods every 15 seconds, whichever is more. A scale-down considers all recommendations from the last 5 minutes ([Horizontal Pod Autoscaling | Kubernetes](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/)). In this example, the HPA removes at most 4 Pods or 10% of the Pods each minute, whichever is more:

```yaml
behavior:
  scaleDown:
    policies:
    - type: Pods
      value: 4
      periodSeconds: 60
    - type: Percent
      value: 10
      periodSeconds: 60
```

Source: [Horizontal Pod Autoscaling | Kubernetes](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/).

## Custom and external metrics

Any metric that the workload emits, or that you can read from an outside source, can drive the HPA. GKE has built-in support for custom and external metrics in many cases. Kubernetes also supports adapters such as KEDA and the Prometheus adapter ([Configuring horizontal Pod autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/horizontal-pod-autoscaling)).

| Metric kind | Where the value comes from | Example | HPA `type` |
|---|---|---|---|
| Resource | The resource metrics API, usually from Metrics Server | CPU, memory | `Resource` |
| Custom | An app in the cluster. Managed Service for Prometheus metrics count as custom metrics | Requests per second, a Prometheus gauge | `Pods` |
| External | A service outside the cluster, through Cloud Monitoring | Undelivered messages in a Pub/Sub subscription | `External` |
| Load balancer traffic | A Gateway load balancer, on GKE 1.31 or later | Fullness of the Service capacity | `Object` |

Sources: [Horizontal Pod Autoscaling | Kubernetes](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/), [Horizontal Pod autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/horizontalpodautoscaler), [About autoscaling workloads based on metrics](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/custom-and-external-metrics), [Optimize Pod autoscaling based on metrics](https://docs.cloud.google.com/kubernetes-engine/docs/tutorials/autoscaling-metrics), [Configuring horizontal Pod autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/horizontal-pod-autoscaling).

**Scale on a Pub/Sub backlog.** A Pub/Sub backlog metric can reduce latency before it becomes a problem. It can use more resources than scaling on CPU ([Optimize Pod autoscaling based on metrics](https://docs.cloud.google.com/kubernetes-engine/docs/tutorials/autoscaling-metrics)). This HPA reads the number of undelivered messages for one subscription:

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: pubsub
spec:
  minReplicas: 1
  maxReplicas: 5
  metrics:
  - external:
      metric:
       name: pubsub.googleapis.com|subscription|num_undelivered_messages
       selector:
         matchLabels:
           resource.labels.subscription_id: echo-read
      target:
        type: AverageValue
        averageValue: 2
    type: External
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: pubsub
```

Source: [Optimize Pod autoscaling based on metrics](https://docs.cloud.google.com/kubernetes-engine/docs/tutorials/autoscaling-metrics).

With an `AverageValue` target, the HPA compares the target with the average of the metric across the Pods ([Horizontal Pod Autoscaling | Kubernetes](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/)). Here, the target is two undelivered messages for each Pod. Metric names in the HPA cannot contain uppercase letters or `/` ([Horizontal Pod autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/horizontalpodautoscaler)). That is why the sample writes the metric name with `|` separators ([Horizontal pod autoscaling (HPA)](https://docs.cloud.google.com/stackdriver/docs/managed-prometheus/hpa)).

**Metric adapters.** In the tutorial, the Custom Metrics Adapter lets the cluster send and receive metrics with Cloud Monitoring. With Workload Identity Federation for GKE, its Kubernetes ServiceAccount needs the Monitoring Viewer role ([Optimize Pod autoscaling based on metrics](https://docs.cloud.google.com/kubernetes-engine/docs/tutorials/autoscaling-metrics)). For Managed Service for Prometheus, you can use KEDA, the Custom Metrics Stackdriver Adapter, or the Prometheus Adapter. Do not install the Stackdriver Adapter and the Prometheus Adapter in the same cluster ([Horizontal pod autoscaling (HPA)](https://docs.cloud.google.com/stackdriver/docs/managed-prometheus/hpa)). You can also send custom metrics from a Pod directly to the autoscaler (Preview) ([About autoscaling workloads based on metrics](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/custom-and-external-metrics)).

**Scale on load balancer traffic.** The capacity is `maxRatePerEndpoint` in a GCPBackendPolicy for the Service. The HPA then uses an `Object` metric named `autoscaling.googleapis.com|gclb-capacity-fullness`. This replaces the earlier name `gclb-capacity-utilization`. Traffic-based autoscaling does not work for LoadBalancer Services, and one HPA must scale one Deployment behind one Service ([Configuring horizontal Pod autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/horizontal-pod-autoscaling)).

**Scale to and from zero.** Set `minReplicas: 0` and add at least one `External` or `Object` metric. GKE reads the metric through the AutoscalingMetric custom resource, so you need no KEDA. GKE cannot collect CPU or memory metrics from zero Pods, so resource metrics alone cannot start a scale-up from zero ([Scale GKE workloads to and from zero using HPA](https://docs.cloud.google.com/kubernetes-engine/docs/tutorials/scale-to-from-zero-hpa)). The HPA also cannot scale to zero with only CPU or memory metrics ([Troubleshoot horizontal Pod autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/troubleshooting/horizontal-pod-autoscaling)). In Kubernetes, the API server rejects `minReplicas: 0` if the HPA has no `Object` or `External` metric ([Horizontal Pod Autoscaling | Kubernetes](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/)).

Autoscaling is a balance between cost and latency. Test combinations of metrics to find a policy that works for your workload ([Optimize Pod autoscaling based on metrics](https://docs.cloud.google.com/kubernetes-engine/docs/tutorials/autoscaling-metrics)). For the Pub/Sub consumer code, see [Messaging](note:4.1-messaging).

## HPA with vertical Pod autoscaling

Vertical Pod autoscaling sets CPU and memory requests from historical usage. It works best for long-running workloads whose Pods have similar usage. For sudden spikes, use the HPA ([Vertical Pod autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/verticalpodautoscaler)).

Do not use both of them on CPU or memory. You have these supported options ([Horizontal Pod autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/horizontalpodautoscaler), [Vertical Pod autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/verticalpodautoscaler)):

- Use the HPA on custom or external metrics, and vertical Pod autoscaling on CPU and memory.
- Use multidimensional Pod autoscaling (Beta). A `MultidimPodAutoscaler` scales horizontally on CPU and vertically on memory ([Configure multidimensional Pod autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/multidimensional-pod-autoscaling)).

| Update mode | What it does |
|---|---|
| `Auto` or `Recreate` (default) | Evicts a Pod to change its requests. Use a PodDisruptionBudget to limit re-creations |
| `Initial` | Sets requests only when a Pod is created |
| `InPlaceOrRecreate` (Preview) | Tries to change requests without a re-creation. Falls back to re-creation when it cannot. Needs 1.34.0-gke.2201000 or later |
| `Off` | Gives recommendations only. You apply them yourself |

Sources: [Vertical Pod autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/verticalpodautoscaler).

Vertical Pod autoscaling is on by default in Autopilot clusters. It is not ready for JVM-based workloads, because it cannot see their real memory use ([Vertical Pod autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/verticalpodautoscaler)).

## Node capacity: cluster autoscaler and Autopilot

More Pods need somewhere to run. On Standard clusters, the cluster autoscaler resizes each node pool between the minimum and maximum that you set ([About GKE cluster autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/cluster-autoscaler)):

- It adds nodes when Pods cannot be scheduled on the current nodes.
- It removes nodes when they are underused and their Pods fit on other nodes.
- It uses Pod requests, not actual use. If requests are too small, the autoscaler does not correct the node shortage. Set explicit requests for all workloads.
- It does not remove a node if the removal exceeds a PodDisruptionBudget, or if a Pod has the annotation `"cluster-autoscaler.kubernetes.io/safe-to-evict": "false"`.
- Do not turn on Compute Engine autoscaling for the node managed instance groups. It conflicts with the cluster autoscaler.

Google calls it a best practice to enable the cluster autoscaler when you use the HPA or vertical Pod autoscaling ([Best practices for running cost-optimized Kubernetes applications on GKE](https://docs.cloud.google.com/architecture/best-practices-for-running-cost-effective-kubernetes-applications-on-gke)).

In Autopilot, Google manages the nodes. When the HPA adds Pods, GKE provisions new nodes and can expand existing nodes. A new Autopilot cluster starts with zero usable nodes, so the first workloads take longer to schedule. A cluster with no running workloads can scale down to zero nodes. To scale the number of Pods, use a mechanism such as the HPA ([GKE Autopilot overview](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/autopilot-overview)).

## Exam traps

- **A CPU utilization HPA that never scales.** The containers have no CPU requests. Utilization targets need requests ([Horizontal Pod autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/horizontalpodautoscaler)).
- **HPA and vertical Pod autoscaling both on CPU.** Do not combine them on CPU or memory. Use the HPA on another metric, or multidimensional Pod autoscaling (Beta) ([Horizontal Pod autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/horizontalpodautoscaler)).
- **"The HPA adds nodes."** It adds Pods only. The cluster autoscaler or Autopilot adds nodes ([Horizontal Pod autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/horizontalpodautoscaler), [GKE Autopilot overview](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/autopilot-overview)).
- **An HPA on the ReplicaSet of a Deployment.** A rolling update replaces the ReplicaSet. Target the Deployment ([Horizontal Pod autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/horizontalpodautoscaler)).
- **"Scale-down is broken because it is slow."** The 300-second stabilization window is the default ([Horizontal Pod autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/horizontalpodautoscaler)).
- **A queue worker that must keep latency low.** Scale on the backlog with an External metric, such as `num_undelivered_messages`. It reacts before latency grows, but can use more resources than CPU scaling ([Optimize Pod autoscaling based on metrics](https://docs.cloud.google.com/kubernetes-engine/docs/tutorials/autoscaling-metrics)).
- **`minReplicas: 0` with only a CPU metric.** The HPA cannot scale to zero, or back up from zero, on resource metrics alone. Add an External or Object metric ([Scale GKE workloads to and from zero using HPA](https://docs.cloud.google.com/kubernetes-engine/docs/tutorials/scale-to-from-zero-hpa), [Troubleshoot horizontal Pod autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/troubleshooting/horizontal-pod-autoscaling)).
- **`spec.replicas` kept in the Deployment manifest.** Each `kubectl apply` resets the Pod count ([Horizontal Pod Autoscaling | Kubernetes](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/)).
- **"The cluster autoscaler adds nodes when CPU use is high."** It adds nodes when Pods cannot be scheduled. It uses requests, not actual use ([About GKE cluster autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/cluster-autoscaler)).
- **Compute Engine autoscaling on GKE node groups.** It conflicts with the cluster autoscaler ([About GKE cluster autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/cluster-autoscaler)).
- **"Deleting the HPA restores the original size."** The replica count stays where the HPA left it ([Configuring horizontal Pod autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/horizontal-pod-autoscaling)).
