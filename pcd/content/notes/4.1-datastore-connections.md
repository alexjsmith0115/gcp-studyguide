## Why it matters

Every database connection uses resources on the client and on the database, and Cloud SQL has a fixed connection limit. On Cloud Run, each instance opens its own connections, so the total grows as the service scales. The exam tests which Cloud SQL connection path to choose and how to size a pool against `max_connections` and maximum instances. It also tests how to create Firestore and Cloud Storage clients once and reuse them.

## Key points

- For improved security, Cloud SQL recommends a private IP address, unless you need internet access to the instance ([Choose how to connect to Cloud SQL](https://docs.cloud.google.com/sql/docs/postgres/connection-options)).
- For a public IP address, use a Cloud SQL connector: the Cloud SQL Auth Proxy or a Cloud SQL Language Connector. You then need no authorized networks ([Choose how to connect to Cloud SQL](https://docs.cloud.google.com/sql/docs/postgres/connection-options)).
- The connectors authorize and encrypt connections, but they do not create a network path. For private IP, the app must already have VPC access ([Connect using Cloud SQL Language Connectors](https://docs.cloud.google.com/sql/docs/postgres/connect-connectors)).
- Cloud Run connects to a public IP instance through `--add-cloudsql-instances`, which gives a Unix socket at `/cloudsql/INSTANCE_CONNECTION_NAME` ([Connect from Cloud Run](https://docs.cloud.google.com/sql/docs/postgres/connect-run)).
- If Cloud Run sends all egress through Direct VPC egress or a Serverless VPC Access connector, use the private IP address ([Connect from Cloud Run](https://docs.cloud.google.com/sql/docs/postgres/connect-run)).
- With the built-in Cloud SQL connection, each Cloud Run instance can have 100 connections to a database. The limit does not apply to Language Connectors, an Auth Proxy sidecar, or a direct IP connection ([Quotas and limits](https://docs.cloud.google.com/sql/docs/postgres/quotas)).
- Limit connections with the pool size in each instance and with Cloud Run maximum instances ([Connect from Cloud Run](https://docs.cloud.google.com/sql/docs/postgres/connect-run), [Set maximum instances for services](https://docs.cloud.google.com/run/docs/configuring/max-instances)).
- The Cloud SQL Auth Proxy does not pool connections. Use a pool in the app ([About the Cloud SQL Auth Proxy](https://docs.cloud.google.com/sql/docs/postgres/sql-proxy)).
- Use IAM database authentication when possible, in automatic mode for connection pools ([Choose how to connect to Cloud SQL](https://docs.cloud.google.com/sql/docs/postgres/connection-options), [IAM authentication](https://docs.cloud.google.com/sql/docs/postgres/iam-authentication)).
- Reuse one client object for many requests. Each new client must authenticate again ([Client libraries best practices](https://docs.cloud.google.com/apis/docs/client-libraries-best-practices)).
- In Cloud Run and Cloud Run functions, keep clients in global variables, because instances serve many requests ([General development tips](https://docs.cloud.google.com/run/docs/tips/general)).
- Cloud Storage client libraries retry transient errors, and Firestore client libraries retry failed transactions. Do not add another retry layer on top ([Retry strategy](https://docs.cloud.google.com/storage/docs/retry-strategy), [Firestore best practices](https://docs.cloud.google.com/firestore/native/docs/best-practices)).

## Choose a Cloud SQL connection path

You make two choices. First, the network path: private IP or public IP. Second, the connection method: a Cloud SQL connector or a direct connection ([Choose how to connect to Cloud SQL](https://docs.cloud.google.com/sql/docs/postgres/connection-options)).

| Path | How it works | Use when |
|---|---|---|
| Language Connector (Java, Python, Go, Node.js) | A library in your code. It authorizes with IAM, encrypts the traffic, and needs no SSL certificates or authorized networks | Your language has a connector |
| Cloud SQL Auth Proxy | A local process or a sidecar. It encrypts with TLS 1.3 and authorizes with IAM | Other languages, tools such as `psql`, or GKE |
| Cloud Run built-in connection | `--add-cloudsql-instances` runs an embedded Auth Proxy and gives a Unix socket | A Cloud Run service on a public IP instance |
| Direct connection to private IP | A TCP connection over the VPC. You configure and enforce SSL | The app has VPC access, and you need the lowest latency |
| Direct connection to public IP with authorized networks | The instance accepts only the listed IP ranges. You configure SSL | Clients with known, fixed IP ranges |

Sources: [Choose how to connect to Cloud SQL](https://docs.cloud.google.com/sql/docs/postgres/connection-options), [Connect using Cloud SQL Language Connectors](https://docs.cloud.google.com/sql/docs/postgres/connect-connectors), [About the Cloud SQL Auth Proxy](https://docs.cloud.google.com/sql/docs/postgres/sql-proxy), [Connect using the Cloud SQL Auth Proxy](https://docs.cloud.google.com/sql/docs/postgres/connect-auth-proxy), [Connect from Cloud Run](https://docs.cloud.google.com/sql/docs/postgres/connect-run), [Authorize with authorized networks](https://docs.cloud.google.com/sql/docs/postgres/authorize-networks).

The docs give a general recommendation. For a private IP address, use a direct connection and enforce SSL. For a public IP address, use a connector ([Choose how to connect to Cloud SQL](https://docs.cloud.google.com/sql/docs/postgres/connection-options)). The GKE page gives a different rule: it recommends the Auth Proxy even with private IP, because the proxy adds IAM authentication and encryption ([Connect from Google Kubernetes Engine](https://docs.cloud.google.com/sql/docs/postgres/connect-kubernetes-engine)). A connector also helps when the client has a dynamically assigned or ephemeral IP address ([Choose how to connect to Cloud SQL](https://docs.cloud.google.com/sql/docs/postgres/connection-options)).

Private IP has two configurations. Private services access connects one VPC network through peering. Private Service Connect connects several VPC networks, even in other projects or organizations ([Choose how to connect to Cloud SQL](https://docs.cloud.google.com/sql/docs/postgres/connection-options)). For network design, see [Service-to-service communication](note:1.2-service-to-service).

For Java, Python, and Go, the Auth Proxy docs say to use the Language Connector instead of the proxy ([About the Cloud SQL Auth Proxy](https://docs.cloud.google.com/sql/docs/postgres/sql-proxy)). Connector enforcement makes Cloud SQL reject connections that do not use a connector ([Connect using Cloud SQL Language Connectors](https://docs.cloud.google.com/sql/docs/postgres/connect-connectors)). For how the proxy and connectors authenticate, see [Authenticating to Google Cloud](note:1.2-authenticating-to-google-cloud).

## Connect Cloud Run to Cloud SQL

Set up the connection in this order ([Connect from Cloud Run](https://docs.cloud.google.com/sql/docs/postgres/connect-run)):

1. Enable the Cloud SQL Admin API.
2. Put the instance in the same region as the service, for lower latency and cost.
3. Give the service account of the service the Cloud SQL Client role.
4. For public IP, add the instance with `--add-cloudsql-instances=INSTANCE_CONNECTION_NAME`. The change creates a new revision.
5. For private IP, send egress through Direct VPC egress or a connector. Then connect to the private IP address on port `5432`.
6. Store the database password in Secret Manager, and pass it as an environment variable or a volume.

A new instance gets a public IP address by default ([Connect from Cloud Run](https://docs.cloud.google.com/sql/docs/postgres/connect-run)). With the built-in connection, the service connects to the Unix socket `/cloudsql/INSTANCE_CONNECTION_NAME`. These connections are encrypted automatically. Linux limits a socket path to 108 characters ([Connect from Cloud Run](https://docs.cloud.google.com/sql/docs/postgres/connect-run)). The Cloud Run docs recommend Direct VPC egress over Serverless VPC Access connectors ([Compare Direct VPC egress and VPC connectors](https://docs.cloud.google.com/run/docs/configuring/connecting-vpc)).

The Python connector with a SQLAlchemy pool looks like this. The pool settings limit the connections that each instance opens:

```python
import os

from google.cloud.sql.connector import Connector, IPTypes
import pg8000
import sqlalchemy

ip_type = IPTypes.PRIVATE if os.environ.get("PRIVATE_IP") else IPTypes.PUBLIC
connector = Connector(refresh_strategy="LAZY")  # for serverless

def getconn() -> pg8000.dbapi.Connection:
    return connector.connect(
        os.environ["INSTANCE_CONNECTION_NAME"],  # project:region:instance
        "pg8000",
        user=os.environ["DB_USER"],
        password=os.environ["DB_PASS"],
        db=os.environ["DB_NAME"],
        ip_type=ip_type,
    )

pool = sqlalchemy.create_engine(
    "postgresql+pg8000://",
    creator=getconn,
    pool_size=5,        # permanent connections to keep
    max_overflow=2,     # extra connections when the pool is empty
    pool_timeout=30,    # seconds to wait for a free connection
    pool_recycle=1800,  # seconds before a connection is re-established
)
```

Sources: [Connect from Cloud Run](https://docs.cloud.google.com/sql/docs/postgres/connect-run), [Manage database connections](https://docs.cloud.google.com/sql/docs/postgres/manage-connections).

The lazy refresh strategy refreshes connection data only when needed, not on a schedule. The Cloud Run samples recommend it for serverless platforms, so that background refreshes do not run while the CPU is throttled ([Connect from Cloud Run](https://docs.cloud.google.com/sql/docs/postgres/connect-run)).

## Size the connection pool

A connection pool keeps database connections open and lends them to requests. This saves the time to open a new connection for each request ([Manage database connections](https://docs.cloud.google.com/sql/docs/postgres/manage-connections)). On Cloud Run, the total number of connections is the connections per instance multiplied by the number of instances.

| Control | What it limits | Default and notes |
|---|---|---|
| `pool_size` + `max_overflow` | Connections from one instance | The total for each instance is the sum of the two |
| Cloud Run maximum instances | The number of instances | 100 for each revision. Can be exceeded for a short time |
| Cloud Run built-in connection | Connections from one instance to one database, with `--add-cloudsql-instances` only | 100. No such limit for Language Connectors, an Auth Proxy sidecar, or a direct IP connection |
| `max_connections` flag | Connections to the Cloud SQL instance | The machine type sets the initial default |

Sources: [Manage database connections](https://docs.cloud.google.com/sql/docs/postgres/manage-connections), [Set maximum instances for services](https://docs.cloud.google.com/run/docs/configuring/max-instances), [Quotas and limits](https://docs.cloud.google.com/sql/docs/postgres/quotas).

For example, with `pool_size=5` and `max_overflow=2`, each instance opens up to 7 connections. With 20 maximum instances, the service can open up to 140 connections. Keep that number below `max_connections`, and leave room for other clients. Cloud Run documents maximum instances as a way to limit connections to a backing service, such as a database ([Set maximum instances for services](https://docs.cloud.google.com/run/docs/configuring/max-instances)). Set it at the service level, as Google recommends. With traffic splitting, the service limit is divided among the revisions ([Set maximum instances for services](https://docs.cloud.google.com/run/docs/configuring/max-instances)).

The built-in connection also uses Cloud SQL Admin API quota. The quota used is about two times the number of Cloud SQL instances times the number of Cloud Run instances ([Connect from Cloud Run](https://docs.cloud.google.com/sql/docs/postgres/connect-run)).

Write the pool code with these rules ([Manage database connections](https://docs.cloud.google.com/sql/docs/postgres/manage-connections)):

- Close each connection when you finish, so that it goes back to the pool. A leaked connection wastes resources.
- Use exponential backoff only when you open a connection or take one from the pool.
- If an error occurs during a transaction, your code must retry the full transaction from the start.
- Limit the lifetime of a connection, for example with `pool_recycle`, so that abandoned connections do not accumulate.

Connections can drop, either at the database or in the platform. Use a pool library that reconnects broken connections ([Connect from Cloud Run](https://docs.cloud.google.com/sql/docs/postgres/connect-run)). After a failover, all connections are lost, and the app must open new ones with the same connection string ([About the Cloud SQL Auth Proxy](https://docs.cloud.google.com/sql/docs/postgres/sql-proxy)).

**Managed Connection Pooling** adds a server-side pool to Cloud SQL for PostgreSQL. It helps most for many short-lived connections or connection surges, for example from Cloud Run. The instance must use Cloud SQL Enterprise Plus edition. The default `transaction` mode returns a connection to the pool after each transaction ([Managed Connection Pooling overview](https://docs.cloud.google.com/sql/docs/postgres/managed-connection-pooling)).

## IAM database authentication on pooled connections

IAM database authentication logs in with a short-lived OAuth 2.0 access token instead of a password. The token is valid for one hour. With automatic IAM database authentication, the connector requests and refreshes the tokens, so pooled connections stay stable ([IAM authentication](https://docs.cloud.google.com/sql/docs/postgres/iam-authentication)). With manual authentication, you pass the token as the password. New connections fail after the token expires ([IAM authentication](https://docs.cloud.google.com/sql/docs/postgres/iam-authentication)).

In Python, pass `enable_iam_auth=True` and no password. The user for a service account is its email without the `.gserviceaccount.com` suffix ([Log in using IAM database authentication](https://docs.cloud.google.com/sql/docs/postgres/iam-logins)). The roles, users, and grants are in [Authenticating to Google Cloud](note:1.2-authenticating-to-google-cloud).

## GKE and Compute Engine

On GKE, run the Auth Proxy as a sidecar container in the same Pod as the app. The app connects to the proxy on `localhost` ([Connect from Google Kubernetes Engine](https://docs.cloud.google.com/sql/docs/postgres/connect-kubernetes-engine)). Give each app its own service account, and use Workload Identity Federation for GKE (the page says Workload Identity) instead of a key file ([Connect from Google Kubernetes Engine](https://docs.cloud.google.com/sql/docs/postgres/connect-kubernetes-engine)). For private IP, the cluster must be VPC-native and in the same VPC network as the instance ([Connect from Google Kubernetes Engine](https://docs.cloud.google.com/sql/docs/postgres/connect-kubernetes-engine)).

On a VM, run the proxy as a persistent service, for example with `systemd`. If the proxy stops, all its connections drop. The proxy places no limit on connections, so your app must limit or pool them ([About the Cloud SQL Auth Proxy](https://docs.cloud.google.com/sql/docs/postgres/sql-proxy)). Run the proxy on the same machine as the app, because the link from the app to the proxy is not encrypted. Allow egress on ports 443 and 3307 ([About the Cloud SQL Auth Proxy](https://docs.cloud.google.com/sql/docs/postgres/sql-proxy)).

## Firestore and Cloud Storage clients

For Firestore and Cloud Storage, create one client object and reuse it for many requests. The first request of a client authenticates and gets an access token, which can take several seconds. Later requests reuse the token, and the client refreshes it automatically ([Client libraries best practices](https://docs.cloud.google.com/apis/docs/client-libraries-best-practices)). Each client has its own credential cache. If you create many clients in a short time, authentication can be rate limited and requests fail ([Client libraries best practices](https://docs.cloud.google.com/apis/docs/client-libraries-best-practices)).

Cloud Run reuses instances, so a global variable keeps its value for later requests. Global initialization runs at startup and adds to startup time. Lazy initialization moves the cost to the first request that needs the object ([General development tips](https://docs.cloud.google.com/run/docs/tips/general)). In Cloud Run functions, global initialization happens at load time ([Functions best practices](https://docs.cloud.google.com/run/docs/tips/functions-best-practices)).

```python
import functions_framework
from google.cloud import firestore, storage

# Always initialized (at cold start): every request needs it
db = firestore.Client()

# Declared at cold start, but only initialized if a request needs it
storage_client = None

@functions_framework.http
def handler(request):
    global storage_client
    if not storage_client:
        storage_client = storage.Client()
    ...
```

Source: [Functions best practices](https://docs.cloud.google.com/run/docs/tips/functions-best-practices).

Lazy initialization makes the first request on a new instance slower. During a deployment under heavy traffic, this can cause extra scaling and dropped requests ([General development tips](https://docs.cloud.google.com/run/docs/tips/general)). If many requests share a mutable global, protect it with a lock ([General development tips](https://docs.cloud.google.com/run/docs/tips/general)).

Know these Firestore client rules:

- A client connects to the `(default)` database. For a named database, set the database ID when you create the client, for example `firestore.Client(database="DATABASE_ID")` ([Create and manage databases](https://docs.cloud.google.com/firestore/native/docs/manage-databases), [Class Client](https://docs.cloud.google.com/python/docs/reference/firestore/latest/google.cloud.firestore_v1.client.Client)).
- Server client libraries have full access to the database. Firestore Security Rules do not apply to them, and IAM controls their access ([Firestore client libraries](https://docs.cloud.google.com/firestore/native/docs/reference/libraries)).
- Give an app service account `roles/datastore.user` for read and write access ([Security for server client libraries](https://docs.cloud.google.com/firestore/native/docs/security/iam)).

## Built-in retries

The Cloud Storage client libraries retry transient errors: HTTP `408`, `429`, and `5xx`, socket timeouts, and TCP disconnects ([Retry strategy](https://docs.cloud.google.com/storage/docs/retry-strategy)). A retry is safe only for an idempotent request:

| Idempotency | Examples |
|---|---|
| Always idempotent | All get and list requests, bucket insert and delete |
| Conditionally idempotent | An object upload or delete with `ifGenerationMatch`, or a metadata update with `ifMetagenerationMatch` or an `etag` |
| Never idempotent | Create an HMAC key, create a Pub/Sub notification, change ACLs |

Source: [Retry strategy](https://docs.cloud.google.com/storage/docs/retry-strategy).

In Python, the default is to retry idempotent operations. The library also retries Objects: insert, Objects: delete, and Objects: patch by default. The first wait is 1 second, the multiplier is 2, the maximum wait is 60 seconds, and the deadline is 120 seconds. A subset of conditionally idempotent operations retries only if you pass `generation` or `if_generation_match` ([Retry strategy](https://docs.cloud.google.com/storage/docs/retry-strategy)). To change the behavior, change a copy of `DEFAULT_RETRY`:

```python
from google.cloud.storage.retry import DEFAULT_RETRY

modified_retry = DEFAULT_RETRY.with_timeout(500.0)  # default 120 seconds
modified_retry = modified_retry.with_delay(initial=1.5, multiplier=1.2, maximum=45.0)
blob.delete(retry=modified_retry)
```

Source: [Retry strategy](https://docs.cloud.google.com/storage/docs/retry-strategy).

Avoid these retry mistakes ([Retry strategy](https://docs.cloud.google.com/storage/docs/retry-strategy)):

- Retrying without a delay. Use exponential backoff with jitter.
- Retrying requests that are not idempotent, or errors that are permanent, such as authorization failures.
- Adding app retries on top of library retries. Three app retries of three library retries give nine attempts. Use and configure the built-in retries.

The Firestore client libraries retry failed transactions automatically. If you call the REST or RPC API directly, your code must retry transactions ([Firestore best practices](https://docs.cloud.google.com/firestore/native/docs/best-practices)). For backoff in other Google APIs, see [Efficient API calls](note:4.2-efficient-api-calls).

## Exam traps

- **The Auth Proxy or a connector to reach a private IP instance from a network without VPC access.** They do not create a network path ([Connect using Cloud SQL Language Connectors](https://docs.cloud.google.com/sql/docs/postgres/connect-connectors)).
- **Authorized networks for a client with an ephemeral IP address.** Use a connector. It needs no authorized networks and supports dynamic IP addresses ([Choose how to connect to Cloud SQL](https://docs.cloud.google.com/sql/docs/postgres/connection-options)).
- **A new connection for each request.** Use a pool, and close each connection so that it goes back to the pool ([Manage database connections](https://docs.cloud.google.com/sql/docs/postgres/manage-connections)).
- **The Auth Proxy as a connection pooler.** It does not pool or limit connections ([About the Cloud SQL Auth Proxy](https://docs.cloud.google.com/sql/docs/postgres/sql-proxy)).
- **"Too many connections" errors after Cloud Run scales out.** Lower the pool size, set maximum instances, or add Managed Connection Pooling ([Connect from Cloud Run](https://docs.cloud.google.com/sql/docs/postgres/connect-run), [Set maximum instances for services](https://docs.cloud.google.com/run/docs/configuring/max-instances), [Managed Connection Pooling overview](https://docs.cloud.google.com/sql/docs/postgres/managed-connection-pooling)).
- **Retrying one failed statement in the middle of a transaction.** Retry the full transaction from the start ([Manage database connections](https://docs.cloud.google.com/sql/docs/postgres/manage-connections)).
- **Manual IAM database authentication in a long-running pool.** Tokens expire after one hour. Use automatic mode ([IAM authentication](https://docs.cloud.google.com/sql/docs/postgres/iam-authentication)).
- **A new storage or Firestore client inside the request handler.** Create it once in a global variable and reuse it ([Client libraries best practices](https://docs.cloud.google.com/apis/docs/client-libraries-best-practices), [Functions best practices](https://docs.cloud.google.com/run/docs/tips/functions-best-practices)).
- **App-level retries around every Cloud Storage call.** The library already retries. Layered retries multiply attempts ([Retry strategy](https://docs.cloud.google.com/storage/docs/retry-strategy)).
- **Firestore Security Rules to limit a backend service.** Server client libraries bypass the rules. Use IAM ([Firestore client libraries](https://docs.cloud.google.com/firestore/native/docs/reference/libraries)).
