## Why it matters

Cloud Build runs your builds, and Artifact Registry stores the images and packages that they make. A developer chooses how to describe the build, what starts it, which identity it runs as, and where the image goes. The exam tests the Google-recommended pattern: a trigger with a dedicated service account runs a `cloudbuild.yaml` file. The image goes to an Artifact Registry repository near the runtime, and the pipeline deploys the exact image that it built.

## Key points

- Cloud Build runs each build step as a Docker container. By default, steps run one after the other on the same machine. Use `waitFor` to run steps at the same time ([Build configuration file schema](https://docs.cloud.google.com/build/docs/build-config-file-schema)).
- You can build an image from a build config file, from a `Dockerfile` only, or from source code only with Google Cloud's buildpacks ([Build container images](https://docs.cloud.google.com/build/docs/building/build-containers)).
- The `images` field pushes images to Artifact Registry after all steps complete, and the build results show them. If the build does not produce a listed image, the build fails ([Build configuration file schema](https://docs.cloud.google.com/build/docs/build-config-file-schema), [Build container images](https://docs.cloud.google.com/build/docs/building/build-containers)).
- A build has a default timeout of 60 minutes and a maximum of 24 hours. The default machine type is `e2-standard-2` ([Build configuration file schema](https://docs.cloud.google.com/build/docs/build-config-file-schema)).
- Triggers start builds on repository events (branch push, tag push, pull request), on manual invocation, on Pub/Sub messages, and on webhooks ([Cloud Build triggers](https://docs.cloud.google.com/build/docs/triggers), [Create and manage build triggers](https://docs.cloud.google.com/build/docs/automating-builds/create-manage-triggers)).
- A triggered build runs as the service account on the trigger. Cloud Build ignores the `serviceAccount` field of the build config for triggered builds ([Create and manage build triggers](https://docs.cloud.google.com/build/docs/automating-builds/create-manage-triggers)).
- New projects use the Compute Engine default service account for builds. Google recommends that you create your own service account with only the roles the build needs ([Cloud Build default service account change](https://docs.cloud.google.com/build/docs/cloud-build-service-account-updates), [Default Cloud Build service account](https://docs.cloud.google.com/build/docs/cloud-build-service-account)).
- A private pool can peer with your VPC network to reach private resources. The default pool cannot ([Private pools overview](https://docs.cloud.google.com/build/docs/private-pools/private-pools-overview)).
- Artifact Registry is the recommended registry. Container Registry shut down on March 18, 2025, and you cannot write images to it ([Transition from Container Registry](https://docs.cloud.google.com/artifact-registry/docs/transition/transition-from-gcr)).
- An Artifact Registry repository has one format and one mode: standard, remote, virtual, or connector (Preview). You cannot change the mode after you create the repository ([Repository overview](https://docs.cloud.google.com/artifact-registry/docs/repositories)).
- A tag can move to another image. A digest identifies one image version and cannot change ([Repository and image names](https://docs.cloud.google.com/artifact-registry/docs/docker/names)).

## The build config file

A build config file (`cloudbuild.yaml` or `cloudbuild.json`) lists the steps and the build options. The fields below are the ones that build questions use.

| Field | What it does |
|---|---|
| `steps[].name` | The builder image that runs the step, for example `gcr.io/cloud-builders/docker` |
| `steps[].args`, `entrypoint`, `script` | The command. `script` cannot be in the same step as `args` or `entrypoint` |
| `steps[].id`, `waitFor` | Step order. `waitFor: ['-']` starts the step when the build starts |
| `steps[].env`, `secretEnv` | Environment variables, and secrets from `availableSecrets` |
| `steps[].timeout` | Time limit for one step. It cannot be more than the build timeout |
| `images` | Images that Cloud Build pushes after the steps complete |
| `artifacts` | Other results: objects in Cloud Storage, and packages or OCI images in Artifact Registry |
| `substitutions` | Default values for user-defined variables |
| `serviceAccount` | The service account at build time. Triggered builds ignore it |
| `options.machineType`, `diskSizeGb` | A larger worker |
| `options.logging` | Where logs go: `CLOUD_LOGGING_ONLY`, `GCS_ONLY`, `LEGACY` (default), or `NONE` |
| `timeout`, `queueTtl` | Build time limit, and the time a build can wait in the queue (default 1 hour) |

Sources: [Build configuration file schema](https://docs.cloud.google.com/build/docs/build-config-file-schema), [Configuring the order of build steps](https://docs.cloud.google.com/build/docs/configuring-builds/configure-build-step-order).

Files in `/workspace` and in named `volumes` persist between steps. Cloud Build mounts the `workspace` volume in each step automatically. Each step container joins a local Docker network named `cloudbuild`, which hosts Application Default Credentials (ADC). A nested `docker build` needs `--network=cloudbuild` to get those credentials ([Build configuration file schema](https://docs.cloud.google.com/build/docs/build-config-file-schema)).

This config builds an image, pushes it, and deploys it to Cloud Run. A trigger supplies `$COMMIT_SHA`. The `logging` setting is necessary with your own service account:

```yaml
steps:
- name: 'gcr.io/cloud-builders/docker'
  args: ['build', '-t', '${_LOCATION}-docker.pkg.dev/$PROJECT_ID/${_REPOSITORY}/${_IMAGE}:$COMMIT_SHA', '.']
- name: 'gcr.io/cloud-builders/docker'
  args: ['push', '${_LOCATION}-docker.pkg.dev/$PROJECT_ID/${_REPOSITORY}/${_IMAGE}:$COMMIT_SHA']
- name: 'gcr.io/google.com/cloudsdktool/cloud-sdk'
  entrypoint: gcloud
  args: ['run', 'deploy', '${_SERVICE}', '--region', '${_LOCATION}',
         '--image', '${_LOCATION}-docker.pkg.dev/$PROJECT_ID/${_REPOSITORY}/${_IMAGE}:$COMMIT_SHA']
images:
- '${_LOCATION}-docker.pkg.dev/$PROJECT_ID/${_REPOSITORY}/${_IMAGE}:$COMMIT_SHA'
substitutions:
  _LOCATION: us-central1
  _REPOSITORY: my-repo
  _IMAGE: my-app
  _SERVICE: my-service
options:
  logging: CLOUD_LOGGING_ONLY
```

Sources: [Deploying to Cloud Run using Cloud Build](https://docs.cloud.google.com/build/docs/deploying-builds/deploy-cloud-run), [Store artifacts in Artifact Registry](https://docs.cloud.google.com/build/docs/building/store-artifacts-in-artifact-registry), [Configure user-specified service accounts](https://docs.cloud.google.com/build/docs/securing-builds/configure-user-specified-service-accounts).

For this sample, the docs give the build service account Cloud Run Admin, Artifact Registry Writer, Logs Writer, and other roles. It also needs Service Account User on the runtime service account. The trigger region must match the region of the Cloud Run service ([Deploying to Cloud Run using Cloud Build](https://docs.cloud.google.com/build/docs/deploying-builds/deploy-cloud-run)).

### Substitutions

Substitutions put values into `steps` and `images` at build time ([Substituting variable values](https://docs.cloud.google.com/build/docs/configuring-builds/substitute-variable-values)):

- **Built-in for all builds:** `$PROJECT_ID`, `$BUILD_ID`, `$PROJECT_NUMBER`, `$LOCATION`. You cannot override `$PROJECT_ID` or `$BUILD_ID`.
- **Built-in for triggered builds:** `$COMMIT_SHA`, `$SHORT_SHA`, `$BRANCH_NAME`, `$TAG_NAME`, `$REPO_NAME`, `$TRIGGER_NAME`, and others. Builds that use a storage source get an empty string for them. With `gcloud builds submit`, you can pass values with `--substitutions`.
- **User-defined:** the name starts with an underscore and uses uppercase letters, numbers, and underscores, for example `_IMAGE`.
- **Literal dollar sign:** write `$$` for a shell variable, for example `$$PASSWORD`. `$FOO` is not valid, because it is not a built-in substitution.
- **Missing values:** a manual build fails on a missing substitution. Triggered builds always use `ALLOW_LOOSE`, so they do not fail.

## Three ways to build an image

| Approach | Command | Use when |
|---|---|---|
| Build config file | `gcloud builds submit --config cloudbuild.yaml .` | The pipeline has several steps: tests, push, sign, deploy |
| `Dockerfile` only | `gcloud builds submit --tag IMAGE` | You have a `Dockerfile` and need only the image. No config file is necessary |
| Buildpacks | `gcloud builds submit --pack image=IMAGE` | You have no `Dockerfile`. The default builder `gcr.io/buildpacks/builder` detects the language |

Sources: [Build container images](https://docs.cloud.google.com/build/docs/building/build-containers), [Google Cloud's buildpacks](https://docs.cloud.google.com/docs/buildpacks/overview).

Buildpacks install dependencies from the language's usual dependency file. Some languages, such as Python, need a `Procfile` to set the start command ([Google Cloud's buildpacks](https://docs.cloud.google.com/docs/buildpacks/overview)). Triggers can also build with a `Dockerfile` or buildpacks instead of a config file ([Create and manage build triggers](https://docs.cloud.google.com/build/docs/automating-builds/create-manage-triggers)).

`gcloud run deploy --source` starts its own build. It does not use the `machineType` in your local `cloudbuild.yaml`. If the build needs a specific machine type, build the image with your own build and deploy it with `--image` ([Increase vCPU for builds](https://docs.cloud.google.com/build/docs/optimize-builds/increase-vcpu-for-builds)). For source deployments, see [Deploying to Cloud Run from source code](note:3.1-deploy-from-source).

**Pushing the image.** The `images` field pushes after the build and shows the image in the build results. A `docker push` step pushes during the build, so a later step can deploy the image. That image does not show in the build results. To get both, use the push step and the `images` field together ([Build container images](https://docs.cloud.google.com/build/docs/building/build-containers), [Deploying to Cloud Run using Cloud Build](https://docs.cloud.google.com/build/docs/deploying-builds/deploy-cloud-run)).

## Triggers

| Trigger | Starts a build when | Notes |
|---|---|---|
| Repository event | A push to a branch, a push of a tag, or a pull request | GitHub, GitHub Enterprise, GitLab, Bitbucket, and Secure Source Manager. Connect the repository first. The repository region must match the trigger region |
| Manual | A user runs it, or Cloud Scheduler runs it on a schedule | You can override substitution values at each run |
| Pub/Sub | A message arrives on a topic, for example an Artifact Registry image push | Add filters on substitution values. Not supported with VPC Service Controls |
| Webhook | An external system posts to the trigger URL | The URL contains an API key and a secret from Secret Manager. For repository events, Google recommends repository triggers instead |

Sources: [Cloud Build triggers](https://docs.cloud.google.com/build/docs/triggers), [Create and manage build triggers](https://docs.cloud.google.com/build/docs/automating-builds/create-manage-triggers), [Automate builds in response to Pub/Sub events](https://docs.cloud.google.com/build/docs/automate-builds-pubsub-events), [Automate builds in response to webhook events](https://docs.cloud.google.com/build/docs/automate-builds-webhook-events).

Connect external repositories with Cloud Build repositories (2nd gen) or Developer Connect. The 1st gen connections are a legacy option ([Cloud Build repositories](https://docs.cloud.google.com/build/docs/repositories)). Cloud Source Repositories is not available to new customers since June 17, 2024 ([Cloud Build triggers](https://docs.cloud.google.com/build/docs/triggers)).

Trigger settings that the exam uses ([Create and manage build triggers](https://docs.cloud.google.com/build/docs/automating-builds/create-manage-triggers)):

- **Included and ignored files.** Glob patterns limit builds to changes in some paths. Only push events (branch or tag) use them. A change to a file in both lists does not start a build ([Create and manage build triggers](https://docs.cloud.google.com/build/docs/automating-builds/create-manage-triggers)).
- **Skip a build.** A commit message with `[skip ci]` or `[ci skip]` does not start a build.
- **Approval.** `--require-approval` holds the build as pending. A user with the Cloud Build Approver role approves it ([Gate builds on approval](https://docs.cloud.google.com/build/docs/securing-builds/gate-builds-on-approval)).
- **Shallow clone.** Cloud Build checks out only the commit that started the build. Add a `git fetch --unshallow` step if the build needs history.
- **Organization policy.** `constraints/cloudbuild.allowedIntegrations` blocks builds from sources that you do not allow.

**Pull requests from outside contributors.** Any user with read access to a GitHub repository can open a pull request. The pull request trigger can then build that code. Set **Comment control** so that an owner or collaborator must comment `/gcbrun` first ([Building repositories from GitHub](https://docs.cloud.google.com/build/docs/automating-builds/github/build-repos-from-github), [Default Cloud Build service account](https://docs.cloud.google.com/build/docs/cloud-build-service-account)).

## The build service account

| Identity | Email | When Cloud Build uses it |
|---|---|---|
| Legacy Cloud Build service account | `PROJECT_NUMBER@cloudbuild.gserviceaccount.com` | Default in projects that ran their first build before the change in May and June 2024. Has the Cloud Build Service Account role |
| Compute Engine default service account | `PROJECT_NUMBER-compute@developer.gserviceaccount.com` | Default in projects that ran their first build after the change |
| User-specified service account | Your own service account | Recommended. Set it on the trigger or in `serviceAccount` |

Sources: [Cloud Build default service account change](https://docs.cloud.google.com/build/docs/cloud-build-service-account-updates), [Default Cloud Build service account](https://docs.cloud.google.com/build/docs/cloud-build-service-account).

- **Act-as permission.** The user who starts a build or creates a trigger needs `iam.serviceAccounts.actAs` on the service account. The Service Account User role gives this permission ([Default Cloud Build service account](https://docs.cloud.google.com/build/docs/cloud-build-service-account)).
- **Trigger permission.** A trigger's service account needs `cloudbuild.builds.create` to create the build. Cloud Build Editor and the Cloud Build Service Account role (`roles/cloudbuild.builds.builder`) both have it ([Troubleshooting build errors and more](https://docs.cloud.google.com/build/docs/troubleshooting), [Cloud Build roles and permissions](https://docs.cloud.google.com/iam/docs/roles-permissions/cloudbuild)).
- **Logs.** With your own service account, store logs in Cloud Logging or in a bucket that you own. A Google-owned log bucket is not allowed ([Configure user-specified service accounts](https://docs.cloud.google.com/build/docs/securing-builds/configure-user-specified-service-accounts)).
- **ID tokens.** The legacy service account cannot generate ID tokens. To call a private Cloud Run service from a build, use a user-specified service account ([Default Cloud Build service account](https://docs.cloud.google.com/build/docs/cloud-build-service-account)).
- **Build-time privilege.** A person with write access to a connected repository changes the code that runs with the trigger's service account, even without project access. Give each trigger a service account with only the roles it needs ([Create and manage build triggers](https://docs.cloud.google.com/build/docs/automating-builds/create-manage-triggers)).

For service account design, see [Service accounts, IAM roles, and least privilege](note:1.2-service-accounts-least-privilege). For tests and secrets in builds, see [Automated integration tests in Cloud Build](note:2.3-integration-tests-cloud-build).

## Faster builds

| Technique | How | Notes |
|---|---|---|
| Docker layer cache | Pull the last image (`docker pull ... \|\| exit 0`), then `docker build --cache-from` that image | Docker builds only. A change in an early layer rebuilds all later layers |
| Cache in Cloud Storage | Copy earlier results from a bucket at the start, and copy new results back at the end | Works with any builder. Best for a small number of files |
| `.gcloudignore` | Exclude files such as `.git`, `node_modules`, and `*.jar` from the upload | The build is also more consistent |
| Larger machine | `options.machineType` or `--machine-type=E2_HIGHCPU_8` | The build can start more slowly |
| Leaner images | Separate the build tools from the runtime image | Smaller images move faster |

Sources: [Best practices for speeding up builds](https://docs.cloud.google.com/build/docs/optimize-builds/speeding-up-builds), [Increase vCPU for builds](https://docs.cloud.google.com/build/docs/optimize-builds/increase-vcpu-for-builds).

For image size and Dockerfile practice, see [Building and refactoring containers for Cloud Run and GKE](note:1.1-containers).

## Artifact Registry repositories

| Mode | What it does | Use when |
|---|---|---|
| Standard | Stores your private artifacts. You push to it | Your build output: images and packages |
| Remote | A read-only proxy that caches an upstream source, such as Docker Hub, Maven Central, PyPI, or another Artifact Registry repository | You want faster access to public dependencies, vulnerability scans of them, and access during an upstream outage |
| Virtual | A read-only single endpoint for several upstream repositories, chosen by priority | You want one client setting, and protection against dependency confusion attacks |
| Connector (Preview) | A proxy that does not cache | You need full auditability, or a policy prevents caching |

Sources: [Repository overview](https://docs.cloud.google.com/artifact-registry/docs/repositories), [Remote repositories overview](https://docs.cloud.google.com/artifact-registry/docs/repositories/remote-overview), [Virtual repositories overview](https://docs.cloud.google.com/artifact-registry/docs/repositories/virtual-overview).

- **Formats.** One repository holds one format, for example Docker (images and OCI Helm charts), Maven, npm, Python, Go, Apt, Yum, or generic ([Supported formats](https://docs.cloud.google.com/artifact-registry/docs/supported-formats)).
- **Virtual priority.** A higher number wins. Give the standard repository with your private packages a higher priority than the remote repository that caches public packages. Configure `pip` to use only the virtual repository, because `pip` picks the latest version from all its sources ([Virtual repositories overview](https://docs.cloud.google.com/artifact-registry/docs/repositories/virtual-overview)).
- **Location.** Put the repository in the region of GKE, Cloud Run, and Cloud Build to reduce latency and egress cost. Egress to services in the same region has no charge ([Repository overview](https://docs.cloud.google.com/artifact-registry/docs/repositories)). A multi-region repository can continue to work when one region is down, but it can be slower ([Artifact Registry locations](https://docs.cloud.google.com/artifact-registry/docs/repositories/repo-locations)).
- **Image names.** `LOCATION-docker.pkg.dev/PROJECT-ID/REPOSITORY/IMAGE:TAG`, or `...IMAGE@sha256:DIGEST` for a digest ([Repository and image names](https://docs.cloud.google.com/artifact-registry/docs/docker/names)).
- **Scanning.** Artifact Analysis (formerly Container Analysis) scans images in Artifact Registry for vulnerabilities ([Artifact Registry overview](https://docs.cloud.google.com/artifact-registry/docs/overview)). For findings and fixes, see [Protecting apps and finding vulnerabilities](note:1.2-protect-and-scan).

### Cleanup policies

A cleanup policy deletes artifact versions that you no longer need. A delete policy matches by tag state, tag prefix, version prefix, package prefix, and age. A keep policy keeps matching versions or the most recent N versions. When both match, the keep policy wins ([Configure cleanup policies](https://docs.cloud.google.com/artifact-registry/docs/repositories/cleanup-policy)):

```json
[
  {"name": "delete-prerelease", "action": {"type": "Delete"},
   "condition": {"tagState": "tagged", "tagPrefixes": ["alpha", "v0"], "olderThan": "30d"}},
  {"name": "keep-minimum-versions", "action": {"type": "Keep"},
   "mostRecentVersions": {"packageNamePrefixes": ["webapp", "mobile"], "keepCount": 5}}
]
```

Source: [Configure cleanup policies](https://docs.cloud.google.com/artifact-registry/docs/repositories/cleanup-policy).

Test the file first with `gcloud artifacts repositories set-cleanup-policies REPOSITORY --location=LOCATION --policy=policy.json --dry-run`. A background job applies policies, and changes take effect in about one day. You can apply cleanup policies only to standard repositories ([Configure cleanup policies](https://docs.cloud.google.com/artifact-registry/docs/repositories/cleanup-policy)). In a repository with immutable tags, cleanup cannot delete tagged images ([Repository overview](https://docs.cloud.google.com/artifact-registry/docs/repositories)).

## Access control and Docker authentication

| Role | Allows |
|---|---|
| Artifact Registry Reader (`roles/artifactregistry.reader`) | View and download artifacts |
| Artifact Registry Writer (`roles/artifactregistry.writer`) | Read and write artifacts |
| Artifact Registry Repository Administrator (`roles/artifactregistry.repoAdmin`) | Read, write, and delete artifacts |
| Artifact Registry Administrator (`roles/artifactregistry.admin`) | Create and manage repositories and artifacts |

Source: [Access control with IAM](https://docs.cloud.google.com/artifact-registry/docs/access-control).

Grant roles on the project or on one repository, with least privilege. For example, GKE nodes need only read access ([Repository overview](https://docs.cloud.google.com/artifact-registry/docs/repositories)). In the same project, Cloud Build can upload and download by default. Compute Engine, GKE, and Cloud Run use the Compute Engine default service account, which has read-only access ([Access control with IAM](https://docs.cloud.google.com/artifact-registry/docs/access-control)).

**Cross-project pulls.** Grant the role in the project that has the repository. For Cloud Run, grant it to the Cloud Run Service Agent of the Cloud Run project (`service-PROJECT_NUMBER@serverless-robot-prod.iam.gserviceaccount.com`) ([Access control with IAM](https://docs.cloud.google.com/artifact-registry/docs/access-control)).

**Docker clients.** Cloud Build, GKE, and Cloud Run need no Docker authentication setup, only permissions ([Authenticate Docker to Artifact Registry](https://docs.cloud.google.com/artifact-registry/docs/docker/authentication)). On a workstation:

```bash
gcloud auth configure-docker us-central1-docker.pkg.dev
```

Source: [Build container images](https://docs.cloud.google.com/build/docs/building/build-containers).

The gcloud credential helper is the simplest method. The standalone credential helper is faster and uses ADC. An access token from service account impersonation is valid for 60 minutes. A service account key is the least secure option ([Authenticate Docker to Artifact Registry](https://docs.cloud.google.com/artifact-registry/docs/docker/authentication)). For a CI system outside Google Cloud, use Workload Identity Federation instead of keys ([Access control with IAM](https://docs.cloud.google.com/artifact-registry/docs/access-control)).

## Container Registry shutdown

| | Container Registry (shut down) | Artifact Registry |
|---|---|---|
| Domain | `gcr.io` | `pkg.dev`, and `gcr.io` repositories for compatibility |
| Formats | Container images only | Images, language packages, and OS packages |
| Create a registry | Push the first image | Create the repository before you push |
| Access control | Cloud Storage roles on a multi-region host | Artifact Registry roles on each repository |

Source: [Transition from Container Registry](https://docs.cloud.google.com/artifact-registry/docs/transition/transition-from-gcr).

`gcr.io` URLs that Artifact Registry hosts still work. For example, the Cloud Build builder images such as `gcr.io/cloud-builders/docker` are not affected ([Transition from Container Registry](https://docs.cloud.google.com/artifact-registry/docs/transition/transition-from-gcr)).

## Deploying by image digest

A tag is a label that can point to a new digest after each push. A digest is the SHA-256 hash of the image manifest or index, and it cannot change ([Repository and image names](https://docs.cloud.google.com/artifact-registry/docs/docker/names)). Deploy by digest when you must run exactly the image that was scanned or signed:

- **Cloud Run** resolves a tag to a digest at deploy time. The revision always serves that digest ([Deploy container images to Cloud Run services](https://docs.cloud.google.com/run/docs/deploying)).
- **GKE** with a tag can run old and new images in one Deployment after the tag moves. Scan results are valid only for the scanned image. Binary Authorization on GKE does not allow tag-based deployment ([About container image digests](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/about-container-images)).
- **Immutable tags.** A Docker repository with `--immutable-tags` does not let a push reuse a tag for another image ([Create standard repositories](https://docs.cloud.google.com/artifact-registry/docs/repositories/create-repos), [Repository and image names](https://docs.cloud.google.com/artifact-registry/docs/docker/names)).

Get the digest from the build or the registry:

```bash
gcloud builds describe BUILD_ID --format 'value(results.images[0].digest)'
gcloud artifacts docker images describe \
    LOCATION-docker.pkg.dev/PROJECT/REPOSITORY/IMAGE:TAG --format 'value(image_summary.digest)'
```

Source: [About container image digests](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/about-container-images).

To require digests in GKE manifests, use Policy Controller or OPA Gatekeeper ([About container image digests](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/about-container-images)). To allow only images that Cloud Build built, see [Build provenance and Binary Authorization](note:2.2-provenance-binary-authorization).

## Exam traps

- **A new pipeline that pushes to Container Registry.** Container Registry is shut down. Push to an Artifact Registry `pkg.dev` repository ([Transition from Container Registry](https://docs.cloud.google.com/artifact-registry/docs/transition/transition-from-gcr)).
- **`serviceAccount` in `cloudbuild.yaml` for a triggered build.** The trigger's service account wins. Set the service account on the trigger ([Create and manage build triggers](https://docs.cloud.google.com/build/docs/automating-builds/create-manage-triggers)).
- **A `docker push` step and an image missing from the build results.** Add the `images` field ([Build container images](https://docs.cloud.google.com/build/docs/building/build-containers)).
- **A Cloud Run service that cannot pull from a repository in another project.** Grant the reader role in the repository's project. Grant it to the Cloud Run Service Agent of the Cloud Run project ([Access control with IAM](https://docs.cloud.google.com/artifact-registry/docs/access-control)).
- **A build that must reach a database or Git server in a VPC network.** The default pool cannot peer with a VPC network. Use a private pool ([Private pools overview](https://docs.cloud.google.com/build/docs/private-pools/private-pools-overview)).
- **A build that calls a private Cloud Run service as the legacy Cloud Build service account.** It cannot generate ID tokens. Use a user-specified service account ([Default Cloud Build service account](https://docs.cloud.google.com/build/docs/cloud-build-service-account)).
- **A pull request trigger on a public repository with comment control off.** Any reader can open a pull request that runs a build. Require `/gcbrun` or approval ([Building repositories from GitHub](https://docs.cloud.google.com/build/docs/automating-builds/github/build-repos-from-github)).
- **`$PASSWORD` in a bash step.** Cloud Build reads `$NAME` as a substitution, and `$PASSWORD` is not a valid one. Write `$$PASSWORD` ([Substituting variable values](https://docs.cloud.google.com/build/docs/configuring-builds/substitute-variable-values)).
- **A cleanup policy on a virtual repository.** Cleanup policies apply only to standard repositories ([Configure cleanup policies](https://docs.cloud.google.com/artifact-registry/docs/repositories/cleanup-policy)).
- **A service account key for `docker login`.** Use a credential helper or a short-lived access token ([Authenticate Docker to Artifact Registry](https://docs.cloud.google.com/artifact-registry/docs/docker/authentication)).
- **Deploying `:latest` to GKE and expecting the scanned image.** Deploy by digest ([About container image digests](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/about-container-images)).
