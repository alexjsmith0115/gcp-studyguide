## Why it matters

Each API call costs time, network traffic, and quota. Exam guide section 4.2 lists five techniques for API calls. They are batching, restricting return data, pagination, caching, and error handling, for example with exponential backoff. This page gives the Google guidance for each technique.

## Key points

- The `fields` system parameter (header `X-Goog-FieldMask`) returns only the fields that you ask for. It works across Google REST and gRPC APIs ([System parameters](https://docs.cloud.google.com/apis/docs/system-parameters)).
- A `PATCH` request sends only the fields that change. `PATCH` with `fields` makes both the request and the response smaller ([Improve Performance](https://docs.cloud.google.com/compute/docs/api/how-tos/performance)).
- To get gzip responses, send `Accept-Encoding: gzip` and put `gzip` in the `User-Agent` header ([Improve Performance](https://docs.cloud.google.com/compute/docs/api/how-tos/performance)).
- A batch request sends many calls in one HTTP request. A batch of n calls counts toward your usage limit as n requests ([Batching requests](https://docs.cloud.google.com/compute/docs/api/how-tos/batch)).
- An empty `next_page_token` is the only sign of the end of a list. A page can have fewer items than `page_size` before the end ([AIP-158](https://google.aip.dev/158)).
- Client library pagers make the next page requests for you ([Using client libraries](https://docs.cloud.google.com/compute/docs/api/using-libraries)).
- A request with `If-None-Match` and a cached ETag returns `304 Not Modified` when the resource did not change. The client then uses its cached copy ([Prevent FHIR resource conflicts using ETags](https://docs.cloud.google.com/healthcare-api/docs/fhir-etag), [Download an object](https://docs.cloud.google.com/storage/docs/xml-api/get-object-download)).
- BigQuery caches query results for about 24 hours. A query that uses cached results costs nothing, but it still counts against quotas ([Use cached query results](https://docs.cloud.google.com/bigquery/docs/cached-results)).
- Retry with truncated exponential backoff and jitter. The jitter stops many clients from retrying at the same time ([Retry failed requests](https://docs.cloud.google.com/iam/docs/retry-strategy)).
- Retry only transient errors (`408`, `429`, `5xx`, and connection errors), and think about idempotency before you retry ([Retry strategy](https://docs.cloud.google.com/storage/docs/retry-strategy)).
- Cloud Client Libraries retry automatically. Use and configure the built-in retries. A second retry loop in your code multiplies the attempts ([AIP-4221](https://google.aip.dev/client-libraries/4221), [Retry strategy](https://docs.cloud.google.com/storage/docs/retry-strategy)).
- Make decisions from error codes, not error messages. Error messages can change without notice ([Best practices for the Compute Engine API](https://docs.cloud.google.com/compute/docs/api/best-practices)).

## Restrict the data

### Partial responses

By default, the server returns the full resource. The `fields` parameter asks for only some fields. It changes only the response data, not the data that you send ([Improve Performance](https://docs.cloud.google.com/compute/docs/api/how-tos/performance)).

| Syntax | Example | Result |
|---|---|---|
| Comma-separated list | `fields=etag,items` | The `etag` field and all items |
| Path with `/` | `fields=items/title` | Only `title` in each item. The response also has the parent objects |
| Sub-selector with `( )` | `fields=kind,items(title,characteristics/length)` | `kind`, plus `title` and `characteristics/length` in each item |
| Wildcard `*` | `fields=items/pagemap/*` | All objects in `pagemap` |

Source: [Improve Performance](https://docs.cloud.google.com/compute/docs/api/how-tos/performance).

An invalid `fields` value returns `400 Bad Request` with a message such as `Invalid field selection a/b`. Use pagination together with partial responses. Without it, you can lose the gain from partial responses ([Improve Performance](https://docs.cloud.google.com/compute/docs/api/how-tos/performance)).

In the API design rules, a field mask that you omit defaults to `*`, which returns all fields. Some APIs use a view enum (`BASIC` or `FULL`) instead of a field mask ([AIP-157](https://google.aip.dev/157)).

### System parameters for efficient calls

| URL parameter | Header | Use it to |
|---|---|---|
| `$fields` or `fields` | `X-Goog-FieldMask` | Return only the listed fields |
| `$prettyPrint` or `prettyPrint` | | Turn off pretty-printed JSON with `false`. The default is `true` |
| `quotaUser` | `X-Goog-Quota-User` | Charge per-user quotas to a pseudo user ID. Needs an API key with service restrictions, or the API ignores it |
| `$userProject` | `X-Goog-User-Project` | Choose the project for quota and billing. Needs `serviceusage.services.use` on that project |
| | `X-Server-Timeout` | Set the time, in seconds, for the server to finish a REST request |

Source: [System parameters](https://docs.cloud.google.com/apis/docs/system-parameters).

gRPC APIs accept system parameters only as headers, with lowercase keys ([System parameters](https://docs.cloud.google.com/apis/docs/system-parameters)).

### Send less with PATCH

A `PATCH` request changes only the fields that you send. Fields that you leave out keep their values. An array is the exception: if you send an array, it replaces the whole array. A `PUT` request clears optional fields that you do not send, so `PATCH` is safer ([Improve Performance](https://docs.cloud.google.com/compute/docs/api/how-tos/performance)). Google APIs generally support `PATCH` with an `update_mask` field, and not `PUT` ([AIP-134](https://google.aip.dev/134)).

If a firewall or proxy blocks `PATCH`, send a `POST` request with the header `X-HTTP-Method-Override: PATCH` ([Improve Performance](https://docs.cloud.google.com/compute/docs/api/how-tos/performance), [System parameters](https://docs.cloud.google.com/apis/docs/system-parameters)). [Designing and deploying REST and gRPC APIs](note:1.1-api-design) explains the standard methods.

## Batch requests

Each HTTP connection has overhead. A batch request puts many API calls into one HTTP request, which reduces network overhead and latency ([Sending batch requests](https://docs.cloud.google.com/storage/docs/batch)).

| | Compute Engine API | Cloud Storage JSON API |
|---|---|---|
| Endpoint | The `batchPath` in the discovery document. The default is `/batch/api_name/api_version` | `https://storage.googleapis.com/batch/storage/v1` |
| Calls in one batch | Up to 1,000. All calls go to the same API | No more than 100. The payload must be less than 10 MB |
| Use it for | Many calls, for example to sync many updates and deletes | Metadata updates, such as permissions, and deletes on many objects. Not uploads or downloads |
| Usage | n calls count as n requests | n calls count as n requests for usage and for operations costs |

Sources: [Batching requests](https://docs.cloud.google.com/compute/docs/api/how-tos/batch), [Sending batch requests](https://docs.cloud.google.com/storage/docs/batch).

A batch request uses the `multipart/mixed` content type, with one nested HTTP request in each part. Each nested request uses only the path of the URL. The headers of the outer request apply to every part, unless a part sets its own value. The responses come back in the same order as the requests ([Batching requests](https://docs.cloud.google.com/compute/docs/api/how-tos/batch)).

The server can run the calls in any order. If two calls must run in a fixed order, send the first call alone and wait for its response ([Batching requests](https://docs.cloud.google.com/compute/docs/api/how-tos/batch)).

### Batching in client libraries

The Python client library for Cloud Storage has a batch context manager:

```python
from google.cloud import storage

client = storage.Client()
bucket = client.bucket(bucket_name)
blobs_to_patch = [blob for blob in bucket.list_blobs(prefix=prefix)]
# The batch request is sent out when the context manager closes.
# No more than 100 calls should be included in a single batch request.
with client.batch():
    for blob in blobs_to_patch:
        metadata = {"your-metadata-key": "your-metadata-value"}
        blob.metadata = metadata
        blob.patch()
```

Source: [Sending batch requests](https://docs.cloud.google.com/storage/docs/batch).

The C++, C#, and Go client libraries for Cloud Storage do not support batch requests ([Sending batch requests](https://docs.cloud.google.com/storage/docs/batch)).

The Pub/Sub publisher client puts messages into batches. In Python, `BatchSettings` sets `max_messages` (default 100), `max_bytes` (default 1 MB), and `max_latency` (default 10 ms). To turn off batching, set `max_messages` to 1. One batch publish request can have at most 1,000 messages or 10 MB ([Batch messaging](https://docs.cloud.google.com/pubsub/docs/batch-messaging)). [Publishing and consuming messages with Pub/Sub](note:4.1-messaging) covers the publisher code.

### Batch methods

Some APIs have batch methods, such as `:batchGet` and `:batchCreate`. A batch get reads a set of resources at one consistent point in time, and it succeeds or fails for all of them. A synchronous batch create must be atomic. Only an asynchronous batch create, which returns a long-running operation, can allow partial success ([AIP-231](https://google.aip.dev/231), [AIP-233](https://google.aip.dev/233)).

For Compute Engine bursts, use dedicated batch APIs when possible, such as the bulk instance API or managed instance groups ([Best practices for the Compute Engine API](https://docs.cloud.google.com/compute/docs/api/best-practices)).

## Paginate results

A List method returns one page at a time. The request has `page_size` and `page_token`. The response has `next_page_token` ([AIP-158](https://google.aip.dev/158)).

| Rule | What the client does |
|---|---|
| `page_size` is optional. Above the maximum, the API lowers it to the maximum | Ask for the page size that you need. Do not depend on the exact count |
| A page can have fewer items, or none, before the end | Do not stop when a page is short |
| An empty `next_page_token` is the only end signal | Loop until `next_page_token` is empty |
| Other request parameters must stay the same between pages | Send the same filter with each `page_token`. A change can give `INVALID_ARGUMENT` |
| Page tokens are opaque and can expire. A rule of thumb is three days | Do not parse page tokens or keep them for a long time |

Source: [AIP-158](https://google.aip.dev/158).

Compute Engine returns at most 500 items (`maxResults`) if you do not paginate ([Best practices for the Compute Engine API](https://docs.cloud.google.com/compute/docs/api/best-practices)). If you iterate over the result of `list()` in a client library, the library makes the page requests for you. To work page by page, use the `pages` attribute:

```python
import google.cloud.compute_v1 as compute_v1

images_client = compute_v1.ImagesClient()
# Listing only non-deprecated images to reduce the size of the reply.
images_list_request = compute_v1.ListImagesRequest(
    project=project, max_results=page_size, filter="deprecated.state != DEPRECATED"
)
# Use the `pages` attribute of returned iterable to have more granular control of
# iteration over paginated results from the API. Each time you want to access the
# next page, the library retrieves that page from the API.
for page_num, page in enumerate(
    images_client.list(request=images_list_request).pages, start=1
):
    print(f"Page {page_num}: ")
    for img in page.items:
        print(f" - {img.name}")
```

Source: [Using client libraries](https://docs.cloud.google.com/compute/docs/api/using-libraries).

## Cache results

| What to cache | How |
|---|---|
| A resource that has an ETag | Keep a local copy with its ETag. Send the ETag in `If-None-Match`. On `304 Not Modified`, use the local copy. Otherwise, the server sends the new resource and a new ETag |
| A Cloud Storage object | Send `If-None-Match` with the ETag, or `If-Modified-Since` with a time. The response is `304 Not Modified` when your copy is current |
| A repeated BigQuery query | BigQuery returns cached results for the exact same query, for about 24 hours. The cache is best-effort |
| An ID token for a service call | The token expires about one hour after creation. If you cache it, check its `exp` claim. The metadata server always returns a valid token |

Sources: [Prevent FHIR resource conflicts using ETags](https://docs.cloud.google.com/healthcare-api/docs/fhir-etag), [Download an object](https://docs.cloud.google.com/storage/docs/xml-api/get-object-download), [Use cached query results](https://docs.cloud.google.com/bigquery/docs/cached-results), [Authenticating service-to-service](https://docs.cloud.google.com/run/docs/authenticating/service-to-service).

For application data that many instances share, see [Caching with Memorystore and Cloud CDN](note:1.1-caching).

BigQuery does not use the cache in these cases ([Use cached query results](https://docs.cloud.google.com/bigquery/docs/cached-results)):

- The job configuration names a destination table.
- A referenced table or view changed, or a table recently received streaming inserts.
- The query uses non-deterministic functions such as `CURRENT_TIMESTAMP()`, or a wildcard table.
- The query reads an external source other than Cloud Storage, or a table with row-level security.

A cache hit sets `statistics.query.cacheHit` to `true`. To force a new run, set `configuration.query.useQueryCache` to `false` ([Use cached query results](https://docs.cloud.google.com/bigquery/docs/cached-results)).

## Handle errors and retry

### Which errors to retry

| HTTP error | Retry? |
|---|---|
| `408`, `429`, `500`, `502`, `503`, `504`, and lost or failed connections | Yes, with exponential backoff, if the request is safe to repeat |
| `404` from IAM soon after you create a resource | Optional. IAM reads are eventually consistent |
| `409 ABORTED` from IAM | Retry the whole read-modify-write sequence, not only the write |
| Authorization failures and invalid requests | No. Log the error and fix the cause |

Sources: [Retry strategy](https://docs.cloud.google.com/storage/docs/retry-strategy), [Retry failed requests](https://docs.cloud.google.com/iam/docs/retry-strategy).

AIP-194 gives the rules for automatic retry of gRPC status codes:

| gRPC code | Automatic retry |
|---|---|
| `UNAVAILABLE` | Yes, for unary, non-transactional requests that are safe to repeat |
| `CANCELLED`, `DEADLINE_EXCEEDED`, `INVALID_ARGUMENT`, `DATA_LOSS` | Never |
| `RESOURCE_EXHAUSTED`, `INTERNAL`, `UNKNOWN` | Generally no. `RESOURCE_EXHAUSTED` can mean a used-up quota that takes hours to return, and retries can have billing effects. Show `INTERNAL` and `UNKNOWN` to the application at once |
| `ABORTED` | Not for one request. Retry at a higher level, for example the whole transaction |
| `NOT_FOUND`, `ALREADY_EXISTS`, `PERMISSION_DENIED`, `UNAUTHENTICATED`, `FAILED_PRECONDITION`, `OUT_OF_RANGE`, `UNIMPLEMENTED` | No. The state must change first |

Source: [AIP-194](https://google.aip.dev/194).

The two lists differ. AIP-194 says generally not to retry `RESOURCE_EXHAUSTED` and `INTERNAL` automatically. The Cloud Storage and IAM docs retry `429` and `500` with backoff ([AIP-194](https://google.aip.dev/194), [Retry strategy](https://docs.cloud.google.com/storage/docs/retry-strategy)).

### Quota errors

A quota error is HTTP `429` for a REST call and `ResourceExhausted` for a gRPC call. Compute Engine returns `403 QUOTA_EXCEEDED`, or `403 RATE_LIMIT_EXCEEDED` for a rate quota ([Troubleshoot quota errors](https://docs.cloud.google.com/docs/quotas/troubleshoot)).

| Quota type | When it comes back | What to do |
|---|---|---|
| Per-minute rate quota | One minute after the first request, in a rolling window | Retry with backoff that leaves time for the quota to refill |
| Per-day rate quota | At midnight Pacific Time | Wait until the next day, or request a quota adjustment |

Sources: [Cloud Quotas overview](https://docs.cloud.google.com/docs/quotas/overview), [Best practices for the Compute Engine API](https://docs.cloud.google.com/compute/docs/api/best-practices), [Troubleshoot quota errors](https://docs.cloud.google.com/docs/quotas/troubleshoot).

The Service Usage docs recommend exponential intervals plus randomness. The minimum wait is 30 seconds for `429` quota errors, and 1 second for `500` and `503` errors ([Troubleshoot issues (Service Usage)](https://docs.cloud.google.com/service-usage/docs/troubleshooting)).

### Truncated exponential backoff with jitter

The IAM docs give this algorithm, and the Compute Engine docs point to it as their example ([Retry failed requests](https://docs.cloud.google.com/iam/docs/retry-strategy), [Best practices for the Compute Engine API](https://docs.cloud.google.com/compute/docs/api/best-practices)):

1. If the request fails, wait 1 second plus a random fraction of a second, then retry.
2. If it fails again, wait 2 seconds plus a random fraction, then 4 seconds plus a random fraction, and so on.
3. Before each retry, wait `min((2^n + random-fraction), maximum-backoff)`, where `n` starts at 0. Use a new random fraction, 1 or less, for each retry. Typical `maximum-backoff` values are 32 or 64 seconds.
4. Stop retrying after a deadline, for example 300 seconds for a CI/CD pipeline that is not time-sensitive.

Source: [Retry failed requests](https://docs.cloud.google.com/iam/docs/retry-strategy).

### Idempotency decides what is safe to retry

| Cloud Storage operation | Idempotency | Retry rule |
|---|---|---|
| All get and list requests, bucket insert and delete | Always idempotent | Safe to retry |
| Object or bucket update with `ifMetagenerationMatch` or an `etag`, object write with `ifGenerationMatch` | Conditionally idempotent | Safe only when the precondition is in the request |
| Create an HMAC key, create a Pub/Sub notification, ACL changes | Never idempotent | Do not retry unconditionally. Handle duplicates |

Source: [Retry strategy](https://docs.cloud.google.com/storage/docs/retry-strategy).

A precondition that fails returns `412 Precondition Failed`, for example `If-Match` with an old ETag ([Download an object](https://docs.cloud.google.com/storage/docs/xml-api/get-object-download)). In an API that you design, a `request_id` field makes a retry safe: the server detects the duplicate and processes the request only once ([AIP-155](https://google.aip.dev/155)).

### Client library retry settings

Cloud Client Libraries retry for you, but the defaults differ by library ([Retry strategy](https://docs.cloud.google.com/storage/docs/retry-strategy)):

- The Python library for Cloud Storage retries idempotent operations. By default, it also retries `Objects: insert`, `Objects: delete`, and `Objects: patch`. The first wait is 1 second, the multiplier is 2, the maximum wait is 60 seconds, and the deadline is 120 seconds.
- The C++ library retries even operations that are never idempotent, unless you use `StrictIdempotencyPolicy`.

```python
from google.cloud import storage
from google.cloud.storage.retry import DEFAULT_RETRY

storage_client = storage.Client()
bucket = storage_client.bucket(bucket_name)
blob = bucket.blob(blob_name)
# Customize retry with a timeout of 500 seconds (default=120 seconds).
modified_retry = DEFAULT_RETRY.with_timeout(500.0)
# Customize retry with an initial wait time of 1.5 (default=1.0).
# Customize retry with a wait time multiplier per iteration of 1.2 (default=2.0).
# Customize retry with a maximum wait time of 45.0 (default=60.0).
modified_retry = modified_retry.with_delay(initial=1.5, multiplier=1.2, maximum=45.0)
blob.delete(retry=modified_retry)
```

Source: [Retry strategy](https://docs.cloud.google.com/storage/docs/retry-strategy).

AIP-4221 says that client libraries retry without an opt-in, and that users must be able to turn off the retries. For gRPC clients, a `RetryPolicy` in the gRPC service config sets values such as `maxAttempts`, `initialBackoff`, `maxBackoff`, `backoffMultiplier`, and `retryableStatusCodes` ([AIP-4221](https://google.aip.dev/client-libraries/4221)).

### Retry anti-patterns

| Anti-pattern | Problem | Fix |
|---|---|---|
| Retry without backoff | Cascading failures | Exponential backoff with jitter |
| Unconditional retry of non-idempotent operations | Unintended overwrites or deletes | Handle duplicates, or do not retry |
| Retry of permanent errors | An infinite loop, for example on an authorization failure | Retry only `408`, `429`, `5xx`, and connection errors |
| No retry limit | Resource exhaustion in the application | A total retry duration for latency-sensitive work |
| Retries on top of library retries | Three app retries times three library retries is nine attempts | Configure the built-in retries, or limit retries in one layer |

Source: [Retry strategy](https://docs.cloud.google.com/storage/docs/retry-strategy).

### Protect your rate quota

The Compute Engine docs list these practices to preserve rate quotas ([Best practices for the Compute Engine API](https://docs.cloud.google.com/compute/docs/api/best-practices)):

- Avoid short polling. Use the `wait` method for an operation, in a retry loop with exponential backoff.
- Use bursting sparingly, and use batch APIs for a burst.
- Use a client-side rate limiter, so that one client cannot use all the quota.
- Split applications across projects, because quotas apply per project.

[Calling Google Cloud APIs](note:4.2-calling-google-apis) explains which project's quota a call uses.

## Exam traps

- **A short page means the end of the list.** Only an empty `next_page_token` means the end ([AIP-158](https://google.aip.dev/158)).
- **A batch request to save quota.** A batch of n calls counts as n requests ([Batching requests](https://docs.cloud.google.com/compute/docs/api/how-tos/batch)).
- **A Cloud Storage batch request for uploads.** Cloud Storage does not support batch uploads or downloads ([Sending batch requests](https://docs.cloud.google.com/storage/docs/batch)).
- **Two dependent calls in one batch.** The server can run batched calls in any order ([Batching requests](https://docs.cloud.google.com/compute/docs/api/how-tos/batch)).
- **`fields` to make an update request smaller.** `fields` changes only the response. Use `PATCH` for the request ([Improve Performance](https://docs.cloud.google.com/compute/docs/api/how-tos/performance)).
- **`PUT` to change one field.** `PUT` clears optional fields that you do not send ([Improve Performance](https://docs.cloud.google.com/compute/docs/api/how-tos/performance)).
- **A `PATCH` that adds one item to an array.** The array in the request replaces the whole array ([Improve Performance](https://docs.cloud.google.com/compute/docs/api/how-tos/performance)).
- **Immediate retries in a tight loop.** They can cause cascading failures. Use exponential backoff with jitter ([Retry strategy](https://docs.cloud.google.com/storage/docs/retry-strategy)).
- **A retry of `PERMISSION_DENIED` or `INVALID_ARGUMENT`.** These errors do not go away on retry ([AIP-194](https://google.aip.dev/194)).
- **An application retry loop around a client library call.** The retries multiply ([Retry strategy](https://docs.cloud.google.com/storage/docs/retry-strategy)).
- **Code that parses error messages.** Use the error codes. Messages can change without notice ([Best practices for the Compute Engine API](https://docs.cloud.google.com/compute/docs/api/best-practices)).
- **BigQuery cached results with `CURRENT_TIMESTAMP()` or a destination table.** These queries are not cached ([Use cached query results](https://docs.cloud.google.com/bigquery/docs/cached-results)).
