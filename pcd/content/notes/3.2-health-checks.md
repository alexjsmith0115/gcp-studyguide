## Why it matters

Kubernetes uses probes to decide three things: whether a container has started, whether to restart it, and whether to send it traffic. GKE load balancers run their own health checks, which do not always follow the probes. The exam tests which probe solves which problem, the settings that control timing, the mistakes that cause restart loops or outages, and a clean shutdown.

## Key points

- A startup probe checks whether the app has started. Until it succeeds, Kubernetes does not run the liveness and readiness probes ([Liveness, Readiness, and Startup Probes | Kubernetes](https://kubernetes.io/docs/concepts/workloads/pods/probes/)).
- A liveness probe decides when to restart a container, for example after a deadlock ([Liveness, Readiness, and Startup Probes | Kubernetes](https://kubernetes.io/docs/concepts/workloads/pods/probes/)).
- A readiness probe decides when a container can take traffic. A failure removes the Pod from the Service endpoints, but the container keeps running ([Liveness, Readiness, and Startup Probes | Kubernetes](https://kubernetes.io/docs/concepts/workloads/pods/probes/)).
- A probe uses one of four mechanisms: `httpGet`, `tcpSocket`, `grpc`, or `exec` ([Liveness, Readiness, and Startup Probes | Kubernetes](https://kubernetes.io/docs/concepts/workloads/pods/probes/)).
- GKE uses readiness probes to add Pods to load balancers and liveness probes to restart Pods. Google says that probe logic must never access other services ([Best practices for running cost-optimized Kubernetes applications on GKE](https://docs.cloud.google.com/architecture/best-practices-for-running-cost-effective-kubernetes-applications-on-gke)).
- Repeated liveness failures restart the container again and again. This can cause a `CrashLoopBackOff` state ([Troubleshoot CrashLoopBackOff events](https://docs.cloud.google.com/kubernetes-engine/docs/troubleshooting/crashloopbackoff-events)).
- A load balancer health check is not a Kubernetes probe. It runs outside the cluster, and each backend service has its own ([About GKE Ingress routing and security](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/ingress-routing-security)).
- GKE Ingress can copy health check settings from a readiness probe. GKE Gateway does not, so you configure a HealthCheckPolicy ([About GKE Ingress routing and security](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/ingress-routing-security), [Configure Gateway resources using Policies](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/configure-gateway-resources)).
- At shutdown, the kubelet runs the `preStop` hook and then sends TERM. After the grace period, which is 30 seconds by default, it sends KILL ([Pod Lifecycle | Kubernetes](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/)).
- A PodDisruptionBudget (PDB) limits voluntary disruptions, such as node drains. It does not limit a Deployment rolling update ([Disruptions | Kubernetes](https://kubernetes.io/docs/concepts/workloads/pods/disruptions/)).
- Cloud Run also has startup, liveness, and readiness probes. If you set no startup probe, Cloud Run adds a default TCP startup probe ([Configure container health checks for services](https://docs.cloud.google.com/run/docs/configuring/healthchecks)).

## The three probes

Each probe answers a different question, and each failure has a different result:

| Probe | Question | When it runs | On failure |
|---|---|---|---|
| Startup | Has the app finished its start? | Only at startup, until it succeeds | The kubelet kills the container, and the restart policy applies |
| Liveness | Is the container stuck? | Periodically, after any startup probe succeeds | The kubelet restarts the container |
| Readiness | Can the container take traffic now? | Periodically, for the whole life of the container | The Pod leaves the Service endpoints. The container keeps running |

Sources: [Liveness, Readiness, and Startup Probes | Kubernetes](https://kubernetes.io/docs/concepts/workloads/pods/probes/).

If a container has no probe of a type, the kubelet treats the result of that probe as success ([Liveness, Readiness, and Startup Probes | Kubernetes](https://kubernetes.io/docs/concepts/workloads/pods/probes/)). Use this table to choose:

| Situation | Use | Why |
|---|---|---|
| Start time can be more than `initialDelaySeconds + failureThreshold × periodSeconds` | A startup probe on the liveness endpoint, with a high `failureThreshold` | Slow starts do not cause restarts, and the liveness settings stay unchanged |
| The app can deadlock while its process keeps running | A liveness probe | A restart is the only recovery |
| The process exits by itself when it fails | No liveness probe is necessary | The kubelet follows the restart policy |
| The app must load a cache before it can serve | A readiness probe that passes only after the load | The Pod gets no traffic until it is ready |
| The app must stop taking traffic for a short time | A readiness probe on its own endpoint | The Pod leaves the endpoints without a restart |

Sources: [Liveness, Readiness, and Startup Probes | Kubernetes](https://kubernetes.io/docs/concepts/workloads/pods/probes/), [Best practices for running cost-optimized Kubernetes applications on GKE](https://docs.cloud.google.com/architecture/best-practices-for-running-cost-effective-kubernetes-applications-on-gke).

## Probe mechanisms and settings

| Mechanism | Success when | What to know |
|---|---|---|
| `httpGet` | The status code is from 200 to 399 | The kubelet sends it to the Pod IP. With HTTPS, it skips the certificate check |
| `tcpSocket` | The port is open | It checks only that a connection opens |
| `grpc` | The response status is `SERVING` | The app must implement gRPC health checks |
| `exec` | The command exits with status 0 | Each run starts new processes. On dense nodes, this adds CPU load |

Sources: [Liveness, Readiness, and Startup Probes | Kubernetes](https://kubernetes.io/docs/concepts/workloads/pods/probes/).

| Setting | Default | Meaning |
|---|---|---|
| `initialDelaySeconds` | 0 | Seconds after the container starts before the first probe |
| `periodSeconds` | 10 | Seconds between probes |
| `timeoutSeconds` | 1 | Seconds before one probe times out |
| `failureThreshold` | 3 | Failures in a row before the check fails |
| `successThreshold` | 1 | Successes in a row after a failure. It must be 1 for liveness and startup probes |
| `terminationGracePeriodSeconds` (probe level) | The Pod value | Grace period after a liveness or startup failure. Readiness probes cannot set it |

Sources: [Liveness, Readiness, and Startup Probes | Kubernetes](https://kubernetes.io/docs/concepts/workloads/pods/probes/).

This container gives the app up to 300 seconds (30 × 10) to start. After that, the liveness probe restarts it after three failures, and the readiness probe uses a separate `/ready` endpoint:

```yaml
spec:
  containers:
  - name: app
    image: registry.k8s.io/e2e-test-images/agnhost:2.40
    ports:
    - containerPort: 8080
    startupProbe:
      httpGet:
        path: /healthz
        port: 8080
      failureThreshold: 30
      periodSeconds: 10
    livenessProbe:
      httpGet:
        path: /healthz
        port: 8080
      initialDelaySeconds: 10
      periodSeconds: 5
      timeoutSeconds: 3
      failureThreshold: 3
    readinessProbe:
      httpGet:
        path: /ready
        port: 8080
      periodSeconds: 5
```

Source: [Liveness, Readiness, and Startup Probes | Kubernetes](https://kubernetes.io/docs/concepts/workloads/pods/probes/).

## Design rules and common mistakes

- **Keep probes simple and local.** If the app can serve at once, an HTTP endpoint that returns 200 is a good default. Google says to never make probe logic access other services, because slow services can damage the Pod lifecycle ([Best practices for running cost-optimized Kubernetes applications on GKE](https://docs.cloud.google.com/architecture/best-practices-for-running-cost-effective-kubernetes-applications-on-gke)).
- **Use liveness only for failures that a restart fixes.** A liveness probe must show an unrecoverable failure, such as a deadlock. A bad liveness probe can cause cascading failures: restarts under high load, failed client requests, and more load on the other Pods ([Liveness, Readiness, and Startup Probes | Kubernetes](https://kubernetes.io/docs/concepts/workloads/pods/probes/)).
- **Know the two views on dependencies.** The Kubernetes docs show a readiness probe that also checks required back-end services. The GKE guidance says that no probe should access other services ([Liveness, Readiness, and Startup Probes | Kubernetes](https://kubernetes.io/docs/concepts/workloads/pods/probes/), [Best practices for running cost-optimized Kubernetes applications on GKE](https://docs.cloud.google.com/architecture/best-practices-for-running-cost-effective-kubernetes-applications-on-gke)).
- **Share one cheap endpoint.** A common pattern uses the same endpoint for liveness and readiness, with a higher `failureThreshold` for liveness. The Pod then goes not-ready before the kubelet kills it ([Liveness, Readiness, and Startup Probes | Kubernetes](https://kubernetes.io/docs/concepts/workloads/pods/probes/)).
- **Define a readiness probe for all containers.** If the app loads a cache at startup, report ready only after the load completes ([Best practices for running cost-optimized Kubernetes applications on GKE](https://docs.cloud.google.com/architecture/best-practices-for-running-cost-effective-kubernetes-applications-on-gke)).
- **Allow for slow starts.** Resource contention causes probe timeouts, which are a major cause of liveness failures. If the app has temporary errors at startup, increase `initialDelaySeconds` or `failureThreshold` ([Troubleshoot CrashLoopBackOff events](https://docs.cloud.google.com/kubernetes-engine/docs/troubleshooting/crashloopbackoff-events)).

In `CrashLoopBackOff`, the delay before each restart grows exponentially (for example 10s, 20s, 40s), up to five minutes. To confirm the cause, query the kubelet logs in Logs Explorer. Use `kubectl logs POD_NAME --previous` to read the logs of the container that stopped ([Troubleshoot CrashLoopBackOff events](https://docs.cloud.google.com/kubernetes-engine/docs/troubleshooting/crashloopbackoff-events)):

```text
resource.type="k8s_node"
log_id("kubelet")
jsonPayload.MESSAGE:"failed liveness probe, will be restarted"
```

Source: [Troubleshoot CrashLoopBackOff events](https://docs.cloud.google.com/kubernetes-engine/docs/troubleshooting/crashloopbackoff-events).

## Load balancer health checks on GKE

Probes control the kubelet. The load balancer health check controls the Google Cloud load balancer. When GKE copies settings from a readiness probe, it does not keep the two in sync ([About GKE Ingress routing and security](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/ingress-routing-security)).

| Topic | GKE Ingress | GKE Gateway |
|---|---|---|
| Source of the settings | A BackendConfig, then the readiness probe, then defaults | A HealthCheckPolicy, then defaults |
| Reads the readiness probe | Yes, if the Pods exist when you create the Ingress. Later probe changes are not copied | No |
| Default request path | `/` | `/` |
| Success | HTTP 200 only | HTTP 200 only. A redirect, 401, or 403 marks the backend unhealthy |
| Default interval | 15 seconds with container-native load balancing, 60 seconds with instance groups | 15 seconds without a HealthCheckPolicy. 5 seconds if a HealthCheckPolicy omits `checkIntervalSec` |
| Google recommendation | A BackendConfig for the most control | A HealthCheckPolicy. It is required if `/` does not return 200 |

Sources: [About GKE Ingress routing and security](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/ingress-routing-security), [GKE Ingress for Application Load Balancers](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/ingress), [Configure Gateway resources using Policies](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/configure-gateway-resources), [Best practices for GKE networking](https://docs.cloud.google.com/kubernetes-engine/docs/best-practices/networking).

Rules for Ingress health checks:

- Inference from the readiness probe needs `containerPort` in the Pod spec and `targetPort` in the Service. Without them, the path is `/` ([About GKE Ingress routing and security](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/ingress-routing-security)).
- If the probe sets HTTP headers other than `Host`, GKE uses the default values ([About GKE Ingress routing and security](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/ingress-routing-security)).
- Use a BackendConfig if Pods have several containers or if you need control of the port ([About GKE Ingress routing and security](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/ingress-routing-security)).
- The Ingress controller creates firewall rules for the health check ranges `130.211.0.0/22` and `35.191.0.0/16` ([GKE Ingress for Application Load Balancers](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/ingress)).

```yaml
apiVersion: cloud.google.com/v1
kind: BackendConfig
metadata:
  name: http-hc-config
spec:
  healthCheck:
    checkIntervalSec: 15
    port: 15020
    type: HTTPS
    requestPath: /healthz
```

Source: [About GKE Ingress routing and security](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/ingress-routing-security).

A Gateway health check cannot send custom headers, such as `Authorization`. Allow unauthenticated access to the health check path. The Service in the policy must also be in an HTTPRoute. A HealthCheckPolicy or a GCPBackendPolicy must be in the same namespace as its target Service ([Configure Gateway resources using Policies](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/configure-gateway-resources)). This policy shows the HTTP fields:

```yaml
apiVersion: networking.gke.io/v1
kind: HealthCheckPolicy
metadata:
  name: lb-healthcheck
  namespace: lb-service-namespace
spec:
  default:
    checkIntervalSec: INTERVAL
    timeoutSec: TIMEOUT
    healthyThreshold: HEALTHY_THRESHOLD
    unhealthyThreshold: UNHEALTHY_THRESHOLD
    config:
      type: PROTOCOL
      httpHealthCheck:
        port: PORT
        requestPath: REQUEST_PATH
  targetRef:
    group: ""
    kind: Service
    name: lb-service
```

Source: [Configure Gateway resources using Policies](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/configure-gateway-resources).

**Readiness gates.** Container-native load balancing through Ingress adds the `cloud.google.com/load-balancer-neg-ready` readiness gate to Pods. During a rolling update, a new Pod must pass the load balancer health check before GKE removes an old Pod. If the health check is wrong, the rollout stalls after the first new Pod. Without container-native load balancing, you control the replacement rate with `minReadySeconds` ([About GKE Ingress routing and security](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/ingress-routing-security)). For Ingress and Gateway setup, see [Deploying to GKE](note:3.2-gke-deployments).

## Graceful shutdown

When Kubernetes deletes a Pod, it gives the containers time to finish their work ([Pod Lifecycle | Kubernetes](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/), [Container Lifecycle Hooks | Kubernetes](https://kubernetes.io/docs/concepts/containers/container-lifecycle-hooks/)):

1. The grace period starts. It is `terminationGracePeriodSeconds`, which is 30 seconds by default.
2. If a container has a `preStop` hook, the kubelet runs it. The TERM signal waits until the hook completes.
3. The kubelet sends TERM to process 1 in each container.
4. When shutdown starts, the control plane also marks the Pod endpoints as not ready. Load balancers then stop sending regular traffic to the Pod.
5. When the grace period ends, the runtime sends `SIGKILL` to the processes that are still running.

The grace period covers the `preStop` hook and the normal stop together. With 60 seconds, a 55-second hook, and a 10-second stop, the kubelet kills the container before it stops ([Container Lifecycle Hooks | Kubernetes](https://kubernetes.io/docs/concepts/containers/container-lifecycle-hooks/)).

Google gives these rules for a clean shutdown ([Best practices for running cost-optimized Kubernetes applications on GKE](https://docs.cloud.google.com/architecture/best-practices-for-running-cost-effective-kubernetes-applications-on-gke)):

- Do not stop accepting requests right after `SIGTERM`. Kubernetes updates endpoints and load balancers asynchronously, so new requests can still arrive.
- If you cannot change the app, add a `preStop` hook that sleeps a few seconds.
- Handle `SIGTERM` to clean up and to save in-memory state.
- Set `terminationGracePeriodSeconds` for the needs of the app. High values slow node upgrades and rollouts.
- With container-native load balancing, start to fail the readiness probe when the app receives `SIGTERM`.

```yaml
    lifecycle:
      preStop:
        exec:
          command: ["/bin/sh","-c","nginx -s quit; while killall -0 nginx; do sleep 1; done"]
```

Source: [Attach Handlers to Container Lifecycle Events | Kubernetes](https://kubernetes.io/docs/tasks/configure-pod-container/attach-handler-lifecycle-event/).

## PodDisruptionBudgets

A PDB sets how many Pods of an app a voluntary disruption can take down at the same time. Tools that respect PDBs use the Eviction API, for example `kubectl drain` ([Disruptions | Kubernetes](https://kubernetes.io/docs/concepts/workloads/pods/disruptions/)).

| Event | Does the PDB limit it? |
|---|---|
| Node drain with `kubectl drain`, or a GKE node upgrade | Yes. In a surge upgrade, GKE respects the PDB and the grace period for up to one hour, then evicts the remaining Pods |
| Cluster autoscaler scale-down | Yes. The autoscaler does not remove a node if the removal exceeds the PDB |
| Deployment rolling update | No. `maxUnavailable` in the Deployment controls it |
| Direct deletion of Pods or Deployments | No. Deletion bypasses PDBs |
| Hardware failure or other involuntary disruption | No, but it counts against the budget |

Sources: [Disruptions | Kubernetes](https://kubernetes.io/docs/concepts/workloads/pods/disruptions/), [Node upgrade strategies](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/node-pool-upgrade-strategies), [About GKE cluster autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/cluster-autoscaler).

Google calls a PDB for every application a best practice, because the cluster autoscaler respects it at scale-down ([Best practices for running cost-optimized Kubernetes applications on GKE](https://docs.cloud.google.com/architecture/best-practices-for-running-cost-effective-kubernetes-applications-on-gke)). The Kubernetes docs recommend `maxUnavailable` over `minAvailable`, because it follows changes to the replica count ([Specifying a Disruption Budget for your Application | Kubernetes](https://kubernetes.io/docs/tasks/run-application/configure-pdb/)).

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: zk-pdb
spec:
  maxUnavailable: 1
  selector:
    matchLabels:
      app: zookeeper
```

Source: [Specifying a Disruption Budget for your Application | Kubernetes](https://kubernetes.io/docs/tasks/run-application/configure-pdb/).

## Cloud Run probes compared

Cloud Run uses the same three probe names, but the behavior is not the same:

| Behavior | GKE (Kubernetes) | Cloud Run |
|---|---|---|
| If you set no probe | The kubelet treats the result as success | Cloud Run adds a TCP startup probe |
| HTTP success | Status 200 to 399 | Any 2XX or 3XX response |
| Liveness failure | The kubelet restarts the container | `SIGKILL`. Requests in progress get HTTP 503, and autoscaling starts a new instance |
| Readiness failure | The Pod leaves the Service endpoints | No new requests. The instance keeps running. With session affinity, requests still go to it |
| Shutdown | TERM, then KILL after the grace period (30 seconds by default) | `SIGTERM`, then `SIGKILL` after 10 seconds |

Sources: [Liveness, Readiness, and Startup Probes | Kubernetes](https://kubernetes.io/docs/concepts/workloads/pods/probes/), [Pod Lifecycle | Kubernetes](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/), [Configure container health checks for services](https://docs.cloud.google.com/run/docs/configuring/healthchecks), [Container runtime contract](https://docs.cloud.google.com/run/docs/container-contract).

On Cloud Run, Google recommends that the startup probe also covers readiness. Cloud Run can send traffic to a new instance before the first readiness probe completes. A startup probe must succeed within `failureThreshold × periodSeconds`, which cannot exceed 600 seconds (1800 with GPUs). HTTP probe endpoints use HTTP/1 and are externally accessible ([Configure container health checks for services](https://docs.cloud.google.com/run/docs/configuring/healthchecks)).

```bash
gcloud run deploy SERVICE \
    --image=IMAGE_URL \
    --liveness-probe httpGet.path=PATH,httpGet.port=CONTAINER_PORT,initialDelaySeconds=DELAY,failureThreshold=THRESHOLD,timeoutSeconds=TIMEOUT,periodSeconds=PERIOD
```

Source: [Configure container health checks for services](https://docs.cloud.google.com/run/docs/configuring/healthchecks).

## Exam traps

- **A liveness probe that checks the database.** Probe logic must not access other services. A bad liveness probe causes cascading restarts ([Best practices for running cost-optimized Kubernetes applications on GKE](https://docs.cloud.google.com/architecture/best-practices-for-running-cost-effective-kubernetes-applications-on-gke), [Liveness, Readiness, and Startup Probes | Kubernetes](https://kubernetes.io/docs/concepts/workloads/pods/probes/)).
- **A slow-starting app in `CrashLoopBackOff`.** Add a startup probe, or increase `initialDelaySeconds` or `failureThreshold` ([Liveness, Readiness, and Startup Probes | Kubernetes](https://kubernetes.io/docs/concepts/workloads/pods/probes/), [Troubleshoot CrashLoopBackOff events](https://docs.cloud.google.com/kubernetes-engine/docs/troubleshooting/crashloopbackoff-events)).
- **"A readiness failure restarts the container."** It only removes the Pod from the endpoints ([Liveness, Readiness, and Startup Probes | Kubernetes](https://kubernetes.io/docs/concepts/workloads/pods/probes/)).
- **"Change the readiness probe to fix the Ingress health check."** Changes after the Ingress exists are not copied. Use a BackendConfig ([GKE Ingress for Application Load Balancers](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/ingress), [About GKE Ingress routing and security](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/ingress-routing-security)).
- **"Gateway reads the readiness probe."** It does not. Configure a HealthCheckPolicy ([Configure Gateway resources using Policies](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/configure-gateway-resources)).
- **A health path that redirects or needs login.** The load balancer needs HTTP 200. A 301, 302, 401, or 403 marks the backend unhealthy ([Configure Gateway resources using Policies](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/configure-gateway-resources)).
- **"The PDB protects the Deployment rollout."** Rolling updates are not limited by PDBs. Use `maxUnavailable` ([Disruptions | Kubernetes](https://kubernetes.io/docs/concepts/workloads/pods/disruptions/)).
- **An app that exits at once on `SIGTERM`.** Endpoints update asynchronously. Finish requests in progress, or add a `preStop` sleep ([Best practices for running cost-optimized Kubernetes applications on GKE](https://docs.cloud.google.com/architecture/best-practices-for-running-cost-effective-kubernetes-applications-on-gke)).
- **A `preStop` hook longer than the grace period.** The grace period covers the hook and the stop. Increase `terminationGracePeriodSeconds` ([Pod Lifecycle | Kubernetes](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/), [Container Lifecycle Hooks | Kubernetes](https://kubernetes.io/docs/concepts/containers/container-lifecycle-hooks/)).
- **Cloud Run readiness with session affinity.** Requests still go to the instance after its readiness check fails ([Configure container health checks for services](https://docs.cloud.google.com/run/docs/configuring/healthchecks)).
