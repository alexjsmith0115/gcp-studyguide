## Why it matters

A container that ignores the platform rules fails in ways that are hard to see. It does not start, it loses data, or it drops requests when it stops. The exam tests the Cloud Run container runtime contract, image practices, and the choice between a Dockerfile and buildpacks. It also tests how to split a monolith, pass configuration, and write logs. This page covers how to build the container. For the deploy commands, see [Deploying to Cloud Run from source code](note:3.1-deploy-from-source) and [Deploying containerized applications to GKE](note:3.2-gke-deployments).

## Key points

- **Listen on `0.0.0.0` at `PORT`.** The ingress container must listen on `0.0.0.0`, not `127.0.0.1`, on the port in the `PORT` variable. The default port is 8080 ([Container runtime contract](https://docs.cloud.google.com/run/docs/container-contract)).
- **Linux x86_64 only.** Cloud Run runs the Linux x86_64 ABI. A multi-architecture image must include `linux/amd64` ([Container runtime contract](https://docs.cloud.google.com/run/docs/container-contract)).
- **The file system is in memory.** Writes use the instance memory, and the data is lost when the instance stops ([Container runtime contract](https://docs.cloud.google.com/run/docs/container-contract)).
- **Shutdown sends `SIGTERM`, then `SIGKILL` 10 seconds later.** In the first generation execution environment, an instance that does not trap `SIGTERM` shuts down at once. In the second generation, Google recommends a `SIGTERM` handler ([Container runtime contract](https://docs.cloud.google.com/run/docs/container-contract)).
- **The app must start fast.** A Cloud Run service must listen within 4 minutes of start ([Container runtime contract](https://docs.cloud.google.com/run/docs/container-contract)).
- **Small, maintained, non-root images.** Use maintained base images, include only what the service needs, rebuild often to get security fixes, and set a non-root `USER` ([General development tips](https://docs.cloud.google.com/run/docs/tips/general)).
- **One app per container.** Run one application with one parent process in each container ([7 Google best practices for building containers](https://cloud.google.com/blog/products/containers-kubernetes/7-best-practices-for-building-containers)).
- **A Dockerfile is optional.** On `gcloud run deploy --source`, Cloud Build uses the Dockerfile if one exists. If not, Google Cloud's buildpacks detect the language and build the image ([Deploy services from source code](https://docs.cloud.google.com/run/docs/deploying-source-code)).
- **Configuration in environment variables, secrets in Secret Manager.** Google does not recommend environment variables for secrets ([Configure environment variables for services](https://docs.cloud.google.com/run/docs/configuring/services/environment-variables)).
- **Logs go to `stdout` and `stderr`.** Cloud Logging collects them. A single line of JSON becomes a structured entry ([Logging and viewing logs in Cloud Run](https://docs.cloud.google.com/run/docs/logging), [About GKE logs](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/about-logs)).
- **Split a monolith one component at a time,** and give each new service its own data ([Learning Path: Transform a monolith into a GKE app - Modularize the monolith](https://docs.cloud.google.com/kubernetes-engine/docs/learn/cymbal-books/lp1/modular)).

## The Cloud Run container runtime contract

| Topic | Rule | Effect if you ignore it |
|---|---|---|
| Port | The ingress container listens on `0.0.0.0` at `$PORT` (default 8080) | Deploy error: "Container failed to start. Failed to start and then listen on the port defined by the PORT environment variable." |
| Architecture | Executables for 64-bit Linux, x86_64 ABI | An image built on an Arm machine might not work; build it with Cloud Build |
| Startup | Listen within 4 minutes; requests wait for up to 3.5 times the average startup time, or 10 seconds, whichever is greater | A request can wait for a new instance to start, so slow startup adds latency |
| File system | In memory; writes count against the memory limit; data does not persist | Large temporary files can crash the instance |
| Memory | Stay under the memory limit | Cloud Run terminates the instance, and its requests fail with HTTP 500 |
| Shutdown | `SIGTERM`, then 10 seconds, then `SIGKILL`; CPU is allocated and billed during the 10 seconds | Telemetry that is not flushed is lost |
| Privileges | No privileged mode, no `sudo`, no `setuid` binaries | Tools such as `sudo` can fail with insufficient permissions |
| User | Set `USER` to a user that exists in the image | If the user name does not exist, Cloud Run runs the container as root (`uid=0`) |
| Jobs | Exit with code 0 on success and a non-zero code on failure; do not listen on a port | Job status depends on the exit code |

Sources: [Container runtime contract](https://docs.cloud.google.com/run/docs/container-contract), [Troubleshoot Cloud Run issues](https://docs.cloud.google.com/run/docs/troubleshooting), [General development tips](https://docs.cloud.google.com/run/docs/tips/general), [Graceful shutdowns on Cloud Run: Deep dive](https://cloud.google.com/blog/topics/developers-practitioners/graceful-shutdowns-cloud-run-deep-dive).

Cloud Run sets `K_SERVICE`, `K_REVISION`, and `K_CONFIGURATION` in all service containers, and `PORT` in the ingress container. Job tasks get `CLOUD_RUN_TASK_INDEX` (starting at 0), `CLOUD_RUN_TASK_ATTEMPT`, and `CLOUD_RUN_TASK_COUNT` ([Container runtime contract](https://docs.cloud.google.com/run/docs/container-contract)).

### Stateless by design

Cloud Run can shut down an idle instance at any time, including instances that minimum instances keep warm ([Container runtime contract](https://docs.cloud.google.com/run/docs/container-contract)). Keep no data in the instance that another request needs later. When you migrate a web service, replace local file storage with Cloud Storage, or with a database such as Firestore or Cloud SQL ([Migrate an existing web service](https://docs.cloud.google.com/run/docs/migrate/a-web-service)). A global variable can still cache an expensive object, because Cloud Run reuses instances. A request cannot know whether it gets that reuse ([General development tips](https://docs.cloud.google.com/run/docs/tips/general)).

When the app needs a file path, use a volume mount:

| Need | Volume type | Limit to know |
|---|---|---|
| Scratch space with a size cap | In-memory volume | Uses container memory; with a size limit, writes fail instead of crashing the instance |
| Objects in a bucket as files | Cloud Storage volume (Cloud Storage FUSE, no install needed) | No file locking: the last write wins; not fully POSIX |
| A shared network file system | NFS volume | Second generation execution environment only |

Sources: [Configure in-memory volume mounts for services](https://docs.cloud.google.com/run/docs/configuring/services/in-memory-volume-mounts), [Configure Cloud Storage volume mounts for Cloud Run services](https://docs.cloud.google.com/run/docs/configuring/services/cloud-storage-volume-mounts), [Select an execution environment for services](https://docs.cloud.google.com/run/docs/configuring/execution-environments).

### Execution environments

The first generation environment uses gVisor, starts fast, and emulates most system calls. The second generation environment is a microVM with full Linux compatibility, faster CPU and network, and NFS support. Both have the same price. Use the first generation for bursty traffic, cold-start-sensitive services, or less than 512 MiB of memory. Use the second generation for steady traffic, CPU-heavy work, NFS, or software that needs all system calls. Jobs and worker pools always use the second generation ([Select an execution environment for services](https://docs.cloud.google.com/run/docs/configuring/execution-environments)).

## Graceful shutdown

**On Cloud Run,** the signal usually comes when Cloud Run scales in instances that get no traffic. Use the handler to flush telemetry, log the shutdown, and close database connections ([Graceful shutdowns on Cloud Run: Deep dive](https://cloud.google.com/blog/topics/developers-practitioners/graceful-shutdowns-cloud-run-deep-dive)). When an instance with requests in progress must stop, Cloud Run lets those requests finish and sends new requests to other instances ([Container runtime contract](https://docs.cloud.google.com/run/docs/container-contract)).

**The process must receive the signal.** Kubernetes and Docker send stop signals to the process with PID 1 ([7 Google best practices for building containers](https://cloud.google.com/blog/products/containers-kubernetes/7-best-practices-for-building-containers)). The shell form `ENTRYPOINT node server.js` runs the app under `/bin/sh -c`, and the shell does not forward signals. Use the exec form, `ENTRYPOINT ["node", "server.js"]`. If one container must start several processes, use an init process such as tini or dumb-init ([Graceful shutdowns on Cloud Run: Deep dive](https://cloud.google.com/blog/topics/developers-practitioners/graceful-shutdowns-cloud-run-deep-dive)).

**On GKE,** Kubernetes updates endpoints and load balancers asynchronously, so a Pod can get new requests after `SIGTERM` ([Best practices for running cost-optimized Kubernetes applications on GKE](https://docs.cloud.google.com/architecture/best-practices-for-running-cost-effective-kubernetes-applications-on-gke)):

1. Do not stop accepting requests right after `SIGTERM`. Finish requests in progress, and keep listening for new connections.
2. If you cannot change the app, for example nginx, add a `preStop` hook that sleeps for a few seconds.
3. Use the `SIGTERM` handler to clean up and save in-memory state.
4. Set `terminationGracePeriodSeconds` if 30 seconds (the default) is not enough. Keep it under 10 minutes, because Cluster Autoscaler honors it for only 10 minutes.
5. With container-native load balancing, start to fail the readiness probe when `SIGTERM` arrives.

For probes and `preStop` details, see [Kubernetes health checks: liveness, readiness, and startup probes](note:3.2-health-checks).

## Writing the Dockerfile

This Python Dockerfile from the Cloud Run docs shows three practices. It copies the dependency list before the code, so a code change does not repeat `pip install`. It sets `PYTHONUNBUFFERED` so that logs appear at once. It starts Gunicorn with `exec` and binds to `$PORT`.

```dockerfile
FROM python:3.14

# Allow statements and log messages to immediately appear in the Cloud Run logs
ENV PYTHONUNBUFFERED True

# Copying this separately prevents re-running pip install on every code change.
COPY requirements.txt ./
RUN pip install -r requirements.txt

ENV APP_HOME /app
WORKDIR $APP_HOME
COPY . ./

# Use gunicorn webserver with one worker process and 8 threads.
# Timeout is set to 0 to disable the timeouts of the workers to allow Cloud Run to handle instance scaling.
CMD exec gunicorn --bind :$PORT --workers 1 --threads 8 --timeout 0 main:app
```

Source: [Use Pub/Sub with Cloud Run tutorial](https://docs.cloud.google.com/run/docs/tutorials/pubsub).

For more vCPUs, set the Gunicorn workers equal to the cores, and then tune the threads. Too many workers or threads increase cold start time and memory use ([Optimize Python applications for Cloud Run](https://docs.cloud.google.com/run/docs/tips/python)).

A multi-stage build keeps the compiler and build tools out of the runtime image. The first stage builds the binary. The second stage copies only the binary into a slim base image:

```dockerfile
FROM golang:1.25-bookworm as builder
WORKDIR /app
COPY go.* ./
RUN go mod download
COPY . ./
RUN go build -v -o server

FROM debian:bookworm-slim
RUN set -x && apt-get update && DEBIAN_FRONTEND=noninteractive apt-get install -y \
    ca-certificates && \
    rm -rf /var/lib/apt/lists/*
COPY --from=builder /app/server /server
CMD ["/server"]
```

Source: [Use Pub/Sub with Cloud Run tutorial](https://docs.cloud.google.com/run/docs/tutorials/pubsub).

## Image practices

| Practice | Reason |
|---|---|
| Use actively maintained base images, such as Google base images or Docker Hub official images | They receive security updates |
| Rebuild and redeploy regularly | The new image picks up security fixes |
| Include only what the service needs; start from a lean base such as `alpine` or `scratch` | Extra packages and tools add vulnerabilities |
| Use multi-stage builds for tool-heavy builds | The runtime image stays small |
| Pin software and library versions | The build is deterministic and has no unverified code |
| Run as a non-root user with the `USER` instruction | Less privilege inside the container |
| Turn on vulnerability scanning in Artifact Registry | It scans the images that you store |
| Package one application per container | Signals work, debugging is easier, and each part scales on its own |
| Add source code late in the Dockerfile | Docker reuses cached layers for the base image and dependencies |

Sources: [General development tips](https://docs.cloud.google.com/run/docs/tips/general), [7 Google best practices for building containers](https://cloud.google.com/blog/products/containers-kubernetes/7-best-practices-for-building-containers).

**Image size and startup.** On Cloud Run, image streaming means that the image size does not change startup time or request time. The image also does not use instance memory ([General development tips](https://docs.cloud.google.com/run/docs/tips/general)). On GKE, size matters: each new node that Cluster Autoscaler adds must download the images, so a smaller image scales out faster ([Best practices for running cost-optimized Kubernetes applications on GKE](https://docs.cloud.google.com/architecture/best-practices-for-running-cost-effective-kubernetes-applications-on-gke)).

**Helper processes.** The Google guidance is one application with one parent process per container. For example, do not put PHP and MySQL in one container ([7 Google best practices for building containers](https://cloud.google.com/blog/products/containers-kubernetes/7-best-practices-for-building-containers)). On Cloud Run, put a helper in a sidecar container. An instance can have up to 10 containers, with one ingress container. The containers share the network namespace and can share an in-memory volume. Typical sidecars are a proxy such as Envoy, a monitoring agent, or the AlloyDB Auth Proxy ([Deploy container images to Cloud Run services](https://docs.cloud.google.com/run/docs/deploying)).

**Where the image comes from.** Docker Hub rate limits apply to pulls on the Docker Free plan, so move base images to Artifact Registry ([Containerize your code](https://docs.cloud.google.com/run/docs/building/containerize-your-code)). Deploy by digest, not by tag, because a tag can point to a new image later ([About container image digests](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/about-container-images)). For repositories, scanning, and digests, see [Building containers with Cloud Build and storing them in Artifact Registry](note:2.2-cloud-build-artifact-registry) and [Protecting apps and finding vulnerabilities](note:1.2-protect-and-scan).

## Dockerfile or buildpacks

| | Dockerfile | Google Cloud's buildpacks |
|---|---|---|
| You provide | A Dockerfile and the source | Only the source and its dependency file |
| Language and base image | You choose them | The builder detects the language and uses a secure base image managed by Google |
| Start command | `CMD` or `ENTRYPOINT` | A default per language, or a `Procfile`, or `GOOGLE_ENTRYPOINT` |
| OS and runtime patches | You rebuild and redeploy | Automatic base image updates on Cloud Run are possible, with no rebuild and no new revision |
| Best for | Custom libraries, utilities, configuration files, and startup processes | Apps in a supported language with the common build steps for that language |

Sources: [Deploy services from source code](https://docs.cloud.google.com/run/docs/deploying-source-code), [Google Cloud's buildpacks](https://docs.cloud.google.com/docs/buildpacks/overview), [Build a Python application](https://docs.cloud.google.com/docs/buildpacks/python), [Configure automatic base image updates](https://docs.cloud.google.com/run/docs/configuring/services/automatic-base-image-updates), [Using system packages tutorial](https://docs.cloud.google.com/run/docs/tutorials/system-packages), [General development tips](https://docs.cloud.google.com/run/docs/tips/general).

For a Cloud Run source deploy with Python 3.13 or later, the Python buildpack picks the entrypoint from `requirements.txt`. With no web server or framework listed, it uses `gunicorn -b :8080 main:app`. A `Procfile` or the `GOOGLE_ENTRYPOINT` variable overrides the default ([Build a Python application](https://docs.cloud.google.com/docs/buildpacks/python)). Automatic base image updates work only with Google Cloud's buildpacks base images ([Configure automatic base image updates](https://docs.cloud.google.com/run/docs/configuring/services/automatic-base-image-updates)).

## Refactoring a monolith into services

Google's GKE learning path splits a monolith in four steps ([Learning Path: Transform a monolith into a GKE app - Modularize the monolith](https://docs.cloud.google.com/kubernetes-engine/docs/learn/cymbal-books/lp1/modular)):

1. Identify the distinct functions of the app.
2. Create one module for each function, for example one route handler in each new app.
3. Let the modules communicate through endpoints, for example with REST or gRPC.
4. Give each module access to only the data that it needs.

In production, modularize one component at a time. Integrate it with the monolith and test it before the next one. Google calls the mixed state a "microlith" ([Learning Path: Transform a monolith into a GKE app - Modularize the monolith](https://docs.cloud.google.com/kubernetes-engine/docs/learn/cymbal-books/lp1/modular)).

**Do not share one database.** The learning path calls a shared data source a frequent mistake. It causes tight coupling, because a schema change forces an update to every module that uses the data. A failure in one module can spread to the others, and the shared source can become a bottleneck. Give each module its own data source, or replicate or partition the data ([Learning Path: Transform a monolith into a GKE app - Modularize the monolith](https://docs.cloud.google.com/kubernetes-engine/docs/learn/cymbal-books/lp1/modular)).

**Replace `localhost` addresses.** When the modular app runs on one machine, the modules call each other at addresses such as `http://localhost:8081`. On Kubernetes, Pods move between machines, so the code must use Service names such as `http://book-details-service` ([Learning Path: Transform a monolith into a GKE app - Prepare the modular app for containerization](https://docs.cloud.google.com/kubernetes-engine/docs/learn/cymbal-books/lp1/prep-containerization)).

**Where to draw the boundary.** A component with a different availability requirement or scaling profile is a good candidate for its own service. Aim for stateless services, and keep the stateful ones clearly separate. Use circuit breakers, exponential backoff, and graceful degradation, so that one failure does not cascade ([Patterns for scalable and resilient apps](https://docs.cloud.google.com/architecture/scalable-and-resilient-apps)). For service identity between the parts, see [Secure service-to-service communication](note:1.2-service-to-service). For queues between them, see [Asynchronous and event-driven integration with Pub/Sub and Eventarc](note:1.1-async-events).

## Configuration and logs

**Environment variables** hold configuration for one revision. A Dockerfile `ENV` sets a default, and a value set on the Cloud Run service takes precedence ([Configure environment variables for services](https://docs.cloud.google.com/run/docs/configuring/services/environment-variables)).

| Rule | Detail |
|---|---|
| `--set-env-vars` and `--env-vars-file` replace | They delete every variable that is not in the new list or file |
| `--update-env-vars` merges | It adds or changes variables and keeps the others |
| No secrets in variables | Store secrets in Secret Manager |
| No key files | Never set `GOOGLE_APPLICATION_CREDENTIALS` on a Cloud Run service; use a user-managed service account as the service identity |
| Limits | Up to 1,000 variables; up to 32 Kb each |

Sources: [Configure environment variables for services](https://docs.cloud.google.com/run/docs/configuring/services/environment-variables), [gcloud run deploy](https://docs.cloud.google.com/sdk/gcloud/reference/run/deploy).

For secrets, see [Secrets, credentials, and keys](note:1.2-secrets-and-keys). For the service identity, see [Service accounts, IAM roles, and least privilege](note:1.2-service-accounts-least-privilege).

**Logs.** Cloud Run collects logs from `stdout`, `stderr`, files under `/var/log`, and syslog ([Logging and viewing logs in Cloud Run](https://docs.cloud.google.com/run/docs/logging)). On GKE, a logging agent on each node reads `stdout` and `stderr`. Lines on `stdout` get severity `INFO` and lines on `stderr` get `ERROR`, unless a JSON `severity` field sets it ([About GKE logs](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/about-logs)). On both platforms, print one line of JSON to get a structured entry in `jsonPayload`:

```python
import json

entry = dict(
    severity="NOTICE",
    message="This is the default display field.",
    component="arbitrary-property",
)
print(json.dumps(entry))
```

Source: [Logging and viewing logs in Cloud Run](https://docs.cloud.google.com/run/docs/logging).

For trace fields and log-based metrics, see [Instrumenting code with logs, metrics, and traces](note:4.3-instrumentation).

## Exam traps

- **The app listens on `localhost` or `127.0.0.1`.** The container fails to start. Listen on `0.0.0.0` at `$PORT` ([Troubleshoot Cloud Run issues](https://docs.cloud.google.com/run/docs/troubleshooting)).
- **An image built on an Arm laptop.** It might not run on Cloud Run. Build it with Cloud Build, or include `linux/amd64` ([Troubleshoot Cloud Run issues](https://docs.cloud.google.com/run/docs/troubleshooting), [Container runtime contract](https://docs.cloud.google.com/run/docs/container-contract)).
- **Large files in `/tmp`.** They use instance memory and can crash the instance. Delete temporary files, or use an in-memory volume with a size limit ([General development tips](https://docs.cloud.google.com/run/docs/tips/general), [Configure in-memory volume mounts for services](https://docs.cloud.google.com/run/docs/configuring/services/in-memory-volume-mounts)).
- **A shell-form `ENTRYPOINT`.** The shell does not forward `SIGTERM`, so cleanup code never runs. Use the exec form ([Graceful shutdowns on Cloud Run: Deep dive](https://cloud.google.com/blog/topics/developers-practitioners/graceful-shutdowns-cloud-run-deep-dive)).
- **`--set-env-vars` to add one variable.** It removes all the others. Use `--update-env-vars` ([Configure environment variables for services](https://docs.cloud.google.com/run/docs/configuring/services/environment-variables)).
- **A service account key in `GOOGLE_APPLICATION_CREDENTIALS`.** Never set it on Cloud Run. Use the service identity ([Configure environment variables for services](https://docs.cloud.google.com/run/docs/configuring/services/environment-variables)).
- **A smaller image to fix Cloud Run cold starts.** Image size does not affect Cloud Run startup. Use startup CPU boost, minimum instances, or fewer startup dependencies ([General development tips](https://docs.cloud.google.com/run/docs/tips/general)).
- **`sudo` or privileged mode on Cloud Run.** Cloud Run has no privileged mode and does not support `setuid` binaries ([Container runtime contract](https://docs.cloud.google.com/run/docs/container-contract)).
- **One database for all new microservices.** The docs call this a frequent mistake. Give each service its own data ([Learning Path: Transform a monolith into a GKE app - Modularize the monolith](https://docs.cloud.google.com/kubernetes-engine/docs/learn/cymbal-books/lp1/modular)).
- **The same tag pushed again for a fix.** New Pods can run the old or the new image. Deploy by digest ([About container image digests](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/about-container-images)).
- **A GKE app that exits at once on `SIGTERM`.** Clients get errors while endpoints update. Keep serving, or add a `preStop` sleep ([Best practices for running cost-optimized Kubernetes applications on GKE](https://docs.cloud.google.com/architecture/best-practices-for-running-cost-effective-kubernetes-applications-on-gke)).
