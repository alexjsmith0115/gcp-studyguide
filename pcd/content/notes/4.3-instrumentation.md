## Why it matters

Instrumentation is the code that makes an application emit logs, metrics, and traces. The developer decides the log format, the instrumentation library, the export path, and the identity that writes the data. The exam tests the pattern that Google recommends for each platform. That pattern is JSON logs to standard output, OpenTelemetry for traces and metrics, and a collector where the platform supports one. Wrong answers often add an agent that the platform does not need, or a metric label with unlimited values.

## Key points

- Cloud Monitoring, Cloud Logging, and Cloud Trace are on by default in a new project. They collect telemetry and audit logs for most Google Cloud services automatically ([Observability in Google Cloud](https://docs.cloud.google.com/stackdriver/docs)).
- Google recommends a vendor-neutral framework such as OpenTelemetry instead of product-specific APIs or client libraries, even when you send telemetry only to Google Cloud ([Observability in Google Cloud](https://docs.cloud.google.com/stackdriver/docs), [Observability for application developers](https://docs.cloud.google.com/stackdriver/docs/instrumentation/overview)).
- On Cloud Run, Cloud Run functions, and GKE, write JSON-structured logs to `stdout` and `stderr`. The platform collects them automatically ([Choose an instrumentation approach](https://docs.cloud.google.com/stackdriver/docs/instrumentation/choose-approach)).
- Special JSON fields such as `severity`, `message`, `logging.googleapis.com/labels`, and `logging.googleapis.com/trace` move into the matching `LogEntry` fields ([Logging and viewing logs in Cloud Run](https://docs.cloud.google.com/run/docs/logging), [Configure the Logging agent](https://docs.cloud.google.com/logging/docs/agent/logging/configuration)).
- For metrics and traces, Google recommends an OpenTelemetry collector when the environment supports one. Otherwise, the process exports directly to the Telemetry API ([Choose an instrumentation approach](https://docs.cloud.google.com/stackdriver/docs/instrumentation/choose-approach)).
- The Telemetry (OTLP) API (`telemetry.googleapis.com`) accepts logs, metrics, and traces in the OpenTelemetry Protocol (OTLP) format. The writer needs the Cloud Telemetry Writer role and a quota project ([Telemetry (OTLP) API overview](https://docs.cloud.google.com/stackdriver/docs/reference/telemetry/overview)).
- On Cloud Run, run the collector as a sidecar and use instance-based billing, because OpenTelemetry instrumentation does background processing ([Choose an instrumentation approach](https://docs.cloud.google.com/stackdriver/docs/instrumentation/choose-approach)).
- Log-based metrics turn matching log entries into Cloud Monitoring metrics. A user-defined log-based metric counts only the entries that arrive after you create it ([Log-based metrics overview](https://docs.cloud.google.com/logging/docs/logs-based-metrics)).
- Do not use timestamps, unique identifiers, user IDs, IP addresses, or unparameterized URLs as metric labels ([Components of the metric model](https://docs.cloud.google.com/monitoring/api/v3/metric-model)).
- Managed collection for Managed Service for Prometheus is Google's recommended approach for all Kubernetes environments ([Google Cloud Managed Service for Prometheus](https://docs.cloud.google.com/stackdriver/docs/managed-prometheus)).
- Cloud Profiler continuously collects CPU and memory-allocation data from production code with low overhead. You add a language-specific agent library to the application ([Cloud Profiler overview](https://docs.cloud.google.com/profiler/docs/about-profiler)).

## The services of Google Cloud Observability

Google Cloud Observability (formerly Stackdriver) is the set of services that store and analyze telemetry ([Modernization path for .NET applications on Google Cloud](https://docs.cloud.google.com/dotnet/docs/modernization-path-dotnet-applications-google-cloud)).

| Service | What it stores | How your code feeds it |
|---|---|---|
| Cloud Logging | Timestamped log entries | JSON lines on `stdout` and `stderr`, or the Cloud Logging client library |
| Cloud Monitoring | Metric time series, uptime checks, alerting policies, and SLOs | OpenTelemetry or Prometheus metrics through a collector, the Monitoring API, or log-based metrics |
| Cloud Trace | The spans of a request across services | The OpenTelemetry SDK with an OTLP exporter. Cloud Run and Cloud Run functions also send HTTP request latency automatically |
| Error Reporting | Error groups | Stack traces in log entries, the Error Reporting client library, or the Error Reporting API |
| Cloud Profiler | Profiles of CPU use and memory allocation | A profiling agent library in the process |

Sources: [Observability in Google Cloud](https://docs.cloud.google.com/stackdriver/docs), [Logging and viewing logs in Cloud Run](https://docs.cloud.google.com/run/docs/logging), [User-defined metrics overview](https://docs.cloud.google.com/monitoring/custom-metrics), [Synthetic monitoring overview](https://docs.cloud.google.com/monitoring/uptime-checks/introduction), [Alerting overview](https://docs.cloud.google.com/monitoring/alerts), [Concepts in service monitoring](https://docs.cloud.google.com/stackdriver/docs/solutions/slo-monitoring), [Cloud Trace overview](https://docs.cloud.google.com/trace/docs/overview), [Collect error data by using Error Reporting](https://docs.cloud.google.com/error-reporting/docs/setup), [Cloud Profiler overview](https://docs.cloud.google.com/profiler/docs/about-profiler).

## The recommended pattern for each platform

| Platform | Logs | Metrics | Traces |
|---|---|---|---|
| Cloud Run | JSON to `stdout` and `stderr` | OpenTelemetry SDK and OTLP exporter, sent to an OpenTelemetry collector sidecar. For Prometheus-format metrics only, use the Prometheus sidecar | The same collector sidecar. Use instance-based billing |
| Cloud Run functions | JSON to `stdout` and `stderr` | Writing metric data directly is not supported. Use log-based metrics | OpenTelemetry SDK and the Cloud Trace exporter |
| GKE | JSON to `stdout` and `stderr` | Managed Service for Prometheus: Prometheus client libraries with managed collection, or OpenTelemetry with the Google-Built OpenTelemetry Collector | The Google-Built OpenTelemetry Collector on GKE, which sends the data to the Telemetry API |
| Compute Engine | JSON to a file, read by an Ops Agent receiver | The Ops Agent OTLP receiver | The Ops Agent OTLP receiver |

Source: [Choose an instrumentation approach](https://docs.cloud.google.com/stackdriver/docs/instrumentation/choose-approach).

For log statements, Google recommends a framework that can write JSON. Examples are `logging` for Python, `slog` for Go, Pino for JavaScript, and SLF4J with Log4j2 for Java ([Choose an instrumentation approach](https://docs.cloud.google.com/stackdriver/docs/instrumentation/choose-approach)).

### Collector-based or direct export

| | Collector-based export (recommended) | Direct export |
|---|---|---|
| Application code | OpenTelemetry SDK and an OTLP exporter. The code stays vendor neutral | OpenTelemetry SDK that sends data to the Telemetry API. The code has vendor-specific dependencies |
| Extra process | A collector, such as the Google-Built OpenTelemetry Collector or an Ops Agent receiver | None |
| Use it when | The compute environment supports a collector | A separate collector process is not practical |

Source: [Choose an instrumentation approach](https://docs.cloud.google.com/stackdriver/docs/instrumentation/choose-approach).

- **Telemetry API endpoint.** In a collector, set only the root URL `https://telemetry.googleapis.com`. OpenTelemetry adds `/v1/traces`, `/v1/metrics`, or `/v1/logs` ([Telemetry (OTLP) API overview](https://docs.cloud.google.com/stackdriver/docs/reference/telemetry/overview)).
- **Older Google exporters.** A Google Cloud trace exporter converts OTLP data into the format of the Cloud Trace API, and the conversion can lose data. Google recommends that you move to the OTLP endpoint ([Migrate from the Trace exporter to the OTLP endpoint](https://docs.cloud.google.com/stackdriver/docs/instrumentation/migrate-to-otlp-endpoints)).
- **Google-Built OpenTelemetry Collector.** It is Google's build of the upstream collector. It adds Google Cloud resource metadata, so you can correlate application data with infrastructure data ([Overview of the Google-Built OpenTelemetry Collector](https://docs.cloud.google.com/stackdriver/docs/instrumentation/google-built-otel)).

The Python instrumentation sample sets up OpenTelemetry once, at startup. This trimmed copy shows the trace and metric setup:

```python
def setup_opentelemetry() -> None:
    resource = Resource.create(
        attributes={
            # Use the PID as the service.instance.id to avoid duplicate timeseries
            # from different Gunicorn worker processes.
            SERVICE_INSTANCE_ID: f"worker-{os.getpid()}",
        }
    )
    tracer_provider = TracerProvider(resource=resource)
    tracer_provider.add_span_processor(BatchSpanProcessor(OTLPSpanExporter()))
    trace.set_tracer_provider(tracer_provider)

    reader = PeriodicExportingMetricReader(OTLPMetricExporter())
    meter_provider = MeterProvider(metric_readers=[reader], resource=resource)
    metrics.set_meter_provider(meter_provider)

# Initialize OpenTelemetry Python SDK and structured logging
setup_opentelemetry()
setup_structured_logging()

app = Flask(__name__)

# Add instrumentation
FlaskInstrumentor().instrument_app(app)
RequestsInstrumentor().instrument()
```

Source: [Python instrumentation sample](https://docs.cloud.google.com/stackdriver/docs/instrumentation/setup/python).

- The `opentelemetry-instrumentation-flask` and `opentelemetry-instrumentation-requests` libraries generate metrics and traces for the HTTP server and the HTTP client ([Python instrumentation sample](https://docs.cloud.google.com/stackdriver/docs/instrumentation/setup/python)).
- Gunicorn starts several worker processes. Each process needs a unique `service.instance.id`, so that their metrics do not conflict ([Python instrumentation sample](https://docs.cloud.google.com/stackdriver/docs/instrumentation/setup/python)).
- The `setup_structured_logging` function writes JSON logs that carry the trace ID. It is on the page [Trace IDs: correlating spans and logs](note:4.3-tracing-and-correlation).

## Structured logs

A log entry is structured when its payload is a JSON object in `jsonPayload`. You can query JSON paths and index fields. A string payload goes to `textPayload`, which you can search but not index ([Structured logging](https://docs.cloud.google.com/logging/docs/structured-logging)).

On Cloud Run, a single line of serialized JSON becomes `jsonPayload`. Cloud Run collects `stdout`, `stderr`, files under `/var/log`, syslog (`/dev/log`), and entries from the client libraries ([Logging and viewing logs in Cloud Run](https://docs.cloud.google.com/run/docs/logging)).

```python
import json

entry = dict(
    severity="NOTICE",
    message="This is the default display field.",
    # Logs Explorer shows this field as jsonPayload.component
    component="arbitrary-property",
)
print(json.dumps(entry))
```

Source: [Logging and viewing logs in Cloud Run](https://docs.cloud.google.com/run/docs/logging).

| JSON field | `LogEntry` field | Use it for |
|---|---|---|
| `severity` | `severity` | The level: `DEBUG`, `INFO`, `NOTICE`, `WARNING`, `ERROR`, `CRITICAL`, `ALERT`, or `EMERGENCY` |
| `message` | `textPayload`, or it stays in `jsonPayload` | The line that the Logs Explorer shows. Put an exception stack trace here, so that Error Reporting can parse it |
| `httpRequest` | `httpRequest` | Request data, such as the method |
| `time` (RFC 3339) | `timestamp` | The time of the event |
| `logging.googleapis.com/labels` | `labels` | Key-value pairs that classify the entry. The value must be a JSON object |
| `logging.googleapis.com/operation` | `operation` | Data about an operation. The Logs Explorer uses it to group related entries |
| `logging.googleapis.com/sourceLocation` | `sourceLocation` | The file, line, and function |
| `logging.googleapis.com/trace`, `logging.googleapis.com/spanId`, `logging.googleapis.com/trace_sampled` | `trace`, `spanId`, `traceSampled` | The link from the entry to a trace and span |

Sources: [Configure the Logging agent](https://docs.cloud.google.com/logging/docs/agent/logging/configuration), [LogEntry](https://docs.cloud.google.com/logging/docs/reference/v2/rest/v2/LogEntry).

How to fill the trace fields is in [Trace IDs: correlating spans and logs](note:4.3-tracing-and-correlation).

Platform rules that the exam can test:

- **No agent on Cloud Run.** Cloud Run has built-in log collection and does not use logging agents. Integrated logging does not use the quota for `entries.write` requests. For higher volume or reliability, call the Cloud Logging API directly, from a library or a sidecar ([Logging and viewing logs in Cloud Run](https://docs.cloud.google.com/run/docs/logging)).
- **Default severity on GKE.** Lines on standard output get `INFO`, and lines on standard error get `ERROR`. A `severity` field in a JSON line sets the level ([About GKE logs](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/about-logs)).
- **JSON limits on GKE.** Duplicate JSON keys are not supported, and `stream` is a reserved key. An entry over the `LogEntry` size limit is dropped if it is `jsonPayload` and truncated if it is `textPayload` ([About GKE logs](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/about-logs)). The limit is 256 KiB ([Quotas and limits](https://docs.cloud.google.com/logging/quotas)).
- **Compute Engine.** Use the Ops Agent to send structured logs. The legacy Logging agent has reached its end of support ([Structured logging](https://docs.cloud.google.com/logging/docs/structured-logging)).

### The Cloud Logging client library for Python

The client library connects the standard `logging` module to Cloud Logging. `setup_logging()` selects a handler for the environment ([Integration with logging Standard Library](https://docs.cloud.google.com/python/docs/reference/logging/latest/std-lib-integration)):

- `StructuredLogHandler` writes JSON to standard output. It is the default on GKE, Cloud Run functions, and Cloud Run.
- `CloudLoggingHandler` sends entries to the Cloud Logging API over the network. It is the default on most other environments, including local development.

```python
import logging
import google.cloud.logging

client = google.cloud.logging.Client()
client.setup_logging()  # selects a handler for this environment

logging.info("message field", extra={"json_fields": {"hello": "world"}})
```

Source: [Integration with logging Standard Library](https://docs.cloud.google.com/python/docs/reference/logging/latest/std-lib-integration).

The library also detects the `trace`, `span_id`, `trace_sampled`, `http_request`, and `source_location` fields ([Integration with logging Standard Library](https://docs.cloud.google.com/python/docs/reference/logging/latest/std-lib-integration)). To write through the library, the service account of the resource needs the Logs Writer role (`roles/logging.logWriter`) ([Setting Up Cloud Logging for Python](https://docs.cloud.google.com/logging/docs/setup/python)).

## Metrics

### Choose the metric source

| Requirement | Use | Why |
|---|---|---|
| Count an error message, or extract a latency value, from logs that you already write | A log-based metric | No code change. Counter metrics count entries. Distribution metrics put extracted values into histogram buckets |
| An application metric from Cloud Run or GKE, such as the number of background routines that the app started | OpenTelemetry metrics through a collector | Google recommends OpenTelemetry instead of direct calls to the Monitoring API |
| Existing Prometheus instrumentation on GKE | Managed Service for Prometheus with managed collection | Recommended for all Kubernetes environments. You keep your PromQL queries and Grafana dashboards. Data is kept for 24 months at no additional cost |
| A custom metric from Cloud Run functions | A log-based metric | Writing metric data directly is not supported |

Sources: [Log-based metrics overview](https://docs.cloud.google.com/logging/docs/logs-based-metrics), [User-defined metrics overview](https://docs.cloud.google.com/monitoring/custom-metrics), [Google Cloud Managed Service for Prometheus](https://docs.cloud.google.com/stackdriver/docs/managed-prometheus), [Choose an instrumentation approach](https://docs.cloud.google.com/stackdriver/docs/instrumentation/choose-approach).

User-defined metrics (also called custom metrics) are chargeable. User-defined log-based metrics are a class of custom metrics, so they are chargeable too ([User-defined metrics overview](https://docs.cloud.google.com/monitoring/custom-metrics), [Log-based metrics overview](https://docs.cloud.google.com/logging/docs/logs-based-metrics)).

### Labels and cardinality

Each unique combination of label values creates one time series. The total cardinality is the metric cardinality multiplied by the resource cardinality. Cardinality depends mostly on the number of values that each label can have, not on the number of labels ([Components of the metric model](https://docs.cloud.google.com/monitoring/api/v3/metric-model)).

- **Log-based metric labels.** You can define up to 10 user-defined labels for each metric. Each metric has a limit of about 30,000 active time series. Never extract a value that is unique for each entry, such as `insertId` or `timestamp` ([Configure labels on log-based metrics](https://docs.cloud.google.com/logging/docs/logs-based-metrics/labels)).
- **No backfill.** A user-defined log-based metric counts only the entries received after you create it. It counts both included and excluded entries ([Log-based metrics overview](https://docs.cloud.google.com/logging/docs/logs-based-metrics)).
- **One resource type.** Google recommends that the filter of a log-based metric names a single resource type ([Log-based metrics overview](https://docs.cloud.google.com/logging/docs/logs-based-metrics)).
- **Monitored resource for custom metrics.** `generic_task` or `generic_node` is usually a better choice than `global`. When many sources write to one `global` resource, their data can collide and overwrite each other ([User-defined metrics overview](https://docs.cloud.google.com/monitoring/custom-metrics)).

## Uptime checks, alerting policies, and SLOs

- **Uptime checks.** Checkers in several regions send HTTP, HTTPS, or TCP requests to a public or private endpoint ([Synthetic monitoring overview](https://docs.cloud.google.com/monitoring/uptime-checks/introduction)). A Cloud Run revision is a supported target. The default configuration has no authentication. Service Agent Authentication sends an identity token for the Monitoring service agent, for HTTPS checks only ([Create public uptime checks](https://docs.cloud.google.com/monitoring/uptime-checks)).
- **Synthetic monitors.** A synthetic monitor runs your own Node.js tests, for example a login flow, in a Cloud Run function ([Synthetic monitoring overview](https://docs.cloud.google.com/monitoring/uptime-checks/introduction)).
- **Alerting policies.** A metric-based policy uses a threshold, absence, forecast, or PromQL condition. A log-based policy fires when a message appears in a log entry. A SQL-based policy watches the results of a SQL query in Observability Analytics (formerly Log Analytics). SQL-based policies are in Public Preview ([Alerting overview](https://docs.cloud.google.com/monitoring/alerts), [Logging release notes](https://docs.cloud.google.com/logging/docs/release-notes)).
- **SLOs.** Cloud Run is a basic service type. Cloud Monitoring creates its SLI automatically as a `BasicSli`, which measures availability or latency. For a GKE service, you must define the SLI ([Constructs in the API](https://docs.cloud.google.com/stackdriver/docs/solutions/slo-monitoring/api/api-structures)). The error budget is (1 − SLO goal) × eligible events ([Concepts in service monitoring](https://docs.cloud.google.com/stackdriver/docs/solutions/slo-monitoring)).

## Traces and profiles

Cloud Run and Cloud Run functions send the latency of incoming and outgoing HTTP requests to Cloud Trace automatically ([Cloud Trace overview](https://docs.cloud.google.com/trace/docs/overview)). Add OpenTelemetry when you need custom spans, for example around a database query, or one trace across several services ([Using distributed tracing](https://docs.cloud.google.com/run/docs/trace)).

Google recommends the Telemetry API instead of the Cloud Trace API for trace data. Its limits are often more generous, it keeps the OTLP format, and some features, such as Application Monitoring, need it ([Cloud Trace overview](https://docs.cloud.google.com/trace/docs/overview)).

Cloud Profiler usually collects data for 10 seconds every minute for one instance of a service. The amortized overhead is commonly less than 0.5%, so you can leave it on in production ([Cloud Profiler overview](https://docs.cloud.google.com/profiler/docs/about-profiler)). For Python, the profile types are CPU time and wall time ([Profiling Python applications](https://docs.cloud.google.com/profiler/docs/profiling-python)).

```python
import googlecloudprofiler

try:
    googlecloudprofiler.start(
        service="hello-profiler",
        service_version="1.0.1",
    )
except (ValueError, NotImplementedError) as exc:
    print(exc)  # handle errors here
```

Source: [Profiling Python applications](https://docs.cloud.google.com/profiler/docs/profiling-python).

Call `start` as early as possible. The `service` parameter is required, and `service_version` lets you filter by application version in the Profiler interface ([Profiling Python applications](https://docs.cloud.google.com/profiler/docs/profiling-python)). The supported configurations of Profiler are Compute Engine, GKE, App Engine, Dataflow, Managed Service for Apache Spark (Java only), and environments outside Google Cloud ([Cloud Profiler overview](https://docs.cloud.google.com/profiler/docs/about-profiler)).

## IAM roles for writing telemetry

| Data | Role for the writing service account | Notes |
|---|---|---|
| Logs through the Cloud Logging API or a client library | Logs Writer (`roles/logging.logWriter`) | Most Google Cloud environments give it to the default service account |
| Metrics through the Monitoring API or a collector | Monitoring Metric Writer (`roles/monitoring.metricWriter`) | The Cloud Run service identity needs it for the collector sidecar |
| Traces through the Cloud Trace API | Cloud Trace Agent (`roles/cloudtrace.agent`) | |
| Logs, metrics, and traces through the Telemetry API | Cloud Telemetry Writer (`roles/telemetry.writer`) | Has `logging.logEntries.create`, `monitoring.timeSeries.create`, and `telemetry.traces.write`. Also grant Service Usage Consumer (`roles/serviceusage.serviceUsageConsumer`) on the quota project |
| Only traces through the Telemetry API | Cloud Telemetry Traces Writer (`roles/telemetry.tracesWriter`) | Has only `telemetry.traces.write`. Use it for least privilege when the code sends only spans. The quota project rule also applies |
| Profiles | Cloud Profiler Agent (`roles/cloudprofiler.agent`) | Needed for a user-created service account. Without it, the project gets no profile data |
| Error events through the Error Reporting API | Error Reporting Writer (`roles/errorreporting.writer`) | |

## Exam traps

- **A logging agent for a Cloud Run service.** Cloud Run collects `stdout` and `stderr` itself and does not use logging agents ([Logging and viewing logs in Cloud Run](https://docs.cloud.google.com/run/docs/logging)).
- **Plain text on standard error for warnings on GKE.** GKE gives standard error lines the `ERROR` severity. Write JSON with a `severity` field ([About GKE logs](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/about-logs)).
- **The Cloud Trace API or a product-specific library for new code.** Google recommends OpenTelemetry with OTLP export, through a collector where possible ([Choose an instrumentation approach](https://docs.cloud.google.com/stackdriver/docs/instrumentation/choose-approach), [Cloud Trace overview](https://docs.cloud.google.com/trace/docs/overview)).
- **A user ID or a request URL as a metric label.** Unbounded label values multiply the time series. Use a small set of discrete values ([Components of the metric model](https://docs.cloud.google.com/monitoring/api/v3/metric-model)).
- **A new log-based metric to chart last week's errors.** The metric counts only entries that arrive after you create it ([Log-based metrics overview](https://docs.cloud.google.com/logging/docs/logs-based-metrics)).
- **A collector sidecar on Cloud Run with request-based billing.** OpenTelemetry does background processing, so use instance-based billing ([Choose an instrumentation approach](https://docs.cloud.google.com/stackdriver/docs/instrumentation/choose-approach)).
- **Custom metrics written directly from Cloud Run functions.** This is not supported. Create a log-based metric ([Choose an instrumentation approach](https://docs.cloud.google.com/stackdriver/docs/instrumentation/choose-approach)).
- **A large JSON log line on GKE.** An entry over the size limit is dropped when it is `jsonPayload`, not truncated ([About GKE logs](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/about-logs)).
- **Telemetry API writes that fail with a correct writer role.** The application also needs a quota project and the Service Usage Consumer role on it ([Telemetry (OTLP) API overview](https://docs.cloud.google.com/stackdriver/docs/reference/telemetry/overview)).
- **No profiles from a service with a user-created service account.** Grant the Cloud Profiler Agent role ([Profiling Python applications](https://docs.cloud.google.com/profiler/docs/profiling-python)).
