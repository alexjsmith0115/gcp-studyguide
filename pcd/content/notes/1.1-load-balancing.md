## Why it matters

A developer chooses the load balancer that puts an app in front of internet clients or internal clients. The developer also decides if requests from one client must go to the same backend. The exam tests three choices: the load balancer type for the traffic, the GKE resource that creates it, and the session affinity setting for each backend type. A frequent wrong answer puts load balancer session affinity on a Cloud Run backend, where it does not work.

## Key points

- Google Cloud has two types of load balancer. Application Load Balancers (formerly HTTP(S) Load Balancing) are Layer 7. Network Load Balancers (formerly TCP Proxy, SSL Proxy, Network, and Internal TCP/UDP Load Balancing) are Layer 4 ([Cloud Load Balancing release notes](https://docs.cloud.google.com/load-balancing/docs/release-notes)).
- Use an Application Load Balancer for HTTP and HTTPS. Use a proxy Network Load Balancer for TCP with optional SSL offload. Use a passthrough Network Load Balancer for UDP, ESP, or ICMP, or to keep the client source IP address ([Choose a load balancer](https://docs.cloud.google.com/load-balancing/docs/choosing-load-balancer)).
- Only external load balancers can be global. For internal clients and backends in several regions, use a cross-region internal load balancer ([Choose a load balancer](https://docs.cloud.google.com/load-balancing/docs/choosing-load-balancer)).
- A global external load balancer gives one anycast IP address for backends in many regions, with automatic failover between regions ([Cloud Load Balancing overview](https://docs.cloud.google.com/load-balancing/docs/load-balancing-overview)).
- A serverless NEG puts a Cloud Run service behind an Application Load Balancer. Proxy and passthrough Network Load Balancers do not support serverless NEGs ([Serverless network endpoint groups overview](https://docs.cloud.google.com/load-balancing/docs/negs/serverless-neg-concepts)).
- Serverless NEGs do not support health checks. Use outlier detection or Cloud Run service health to move traffic away from a failed region ([Serverless network endpoint groups overview](https://docs.cloud.google.com/load-balancing/docs/negs/serverless-neg-concepts), [Serve traffic from multiple regions](https://docs.cloud.google.com/run/docs/multiple-regions)).
- On GKE, Google recommends the Gateway API for load balancers. GKE Ingress is in maintenance mode and gets no new features ([About load balancing in GKE](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/about-load-balancing), [GKE Ingress for Application Load Balancers](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/ingress)).
- Container-native load balancing sends traffic directly to Pod IP addresses through `GCE_VM_IP_PORT` NEGs. All GKE-managed Layer 7 load balancers use it ([About load balancing in GKE](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/about-load-balancing)).
- Session affinity is best effort. It can break when backend health changes, when backends are added or removed, or when a backend is full ([Backend services overview](https://docs.cloud.google.com/load-balancing/docs/backend-service)).
- Load balancer session affinity is not supported on a serverless NEG. For Cloud Run, enable Cloud Run session affinity on the service ([Set session affinity for services](https://docs.cloud.google.com/run/docs/configuring/session-affinity)).
- On the global external Application Load Balancer and on GKE Gateway, weighted traffic splitting takes precedence over session affinity ([Request distribution for external Application Load Balancers](https://docs.cloud.google.com/load-balancing/docs/https/request-distribution), [Configure Gateway resources using Policies](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/configure-gateway-resources)).
- On GKE Gateway, the recommended way to set session affinity is a `GCPTrafficDistributionPolicy` that targets the Service ([Configure Gateway resources using Policies](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/configure-gateway-resources)).

## Choosing a load balancer

Answer three questions in this order.

| Question | Answer | Result |
|---|---|---|
| What is the traffic type? | HTTP or HTTPS, which includes gRPC and WebSocket | Application Load Balancer |
| | TCP, with optional SSL offload | Proxy Network Load Balancer |
| | UDP, ESP, GRE, or ICMP, or the backend must see the client source IP | Passthrough Network Load Balancer |
| Where are the clients? | The internet | External load balancer |
| | The same VPC network, or a network that connects through VPC Network Peering, Cloud VPN, or Cloud Interconnect | Internal load balancer |
| Where are the backends? | Several regions, external clients | Global load balancer |
| | Several regions, internal clients | Cross-region internal load balancer |
| | One region, or traffic must stay in one region for compliance | Regional load balancer |

Sources: [Choose a load balancer](https://docs.cloud.google.com/load-balancing/docs/choosing-load-balancer), [External Application Load Balancer overview](https://docs.cloud.google.com/load-balancing/docs/https).

### Proxy compared with passthrough

A proxy load balancer terminates the client connection on a Google Front End (GFE) or an Envoy proxy. It then opens a new connection to the backend, so the backend sees a proxy IP address. A passthrough load balancer does not terminate connections. The backend receives each packet with its original source, destination, and port. The backend replies to the client directly, which is called direct server return ([Choose a load balancer](https://docs.cloud.google.com/load-balancing/docs/choosing-load-balancer)).

An Application Load Balancer adds the client IP address to the `X-Forwarded-For` header. The format is `[<supplied-value>,]<client-ip>,<load-balancer-ip>`. The load balancer does not verify the values before the last two entries ([External Application Load Balancer overview](https://docs.cloud.google.com/load-balancing/docs/https)). If an app authenticates clients by IP address, a proxy load balancer is a bad fit. For Application Load Balancers, Google recommends Identity-Aware Proxy (IAP) instead ([Choose a load balancer](https://docs.cloud.google.com/load-balancing/docs/choosing-load-balancer)). The [IAP page](note:1.2-protect-and-scan) covers IAP.

### The load balancer types

| Load balancer | Scope and tier | Scheme | Use it for |
|---|---|---|---|
| Global external Application Load Balancer | Global, Premium Tier only | `EXTERNAL_MANAGED` | Public web apps and APIs, backends in several regions, Cloud CDN |
| Classic Application Load Balancer | Global in Premium Tier, regional in Standard Tier | `EXTERNAL` | Existing setups. Google recommends migration to `EXTERNAL_MANAGED` |
| Regional external Application Load Balancer | One region, Premium or Standard Tier | `EXTERNAL_MANAGED` | Public apps where TLS must terminate in one region |
| Regional internal Application Load Balancer | One region | `INTERNAL_MANAGED` | Internal HTTP services in one region |
| Cross-region internal Application Load Balancer | Several regions | `INTERNAL_MANAGED` | Internal HTTP services in several regions |
| Proxy Network Load Balancer | Global external, regional, or cross-region internal | `EXTERNAL_MANAGED`, `INTERNAL_MANAGED`, or `EXTERNAL` (classic) | TCP services |
| Regional external passthrough Network Load Balancer | One region | `EXTERNAL` | TCP, UDP, and other IP protocols from the internet |
| Internal passthrough Network Load Balancer | Always regional | `INTERNAL` | Internal TCP and UDP services |

Sources: [Choose a load balancer](https://docs.cloud.google.com/load-balancing/docs/choosing-load-balancer), [Request distribution for external Application Load Balancers](https://docs.cloud.google.com/load-balancing/docs/https/request-distribution).

More facts about the types:

- A global external passthrough Network Load Balancer is in Preview ([Choose a load balancer](https://docs.cloud.google.com/load-balancing/docs/choosing-load-balancer)).
- A regional external load balancer has backends in one region only, but clients can reach it from anywhere on the internet ([Cloud Load Balancing overview](https://docs.cloud.google.com/load-balancing/docs/load-balancing-overview)).
- A regional internal load balancer accepts only clients in its own region. Enable global access on the forwarding rule to accept clients from other regions ([Choose a load balancer](https://docs.cloud.google.com/load-balancing/docs/choosing-load-balancer)).
- Failover between regions works only with the global external, classic, and cross-region internal Application Load Balancers ([Application Load Balancer overview](https://docs.cloud.google.com/load-balancing/docs/application-load-balancer)).
- Cloud CDN works only with the global external and the classic Application Load Balancer ([Cloud Load Balancing overview](https://docs.cloud.google.com/load-balancing/docs/load-balancing-overview)).

## Load balancer use cases for a developer

| Requirement | Recommended setup |
|---|---|
| A custom domain with your own TLS certificate for Cloud Run | Global external Application Load Balancer with a serverless NEG. Google recommends this over Cloud Run domain mapping, which is in Preview |
| Cache content near users | Cloud CDN on the global external Application Load Balancer |
| Cloud Armor in front of a public app | External Application Load Balancer, and Cloud Run ingress set to `internal-and-cloud-load-balancing` |
| One IP address for a Cloud Run service in several regions | Global external Application Load Balancer with one serverless NEG in each region |
| gRPC from clients to backends | Application Load Balancer with backend service protocol `HTTP2` (TLS) or `H2C` (cleartext) |
| A game server on UDP | External passthrough Network Load Balancer |

Sources: [Mapping custom domains](https://docs.cloud.google.com/run/docs/mapping-custom-domains), [Serverless network endpoint groups overview](https://docs.cloud.google.com/load-balancing/docs/negs/serverless-neg-concepts), [Restrict network endpoint ingress for Cloud Run services and instances](https://docs.cloud.google.com/run/docs/securing/ingress), [External Application Load Balancer overview](https://docs.cloud.google.com/load-balancing/docs/https), [Choose a load balancer](https://docs.cloud.google.com/load-balancing/docs/choosing-load-balancer).

For gRPC, the load balancer must proxy requests over HTTP/2 from end to end ([External Application Load Balancer overview](https://docs.cloud.google.com/load-balancing/docs/https)). See the [API design page](note:1.1-api-design) for gRPC, the [API exposure page](note:3.1-api-versioning-and-exposure) for custom domains, and the [caching page](note:1.1-caching) for Cloud CDN.

## Cloud Run behind a load balancer

A serverless NEG is a backend for a Cloud Run service, an App Engine app, Cloud Run functions (formerly Cloud Functions), or API Gateway. API Gateway support is in Preview. A serverless NEG has one endpoint: one service or one URL mask, in the same region and project as the NEG ([Serverless network endpoint groups overview](https://docs.cloud.google.com/load-balancing/docs/negs/serverless-neg-concepts), [Compare Cloud Run functions](https://docs.cloud.google.com/run/docs/functions/comparison)).

1. Create a serverless NEG in the region of the Cloud Run service.
2. Create a global backend service with the scheme `EXTERNAL_MANAGED`, and add the NEG.
3. Create a URL map, a target HTTPS proxy with a certificate, and a forwarding rule.
4. Set the service ingress to `internal-and-cloud-load-balancing`. Otherwise clients can call the default URL and bypass the load balancer and Cloud Armor. Do not use `internal`, which rejects requests from an external Application Load Balancer ([Restrict network endpoint ingress for Cloud Run services and instances](https://docs.cloud.google.com/run/docs/securing/ingress)).

```bash
gcloud compute network-endpoint-groups create SERVERLESS_NEG_NAME \
    --region=us-central1 \
    --network-endpoint-type=serverless \
    --cloud-run-service=CLOUD_RUN_SERVICE_NAME

gcloud compute backend-services create BACKEND_SERVICE_NAME \
    --load-balancing-scheme=EXTERNAL_MANAGED \
    --global

gcloud compute backend-services add-backend BACKEND_SERVICE_NAME \
    --global \
    --network-endpoint-group=SERVERLESS_NEG_NAME \
    --network-endpoint-group-region=us-central1

gcloud compute url-maps create URL_MAP_NAME \
    --default-service BACKEND_SERVICE_NAME
```

Source: [Set up a global external Application Load Balancer with Cloud Run, App Engine, or Cloud Run functions](https://docs.cloud.google.com/load-balancing/docs/https/setup-global-ext-https-serverless).

Know these limits of serverless NEGs:

| Limit | What to do |
|---|---|
| No health checks | Enable outlier detection (global external and cross-region internal Application Load Balancers only, and not on a backend service with IAP), or Cloud Run service health |
| A global backend service takes one serverless NEG per region | Add one NEG for each region of a multi-region service. The load balancer sends each request to the closest region |
| A regional backend service takes one serverless NEG | Use a global backend service for several regions |
| The backend timeout is fixed at 60 minutes | Configure clients of long-running connections to retry on failure |
| IAP and Cloud CDN cannot be on the same backend service | Use separate backend services |
| Load balancer session affinity is not supported | Use Cloud Run session affinity |
| Internal Application Load Balancers need a proxy-only subnet | Create the subnet before the load balancer |

Sources: [Serverless network endpoint groups overview](https://docs.cloud.google.com/load-balancing/docs/negs/serverless-neg-concepts), [Set session affinity for services](https://docs.cloud.google.com/run/docs/configuring/session-affinity).

With serverless NEGs, the regional external, regional internal, and cross-region internal Application Load Balancers support only Cloud Run backends ([Application Load Balancer overview](https://docs.cloud.google.com/load-balancing/docs/application-load-balancer)). Each Cloud Run service is in one region ([Cloud Run locations](https://docs.cloud.google.com/run/docs/locations)). To serve users from several regions, deploy the service in each region and put a global external Application Load Balancer in front ([Serve traffic from multiple regions](https://docs.cloud.google.com/run/docs/multiple-regions)). Cloud Run service health uses readiness probes to mark a region unhealthy. It needs at least one minimum instance in each region ([Automate cross-region failover with Cloud Run service health](https://docs.cloud.google.com/run/docs/configuring/configure-service-health)).

## Load balancing on GKE

GKE creates a Google Cloud load balancer from a Kubernetes resource. The resource and its class decide the load balancer type.

| GKE resource | Load balancer that GKE creates | Use it for |
|---|---|---|
| Gateway, class `gke-l7-global-external-managed` | Global external Application Load Balancer | Public HTTP and HTTPS apps |
| Gateway, class `gke-l7-regional-external-managed` | Regional external Application Load Balancer | Public apps in one region |
| Gateway, class `gke-l7-rilb` | Internal Application Load Balancer | Internal HTTP and HTTPS apps |
| Gateway, class `gke-l7-gxlb` | Classic Application Load Balancer | Existing setups only |
| Ingress, class `gce` | Classic Application Load Balancer | Existing setups. Ingress is in maintenance mode |
| Ingress, class `gce-internal` | Internal Application Load Balancer | Existing setups |
| Service of type `LoadBalancer`, class `networking.gke.io/l4-regional-external` | Regional external passthrough Network Load Balancer | TCP and UDP apps |
| Service of type `LoadBalancer`, class `networking.gke.io/l4-regional-internal` | Internal passthrough Network Load Balancer | Internal TCP and UDP apps |

Sources: [About Gateway API](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/gateway-api), [GKE Ingress for Application Load Balancers](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/ingress), [About LoadBalancer Services](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/service-load-balancer).

Google recommends the `gke-l7-global-external-managed` class over `gke-l7-gxlb` for advanced security and traffic management ([About Gateway API](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/gateway-api)).

### Gateway API resources

The Gateway API divides the work by role ([About Gateway API](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/gateway-api)):

- **GatewayClass** is a template for a load balancer type. GKE provides the classes.
- **Gateway** defines where and how the load balancer listens. Cluster operators create Gateways.
- **HTTPRoute** defines the rules that send requests from a Gateway to Services. Application developers create HTTPRoutes. Routes can match request headers and split traffic by weight.
- **Policy** resources set Google Cloud behavior on a Gateway, a Route, or a Service. Examples are `HealthCheckPolicy`, `GCPGatewayPolicy`, and `GCPBackendPolicy`.

All HTTPRoutes attached to one Gateway compile into one URL map, so they share its quotas and limits. The Gateway controllers run in Google-hosted infrastructure, not in your cluster or project ([About Gateway API](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/gateway-api)). The [traffic splitting page](note:1.1-traffic-splitting) shows HTTPRoute weights and header matches.

### Container-native load balancing

Without container-native load balancing, traffic goes to node instance groups, and kube-proxy forwards it to a Pod. This double hop adds latency ([GKE Ingress for Application Load Balancers](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/ingress)).

With container-native load balancing, the load balancer sends traffic directly to Pod IP addresses through `GCE_VM_IP_PORT` NEGs. The benefits are ([GKE Ingress for Application Load Balancers](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/ingress)):

- Lower latency and higher throughput, because traffic skips the node and kube-proxy.
- Pod readiness gates, so Pod readiness includes the load balancer's view of Pod health.
- Latency data for each Pod, not each node.
- Support for Cloud Service Mesh (formerly Anthos Service Mesh and Traffic Director), which needs the NEG data model ([Cloud Service Mesh overview](https://docs.cloud.google.com/service-mesh/docs/overview)).

GKE enables it automatically when the cluster is VPC-native, does not use Shared VPC, does not use GKE Network Policy, and has the `HttpLoadBalancing` add-on. Gateway and Ingress use it. `LoadBalancer` Services do not, but weighted load balancing gives a similar result ([GKE Ingress for Application Load Balancers](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/ingress), [About load balancing in GKE](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/about-load-balancing)).

## Session affinity

Session affinity sends the requests of one client to the same backend. Use it for backends that keep state in memory, for example ad servers, game servers, or services with large local caches ([Backend services overview](https://docs.cloud.google.com/load-balancing/docs/backend-service)). Do not use it for authentication or security ([Request distribution for external Application Load Balancers](https://docs.cloud.google.com/load-balancing/docs/https/request-distribution)).

| Type (`--session-affinity`) | How the load balancer selects the backend | Requirements and notes |
|---|---|---|
| `NONE` (default) | A 5-tuple hash: source IP and port, protocol, destination IP and port | No affinity is configured |
| `CLIENT_IP` | A 2-tuple hash of the source and destination IP addresses | Clients behind one NAT or proxy all go to one backend |
| `HEADER_FIELD` | A hash of the HTTP header that `consistentHash.httpHeaderName` names | `localityLbPolicy` is `RING_HASH` or `MAGLEV` |
| `GENERATED_COOKIE` | The load balancer sets a cookie named `GCLB` (global external and classic) or `GCILB` (regional external) | TTL from 0 to 1,209,600 seconds. `RATE` balancing mode for instance groups. `RING_HASH` or `MAGLEV` |
| `HTTP_COOKIE` | The load balancer sets a cookie. You set its name, path, and TTL | `RATE` balancing mode for instance groups. `RING_HASH` or `MAGLEV` |
| `STRONG_COOKIE_AFFINITY` (stateful cookie-based) | The cookie value encodes the selected backend | No balancing mode or locality policy requirement. TTL up to two weeks. Not on the classic load balancer |

Source: [Request distribution for external Application Load Balancers](https://docs.cloud.google.com/load-balancing/docs/https/request-distribution).

The classic Application Load Balancer supports only `NONE`, `CLIENT_IP`, and `GENERATED_COOKIE`. A cookie TTL of 0 makes a session cookie ([Request distribution for external Application Load Balancers](https://docs.cloud.google.com/load-balancing/docs/https/request-distribution)).

### When affinity breaks

Every affinity type can break when the selected backend is removed or fails its health check. On the global external and classic load balancers, affinity can also break when a later request reaches a different first-layer GFE. All types except stateful cookie-based affinity can also break in these cases ([Request distribution for external Application Load Balancers](https://docs.cloud.google.com/load-balancing/docs/https/request-distribution)):

- The number of configured backends changes, for example when the autoscaler adds or removes an instance.
- The number of healthy backends changes.
- The instance group or NEG of the selected backend becomes full.

Stateful cookie-based affinity survives autoscaling, unless the autoscaler removes the selected instance ([Request distribution for external Application Load Balancers](https://docs.cloud.google.com/load-balancing/docs/https/request-distribution)). Use the `UTILIZATION` balancing mode only with affinity `NONE`. With other affinity types, use `RATE`, `IN-FLIGHT`, or `CONNECTION` ([Backend services overview](https://docs.cloud.google.com/load-balancing/docs/backend-service)).

Internal passthrough Network Load Balancers offer only hash-based affinity, for example `CLIENT_IP_PROTO` and `CLIENT_IP_NO_DESTINATION` ([Traffic distribution for internal passthrough Network Load Balancers](https://docs.cloud.google.com/load-balancing/docs/internal/int-netlb-traffic-distribution)).

## Session affinity on Cloud Run

Cloud Run has its own session affinity. It is separate from load balancer session affinity, and it works when the service is behind a load balancer ([Set session affinity for services](https://docs.cloud.google.com/run/docs/configuring/session-affinity)):

- It is off by default. When it is on, Cloud Run sets a cookie with a TTL of 30 days and sends the client's later requests to the same instance.
- The instance still serves other clients.
- It is best effort. It breaks when the instance stops, or when the instance reaches maximum concurrency or maximum CPU utilization.
- You set it for each revision. Later revisions keep the setting until you change it.
- It takes precedence over traffic splitting. The [traffic splitting page](note:1.1-traffic-splitting) explains the effect on a rollout.

```bash
# Turn on session affinity (this creates a new revision)
gcloud run services update SERVICE --session-affinity

# Turn it off
gcloud run services update SERVICE --no-session-affinity
```

Source: [Set session affinity for services](https://docs.cloud.google.com/run/docs/configuring/session-affinity).

An instance can keep session data in memory, but you cannot assume that a client always returns to the same instance ([Set session affinity for services](https://docs.cloud.google.com/run/docs/configuring/session-affinity)). Keep session state that must survive in a shared store. Session management is a common Memorystore use case ([Memorystore for Redis overview](https://docs.cloud.google.com/memorystore/docs/redis/memorystore-for-redis-overview)). The [caching page](note:1.1-caching) covers Memorystore.

## Session affinity on GKE

| Traffic path | Where to set affinity | Types |
|---|---|---|
| GKE Gateway, single cluster | `GCPTrafficDistributionPolicy` that targets the Service (default and recommended) | `STRONG_COOKIE_AFFINITY`, `HTTP_COOKIE`, `GENERATED_COOKIE`, `HEADER_FIELD`, `CLIENT_IP` |
| GKE Gateway, existing setups | `GCPBackendPolicy` | `CLIENT_IP`, `GENERATED_COOKIE` |
| GKE Ingress | `BackendConfig` field `sessionAffinity.affinityType` | `CLIENT_IP`, `GENERATED_COOKIE` |
| Traffic inside the cluster to a Service | `spec.sessionAffinity: ClientIP` on the Service | Client IP only. The default timeout is 10,800 seconds |

Sources: [Configure Gateway resources using Policies](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/configure-gateway-resources), [Ingress configuration](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/ingress-configuration), [Virtual IPs and Service Proxies](https://kubernetes.io/docs/reference/networking/virtual-ips/).

The `GCPTrafficDistributionPolicy` rules ([Configure Gateway resources using Policies](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/configure-gateway-resources)):

- It supports single-cluster Gateways only, and it does not support the classic load balancer.
- All types except `NONE` and `STRONG_COOKIE_AFFINITY` need `localityLbAlgorithm` set to `MAGLEV` or `RING_HASH`.
- `HEADER_FIELD` fits A/B tests or special client routing where a cookie is not suitable.

```yaml
apiVersion: networking.gke.io/v1
kind: GCPTrafficDistributionPolicy
metadata:
  name: http-cookie-affinity-policy
  namespace: default
spec:
  default:
    sessionAffinity:
      type: HTTP_COOKIE
      cookie:
        name: "my-app-session-id"
        path: "/"
        ttl: "3600s"
    # HTTP_COOKIE affinity requires localityLbAlgorithm to be MAGLEV or RING_HASH.
    localityLbAlgorithm: MAGLEV
  targetRefs:
  - group: ""
    kind: Service
    name: my-stateful-service
```

Source: [Configure Gateway resources using Policies](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/configure-gateway-resources).

If an HTTPRoute rule has weights for several backends, the load balancer first selects a backend based on the weights, before it applies affinity. Do not put weights on a route rule that needs stickiness ([Configure Gateway resources using Policies](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/configure-gateway-resources)).

## Exam traps

- **Load balancer session affinity for a Cloud Run backend.** It is not supported on a serverless NEG. Enable Cloud Run session affinity ([Set session affinity for services](https://docs.cloud.google.com/run/docs/configuring/session-affinity)).
- **Session affinity and weighted traffic splitting on the same route.** On the global external Application Load Balancer and on GKE Gateway, the weights win ([Request distribution for external Application Load Balancers](https://docs.cloud.google.com/load-balancing/docs/https/request-distribution), [Configure Gateway resources using Policies](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/configure-gateway-resources)).
- **Session affinity to keep users signed in.** Affinity is best effort and is not for authentication. Keep session state in a shared store ([Request distribution for external Application Load Balancers](https://docs.cloud.google.com/load-balancing/docs/https/request-distribution), [Set session affinity for services](https://docs.cloud.google.com/run/docs/configuring/session-affinity)).
- **`CLIENT_IP` affinity for users behind a corporate NAT or proxy.** Many users share one source IP address, so some backends get more requests than others ([Request distribution for external Application Load Balancers](https://docs.cloud.google.com/load-balancing/docs/https/request-distribution)).
- **A Network Load Balancer in front of Cloud Run.** Network Load Balancers do not support serverless NEGs. Use an Application Load Balancer ([Serverless network endpoint groups overview](https://docs.cloud.google.com/load-balancing/docs/negs/serverless-neg-concepts)).
- **A "global internal" load balancer.** Only external load balancers are global. Use a cross-region internal load balancer ([Choose a load balancer](https://docs.cloud.google.com/load-balancing/docs/choosing-load-balancer)).
- **An IP allow list in the app behind an Application Load Balancer.** Proxy load balancers do not keep the client IP address by default. Use IAP, or a passthrough load balancer ([Choose a load balancer](https://docs.cloud.google.com/load-balancing/docs/choosing-load-balancer)).
- **Trusting the first value of `X-Forwarded-For`.** The load balancer does not verify values before the last two entries ([External Application Load Balancer overview](https://docs.cloud.google.com/load-balancing/docs/https)).
- **Cloud Armor on the load balancer while Cloud Run ingress allows all traffic.** Clients use the default URL and bypass Cloud Armor. Set ingress to `internal-and-cloud-load-balancing` ([Set up a global external Application Load Balancer with Cloud Run, App Engine, or Cloud Run functions](https://docs.cloud.google.com/load-balancing/docs/https/setup-global-ext-https-serverless)).
- **Health checks to remove a failed Cloud Run region.** Serverless NEGs do not support health checks. Use outlier detection or Cloud Run service health ([Serverless network endpoint groups overview](https://docs.cloud.google.com/load-balancing/docs/negs/serverless-neg-concepts), [Serve traffic from multiple regions](https://docs.cloud.google.com/run/docs/multiple-regions)).
- **GKE Ingress for a new design.** Ingress is in maintenance mode. Use the Gateway API ([GKE Ingress for Application Load Balancers](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/ingress)).
- **A change to a GKE-created load balancer in the console.** GKE overwrites it. Use standalone NEGs if you must manage the load balancer ([GKE Ingress for Application Load Balancers](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/ingress)).
- **A `LoadBalancer` Service for HTTP path routing.** It creates a Layer 4 passthrough load balancer. Use a Gateway and an HTTPRoute ([About load balancing in GKE](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/about-load-balancing)).
- **gRPC error rates from load balancer logs.** The load balancer reports `200 OK` when a gRPC endpoint returns an error ([External Application Load Balancer overview](https://docs.cloud.google.com/load-balancing/docs/https)).
