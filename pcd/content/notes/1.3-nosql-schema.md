## Why it matters

Bigtable and the Firestore Standard edition have no joins, so the key design decides which reads are fast and where the writes go ([Schema design best practices](https://docs.cloud.google.com/bigtable/docs/schema-design), [Firestore editions overview](https://docs.cloud.google.com/firestore/native/docs/editions-overview)). In Bigtable, the row key is the only index. In Firestore, the document layout and the indexes decide query support, write latency, and hotspots. The exam shows a row key, a document layout, or an index setting, and asks you to find the hotspot or the scaling limit.

## Key points

- Design a Bigtable schema for the queries that you plan to send. A read by row key, row key prefix, or row range is fast. Other reads scan the full table ([Schema design best practices](https://docs.cloud.google.com/bigtable/docs/schema-design)).
- Each Bigtable table has one index, the row key. Rows sort lexicographically by the bytes of the row key ([Schema design best practices](https://docs.cloud.google.com/bigtable/docs/schema-design)).
- A row key that starts with a timestamp sends sequential writes to one node. This is a hotspot ([Schema design best practices](https://docs.cloud.google.com/bigtable/docs/schema-design)).
- Bigtable operations are atomic only at the row level, and Bigtable has no joins. Keep all data for an entity in one row ([Schema design best practices](https://docs.cloud.google.com/bigtable/docs/schema-design)).
- Garbage collection policies apply to a column family. Deletion can take up to a week, so filter your reads ([Garbage collection overview](https://docs.cloud.google.com/bigtable/docs/garbage-collection)).
- Firestore stores documents in collections. Put a small, fixed list in the document, and put data that grows in a subcollection ([Data model](https://docs.cloud.google.com/firestore/native/docs/data-model), [Structure data](https://docs.cloud.google.com/firestore/native/docs/concepts/structure-data)).
- Firestore Standard edition indexes each field automatically. A query that combines a range filter or a sort with another field needs a manual (composite) index ([Standard edition index overview](https://docs.cloud.google.com/firestore/native/docs/standard-index-overview)).
- Monotonically increasing document IDs and indexed timestamps cause Firestore hotspots. An indexed sequential field limits the collection to 500 writes per second ([Firestore best practices](https://docs.cloud.google.com/firestore/native/docs/best-practices)).
- Ramp up traffic with the "500/50/5" rule: start at 500 operations per second, then increase by 50% every 5 minutes ([Firestore best practices](https://docs.cloud.google.com/firestore/native/docs/best-practices)).
- Use the Firestore API for new applications. Firestore in Datastore mode (formerly Cloud Datastore) is for legacy App Engine apps, and you cannot change the mode after you create the database ([Datastore overview](https://docs.cloud.google.com/datastore/docs/concepts/overview), [Choose between Firestore APIs](https://docs.cloud.google.com/datastore/docs/firestore-or-datastore), [Firestore editions overview](https://docs.cloud.google.com/firestore/native/docs/editions-overview)).

## Bigtable: design the row key for your queries

Bigtable (formerly Cloud Bigtable) stores each table as a sorted key-value map, and the row key is the only indexed value ([Bigtable overview](https://docs.cloud.google.com/bigtable/docs/overview), [Cloud Bigtable schema optimization: Key Salting](https://cloud.google.com/blog/products/databases/cloud-bigtable-schema-optimization-key-salting/)). The docs give two design goals, in this order ([Schema design best practices](https://docs.cloud.google.com/bigtable/docs/schema-design)):

1. Make the most frequent queries into row key reads, prefix reads, or row range reads.
2. Spread reads and writes evenly across the row space, so that no small key range gets most of the traffic.

Put several delimited values in the row key. Start with a common value and end with a granular value. The docs example tracks mobile devices with the device type, the device ID, and the day:

```text
phone#4c410523#20200501
phone#4c410523#20200502
tablet#a0b81f74#20200501
tablet#a0b81f74#20200502
```

Source: [Schema design best practices](https://docs.cloud.google.com/bigtable/docs/schema-design).

One request reads all rows for a device type, or for one device. A query for one day across all devices must scan the table, because the day is the row key suffix ([Schema design best practices](https://docs.cloud.google.com/bigtable/docs/schema-design)).

| Row key pattern | Problem | Do this instead |
|---|---|---|
| Starts with a timestamp | Sequential writes go to one node: a hotspot | Put a high-cardinality value first: `machine_4223421#1425330757685` |
| Sequential numeric user ID | New users are more likely to be active, so traffic goes to a few nodes | Use the reversed numeric ID |
| One row that you update again and again, for example `4c410523#memusage` every second | The tablet with that row is overloaded, and the row can exceed its size limit | Write a new row for each reading: `4c410523#memusage#1423523569918` |
| A hash of the key | You lose the sort order, and Key Visualizer output is hard to read | Use human-readable values |
| Domain names as written (`maps.google.com`) | Rows for one domain are not next to each other | Use reversed domain names (`com.google.maps`) when you have many domains |
| Integers without padding | `3` sorts after `20` | Pad with leading zeroes |

Source: [Schema design best practices](https://docs.cloud.google.com/bigtable/docs/schema-design).

More row key rules ([Schema design best practices](https://docs.cloud.google.com/bigtable/docs/schema-design)):

- **Keep row keys short.** The limit is 4 KB. Long keys use more memory and storage and make responses slower.
- **Newest data first.** A reversed timestamp (the maximum long value minus the timestamp) sorts recent rows first. Do not start the row key with a reversed timestamp either.
- **No personal data in keys.** Row keys and column family names are also service data, so avoid PII in them.

**Salting a hot prefix.** Some keys can get much more traffic than others, for example a very active user. A Google blog post adds a prefix that is the hash of the row key modulo N, for example `01-user_id-xxx-yyy`. The code computes the prefix, so a point read is still one request. A prefix scan becomes N parallel scans, and the results may not come back in sorted order. Salting does not remove a hotspot: it splits it into N smaller hotspots ([Cloud Bigtable schema optimization: Key Salting](https://cloud.google.com/blog/products/databases/cloud-bigtable-schema-optimization-key-salting/)).

**Test the design.** Load at least 30 GB of test data, run a heavy load test, and then run a one-hour simulation of normal traffic. Look for hotspots with Key Visualizer and Cloud Monitoring, and change the row key if you find them ([Design a schema](https://docs.cloud.google.com/bigtable/docs/schema-design-steps)).

**A second lookup pattern.** One row key serves one lookup pattern. For another pattern, store a copy of the data in a second table with a row key for that query ([Schema design for time series data](https://docs.cloud.google.com/bigtable/docs/schema-design-time-series)). Or create a continuous materialized view with a different row key as an asynchronous secondary index. Bigtable keeps it eventually consistent with the source table ([Create an asynchronous secondary index](https://docs.cloud.google.com/bigtable/docs/asynchronous-secondary-index)).

## Bigtable: tables, column families, and size limits

- **One table for similar data.** Give each dataset or tenant a row key prefix. Do not create a table for each customer or each year. More tables add connection overhead and tail latency, and an instance allows 1,000 tables ([Schema design best practices](https://docs.cloud.google.com/bigtable/docs/schema-design), [Bigtable quotas and limits](https://docs.cloud.google.com/bigtable/quotas)).
- **Tenant removal.** When a tenant leaves, drop the range of rows with its row key prefix ([Schema design best practices](https://docs.cloud.google.com/bigtable/docs/schema-design)).
- **Column families.** Group related columns in one family. Use short names, because names are sent with each request. Keep to about 100 families per table. Put data with different retention needs in different families ([Schema design best practices](https://docs.cloud.google.com/bigtable/docs/schema-design)).
- **Columns.** Tables are sparse, so an unused column takes no space. A table can have millions of columns, but a row should not. A column qualifier can hold data, for example one column for each friend ID in a `Friends` family ([Schema design best practices](https://docs.cloud.google.com/bigtable/docs/schema-design)).
- **Schema in the data.** You add column families when you create or update a table. Columns and row key patterns come from the data that you write ([Schema design best practices](https://docs.cloud.google.com/bigtable/docs/schema-design)).
- **Entities and rows.** Keep each entity in one row, and store related entities in adjacent rows. Split an entity across rows only when its row would be hundreds of MB ([Schema design best practices](https://docs.cloud.google.com/bigtable/docs/schema-design)).

| Item | Recommended limit | Hard limit |
|---|---|---|
| Row key | As short as possible | 4 KB |
| Column qualifier | 16 KB | — |
| Value in one cell | 10 MB | 100 MB |
| All values in one row | 100 MB | 256 MB |
| Column families per table | 100 | — |
| Tables per instance | — | 1,000, including materialized views |

Sources: [Bigtable quotas and limits](https://docs.cloud.google.com/bigtable/quotas), [Schema design best practices](https://docs.cloud.google.com/bigtable/docs/schema-design).

## Bigtable: tall and narrow or wide rows for time series

| Pattern | Row key example | Use when | Watch for |
|---|---|---|---|
| Time bucket, new column for each event | `us-west2#3698#pressure#week1` | You do not need to measure change, and you store the value in the column qualifier | Choose a bucket size that keeps rows under 100 MB |
| Time bucket, new cell for each event | `asia-south2#3698#week1` | You want changes over time from timestamped cells | Set garbage collection rules |
| Single-timestamp row, serialized (JSON or protobuf in one column) | `us-west2#3698#2021-03-05-1200` | You read all measurements of an event together | Without the SQL features, you cannot read one field only |
| Single-timestamp row, unserialized | `us-west2#3698#2021-03-05-1200` | You want a simple start or an unbounded number of events | Lower performance and compression. Hotspots are possible even with the timestamp at the end |

Source: [Schema design for time series data](https://docs.cloud.google.com/bigtable/docs/schema-design-time-series).

Single-timestamp rows make tall and narrow tables. Time buckets put many events in one row. This gives better performance and compression, but it takes more effort to design. Never use a timestamp as the row key prefix ([Schema design for time series data](https://docs.cloud.google.com/bigtable/docs/schema-design-time-series)).

## Bigtable: garbage collection

- **Rule types.** Age (a time to live), number of versions, or a combination: intersection (both rules), union (either rule), or nested ([Garbage collection overview](https://docs.cloud.google.com/bigtable/docs/garbage-collection)).
- **Defaults depend on the tool.** No column family has a default TTL. A family that you create with the HBase client keeps one version. A family that you create with `gcloud`, the `cbt` CLI, or the other client libraries keeps all versions ([Garbage collection overview](https://docs.cloud.google.com/bigtable/docs/garbage-collection)).
- **Late deletion.** Garbage collection runs during compaction, and deletion can take up to a week. Until then, expired cells appear in reads, and you pay to store them. Add a read filter that matches the rule ([Garbage collection overview](https://docs.cloud.google.com/bigtable/docs/garbage-collection)).
- **Retroactive.** A stricter new policy also deletes data that you wrote before the change ([Garbage collection overview](https://docs.cloud.google.com/bigtable/docs/garbage-collection)).

```bash
cbt createfamily your-table cf1
cbt setgcpolicy your-table cf1 maxage=5d                    # age
cbt setgcpolicy your-table cf2 maxversions=1                 # newest cell only
cbt setgcpolicy your-table cf4 maxage=14d and maxversions=1  # intersection
cbt setgcpolicy your-table cf3 maxage=5d or maxversions=2    # union
```

Source: [Configure garbage collection](https://docs.cloud.google.com/bigtable/docs/configuring-garbage-collection).

## Bigtable: atomicity is per row

Bigtable supports transactions only within a single row ([Schema design best practices](https://docs.cloud.google.com/bigtable/docs/schema-design)). Design the schema so that one write to one row keeps related data correct.

| Request | Atomic scope | Notes |
|---|---|---|
| `MutateRow` (simple write) | One row, up to 100,000 mutations | Use it for several changes to one row |
| `MutateRows` (batch write) | Each entry, not the batch | Use it for rows with similar row keys |
| `CheckAndMutateRow` (conditional write) | One row: check, then write | Not with multi-cluster routing |
| `ReadModifyWriteRow` (append or increment) | One row | Not with multi-cluster routing. Not retried after a failure |
| `MutateRow` with `AddToCell` (aggregate cells) | One row | Recommended over `ReadModifyWriteRow` for counters |

Source: [Writes](https://docs.cloud.google.com/bigtable/docs/writes).

A replicated instance is eventually consistent, and the app profile routing decides which of these requests you can use ([Writes](https://docs.cloud.google.com/bigtable/docs/writes)). See [Consistency and replication](note:1.3-consistency-and-replication). For client code, see [Reading and writing data](note:4.1-reading-writing-data).

## Firestore: documents, collections, and subcollections

Firestore stores documents in collections. A document is a set of fields that can hold maps (nested objects) and arrays. A collection holds only documents, and every path alternates between collections and documents. Firestore is optimized for large collections of small documents. It is schemaless, but use the same fields and data types across documents so that queries are easier ([Data model](https://docs.cloud.google.com/firestore/native/docs/data-model)).

| Option | Use when | Limitation |
|---|---|---|
| Nested data (a map or an array) | A simple, fixed list, for example a user's 3 most recent chat rooms | The document grows with the list, and reads get slower |
| Subcollection | Data that grows, for example the messages of a chat room | You cannot easily delete subcollections |
| Root-level collection | Many-to-many relationships and separate datasets | Hierarchical data gets harder to read as the database grows |

Source: [Structure data](https://docs.cloud.google.com/firestore/native/docs/concepts/structure-data).

```text
rooms/                 collection
  roomA                document   name: "my chat room"
    messages/          subcollection
      message1         document   from: "alex", msg: "Hello World!"
users/                 collection
  alovelace            document   name: {first: "Ada", last: "Lovelace"}, born: 1815
```

Source: [Data model](https://docs.cloud.google.com/firestore/native/docs/data-model).

- **Subcollections stay.** Deleting a document does not delete its subcollections ([Data model](https://docs.cloud.google.com/firestore/native/docs/data-model)).
- **Collection groups.** A collection group query searches all collections with the same collection ID, for example every `messages` subcollection ([Data model](https://docs.cloud.google.com/firestore/native/docs/data-model)).
- **Size and depth.** In Native mode, a document can be 1 MiB. Subcollections nest up to 100 levels, and maps and arrays up to 20 levels ([Firestore quotas and limits](https://docs.cloud.google.com/firestore/quotas)). With MongoDB compatibility, the Enterprise edition allows 16 MiB documents ([Firestore editions overview](https://docs.cloud.google.com/firestore/native/docs/editions-overview)).
- **Document IDs.** An ID is up to 1,500 bytes. It cannot contain `/`, be `.` or `..`, or match `__.*__` ([Firestore quotas and limits](https://docs.cloud.google.com/firestore/quotas)).
- **Names are data.** Do not store sensitive information in document names or field names ([Firestore best practices](https://docs.cloud.google.com/firestore/native/docs/best-practices)).

## Firestore: indexes

The Standard edition uses an index for every query. Query time depends on the size of the result set, not on the size of the database ([Standard edition index overview](https://docs.cloud.google.com/firestore/native/docs/standard-index-overview)).

| | Automatic index (formerly single-field index) | Manual index (formerly composite index) |
|---|---|---|
| Created by | Firestore, for each field: ascending and descending, plus `array-contains` for arrays. Map subfields too | You. The error for a missing index has a link that creates it |
| Supports | Equality, range, and sort on one field, and equality on several fields | A range filter or a sort combined with another field |
| Scope | Collection. Collection group scope is not on by default | Collection or collection group |
| You manage it with | Automatic index settings and exemptions | The console, the Firebase CLI, or Terraform |

Sources: [Standard edition index overview](https://docs.cloud.google.com/firestore/native/docs/standard-index-overview), [Manage Standard edition indexes](https://docs.cloud.google.com/firestore/native/docs/standard-indexing).

- **Missing fields.** A document is in an index only when it has a value for every field of the index. Queries that use that index never return it ([Standard edition index overview](https://docs.cloud.google.com/firestore/native/docs/standard-index-overview)).
- **Index merging.** Firestore can merge indexes for equality filters, so you need fewer manual indexes ([Standard edition index overview](https://docs.cloud.google.com/firestore/native/docs/standard-index-overview)).
- **Write latency.** Index fanout is the main cause of write latency. Set collection-level exemptions, for example disable descending and array indexing ([Firestore best practices](https://docs.cloud.google.com/firestore/native/docs/best-practices)).

| Exempt a field from automatic indexing when | Reason |
|---|---|
| It holds long strings that you do not query | Lower storage cost |
| It holds sequential values, like a timestamp, and the collection has a high write rate | An indexed sequential field limits the collection to 500 writes per second |
| It is a TTL field | An indexed timestamp can create hotspots |
| It is a large array or map that you do not query | A document can have at most 40,000 index entries |

Sources: [Standard edition index overview](https://docs.cloud.google.com/firestore/native/docs/standard-index-overview), [Manage data retention with TTL policies](https://docs.cloud.google.com/firestore/native/docs/ttl).

Other Standard edition limits: 200 manual indexes for each database without billing, or 1,000 with billing. An indexed field value is truncated after 1,500 bytes, and queries on truncated values can return inconsistent results ([Standard edition index overview](https://docs.cloud.google.com/firestore/native/docs/standard-index-overview)).

The Enterprise edition creates no indexes by default. You create indexes for your common queries, and you can make an index sparse or unique ([Enterprise edition index overview](https://docs.cloud.google.com/firestore/native/docs/enterprise-index-overview)).

## Firestore: hotspots and hot documents

Firestore orders documents by a key that comes from the collection path and the document ID. It splits key ranges across storage servers as load grows ([Understand reads and writes at scale](https://docs.cloud.google.com/firestore/native/docs/understand-reads-writes-scale)). A hotspot occurs when an app does one of these ([Firestore best practices](https://docs.cloud.google.com/firestore/native/docs/best-practices)):

- Creates documents at a very high rate with its own monotonically increasing IDs, for example `Customer1`, `Customer2`. Automatic document IDs use a scatter algorithm and avoid this.
- Creates documents at a high rate in a collection with few documents.
- Creates documents at a very high rate with a monotonically increasing field, like a timestamp.
- Deletes documents in a collection at a high rate.
- Writes at a very high rate without a gradual increase of traffic.

New splits do not fix sequential IDs, because the traffic moves to the newest split ([Understand reads and writes at scale](https://docs.cloud.google.com/firestore/native/docs/understand-reads-writes-scale)).

**A hot document.** You cannot update one document at an unlimited rate. For a high-rate counter, use a distributed counter: a counter document with a `shards` subcollection. The count is the sum of the shards. Write throughput grows with the number of shards, but each read of the total reads every shard ([Support frequent and distributed counters](https://docs.cloud.google.com/firestore/native/docs/solutions/counters)).

```python
# counters/{ID} holds num_shards; counters/{ID}/shards/{N} holds count
def increment_counter(self, doc_ref):
    """Increment a randomly picked shard."""
    doc_id = random.randint(0, self._num_shards - 1)

    shard_ref = doc_ref.collection("shards").document(str(doc_id))
    return shard_ref.update({"count": firestore.Increment(1)})
```

Source: [Support frequent and distributed counters](https://docs.cloud.google.com/firestore/native/docs/solutions/counters).

**Expiring data.** A TTL policy marks one timestamp field as the expiration time for a collection group. Deletion typically occurs within 24 hours, and expired documents appear in queries until then. TTL does not delete subcollections ([Manage data retention with TTL policies](https://docs.cloud.google.com/firestore/native/docs/ttl)).

## Firestore editions and data access modes

Unless a section says otherwise, this page describes Firestore in Native mode on the Standard edition. You select the data access mode when you create a database, and you cannot change it later. A project can hold Standard and Enterprise edition databases ([Firestore editions overview](https://docs.cloud.google.com/firestore/native/docs/editions-overview)).

| | Firestore in Native mode | Firestore in Datastore mode | Firestore with MongoDB compatibility |
|---|---|---|---|
| Use for | New server, web, and mobile apps | Legacy apps that depend on the Datastore API, such as App Engine apps | MongoDB applications, drivers, and tools |
| Editions | Standard and Enterprise | Standard | Enterprise |
| Features | Rich queries, more index types, real-time updates, mobile and web client libraries | Datastore indexes. No joins, no inequality filters on several properties, no subquery filters | MongoDB-compatible API, documents up to 16 MiB |

Sources: [Firestore editions overview](https://docs.cloud.google.com/firestore/native/docs/editions-overview), [Choose between Firestore APIs](https://docs.cloud.google.com/datastore/docs/firestore-or-datastore), [Datastore overview](https://docs.cloud.google.com/datastore/docs/concepts/overview).

Datastore is no longer a standalone product, and Firestore is its successor. Some docs pages call Datastore mode "Firestore with Datastore compatibility" ([Datastore overview](https://docs.cloud.google.com/datastore/docs/concepts/overview), [Firestore overview](https://docs.cloud.google.com/firestore/native/docs/overview)). The terms map like this: a Datastore kind is a Firestore collection group, and an entity is a document. A property is a field, and a key is a document ID ([Datastore overview](https://docs.cloud.google.com/datastore/docs/concepts/overview)). For consistency, see [Consistency and replication](note:1.3-consistency-and-replication). For the product choice, see [Choosing a storage system](note:1.3-storage-choice).

## Exam traps

- **A row key that starts with a timestamp, so that recent data is easy to find.** It creates a hotspot. Put a high-cardinality value, like a device or user ID, first ([Schema design best practices](https://docs.cloud.google.com/bigtable/docs/schema-design)).
- **A hash of every row key to spread load.** You lose the sort order and readable Key Visualizer output. Use readable values. Salting is for a few very active keys in an otherwise balanced schema ([Schema design best practices](https://docs.cloud.google.com/bigtable/docs/schema-design), [Cloud Bigtable schema optimization: Key Salting](https://cloud.google.com/blog/products/databases/cloud-bigtable-schema-optimization-key-salting/)).
- **A new table for each customer or each year.** Use one table with a row key prefix. An instance allows 1,000 tables ([Schema design best practices](https://docs.cloud.google.com/bigtable/docs/schema-design)).
- **An all-or-nothing update across several Bigtable rows.** Only single-row operations are atomic, and a batch write is not atomic as a whole ([Writes](https://docs.cloud.google.com/bigtable/docs/writes)).
- **Expired cells that should disappear at once.** Garbage collection can take up to a week. Filter reads with the same rule ([Garbage collection overview](https://docs.cloud.google.com/bigtable/docs/garbage-collection)).
- **A column family created with `cbt` or `gcloud` with no policy.** It keeps all versions until you set a garbage collection policy ([Garbage collection overview](https://docs.cloud.google.com/bigtable/docs/garbage-collection)).
- **Sequential document IDs or an indexed timestamp at a high write rate.** Use automatic document IDs, and exempt the timestamp field if you do not query it ([Firestore best practices](https://docs.cloud.google.com/firestore/native/docs/best-practices)).
- **One document as a high-rate counter.** Use a distributed counter with shards ([Support frequent and distributed counters](https://docs.cloud.google.com/firestore/native/docs/solutions/counters)).
- **A growing list in an array field.** The document grows toward the 1 MiB limit of Native mode, and reads get slower. Use a subcollection ([Structure data](https://docs.cloud.google.com/firestore/native/docs/concepts/structure-data), [Firestore quotas and limits](https://docs.cloud.google.com/firestore/quotas)).
- **Deleting a parent document to delete its messages.** Subcollections remain ([Data model](https://docs.cloud.google.com/firestore/native/docs/data-model)).
- **Datastore mode for a new app, or a plan to change the mode later.** Use the Firestore API. The mode is fixed when you create the database ([Choose between Firestore APIs](https://docs.cloud.google.com/datastore/docs/firestore-or-datastore), [Firestore editions overview](https://docs.cloud.google.com/firestore/native/docs/editions-overview)).
