## Why it matters

A developer releases a new version to a small part of the traffic first, and must be able to undo the release fast. Cloud Run and GKE both split traffic between versions, but they use different resources and commands. The exam tests the Cloud Run revision and traffic commands, and the GKE Gateway and Deployment settings. It also tests Cloud Deploy canaries, and how traffic splits interact with session affinity.

## Key points

- Each Cloud Run deployment or configuration change creates an immutable revision. A revision that receives no requests is not billed, unless it has minimum instances ([Manage revisions](https://docs.cloud.google.com/run/docs/managing/revisions)).
- `gcloud run deploy --no-traffic` creates a revision that gets no traffic. `gcloud run services update-traffic` then moves a percentage of traffic to it ([Rollbacks, gradual rollouts, and traffic migration](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration)).
- A traffic split stays in place for all later deployments. To send all traffic to each new revision again, run `update-traffic --to-latest` ([Rollbacks, gradual rollouts, and traffic migration](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration)).
- A revision tag gives a revision its own URL, so you can test it before it gets traffic ([Rollbacks, gradual rollouts, and traffic migration](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration)).
- To roll back on Cloud Run, send 100% of traffic to an earlier revision. You do not rebuild or redeploy ([Rollbacks, gradual rollouts, and traffic migration](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration)).
- Cloud Run session affinity takes precedence over the traffic split ([Set session affinity for services](https://docs.cloud.google.com/run/docs/configuring/session-affinity)).
- On GKE, an `HTTPRoute` splits traffic by `weight` and sends test traffic to a version by header match ([Deploying Gateways](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/deploying-gateways), [Deploy a multi-cluster Gateway for weighted traffic splitting](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/deploy-gateway-traffic-splitting)).
- A Deployment rolling update uses `maxSurge` and `maxUnavailable`. Both default to 25% ([Deployments](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/)).
- A Cloud Deploy canary on GKE with service networking splits by Pod count, not by traffic. For a split based on traffic, use the Gateway API ([Canary Deployments to GKE and GKE attached clusters using service-based networking](https://docs.cloud.google.com/deploy/docs/deployment-strategies/canary/gke/service-networking)).
- On GKE Gateway, weighted traffic splitting takes precedence over session affinity ([Configure Gateway resources using Policies](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/configure-gateway-resources)).

## Choosing a release strategy

| Strategy | How it works | Rollback | Where on Google Cloud |
|---|---|---|---|
| Recreate | Stop all old instances, then start the new version | Deploy the old version again | GKE Deployment strategy `Recreate` |
| Rolling update | Replace a subset of instances, then more, until all run the new version | Roll out the old version | GKE Deployment strategy `RollingUpdate` (default) |
| Canary or gradual rollout | Send a small percentage of traffic to the new version, check it, then increase | Move the traffic back | Cloud Run traffic split, `HTTPRoute` weights, Cloud Deploy canary, Cloud Service Mesh (formerly Anthos Service Mesh and Traffic Director) |
| Blue/green | Run a second full set of instances with the new version, then switch all traffic | Reverse the switch | GKE Service selector, `HTTPRoute`, Cloud Run 0% to 100% |
| A/B test | Send groups of users to two versions and compare results | Remove the split | Header routing, traffic split with session affinity |
| Traffic mirroring | Copy live traffic to the new version, which discards its responses | Nothing to undo | `HTTPRoute` `RequestMirror` filter, URL map `requestMirrorPolicy` |

Sources: [Best practices for continuous integration and delivery to Google Kubernetes Engine](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/best-practices-continuous-integration-delivery-kubernetes), [Canarying Releases](https://sre.google/workbook/canarying-releases/), [Deploy a multi-cluster Gateway for weighted traffic splitting](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/deploy-gateway-traffic-splitting), [Traffic management overview for global external Application Load Balancers](https://docs.cloud.google.com/load-balancing/docs/https/traffic-management-global), [Cloud Service Mesh overview](https://docs.cloud.google.com/service-mesh/docs/overview).

Blue/green rollback is a simple reversal of the routing change, but it uses twice the resources ([Canarying Releases](https://sre.google/workbook/canarying-releases/)). Google SRE gives this guidance for canaries ([Canarying Releases](https://sre.google/workbook/canarying-releases/)):

- Compare the canary with the control, not with the whole service. A 5% canary with a 20% error rate shows only a 1% error rate for the whole service.
- Run only one canary at a time, so that the signals do not mix.
- Make the canary large enough and long enough to be representative.
- Traffic mirroring (teeing) does not find risk well in stateful systems. For example, a shared cache gives a false cache hit rate.

## Cloud Run: revisions, traffic splits, and tags

Cloud Run routes traffic to revisions of one service. You can start with 1% of requests on a new revision and increase the percentage while you watch telemetry ([What is Cloud Run](https://docs.cloud.google.com/run/docs/overview/what-is-cloud-run)). A typical gradual rollout with a tag:

```bash
# 1. Deploy a new revision that gets no traffic, with a tag for testing
gcloud run deploy SERVICE --image IMAGE_URL --no-traffic --tag TAG_NAME

# 2. Test the tagged revision at its own URL, then send it a small share of traffic
gcloud run services update-traffic SERVICE --to-tags TAG_NAME=TRAFFIC_PERCENT

# 3. Split traffic between named revisions (the list is comma-separated)
gcloud run services update-traffic SERVICE --to-revisions REVISION1=PERCENTAGE1,REVISION2=PERCENTAGE2

# 4. Send all traffic to the latest revision, and remove the tag
gcloud run services update-traffic SERVICE --to-latest
gcloud run services update-traffic SERVICE --remove-tags TAG_NAME

# Roll back: send all traffic to a known good revision
gcloud run services update-traffic SERVICE --to-revisions REVISION=100
```

Source: [Rollbacks, gradual rollouts, and traffic migration](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration).

Rules for traffic splits:

- A traffic change is not instant. Requests in progress complete, and during the change they can go to the old or the new revision ([Rollbacks, gradual rollouts, and traffic migration](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration)).
- After a deployment with `--no-traffic`, the latest revision does not get traffic on future deployments. Run `update-traffic --to-latest` to restore the default ([gcloud run deploy](https://docs.cloud.google.com/sdk/gcloud/reference/run/deploy)).
- `--to-latest` is the same as `--to-revisions=LATEST=100`. `--to-revisions=LATEST=10` sends 10% to whichever revision is the latest, now and after later deployments ([gcloud run services update-traffic](https://docs.cloud.google.com/sdk/gcloud/reference/run/services/update-traffic)).
- If your assignments total less than 100%, Cloud Run scales the other serving revisions proportionally. For example, with a 40/60 split, `revision-1=45` gives 45/55 ([gcloud run services update-traffic](https://docs.cloud.google.com/sdk/gcloud/reference/run/services/update-traffic)).
- In a service YAML file, the traffic percentages must add up to 100 ([Rollbacks, gradual rollouts, and traffic migration](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration)).
- In the console, the **Serve this revision immediately** checkbox sends 100% to the new revision and overrides any split ([Rollbacks, gradual rollouts, and traffic migration](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration)).

Rules for tags:

- A tag URL starts with the tag name, for example `https://green---myservice-abcdef.a.run.app` ([Rollbacks, gradual rollouts, and traffic migration](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration)).
- A tag URL reaches its revision at any traffic percentage, also at 0% ([gcloud run services update-traffic](https://docs.cloud.google.com/sdk/gcloud/reference/run/services/update-traffic)).
- With minimum instances set on the revision, a tag keeps those instances running for the tagged revision, and you pay for them. Minimum instances set on the service do not do this. Remove tags that you no longer need ([Rollbacks, gradual rollouts, and traffic migration](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration)).
- The documented test sequence has four steps: integration tests, a tagged revision in staging, a tagged revision with no traffic in production, and traffic migration ([Rollbacks, gradual rollouts, and traffic migration](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration)).

A service keeps up to 1000 revisions. Cloud Run deletes the oldest revisions after that. You cannot delete a revision that can receive traffic, the only revision, or the latest revision ([Manage revisions](https://docs.cloud.google.com/run/docs/managing/revisions)). Cloud Run functions (formerly Cloud Functions) support traffic splitting, but Cloud Run functions (1st gen) do not ([Compare Cloud Run functions](https://docs.cloud.google.com/run/docs/functions/comparison)). Worker pools split instances between revisions, not traffic ([What is Cloud Run](https://docs.cloud.google.com/run/docs/overview/what-is-cloud-run)). See the [deploy from source page](note:3.1-deploy-from-source) for `--source` deployments. The [integration tests page](note:2.3-integration-tests-cloud-build) covers tests against a tagged revision, and the [API versioning page](note:3.1-api-versioning-and-exposure) covers tags as API versions.

## A/B tests on Cloud Run

| Need | Use |
|---|---|
| A random split where each user stays on one version (best effort) | A traffic split, with Cloud Run session affinity on both revisions |
| Only chosen testers see the new version | The tag URL of the new revision |
| Routing by request header, or a split between two services | A URL map of a global external Application Load Balancer (formerly HTTP(S) Load Balancing), with header-based routing or `weightedBackendServices` |

Sources: [Set session affinity for services](https://docs.cloud.google.com/run/docs/configuring/session-affinity), [Rollbacks, gradual rollouts, and traffic migration](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration), [Traffic management overview for global external Application Load Balancers](https://docs.cloud.google.com/load-balancing/docs/https/traffic-management-global), [Cloud Load Balancing release notes](https://docs.cloud.google.com/load-balancing/docs/release-notes).

Know how Cloud Run session affinity changes a split ([Set session affinity for services](https://docs.cloud.google.com/run/docs/configuring/session-affinity)):

- Session affinity takes precedence over the split. If one client sends most requests, those requests can all go to one revision, whatever the split says.
- If only some revisions have session affinity, requests gradually shift toward those revisions. Set affinity the same way on all revisions in the split.
- When you change a split from 90/10 to 80/20, Cloud Run moves only the 10% of traffic that must change.
- Affinity is best effort. It breaks when an instance stops or reaches its concurrency or CPU limit.

The URL map can send requests that match a header, such as `user-agent:Mobile`, to a different backend service. It can also split traffic by weight, for example 95% and 5%. Google lists A/B testing as a typical use of weighted splitting ([Traffic management overview for global external Application Load Balancers](https://docs.cloud.google.com/load-balancing/docs/https/traffic-management-global)). Load balancer session affinity does not work with serverless NEGs ([Serverless network endpoint groups overview](https://docs.cloud.google.com/load-balancing/docs/negs/serverless-neg-concepts)). The [load balancing page](note:1.1-load-balancing) covers serverless NEGs.

## GKE: rolling updates

A Deployment replaces Pods with `.spec.strategy.type` `RollingUpdate` (the default) or `Recreate`. `Recreate` stops all old Pods before it creates new ones ([Deployments](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/)).

| Field | Meaning | Default and rounding |
|---|---|---|
| `maxUnavailable` | The maximum number of Pods that can be unavailable during the update. At 30%, at least 70% of the desired Pods stay available | 25%. A percentage rounds down |
| `maxSurge` | The maximum number of Pods above the desired count. At 30%, at most 130% of the desired Pods run | 25%. A percentage rounds up |

Source: [Deployments](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/).

The two fields cannot both be 0. To keep full capacity during an update, set `maxUnavailable` to 0 and `maxSurge` above 0 ([Deployments](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/)).

```yaml
spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 25%        # at most 5 Pods during the update (rounds up)
      maxUnavailable: 25%  # at least 3 Pods available (rounds down)
```

Source: [Deployments](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/).

A rolling update controls how many Pods change at a time. To control the share of traffic, use `HTTPRoute` weights or a Cloud Deploy canary. The [GKE deployments page](note:3.2-gke-deployments) covers rollout status and undo, and the [health checks page](note:3.2-health-checks) covers the readiness probes that a rolling update depends on.

## GKE: blue/green with Services

A Service selects its Pods with a label selector. A Pod is a member only if it has all the selector labels ([Understand Kubernetes Services](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/service)). For blue/green, run two Deployments with different `version` labels. Point the Service selector at one version, and change the selector to switch all traffic when the new version is ready ([Best practices for continuous integration and delivery to Google Kubernetes Engine](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/best-practices-continuous-integration-delivery-kubernetes)).

```yaml
apiVersion: v1
kind: Service
metadata:
  name: store
spec:
  selector:
    app: store
    version: green   # was "blue"; change it back to roll back
  ports:
  - port: 8080
```

Source: [Understand Kubernetes Services](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/service).

## GKE: canary and A/B with the Gateway API

An `HTTPRoute` can match request headers and split traffic by weight ([About Gateway API](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/gateway-api)). The GKE traffic splitting guide uses four stages ([Deploy a multi-cluster Gateway for weighted traffic splitting](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/deploy-gateway-traffic-splitting)):

1. **Header-based canary:** only test requests with a header, such as `env: canary`, reach the new version.
2. **Traffic mirror:** a `RequestMirror` filter copies all traffic to the new version to test its capacity. Users get responses only from the current version.
3. **Traffic split:** weights send 90% to the current version and 10% to the new version.
4. **Cutover:** weights send 100% to the new version. You can switch back if errors appear.

```yaml
kind: HTTPRoute
apiVersion: gateway.networking.k8s.io/v1
metadata:
  name: store
spec:
  parentRefs:
  - kind: Gateway
    name: internal-http
  hostnames:
  - "store.example.com"
  rules:
  # Test requests with the `env: canary` header always go to store-v2
  - matches:
    - headers:
      - name: env
        value: canary
    backendRefs:
    - name: store-v2
      port: 8080
  # All other requests: 90% to store-v1, 10% to store-v2
  - backendRefs:
    - name: store-v1
      port: 8080
      weight: 90
    - name: store-v2
      port: 8080
      weight: 10
```

Sources: [Deploying Gateways](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/deploying-gateways), [Deploy a multi-cluster Gateway for weighted traffic splitting](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/deploy-gateway-traffic-splitting).

The `gke-l7-gxlb` GatewayClass does not support advanced traffic management such as these weights and mirrors ([Deploy a multi-cluster Gateway for weighted traffic splitting](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/deploy-gateway-traffic-splitting)). For an A/B test, a weighted rule does not keep a user on one version. The load balancer selects a backend by weight first and applies session affinity after that. Do not put weights on a rule that needs stickiness ([Configure Gateway resources using Policies](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/configure-gateway-resources)). A header match sends every request that carries the header to one version, so it keeps a group of users on that version ([Deploying Gateways](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/deploying-gateways)).

## Cloud Deploy canary strategies

Cloud Deploy supports two strategies: standard and canary. Both support rollback. A canary can use any percentages except fractions ([Use a deployment strategy](https://docs.cloud.google.com/deploy/docs/deployment-strategies)).

| Target | How Cloud Deploy splits traffic | Notes |
|---|---|---|
| Cloud Run services and worker pools (not jobs) | Cloud Run splits traffic (instances, for worker pools) between the last stable revision and the new revision | The service YAML must not have a `traffic` stanza |
| GKE with service networking | Creates a `-canary` Deployment and changes the Service selector to include its Pods | The split is by Pod count, so it can be inexact |
| GKE with the Gateway API | Creates a `-canary` Deployment and Service, and changes the `HTTPRoute` weights in each phase | The split is by traffic. A 100% canary phase is allowed |

Sources: [Use a canary deployment strategy](https://docs.cloud.google.com/deploy/docs/deployment-strategies/canary), [Canary Deployments to Cloud Run](https://docs.cloud.google.com/deploy/docs/deployment-strategies/canary/cloud-run), [Canary Deployments to GKE and GKE attached clusters using service-based networking](https://docs.cloud.google.com/deploy/docs/deployment-strategies/canary/gke/service-networking), [Canary Deployments to GKE and GKE attached clusters using Gateway API networking](https://docs.cloud.google.com/deploy/docs/deployment-strategies/canary/gke/gateway-api).

```yaml
serialPipeline:
  stages:
  - targetId: prod
    profiles: []
    strategy:
      canary:
        runtimeConfig:
          cloudRun:
            automaticTrafficControl: true
        canaryDeployment:
          percentages: [25, 50, 75]   # "stable" (100%) is added for you
          verify:
            tasks: [TASKS]
```

Source: [Canary Deployments to Cloud Run](https://docs.cloud.google.com/deploy/docs/deployment-strategies/canary/cloud-run).

How a Cloud Deploy canary runs:

- The rollout has one phase for each percentage, then a `stable` phase. For example: `canary-25`, `canary-50`, `canary-75`, and `stable` ([Use a canary deployment strategy](https://docs.cloud.google.com/deploy/docs/deployment-strategies/canary)).
- A `verify` job runs in each canary phase. A `predeploy` job runs in the first phase, and a `postdeploy` job runs in the `stable` phase ([Canary Deployments to Cloud Run](https://docs.cloud.google.com/deploy/docs/deployment-strategies/canary/cloud-run)).
- The first deployment to a target skips the canary phases, because no earlier version exists to compare ([Use a deployment strategy](https://docs.cloud.google.com/deploy/docs/deployment-strategies)).
- The three canary types are automated, custom-automated, and custom. In a custom canary, you supply all the traffic configuration ([Use a canary deployment strategy](https://docs.cloud.google.com/deploy/docs/deployment-strategies/canary)).
- Deploy analysis with an `advanceRolloutRule` automation can advance the rollout to the next phase automatically ([Use a canary deployment strategy](https://docs.cloud.google.com/deploy/docs/deployment-strategies/canary)).
- With service networking, pod overprovisioning is the default. Large percentages create many Pods: a 90% canary on 4 Pods creates 36 canary Pods ([Canary Deployments to GKE and GKE attached clusters using service-based networking](https://docs.cloud.google.com/deploy/docs/deployment-strategies/canary/gke/service-networking)).

To roll back, run `gcloud deploy targets rollback TARGET_NAME --delivery-pipeline=PIPELINE_NAME`. By default, it creates a new rollout of the last release that deployed successfully to the target ([Roll back a target](https://docs.cloud.google.com/deploy/docs/roll-back)). A `repairRolloutRule` automation retries failed jobs and rolls back if all retries fail ([Using automation rules](https://docs.cloud.google.com/deploy/docs/automation-rules)). The [GKE deployments page](note:3.2-gke-deployments) covers Cloud Deploy pipelines for GKE.

## Cloud Service Mesh traffic splitting

Cloud Service Mesh (formerly Anthos Service Mesh and Traffic Director) supports canary and blue/green deployments. On GKE, it uses the Istio APIs ([Cloud Service Mesh overview](https://docs.cloud.google.com/service-mesh/docs/overview)). A `DestinationRule` defines subsets by the Pod `version` label. A `VirtualService` sets the weight of each subset. To finish the rollout, raise the weight of the new subset step by step until it gets 100% ([Cloud Service Mesh by example: canary deployments](https://docs.cloud.google.com/service-mesh/docs/tutorials/canary-deployment)).

```yaml
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: productcatalogservice
spec:
  hosts:
  - productcatalogservice
  http:
  - route:
    - destination:
        host: productcatalogservice
        subset: v1
      weight: 75
    - destination:
        host: productcatalogservice
        subset: v2
      weight: 25
```

Source: [Cloud Service Mesh by example: canary deployments](https://docs.cloud.google.com/service-mesh/docs/tutorials/canary-deployment).

The [service-to-service page](note:1.2-service-to-service) covers Cloud Service Mesh security.

## Exam traps

- **One deployment with `--no-traffic`, then later deployments that never get traffic.** Run `update-traffic --to-latest` ([gcloud run deploy](https://docs.cloud.google.com/sdk/gcloud/reference/run/deploy)).
- **A new deployment while a split exists, and the expectation that it gets 100%.** The split stays for all later deployments ([Rollbacks, gradual rollouts, and traffic migration](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration)).
- **A rebuild of the old image to roll back Cloud Run.** Send 100% of traffic to the earlier revision ([Rollbacks, gradual rollouts, and traffic migration](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration)).
- **An exact 5% canary on Cloud Run with session affinity on.** Affinity takes precedence over the split, so the real share can differ from 5% ([Set session affinity for services](https://docs.cloud.google.com/run/docs/configuring/session-affinity)).
- **A weighted `HTTPRoute` with session affinity for a sticky A/B test.** The weights take precedence ([Configure Gateway resources using Policies](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/configure-gateway-resources)).
- **A Cloud Deploy service networking canary for an exact 10% of traffic.** It splits by Pod count. Use the Gateway API ([Canary Deployments to GKE and GKE attached clusters using service-based networking](https://docs.cloud.google.com/deploy/docs/deployment-strategies/canary/gke/service-networking)).
- **A canary on the first release to a target.** Cloud Deploy skips the canary phases ([Use a deployment strategy](https://docs.cloud.google.com/deploy/docs/deployment-strategies)).
- **A `traffic` stanza in the service YAML for a Cloud Deploy canary.** Remove it. Cloud Deploy manages the split ([Canary Deployments to Cloud Run](https://docs.cloud.google.com/deploy/docs/deployment-strategies/canary/cloud-run)).
- **A Cloud Deploy canary for a Cloud Run job.** Canary supports services and worker pools only ([Use a canary deployment strategy](https://docs.cloud.google.com/deploy/docs/deployment-strategies/canary)).
- **`maxSurge: 0` and `maxUnavailable: 0`.** Both cannot be 0 ([Deployments](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/)).
- **Tags on revisions with revision-level minimum instances.** You pay for idle instances. Remove unused tags ([Rollbacks, gradual rollouts, and traffic migration](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration)).
- **The `gke-l7-gxlb` GatewayClass for weights or mirroring.** It does not support advanced traffic management ([Deploy a multi-cluster Gateway for weighted traffic splitting](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/deploy-gateway-traffic-splitting)).
- **The error rate of the whole service to judge a canary.** A small canary hides its errors. Compare the canary with the control ([Canarying Releases](https://sre.google/workbook/canarying-releases/)).
- **Traffic splitting on Cloud Run functions (1st gen).** It is not supported ([Compare Cloud Run functions](https://docs.cloud.google.com/run/docs/functions/comparison)).
