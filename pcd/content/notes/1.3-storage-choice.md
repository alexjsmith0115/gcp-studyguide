## Why it matters

The storage system decides what your code can do with its data: transactions and joins, lookups by key, document queries, or file access. Each system also has its own limits for volume, request rate, and latency. The exam describes the data, the access pattern, and the scale, and then asks for the Google-recommended service. Most wrong options are real products that do a different job, for example BigQuery as the database of a transactional app.

## Key points

- **Cloud SQL** runs managed MySQL, PostgreSQL, and SQL Server. An instance with dedicated cores stores up to 64 TB ([Cloud SQL overview](https://docs.cloud.google.com/sql/docs/introduction), [Cloud SQL quotas and limits](https://docs.cloud.google.com/sql/docs/quotas)).
- **AlloyDB for PostgreSQL** is a PostgreSQL-compatible service for demanding transactional workloads and for analytics on live transactional data ([AlloyDB overview](https://docs.cloud.google.com/alloydb/docs/overview)). A cluster stores 16 TiB by default and up to 128 TiB ([AlloyDB quotas and limits](https://docs.cloud.google.com/alloydb/quotas)).
- **Spanner** (formerly Cloud Spanner) is a relational database that scales horizontally ([Your Google Cloud database options, explained](https://cloud.google.com/blog/topics/developers-practitioners/your-google-cloud-database-options-explained)). Read and write throughput grow linearly with compute capacity, and each node holds 10 TiB of data ([Performance overview](https://docs.cloud.google.com/spanner/docs/performance), [Compute capacity, nodes and processing units](https://docs.cloud.google.com/spanner/docs/compute-capacity)).
- **Bigtable** (formerly Cloud Bigtable) is a wide-column NoSQL database for terabytes or petabytes of single-keyed data, with high throughput at low latency ([Bigtable overview](https://docs.cloud.google.com/bigtable/docs/overview), [Your Google Cloud database options, explained](https://cloud.google.com/blog/topics/developers-practitioners/your-google-cloud-database-options-explained)). It performs best with large tables that get frequent requests ([Understand performance](https://docs.cloud.google.com/bigtable/docs/performance)).
- **Firestore** is a serverless document database. It needs no capacity planning, scales automatically, and gives single-digit millisecond reads and ACID transactions ([Firestore overview](https://docs.cloud.google.com/firestore/native/docs/overview)).
- **BigQuery** is a serverless analytics platform with columnar storage. It queries terabytes in seconds and petabytes in minutes ([BigQuery overview](https://docs.cloud.google.com/bigquery/docs/introduction)). It is not a database for frequent small updates: a table runs at most 2 `UPDATE`, `DELETE`, or `MERGE` statements at the same time ([Transform data with DML](https://docs.cloud.google.com/bigquery/docs/data-manipulation-language)).
- **Cloud Storage** has no lower or upper capacity limit. An object can be 5 TiB, but you can write to one object name only once per second ([Design an optimal storage strategy for your cloud workload](https://docs.cloud.google.com/architecture/storage-advisor), [Cloud Storage quotas and limits](https://docs.cloud.google.com/storage/quotas)).
- **Memorystore** gives managed Valkey, Redis, and Memcached caches, and Memorystore for Memcached is deprecated ([Memorystore](https://docs.cloud.google.com/memorystore/docs)). Memorystore for Redis gives sub-millisecond data access ([Memorystore for Redis overview](https://docs.cloud.google.com/memorystore/docs/redis/memorystore-for-redis-overview)).
- **Filestore** is a managed NFS file server. VMs, GKE clusters, and Cloud Run services can use one file system at the same time ([Filestore overview](https://docs.cloud.google.com/filestore/docs/overview)).
- **Block storage** (Hyperdisk, Persistent Disk, and Local SSD) attaches to Compute Engine VMs and GKE clusters. Local SSD data is lost when the VM stops or is deleted ([Design an optimal storage strategy for your cloud workload](https://docs.cloud.google.com/architecture/storage-advisor)).
- **Cloud Run** has an in-memory file system. Files use instance memory and disappear when the instance stops ([Container runtime contract](https://docs.cloud.google.com/run/docs/container-contract)).

## Use each service when

| Service | Use it when | Do not use it when |
|---|---|---|
| Cloud SQL | A general-purpose relational app uses MySQL, PostgreSQL, or SQL Server, with up to 64 TB of data | The data grows past 64 TB, or writes must scale past one primary instance |
| AlloyDB | A PostgreSQL app needs more performance, analytics on live transactional data, or up to 128 TiB | The app uses MySQL or SQL Server |
| Spanner | Relational data needs horizontal scale, strong consistency, and up to 99.999% availability | A general-purpose app has no need to scale out. Google suggests Cloud SQL for general-purpose SQL databases |
| Bigtable | Terabytes to petabytes of key-value or time-series data need high throughput and low-latency reads by row key | The dataset is small, or the app needs joins or transactions across rows |
| Firestore | Web, mobile, and server apps store documents, with automatic scaling, real-time listeners, and offline support | Items are larger than 1 MiB, the maximum document size in Native mode |
| BigQuery | Analysts and ML jobs query large datasets with SQL | An app updates single rows often |
| Cloud Storage | The app stores unstructured objects: media, backups, data lake files, or static web content | The app writes the same object name more than once per second, or needs file locking |
| Filestore | Several VMs, GKE Pods, or Cloud Run instances need one shared NFS file system | Clients need SMB. Use NetApp Volumes |
| Hyperdisk or Persistent Disk | A VM or a GKE Pod needs a durable block device, for example for a self-managed database | Many clients must write the same data. Block disks support only limited multi-writer access |
| Local SSD | A VM needs fast scratch space or a cache | The data must survive a VM stop |
| Memorystore | An app needs a cache with sub-millisecond data access | A new design selects Memcached, which is deprecated |

## Volume, throughput, and scaling limits

| Service | Capacity | How it scales | Limit that changes the design |
|---|---|---|---|
| Cloud SQL | Up to 64 TB with dedicated cores, 3 TB with a shared core | Vertical: a larger machine type. Read replicas for reads | The connection limit (`max_connections`) depends on the memory of the machine type |
| AlloyDB | 16 TiB per cluster by default, up to 128 TiB | Compute and storage scale separately. Read pool instances add up to 20 nodes per cluster | One primary instance per cluster takes all writes |
| Spanner | 10 TiB per node. Below 1 node: 1,024 GiB for every 100 processing units | Horizontal: add nodes or processing units | Storage follows compute capacity, so data growth can need more nodes |
| Bigtable | 5 TB per node on SSD, 16 TB per node on HDD | Horizontal: add nodes, or turn on autoscaling | If one cluster passes the storage limit, writes to all clusters fail. Plan for 70% use |
| Firestore | No provisioning | Automatic | 1 MiB per document in Native mode. Ramp up traffic to a new collection: 500 operations per second, then 50% more every 5 minutes |
| BigQuery | Petabytes | Serverless | 2 concurrent mutating DML statements per table, and 20 more in the queue |
| Cloud Storage | No lower or upper limit | Automatic, for each bucket and key range | 5 TiB per object. About 1,000 writes and 5,000 reads per second for each bucket before autoscaling |
| Filestore | 1 to 100 TiB per instance | Basic tiers (legacy): up only. Zonal and Regional tiers: up and down | — |
| Hyperdisk | 4 GiB to 64 TiB per disk, up to 512 TiB per VM | Scale up | — |
| Persistent Disk | 10 GiB to 64 TiB per disk, up to 257 TiB per VM | Scale up, or add disks | — |

Sources: [Cloud SQL quotas and limits](https://docs.cloud.google.com/sql/docs/quotas), [AlloyDB quotas and limits](https://docs.cloud.google.com/alloydb/quotas), [AlloyDB overview](https://docs.cloud.google.com/alloydb/docs/overview), [Compute capacity, nodes and processing units](https://docs.cloud.google.com/spanner/docs/compute-capacity), [Performance overview](https://docs.cloud.google.com/spanner/docs/performance), [Bigtable quotas and limits](https://docs.cloud.google.com/bigtable/quotas), [Bigtable overview](https://docs.cloud.google.com/bigtable/docs/overview), [Firestore quotas and limits](https://docs.cloud.google.com/firestore/quotas), [Firestore editions overview](https://docs.cloud.google.com/firestore/native/docs/editions-overview), [Firestore best practices](https://docs.cloud.google.com/firestore/native/docs/best-practices), [BigQuery overview](https://docs.cloud.google.com/bigquery/docs/introduction), [Transform data with DML](https://docs.cloud.google.com/bigquery/docs/data-manipulation-language), [Request rate and access distribution guidelines](https://docs.cloud.google.com/storage/docs/request-rate), [About service tiers](https://docs.cloud.google.com/filestore/docs/service-tiers), [Design an optimal storage strategy for your cloud workload](https://docs.cloud.google.com/architecture/storage-advisor).

Scale rules that the exam tests:

- **Small Bigtable tables.** Bigtable keeps all tablets of a table on one node until the table holds more than several GB. Low request rates also increase latency ([Understand performance](https://docs.cloud.google.com/bigtable/docs/performance)).
- **Cloud Storage ramp-up.** Above about 1,000 writes or 5,000 reads per second, start near those rates. Then increase the rate no faster than double every 20 minutes ([Request rate and access distribution guidelines](https://docs.cloud.google.com/storage/docs/request-rate)).
- **Object names.** Sequential names, for example names that start with a timestamp, slow the autoscaling of the key index. Add a short hash prefix to spread the load ([Request rate and access distribution guidelines](https://docs.cloud.google.com/storage/docs/request-rate)).
- **Hierarchical namespace.** A bucket with hierarchical namespace starts with up to 8 times higher read and write limits ([Request rate and access distribution guidelines](https://docs.cloud.google.com/storage/docs/request-rate)).

## Relational: Cloud SQL, AlloyDB, or Spanner

| | Cloud SQL | AlloyDB | Spanner |
|---|---|---|---|
| Engine | MySQL, PostgreSQL, or SQL Server | PostgreSQL-compatible | GoogleSQL or PostgreSQL dialect |
| Writes | One primary instance. Read replicas are read-only | One primary instance per cluster | Horizontal scale |
| Reads | Read replicas. Read pools in Enterprise Plus edition | Read pool instances with load balancing | More compute capacity. Optional read-only replicas |
| Availability SLA | Enterprise edition: 99.95%, without maintenance. Enterprise Plus edition: 99.99%, with maintenance | 99.99%, with maintenance | Standard and Enterprise editions: 99.99%. Enterprise Plus edition: up to 99.999% |
| Typical use | General-purpose web apps, CRM, ERP, SaaS, and e-commerce | Demanding transactional workloads, HTAP, and vector search | Strongly consistent apps at global scale: payments, ledgers, and inventory |

Sources: [Cloud SQL editions overview](https://docs.cloud.google.com/sql/docs/postgres/editions-intro), [About replication in Cloud SQL](https://docs.cloud.google.com/sql/docs/postgres/replication), [AlloyDB overview](https://docs.cloud.google.com/alloydb/docs/overview), [AlloyDB for PostgreSQL](https://cloud.google.com/products/alloydb), [Spanner editions overview](https://docs.cloud.google.com/spanner/docs/editions-overview), [Performance overview](https://docs.cloud.google.com/spanner/docs/performance), [Your Google Cloud database options, explained](https://cloud.google.com/blog/topics/developers-practitioners/your-google-cloud-database-options-explained).

Start with Cloud SQL for a general-purpose app ([Your Google Cloud database options, explained](https://cloud.google.com/blog/topics/developers-practitioners/your-google-cloud-database-options-explained)). Choose Spanner for large-scale, globally scalable, and strongly consistent workloads ([Your Google Cloud database options, explained](https://cloud.google.com/blog/topics/developers-practitioners/your-google-cloud-database-options-explained)). Choose AlloyDB when a PostgreSQL workload needs analytics on live transactional data or AI features in the database ([AlloyDB overview](https://docs.cloud.google.com/alloydb/docs/overview)). Its columnar engine keeps data in memory in a columnar format to speed up analytical queries ([AlloyDB overview](https://docs.cloud.google.com/alloydb/docs/overview)).

For schema design and a closer AlloyDB and Cloud SQL comparison, see [Schema design for AlloyDB and Spanner](note:1.3-relational-schema). For replicas, read pools, and stale reads, see [Consistency and replication](note:1.3-consistency-and-replication).

## NoSQL: Firestore or Bigtable

| | Firestore | Bigtable |
|---|---|---|
| Data model | Documents in collections | A sorted key-value map. Rows have column families and timestamped cells |
| Capacity | Serverless and pay per use. No provisioning | Nodes in clusters. Autoscaling changes the node count |
| Read latency | Single-digit milliseconds | Low. The in-memory tier (Preview) gives sub-millisecond reads |
| Transactions | ACID transactions | Single-row transactions only |
| Clients | Server, web, and mobile libraries, with real-time listeners and offline support | Client libraries, and the Apache HBase API for Java |
| Typical data | E-commerce, gaming, IoT, and real-time dashboards | Time series, marketing, financial, and IoT data, also for batch and stream processing |

Sources: [Firestore overview](https://docs.cloud.google.com/firestore/native/docs/overview), [Choose between Firestore APIs](https://docs.cloud.google.com/datastore/docs/firestore-or-datastore), [Firestore](https://firebase.google.com/docs/firestore), [Bigtable overview](https://docs.cloud.google.com/bigtable/docs/overview), [Schema design best practices](https://docs.cloud.google.com/bigtable/docs/schema-design), [Your Google Cloud database options, explained](https://cloud.google.com/blog/topics/developers-practitioners/your-google-cloud-database-options-explained).

- **Bigtable is not a traditional relational database.** For structured objects with ACID transactions and SQL-like queries, the Bigtable docs point to Firestore. For OLAP queries, they point to BigQuery ([Bigtable overview](https://docs.cloud.google.com/bigtable/docs/overview)).
- **Firestore access modes.** New apps use the Firestore API. Firestore in Datastore mode (formerly Cloud Datastore) is only for legacy apps that depend on the Datastore API, such as App Engine apps ([Choose between Firestore APIs](https://docs.cloud.google.com/datastore/docs/firestore-or-datastore), [Datastore overview](https://docs.cloud.google.com/datastore/docs/concepts/overview)). Firestore with MongoDB compatibility lets MongoDB apps and tools use Firestore ([Firestore overview](https://docs.cloud.google.com/firestore/native/docs/overview)).
- **Firebase name.** The Firebase docs still say Cloud Firestore ([Firestore](https://firebase.google.com/docs/firestore)).

For keys, indexes, and hotspots, see [Schema design for Bigtable and Firestore](note:1.3-nosql-schema).

## Files and objects from Cloud Run, GKE, and VMs

| Need | Use | Watch for |
|---|---|---|
| Temporary files in a Cloud Run instance | The in-memory file system, or an in-memory volume with a size limit | Files use instance memory, and they disappear when the instance stops |
| Objects that code reads and writes through the API | Cloud Storage with the client library | One write per second to the same object name |
| Bucket contents as local files in Cloud Run | A Cloud Storage volume mount (Cloud Storage FUSE) | No file locking, so the last write wins. Not fully POSIX-compliant |
| One shared POSIX file system | Filestore. Cloud Run mounts it as an NFS volume | Cloud Run mounts NFS in no-lock mode. The service needs a VPC connection, preferably Direct VPC |
| A disk for a VM or a GKE Pod | Hyperdisk or Persistent Disk | A zonal disk stays in one zone. For redundancy across zones, use Hyperdisk Balanced High Availability or regional Persistent Disk |
| Fast scratch space on a VM | Local SSD | Data is lost when the VM stops or is deleted |

Sources: [Container runtime contract](https://docs.cloud.google.com/run/docs/container-contract), [Cloud Storage quotas and limits](https://docs.cloud.google.com/storage/quotas), [Configure Cloud Storage volume mounts for Cloud Run services](https://docs.cloud.google.com/run/docs/configuring/services/cloud-storage-volume-mounts), [Configure NFS volume mounts for services](https://docs.cloud.google.com/run/docs/configuring/services/nfs-volume-mounts), [Filestore overview](https://docs.cloud.google.com/filestore/docs/overview), [Design an optimal storage strategy for your cloud workload](https://docs.cloud.google.com/architecture/storage-advisor).

Pick the Cloud Storage class by access frequency and storage time:

| Storage class | Minimum storage duration | Use for |
|---|---|---|
| Standard (default) | None | Frequently read data: websites, streaming video, mobile apps, and analytics |
| Nearline | 30 days | Backups and long-tail media |
| Coldline | 90 days | Disaster recovery data |
| Archive | 365 days | Regulatory archives |

Sources: [Storage classes](https://docs.cloud.google.com/storage/docs/storage-classes), [Design an optimal storage strategy for your cloud workload](https://docs.cloud.google.com/architecture/storage-advisor).

Even Archive data is available within milliseconds, not hours or days. The colder classes cost less to store, but they add costs for data access ([Storage classes](https://docs.cloud.google.com/storage/docs/storage-classes)). When the access pattern is unknown, turn on Autoclass ([Design an optimal storage strategy for your cloud workload](https://docs.cloud.google.com/architecture/storage-advisor)). For lifecycle rules and retention, see [Data retention and organization policies](note:1.2-retention-and-org-policy).

## Analytics and caching

- **BigQuery next to the app database.** For frequent inserts, the BigQuery docs suggest the Storage Write API instead of DML `INSERT` statements ([Transform data with DML](https://docs.cloud.google.com/bigquery/docs/data-manipulation-language)). For the write paths, see [Writing data to BigQuery](note:1.3-bigquery-writes).
- **Analytics on live data.** AlloyDB runs analytical queries on live transactional data with its columnar engine ([AlloyDB overview](https://docs.cloud.google.com/alloydb/docs/overview)). The Spanner Enterprise and Enterprise Plus editions also include a columnar engine ([Spanner editions overview](https://docs.cloud.google.com/spanner/docs/editions-overview)).
- **Caches.** Memorystore offers Memorystore for Valkey, Memorystore for Redis Cluster, and Memorystore for Redis ([Memorystore](https://docs.cloud.google.com/memorystore/docs)). For cache patterns and connections from Cloud Run, see [Caching with Memorystore and Cloud CDN](note:1.1-caching).

## Exam traps

- **BigQuery as the database of a transactional app.** A table runs at most 2 mutating DML statements at a time and queues 20 more. Use an operational database for app transactions ([Transform data with DML](https://docs.cloud.google.com/bigquery/docs/data-manipulation-language)).
- **Bigtable for a small dataset or for multi-row transactions.** Bigtable performs best with large tables, and it supports transactions only within a single row ([Understand performance](https://docs.cloud.google.com/bigtable/docs/performance), [Schema design best practices](https://docs.cloud.google.com/bigtable/docs/schema-design)).
- **Spanner for every relational app.** For a general-purpose SQL database, Google suggests Cloud SQL. Spanner is for large-scale, strongly consistent workloads ([Your Google Cloud database options, explained](https://cloud.google.com/blog/topics/developers-practitioners/your-google-cloud-database-options-explained)).
- **Cloud SQL past 64 TB.** AlloyDB stores up to 128 TiB per cluster, and Spanner adds storage with each node ([Cloud SQL quotas and limits](https://docs.cloud.google.com/sql/docs/quotas), [AlloyDB quotas and limits](https://docs.cloud.google.com/alloydb/quotas), [Compute capacity, nodes and processing units](https://docs.cloud.google.com/spanner/docs/compute-capacity)).
- **A read replica for more write capacity.** Cloud SQL read replicas are read-only ([About replication in Cloud SQL](https://docs.cloud.google.com/sql/docs/postgres/replication)).
- **Files on the Cloud Run file system.** The file system is in memory and does not persist. Use Cloud Storage or Filestore ([Container runtime contract](https://docs.cloud.google.com/run/docs/container-contract), [Configure Cloud Storage volume mounts for Cloud Run services](https://docs.cloud.google.com/run/docs/configuring/services/cloud-storage-volume-mounts), [Configure NFS volume mounts for services](https://docs.cloud.google.com/run/docs/configuring/services/nfs-volume-mounts)).
- **Several writers through a Cloud Storage volume mount.** Cloud Storage FUSE has no file locking, and the last write wins ([Configure Cloud Storage volume mounts for Cloud Run services](https://docs.cloud.google.com/run/docs/configuring/services/cloud-storage-volume-mounts)).
- **A counter or a status record in one Cloud Storage object.** One object name accepts one write per second. Faster writes can fail with throttling errors ([Cloud Storage quotas and limits](https://docs.cloud.google.com/storage/quotas)).
- **Timestamp object names at high request rates.** Sequential names slow autoscaling. Add a hash prefix ([Request rate and access distribution guidelines](https://docs.cloud.google.com/storage/docs/request-rate)).
- **A restore step for Archive storage.** Archive data is available within milliseconds. The trade-offs are a 365-day minimum storage duration and retrieval fees ([Storage classes](https://docs.cloud.google.com/storage/docs/storage-classes)).
- **Local SSD for data that must survive.** Local SSD is ephemeral ([Design an optimal storage strategy for your cloud workload](https://docs.cloud.google.com/architecture/storage-advisor)).
- **A Bigtable cluster at its storage limit.** If one cluster passes the limit per node, writes fail in all clusters of the instance ([Bigtable quotas and limits](https://docs.cloud.google.com/bigtable/quotas)).
