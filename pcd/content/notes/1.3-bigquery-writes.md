## Why it matters

Your code can put rows into BigQuery in several ways: load jobs, the Storage Write API, a Pub/Sub BigQuery subscription, Dataflow, or DML statements. Each path has a different latency, cost, and delivery guarantee. The exam gives a source, a latency need, and a duplicate rule, and asks for the write path. It also tests the DML limits for small frequent writes and how BigQuery ML uses the stored data.

## Key points

- Batch load jobs from Cloud Storage are free when they use the shared slot pool. Load jobs can be a less expensive way to load data that does not change often ([BigQuery pricing](https://cloud.google.com/bigquery/pricing), [Introduction to loading data](https://docs.cloud.google.com/bigquery/docs/loading-data)).
- For new streaming code, use the Storage Write API (gRPC). It costs less than the legacy streaming API and supports exactly-once delivery ([Use the Storage Write API (REST)](https://docs.cloud.google.com/bigquery/docs/write-api-rest)).
- The default stream of the Storage Write API gives at-least-once delivery, and the data is available for query at once ([Introduction to the Storage Write API (gRPC)](https://docs.cloud.google.com/bigquery/docs/write-api-grpc)).
- For exactly-once delivery, create a stream of committed type and give an offset with each append ([Stream data using the Storage Write API (gRPC)](https://docs.cloud.google.com/bigquery/docs/write-api-streaming)).
- A stream of pending type keeps rows until you commit, and the commit is atomic. Use it for batch work, as an alternative to load jobs ([Introduction to the Storage Write API (gRPC)](https://docs.cloud.google.com/bigquery/docs/write-api-grpc)).
- The legacy `tabledata.insertAll` method is now the Storage Write API (REST). Its `insertId` de-duplication is only best effort ([Use the Storage Write API (REST)](https://docs.cloud.google.com/bigquery/docs/write-api-rest)).
- A Pub/Sub BigQuery subscription writes messages to a table with no subscriber code. It supports only at-least-once delivery ([BigQuery subscriptions](https://docs.cloud.google.com/pubsub/docs/bigquery)).
- Use Dataflow for custom sources, or for complex transforms, windows, and aggregation before the write ([Introduction to loading data](https://docs.cloud.google.com/bigquery/docs/loading-data), [BigQuery subscriptions](https://docs.cloud.google.com/pubsub/docs/bigquery)).
- After the first 1,500 `INSERT` statements in 24 hours, BigQuery runs at most 10 at a time on a table. For frequent inserts, use the Storage Write API ([Transform data with DML](https://docs.cloud.google.com/bigquery/docs/data-manipulation-language)).
- Partitioning lets queries skip data. Clustering helps when filters use several columns or values with high cardinality ([Introduction to partitioned tables](https://docs.cloud.google.com/bigquery/docs/partitioned-tables)).
- BigQuery ML creates and runs models with GoogleSQL, so the data stays in BigQuery. AI functions send rows to Gemini models and store the results in BigQuery ([Introduction to ML in BigQuery](https://docs.cloud.google.com/bigquery/docs/bqml-introduction), [Generative AI overview](https://docs.cloud.google.com/bigquery/docs/generative-ai-overview)).

## Choose a write path

Start from where the data comes from and how fast it must be queryable. Then check the delivery guarantee that you need.

| Path | Data is queryable | Delivery | Use when |
|---|---|---|---|
| Load job from Cloud Storage | After the job completes | Each job succeeds or fails as a unit | Files arrive in batches, and you want the lowest cost |
| BigQuery Data Transfer Service | After each scheduled load | Scheduled load jobs | Recurring loads from Cloud Storage and other sources |
| Storage Write API, default stream | At once | At-least-once | Continuous streaming from your code |
| Storage Write API, committed type with offsets | At once | Exactly-once | Streaming where duplicates are not acceptable |
| Storage Write API, pending type | After the commit | Atomic commit | Batch writes from code |
| Pub/Sub BigQuery subscription | As messages arrive | At-least-once | Messages need no processing, or only a Single Message Transform |
| Dataflow | Depends on the write method | Exactly-once with `STORAGE_WRITE_API` | Custom sources, complex transforms, windows, aggregation |
| Storage Write API (REST), formerly `tabledata.insertAll` | At once | Best-effort de-duplication | Existing code only |
| DML `INSERT` | After the statement | Each statement is a transaction | A few small changes, not a high write rate |

Sources: [Introduction to loading data](https://docs.cloud.google.com/bigquery/docs/loading-data), [Introduction to the Storage Write API (gRPC)](https://docs.cloud.google.com/bigquery/docs/write-api-grpc), [BigQuery subscriptions](https://docs.cloud.google.com/pubsub/docs/bigquery), [Write from Dataflow to BigQuery](https://docs.cloud.google.com/dataflow/docs/guides/write-to-bigquery), [Use the Storage Write API (REST)](https://docs.cloud.google.com/bigquery/docs/write-api-rest), [Transform data with DML](https://docs.cloud.google.com/bigquery/docs/data-manipulation-language).

Cost differs by path. Batch loads with the shared slot pool are free, and you pay for storage after the load. The Storage Write API (gRPC) includes 2 TiB each month at no charge. The Storage Write API (REST) charges each row as at least 1 KB ([BigQuery pricing](https://cloud.google.com/bigquery/pricing)). The shared slot pool has no capacity guarantee. For guaranteed capacity, use a reservation ([Write from Dataflow to BigQuery](https://docs.cloud.google.com/dataflow/docs/guides/write-to-bigquery)).

## Batch load jobs

A load job reads files from Cloud Storage or a local file. The formats are Avro, CSV, JSON, ORC, and Parquet. You can also run the `LOAD DATA` SQL statement ([Introduction to loading data](https://docs.cloud.google.com/bigquery/docs/loading-data)). Datastore and Firestore exports are also valid sources ([Batch load data](https://docs.cloud.google.com/bigquery/docs/batch-loading-data)). For scheduled loads, the docs recommend the BigQuery Data Transfer Service ([Introduction to loading data](https://docs.cloud.google.com/bigquery/docs/loading-data)).

```python
from google.cloud import bigquery

client = bigquery.Client()
# table_id = "your-project.your_dataset.your_table_name"

job_config = bigquery.LoadJobConfig(
    source_format=bigquery.SourceFormat.PARQUET,
)
uri = "gs://cloud-samples-data/bigquery/us-states/us-states.parquet"

load_job = client.load_table_from_uri(uri, table_id, job_config=job_config)
load_job.result()  # Waits for the job to complete.
```

Source: [Load Parquet data from Cloud Storage](https://docs.cloud.google.com/bigquery/docs/loading-data-cloud-storage-parquet).

The write disposition decides what happens to existing data ([Load Parquet data from Cloud Storage](https://docs.cloud.google.com/bigquery/docs/loading-data-cloud-storage-parquet)):

| Disposition | Effect |
|---|---|
| `WRITE_APPEND` (default) | Adds the rows to the table |
| `WRITE_TRUNCATE` | Erases the existing data. It also deletes the table schema and row-level security, and removes the Cloud KMS key |
| `WRITE_EMPTY` | Writes only if the table is empty |

Source: [Load Parquet data from Cloud Storage](https://docs.cloud.google.com/bigquery/docs/loading-data-cloud-storage-parquet).

Know these load limits:

- A table allows 1,500 load jobs each day, and failed jobs count. A project allows 100,000 load jobs each day ([Quotas and limits](https://docs.cloud.google.com/bigquery/quotas)). So do not run one load job for each event.
- A Cloud Storage URI can contain one wildcard. A URI with an object generation number makes the load job fail ([Batch load data](https://docs.cloud.google.com/bigquery/docs/batch-loading-data)).
- Parquet and Avro files describe their own schema, so BigQuery reads the schema from them ([Load Parquet data from Cloud Storage](https://docs.cloud.google.com/bigquery/docs/loading-data-cloud-storage-parquet), [Load Avro data from Cloud Storage](https://docs.cloud.google.com/bigquery/docs/loading-data-cloud-storage-avro)).

## The Storage Write API (gRPC)

The Storage Write API sends rows over a gRPC connection. The caller needs `bigquery.tables.updateData`, for example through BigQuery Data Editor ([Introduction to the Storage Write API (gRPC)](https://docs.cloud.google.com/bigquery/docs/write-api-grpc)). You write to a stream. The stream type sets when rows become visible and which delivery guarantee you get:

| Stream | Rows become visible | Delivery | Use for |
|---|---|---|---|
| Default stream | At once | At-least-once | Continuous streaming. You do not create it, and it has fewer quota limits |
| Committed type | At once | Exactly-once with offsets | Streaming that must not write duplicates |
| Pending type | When you commit the stream. The commit is atomic | Exactly-once | Batch writes, as an alternative to load jobs |
| Buffered type | When you flush the stream | Row-level commits | Generally do not use, except with the Apache Beam BigQuery I/O connector |

Sources: [Introduction to the Storage Write API (gRPC)](https://docs.cloud.google.com/bigquery/docs/write-api-grpc), [BigQuery Storage Write API (gRPC) best practices](https://docs.cloud.google.com/bigquery/docs/write-api-best-practices).

The Python client is low level. You send rows as serialized protocol buffers or in Apache Arrow format ([Introduction to the Storage Write API (gRPC)](https://docs.cloud.google.com/bigquery/docs/write-api-grpc)). This shortened docs sample appends rows to the default stream:

```python
from google.cloud import bigquery_storage_v1
from google.cloud.bigquery_storage_v1 import types, writer
from google.protobuf import descriptor_pb2
import sample_data_pb2  # class compiled from your .proto file

write_client = bigquery_storage_v1.BigQueryWriteClient()
parent = write_client.table_path(project_id, dataset_id, table_id)

request_template = types.AppendRowsRequest()
request_template.write_stream = f"{parent}/_default"
proto_schema = types.ProtoSchema()
proto_descriptor = descriptor_pb2.DescriptorProto()
sample_data_pb2.SampleData.DESCRIPTOR.CopyToProto(proto_descriptor)
proto_schema.proto_descriptor = proto_descriptor
proto_data = types.AppendRowsRequest.ProtoData()
proto_data.writer_schema = proto_schema
request_template.proto_rows = proto_data
append_rows_stream = writer.AppendRowsStream(write_client, request_template)

proto_rows = types.ProtoRows()
for row in data:  # a batch of rows in one request
    proto_rows.serialized_rows.append(create_row_data(row))
request = types.AppendRowsRequest()
proto_data = types.AppendRowsRequest.ProtoData()
proto_data.rows = proto_rows
request.proto_rows = proto_data
append_rows_stream.send(request)
```

Source: [Stream data using the Storage Write API (gRPC)](https://docs.cloud.google.com/bigquery/docs/write-api-streaming).

### Exactly-once with offsets

With committed type, the app gives the next append offset in each `AppendRows` call. BigQuery writes the rows only if the offset matches the next append offset. Without an offset, a retry after an error can write the same rows twice ([Stream data using the Storage Write API (gRPC)](https://docs.cloud.google.com/bigquery/docs/write-api-streaming)). With an offset, a retry is safe. Handle two errors ([BigQuery Storage Write API (gRPC) best practices](https://docs.cloud.google.com/bigquery/docs/write-api-best-practices)):

- `ALREADY_EXISTS`: the rows are already written. Ignore the error.
- `OUT_OF_RANGE`: an earlier write failed. Retry from the last successful write.

You may not need exactly-once. If the upstream system delivers at least once, or you can find duplicates after the load, use the default stream. It needs no offset tracking ([BigQuery Storage Write API (gRPC) best practices](https://docs.cloud.google.com/bigquery/docs/write-api-best-practices)). The default stream also gives higher throughput, and it does not count against the quota for stream creation ([Introduction to the Storage Write API (gRPC)](https://docs.cloud.google.com/bigquery/docs/write-api-grpc)).

### Write code that scales

Follow these practices ([BigQuery Storage Write API (gRPC) best practices](https://docs.cloud.google.com/bigquery/docs/write-api-best-practices), [Introduction to the Storage Write API (gRPC)](https://docs.cloud.google.com/bigquery/docs/write-api-grpc)):

- Send a batch of rows in each `AppendRows` call, not one row at a time. Requests larger than 1 MB are more efficient.
- Do not wait for each response before the next append. Responses arrive in request order.
- Use one connection for as many writes as possible. An application-created stream allows only one active connection.
- Do not call `CreateWriteStream` at a high rate. Prefer the default stream.
- Update the table schema before you send new fields. A row with an extra field fails with `SCHEMA_MISMATCH_EXTRA_FIELD`.
- If BigQuery stays unavailable, keep the rows. Publish them to a Pub/Sub topic, or store them on the client, and insert them later.

Rows streamed into a partitioned table go first to the `__UNPARTITIONED__` partition. No SLA says when they move to their partition ([Introduction to the Storage Write API (gRPC)](https://docs.cloud.google.com/bigquery/docs/write-api-grpc)). For the pending type, the flow is `CreateWriteStream`, `AppendRows`, `FinalizeWriteStream`, and `BatchCommitWriteStreams` ([Introduction to the Storage Write API (gRPC)](https://docs.cloud.google.com/bigquery/docs/write-api-grpc)). Several workers can each write and finalize a stream. The main process then commits the data. If a worker fails, its data does not appear, and you can retry that worker ([Batch load data using the Storage Write API (gRPC)](https://docs.cloud.google.com/bigquery/docs/write-api-batch)).

## Legacy streaming inserts

The Storage Write API (REST) was previously the `tabledata.insertAll` method. It is still fully supported. For new projects, the docs recommend the gRPC API, and for a migration they recommend the default stream ([Use the Storage Write API (REST)](https://docs.cloud.google.com/bigquery/docs/write-api-rest)).

```python
errors = client.insert_rows_json(
    table_id, rows_to_insert, row_ids=[None] * len(rows_to_insert)
)  # no insertId: best-effort de-duplication is off
if errors == []:
    print("New rows have been added.")
```

Source: [Use the Storage Write API (REST)](https://docs.cloud.google.com/bigquery/docs/write-api-rest).

Know these facts ([Use the Storage Write API (REST)](https://docs.cloud.google.com/bigquery/docs/write-api-rest)):

- With an `insertId`, BigQuery tries to remove duplicates for up to one minute. Do not rely on it to prevent duplicates.
- The docs recommend that you leave `insertId` empty, which turns off best-effort de-duplication.
- Streaming is not available in the free tier.
- Some recently streamed rows cannot be copied for a few minutes, and in rare cases for up to 90 minutes.

DML is different for the two APIs. `UPDATE`, `DELETE`, and `MERGE` cannot change rows that the REST API wrote in the last 30 minutes. Rows that the gRPC API wrote recently can be changed ([Transform data with DML](https://docs.cloud.google.com/bigquery/docs/data-manipulation-language)).

## Pub/Sub BigQuery subscriptions and Dataflow

A BigQuery subscription writes each message to an existing table as it arrives. You run no subscriber client and no Dataflow job ([BigQuery subscriptions](https://docs.cloud.google.com/pubsub/docs/bigquery)). For Pub/Sub topics and subscribers in general, see [Messaging](note:4.1-messaging).

| | BigQuery subscription | Dataflow |
|---|---|---|
| Code to run | None | A pipeline, or a Google template |
| Processing | None, or a Single Message Transform for light changes | Complex transforms, windows, and aggregation |
| Delivery | At-least-once | The Pub/Sub to BigQuery template enforces exactly-once by default |
| Write method | Storage Write API (gRPC) | Chosen by Managed I/O, or set on BigQueryIO |
| Failed writes | Pub/Sub sends the message again, then moves it to a dead-letter topic if you configure one | Handled in the pipeline |

Sources: [BigQuery subscriptions](https://docs.cloud.google.com/pubsub/docs/bigquery), [Write from Dataflow to BigQuery](https://docs.cloud.google.com/dataflow/docs/guides/write-to-bigquery).

A message in the dead-letter topic has the attribute `CloudPubSubDeadLetterSourceDeliveryErrorMessage`, which gives the reason for the failure. A subscription can also apply change data capture: the `_CHANGE_TYPE` field is `UPSERT` or `DELETE`, and the table must have a primary key ([BigQuery subscriptions](https://docs.cloud.google.com/pubsub/docs/bigquery)).

In Dataflow, prefer Managed I/O, which chooses the write method for you. The BigQueryIO write methods are ([Write from Dataflow to BigQuery](https://docs.cloud.google.com/dataflow/docs/guides/write-to-bigquery)):

| Method | Behavior |
|---|---|
| `STORAGE_WRITE_API` | Storage Write API with exactly-once semantics |
| `STORAGE_API_AT_LEAST_ONCE` | Storage Write API with at-least-once semantics. Lower latency, but duplicates are possible |
| `FILE_LOADS` | Stages files in Cloud Storage, then runs load jobs. The default for bounded (batch) data |
| `STREAMING_INSERTS` | The legacy streaming API. The default for unbounded data, but not recommended for new projects |

Source: [Write from Dataflow to BigQuery](https://docs.cloud.google.com/dataflow/docs/guides/write-to-bigquery).

For streaming pipelines, use one of the two Storage Write API methods. For large batch pipelines, try `FILE_LOADS` first. Avoid `STREAMING_INSERTS`, because it costs more and is slower ([Write from Dataflow to BigQuery](https://docs.cloud.google.com/dataflow/docs/guides/write-to-bigquery)).

## DML for frequent small writes

BigQuery limits DML concurrency for each table. Each DML statement is an implicit transaction ([Transform data with DML](https://docs.cloud.google.com/bigquery/docs/data-manipulation-language)).

| Statement | Limit on one table |
|---|---|
| `INSERT` | The first 1,500 in 24 hours run at once. Then 10 run at a time, and up to 100 wait in a queue |
| `UPDATE`, `DELETE`, `MERGE` | 2 run at a time, and up to 20 wait in a queue. Statements past the queue limit fail |

Source: [Transform data with DML](https://docs.cloud.google.com/bigquery/docs/data-manipulation-language).

When the mutating queue is full, the error is "Too many DML statements outstanding against table ..., limit is 20". Two mutating statements conflict only when they change the same partition. An `INSERT` does not conflict with other DML ([Transform data with DML](https://docs.cloud.google.com/bigquery/docs/data-manipulation-language)). DML statements do not count toward the limit of 1,500 table modifications each day ([Quotas and limits](https://docs.cloud.google.com/bigquery/quotas)).

Apply these practices ([Transform data with DML](https://docs.cloud.google.com/bigquery/docs/data-manipulation-language)):

- Group many row changes into one statement. Do not send one statement for each row.
- For frequent inserts, stream with the Storage Write API (gRPC).
- If updates often filter on a narrow range of values, cluster the table on that column.
- If you need OLTP behavior, keep the data in Cloud SQL and query it from BigQuery with federated queries. For the database choice, see [Choosing a storage system](note:1.3-storage-choice).
- Fine-grained DML (Preview) rewrites less data for mutating statements.

## Partitioned and clustered tables

A partitioned table splits data into segments called partitions. A query that filters on the partition column scans only the matching partitions. This is called pruning. BigQuery can also estimate the query cost before the query runs ([Introduction to partitioned tables](https://docs.cloud.google.com/bigquery/docs/partitioned-tables)).

| Partition type | Partition column |
|---|---|
| Time-unit column | A `DATE`, `TIMESTAMP`, or `DATETIME` column. Daily partitioning is the default |
| Ingestion time | The time when BigQuery ingests the row, in the `_PARTITIONTIME` pseudocolumn |
| Integer range | An `INTEGER` column, with a start, an end, and an interval for the ranges |

Source: [Introduction to partitioned tables](https://docs.cloud.google.com/bigquery/docs/partitioned-tables).

Partition when you need a cost estimate before a query runs, partition expiration, or loads and deletes for one partition. Cluster instead when ([Introduction to partitioned tables](https://docs.cloud.google.com/bigquery/docs/partitioned-tables)):

- Queries filter or aggregate on several columns, or on columns with many distinct values.
- Each partition would hold less than about 10 GB, or the table would have more partitions than the limits allow.
- DML statements often change most partitions, for example every few minutes.

You can use partitioning and clustering together ([Introduction to partitioned tables](https://docs.cloud.google.com/bigquery/docs/partitioned-tables)).

## Use the data for AI and ML

BigQuery ML creates and runs models with GoogleSQL. The models are stored in datasets, like tables. The data does not move out of the warehouse ([Introduction to ML in BigQuery](https://docs.cloud.google.com/bigquery/docs/bqml-introduction)). `CREATE MODEL` runs as a query and trains the model. `ML.PREDICT` then scores new rows ([The CREATE MODEL statement](https://docs.cloud.google.com/bigquery/docs/reference/standard-sql/bigqueryml-syntax-create), [The ML.PREDICT function](https://docs.cloud.google.com/bigquery/docs/reference/standard-sql/bigqueryml-syntax-predict)).

```sql
CREATE OR REPLACE MODEL `myproject.mydataset.mymodel`
  OPTIONS(model_type='linear_reg', input_label_cols=['label_col'])
AS SELECT * FROM t;

SELECT * FROM ML.PREDICT(MODEL `myproject.mydataset.mymodel`,
  (SELECT f1, f2, f3 FROM table));
```

Source: [The CREATE MODEL statement](https://docs.cloud.google.com/bigquery/docs/reference/standard-sql/bigqueryml-syntax-create).

Built-in model types include linear and logistic regression, k-means clustering, and `ARIMA_PLUS` for time series. The `AI.FORECAST` function with the TimesFM model is Preview ([Introduction to ML in BigQuery](https://docs.cloud.google.com/bigquery/docs/bqml-introduction)).

AI functions call Gemini models in Gemini Enterprise Agent Platform, or Agent Platform (formerly Vertex AI). All inference runs in Agent Platform, and the results are stored in BigQuery ([Generative AI overview](https://docs.cloud.google.com/bigquery/docs/generative-ai-overview)).

```sql
SELECT
  title,
  AI.GENERATE(CONCAT("Summarize in one sentence: ", body)).result AS article_summary
FROM `bigquery-public-data.bbc_news.fulltext`
LIMIT 3;
```

Source: [The AI.GENERATE function](https://docs.cloud.google.com/bigquery/docs/reference/standard-sql/bigqueryml-syntax-ai-generate).

| Function | Use |
|---|---|
| `AI.GENERATE` | Analyze text, image, audio, video, or PDF data with a prompt. Add `output_schema` for structured output |
| `AI.GENERATE_TABLE` | A table-valued function that returns rows with your schema |
| `AI.IF`, `AI.SCORE`, `AI.CLASSIFY` | Filter, rank, or classify rows with a natural language prompt |
| `AI.EMBED`, `AI.GENERATE_EMBEDDING` | Create embeddings for vector search and retrieval-augmented generation (RAG) |

Sources: [Generative AI overview](https://docs.cloud.google.com/bigquery/docs/generative-ai-overview), [The AI.GENERATE function](https://docs.cloud.google.com/bigquery/docs/reference/standard-sql/bigqueryml-syntax-ai-generate), [The ML.GENERATE_EMBEDDING function](https://docs.cloud.google.com/bigquery/docs/reference/standard-sql/bigqueryml-syntax-generate-embedding).

For new queries, use `AI.GENERATE_EMBEDDING` instead of `ML.GENERATE_EMBEDDING` ([The ML.GENERATE_EMBEDDING function](https://docs.cloud.google.com/bigquery/docs/reference/standard-sql/bigqueryml-syntax-generate-embedding)). Optimized mode for `AI.IF` and `AI.CLASSIFY` is Preview ([Generative AI overview](https://docs.cloud.google.com/bigquery/docs/generative-ai-overview)). To call Gemini from application code, see [Generative AI APIs](note:4.2-generative-ai-apis).

## Exam traps

- **`tabledata.insertAll` or `STREAMING_INSERTS` for a new streaming app.** Use the Storage Write API (gRPC). It costs less and supports exactly-once delivery ([Use the Storage Write API (REST)](https://docs.cloud.google.com/bigquery/docs/write-api-rest), [Write from Dataflow to BigQuery](https://docs.cloud.google.com/dataflow/docs/guides/write-to-bigquery)).
- **`insertId` to guarantee no duplicates.** It is best effort for about one minute. For exactly-once, use committed type with offsets ([Use the Storage Write API (REST)](https://docs.cloud.google.com/bigquery/docs/write-api-rest), [Stream data using the Storage Write API (gRPC)](https://docs.cloud.google.com/bigquery/docs/write-api-streaming)).
- **The default stream for an exactly-once requirement.** The default stream is at-least-once ([Introduction to the Storage Write API (gRPC)](https://docs.cloud.google.com/bigquery/docs/write-api-grpc)).
- **A BigQuery subscription for exactly-once delivery.** It is at-least-once only. The Dataflow Pub/Sub to BigQuery template enforces exactly-once ([BigQuery subscriptions](https://docs.cloud.google.com/pubsub/docs/bigquery)).
- **Dataflow when messages need no processing.** A BigQuery subscription removes the Dataflow overhead ([BigQuery subscriptions](https://docs.cloud.google.com/pubsub/docs/bigquery)).
- **One DML `INSERT` for each event.** DML concurrency limits apply after 1,500 statements. Stream with the Storage Write API ([Transform data with DML](https://docs.cloud.google.com/bigquery/docs/data-manipulation-language)).
- **One load job for each small file or event.** A table allows 1,500 load jobs each day, failed jobs included ([Quotas and limits](https://docs.cloud.google.com/bigquery/quotas)).
- **`UPDATE` on rows that the REST API streamed a few minutes ago.** DML cannot change them for 30 minutes. Rows from the gRPC API can change ([Transform data with DML](https://docs.cloud.google.com/bigquery/docs/data-manipulation-language)).
- **`WRITE_TRUNCATE` to replace data and keep the table setup.** It also deletes the schema and row-level security, and removes the Cloud KMS key ([Load Parquet data from Cloud Storage](https://docs.cloud.google.com/bigquery/docs/loading-data-cloud-storage-parquet)).
- **Export data to train a simple model elsewhere.** BigQuery ML trains it with SQL where the data is ([Introduction to ML in BigQuery](https://docs.cloud.google.com/bigquery/docs/bqml-introduction)).
