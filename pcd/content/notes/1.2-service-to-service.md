## Why it matters

A microservice app makes many calls between services and to datastores. The developer decides who can call each service, which network path each call uses, and whether the traffic is authenticated and encrypted. The exam tests Cloud Run service-to-service authentication with ID tokens, and Cloud Run ingress with Direct VPC egress. It also tests the private connectivity options, Kubernetes network policies, and Cloud Service Mesh.

## Key points

- For synchronous calls between Cloud Run services, Google recommends a user-managed service account for each service. Each request carries a Google-signed OIDC ID token ([Authenticating service-to-service](https://docs.cloud.google.com/run/docs/authenticating/service-to-service)).
- Grant the calling service account the Cloud Run Invoker role (`roles/run.invoker`) on the receiving service ([Authenticating service-to-service](https://docs.cloud.google.com/run/docs/authenticating/service-to-service)).
- The `aud` claim of the ID token is the URL of the receiving service or a custom audience. The audience limits the risk that someone replays a token for one service against another service ([Set custom audiences for services](https://docs.cloud.google.com/run/docs/configuring/custom-audiences)).
- Ingress settings control the network paths that can reach a Cloud Run service. IAM authentication still applies on every path. Google recommends both ([Restrict network endpoint ingress](https://docs.cloud.google.com/run/docs/securing/ingress)).
- A call from one Cloud Run service to another service with `internal` ingress counts as internal only if it goes through a VPC network ([Private networking and Cloud Run](https://docs.cloud.google.com/run/docs/securing/private-networking)).
- Direct VPC egress (recommended) and Serverless VPC Access connectors send Cloud Run traffic to internal IP addresses, for example to Memorystore instances. They are for outbound traffic only ([Compare Direct VPC egress and VPC connectors](https://docs.cloud.google.com/run/docs/configuring/connecting-vpc)).
- Private Google Access and Private Service Connect give private access to Google APIs. Private Service Connect and private services access give private access to services in other VPC networks ([Private access options for services](https://docs.cloud.google.com/vpc/docs/private-access-options)).
- By default, all Pods in a GKE cluster can communicate freely. Kubernetes network policies create Pod-level firewall rules ([Control communication between Pods and Services using network policies](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/network-policy)).
- Cloud Service Mesh (formerly Anthos Service Mesh and Traffic Director) uses mutual TLS (mTLS) to authenticate and encrypt traffic between services. Authorization policies control access ([Cloud Service Mesh security overview](https://docs.cloud.google.com/service-mesh/docs/security/security-overview), [Authorization policy overview](https://docs.cloud.google.com/service-mesh/docs/security/authorization-policy-overview)).
- VPC Service Controls creates perimeters around Google Cloud services to reduce data exfiltration. It is independent of IAM, and Google recommends both ([Overview of VPC Service Controls](https://docs.cloud.google.com/vpc-service-controls/docs/overview)).

## Layers of protection

| Layer | Control | What it decides |
|---|---|---|
| Identity | Cloud Run Invoker role and ID tokens | Which principals can call a Cloud Run service |
| Network entry | Cloud Run ingress settings | Which network paths can reach the service |
| Network path | Direct VPC egress, Private Google Access, Private Service Connect, private services access | Whether traffic uses internal IP addresses and the VPC network |
| Pods on GKE | Kubernetes network policies | Which Pods can open connections to which Pods |
| Service mesh | Cloud Service Mesh mTLS and authorization policies | Encryption, workload identity, and access rules for requests |
| Perimeter | VPC Service Controls | Whether data can leave a perimeter through Google Cloud APIs |

Sources: [Authenticating service-to-service](https://docs.cloud.google.com/run/docs/authenticating/service-to-service), [Restrict network endpoint ingress](https://docs.cloud.google.com/run/docs/securing/ingress), [Private access options for services](https://docs.cloud.google.com/vpc/docs/private-access-options), [Configure network policies for applications](https://docs.cloud.google.com/kubernetes-engine/docs/tutorials/network-policy), [Authorization policy overview](https://docs.cloud.google.com/service-mesh/docs/security/authorization-policy-overview), [Overview of VPC Service Controls](https://docs.cloud.google.com/vpc-service-controls/docs/overview).

## Cloud Run service-to-service authentication

For asynchronous calls, Cloud Tasks, Pub/Sub, Cloud Scheduler, and Eventarc call the receiving service for you, based on their configuration. For synchronous HTTP calls, your code calls the service URL directly ([Authenticating service-to-service](https://docs.cloud.google.com/run/docs/authenticating/service-to-service)). For the asynchronous case, see [Triggering Cloud Run with Eventarc and Pub/Sub](note:3.1-triggers-and-receivers).

1. Give each service its own user-managed service account with the minimum roles. See [Service accounts, IAM roles, and least privilege](note:1.2-service-accounts-least-privilege).
2. Keep the receiving service private. Cloud Run services require authentication by default ([Authentication overview](https://docs.cloud.google.com/run/docs/authenticating/overview)).
3. Grant the calling service account `roles/run.invoker` on the receiving service. This role has `run.instances.invoke`, `run.jobs.run`, and `run.routes.invoke`. For services only, the Cloud Run Service Invoker role (`roles/run.servicesInvoker`) is narrower, with only `run.routes.invoke` ([Cloud Run IAM roles](https://docs.cloud.google.com/run/docs/reference/iam/roles)).
4. In the calling service, get a Google-signed ID token for the audience, and send it in the `Authorization: Bearer ID_TOKEN` header.

```bash
gcloud run services add-iam-policy-binding RECEIVING_SERVICE \
  --member='serviceAccount:CALLING_SERVICE_IDENTITY' \
  --role='roles/run.invoker'
```

Source: [Authenticating service-to-service](https://docs.cloud.google.com/run/docs/authenticating/service-to-service).

```python
import urllib

import google.auth.transport.requests
import google.oauth2.id_token


def make_authorized_get_request(endpoint, audience):
    # audience = 'https://my-cloud-run-service.run.app/'
    # endpoint = 'https://my-cloud-run-service.run.app/my/awesome/url'
    req = urllib.request.Request(endpoint)
    auth_req = google.auth.transport.requests.Request()
    id_token = google.oauth2.id_token.fetch_id_token(auth_req, audience)
    req.add_header("Authorization", f"Bearer {id_token}")
    response = urllib.request.urlopen(req)
    return response.read()
```

Source: [Authenticating service-to-service](https://docs.cloud.google.com/run/docs/authenticating/service-to-service).

Rules for the token ([Authenticating service-to-service](https://docs.cloud.google.com/run/docs/authenticating/service-to-service)):

- Use the URL of the receiving service as the audience, also when you call a traffic tag URL. Custom domains are not supported as the audience. For a custom domain or a load balancer, configure a custom audience on the service ([Set custom audiences for services](https://docs.cloud.google.com/run/docs/configuring/custom-audiences)).
- If the client library is not available, get the token from the metadata server: `http://metadata.google.internal/computeMetadata/v1/instance/service-accounts/default/identity?audience=AUDIENCE`, with the header `Metadata-Flavor: Google`. This works only on Google Cloud.
- ID tokens expire after about one hour. The metadata server always returns a valid token. If you cache tokens, check the `exp` claim.
- If the app already uses the `Authorization` header, send the token in `X-Serverless-Authorization`. When both headers are present, Cloud Run checks only `X-Serverless-Authorization`.
- From outside Google Cloud, use Workload Identity Federation and the `generateIdToken` method. A downloaded service account key is the last choice.

Service-to-service traffic between two services in the same region has no networking charges ([Authenticating service-to-service](https://docs.cloud.google.com/run/docs/authenticating/service-to-service)). For token types in general, see [Authenticating to Google Cloud](note:1.2-authenticating-to-google-cloud). Cloud Service Mesh for Cloud Run (Preview) can add the authentication for you ([Configure Cloud Service Mesh for Cloud Run](https://docs.cloud.google.com/service-mesh/docs/configure-cloud-service-mesh-for-cloud-run)).

## Cloud Run ingress and internal traffic

| Ingress setting | Allowed sources | Use it when |
|---|---|---|
| `all` | All requests, including from the internet to the `run.app` URL | A public API or website |
| `internal-and-cloud-load-balancing` | Internal sources and external Application Load Balancers | Internet traffic must pass through the load balancer, for example for Google Cloud Armor or IAP |
| `internal` | Internal Application Load Balancers, VPC networks in the same project, allowed Shared VPC networks, the VPC Service Controls perimeter, and some Google Cloud services | Only private callers |

Source: [Restrict network endpoint ingress](https://docs.cloud.google.com/run/docs/securing/ingress).

Some Google Cloud services count as internal, for example Cloud Scheduler, Cloud Tasks, Eventarc, Pub/Sub subscriptions, and Workflows. They must be in the same project or VPC Service Controls perimeter and use the `run.app` URL ([Restrict network endpoint ingress](https://docs.cloud.google.com/run/docs/securing/ingress)).

**Calls from another Cloud Run service.** Requests from Cloud Run or App Engine to a service with `internal` ingress must go through a VPC network. Configure the calling service with Direct VPC egress or a connector, and then use one of these paths ([Private networking and Cloud Run](https://docs.cloud.google.com/run/docs/securing/private-networking)):

- Route all traffic through the VPC network, and enable Private Google Access on the subnet.
- Put Private Service Connect or an internal Application Load Balancer in front of the receiving service.
- Enable Private Google Access, and resolve `run.app` to `private.googleapis.com` or `restricted.googleapis.com` in DNS.

```bash
gcloud run deploy RECEIVING_SERVICE --image IMAGE_URL --ingress internal

gcloud run deploy CALLING_SERVICE --image IMAGE_URL \
  --network=NETWORK --subnet=SUBNET --vpc-egress=all-traffic

gcloud compute networks subnets update SUBNET \
  --region=REGION --enable-private-ip-google-access
```

Sources: [Restrict network endpoint ingress](https://docs.cloud.google.com/run/docs/securing/ingress), [Direct VPC with a VPC network](https://docs.cloud.google.com/run/docs/configuring/vpc-direct-vpc), [Configure Private Google Access](https://docs.cloud.google.com/vpc/docs/configure-private-google-access).

With `--vpc-egress=private-ranges-only`, only traffic to internal addresses uses the VPC network ([Direct VPC with a VPC network](https://docs.cloud.google.com/run/docs/configuring/vpc-direct-vpc)). The organization policy constraints `run.allowedIngress` and `run.allowedVPCEgress` can enforce these settings ([Private networking and Cloud Run](https://docs.cloud.google.com/run/docs/securing/private-networking)). See [Data retention and organization policies](note:1.2-retention-and-org-policy).

## Direct VPC egress

| | Direct VPC egress (recommended) | Serverless VPC Access connector |
|---|---|---|
| Cost | Network egress only | Also connector VM charges |
| Latency and throughput | Lower latency, higher throughput | Higher latency, lower throughput |
| IP addresses | Uses more in most cases | Uses fewer |
| Network tags | For each service revision or job | Shared by all services that use the connector |
| Scaling | New instances start slower, because Cloud Run creates network interfaces | Latency during traffic surges, while connector instances start |

Source: [Compare Direct VPC egress and VPC connectors](https://docs.cloud.google.com/run/docs/configuring/connecting-vpc).

Facts about Direct VPC egress ([Direct VPC with a VPC network](https://docs.cloud.google.com/run/docs/configuring/vpc-direct-vpc)):

- Cloud Run services and jobs do not support Direct VPC ingress. Requests from the VPC network to Cloud Run use other paths ([Private networking and Cloud Run](https://docs.cloud.google.com/run/docs/securing/private-networking)).
- Instances get IP addresses from your subnet. The subnet must be `/26` or larger. At steady state, a service uses twice as many IP addresses as instances.
- The IP addresses change, so do not write rules for single addresses. Ingress firewall rules refer to the service by the subnet range. Egress firewall rules can also use network tags or the service account.
- Connections can take a minute or more to work at instance startup. Use a startup probe that tests an egress destination.

**Memorystore over Direct VPC egress.** Memorystore for Redis connects to your network through VPC peering: direct peering or private services access ([Networking (Redis)](https://docs.cloud.google.com/memorystore/docs/redis/networking)). Memorystore for Valkey connects only through Private Service Connect, set up by a service connection policy ([Networking (Valkey)](https://docs.cloud.google.com/memorystore/docs/valkey/networking)). The network path is not the whole protection:

- Redis AUTH helps stop unintended access by known clients. It does not encrypt traffic, and it does not stop malicious entities that have access to your VPC network ([About Redis AUTH](https://docs.cloud.google.com/memorystore/docs/redis/about-redis-auth)).
- In-transit encryption makes clients use TLS 1.2 or higher. Clients without TLS are blocked ([About in-transit encryption](https://docs.cloud.google.com/memorystore/docs/redis/about-in-transit-encryption)).
- Memorystore for Valkey supports IAM authentication. The service account needs `roles/memorystore.dbConnectionUser`, and it sends an access token in the `AUTH` command ([About IAM authentication](https://docs.cloud.google.com/memorystore/docs/valkey/about-iam-auth)).

For the cache design, see [Caching with Memorystore and Cloud CDN](note:1.1-caching).

## Private Google Access, Private Service Connect, and private services access

The exam guide says private service connectivity. No product has this name. The docs list four private access options: Private Service Connect, Private Google Access, private services access, and VPC Network Peering ([Private access options for services](https://docs.cloud.google.com/vpc/docs/private-access-options)).

| Need | Option | Notes |
|---|---|---|
| VMs without external IP addresses call Google APIs or `run.app` URLs | Private Google Access | You enable it for each subnet. No effect on VMs with external IP addresses. Does not support `rep.googleapis.com` regional endpoints |
| Call Google APIs or Cloud Run at an internal IP address that you choose | Private Service Connect endpoint for Google APIs | Add a private DNS zone for `run.app` |
| Consume a service that another VPC network, team, or company publishes | Private Service Connect endpoint or backend | Uses NAT, so the two networks need no IP address coordination |
| Reach Cloud SQL, AlloyDB, Memorystore for Redis, or Filestore by internal IP address | Private services access | VPC Network Peering with an allocated range. The ranges must not overlap |

Sources: [Private access options for services](https://docs.cloud.google.com/vpc/docs/private-access-options), [Private Google Access](https://docs.cloud.google.com/vpc/docs/private-google-access), [Private Service Connect](https://docs.cloud.google.com/vpc/docs/private-service-connect), [Private services access](https://docs.cloud.google.com/vpc/docs/private-services-access), [Private networking and Cloud Run](https://docs.cloud.google.com/run/docs/securing/private-networking).

To publish a Cloud Run service to other projects as a managed service, put it behind an internal Application Load Balancer and publish it with Private Service Connect ([Private networking and Cloud Run](https://docs.cloud.google.com/run/docs/securing/private-networking)).

## Kubernetes network policies on GKE

A network policy selects Pods by label and lists the Pods that can connect to them (ingress) or that they can connect to (egress). Network policies only allow or block connections. They do not give authorization or TLS ([Configure network policies for applications](https://docs.cloud.google.com/kubernetes-engine/docs/tutorials/network-policy)).

```yaml
kind: NetworkPolicy
apiVersion: networking.k8s.io/v1
metadata:
  name: hello-allow-from-foo
spec:
  policyTypes:
  - Ingress
  podSelector:
    matchLabels:
      app: hello
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: foo
```

Source: [Configure network policies for applications](https://docs.cloud.google.com/kubernetes-engine/docs/tutorials/network-policy).

- A Pod that no policy selects accepts all connections. When a policy selects a Pod for ingress, the Pod accepts only connections from its node and connections that a policy allows. Policies add together, and their order does not matter. A policy with an empty `podSelector`, the `Ingress` policy type, and no rules isolates all Pods in its namespace for ingress ([Network Policies](https://kubernetes.io/docs/concepts/services-networking/network-policies/)).
- GKE Dataplane V2 is the recommended network plugin. It is based on Cilium and eBPF, and it is the default for new Autopilot clusters. Network policy enforcement and network policy logging are built in. You cannot enable or disable the enforcement. You can enable Dataplane V2 only when you create a cluster ([GKE Dataplane V2](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/dataplane-v2), [Using GKE Dataplane V2](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/dataplane-v2), [Control communication between Pods and Services using network policies](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/network-policy)).
- In a Standard cluster without Dataplane V2, use the Calico plugin. On an existing cluster, run two commands in sequence. First, `gcloud container clusters update CLUSTER_NAME --update-addons=NetworkPolicy=ENABLED` enables the add-on. Then, `gcloud container clusters update CLUSTER_NAME --enable-network-policy` enables enforcement and re-creates the node pools. The add-on alone does not enforce policies. Without a network plugin, GKE ignores network policies ([Control communication between Pods and Services using network policies](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/network-policy)).
- With Workload Identity Federation for GKE (formerly GKE Workload Identity), allow egress to the GKE metadata server ([Control communication between Pods and Services using network policies](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/network-policy), [Make IAM for GKE easier to use with Workload Identity Federation](https://cloud.google.com/blog/products/identity-security/make-iam-for-gke-easier-to-use-with-workload-identity-federation)).
- Select Pods with labels, not with `ipBlock`, because Pod IP addresses change. In Dataplane V2, an `ipBlock` rule never matches Pod traffic ([Control communication between Pods and Services using network policies](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/network-policy)).

## Cloud Service Mesh: mTLS, authorization, and service identity

On GKE, Cloud Service Mesh runs a sidecar proxy next to each workload and uses the open source Istio APIs. With the sidecar, you do not change the application code. On Compute Engine, you can also use proxyless gRPC ([Cloud Service Mesh overview](https://docs.cloud.google.com/service-mesh/docs/overview)).

**Service identity.** The Cloud Service Mesh certificate authority issues mTLS certificates that contain the project ID, the namespace, and the Kubernetes service account name. The mesh rotates the keys and certificates automatically ([Cloud Service Mesh security overview](https://docs.cloud.google.com/service-mesh/docs/security/security-overview)). In policies, a workload identity has the form `PROJECT_ID.svc.id.goog/ns/NAMESPACE/sa/SERVICE_ACCOUNT_NAME` ([Authorization policy overview](https://docs.cloud.google.com/service-mesh/docs/security/authorization-policy-overview)).

**mTLS.** Auto mTLS is on by default, but services accept both plaintext and mTLS traffic. The default mode is `PERMISSIVE`. A `PeerAuthentication` policy with mode `STRICT` makes services accept only mTLS. Apply it to the whole mesh in the `istio-system` namespace, to a namespace, or to a workload ([Configure transport security](https://docs.cloud.google.com/service-mesh/docs/security/configuring-mtls)).

**Authorization policies.** Without policies, all requests are allowed. `DENY` policies are evaluated before `ALLOW` policies. Google recommends that you start with an allow-nothing policy and add `ALLOW` policies. Rules on `principals` and `namespaces` need `STRICT` mTLS ([Authorization policy overview](https://docs.cloud.google.com/service-mesh/docs/security/authorization-policy-overview)).

```yaml
apiVersion: "security.istio.io/v1beta1"
kind: "PeerAuthentication"
metadata:
  name: "AUTH_POLICY_NAME"
  namespace: "NAMESPACE"
spec:
  mtls:
    mode: STRICT
---
apiVersion: "security.istio.io/v1beta1"
kind: "AuthorizationPolicy"
metadata:
  name: "currencyservice"
  namespace: demo
spec:
  selector:
    matchLabels:
      app: currencyservice
  action: ALLOW
  rules:
  - from:
    - source:
        principals: ["example-project-1234.svc.id.goog/ns/demo/sa/frontend-sa"]
```

Sources: [Configure transport security](https://docs.cloud.google.com/service-mesh/docs/security/configuring-mtls), [Authorization policy overview](https://docs.cloud.google.com/service-mesh/docs/security/authorization-policy-overview).

| | Kubernetes network policy | Cloud Service Mesh |
|---|---|---|
| Controls | Which Pods can open connections | Which workload identities can send which requests |
| Encrypts traffic | No | Yes, with mTLS |
| Rules on HTTP methods, paths, and JWT claims | No | Yes |

Sources: [Configure network policies for applications](https://docs.cloud.google.com/kubernetes-engine/docs/tutorials/network-policy), [Network Policies](https://kubernetes.io/docs/concepts/services-networking/network-policies/), [Cloud Service Mesh security overview](https://docs.cloud.google.com/service-mesh/docs/security/security-overview), [Authorization policy overview](https://docs.cloud.google.com/service-mesh/docs/security/authorization-policy-overview).

Use the managed Cloud Service Mesh. The in-cluster control plane on GKE was deprecated on September 28, 2026, and support ends on March 1, 2028 ([Cloud Service Mesh overview](https://docs.cloud.google.com/service-mesh/docs/overview), [Deprecations](https://docs.cloud.google.com/service-mesh/deprecations)).

## VPC Service Controls

VPC Service Controls puts a perimeter around Google Cloud services, such as Cloud Storage and BigQuery, to reduce the risk of data exfiltration. It adds a layer of defense to IAM and does not replace it ([Overview of VPC Service Controls](https://docs.cloud.google.com/vpc-service-controls/docs/overview)).

## Exam traps

- **`allUsers` or a project-level Invoker grant so that one service can call another.** Grant `roles/run.invoker` to the caller's service account on the receiving service ([Authenticating service-to-service](https://docs.cloud.google.com/run/docs/authenticating/service-to-service)).
- **An ID token with a custom domain or a tag URL as the audience.** Use the service URL, or configure a custom audience ([Authenticating service-to-service](https://docs.cloud.google.com/run/docs/authenticating/service-to-service)).
- **`internal` ingress, and a caller on Cloud Run without VPC egress.** The request does not go through a VPC network, so it is not internal ([Private networking and Cloud Run](https://docs.cloud.google.com/run/docs/securing/private-networking)).
- **Direct VPC egress so that VMs can call a Cloud Run service.** It is outbound only. Use Private Google Access, Private Service Connect, or an internal Application Load Balancer ([Private networking and Cloud Run](https://docs.cloud.google.com/run/docs/securing/private-networking)).
- **Firewall rules on individual Cloud Run IP addresses.** The addresses change. Use the subnet range, or network tags in egress rules ([Direct VPC with a VPC network](https://docs.cloud.google.com/run/docs/configuring/vpc-direct-vpc)).
- **Private services access to reach Google APIs.** It is for VPC-hosted services such as Cloud SQL. Use Private Google Access or Private Service Connect ([Private access options for services](https://docs.cloud.google.com/vpc/docs/private-access-options)).
- **Network policies in a Standard cluster without a network plugin.** GKE ignores them ([Configure network policies for applications](https://docs.cloud.google.com/kubernetes-engine/docs/tutorials/network-policy)).
- **Network policies to encrypt traffic or to authorize by service identity.** Use Cloud Service Mesh ([Network Policies](https://kubernetes.io/docs/concepts/services-networking/network-policies/), [Cloud Service Mesh security overview](https://docs.cloud.google.com/service-mesh/docs/security/security-overview)).
- **A mesh without a `STRICT` policy.** Services still accept plaintext ([Configure transport security](https://docs.cloud.google.com/service-mesh/docs/security/configuring-mtls)).
- **Redis AUTH as protection against attackers in the VPC network.** AUTH does not protect against them, and it does not encrypt. Limit network access and enable in-transit encryption ([About Redis AUTH](https://docs.cloud.google.com/memorystore/docs/redis/about-redis-auth)).
- **VPC Service Controls instead of IAM.** Use both ([Overview of VPC Service Controls](https://docs.cloud.google.com/vpc-service-controls/docs/overview)).
