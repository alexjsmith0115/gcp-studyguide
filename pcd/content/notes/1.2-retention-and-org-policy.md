## Why it matters

A developer decides how long objects stay in Cloud Storage, how deleted data comes back, and which rules nobody can undo later. Cloud Storage has a different feature for each of these jobs, and some of them are permanent. Organization policies add guardrails that block a configuration even when IAM allows the principal to act. The exam tests which feature meets a stated retention requirement, which actions you cannot reverse, and how a constraint changes what your code and deployments can do.

## Key points

- A lifecycle rule has exactly one action (`Delete`, `SetStorageClass`, or `AbortIncompleteMultipartUpload`) and one or more conditions. An object must match all conditions of the rule ([Object Lifecycle Management](https://docs.cloud.google.com/storage/docs/lifecycle)).
- Lifecycle actions run asynchronously, and a configuration change can take up to 24 hours to take effect ([Object Lifecycle Management](https://docs.cloud.google.com/storage/docs/lifecycle)).
- Soft delete is on by default with a 7-day retention duration. You can set 7 to 90 days, or 0 to disable it ([Soft delete overview](https://docs.cloud.google.com/storage/docs/soft-delete)).
- Google recommends soft delete instead of Object Versioning to protect against accidental or malicious deletion. Object Versioning does not protect against bucket deletion ([Object Versioning](https://docs.cloud.google.com/storage/docs/object-versioning)).
- A bucket retention policy blocks the deletion or replacement of every object, existing and new, until the object is older than the retention period ([Bucket Lock](https://docs.cloud.google.com/storage/docs/bucket-lock)).
- Locking a retention policy is irreversible. You can increase the period, but you cannot reduce or remove it ([Bucket Lock](https://docs.cloud.google.com/storage/docs/bucket-lock)).
- Object Retention Lock sets a retain-until time on each object. Bucket Lock sets one period for all objects in the bucket ([Object Retention Lock](https://docs.cloud.google.com/storage/docs/object-lock)).
- When you release an event-based hold, the retention period starts again for that object. Releasing a temporary hold does not restart the retention period ([Object holds](https://docs.cloud.google.com/storage/docs/object-holds)).
- IAM controls who can act on a resource. An organization policy controls what configurations are allowed. Descendant resources inherit the policy ([Organization Policy overview](https://docs.cloud.google.com/organization-policy/overview)).
- Most new organization policies are not retroactive. Existing resources that break the policy keep working until you fix them ([Organization Policy overview](https://docs.cloud.google.com/organization-policy/overview)).
- Dry-run mode writes audit logs for violations but does not deny the request ([Test organization policies](https://docs.cloud.google.com/organization-policy/test-policies)).

## Choosing a Cloud Storage protection feature

Each feature answers a different requirement. Match the words in the requirement to the row.

| Requirement | Feature | What to remember |
|---|---|---|
| Delete objects, or move them to a colder class, by age, name, or version count | Object Lifecycle Management | Asynchronous. The rule waits for holds and retention periods |
| Recover from an accidental or malicious delete or overwrite, including a bucket delete | Soft delete | On by default. Soft-deleted objects are not readable until you restore them |
| Keep earlier versions readable in the bucket | Object Versioning, plus a lifecycle rule that limits versions | Each noncurrent version costs the same as a live object |
| Keep all objects for a minimum period, for example for a regulation | Bucket retention policy, then lock it | Applies to existing objects too. The lock is permanent |
| Keep each object until its own date | Object Retention Lock | Enable it on the bucket first. You cannot disable it |
| Keep an object until an event occurs, then for a fixed period | Default event-based hold and a retention policy | Releasing the hold starts the retention period |
| Keep some objects during a legal investigation | Temporary hold | Releasing the hold does not restart the retention period |

Sources: [Data protection, backup, and recovery options](https://docs.cloud.google.com/storage/docs/protection-backup-recovery-overview), [Object Lifecycle Management](https://docs.cloud.google.com/storage/docs/lifecycle), [Soft delete overview](https://docs.cloud.google.com/storage/docs/soft-delete), [Object Versioning](https://docs.cloud.google.com/storage/docs/object-versioning), [Bucket Lock](https://docs.cloud.google.com/storage/docs/bucket-lock), [Object Retention Lock](https://docs.cloud.google.com/storage/docs/object-lock), [Object holds](https://docs.cloud.google.com/storage/docs/object-holds).

## Object Lifecycle Management

A lifecycle configuration is a set of rules on a bucket. The rules apply to current and future objects ([Object Lifecycle Management](https://docs.cloud.google.com/storage/docs/lifecycle)).

**Actions.** A rule has one action ([Object Lifecycle Management](https://docs.cloud.google.com/storage/docs/lifecycle)):

- `Delete` deletes the object. With soft delete on, the object becomes soft-deleted. With Object Versioning on, a deleted live object becomes noncurrent, and a deleted noncurrent version leaves the bucket.
- `SetStorageClass` moves the object to a colder class, for example Standard to Nearline, Coldline, or Archive. You cannot use it on a bucket with Autoclass.
- `AbortIncompleteMultipartUpload` deletes the parts of an unfinished XML API multipart upload. It accepts only the `age`, `matchesPrefix`, and `matchesSuffix` conditions.

**Conditions.** The conditions are `age`, `createdBefore`, `customTimeBefore`, `daysSinceCustomTime`, `daysSinceNoncurrentTime`, `isLive`, `matchesStorageClass`, `matchesPrefix`, `matchesSuffix`, `noncurrentTimeBefore`, `numNewerVersions`, `sizeAboveBytes`, and `sizeBelowBytes` ([Object Lifecycle Management](https://docs.cloud.google.com/storage/docs/lifecycle)). The `age` condition counts from the object creation time. The `daysSinceCustomTime` condition counts from the `Custom-Time` metadata that your code sets, so it fits a business date that differs from the upload date.

**Precedence.** If several rules match one object at the same time, `Delete` wins over `SetStorageClass`. Among `SetStorageClass` rules, the class with the lowest storage price wins ([Object Lifecycle Management](https://docs.cloud.google.com/storage/docs/lifecycle)).

This configuration keeps a recovery window in a versioned bucket. It deletes a noncurrent version when 2 newer versions exist, or after it is noncurrent for 7 days:

```json
{
  "lifecycle": {
    "rule": [
      {
        "action": {"type": "Delete"},
        "condition": {"numNewerVersions": 2, "isLive": false}
      },
      {
        "action": {"type": "Delete"},
        "condition": {"daysSinceNoncurrentTime": 7}
      }
    ]
  }
}
```

```bash
gcloud storage buckets update gs://BUCKET_NAME --lifecycle-file=LIFECYCLE_CONFIG_FILE
```

Sources: [Configuration examples for Object Lifecycle Management](https://docs.cloud.google.com/storage/docs/lifecycle-configurations), [Manage object lifecycles](https://docs.cloud.google.com/storage/docs/managing-lifecycles).

Behavior that the exam tests:

- **No exact timing.** Cloud Storage inspects objects regularly and acts asynchronously. Do not build application logic that expects deletion at an exact time ([Object Lifecycle Management](https://docs.cloud.google.com/storage/docs/lifecycle)).
- **Holds and retention win.** `Delete` does not act on an object that has a hold or an unmet retention policy. It acts after the hold is released and the retention period is met ([Object Lifecycle Management](https://docs.cloud.google.com/storage/docs/lifecycle)).
- **Class changes cost operations.** `SetStorageClass` counts as a Class A operation. For small objects, this cost can be larger than the storage saving, so add `sizeAboveBytes` ([Object Lifecycle Management](https://docs.cloud.google.com/storage/docs/lifecycle)).
- **No rewrite.** `SetStorageClass` does not rewrite the object, so the class change itself has no early deletion fee or retrieval fee ([Object Lifecycle Management](https://docs.cloud.google.com/storage/docs/lifecycle)).
- **Test first.** Test rules on development data, or on a small set of production data with `matchesPrefix` or `matchesSuffix` ([Object Lifecycle Management](https://docs.cloud.google.com/storage/docs/lifecycle)).
- **Audit.** Usage logs show lifecycle actions with the user agent `GCS Lifecycle Management`. Pub/Sub notifications report the action but not who did it ([Object Lifecycle Management](https://docs.cloud.google.com/storage/docs/lifecycle)).

## Soft delete and Object Versioning

Both features keep deleted data, but they protect against different events.

| | Soft delete | Object Versioning |
|---|---|---|
| Default | On, 7 days | Off |
| Keeps | Deleted and overwritten objects, and deleted buckets | Earlier versions as noncurrent objects |
| Read the kept data | No. Restore it first | Yes, by generation number |
| Protects against bucket deletion | Yes | No |
| Removed by | The end of the retention duration (7 to 90 days) | You, or a lifecycle rule |
| Use it for | Protection against accidental or malicious deletion | Access to recent versions, with a lifecycle rule that keeps a set number of versions |

Sources: [Soft delete overview](https://docs.cloud.google.com/storage/docs/soft-delete), [Object Versioning](https://docs.cloud.google.com/storage/docs/object-versioning).

- **Combine them.** For readable versions and strong protection, enable both. A lifecycle rule deletes old noncurrent versions, and soft delete keeps them for one more period ([Object Versioning](https://docs.cloud.google.com/storage/docs/object-versioning)).
- **Restore permissions.** The permissions to restore soft-deleted objects are in the Storage Admin role (`roles/storage.admin`) ([Object Versioning](https://docs.cloud.google.com/storage/docs/object-versioning)).
- **Restore results.** A restored object is a new live object in the Standard storage class. If you restore a bucket with the gcloud CLI or the JSON API, you get an empty bucket. You restore its objects in a separate operation ([Soft delete overview](https://docs.cloud.google.com/storage/docs/soft-delete)).
- **Temporary data.** Soft delete can increase the cost of buckets that hold short-lived objects, such as staging files. Google recommends that you keep such objects in a bucket with soft delete disabled ([Soft delete overview](https://docs.cloud.google.com/storage/docs/soft-delete)).
- **Policy changes.** A change to the soft delete duration applies only to objects that you delete after the change ([Soft delete overview](https://docs.cloud.google.com/storage/docs/soft-delete)).

## Retention policies and Bucket Lock

A retention policy sets a minimum age for all objects in a bucket. A request to delete or replace a younger object fails with `403 - retentionPolicyNotMet`. The policy applies retroactively to objects that are already in the bucket. When you replace an object, the new object starts again at age 0 ([Bucket Lock](https://docs.cloud.google.com/storage/docs/bucket-lock)).

| | Unlocked retention policy | Locked retention policy |
|---|---|---|
| Increase the period | Yes | Yes |
| Reduce or remove the policy | Yes | No. The request fails with `400 BadRequestException` |
| Delete the bucket | Yes, when the objects allow it | Only after every object meets the retention period |
| Effect on the project | None | Cloud Storage adds a lien that blocks project deletion |
| Use it for | Retention that you might need to change or remove | Immutable records for regulations, for example FINRA, SEC, and CFTC rules |

Sources: [Bucket Lock](https://docs.cloud.google.com/storage/docs/bucket-lock), [Use and lock retention policies](https://docs.cloud.google.com/storage/docs/using-bucket-lock).

```bash
# Set or change the retention period (unlocked)
gcloud storage buckets update gs://BUCKET_NAME --retention-period=1d43200s

# Lock the policy. This step is irreversible.
gcloud storage buckets update gs://BUCKET_NAME --lock-retention-period
```

Source: [Use and lock retention policies](https://docs.cloud.google.com/storage/docs/using-bucket-lock).

Interactions with other features ([Bucket Lock](https://docs.cloud.google.com/storage/docs/bucket-lock)):

- A lifecycle rule can delete objects in a locked bucket, but only after each object meets the retention period. Use this to remove expired records automatically.
- In a versioned bucket, a live object that is still under retention can become noncurrent.
- Do not use parallel composite uploads, because the component objects cannot be deleted until they meet the retention period.
- You cannot destroy a Cloud KMS key version that encrypts objects in a locked bucket before those objects meet their retention time.
- An object's editable metadata is not under the retention policy.
- The maximum retention period is 100 years.

For compliance records, Google pairs Bucket Lock with Detailed audit logging mode, which logs request and response details ([Bucket Lock](https://docs.cloud.google.com/storage/docs/bucket-lock), [Organization policy constraints for Cloud Storage](https://docs.cloud.google.com/storage/docs/org-policy-constraints)).

## Object Retention Lock and object holds

**Object Retention Lock** gives each object a retain-until time and a mode ([Object Retention Lock](https://docs.cloud.google.com/storage/docs/object-lock)):

- `Unlocked` lets authorized users change or remove the configuration. The XML API calls this mode `GOVERNANCE`.
- `Locked` is permanent. You can only increase the retain-until time. The XML API calls this mode `COMPLIANCE`.

You must enable the feature on the bucket, and you cannot disable it later. For a new bucket, add `--enable-per-object-retention` when you create it. For an existing bucket, use the Google Cloud console ([Enable and use object retention configurations](https://docs.cloud.google.com/storage/docs/using-object-lock)). If an object has its own retention configuration and the bucket has a retention policy, Cloud Storage keeps the object until both are satisfied ([Object Retention Lock](https://docs.cloud.google.com/storage/docs/object-lock)).

**Object holds** are metadata flags. An object with a hold cannot be deleted or replaced ([Object holds](https://docs.cloud.google.com/storage/docs/object-holds)).

| | Event-based hold | Temporary hold |
|---|---|---|
| Effect of release in a bucket with a retention policy | The object's time in the bucket starts again | No change to the object's time in the bucket |
| Typical use | Keep a loan document for N years after the loan is paid | Keep trading records during a legal investigation |
| With an object retention configuration | Not allowed | Allowed |

Source: [Object holds](https://docs.cloud.google.com/storage/docs/object-holds).

The default event-based hold property of a bucket puts an event-based hold on each new object. With a retention policy on the bucket, the retention period starts when you release the hold ([Object holds](https://docs.cloud.google.com/storage/docs/object-holds)).

```bash
# Put a hold on each new object in the bucket
gcloud storage buckets update gs://BUCKET_NAME --default-event-based-hold

# Release the event-based hold when the event occurs
gcloud storage objects update gs://BUCKET_NAME/OBJECT_NAME --no-event-based-hold
```

Source: [Use object holds](https://docs.cloud.google.com/storage/docs/holding-objects).

The XML API cannot manage holds, and buckets with hierarchical namespace do not support holds ([Object holds](https://docs.cloud.google.com/storage/docs/object-holds)).

## Organization policies that affect developers

The Organization Policy Service sets constraints on an organization, folder, or project. Descendant resources inherit them. IAM decides who can act. An organization policy decides which configurations are allowed, for any principal ([Organization Policy overview](https://docs.cloud.google.com/organization-policy/overview)).

**Constraint types.** Managed constraints, such as `iam.managed.disableServiceAccountKeyCreation`, replace the equivalent legacy managed constraints (called predefined constraints in older docs). Google manages the managed constraints. Your organization manages its custom constraints ([Organization Policy overview](https://docs.cloud.google.com/organization-policy/overview), [Organization Policy Service release notes](https://docs.cloud.google.com/organization-policy/release-notes)).

| Constraint | Effect on your work |
|---|---|
| `storage.publicAccessPrevention` | Blocks access through `allUsers` and `allAuthenticatedUsers`, also on existing buckets. A request to add them fails with `412 Precondition Failed`. Signed URLs still work |
| `storage.uniformBucketLevelAccess` | New buckets must use uniform bucket-level access, so only IAM grants access. ACL requests fail with `400 Bad Request` |
| `storage.retentionPolicySeconds`, `storage.softDeletePolicySeconds` | A bucket create or update request must include one of the allowed durations |
| `gcp.resourceLocations` | You can create resources only in the allowed locations. Existing resources stay |
| `iam.managed.disableServiceAccountKeyCreation` | Blocks service account key creation. The legacy `iam.disableServiceAccountKeyCreation` also blocks Cloud Storage HMAC keys |
| `iam.allowedPolicyMemberDomains` | Limits IAM grants to principals from allowed organizations or Google Workspace customers |
| `run.allowedIngress` | Limits Cloud Run ingress to the allowed values: `all`, `internal`, `internal-and-cloud-load-balancing` |
| `run.allowedVPCEgress` | Requires Direct VPC egress or a connector, and an allowed egress setting |
| `run.managed.requireInvokerIam` | Keeps the IAM invoker check on for Cloud Run services |
| `gcp.restrictNonCmekServices` | New resources of the listed services must use a customer-managed encryption key (CMEK) |

Sources: [Organization policy constraints](https://docs.cloud.google.com/organization-policy/reference/org-policy-constraints), [Organization policy constraints for Cloud Storage](https://docs.cloud.google.com/storage/docs/org-policy-constraints), [Public access prevention](https://docs.cloud.google.com/storage/docs/public-access-prevention), [Uniform bucket-level access](https://docs.cloud.google.com/storage/docs/uniform-bucket-level-access), [Restrict resource locations](https://docs.cloud.google.com/organization-policy/restrict-locations).

**Security baseline.** Organizations created on or after May 3, 2024 get a set of enforced policies. The set includes disabled service account key creation and upload, no Editor role for default service accounts, domain restricted sharing, and uniform bucket-level access ([Manage Google Cloud security baseline constraints](https://docs.cloud.google.com/resource-manager/docs/manage-baseline-constraints)). So in a new organization, a request to create a service account key fails. Use an attached service account or Workload Identity Federation instead (see [Secrets, credentials, and keys](note:1.2-secrets-and-keys)).

**Inheritance rules** ([Hierarchy evaluation](https://docs.cloud.google.com/organization-policy/hierarchy-evaluation)):

- A policy on a resource replaces the parent policy, unless it sets `inheritFromParent = true`. Then list values merge, and `DENY` values always win.
- Boolean policies do not merge. A project with `enforce: false` is not enforced, even if its folder sets `enforce: true`.
- Inherited managed constraints do not merge. The child uses the parent policy or its own policy.
- `restoreDefault` returns the resource to the constraint's default behavior.

**Not retroactive.** A new policy usually does not change existing resources. A violation stays until you fix it ([Organization Policy overview](https://docs.cloud.google.com/organization-policy/overview)). Public access prevention is an exception: it overrides existing public permissions ([Organization policy constraints](https://docs.cloud.google.com/organization-policy/reference/org-policy-constraints)). Enforcement can take up to 10 minutes ([Public access prevention](https://docs.cloud.google.com/storage/docs/public-access-prevention)).

**Dry run and custom constraints.** Google recommends that you test and dry-run all policy changes ([Organization Policy overview](https://docs.cloud.google.com/organization-policy/overview)). A policy file with `dryRunSpec` logs violations and does not block them. A file can hold both `spec` (live) and `dryRunSpec`. Dry-run mode accepts only custom constraints, managed constraints, and a few legacy managed constraints ([Test organization policies](https://docs.cloud.google.com/organization-policy/test-policies)). A custom constraint is a YAML file with a resource type, a Common Expression Language (CEL) condition, and an `ALLOW` or `DENY` action ([Create custom constraints](https://docs.cloud.google.com/organization-policy/create-custom-constraints)).

```yaml
name: RESOURCE_TYPE/RESOURCE_ID/policies/CONSTRAINT_NAME
spec:
  rules:
  - enforce: false

dryRunSpec:
  rules:
  - enforce: true
```

Source: [Test organization policies](https://docs.cloud.google.com/organization-policy/test-policies).

**No organization.** A project that is not in an organization cannot use organization policies. Use the bucket-level public access prevention setting instead ([Public access prevention](https://docs.cloud.google.com/storage/docs/public-access-prevention)).

## AWS mapping

| AWS | Google Cloud | Difference that matters |
|---|---|---|
| Amazon S3 object lifecycle | Object Lifecycle Management | One action per rule. `Delete` waits for holds and retention periods |
| Amazon S3 object versioning | Object Versioning | Google recommends soft delete, which is on by default, for deletion protection |
| Public access settings for Amazon S3 | Public access prevention | Signed URLs still work when public access prevention applies |
| S3 Object Lock | Retention policies and retention policy lock (Bucket Lock), Object Retention Lock | A bucket lock is permanent and adds a lien to the project |
| AWS Organizations | Resource Manager (organization, folders, projects) | Organization policies inherit down this hierarchy |
| AWS Config | Organization Policy Service | A constraint blocks a non-compliant create or update request. Dry-run mode only logs it |

Sources: [Migrate from AWS to Google Cloud: Migrate from Amazon S3 to Cloud Storage](https://docs.cloud.google.com/architecture/migrate-amazon-s3-to-cloud-storage), [Compare AWS and Azure services to Google Cloud](https://docs.cloud.google.com/docs/get-started/aws-azure-gcp-service-comparison), [Object Versioning](https://docs.cloud.google.com/storage/docs/object-versioning), [Bucket Lock](https://docs.cloud.google.com/storage/docs/bucket-lock), [Test organization policies](https://docs.cloud.google.com/organization-policy/test-policies).

If your code moved from Amazon S3 with HMAC keys, check for the `storage.restrictAuthTypes` constraint, which can block HMAC-signed requests ([Organization policy constraints for Cloud Storage](https://docs.cloud.google.com/storage/docs/org-policy-constraints)).

## Exam traps

- **Object Versioning as the answer to accidental deletion.** Google recommends soft delete. Versioning does not protect against bucket deletion ([Object Versioning](https://docs.cloud.google.com/storage/docs/object-versioning)).
- **Locking a retention policy "to test it".** The lock is permanent, blocks bucket deletion until all objects expire, and adds a project lien. Test with an unlocked policy ([Bucket Lock](https://docs.cloud.google.com/storage/docs/bucket-lock)).
- **A lifecycle rule to delete data before the retention period ends.** `Delete` waits for the retention period and for holds ([Object Lifecycle Management](https://docs.cloud.google.com/storage/docs/lifecycle)).
- **A temporary hold for "N years after an event".** Only an event-based hold restarts the retention period on release ([Object holds](https://docs.cloud.google.com/storage/docs/object-holds)).
- **Expecting lifecycle deletion at an exact time.** Actions are asynchronous, and changes can take 24 hours ([Object Lifecycle Management](https://docs.cloud.google.com/storage/docs/lifecycle)).
- **Parallel composite uploads to a bucket with a retention policy.** The temporary components cannot be deleted until they meet the period ([Bucket Lock](https://docs.cloud.google.com/storage/docs/bucket-lock)).
- **Granting `allUsers` when public access prevention applies.** The request fails. Use signed URLs for time-limited access (see [Signed URLs](note:1.3-signed-urls)) ([Public access prevention](https://docs.cloud.google.com/storage/docs/public-access-prevention)).
- **Expecting a new organization policy to fix existing resources.** Most constraints apply only to new create and update requests ([Organization Policy overview](https://docs.cloud.google.com/organization-policy/overview)).
- **A folder boolean policy that "overrides" a project.** A boolean policy set on the project is the effective policy for the project ([Hierarchy evaluation](https://docs.cloud.google.com/organization-policy/hierarchy-evaluation)).
- **Asking for a service account key exception.** New organizations block key creation by default. Use attached service accounts or Workload Identity Federation ([Manage Google Cloud security baseline constraints](https://docs.cloud.google.com/resource-manager/docs/manage-baseline-constraints)).
- **Turning off uniform bucket-level access later.** After 90 consecutive days you cannot disable it ([Uniform bucket-level access](https://docs.cloud.google.com/storage/docs/uniform-bucket-level-access)).
