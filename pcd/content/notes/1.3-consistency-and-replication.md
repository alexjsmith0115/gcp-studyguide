## Why it matters

Replication keeps data available and puts copies near users, but each product decides what a read returns after a write. The developer chooses the endpoint, the read mode, or the app profile that gives the freshness that the code needs. The exam tests which replicas are strongly or eventually consistent, how to get read-your-writes behavior, and how much data each failover model can lose. For locations and the zonal and regional failover models, see [Regions, zones, latency, and replication for failover](note:1.1-regions-and-replication).

## Key points

- **Spanner** replicates synchronously with Paxos, so any read-write or read-only replica can return the latest data ([Spanner replication](https://docs.cloud.google.com/spanner/docs/replication)). Strong reads are the default. A stale read uses a past timestamp and can lower latency ([Reads outside of transactions](https://docs.cloud.google.com/spanner/docs/reads)).
- **Cloud SQL high availability (HA)** replicates each write synchronously to the persistent disks in two zones before it reports the commit. Failover to the standby is automatic ([About high availability](https://docs.cloud.google.com/sql/docs/postgres/high-availability)).
- **Cloud SQL read replicas** can lag behind the primary instance. They give no failover, and you promote them manually ([About replication in Cloud SQL](https://docs.cloud.google.com/sql/docs/postgres/replication), [Replication lag](https://docs.cloud.google.com/sql/docs/postgres/replication/replication-lag), [Promote replicas for regional migration or disaster recovery](https://docs.cloud.google.com/sql/docs/postgres/replication/cross-region-replicas)).
- **AlloyDB** writes the write-ahead log (WAL) synchronously to a regional log persistor, so an HA failover loses no data ([AlloyDB high availability overview](https://docs.cloud.google.com/alloydb/docs/high-availability)). Read pool instances and secondary clusters receive changes with a lag ([Troubleshoot replication issues](https://docs.cloud.google.com/alloydb/docs/troubleshoot/replication-issues), [Cross-region replication overview](https://docs.cloud.google.com/alloydb/docs/cross-region-replication/about-cross-region-replication)).
- **Bigtable** replication between clusters has eventual consistency. Reads and writes to the same cluster are consistent ([Bigtable replication overview](https://docs.cloud.google.com/bigtable/docs/replication-overview)).
- **Bigtable app profiles** set the routing. Single-cluster routing gives read-your-writes consistency and is the only policy that allows single-row transactions. Multi-cluster routing gives automatic failover ([Routing options](https://docs.cloud.google.com/bigtable/docs/routing)).
- **Cloud Storage** gives strong global consistency for object writes, metadata updates, deletes, and listings, in all location types ([Cloud Storage consistency](https://docs.cloud.google.com/storage/docs/consistency)).
- **Cloud Storage exceptions:** access changes have eventual consistency, and a cached public object can be stale until its `Cache-Control` lifetime ends ([Cloud Storage consistency](https://docs.cloud.google.com/storage/docs/consistency)).
- **Dual-region and multi-region buckets** copy new objects to the second region asynchronously. Turbo replication gives dual-region buckets a 15-minute recovery point objective (RPO) ([Data availability and durability](https://docs.cloud.google.com/storage/docs/availability-durability)).
- **Firestore** replicates synchronously and serves strong reads by default. You can request stale reads with `read_time` ([Understand reads and writes at scale](https://docs.cloud.google.com/firestore/native/docs/understand-reads-writes-scale)).

## What strong and eventual consistency mean for your code

A strong read returns all data that was committed before the read started ([Reads outside of transactions](https://docs.cloud.google.com/spanner/docs/reads)). With eventual consistency, a write to one copy becomes readable from the other copies only after replication ([Bigtable replication overview](https://docs.cloud.google.com/bigtable/docs/replication-overview)). If a read must see the write that the code just made, you have two options:

1. Read from the copy that took the write: the Cloud SQL or AlloyDB primary instance, or one Bigtable cluster.
2. Use a product with strongly consistent reads: Spanner, Firestore, or Cloud Storage objects.

| Product | Replication | Read consistency | For read-after-write |
|---|---|---|---|
| Spanner | Synchronous. A majority of voting replicas must accept each write | Strong by default, from any read-write or read-only replica | Nothing extra. Use stale reads only where old data is acceptable |
| Cloud SQL | HA: synchronous to disks in two zones. Read replicas: they can lag | Primary: current. Read replica: can be stale | Read from the primary instance |
| AlloyDB | HA primary: synchronous WAL. Read pools and secondary clusters: they can lag | Primary: current. Read pool: can be stale | Read from the primary instance |
| Bigtable | Between clusters, with some latency | Eventual across clusters. Consistent inside one cluster | Single-cluster routing to one cluster |
| Cloud Storage | A write succeeds after storage in two zones. The copy to a second region is asynchronous | Strong for object and list operations | Nothing extra. Do not cache public objects that change |
| Firestore | Synchronous (Paxos) | Strong by default | Nothing extra |

Sources: [Spanner replication](https://docs.cloud.google.com/spanner/docs/replication), [About high availability](https://docs.cloud.google.com/sql/docs/postgres/high-availability), [Replication lag](https://docs.cloud.google.com/sql/docs/postgres/replication/replication-lag), [AlloyDB high availability overview](https://docs.cloud.google.com/alloydb/docs/high-availability), [Troubleshoot replication issues](https://docs.cloud.google.com/alloydb/docs/troubleshoot/replication-issues), [Bigtable replication overview](https://docs.cloud.google.com/bigtable/docs/replication-overview), [Cloud Storage consistency](https://docs.cloud.google.com/storage/docs/consistency), [Data availability and durability](https://docs.cloud.google.com/storage/docs/availability-durability), [Understand reads and writes at scale](https://docs.cloud.google.com/firestore/native/docs/understand-reads-writes-scale).

## Spanner: strong reads by default, stale reads by choice

Spanner uses synchronous, Paxos-based replication. The leader replica processes every write first, even when a closer replica exists. The write commits when a majority of voting replicas agree ([Spanner replication](https://docs.cloud.google.com/spanner/docs/replication)). By default, Spanner gives external consistency, which is stronger than strong consistency. Transactions appear to run one at a time, in the order that clients see them commit ([Spanner: TrueTime and external consistency](https://docs.cloud.google.com/spanner/docs/true-time-external-consistency)). TrueTime is the distributed clock that gives Spanner these ordered commit timestamps ([Spanner: TrueTime and external consistency](https://docs.cloud.google.com/spanner/docs/true-time-external-consistency)).

You choose the read type with a timestamp bound:

| Timestamp bound | What the read returns | Use when |
|---|---|---|
| Strong (default) | All data committed before the read starts | Almost always. Google says to choose strong reads whenever possible |
| Bounded staleness | The newest data inside your staleness bound that the closest replica can serve without blocking | Latency matters, some staleness is acceptable, and fresher data is better |
| Exact staleness | The data at an exact timestamp, or at an exact age | Several reads must see the same snapshot, or you want the fastest stale read |

Sources: [Reads outside of transactions](https://docs.cloud.google.com/spanner/docs/reads), [Timestamp bounds](https://docs.cloud.google.com/spanner/docs/timestamp-bounds).

- **Strong reads are not repeatable.** Two strong reads in a row can return different data if writes occur between them. For one consistent view, use one transaction or an exact timestamp ([Timestamp bounds](https://docs.cloud.google.com/spanner/docs/timestamp-bounds)).
- **Staleness values.** Use a staleness of at least 10 seconds to get a benefit. The docs call 15 seconds a reasonable value ([Timestamp bounds](https://docs.cloud.google.com/spanner/docs/timestamp-bounds), [Reads outside of transactions](https://docs.cloud.google.com/spanner/docs/reads)).
- **Old timestamps fail.** A read older than the `version_retention_period` fails with `FAILED_PRECONDITION`. The period is 1 hour by default and up to 1 week ([Timestamp bounds](https://docs.cloud.google.com/spanner/docs/timestamp-bounds)).

A stale read with the Python client, from the docs sample:

```python
import datetime
from google.cloud import spanner

spanner_client = spanner.Client()
instance = spanner_client.instance(instance_id)
database = instance.database(database_id)
staleness = datetime.timedelta(seconds=15)

# Exact staleness. For bounded staleness, pass max_staleness instead.
with database.snapshot(exact_staleness=staleness) as snapshot:
    results = snapshot.read(
        table="Albums",
        columns=("SingerId", "AlbumId", "MarketingBudget"),
        keyset=spanner.KeySet(all_=True),
    )
    for row in results:
        print(row)
```

Source: [Reads outside of transactions](https://docs.cloud.google.com/spanner/docs/reads).

**Transactions and locks.** Reads inside a read-write transaction go to the leader replica, because the leader holds the locks for serializability ([Spanner replication](https://docs.cloud.google.com/spanner/docs/replication)). A read-only transaction takes no locks and can run on any replica, so use it for reads unless you must write ([Transactions overview](https://docs.cloud.google.com/spanner/docs/transactions)). Keep read-write transactions short, because locks that stay for a long time cause deadlocks and aborts. The client libraries retry aborted transactions automatically ([Transactions overview](https://docs.cloud.google.com/spanner/docs/transactions)). Transaction code belongs to [Reading and writing data with the client libraries](note:4.1-reading-writing-data).

**Instance configurations.** The configuration sets the replicas, the availability, and the latency:

| Configuration | Replicas | Availability | Latency |
|---|---|---|---|
| Regional | Three read-write replicas in three zones. A write needs two of the three | 99.99% | Lower write latency inside the region |
| Dual-region (Enterprise Plus edition) | Two regions in one country. Each region has two read-write replicas and one witness replica | 99.999%, zero RPO | Lower read latency in two regions, a small increase in write latency |
| Multi-region (Enterprise Plus edition) | Two read-write regions, a witness region, and in some configurations read-only regions | 99.999% | Lower read latency in more places, a small increase in write latency |

Source: [Regional, dual-region, and multi-region configurations](https://docs.cloud.google.com/spanner/docs/instance-configurations).

- **Read-only replicas** serve reads but do not vote, so they add read capacity and do not slow writes. A nearby read-only replica can usually serve a stale read of 15 seconds or more without a round trip to the leader region ([Spanner replication](https://docs.cloud.google.com/spanner/docs/replication)).
- **Strong reads far from the leader** can need a round trip to the leader to agree on a timestamp ([Spanner replication](https://docs.cloud.google.com/spanner/docs/replication)). Read leases let non-leader regions serve strong reads locally, but all writes get slower ([Read lease](https://docs.cloud.google.com/spanner/docs/read-lease)).
- **Placement.** Put write-heavy compute in or near the default leader region. For fast reads outside it, use a staleness of at least 15 seconds. If the default leader region fails, Spanner moves the leaders to the second read-write region automatically ([Regional, dual-region, and multi-region configurations](https://docs.cloud.google.com/spanner/docs/instance-configurations)).

## Cloud SQL: synchronous HA, read replicas that lag

| | HA (regional instance) | Read replica | Cross-region read replica |
|---|---|---|---|
| Purpose | Survive a zone or instance failure | Move read load off the primary instance | Faster reads near the app, regional disaster recovery, region migration |
| Replication | Synchronous to the disk in each zone, before the commit returns | Streaming replication, almost real time, can lag | Asynchronous |
| Failover | Automatic, about 60 seconds, same IP address | None. You can promote a replica manually | Manual promotion, or replica failover to a disaster recovery (DR) replica (Enterprise Plus edition) |
| Data loss | The standby state is identical to the primary state | Depends on replication lag | The RPO is likely more than zero |

Sources: [About high availability](https://docs.cloud.google.com/sql/docs/postgres/high-availability), [About replication in Cloud SQL](https://docs.cloud.google.com/sql/docs/postgres/replication), [Replication lag](https://docs.cloud.google.com/sql/docs/postgres/replication/replication-lag), [About disaster recovery (DR) in Cloud SQL](https://docs.cloud.google.com/sql/docs/postgres/intro-to-cloud-sql-disaster-recovery).

- **Failover closes connections.** A failover closes the connections to the primary instance and to the read replicas. The application reconnects with the same connection string or IP address after about 60 seconds ([About high availability](https://docs.cloud.google.com/sql/docs/postgres/high-availability)).
- **Read-after-write.** A replica applies changes after the primary commits them, so a read on a replica right after a write can return the old row. Read from the primary instance when the code must see its own write. Monitor the `replica_lag` and `network_lag` metrics ([Replication lag](https://docs.cloud.google.com/sql/docs/postgres/replication/replication-lag)).
- **Replica placement.** Put a read replica in a third zone. Send reads to the primary instance when the replicas are not available ([About high availability](https://docs.cloud.google.com/sql/docs/postgres/high-availability)).
- **Standalone instances.** Cloud SQL does not recover a zonal (non-HA) instance from a zonal outage automatically. Point-in-time recovery gives an RPO of typically five minutes or less ([About high availability](https://docs.cloud.google.com/sql/docs/postgres/high-availability)).

**Advanced disaster recovery (Enterprise Plus edition).** You designate a cross-region replica as the DR replica ([About disaster recovery (DR) in Cloud SQL](https://docs.cloud.google.com/sql/docs/postgres/intro-to-cloud-sql-disaster-recovery)):

- **Replica failover** promotes the DR replica immediately. It can lose data if the DR replica has replication lag.
- **Switchover** has zero data loss. The primary stays read-only until the DR replica catches up. Use it for DR drills and to move back after a failover.
- **Write endpoint.** This global DNS name points to the current primary instance, so clients need no change after a replica failover or switchover.
- **Split brain.** After a regional failover, stop clients from reaching the old primary instance before they use the new one.

## AlloyDB: HA primary, read pools, and secondary clusters

| Component | Replication | Reads | On failure |
|---|---|---|---|
| Primary instance with HA (active and standby nodes in two zones) | Synchronous WAL writes to the regional log persistor | Current data | Automatic failover with no data loss. Detection takes up to 30 seconds, and the database typically starts in less than 30 seconds |
| Read pool instance (up to 20 nodes in a cluster) | Shares the cluster storage. The read nodes receive and replay the WAL | Can be stale by the flush lag plus the replay lag | With two or more nodes across zones, traffic moves to healthy nodes |
| Secondary cluster (another region, up to five) | Asynchronous from the primary cluster | Can be stale. You cannot write until you promote it | Manual promotion, switchover with zero data loss, or cross-region failover (Preview) |

Sources: [AlloyDB high availability overview](https://docs.cloud.google.com/alloydb/docs/high-availability), [AlloyDB overview](https://docs.cloud.google.com/alloydb/docs/overview), [Troubleshoot replication issues](https://docs.cloud.google.com/alloydb/docs/troubleshoot/replication-issues), [Cross-region replication overview](https://docs.cloud.google.com/alloydb/docs/cross-region-replication/about-cross-region-replication).

- **Two kinds of lag.** Flush lag decides data loss on a secondary cluster. Flush lag and replay lag together decide how stale a read pool is ([Troubleshoot replication issues](https://docs.cloud.google.com/alloydb/docs/troubleshoot/replication-issues)).
- **Causes of lag.** Heavy reads, small read nodes, long queries that block replay, and very large transactions increase lag ([Troubleshoot replication issues](https://docs.cloud.google.com/alloydb/docs/troubleshoot/replication-issues)).
- **Transparent query forwarding (Preview).** The primary sends eligible read-only `SELECT` queries to read pools with read-your-writes consistency ([Optimize resources and isolate read queries with transparent query forwarding](https://docs.cloud.google.com/alloydb/docs/transparent-query-forwarding)).

## Bigtable: eventual consistency across clusters

Each cluster in a replicated instance is a primary cluster that accepts reads and writes. Replication usually takes seconds or minutes, but it can take longer under heavy writes or when clusters are far apart. Do not assume that a short wait after a write is enough ([Bigtable replication overview](https://docs.cloud.google.com/bigtable/docs/replication-overview)). An instance with one cluster has strong consistency ([Bigtable replication overview](https://docs.cloud.google.com/bigtable/docs/replication-overview)).

| App profile routing | Consistency | Failover | Single-row transactions |
|---|---|---|---|
| Single-cluster routing | Read-your-writes when all app profiles route to the same cluster. Strong when other clusters are used only for failover | Manual | Allowed. The only policy that allows them |
| Multi-cluster routing (any cluster or a cluster group) | Eventual. With one cluster in each region, read-your-writes inside the source region unless a failover occurs | Automatic, to the nearest available cluster | Never allowed |
| Multi-cluster with row-affinity routing | More read-your-writes for single-row requests, but not guaranteed | Automatic | Never allowed |

Sources: [Bigtable replication overview](https://docs.cloud.google.com/bigtable/docs/replication-overview), [Routing options](https://docs.cloud.google.com/bigtable/docs/routing), [App profiles overview](https://docs.cloud.google.com/bigtable/docs/app-profiles).

- **Single-row transactions** are read-modify-write operations (increments and appends) and check-and-mutate operations (conditional writes) ([Routing options](https://docs.cloud.google.com/bigtable/docs/routing)).
- **Why multi-cluster routing blocks them.** Two increments on two clusters each add 1, and replication cannot know that you meant 2. For counters, aggregates merge each new value at write time ([Routing options](https://docs.cloud.google.com/bigtable/docs/routing)).
- **Conflicts.** For writes to the same cell on two clusters, last write wins, based on the server time ([Bigtable replication overview](https://docs.cloud.google.com/bigtable/docs/replication-overview)).
- **After a failover**, Bigtable returns to eventual consistency. Some reads return stale data until replication completes ([Bigtable replication overview](https://docs.cloud.google.com/bigtable/docs/replication-overview)).
- **Consistency tokens.** A writer creates a token after a batch of writes. A reader calls `CheckConsistency` with it to confirm replication before it reads ([Bigtable writes](https://docs.cloud.google.com/bigtable/docs/writes)).
- **The default app profile** uses single-cluster routing with single-row transactions if the instance had one cluster at creation, and multi-cluster routing if it had more. Create one app profile for each workload ([App profiles overview](https://docs.cloud.google.com/bigtable/docs/app-profiles)).

```bash
# Read-your-writes and single-row transactions: one cluster, manual failover
gcloud bigtable app-profiles create orders-writer \
    --instance=INSTANCE_ID \
    --route-to=CLUSTER_ID \
    --transactional-writes

# High availability: any cluster, automatic failover, eventual consistency
gcloud bigtable app-profiles create catalog-reader \
    --instance=INSTANCE_ID \
    --route-any
```

Source: [Create and configure app profiles](https://docs.cloud.google.com/bigtable/docs/configuring-app-profiles).

The code selects the app profile when it opens the table:

```python
from google.cloud import bigtable

client = bigtable.Client(project=project_id)
instance = client.instance(instance_id)
table = bigtable.table.Table(table_id, instance, "orders-writer")
```

Source: [Create and configure app profiles](https://docs.cloud.google.com/bigtable/docs/configuring-app-profiles).

## Cloud Storage: strong for objects, eventual for access and caches

Cloud Storage gives strong global consistency for bucket listing, object listing, and read-after-write, read-after-metadata-update, and read-after-delete for buckets and objects. After a write succeeds, the object is readable at once, also in dual-region and multi-region buckets ([Cloud Storage consistency](https://docs.cloud.google.com/storage/docs/consistency)). If the first region becomes unavailable before replication, a read gets a retryable `500` error, not stale data ([Cloud Storage consistency](https://docs.cloud.google.com/storage/docs/consistency)).

Exceptions that a developer must plan for:

- **Access changes** (grant or revoke) usually take about a minute, sometimes several minutes. A user can keep access for a short time after you remove it ([Cloud Storage consistency](https://docs.cloud.google.com/storage/docs/consistency)).
- **Cached public objects** stay in the cache after an update or delete, until the `Cache-Control` lifetime ends. Without a lifetime, a public object can be cached for up to 60 minutes ([Cloud Storage consistency](https://docs.cloud.google.com/storage/docs/consistency)).
- **The fix for a changing object** is `Cache-Control: no-store`, or `public` with a `max-age` of 15 to 60 seconds. The built-in cache has no invalidation, but Cloud CDN does ([Caching with Cloud Storage built-in cache](https://docs.cloud.google.com/storage/docs/caching)). For Cloud CDN, see [Caching with Memorystore and Cloud CDN](note:1.1-caching).

| Bucket location | The write succeeds after | Copy to a second region | RPO |
|---|---|---|---|
| Region | Storage in at least two zones | None | Not applicable |
| Dual-region or multi-region, default replication | Storage in two zones of one region | Asynchronous. Target: 99.9% of new objects in one hour, 100% in 12 hours | 12 hours |
| Dual-region with turbo replication | Storage in two zones of one region | 100% of new objects in 15 minutes | 15 minutes |

Source: [Data availability and durability](https://docs.cloud.google.com/storage/docs/availability-durability).

Dual-region and multi-region buckets are active-active, with a recovery time objective (RTO) of zero for replicated data. Data that is not yet replicated stays unavailable until the failed region comes back ([Data availability and durability](https://docs.cloud.google.com/storage/docs/availability-durability)).

## Firestore: strong reads, optional stale reads

- **Replication.** Firestore replicates each database automatically and synchronously with Paxos, so a read can always get the latest version ([Understand reads and writes at scale](https://docs.cloud.google.com/firestore/native/docs/understand-reads-writes-scale)).
- **Locations.** A multi-region location has two regions with full replicas and a witness region, and it survives the loss of a region. A regional location has lower cost and lower write latency. You cannot change the location later ([Firestore locations](https://docs.cloud.google.com/firestore/native/docs/locations)). Availability is 99.99% for regional and 99.999% for multi-region databases ([Firestore overview](https://docs.cloud.google.com/firestore/native/docs/overview)).
- **Stale reads.** Reads are strong by default. For lower latency, read at a past `read_time`. The docs call 15 seconds a reasonable staleness ([Understand reads and writes at scale](https://docs.cloud.google.com/firestore/native/docs/understand-reads-writes-scale)).
- **Datastore compatibility.** Firestore with Datastore compatibility (the docs also say Firestore in Datastore mode) has strongly consistent queries ([Datastore overview](https://docs.cloud.google.com/datastore/docs/concepts/overview), [Choose between Firestore APIs](https://docs.cloud.google.com/datastore/docs/firestore-or-datastore)). Eventually consistent global queries exist only in legacy Datastore databases that were not upgraded ([Structuring Data for Strong Consistency](https://docs.cloud.google.com/datastore/docs/concepts/structuring_for_strong_consistency)).

For Firestore data modeling and hotspots, see [Schema design for Bigtable and Firestore](note:1.3-nosql-schema).

## Choosing a replication design

| Requirement | Use | Do not use |
|---|---|---|
| A read must see the write that the code just made (Cloud SQL, AlloyDB) | The primary instance | A read replica or a read pool instance |
| Read-your-writes in a replicated Bigtable instance | Single-cluster routing, with all readers and writers on one cluster | Multi-cluster routing |
| Lower read latency far from the Spanner leader, and old data is acceptable | Stale reads of 15 seconds or more | Read-write transactions for read-only work |
| Survive a zone failure in Cloud SQL | The HA configuration | A read replica, which has no failover |
| Survive a region failure in Cloud SQL | A cross-region read replica (a DR replica in Enterprise Plus edition) | HA alone, which stays in one region |
| Move a database to another region with no data loss | Switchover (Cloud SQL Enterprise Plus edition, AlloyDB) | Replica failover or promotion while lag exists |
| Relational writes from several regions with strong consistency | A Spanner multi-region configuration | Cloud SQL cross-region replicas, which are read-only |
| Objects that survive a region loss with a short RPO | A dual-region bucket with turbo replication | Default replication only |

Sources: [About replication in Cloud SQL](https://docs.cloud.google.com/sql/docs/postgres/replication), [Replication lag](https://docs.cloud.google.com/sql/docs/postgres/replication/replication-lag), [Troubleshoot replication issues](https://docs.cloud.google.com/alloydb/docs/troubleshoot/replication-issues), [Routing options](https://docs.cloud.google.com/bigtable/docs/routing), [Reads outside of transactions](https://docs.cloud.google.com/spanner/docs/reads), [About disaster recovery (DR) in Cloud SQL](https://docs.cloud.google.com/sql/docs/postgres/intro-to-cloud-sql-disaster-recovery), [Cross-region replication overview](https://docs.cloud.google.com/alloydb/docs/cross-region-replication/about-cross-region-replication), [Regional, dual-region, and multi-region configurations](https://docs.cloud.google.com/spanner/docs/instance-configurations), [Data availability and durability](https://docs.cloud.google.com/storage/docs/availability-durability).

## Exam traps

- **A read replica as the failover target.** Read replicas give no failover. For zone failures, use the HA configuration ([About replication in Cloud SQL](https://docs.cloud.google.com/sql/docs/postgres/replication)).
- **Reading your own write from a replica.** A Cloud SQL replica or an AlloyDB read pool can lag. Read from the primary instance ([Replication lag](https://docs.cloud.google.com/sql/docs/postgres/replication/replication-lag), [Troubleshoot replication issues](https://docs.cloud.google.com/alloydb/docs/troubleshoot/replication-issues)).
- **"Wait a few seconds" for Bigtable replication.** The docs say that this is not safe. Use single-cluster routing or a consistency token ([Bigtable replication overview](https://docs.cloud.google.com/bigtable/docs/replication-overview), [Bigtable writes](https://docs.cloud.google.com/bigtable/docs/writes)).
- **Increments with multi-cluster routing.** Bigtable never allows single-row transactions with multi-cluster routing ([Routing options](https://docs.cloud.google.com/bigtable/docs/routing)).
- **"Datastore global queries are eventually consistent."** That is true only for legacy Datastore databases. Firestore queries, also with Datastore compatibility, are strongly consistent ([Datastore overview](https://docs.cloud.google.com/datastore/docs/concepts/overview), [Structuring Data for Strong Consistency](https://docs.cloud.google.com/datastore/docs/concepts/structuring_for_strong_consistency)).
- **An updated public object that clients still see in the old version.** The cache keeps it until its lifetime ends. Set `Cache-Control: no-store` or a short `max-age` on objects that change ([Cloud Storage consistency](https://docs.cloud.google.com/storage/docs/consistency), [Caching with Cloud Storage built-in cache](https://docs.cloud.google.com/storage/docs/caching)).
- **Instant access revocation on a bucket.** Access changes have eventual consistency, usually about a minute ([Cloud Storage consistency](https://docs.cloud.google.com/storage/docs/consistency)).
- **Read-write transactions for read-only work.** They take locks at the leader. Use a single read or a read-only transaction ([Transactions overview](https://docs.cloud.google.com/spanner/docs/transactions), [Spanner replication](https://docs.cloud.google.com/spanner/docs/replication)).
- **Promotion for a planned region move.** Promotion or replica failover can lose lagging data. Switchover has zero data loss ([About disaster recovery (DR) in Cloud SQL](https://docs.cloud.google.com/sql/docs/postgres/intro-to-cloud-sql-disaster-recovery), [Cross-region replication overview](https://docs.cloud.google.com/alloydb/docs/cross-region-replication/about-cross-region-replication)).
- **Multi-region Spanner to make writes faster.** Writes go through the leader region, and multi-region adds a small write latency ([Regional, dual-region, and multi-region configurations](https://docs.cloud.google.com/spanner/docs/instance-configurations)).
