## Why it matters

Some processes need a central controller: call service A, then B and C in parallel, wait for an approval, and retry on errors. Other work must run later, at a controlled rate, or on a schedule. The developer chooses between Workflows, Cloud Tasks, Cloud Scheduler, and event choreography, and configures authentication and retries for each. The exam tests the choice, the token type (OIDC or OAuth 2.0), and the retry defaults.

## Key points

- In orchestration, a central service controls the flow between services. In choreography, each service reacts to events, and no service controls the flow ([Better service orchestration with Workflows](https://cloud.google.com/blog/topics/developers-practitioners/better-service-orchestration-workflows)).
- Workflows is a serverless orchestration platform. It has no charges while idle, and a workflow can hold state, retry, poll, or wait for up to a year ([Workflows overview](https://docs.cloud.google.com/workflows/docs/overview)).
- HTTP requests from a workflow carry no token by default. Use OIDC for Cloud Run and Cloud Run functions, and OAuth 2.0 for `*.googleapis.com` APIs ([Make authenticated requests from a workflow](https://docs.cloud.google.com/workflows/docs/authenticate-from-workflow)).
- A workflow started by an Eventarc event is not retried if the execution starts and later fails ([Trigger a workflow with events or Pub/Sub messages](https://docs.cloud.google.com/workflows/docs/trigger-workflow-eventarc)).
- Cloud Tasks uses explicit invocation: the producer sets the endpoint, and the queue controls the rate and the retries ([Choosing Pub/Sub or Cloud Tasks](https://docs.cloud.google.com/pubsub/docs/choosing-pubsub-or-cloud-tasks)).
- A named task deduplicates. Cloud Tasks rejects a second task with the same name, for up to 24 hours after the first task is deleted ([Understand Cloud Tasks](https://docs.cloud.google.com/tasks/docs/dual-overview)).
- Cloud Tasks and Cloud Scheduler deliver at least once, so the handlers must be idempotent ([Understand Cloud Tasks](https://docs.cloud.google.com/tasks/docs/dual-overview), [About Cloud Scheduler](https://docs.cloud.google.com/scheduler/docs/overview)).
- A Cloud Scheduler job does not retry by default. The retry count and the retry duration both default to 0 ([Retry jobs](https://docs.cloud.google.com/scheduler/docs/configuring/retry-jobs)).
- For a one-time job, use Cloud Tasks instead of Cloud Scheduler. Cloud Tasks can schedule a task up to 30 days in advance ([Manage cron jobs](https://docs.cloud.google.com/scheduler/docs/creating)).

## Orchestration compared with choreography

| | Orchestration | Choreography |
|---|---|---|
| Control | A central service defines and controls the flow | Each service subscribes to events and emits events. A broker passes the events but does not direct the flow |
| Trade-off | You change and monitor the flow in one place, and apply consistent timeout and error policies | Services are fully independent, but the flow and the policies are harder to trace and manage |
| Good fit | A well-defined process with a bounded context, which you can draw as a flow diagram | A distributed system across different domains |
| Google Cloud product | Workflows | Pub/Sub and Eventarc |

Sources: [Better service orchestration with Workflows](https://cloud.google.com/blog/topics/developers-practitioners/better-service-orchestration-workflows), [Workflows overview](https://docs.cloud.google.com/workflows/docs/overview).

A hybrid is also possible: orchestrated workflows communicate with each other through events ([Better service orchestration with Workflows](https://cloud.google.com/blog/topics/developers-practitioners/better-service-orchestration-workflows)). Pub/Sub and Eventarc are on [the asynchronous integration page](note:1.1-async-events).

## Choose the tool

| Requirement | Use | Why |
|---|---|---|
| Call several services in a defined order, with branches, parallel steps, and retries | Workflows | The workflow definition makes the dependencies explicit and observable |
| Pause a process until a person or a system responds | Workflows callbacks | The execution waits without polling |
| Hand off one HTTP call to run later, at a controlled rate | Cloud Tasks | The queue sets the dispatch rate, concurrency, and retries |
| Run one call at a set time in the future | Cloud Tasks | Scheduled delivery, up to 30 days in advance |
| Run a call on a repeating schedule | Cloud Scheduler | Cron jobs with HTTP, Pub/Sub, or App Engine targets |
| Run ETL or ELT pipelines as Python DAGs | Managed Service for Apache Airflow (formerly Cloud Composer) | Designed for data-driven batch workflows |

Sources: [Workflows overview](https://docs.cloud.google.com/workflows/docs/overview), [Wait using callbacks](https://docs.cloud.google.com/workflows/docs/creating-callback-endpoints), [Understand Cloud Tasks](https://docs.cloud.google.com/tasks/docs/dual-overview), [Manage cron jobs](https://docs.cloud.google.com/scheduler/docs/creating), [Choose Workflows or Managed Airflow for service orchestration](https://docs.cloud.google.com/workflows/docs/choose-orchestration).

On April 15, 2026, Google renamed Cloud Composer to Managed Service for Apache Airflow (Managed Airflow). The docs URLs and the Cloud Composer API keep the old name ([Managed Service for Apache Airflow release notes](https://docs.cloud.google.com/composer/docs/release-notes)). Compared with Workflows, Managed Airflow has latency in seconds instead of milliseconds, and you pay for provisioned capacity instead of each step ([Choose Workflows or Managed Airflow for service orchestration](https://docs.cloud.google.com/workflows/docs/choose-orchestration)).

## Workflows

A workflow definition is YAML or JSON. It contains steps, which run in order by default, plus `switch` conditions, `for` loops, parallel steps, and subworkflows. Workflows is a regional service ([Workflows overview](https://docs.cloud.google.com/workflows/docs/overview)).

Workflows has two ways to reach other services ([Invoke Cloud Run functions or Cloud Run](https://docs.cloud.google.com/workflows/docs/calling-run-functions), [Understand connectors](https://docs.cloud.google.com/workflows/docs/connectors)):

- **HTTP requests** (`http.get`, `http.post`, `http.request`) call Cloud Run services, Cloud Run functions, and other HTTP APIs.
- **Connectors** call Google Cloud APIs. They format the requests and handle retries and long-running operations. The workflow's service account still needs the IAM role, for example `roles/pubsub.publisher` to publish to Pub/Sub.

Put complex logic in a service, not in the workflow definition. Examples are reusable business logic, complex computations, and transformations that Workflows expressions do not support ([Invoke Cloud Run functions or Cloud Run](https://docs.cloud.google.com/workflows/docs/calling-run-functions)).

### Authentication from a workflow

| Target | Token | How |
|---|---|---|
| Cloud Run service or Cloud Run function | ID token (OIDC) | `auth: {type: OIDC}`. Grant `roles/run.invoker` to the workflow's service account, also for functions |
| Google Cloud API (`*.googleapis.com`) | Access token (OAuth 2.0) | Use a connector. If no connector exists, use `auth: {type: OAuth2}` |
| Private endpoint (on-premises, Compute Engine, GKE) | OIDC | Put Identity-Aware Proxy (IAP) in front of it |

Sources: [Make authenticated requests from a workflow](https://docs.cloud.google.com/workflows/docs/authenticate-from-workflow), [Invoke Cloud Run functions or Cloud Run](https://docs.cloud.google.com/workflows/docs/calling-run-functions).

The OIDC `audience` defaults to the value of `url`, but you should set it to the root URL of the service ([Invoke Cloud Run functions or Cloud Run](https://docs.cloud.google.com/workflows/docs/calling-run-functions)). Workflows can call a Cloud Run service with internal ingress in the same project. Use the `run.app` URL, not a custom domain ([Invoke Cloud Run functions or Cloud Run](https://docs.cloud.google.com/workflows/docs/calling-run-functions)). To run a Cloud Run job, use the Cloud Run Admin API connector, because a job does not serve HTTP requests ([Invoke Cloud Run functions or Cloud Run](https://docs.cloud.google.com/workflows/docs/calling-run-functions)).

### Retries

A `try` block with a `retry` policy retries a step. Workflows has two default policies ([Retry steps](https://docs.cloud.google.com/workflows/docs/reference/syntax/retrying)):

| Policy | Retries on | Use for |
|---|---|---|
| `${http.default_retry}` | HTTP 429, 502, 503, 504, connection errors, and timeouts | Idempotent steps only |
| `${http.default_retry_non_idempotent}` | HTTP 429, 503, and connection failures | Steps that are not safe to repeat |

Sources: [Retry steps](https://docs.cloud.google.com/workflows/docs/reference/syntax/retrying).

Both policies make up to 5 retries, with a delay that starts at 1 second and grows to 60 seconds. Each retry counts as an extra billed step ([Retry steps](https://docs.cloud.google.com/workflows/docs/reference/syntax/retrying)). Connectors use the idempotent policy for GET requests and the non-idempotent policy for other methods ([Understand connectors](https://docs.cloud.google.com/workflows/docs/connectors)).

Sources: [Invoke Cloud Run functions or Cloud Run](https://docs.cloud.google.com/workflows/docs/calling-run-functions), [Retry steps](https://docs.cloud.google.com/workflows/docs/reference/syntax/retrying).

```yaml
- get_order:
    try:
      call: http.get
      args:
        url: https://SERVICE_URL/orders
        auth:
          type: OIDC
          audience: OIDC_AUDIENCE
      result: order
    retry: ${http.default_retry}
```

### Parallel steps

A `parallel` step runs 2 to 10 `branches` at the same time, or runs the iterations of a `for` loop at the same time. Variables in the `shared` list are writable from all branches. The branches can run in any order ([Parallel steps](https://docs.cloud.google.com/workflows/docs/reference/syntax/parallel-steps)).

Source: [Parallel steps](https://docs.cloud.google.com/workflows/docs/reference/syntax/parallel-steps).

```yaml
- parallelStep:
    parallel:
      shared: [user, notification]
      branches:
        - getUser:
            steps:
              - getUserCall:
                  call: http.get
                  args:
                    url: ${"https://example.com/users/" + args.userId}
                  result: user
        - getNotification:
            steps:
              - getNotificationCall:
                  call: http.get
                  args:
                    url: ${"https://example.com/notification/" + args.notificationId}
                  result: notification
```

The parallel step waits until all branches complete. The only exception policy is `continueAll`: an unhandled error in one branch does not stop the other branches. `concurrency_limit` sets the maximum number of branches or iterations that run at once ([Parallel steps](https://docs.cloud.google.com/workflows/docs/reference/syntax/parallel-steps)).

### Callbacks and polling

A callback lets a workflow wait for an external request without polling, for example a human approval. The workflow creates a callback endpoint and then waits on it ([Wait using callbacks](https://docs.cloud.google.com/workflows/docs/creating-callback-endpoints)).

Source: [Wait using callbacks](https://docs.cloud.google.com/workflows/docs/creating-callback-endpoints).

```yaml
- create_callback:
    call: events.create_callback_endpoint
    args:
      http_callback_method: "GET"
    result: callback_details
- print_callback_details:
    call: sys.log
    args:
      severity: "INFO"
      text: ${"Listening for callbacks on " + callback_details.url}
- await_callback:
    call: events.await_callback
    args:
      callback: ${callback_details}
      timeout: 3600
    result: callback_request
```

The default wait is 43,200 seconds (12 hours). After the timeout, the step raises a `TimeoutError`. The caller of the endpoint needs the `workflows.callbacks.send` permission, which is in the Workflows Invoker role. Callbacks are fully idempotent, so the caller can safely retry ([Wait using callbacks](https://docs.cloud.google.com/workflows/docs/creating-callback-endpoints)). When no callback is possible, a workflow can poll with `sys.sleep` ([Workflows overview](https://docs.cloud.google.com/workflows/docs/overview)).

### How a workflow starts

| Trigger | Setup | Note |
|---|---|---|
| Manual or programmatic | The console, gcloud, a client library, or the Workflows API | Every execution needs an authenticated call |
| Eventarc trigger | The trigger's service account needs `roles/workflows.invoker` | The event arrives as a JSON runtime argument |
| Cloud Scheduler | An HTTP job to the Workflow Executions API with an OAuth token | The job's service account needs `roles/workflows.invoker` |

Sources: [Workflows overview](https://docs.cloud.google.com/workflows/docs/overview), [Trigger a workflow with events or Pub/Sub messages](https://docs.cloud.google.com/workflows/docs/trigger-workflow-eventarc), [Schedule a workflow using Cloud Scheduler](https://docs.cloud.google.com/workflows/docs/schedule-workflow).

With an Eventarc trigger, the event counts as delivered as soon as the execution starts. If the execution fails later, Eventarc does not retry it. Workflows deduplicates events within a 24-hour window. An event larger than the maximum Workflows argument size does not start an execution ([Trigger a workflow with events or Pub/Sub messages](https://docs.cloud.google.com/workflows/docs/trigger-workflow-eventarc)). Handle errors inside the workflow with `try` and `retry`.

## Cloud Tasks

Cloud Tasks takes work out of the request path. The application adds a task to a queue. The queue keeps the task until the handler succeeds or the retries run out ([Understand Cloud Tasks](https://docs.cloud.google.com/tasks/docs/dual-overview)). Typical uses are a faster user response, smoothing traffic spikes, and limiting the call rate to a third-party API ([Understand Cloud Tasks](https://docs.cloud.google.com/tasks/docs/dual-overview)).

An HTTP target can be Cloud Run, Cloud Run functions, GKE, Compute Engine, or an on-premises server. The handler must return HTTP 200 to 299 before the deadline: 10 minutes by default, 30 minutes at most. Any other response, or no response, causes a retry ([Understand Cloud Tasks](https://docs.cloud.google.com/tasks/docs/dual-overview)).

### Queue rate limits and retries

Source: [Configure queue routing, limits, and retries](https://docs.cloud.google.com/tasks/docs/configuring-queues).

```bash
gcloud tasks queues update QUEUE_ID \
    --max-dispatches-per-second=DISPATCH_RATE \
    --max-concurrent-dispatches=MAX_CONCURRENT_DISPATCHES

gcloud tasks queues update QUEUE_ID \
    --max-attempts=MAX_ATTEMPTS \
    --max-retry-duration=MAX_RETRY_DURATION \
    --min-backoff=MIN_INTERVAL \
    --max-backoff=MAX_INTERVAL \
    --max-doublings=MAX_DOUBLINGS
```

How the settings work ([Configure queue routing, limits, and retries](https://docs.cloud.google.com/tasks/docs/configuring-queues)):

- The rate limit applies to first attempts and to retries.
- The queue uses a token bucket. After a quiet period, the bucket fills, so a burst can exceed `max_dispatches_per_second`. For a slow downstream service, also set a small `max_concurrent_dispatches`.
- `--max-attempts` includes the first attempt. `-1` means unlimited.
- Cloud Tasks stops retrying only after both `--max-attempts` and `--max-retry-duration` are reached.
- A queue that you create with no parameters shows 500 dispatches per second, 100 maximum attempts, and a maximum backoff of 3,600 seconds.
- Queue-level routing (`uriOverride`) overrides task-level routing. Use it to put the queue as a buffer in front of one service.

### Create a task with a name, a schedule, and an OIDC token

Source: [Create HTTP target tasks programmatically](https://docs.cloud.google.com/tasks/docs/creating-http-target-tasks).

```python
import datetime
from google.cloud import tasks_v2
from google.protobuf import timestamp_pb2

client = tasks_v2.CloudTasksClient()
task = tasks_v2.Task(
    http_request=tasks_v2.HttpRequest(
        http_method=tasks_v2.HttpMethod.POST,
        url=url,
        oidc_token=tasks_v2.OidcToken(
            service_account_email=service_account_email,
            audience=audience,
        ),
        body=payload,
    ),
    name=client.task_path(project, location, queue, task_id),
)
timestamp = timestamp_pb2.Timestamp()
timestamp.FromDatetime(
    datetime.datetime.utcnow() + datetime.timedelta(seconds=scheduled_seconds_from_now)
)
task.schedule_time = timestamp
client.create_task(
    tasks_v2.CreateTaskRequest(
        parent=client.queue_path(project, location, queue), task=task
    )
)
```

Rules for this pattern ([Create HTTP target tasks programmatically](https://docs.cloud.google.com/tasks/docs/creating-http-target-tasks), [Understand Cloud Tasks](https://docs.cloud.google.com/tasks/docs/dual-overview)):

- **Name.** A task name that you set gives deduplication but adds latency. Without a name, Cloud Tasks generates a unique name, and no deduplication occurs. Do not use the `X-CloudTasks-TaskETA` header for deduplication.
- **Token.** Use an ID token (OIDC) for handlers on Google Cloud, such as Cloud Run. Use an access token only for `*.googleapis.com` APIs. A token set on the queue overrides the token on the task.
- **Service account.** The token's service account must be in the queue's project. It needs Cloud Tasks Enqueuer to add tasks and Cloud Run Invoker on the handler. The Cloud Tasks service agent needs Service Account User on that service account.
- **Headers.** The `X-CloudTasks-*` headers, such as `X-CloudTasks-TaskRetryCount`, give information only. They are not proof of identity.
- **Method.** `CreateTask` supports scheduling and is in the client libraries. `BufferTask` needs queue-level routing and is not in the client libraries.

### Cloud Tasks compared with Pub/Sub

Google's guidance: use Cloud Tasks when the producer must defer or control the execution of a specific webhook. Use Pub/Sub for general event ingestion and distribution ([Choosing Pub/Sub or Cloud Tasks](https://docs.cloud.google.com/pubsub/docs/choosing-pubsub-or-cloud-tasks)).

| Feature | Cloud Tasks | Pub/Sub |
|---|---|---|
| Invocation | Explicit: the producer sets the endpoint | Implicit: the publisher does not know the subscribers |
| Deduplication at creation | Yes | No |
| Scheduled delivery | Yes | No |
| Explicit rate controls | Yes | Flow control in pull subscribers |
| Handlers for each message | One | Many |
| Maximum size | 1 MB | 10 MB |
| Location | Regional | Global |

Sources: [Choosing Pub/Sub or Cloud Tasks](https://docs.cloud.google.com/pubsub/docs/choosing-pubsub-or-cloud-tasks).

## Cloud Scheduler

Cloud Scheduler runs cron jobs on a unix-cron schedule. A job sends a request to one target: an HTTP or HTTPS endpoint, a Pub/Sub topic, or an App Engine app ([About Cloud Scheduler](https://docs.cloud.google.com/scheduler/docs/overview), [Manage cron jobs](https://docs.cloud.google.com/scheduler/docs/creating)).

### Targets and authentication

| Target | Command or setting | Token |
|---|---|---|
| Cloud Run service or function | `gcloud scheduler jobs create http` with `--oidc-service-account-email` and `--oidc-token-audience` | OIDC. The service account needs `roles/run.invoker` |
| Workflows | An HTTP job to `https://workflowexecutions.googleapis.com/v1/.../executions` with `--oauth-service-account-email` | OAuth. The service account needs `roles/workflows.invoker` |
| Cloud Run job | An HTTP POST to `https://run.googleapis.com/v2/.../jobs/JOB:run` with `--oauth-service-account-email` | OAuth |
| Pub/Sub topic | `gcloud scheduler jobs create pubsub` with `--topic` and `--message-body` | None. The body becomes the message `data` |

Sources: [Running services on a schedule](https://docs.cloud.google.com/run/docs/triggering/using-scheduler), [Schedule a workflow using Cloud Scheduler](https://docs.cloud.google.com/workflows/docs/schedule-workflow), [Execute jobs on a schedule](https://docs.cloud.google.com/run/docs/execute/jobs-on-schedule), [Manage cron jobs](https://docs.cloud.google.com/scheduler/docs/creating).

Source: [Schedule a workflow using Cloud Scheduler](https://docs.cloud.google.com/workflows/docs/schedule-workflow).

```bash
gcloud scheduler jobs create http JOB_NAME \
    --schedule="FREQUENCY" \
    --uri="https://workflowexecutions.googleapis.com/v1/projects/PROJECT_ID/locations/REGION_NAME/workflows/WORKFLOW_NAME/executions" \
    --message-body="{\"argument\": \"DOUBLE_ESCAPED_JSON_STRING\"}" \
    --time-zone="TIME_ZONE" \
    --oauth-service-account-email="SERVICE_ACCOUNT_NAME@PROJECT_ID.iam.gserviceaccount.com"
```

The rule is the same as in Workflows and Cloud Tasks: use OIDC, except for Google APIs on `*.googleapis.com`, which expect an OAuth token ([Use authentication with HTTP targets](https://docs.cloud.google.com/scheduler/docs/http-target-auth)). Other rules from the same page:

- The job's service account must belong to the job's project.
- Do not use the Cloud Scheduler service agent as the job's service account. Do not revoke its `roles/cloudscheduler.serviceAgent` role, or authenticated targets return `403`.
- To attach the service account to the job, you need `iam.serviceAccounts.actAs`, which is in the Service Account User role.

A Cloud Run target with internal ingress works when it is in the same project or VPC Service Controls perimeter as the job. Use the `run.app` URL ([Manage cron jobs](https://docs.cloud.google.com/scheduler/docs/creating)).

### Retries and deduplication

| Setting | Flag | Default |
|---|---|---|
| Maximum retry attempts | `--max-retry-attempts` | 0 (maximum 5) |
| Maximum retry duration | `--max-retry-duration` | 0 seconds |
| Minimum backoff | `--min-backoff` | 5 seconds |
| Maximum backoff | `--max-backoff` | 3,600 seconds |
| Maximum doublings | `--max-doublings` | 5 |

Sources: [Retry jobs](https://docs.cloud.google.com/scheduler/docs/configuring/retry-jobs).

With both retry settings at 0, a failed attempt is not retried, and the job waits for the next scheduled time ([Retry jobs](https://docs.cloud.google.com/scheduler/docs/configuring/retry-jobs)). Set an attempt deadline that matches the timeout of the target. A mismatch can make Cloud Scheduler report a failure for a request that succeeded ([Manage cron jobs](https://docs.cloud.google.com/scheduler/docs/creating)). While a run waits for a response, Cloud Scheduler skips the next scheduled runs of that job ([Manage cron jobs](https://docs.cloud.google.com/scheduler/docs/creating)).

To make a handler idempotent, identify each request by the job name and the `X-CloudScheduler-ScheduleTime` header. The header keeps the same value across retries ([About Cloud Scheduler](https://docs.cloud.google.com/scheduler/docs/overview)).

## AWS mapping

| AWS | Google Cloud | Difference that matters |
|---|---|---|
| AWS Step Functions | Workflows | Definitions are YAML or JSON. HTTP calls carry no token until you add an `auth` block. Billing is per executed step |
| Amazon SQS, Amazon SNS | Cloud Tasks | Each task targets one HTTP endpoint that the producer names. The queue pushes to the handler at a rate that you set |
| Amazon EventBridge | Cloud Scheduler | A job has one target. Retries are off by default |
| Managed Workflows for Apache Airflow | Managed Service for Apache Airflow | For data pipelines as Python DAGs, not for low-latency service orchestration |

Sources: [Compare AWS and Azure services to Google Cloud](https://docs.cloud.google.com/docs/get-started/aws-azure-gcp-service-comparison), [Workflows overview](https://docs.cloud.google.com/workflows/docs/overview), [Make authenticated requests from a workflow](https://docs.cloud.google.com/workflows/docs/authenticate-from-workflow), [Understand Cloud Tasks](https://docs.cloud.google.com/tasks/docs/dual-overview), [Retry jobs](https://docs.cloud.google.com/scheduler/docs/configuring/retry-jobs), [Choose Workflows or Managed Airflow for service orchestration](https://docs.cloud.google.com/workflows/docs/choose-orchestration).

## Exam traps

- **A workflow that calls a private Cloud Run service with no `auth` block.** Workflows adds no token by default. Add `type: OIDC` ([Invoke Cloud Run functions or Cloud Run](https://docs.cloud.google.com/workflows/docs/calling-run-functions)).
- **An OIDC token to call a `googleapis.com` API.** Google APIs expect an OAuth 2.0 access token. Prefer a connector ([Make authenticated requests from a workflow](https://docs.cloud.google.com/workflows/docs/authenticate-from-workflow)).
- **`roles/cloudfunctions.invoker` for a Cloud Run function called from Workflows.** Grant `roles/run.invoker` ([Invoke Cloud Run functions or Cloud Run](https://docs.cloud.google.com/workflows/docs/calling-run-functions)).
- **`${http.default_retry}` on a payment step.** Use the idempotent policy only for idempotent steps ([Retry steps](https://docs.cloud.google.com/workflows/docs/reference/syntax/retrying)).
- **Eventarc retries for a failed workflow execution.** The event counts as delivered when the execution starts ([Trigger a workflow with events or Pub/Sub messages](https://docs.cloud.google.com/workflows/docs/trigger-workflow-eventarc)).
- **A loop with `sys.sleep` to wait for a human approval.** Use a callback endpoint ([Wait using callbacks](https://docs.cloud.google.com/workflows/docs/creating-callback-endpoints)).
- **Cloud Scheduler for a one-time future call.** Use a Cloud Tasks task with a schedule time ([Manage cron jobs](https://docs.cloud.google.com/scheduler/docs/creating)).
- **A Cloud Scheduler job that is expected to retry.** Retries default to 0. Set `--max-retry-attempts` ([Retry jobs](https://docs.cloud.google.com/scheduler/docs/configuring/retry-jobs)).
- **Pub/Sub to protect a third-party API from too many calls.** Use a Cloud Tasks queue with a dispatch rate ([Understand Cloud Tasks](https://docs.cloud.google.com/tasks/docs/dual-overview)).
- **Deduplication with `X-CloudTasks-TaskETA` or an auto-generated task name.** Set your own task name ([Understand Cloud Tasks](https://docs.cloud.google.com/tasks/docs/dual-overview)).
- **Cloud Tasks for a request where the user waits for the result.** Cloud Tasks gives no strong timing guarantee ([Understand Cloud Tasks](https://docs.cloud.google.com/tasks/docs/dual-overview)).
