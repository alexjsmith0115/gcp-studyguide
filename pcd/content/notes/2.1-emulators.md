## Why it matters

An emulator is a local program that copies the API of a Google Cloud service. You can use it to run and test your code on your own machine without cloud resources. The exam tests the start commands and the environment variables that send client library calls to an emulator. It also tests the features that an emulator does not copy and how to run Cloud Run services and functions locally.

## Key points

- The GA `gcloud emulators` group has commands for Firestore and Spanner. The Bigtable, Datastore, and Pub/Sub emulators are only in the `gcloud beta emulators` group ([gcloud emulators](https://docs.cloud.google.com/sdk/gcloud/reference/emulators), [gcloud beta emulators](https://docs.cloud.google.com/sdk/gcloud/reference/beta/emulators)).
- A Cloud Client Library connects to an emulator when an environment variable is set: `PUBSUB_EMULATOR_HOST`, `FIRESTORE_EMULATOR_HOST`, `BIGTABLE_EMULATOR_HOST`, or `SPANNER_EMULATOR_HOST` ([Testing apps locally with the emulator](https://docs.cloud.google.com/pubsub/docs/emulator), [Use Firestore emulator locally](https://docs.cloud.google.com/firestore/native/docs/emulator), [Test using the emulator](https://docs.cloud.google.com/bigtable/docs/emulator), [Emulate Spanner locally](https://docs.cloud.google.com/spanner/docs/emulator)).
- You must set the Pub/Sub variables each time you start the emulator, because the port can change. `env-init` prints the commands that set them ([Testing apps locally with the emulator](https://docs.cloud.google.com/pubsub/docs/emulator)).
- The Pub/Sub emulator works only with the Cloud Client Libraries. It does not support the Google Cloud console or `gcloud pubsub` commands ([Testing apps locally with the emulator](https://docs.cloud.google.com/pubsub/docs/emulator)).
- The Firestore, Bigtable, and Spanner emulators keep data in memory. The data is lost when the emulator stops ([Use Firestore emulator locally](https://docs.cloud.google.com/firestore/native/docs/emulator), [Test using the emulator](https://docs.cloud.google.com/bigtable/docs/emulator), [Emulate Spanner locally](https://docs.cloud.google.com/spanner/docs/emulator)).
- Emulators do not check identity. The Spanner emulator has no TLS, authentication, or IAM, and the Pub/Sub emulator does not support IAM operations ([Emulate Spanner locally](https://docs.cloud.google.com/spanner/docs/emulator), [Testing apps locally with the emulator](https://docs.cloud.google.com/pubsub/docs/emulator)).
- The Firestore emulator does not track manual indexes (formerly composite indexes) and runs any valid query. Test against Firestore to find the indexes that your queries need ([Use Firestore emulator locally](https://docs.cloud.google.com/firestore/native/docs/emulator), [Standard edition index overview](https://docs.cloud.google.com/firestore/native/docs/standard-index-overview)).
- To emulate Firestore in Datastore mode, use `gcloud emulators firestore start --database-mode=datastore-mode`. The Datastore emulator is for legacy Cloud Datastore ([Running the Datastore Emulator](https://docs.cloud.google.com/datastore/docs/tools/datastore-emulator)).
- The Firebase Local Emulator Suite runs several emulators together, for example Cloud Firestore, Cloud Storage for Firebase, Authentication, and Pub/Sub (beta) ([Introduction to Firebase Local Emulator Suite](https://firebase.google.com/docs/emulator-suite)).
- The Functions Framework runs a function as a local HTTP server. `gcloud beta code dev` and the Cloud Code Cloud Run Emulator run a Cloud Run service on your machine ([Local functions development](https://docs.cloud.google.com/run/docs/local-dev-functions), [Test a Cloud Run service locally](https://docs.cloud.google.com/run/docs/testing/local)).

## Choose and start an emulator

Each emulator has a start command, a default address, and a way to send client library calls to it. Some emulators need Java: the Pub/Sub emulator needs a JDK, and the Firestore and Datastore emulators need Java 21 or later.

| Service | Start command | Default address | Send client library calls to the emulator |
|---|---|---|---|
| Pub/Sub | `gcloud beta emulators pubsub start --project=PROJECT_ID` | Port 8085 on IPv6 localhost (`::1`) | `$(gcloud beta emulators pubsub env-init)` sets `PUBSUB_EMULATOR_HOST` |
| Firestore | `gcloud emulators firestore start` | `127.0.0.1:8080` | `export FIRESTORE_EMULATOR_HOST="HOST:PORT"`. The Firestore group has only the `start` command |
| Bigtable | `gcloud beta emulators bigtable start` | `localhost:8086` | `export BIGTABLE_EMULATOR_HOST=localhost:8086` |
| Spanner | `gcloud emulators spanner start` | `localhost:9010` (gRPC) and `localhost:9020` (REST) | `$(gcloud emulators spanner env-init)` or `export SPANNER_EMULATOR_HOST=localhost:9010` |
| Datastore (legacy) | `gcloud beta emulators datastore start` | A port that can change at each start | `$(gcloud beta emulators datastore env-init)` |

Sources: [Testing apps locally with the emulator](https://docs.cloud.google.com/pubsub/docs/emulator), [Use Firestore emulator locally](https://docs.cloud.google.com/firestore/native/docs/emulator), [gcloud emulators firestore](https://docs.cloud.google.com/sdk/gcloud/reference/emulators/firestore), [Test using the emulator](https://docs.cloud.google.com/bigtable/docs/emulator), [Emulate Spanner locally](https://docs.cloud.google.com/spanner/docs/emulator), [Running the Datastore Emulator](https://docs.cloud.google.com/datastore/docs/tools/datastore-emulator).

The project ID for the Pub/Sub emulator does not have to be a real project, because the emulator runs locally. In all languages except Java and C#, the Pub/Sub client library uses `PUBSUB_EMULATOR_HOST` automatically. Java and C# need extra code to connect to the emulator. The C# Spanner client also ignores `SPANNER_EMULATOR_HOST` by default ([Testing apps locally with the emulator](https://docs.cloud.google.com/pubsub/docs/emulator), [Emulate Spanner locally](https://docs.cloud.google.com/spanner/docs/emulator)).

This sequence installs the Pub/Sub emulator, starts it, and runs the Python samples against it:

```bash
gcloud components install pubsub-emulator
gcloud components update
gcloud beta emulators pubsub start --project=PUBSUB_PROJECT_ID

# In a second terminal on the same machine
$(gcloud beta emulators pubsub env-init)
python publisher.py PUBSUB_PROJECT_ID create TOPIC_ID
python subscriber.py PUBSUB_PROJECT_ID create TOPIC_ID SUBSCRIPTION_ID
python publisher.py PUBSUB_PROJECT_ID publish TOPIC_ID
python subscriber.py PUBSUB_PROJECT_ID receive SUBSCRIPTION_ID

# After you stop the emulator
unset PUBSUB_EMULATOR_HOST
```

Source: [Testing apps locally with the emulator](https://docs.cloud.google.com/pubsub/docs/emulator).

The variable controls where the client library sends calls. When it is set, calls go to the emulator. When it is not set, calls go to the production service. Unset it after you stop the emulator so that your app connects to Pub/Sub again ([Testing apps locally with the emulator](https://docs.cloud.google.com/pubsub/docs/emulator)).

You can also send gcloud commands to the Spanner emulator. Create a separate gcloud configuration that turns off credentials and sends Spanner requests to the local REST port:

```bash
gcloud config configurations create emulator
gcloud config set auth/disable_credentials true
gcloud config set project your-project-id
gcloud config set api_endpoint_overrides/spanner http://localhost:9020/
gcloud spanner instances create test-instance \
  --config=emulator-config --description="Test Instance" --nodes=1
```

Source: [Emulate Spanner locally](https://docs.cloud.google.com/spanner/docs/emulator).

## What the emulators do not emulate

An emulator copies the data API, not the full service. Each emulator page lists gaps. These gaps decide which tests can use an emulator.

| Emulator | Gaps that the docs list |
|---|---|
| Pub/Sub | No `UpdateTopic` or `UpdateSnapshot`. No IAM operations. No configurable message retention: it keeps all messages. Subscriptions do not expire. No seek to a timestamp for ordered subscriptions |
| Firestore | Simple locking transactions. Not all limits are enforced. No tracking of manual (composite) indexes, so any valid query runs |
| Bigtable | No admin API for instances and clusters. No secure connection. You cannot use it from the HBase shell |
| Spanner | No TLS, authentication, or IAM. Empty query plans. No audit logs or monitoring. Read-write transactions and schema changes lock the whole database |
| Datastore (legacy) | Simulates eventual consistency by default. No `IN`, `!=`, or `NOT-IN` queries. No aggregation queries such as `COUNT(*)` |

Sources: [Testing apps locally with the emulator](https://docs.cloud.google.com/pubsub/docs/emulator), [Use Firestore emulator locally](https://docs.cloud.google.com/firestore/native/docs/emulator), [Test using the emulator](https://docs.cloud.google.com/bigtable/docs/emulator), [Emulate Spanner locally](https://docs.cloud.google.com/spanner/docs/emulator), [Running the Datastore Emulator](https://docs.cloud.google.com/datastore/docs/tools/datastore-emulator).

The Pub/Sub emulator supports push and pull subscriptions, message ordering, replay, dead-letter topics, retry policies, and filtering ([Testing apps locally with the emulator](https://docs.cloud.google.com/pubsub/docs/emulator)).

Because of these gaps, an emulator test does not prove that a deployed app works. The Firestore page tells you to use a production environment for features that depend on limits ([Use Firestore emulator locally](https://docs.cloud.google.com/firestore/native/docs/emulator)). Test IAM, indexes, quotas, and performance against real resources in a test project. [Automated integration tests in Cloud Build](note:2.3-integration-tests-cloud-build) covers those tests.

## Firestore, Datastore mode, and saved data

The Firestore emulator can start in two database modes. The legacy Datastore emulator is a different program with different behavior.

| Need | Command or flag |
|---|---|
| Firestore in Native mode | `gcloud emulators firestore start` (`--database-mode=firestore-native` is the default) |
| Firestore in Datastore mode | `gcloud emulators firestore start --database-mode=datastore-mode` |
| Fail queries that have no composite index (Datastore mode only. The Datastore mode docs still say composite index) | `--require-indexes` together with `--index-file=firestore.indexes.yaml` |
| Load data at start, save data at shutdown | `--import-data=PATH`, `--export-on-exit=DIRECTORY` |
| Test Firebase Security Rules | `--rules=firestore.rules` |
| Clear all data between tests | Send `DELETE` to `http://HOST:PORT/emulator/v1/projects/PROJECT_ID/databases/(default)/documents` |

Sources: [gcloud emulators firestore start](https://docs.cloud.google.com/sdk/gcloud/reference/emulators/firestore/start), [Use Firestore emulator locally](https://docs.cloud.google.com/firestore/native/docs/emulator).

The legacy Datastore emulator stores data in a `local_db.bin` file, and the file persists between sessions. Firestore in Datastore mode is strongly consistent, but the legacy emulator simulates eventual consistency by default. The `--use-firestore-in-datastore-mode` flag removes some of these differences. For new work, the docs point you to the Firestore emulator in Datastore mode ([Running the Datastore Emulator](https://docs.cloud.google.com/datastore/docs/tools/datastore-emulator)).

## The Firebase Local Emulator Suite

The Firebase Local Emulator Suite is a set of emulators that the Firebase CLI starts together. It uses the same Firestore emulator as the gcloud CLI. Use it when a test needs several Firebase services at the same time, for example Firestore writes that start a function.

| Item | gcloud emulators | Firebase Local Emulator Suite |
|---|---|---|
| Services | Pub/Sub, Firestore, Bigtable, Spanner, Datastore | Cloud Firestore, Realtime Database, Cloud Storage for Firebase, Authentication, Firebase Hosting, Cloud Functions (beta), Pub/Sub (beta), Firebase Extensions (beta) |
| Start | One command for each emulator | `firebase emulators:start` starts the configured emulators |
| Continuous integration | Start the emulator, set the variable, run the tests | `firebase emulators:exec scriptpath` starts the emulators, runs the script, and stops the emulators |
| Requirements | gcloud CLI. Some emulators also need Java | Firebase CLI 8.14.0 or later and a JDK. The Firebase page says version 11 or later, but the Firestore emulator needs Java 21 or later |

Sources: [Use Firestore emulator locally](https://docs.cloud.google.com/firestore/native/docs/emulator), [Introduction to Firebase Local Emulator Suite](https://firebase.google.com/docs/emulator-suite), [Install, configure and integrate Local Emulator Suite](https://firebase.google.com/docs/emulator-suite/install_and_configure).

The gcloud CLI has no emulator group for Cloud Storage ([gcloud beta emulators](https://docs.cloud.google.com/sdk/gcloud/reference/beta/emulators)). The Firebase suite has an emulator for Cloud Storage for Firebase. Firebase tells you not to use its emulators as self-hosted production services, because they are built for accuracy, not for performance or security ([Introduction to Firebase Local Emulator Suite](https://firebase.google.com/docs/emulator-suite)).

## Run Cloud Run services and functions locally

You can run your service or function on your machine before you deploy it. Choose the tool by what you have: an image, source code, or a function.

| Option | What it does | Use it when |
|---|---|---|
| `docker run` with `-e PORT=8080` | Runs an image that you built, with the `PORT` variable that Cloud Run sets | You want to test the exact image |
| `gcloud beta code dev` (Beta) | Builds from a Dockerfile or with buildpacks, runs the service on a local port (`--local-port`), and rebuilds when a file changes | You want a fast edit and run loop in a terminal |
| Cloud Code Cloud Run Emulator | Builds and runs the service from the IDE, with environment variables and Cloud SQL connections, in watch mode | You develop in VS Code with Cloud Code |
| Functions Framework | Wraps one function in an HTTP server on port 8080 | You develop a Cloud Run function (formerly Cloud Functions) |

Sources: [Test a Cloud Run service locally](https://docs.cloud.google.com/run/docs/testing/local), [gcloud beta code dev](https://docs.cloud.google.com/sdk/gcloud/reference/beta/code/dev), [Develop a Cloud Run service locally in Cloud Code for VS Code](https://docs.cloud.google.com/code/docs/vscode/develop-service), [Local functions development](https://docs.cloud.google.com/run/docs/local-dev-functions).

A local container does not get the default service account of a Cloud Run service. With `gcloud beta code dev`, the `--application-default-credential` flag passes your Application Default Credentials (ADC) to the container. The `--service-account` flag downloads a service account key, and the docs call this a security risk ([Test a Cloud Run service locally](https://docs.cloud.google.com/run/docs/testing/local)). [Authenticating code to Google Cloud](note:1.2-authenticating-to-google-cloud) explains ADC.

The Functions Framework is open source. Cloud Run uses it to wrap deployed functions. The flags `--target` and `--signature-type` (`http` or `cloudevent`) select the function and its type. For an event-driven function, send a CloudEvent with `curl` and `ce-*` headers:

```bash
pip3 install functions-framework
functions-framework --target=YOUR_FUNCTION_NAME --signature-type=cloudevent

# In a second terminal: send a sample Pub/Sub event
curl localhost:8080 \
  -X POST \
  -H "Content-Type: application/json" \
  -H "ce-id: 123451234512345" \
  -H "ce-specversion: 1.0" \
  -H "ce-time: 2020-01-02T12:34:56.789Z" \
  -H "ce-type: google.cloud.pubsub.topic.v1.messagePublished" \
  -H "ce-source: //pubsub.googleapis.com/projects/MY-PROJECT/topics/MY-TOPIC" \
  -d '{"message": {"data": "d29ybGQ=", "attributes": {"attr1": "attr1-value"}},
       "subscription": "projects/MY-PROJECT/subscriptions/MY-SUB"}'
```

Source: [Local functions development](https://docs.cloud.google.com/run/docs/local-dev-functions).

The Pub/Sub `data` value is base64-encoded. The function must decode it ([Local functions development](https://docs.cloud.google.com/run/docs/local-dev-functions)).

## Unit tests, emulator tests, and integration tests

A test can call a fake input, an emulator, or a real service. Each level finds different problems.

| Test level | What the code under test talks to | What it finds | What it misses |
|---|---|---|---|
| Unit test | An event object or a mock that the test builds | Errors in your own logic | Errors in client library calls and service behavior |
| Emulator test | The real client library, connected to a local emulator | Errors in API calls and data handling | IAM, limits, manual indexes, and performance |
| Integration test | Real services in a test project | IAM, configuration, and service behavior | It needs a test project and cloud resources |

Sources: [Cloud Storage (2nd Gen) Unit Test](https://docs.cloud.google.com/functions/docs/samples/functions-cloudevent-storage-unit-test), [Pub/Sub integration tests](https://docs.cloud.google.com/functions/docs/samples/functions-pubsub-integration-test), [Use Firestore emulator locally](https://docs.cloud.google.com/firestore/native/docs/emulator), [Emulate Spanner locally](https://docs.cloud.google.com/spanner/docs/emulator).

The docs sample for a Cloud Storage event function builds a `CloudEvent` in the test and calls the function directly. No emulator or project is necessary:

```python
from cloudevents.http import CloudEvent
import main

def test_functions_eventsource_storage(capsys):
    attributes = {
        "id": "5e9f24a",
        "type": "google.cloud.storage.object.v1.finalized",
        "source": "sourceUrlHere",
    }
    data = {
        "bucket": "test_bucket_for_storage",
        "name": "new_blob_uploaded",
        "generation": 1,
        "metageneration": 1,
        "timeCreated": "2021-10-10 00:00:00.000000Z",
        "updated": "2021-11-11 00:00:00.000000Z",
    }
    event = CloudEvent(attributes, data)
    (event_id, event_type, bucket, name, metageneration,
     timeCreated, updated) = main.hello_gcs(event)
    assert "5e9f24a" in event_id
    assert "test_bucket_for_storage" in bucket
```

Source: [Cloud Storage (2nd Gen) Unit Test](https://docs.cloud.google.com/functions/docs/samples/functions-cloudevent-storage-unit-test).

The docs integration test for a Pub/Sub function goes one level up. It starts `functions-framework` as a subprocess and sends an HTTP request to it ([Pub/Sub integration tests](https://docs.cloud.google.com/functions/docs/samples/functions-pubsub-integration-test)). [Writing unit tests with AI coding assistants](note:2.3-unit-tests-with-ai) shows how to generate and review these tests.

## Exam traps

- **`gcloud pubsub topics create` against the emulator.** The Pub/Sub emulator does not support `gcloud pubsub` commands or the console. Create topics with a client library ([Testing apps locally with the emulator](https://docs.cloud.google.com/pubsub/docs/emulator)).
- **`gcloud emulators pubsub start` without `beta`.** The Pub/Sub, Bigtable, and Datastore emulators are only in the beta group ([gcloud emulators](https://docs.cloud.google.com/sdk/gcloud/reference/emulators)).
- **Old environment variables after a restart.** The Pub/Sub port can change at each start. Run `env-init` again ([Testing apps locally with the emulator](https://docs.cloud.google.com/pubsub/docs/emulator)).
- **"The tests pass on the emulator, so the indexes are correct."** The Firestore emulator in Native mode runs queries that need a missing manual index ([Use Firestore emulator locally](https://docs.cloud.google.com/firestore/native/docs/emulator)).
- **Testing IAM with an emulator.** The Spanner emulator has no IAM, and the Pub/Sub emulator does not support IAM operations ([Emulate Spanner locally](https://docs.cloud.google.com/spanner/docs/emulator), [Testing apps locally with the emulator](https://docs.cloud.google.com/pubsub/docs/emulator)).
- **The legacy Datastore emulator for Firestore in Datastore mode.** Its default eventual consistency does not match Datastore mode. Use the Firestore emulator with `--database-mode=datastore-mode` ([Running the Datastore Emulator](https://docs.cloud.google.com/datastore/docs/tools/datastore-emulator)).
- **A service account key for local runs.** `gcloud beta code dev --service-account` downloads a key. Use `--application-default-credential` ([Test a Cloud Run service locally](https://docs.cloud.google.com/run/docs/testing/local)).
- **An emulator in production.** The Firestore emulator is for local testing only and does not keep data across runs ([Use Firestore emulator locally](https://docs.cloud.google.com/firestore/native/docs/emulator)).
- **A missing variable in the test shell.** Without the emulator variable, the client library sends calls to the production service ([Testing apps locally with the emulator](https://docs.cloud.google.com/pubsub/docs/emulator)).
