## Why it matters

A design must exchange requests, events, files, and bulk data with systems that you do not control. The exam gives a constraint, such as a partner rate limit, a failure that must not spread, or a transfer deadline. You pick the integration style and the service that meets that constraint. Most wrong options are real products that do a different job.

## Key points

- Pub/Sub is an asynchronous messaging service. It decouples the services that produce messages from the services that process them, with latencies of typically about 100 milliseconds ([What is Pub/Sub?](https://docs.cloud.google.com/pubsub/docs/overview)).
- Pub/Sub uses implicit invocation: the publisher knows nothing about its subscribers. Cloud Tasks uses explicit invocation: the sender names the endpoint and keeps full control of execution ([Choosing Pub/Sub or Cloud Tasks](https://docs.cloud.google.com/pubsub/docs/choosing-pubsub-or-cloud-tasks)).
- Eventarc Standard routes events from a provider to a destination. Eventarc Advanced adds a central bus, many-to-many routing, and event transformation ([Eventarc overview](https://docs.cloud.google.com/eventarc/docs/overview)).
- In choreography, services react to events and no service controls the flow; Pub/Sub and Eventarc suit it. In orchestration, a central orchestrator controls the calls; Workflows suits it ([Service orchestration on Google Cloud](https://cloud.google.com/blog/topics/developers-practitioners/service-orchestration-google-cloud)).
- Use Application Integration to connect and map data between business systems. Use Workflows to orchestrate services. Use Managed Service for Apache Airflow (formerly Cloud Composer) for batch data pipelines ([Choose Workflows or Application Integration](https://docs.cloud.google.com/workflows/docs/choose-app-integ-or-workflows), [Choose Workflows or Managed Airflow](https://docs.cloud.google.com/workflows/docs/choose-orchestration), [Managed Service for Apache Airflow documentation](https://docs.cloud.google.com/composer/docs)).
- If your bandwidth can meet the project deadline, transfer online with `gcloud storage` or Storage Transfer Service. If it cannot, use Transfer Appliance ([Transfer your large datasets](https://docs.cloud.google.com/architecture/migration-to-google-cloud-transferring-your-large-datasets)).
- At 1 Gbps, an online transfer of 100 TB takes over 10 days. At 100 Mbps, it takes over 100 days ([Transfer your large datasets](https://docs.cloud.google.com/architecture/migration-to-google-cloud-transferring-your-large-datasets)).
- Inbound data transfer has no charge. Data transfer between zones, between regions, and to the internet has a charge ([Network pricing](https://cloud.google.com/vpc/network-pricing)).
- Cloud Interconnect and Peering can reduce egress costs. Cloud VPN by itself does not ([Cloud Interconnect overview](https://docs.cloud.google.com/network-connectivity/docs/interconnect/concepts/overview)).
- Process data where it already is, when you can. BigQuery Omni runs the BigQuery query engine in AWS and Azure, so you do not move the data ([Introduction to BigQuery Omni](https://docs.cloud.google.com/bigquery/docs/omni-introduction)).

## Synchronous calls or asynchronous messages

Choose the interaction style before you choose a product. The deciding question is: must the caller wait for the result?

| Criterion | Synchronous API call (REST, gRPC) | Asynchronous message or event |
|---|---|---|
| Caller needs the result now | Yes. Example: a price or stock check. | No. The caller continues without the result. |
| A receiver is slow or down | The caller waits or fails too. The failure can cascade. | Other services are not affected. The receiver can resume from the point of failure. |
| Traffic spikes | The receiver must scale for the peak. | The queue smooths the spike. |
| Number of receivers | One for each call | One (Cloud Tasks) or many (Pub/Sub, Eventarc) |
| Latency | Lowest for one request | Adds delivery time, typically about 100 ms for Pub/Sub |
| Tracing a flow | One request path | You track the flow with monitoring, not with code analysis. |

Sources: [What is Pub/Sub?](https://docs.cloud.google.com/pubsub/docs/overview), [Event-driven architectures](https://docs.cloud.google.com/eventarc/docs/event-driven-architectures), [Patterns for scalable and resilient apps](https://docs.cloud.google.com/architecture/scalable-and-resilient-apps), [Understand Cloud Tasks](https://docs.cloud.google.com/tasks/docs/dual-overview).

Two rules balance this table:

- The performance pillar asks for loosely coupled modules with clear interfaces, such as APIs and message queues. Calls between modules add latency, so tighter coupling can be right when performance is critical ([Promote modular design](https://docs.cloud.google.com/architecture/framework/performance-optimization/promote-modular-design)).
- Cloud Tasks guarantees delivery but not the timing of delivery. It is unsuitable when a user waits for the result ([Understand Cloud Tasks](https://docs.cloud.google.com/tasks/docs/dual-overview)).

When services call each other synchronously, use circuit breakers, exponential backoff, and graceful degradation to stop cascading failures ([Patterns for scalable and resilient apps](https://docs.cloud.google.com/architecture/scalable-and-resilient-apps)).

## Choose the messaging or event service

| Service | Use it when | Do not use it when |
|---|---|---|
| Pub/Sub | Many services react to the same message. You ingest event streams, distribute database change events, or spread tasks across many workers. | The sender must set the delivery rate or time, or must name one endpoint. |
| Cloud Tasks | The sender dispatches work to one handler and needs rate limits, scheduled delivery, retry control, or deduplication. Example: calls to a partner API with a rate limit. | Several consumers need the same message, or a user waits for the result. |
| Eventarc Standard | You route Google Cloud events, such as a Cloud Storage change or an audit log entry, to Cloud Run, Cloud Run functions (formerly Cloud Functions), or Workflows. | Events must cross projects or need transformation. |
| Eventarc Advanced | Many teams and projects share one bus. You filter on any attribute and transform events. | The workload needs the compliance standards that Eventarc Standard supports, or a dead-letter queue. |
| Cloud Scheduler | Work runs at fixed times. A job can start a workflow or publish a Pub/Sub message. | The work reacts to an event. |
| Managed Service for Apache Kafka | Existing Kafka applications must keep using Kafka. You pay for provisioned vCPU, RAM, and local storage. | The applications have no Kafka dependency. |

Sources: [Choosing Pub/Sub or Cloud Tasks](https://docs.cloud.google.com/pubsub/docs/choosing-pubsub-or-cloud-tasks), [What is Pub/Sub?](https://docs.cloud.google.com/pubsub/docs/overview), [Understand Cloud Tasks](https://docs.cloud.google.com/tasks/docs/dual-overview), [Eventarc overview](https://docs.cloud.google.com/eventarc/docs/overview), [Eventarc Advanced overview](https://docs.cloud.google.com/eventarc/advanced/docs/overview), [Service orchestration on Google Cloud](https://cloud.google.com/blog/topics/developers-practitioners/service-orchestration-google-cloud), [Managed Service for Apache Kafka overview](https://docs.cloud.google.com/managed-service-for-apache-kafka/docs/overview), [What is Apache Kafka?](https://cloud.google.com/learn/what-is-apache-kafka).

Eventarc Advanced has been GA since August 2025 ([Eventarc release notes](https://docs.cloud.google.com/eventarc/docs/release-notes)).

### Delivery rules that shape the design

- Pub/Sub and Cloud Tasks both give at-least-once delivery. Only Cloud Tasks deduplicates creation ([Choosing Pub/Sub or Cloud Tasks](https://docs.cloud.google.com/pubsub/docs/choosing-pubsub-or-cloud-tasks)). Make consumers idempotent, so that a repeated operation gives the same outcome ([What is microservices architecture?](https://cloud.google.com/learn/what-is-microservices-architecture)).
- Pub/Sub exactly-once delivery works only with pull subscriptions, and only when subscribers connect in the same region ([Exactly-once delivery](https://docs.cloud.google.com/pubsub/docs/exactly-once-delivery)).
- Pub/Sub keeps order only with ordering keys. Cloud Tasks keeps order only on a best-effort basis ([Choosing Pub/Sub or Cloud Tasks](https://docs.cloud.google.com/pubsub/docs/choosing-pubsub-or-cloud-tasks)).
- Pub/Sub can forward messages that subscribers cannot acknowledge to a dead-letter topic ([Dead-letter topics](https://docs.cloud.google.com/pubsub/docs/dead-letter-topics)).

## Orchestration or choreography

A business process usually spans several services. Google describes two ways to coordinate them.

| Question | Choreography | Orchestration |
|---|---|---|
| How do services interact? | Each service works independently and reacts to events. | A central orchestrator controls all interactions between the services. |
| Google Cloud services | Pub/Sub, Eventarc | Workflows |
| Main benefit | Services change and scale independently. There is no single point of failure. | A high-level view of the business process, to track execution and troubleshoot. |
| Main problem | Hard to monitor. Business logic spreads across services, with no central source of truth. | You must define the flow and its error handling in the workflow. |
| Where to prefer it | Between bounded contexts | Inside the bounded context of a microservice |

Source: [Service orchestration on Google Cloud](https://cloud.google.com/blog/topics/developers-practitioners/service-orchestration-google-cloud).

Most systems combine the two. An event can also start an orchestrated flow: a file upload to Cloud Storage triggers a workflow through Eventarc. The trigger is an event, but a workflow does the work ([Integrating Eventarc and Workflows](https://cloud.google.com/blog/topics/developers-practitioners/integrating-eventarc-and-workflows)).

A workflow can hold state, retry, poll, or wait for up to a year. With callbacks, it waits for another service to call it, without polling ([Workflows overview](https://docs.cloud.google.com/workflows/docs/overview)).

### Choose the orchestration or integration tool

| Need | Service | Why |
|---|---|---|
| Chain microservices and HTTP APIs; automate infrastructure tasks | Workflows | Serverless, millisecond latency, billed for each step, YAML or JSON syntax |
| Batch data pipelines (ETL, ELT) written as Python DAGs, with backfills | Managed Service for Apache Airflow (formerly Cloud Composer) | Built on Apache Airflow; provisioned capacity; seconds of latency between tasks |
| Connect, map, and transform data between business systems such as Salesforce, ServiceNow, or Cloud SQL | Application Integration with Integration Connectors | Integration Platform as a Service (iPaaS); drag-and-drop editor; little or no code |

Sources: [Choose Workflows or Managed Airflow](https://docs.cloud.google.com/workflows/docs/choose-orchestration), [Choose Workflows or Application Integration](https://docs.cloud.google.com/workflows/docs/choose-app-integ-or-workflows), [Application Integration overview](https://docs.cloud.google.com/application-integration/docs/overview).

Workflows has a connector to Application Integration, so you can use both together. For ETL and ELT pipelines, Google recommends Cloud Data Fusion ([Choose Workflows or Application Integration](https://docs.cloud.google.com/workflows/docs/choose-app-integ-or-workflows)). Pipeline services are in [Choosing data processing solutions](note:1.3-data-processing).

## API-led integration

Put an API layer in front of backend systems that many consumers call. Apigee puts an API proxy layer between clients and backend services. Policies on the proxy add security, traffic management, and data mediation, while the backend services stay unchanged ([What is Apigee?](https://docs.cloud.google.com/apigee/docs/api-platform/get-started/what-apigee)).

Apigee fits high API volumes, APIs for partners or third parties, developer portals, and monetization. API Gateway fits APIs for serverless backends on Google Cloud when consumers need no developer portal ([Choosing between Apigee, API Gateway, and Cloud Endpoints](https://cloud.google.com/blog/products/application-modernization/choosing-between-apigee-api-gateway-and-cloud-endpoints)). The full comparison is in [Advising teams: deployment, API management, and testing](note:5.1-deployment-and-apis). Private network paths to other environments are in [Hybrid and multicloud connectivity](note:2.1-hybrid-multicloud).

## File and batch exchange

Many external systems still exchange files. Use Cloud Storage as the landing zone, and add a managed service for each part of the exchange.

| Scenario | Pattern |
|---|---|
| Partners without a Google account upload or download files | Give each partner a signed URL. It gives time-limited access to one object. |
| Start processing when a file arrives | Pub/Sub notifications for Cloud Storage, or an Eventarc trigger, starts the processor or a workflow. |
| Recurring copies from Amazon S3, Azure Blob Storage, public URLs, or on-premises file systems | Storage Transfer Service on a schedule, with agents for file systems |
| A partner offers files on an SFTP server | Application Integration with the SFTP connector of Integration Connectors |
| Scheduled loads of SaaS or other-cloud data into BigQuery | BigQuery Data Transfer Service |
| Keep an analytics copy of an operational database current | Datastream change data capture (CDC) into BigQuery |

Sources: [Signed URLs](https://docs.cloud.google.com/storage/docs/access-control/signed-urls), [Pub/Sub notifications for Cloud Storage](https://docs.cloud.google.com/storage/docs/pubsub-notifications), [Storage Transfer Service](https://docs.cloud.google.com/storage-transfer/docs/overview), [SFTP connector](https://docs.cloud.google.com/integration-connectors/docs/connectors/sftp/configure), [BigQuery Data Transfer Service](https://docs.cloud.google.com/bigquery/docs/dts-introduction), [Datastream overview](https://docs.cloud.google.com/datastream/docs/overview), [Eventarc Standard overview](https://docs.cloud.google.com/eventarc/standard/docs/overview), [Transfer your large datasets](https://docs.cloud.google.com/architecture/migration-to-google-cloud-transferring-your-large-datasets).

## Move data: online or offline

Start with arithmetic. Transfer time depends on the dataset size, the available bandwidth, the management time, and the bandwidth efficiency.

| Dataset and link | Time |
|---|---|
| 1 GB at 1 Gbps | About 8 seconds in ideal conditions |
| 100 TB at 1 Gbps | About 12 days in ideal conditions |
| 100 TB at 100 Mbps | Over 100 days |
| 300 TB at 100 Mbps | About 9 months online. Transfer Appliance: capture in under 25 days, then data in Cloud Storage within about 10 more business days. |

Sources: [Transfer your large datasets](https://docs.cloud.google.com/architecture/migration-to-google-cloud-transferring-your-large-datasets), [Transfer Appliance](https://docs.cloud.google.com/transfer-appliance/docs/4.0/overview).

| Source of the data | Condition | Recommended product |
|---|---|---|
| Another cloud provider (Amazon S3, Azure Blob Storage) | Any size | Storage Transfer Service |
| Another Cloud Storage bucket | More than 1 TB | Storage Transfer Service |
| On-premises | Less than 1 TB | `gcloud storage` |
| On-premises | More than 1 TB, and the bandwidth meets the deadline | Storage Transfer Service with agents, or Transfer Appliance in online mode |
| On-premises | The bandwidth does not meet the deadline, or connectivity is poor | Transfer Appliance |

Sources: [Data transfer options](https://docs.cloud.google.com/storage-transfer/docs/transfer-options), [Transfer your large datasets](https://docs.cloud.google.com/architecture/migration-to-google-cloud-transferring-your-large-datasets).

Details that decide close questions (all from [Transfer your large datasets](https://docs.cloud.google.com/architecture/migration-to-google-cloud-transferring-your-large-datasets)):

- Storage Transfer Service stays under a bandwidth limit that you set, runs recurring transfers, and records every file that it moves.
- Transfer Appliance fits a remote site with little bandwidth, or bandwidth that you cannot get before the deadline. You must be able to receive and ship back Google-owned hardware, and it is available only in certain countries.
- Bandwidth bought only for a transfer can cost too much. When you count long-term use of Google Cloud, the investment can still be worthwhile.

Tool setup and database migration tools are in [Data and system migration tooling](note:5.1-migration-tooling).

## Move data: cost and latency

Every copy of data across a boundary costs money and time. Know which paths have a charge.

| Traffic path | Charge |
|---|---|
| Into Google Cloud | No charge for inbound data transfer. Resources that process it, such as load balancers and Cloud NAT, can charge. |
| VM to VM in the same zone, internal IP addresses | No charge |
| VM to VM in different zones of one region | Charge for each GiB |
| Between regions | Charge for each GiB. Traffic between continents usually costs more than traffic inside one continent. |
| To the internet | Internet data transfer rates |
| Reads from a regional Cloud Storage bucket in the same region | No outbound data transfer charge |
| Reads from a multi-region Cloud Storage bucket | Outbound data transfer charges always apply |

Sources: [Network pricing](https://cloud.google.com/vpc/network-pricing), [Bucket locations](https://docs.cloud.google.com/storage/docs/locations).

Large datasets are slow and costly to move, so design the processing around the data:

- Colocate compute with the data that it reads. Workloads that read a multi-region bucket can see variable performance, because storage and compute are not colocated ([Bucket locations](https://docs.cloud.google.com/storage/docs/locations)).
- In the analytics hybrid and multicloud pattern, transactional systems stay where they are. Raw data moves into Google Cloud for analysis ([Analytics hybrid and multicloud pattern](https://docs.cloud.google.com/architecture/hybrid-multicloud-patterns-and-practices/analytics-hybrid-multicloud-pattern)).
- BigQuery Omni can write results directly to Amazon S3 or Blob Storage, so the results do not cross clouds ([Introduction to BigQuery Omni](https://docs.cloud.google.com/bigquery/docs/omni-introduction)).
- Choose a region for low user latency, data-locality rules, and product availability ([Plan resource allocation](https://docs.cloud.google.com/architecture/framework/performance-optimization/plan-resource-allocation)).

## Data that changes during the move

A live system writes data while you move it. Google describes four approaches, and none is best for every case.

| Approach | Cut-over window | Who does most work | Use when |
|---|---|---|---|
| Scheduled maintenance (big bang) | Yes, planned | Operations | The workload can accept a cut-over window. |
| Continuous replication (trickle) | Short | Operations | A long window is not acceptable. |
| Y (writing and reading) | None | Development: many refactorings | Hard high-availability requirements |
| Data-access microservice | None | Development: one service | Microservices architectures, where it is the preferred option |

Source: [Transfer your large datasets](https://docs.cloud.google.com/architecture/migration-to-google-cloud-transferring-your-large-datasets). Migration methods are in [Planning a migration](note:1.4-migration-planning).

## AWS mapping

| AWS | Google Cloud | Difference that matters |
|---|---|---|
| Amazon SQS, Amazon SNS | Cloud Tasks or Pub/Sub | Google maps SQS and SNS to Cloud Tasks. Choose by invocation: Cloud Tasks when the sender controls delivery, Pub/Sub when many subscribers get each message. |
| Amazon Kinesis Data Streams | Pub/Sub | Pub/Sub leases single messages, not partitions, so parallelism does not depend on a partition count. |
| Amazon EventBridge | Eventarc | Standard routes a provider to a destination. Advanced adds a central bus. |
| AWS Step Functions | Workflows | YAML or JSON. A workflow can wait for up to a year. |
| Amazon Managed Workflows for Apache Airflow | Managed Service for Apache Airflow | For data pipelines, not low-latency service calls |
| Amazon AppFlow | Application Integration and Integration Connectors | An iPaaS with connectors and data mapping |
| AWS DataSync, AWS Snowball | Storage Transfer Service, Transfer Appliance | Transfer Appliance also has an online mode. |
| AWS Database Migration Service (CDC) | Datastream | Serverless CDC into BigQuery |

Sources: [Compare AWS and Azure services to Google Cloud](https://docs.cloud.google.com/docs/get-started/aws-azure-gcp-service-comparison), [Choosing Pub/Sub or Cloud Tasks](https://docs.cloud.google.com/pubsub/docs/choosing-pubsub-or-cloud-tasks), [What is Pub/Sub?](https://docs.cloud.google.com/pubsub/docs/overview), [Transfer Appliance](https://docs.cloud.google.com/transfer-appliance/docs/4.0/overview), [Eventarc overview](https://docs.cloud.google.com/eventarc/docs/overview), [Workflows overview](https://docs.cloud.google.com/workflows/docs/overview), [Choose Workflows or Managed Airflow](https://docs.cloud.google.com/workflows/docs/choose-orchestration), [Application Integration overview](https://docs.cloud.google.com/application-integration/docs/overview), [Datastream overview](https://docs.cloud.google.com/datastream/docs/overview).

## Exam traps

- **Pub/Sub for a partner API with a rate limit.** The sender must control the rate, so use Cloud Tasks. Managing third-party API call rates is a Cloud Tasks use case ([Understand Cloud Tasks](https://docs.cloud.google.com/tasks/docs/dual-overview)).
- **Cloud Tasks for fan-out.** Cloud Tasks has one handler for each task. Pub/Sub supports multiple subscribers for each message ([Choosing Pub/Sub or Cloud Tasks](https://docs.cloud.google.com/pubsub/docs/choosing-pubsub-or-cloud-tasks)).
- **Exactly-once delivery on a push subscription.** Push and export subscriptions do not support exactly-once delivery ([Exactly-once delivery](https://docs.cloud.google.com/pubsub/docs/exactly-once-delivery)).
- **Airflow for low-latency service orchestration.** Managed Airflow has seconds of latency between tasks. Workflows has millisecond latency and scales to zero ([Choose Workflows or Managed Airflow](https://docs.cloud.google.com/workflows/docs/choose-orchestration)).
- **Workflows to map data between SaaS business systems.** Application Integration connects and transforms data between business systems ([Choose Workflows or Application Integration](https://docs.cloud.google.com/workflows/docs/choose-app-integ-or-workflows)).
- **Pure choreography for a process that the business must track end to end.** Choreography has no central place to troubleshoot ([Service orchestration on Google Cloud](https://cloud.google.com/blog/topics/developers-practitioners/service-orchestration-google-cloud)).
- **An online transfer that cannot finish before the deadline.** Use Transfer Appliance. With enough bandwidth, use Storage Transfer Service for more than 1 TB ([Data transfer options](https://docs.cloud.google.com/storage-transfer/docs/transfer-options), [Transfer your large datasets](https://docs.cloud.google.com/architecture/migration-to-google-cloud-transferring-your-large-datasets)).
- **Cloud VPN to cut egress cost.** Cloud VPN by itself does not reduce egress costs ([Cloud Interconnect overview](https://docs.cloud.google.com/network-connectivity/docs/interconnect/concepts/overview)).
- **Eventarc Advanced in a regulated workload.** It does not comply with the certifications and standards that Eventarc Standard supports ([Eventarc Advanced overview](https://docs.cloud.google.com/eventarc/advanced/docs/overview)).
