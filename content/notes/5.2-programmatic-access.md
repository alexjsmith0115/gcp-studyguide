## Why it matters

Objective 5.2 tests whether you can pick the right tool and the right credential wherever people or code call Google Cloud APIs. A typical question describes a laptop, a CI runner, a production service, or a test suite, and asks for the Google-recommended approach. The wrong options usually work but break a best practice. Examples are a service account key, parsed default output, or retries without backoff.

## Key points

- Cloud Shell is for interactive use only. The default weekly quota is 50 hours, sessions end after 12 hours, and non-interactive sessions end after 40 minutes ([Cloud Shell quotas and limits](https://docs.cloud.google.com/shell/docs/quotas-limits)).
- A gcloud configuration is a named set of properties, such as the project and the account. You select one per command with `--configuration` or per terminal with `CLOUDSDK_ACTIVE_CONFIG_NAME` ([Managing gcloud CLI configurations](https://docs.cloud.google.com/sdk/docs/configurations)).
- `--impersonate-service-account` makes gcloud request short-lived credentials for a service account. The caller needs the Service Account Token Creator role on that service account ([Use service account impersonation](https://docs.cloud.google.com/docs/authentication/use-service-account-impersonation)).
- Application Default Credentials (ADC) looks in `GOOGLE_APPLICATION_CREDENTIALS`, then in the local file from `gcloud auth application-default login`, then at the attached service account ([How ADC works](https://docs.cloud.google.com/docs/authentication/application-default-credentials)).
- The gcloud CLI does not use ADC. `gcloud auth login` and `gcloud auth application-default login` give credentials to two different consumers ([Set up ADC](https://docs.cloud.google.com/docs/authentication/provide-credentials-adc), [Authenticate for the gcloud CLI](https://docs.cloud.google.com/sdk/docs/authenticate)).
- A standard API key associates a request with a project for billing and quota. It does not identify a principal, so IAM cannot authorize the request ([Manage API keys](https://docs.cloud.google.com/docs/authentication/api-keys)).
- Cloud Client Libraries are the recommended way to call Google Cloud APIs from code. Google API Client Libraries are the earlier type and support REST only ([Client libraries explained](https://docs.cloud.google.com/apis/docs/client-libraries-explained)).
- Retry only transient errors, such as HTTP 408, 429, and 5xx, with exponential backoff and jitter. Prefer the retry logic that is built into the client libraries ([Retry strategy](https://docs.cloud.google.com/storage/docs/retry-strategy)).
- The Pub/Sub, Firestore, Spanner, and Bigtable emulators run on your machine for development and tests. Each emulator has documented gaps, such as no IAM support in the Pub/Sub emulator ([Pub/Sub emulator](https://docs.cloud.google.com/pubsub/docs/emulator), [Firestore emulator](https://docs.cloud.google.com/firestore/native/docs/emulator), [Spanner emulator](https://docs.cloud.google.com/spanner/docs/emulator), [Bigtable emulator](https://docs.cloud.google.com/bigtable/docs/emulator)).

## Where to run commands and code

Match the tool to the job. Cloud Shell is a convenience for people, not a runtime for automation.

| Need | Use | Why |
|---|---|---|
| Quick administration from a browser | Cloud Shell | Google manages the VM and keeps the gcloud CLI, Docker, and other tools up to date. |
| Edit code in the browser | Cloud Shell Editor | Based on Code OSS, with Cloud Code built in. No custom extensions. |
| Build Kubernetes and Cloud Run apps in your IDE | Cloud Code for VS Code or IntelliJ | Run-ready samples, Skaffold support, debugging, and a local Cloud Run emulator. |
| A development environment in your VPC | Cloud Workstations | The Cloud Shell docs recommend it for more storage and no weekly usage limit. |
| Scheduled or pipeline automation | gcloud CLI or client libraries on the runner, with a service account identity | Cloud Shell is for interactive use only. |

Sources: [How Cloud Shell works](https://docs.cloud.google.com/shell/docs/how-cloud-shell-works), [Cloud Shell Editor interface overview](https://docs.cloud.google.com/shell/docs/editor-overview), [Cloud Code extensions](https://docs.cloud.google.com/code/docs), [Develop a Cloud Run service locally in Cloud Code for VS Code](https://docs.cloud.google.com/code/docs/vscode/develop-service), [Cloud Shell quotas and limits](https://docs.cloud.google.com/shell/docs/quotas-limits), [Authentication for Google Cloud APIs and services](https://docs.cloud.google.com/docs/authentication).

## Cloud Shell, Cloud Shell Editor, and Cloud Code

Cloud Shell gives each user a temporary VM that Google owns. The VM does not appear in any of your projects, and the environment is a Docker container on that VM ([How Cloud Shell works](https://docs.cloud.google.com/shell/docs/how-cloud-shell-works)). When you start it, Cloud Shell copies the active console project into your gcloud configuration and sets `GOOGLE_CLOUD_PROJECT` ([How Cloud Shell works](https://docs.cloud.google.com/shell/docs/how-cloud-shell-works)). It is not necessary to run `gcloud auth application-default login` in Cloud Shell ([Set up ADC for a local development environment](https://docs.cloud.google.com/docs/authentication/set-up-adc-local-dev-environment)).

| Behavior | What the docs say |
|---|---|
| Persistent storage | 5 GB in `$HOME`, per user, available across projects. You cannot expand it. |
| Unused `$HOME` | Cloud Shell deletes `$HOME` if you do not access Cloud Shell for 120 days. |
| Software outside `$HOME` | Lost when the VM ends. Install into `$HOME`, or use `$HOME/.customize_environment`, which runs as root once at VM boot. |
| Ephemeral mode | No persistent disk. The session starts faster, and all files are lost at session end. |
| gcloud properties | Stored in a temporary folder for the current Cloud Shell tab. They do not persist across sessions. |
| Usage | 50 hours per week by default, 12 hours per session, 40 minutes for non-interactive sessions. |

Sources: [How Cloud Shell works](https://docs.cloud.google.com/shell/docs/how-cloud-shell-works), [Configure Cloud Shell](https://docs.cloud.google.com/shell/docs/configuring-cloud-shell), [Use Cloud Shell](https://docs.cloud.google.com/shell/docs/using-cloud-shell), [Managing gcloud CLI configurations](https://docs.cloud.google.com/sdk/docs/configurations), [Cloud Shell quotas and limits](https://docs.cloud.google.com/shell/docs/quotas-limits).

Cloud Code adds IDE support for Kubernetes and Cloud Run apps in VS Code, IntelliJ, and Cloud Shell. It comes with the Gemini Code Assist extension ([Cloud Code extensions](https://docs.cloud.google.com/code/docs)).

## The gcloud CLI for people and scripts

**Configurations.** Create one configuration per project, account, or independent task. `gcloud config configurations activate` switches the active configuration. The `--configuration` flag changes it for one command, and `CLOUDSDK_ACTIVE_CONFIG_NAME` changes it for one terminal ([Managing gcloud CLI configurations](https://docs.cloud.google.com/sdk/docs/configurations)). The Spanner docs use a separate configuration with an endpoint override to switch between the emulator and production ([Emulate Spanner locally](https://docs.cloud.google.com/spanner/docs/emulator)).

**Impersonation.** Add `--impersonate-service-account=SA_EMAIL` to one command, or set the `auth/impersonate_service_account` property for all commands ([Use service account impersonation](https://docs.cloud.google.com/docs/authentication/use-service-account-impersonation)). Impersonation is more secure than a key: it needs a prior authenticated identity, and its credentials do not persist ([Use service account impersonation](https://docs.cloud.google.com/docs/authentication/use-service-account-impersonation)). For the access design, see [Secure remote and workload access](note:3.1-secure-access).

**Scripting.** The gcloud docs give clear rules for automation ([Scripting gcloud CLI commands](https://docs.cloud.google.com/sdk/docs/scripting-gcloud)):

| Do | Do not |
|---|---|
| Check the command exit status. | Depend on messages on standard error. Their wording can change. |
| Use `--format` (`json`, `yaml`, `csv`, `value`) and `--filter`. | Parse the default table output. It can change in a later release. |
| Disable prompts with `--quiet` or the `disable_prompts` property. | Run several gcloud commands in parallel. The CLI does not support it. |

Source: [Scripting gcloud CLI commands](https://docs.cloud.google.com/sdk/docs/scripting-gcloud).

**Release levels.** A default installation has only GA commands, and `alpha`, `beta`, and `preview` are separate components. Beta commands can have breaking changes without notice ([gcloud CLI overview](https://docs.cloud.google.com/sdk/gcloud)). Prefer GA commands in production automation.

**`gcloud storage`, gsutil, and bq.** gsutil does not support newer Cloud Storage features such as soft delete and managed folders. `gcloud storage` needs less manual tuning for the fastest transfers ([gsutil tool](https://docs.cloud.google.com/storage/docs/gsutil)). `bq` is the Python-based CLI for BigQuery. `bq query --dry_run` validates a query without running it, and `--nouse_legacy_sql` is required for GoogleSQL unless you set a default ([bq command-line tool reference](https://docs.cloud.google.com/bigquery/docs/reference/bq-cli-reference)).

## Authentication for code: use ADC

ADC is the strategy that the authentication libraries use to find credentials from the environment. The same code then runs on a laptop and in production without changes to how it authenticates ([How ADC works](https://docs.cloud.google.com/docs/authentication/application-default-credentials)).

| ADC checks | Contents | Typical use |
|---|---|---|
| 1. `GOOGLE_APPLICATION_CREDENTIALS` | A credential configuration file for Workload or Workforce Identity Federation, or a service account key (not recommended) | Workloads outside Google Cloud |
| 2. Local ADC file | Your user credentials, or credentials from an impersonated service account | Local development |
| 3. Metadata server | The service account attached to the resource | Production on Google Cloud (preferred) |

Sources: [How ADC works](https://docs.cloud.google.com/docs/authentication/application-default-credentials), [Set up ADC for on-premises or another cloud provider](https://docs.cloud.google.com/docs/authentication/set-up-adc-on-premises). The order does not rank the options by merit.

The authentication overview gives a decision flow for the credential itself:

| Where the code runs | Recommended credential |
|---|---|
| Single-user environment (workstation, Cloud Shell) | Your user credentials. If the use case needs a service account, impersonate it. |
| Google Cloud, not GKE | Attach a service account to the resource. |
| GKE | Workload Identity Federation for GKE. |
| On-premises or another cloud, with a supported identity provider | Workload Identity Federation. |
| None of the above | A service account key, managed with the key best practices. |

Source: [Authentication for Google Cloud APIs and services](https://docs.cloud.google.com/docs/authentication).

Google recommends that you avoid user-managed service account keys whenever possible. Organization policy constraints can block key creation, with exceptions only for projects that cannot use an alternative ([Best practices for managing service account keys](https://docs.cloud.google.com/iam/docs/best-practices-for-managing-service-account-keys)). A local ADC file contains a refresh token, so anyone with access to your file system can use it ([Set up ADC for a local development environment](https://docs.cloud.google.com/docs/authentication/set-up-adc-local-dev-environment)).

**API keys.** Use an API key only with an API that accepts keys ([Use API keys to access APIs](https://docs.cloud.google.com/docs/authentication/api-keys-use)). Restrict every key in two ways ([Manage API keys](https://docs.cloud.google.com/docs/authentication/api-keys)):

- API restrictions limit which APIs the key can call. The console and gcloud require at least one when you create a key. The REST API creates unrestricted keys unless you add one.
- Application restrictions limit the websites, IP addresses, or Android or iOS apps that can use the key.

Send the key in the `x-goog-api-key` header. The `key` query parameter puts the key in the URL, where URL scans can steal it ([Use API keys to access APIs](https://docs.cloud.google.com/docs/authentication/api-keys-use)). An authorization key is an API key bound to a service account. Do not use it in production for APIs that create or manage resources ([Manage API keys](https://docs.cloud.google.com/docs/authentication/api-keys)).

## Quotas and the quota project

Every API request counts against a quota, and Google Cloud enforces quotas by project ([Quota project overview](https://docs.cloud.google.com/docs/quotas/quota-project)). Which project pays the quota depends on the API type:

| API type | Quota project |
|---|---|
| Resource-based (for example, Compute Engine) | The project that contains the resource. You cannot change it. |
| Client-based (for example, Cloud Translation) | In order: the project set in the request, the API key's project, sometimes the gcloud shared project, the service account's project, or the workforce pool user project. If none applies, the request fails. |

Source: [Quota project overview](https://docs.cloud.google.com/docs/quotas/quota-project).

- Set the quota project with the `x-goog-user-project` header, the `GOOGLE_CLOUD_QUOTA_PROJECT` variable, `gcloud auth application-default set-quota-project`, or `--billing-project`. The principal needs `serviceusage.services.use` on that project ([Set the quota project](https://docs.cloud.google.com/docs/quotas/set-quota-project)).
- A rate quota resets after its time period. For an allocation quota, free resources or request an adjustment. System limits cannot change ([Cloud Quotas overview](https://docs.cloud.google.com/docs/quotas/overview)).
- Over quota, a REST request gets HTTP 429 and a gRPC request gets `ResourceExhausted`. Compute Engine usually returns HTTP 403 `QUOTA_EXCEEDED` instead, or `RATE_LIMIT_EXCEEDED` for a rate quota ([Troubleshoot quota errors](https://docs.cloud.google.com/docs/quotas/troubleshoot)).

## Retries with exponential backoff

Retry a failed request only when two things are true. The response shows a transient problem (HTTP 408, 429, 5xx, a socket timeout, or a TCP disconnect), and the request is idempotent ([Retry strategy](https://docs.cloud.google.com/storage/docs/retry-strategy)). Some requests are idempotent only with a precondition, such as `ifGenerationMatch` on a Cloud Storage write ([Retry strategy](https://docs.cloud.google.com/storage/docs/retry-strategy)).

| Anti-pattern | Result | Fix |
|---|---|---|
| Retry without backoff | Cascading failures | Exponential backoff with jitter |
| Retry non-idempotent operations | Duplicates or overwrites | Check idempotency, or handle duplicates |
| Retry permanent errors | Endless loops on authorization or invalid requests | Retry only transient errors |
| No retry limit | Resource exhaustion | Set a total retry duration or count |
| Retries in several layers | 3 app retries × 3 library retries = 9 attempts | Use and configure the built-in retries |

Source: [Retry strategy](https://docs.cloud.google.com/storage/docs/retry-strategy).

## Regional endpoints

The global endpoint (`SERVICE.googleapis.com`) ends TLS as close to the client as possible. It gives no regional isolation and no data residency ([Google Cloud API endpoint overview](https://docs.cloud.google.com/docs/security/compliance/endpoints)). A regional endpoint (`SERVICE.REGION.rep.googleapis.com`) processes the request and ends TLS in the named region. Multi-regional endpoints do the same for a jurisdiction such as the EU ([Google Cloud API endpoint overview](https://docs.cloud.google.com/docs/security/compliance/endpoints)).

All facts in this list come from [Regional and multi-regional API endpoints](https://docs.cloud.google.com/docs/security/compliance/about-regional-endpoints) and [Google Cloud API endpoint overview](https://docs.cloud.google.com/docs/security/compliance/endpoints):

- Use them when data in transit must stay in a region, when auditors need evidence of regional handling, or for regional failure isolation.
- Private Google Access cannot reach them. For private access, use Private Service Connect endpoints (`.p.rep.googleapis.com`).
- Only some services support them. Many services do not support cross-region operations through them, and latency can be higher.
- To enforce them, deny global endpoints with `constraints/gcp.restrictEndpointUsage`. Add `constraints/gcp.resourceLocations` for data at rest.

For Private Service Connect design, see [Access to Google APIs, the internet, and cloud-adjacent services](note:2.1-vpc-access-patterns). For residency requirements, see [Designing for compliance](note:3.2-compliance).

## Client libraries, REST, and gRPC

| Option | Interface | Use when |
|---|---|---|
| Cloud Client Libraries (recommended) | Idiomatic code. Some libraries use gRPC for better performance. | First choice, if a library exists for your language and API |
| Google API Client Libraries | REST only. Generated code that can be less idiomatic. | No Cloud Client Library exists, or an existing project already uses them |
| Your own REST client | JSON over HTTP. Every Google Cloud API has it. | You have a special need and an HTTP client |
| Your own gRPC client | Protocol buffers over HTTP/2, generated from the API's service definition | The API is gRPC-enabled, and Cloud Client Libraries do not meet your needs |

Source: [Client libraries and Cloud APIs explained](https://docs.cloud.google.com/apis/docs/client-libraries-explained).

gRPC can increase throughput per CPU by as much as ten times compared with the JSON REST API ([Client libraries explained](https://docs.cloud.google.com/apis/docs/client-libraries-explained)). Both library types handle authentication ([Client libraries explained](https://docs.cloud.google.com/apis/docs/client-libraries-explained)), and both get credentials from ADC ([How ADC works](https://docs.cloud.google.com/docs/authentication/application-default-credentials)).

## Emulators

Emulators let you develop and test an application on your local machine ([Pub/Sub emulator](https://docs.cloud.google.com/pubsub/docs/emulator), [Spanner emulator](https://docs.cloud.google.com/spanner/docs/emulator)). They do not replace a test stage in a real project: test IAM, indexes, limits, and performance there ([Firestore emulator](https://docs.cloud.google.com/firestore/native/docs/emulator), [Spanner emulator](https://docs.cloud.google.com/spanner/docs/emulator)).

| Emulator | Start command (release level) | Client variable | Gaps to know |
|---|---|---|---|
| Pub/Sub | `gcloud beta emulators pubsub start` (beta) | `PUBSUB_EMULATOR_HOST` | Client libraries only: no console and no `gcloud pubsub`. No IAM. No configurable retention. BigQuery subscriptions do not send messages. |
| Firestore | `gcloud emulators firestore start` (GA) | `FIRESTORE_EMULATOR_HOST` | In memory. Simple locking instead of production transaction behavior. No composite index tracking. Not all production limits. |
| Spanner | `gcloud emulators spanner start` (GA) | `SPANNER_EMULATOR_HOST` | In memory. No TLS, authentication, IAM, or audit logging. Performance does not compare. Read-write transactions lock the whole database. |
| Bigtable | `gcloud beta emulators bigtable start` (beta) | `BIGTABLE_EMULATOR_HOST` | In memory. No instance or cluster admin API. No secure connection. Not in the HBase shell. |

Sources: [Pub/Sub emulator](https://docs.cloud.google.com/pubsub/docs/emulator), [Firestore emulator](https://docs.cloud.google.com/firestore/native/docs/emulator), [Spanner emulator](https://docs.cloud.google.com/spanner/docs/emulator), [Bigtable emulator](https://docs.cloud.google.com/bigtable/docs/emulator).

- For the Pub/Sub emulator, set the variables again each time you start it, because the port can change. Unset them after you stop it ([Pub/Sub emulator](https://docs.cloud.google.com/pubsub/docs/emulator)).
- For Firestore in Datastore mode, use `gcloud emulators firestore start --database-mode=datastore-mode`, not the legacy Datastore emulator ([Running the Datastore Emulator](https://docs.cloud.google.com/datastore/docs/tools/datastore-emulator)).

For test strategy, see [Testing, validation, and root cause analysis](note:4.1-testing-and-troubleshooting).

## Exam traps

- **"Create a service account key for the developer or the CI job."** Local code should use user credentials or impersonation through ADC. Workloads on Google Cloud use an attached service account, and external workloads use Workload Identity Federation ([Authentication for Google Cloud APIs and services](https://docs.cloud.google.com/docs/authentication)).
- **"Run the nightly job from Cloud Shell."** Cloud Shell is for interactive use only, and non-interactive sessions end after 40 minutes ([Cloud Shell quotas and limits](https://docs.cloud.google.com/shell/docs/quotas-limits)).
- **"Run `gcloud auth login` so that the local app can authenticate."** Client libraries use ADC, and gcloud credentials are not ADC credentials. Run `gcloud auth application-default login` ([Set up ADC](https://docs.cloud.google.com/docs/authentication/provide-credentials-adc), [How ADC works](https://docs.cloud.google.com/docs/authentication/application-default-credentials)).
- **"Protect the admin API with an API key."** A standard API key identifies no principal, so IAM cannot authorize the caller ([Manage API keys](https://docs.cloud.google.com/docs/authentication/api-keys)).
- **"Parse the default gcloud output" or "run gcloud commands in parallel."** Use `--format`, `--filter`, and exit codes. Parallel gcloud execution is not supported ([Scripting gcloud CLI commands](https://docs.cloud.google.com/sdk/docs/scripting-gcloud)).
- **"Add an application retry loop around each client call."** Layered retries multiply attempts. Configure the built-in retries instead ([Retry strategy](https://docs.cloud.google.com/storage/docs/retry-strategy)).
- **"The emulator tests passed, so IAM and indexes are correct."** The Pub/Sub emulator does not support IAM, and the Firestore emulator does not track composite indexes ([Pub/Sub emulator](https://docs.cloud.google.com/pubsub/docs/emulator), [Firestore emulator](https://docs.cloud.google.com/firestore/native/docs/emulator)).
- **"Reach the regional endpoint through Private Google Access."** Regional endpoints need Private Service Connect for private access ([Regional and multi-regional API endpoints](https://docs.cloud.google.com/docs/security/compliance/about-regional-endpoints)).
- **"Write the new script with gsutil."** gsutil is legacy and leaves the gcloud CLI package after March 2027 ([gsutil tool](https://docs.cloud.google.com/storage/docs/gsutil)).
