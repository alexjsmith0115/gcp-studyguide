## Why it matters

An exam question gives a source, such as VMware VMs, a MySQL database, or 500 TB of files. It adds a constraint, such as downtime, bandwidth, or skills. Then it asks for the Google tool. Most wrong answers use a real tool for the wrong source or target, or move data over a network that is too slow. Learn the source-to-target map and the size thresholds.

## Key points

- Migrate to Virtual Machines (formerly Migrate for Compute Engine) moves VMs from vSphere, AWS, Azure, and VMware Engine to Compute Engine ([Migrate to Virtual Machines architecture](https://docs.cloud.google.com/migrate/virtual-machines/docs/5.0/discover/architecture), [Migrate to Virtual Machines release notes](https://docs.cloud.google.com/migrate/virtual-machines/docs/5.0/resources/release-notes)).
- Migrate to Virtual Machines replicates disks while the source runs, supports test clones, and needs only a short cutover downtime ([VM migration process](https://docs.cloud.google.com/migrate/virtual-machines/docs/5.0/discover/lifecycle)).
- Google Cloud VMware Engine includes VMware HCX, so you can move VMware VMs and keep your VMware tools and processes ([VMware Engine overview](https://docs.cloud.google.com/vmware-engine/docs/overview)).
- Migrate to Containers (formerly Migrate for Anthos and GKE) moves workloads from VMs into containers on GKE or Cloud Run ([Migrate to Containers overview](https://docs.cloud.google.com/migrate/containers/docs/getting-started), [Migrate to Containers release notes](https://docs.cloud.google.com/migrate/containers/docs/release-notes)).
- Database Migration Service migrates databases into Cloud SQL and AlloyDB for PostgreSQL, with continuous replication for minimal downtime ([Database Migration Service overview](https://docs.cloud.google.com/database-migration/docs/overview)).
- Datastream is a serverless change data capture (CDC) service that replicates operational databases into BigQuery or Cloud Storage ([Datastream overview](https://docs.cloud.google.com/datastream/docs/overview)).
- BigQuery Migration Service assesses a data warehouse, translates its SQL, and transfers its data to BigQuery ([Introduction to BigQuery migration](https://docs.cloud.google.com/bigquery/docs/migration-intro)).
- From on-premises, use `gcloud storage` below 1 TB, and Storage Transfer Service or Transfer Appliance above 1 TB ([Data transfer options](https://docs.cloud.google.com/storage-transfer/docs/transfer-options)).
- Transfer Appliance is a good fit when an upload over the network would take more than one week ([Transfer Appliance](https://docs.cloud.google.com/transfer-appliance/docs/4.0/overview)).

## Choose the tool from the source and the target

| Source | Target | Tool |
|---|---|---|
| VMs on vSphere, AWS, Azure, or VMware Engine | Compute Engine | Migrate to Virtual Machines |
| Virtual disk images (VMDK, VHD, VHDX, QCOW2, and others) | Compute Engine image | Migrate to Virtual Machines image import |
| Physical servers or non-vSphere hypervisors | Compute Engine | Image import for virtual disks, or third-party tools that Google lists, such as RackWare or SUREedge |
| On-premises VMware VMs that stay on VMware | VMware Engine | VMware HCX |
| Applications on VMs (Tomcat, JBoss, WebSphere, IIS, Linux) | GKE or Cloud Run | Migrate to Containers |
| MySQL, PostgreSQL, or SQL Server | Cloud SQL or AlloyDB for PostgreSQL | Database Migration Service (homogeneous) |
| Oracle or SQL Server | Cloud SQL for PostgreSQL or AlloyDB for PostgreSQL | Database Migration Service (heterogeneous) |
| Operational databases | BigQuery or Cloud Storage, in near real time | Datastream |
| Data warehouses (Teradata, Redshift, Snowflake, and others) | BigQuery | BigQuery Migration Service with BigQuery Data Transfer Service |
| Amazon S3, Azure Blob Storage, HTTP URLs, HDFS, or file systems | Cloud Storage | Storage Transfer Service |
| Large on-premises datasets with limited bandwidth | Cloud Storage | Transfer Appliance |

Sources: [Migrate to Virtual Machines architecture](https://docs.cloud.google.com/migrate/virtual-machines/docs/5.0/discover/architecture), [Import virtual disk images](https://docs.cloud.google.com/migrate/virtual-machines/docs/5.0/migrate/image_import), [Migration tools](https://docs.cloud.google.com/migration-center/docs/migration-modernization-tools), [Migrate to Containers overview](https://docs.cloud.google.com/migrate/containers/docs/getting-started), [Database Migration Service overview](https://docs.cloud.google.com/database-migration/docs/overview), [Datastream overview](https://docs.cloud.google.com/datastream/docs/overview), [Introduction to BigQuery migration](https://docs.cloud.google.com/bigquery/docs/migration-intro), [Storage Transfer Service](https://docs.cloud.google.com/storage-transfer/docs/overview), [Transfer your large datasets](https://docs.cloud.google.com/architecture/migration-to-google-cloud-transferring-your-large-datasets).

The migration type from [Planning a migration](note:1.4-migration-planning) narrows the choice. Google lists Migrate to Virtual Machines and VMware HCX for lift and shift. It lists Migrate to Containers, Datastream, and Database Migration Service for replatform ([Migration tools](https://docs.cloud.google.com/migration-center/docs/migration-modernization-tools)).

## Migrate to Virtual Machines

Migrate to Virtual Machines is a lift-and-shift tool. It runs in phases ([VM migration process](https://docs.cloud.google.com/migrate/virtual-machines/docs/5.0/discover/lifecycle)):

1. **Onboard.** Select the source VMs. For vSphere, you install the Migrate Connector in the data center ([Prepare a VMware source](https://docs.cloud.google.com/migrate/virtual-machines/docs/5.0/migrate/create-a-vmware-source)).
2. **Replicate.** The first replication copies a snapshot of the disks. Incremental replications follow every two hours by default. The source VM keeps running.
3. **Set target details.** Choose the project, machine type, and network. You can change them at any time.
4. **Test-clone.** Create a Compute Engine clone from the latest replicated data. Test it in an isolated sandbox, because the source VM still runs.
5. **Cut over.** The tool stops the source VM, runs a final replication, and creates the production instance. Plan a maintenance window for the short downtime.
6. **Finalize.** Delete the replication data. You pay for its storage until you finalize.

Source: [VM migration process](https://docs.cloud.google.com/migrate/virtual-machines/docs/5.0/discover/lifecycle).

Other facts to know:

- Migrate to Virtual Machines adapts the OS for Google Cloud. For example, it adapts network settings and deploys the Compute Engine agent ([VM migration process](https://docs.cloud.google.com/migrate/virtual-machines/docs/5.0/discover/lifecycle)).
- Rollback is manual. You delete the new VM, start the source VM, and redirect traffic. Data written to the new VM is not copied back ([VM migration process](https://docs.cloud.google.com/migrate/virtual-machines/docs/5.0/discover/lifecycle)).
- Target details support sole-tenant node affinity labels for BYOL workloads ([Migrate individual VMs](https://docs.cloud.google.com/migrate/virtual-machines/docs/5.0/migrate/migrating-vms), [Sole-tenancy overview](https://docs.cloud.google.com/compute/docs/nodes/sole-tenant-nodes)).
- Google recommends separate target projects for test VMs and production VMs ([Migrate to Virtual Machines architecture](https://docs.cloud.google.com/migrate/virtual-machines/docs/5.0/discover/architecture)).
- The service itself has no charge. You pay for test-clone and cutover VMs, storage, and networking. AWS and Azure also charge for the temporary resources on their side ([Migrate to Virtual Machines pricing](https://cloud.google.com/migrate/virtual-machines/pricing)).

## VMware Engine and HCX

Google Cloud VMware Engine runs the VMware platform (vSphere, vCenter, vSAN, NSX, and HCX) on Google Cloud bare-metal infrastructure. Teams keep their VMware tools, skills, and processes ([VMware Engine overview](https://docs.cloud.google.com/vmware-engine/docs/overview)).

VMware HCX presents on-premises and cloud vSphere resources as one continuous resource. It supports live, cold, and bulk migration. You connect the environments with Cloud VPN or Cloud Interconnect. VMware Engine deploys HCX automatically when it creates the private cloud ([Use VMware HCX to migrate VMware VMs](https://docs.cloud.google.com/vmware-engine/docs/workloads/howto-migrate-vms-using-hcx)). Other options include backup restores, VMware PowerCLI, and NSX Layer 2 VPN. For vMotion, the on-premises vMotion network must support routing ([Workload VM migration](https://docs.cloud.google.com/vmware-engine/docs/concepts-migration-options)).

| Requirement | Migrate to Virtual Machines | VMware Engine with HCX |
|---|---|---|
| Target | Compute Engine VMs | VMware VMs in a private cloud |
| VM format | Adapted to run natively on Compute Engine | Unchanged VMware VMs |
| Operations model | Google Cloud tools | Your existing VMware tools and processes |
| Good for | Rehost now, then use managed services | Fast data center exit with no change to operations |

Sources: [VM migration process](https://docs.cloud.google.com/migrate/virtual-machines/docs/5.0/discover/lifecycle), [VMware Engine overview](https://docs.cloud.google.com/vmware-engine/docs/overview), [Google Cloud VMware Engine](https://cloud.google.com/vmware-engine), [Migrate to Google Cloud: Get started](https://docs.cloud.google.com/architecture/migration-to-gcp-getting-started).

VMware Engine networking is in [Configuring serverless and VMware Engine networking](note:2.3-serverless).

## Migrate to Containers

Migrate to Containers moves workloads from VMs on VMware or Compute Engine into containers on GKE, GKE Autopilot, or Cloud Run. It supports IBM WebSphere, JBoss, Apache, Tomcat, WordPress, Windows IIS, and Linux applications. Its CLI runs on your local machine. Its offline mode migrates Linux workloads without pulling resources from the internet ([Migrate to Containers overview](https://docs.cloud.google.com/migrate/containers/docs/getting-started)).

| Good fit | Not a good fit |
|---|---|
| Web and application servers, business logic middleware such as Tomcat | High-performance and large in-memory databases |
| Multi-VM, multi-tier stacks such as LAMP | VMs with special kernel drivers, such as kernel-mode NFS |
| Small and medium databases such as MySQL and PostgreSQL | Dependencies on specific hardware, or licenses tied to hardware IDs |
| Low duty-cycle, bursty workloads, and test or training labs | Windows: GPU or TPU dependencies, desktop and VDI applications, BYOL applications |

Source: [Migrate to Containers planning best practices](https://docs.cloud.google.com/migrate/containers/docs/planning-best-practices).

## Database Migration Service

Database Migration Service (DMS) manages the initial snapshot and the ongoing replication ([Database Migration Service overview](https://docs.cloud.google.com/database-migration/docs/overview)).

| Migration type | How it works | Downtime |
|---|---|---|
| One-time | A dump and load of a single point-in-time snapshot. No new writes are allowed during the migration. | The whole migration |
| Continuous | A full dump and load, then CDC replication until you switch. | Minimal |

Source: [Database Migration Service overview](https://docs.cloud.google.com/database-migration/docs/overview).

| Path | Supported routes |
|---|---|
| Homogeneous | MySQL to Cloud SQL for MySQL. PostgreSQL to Cloud SQL for PostgreSQL or AlloyDB. SQL Server to Cloud SQL for SQL Server. |
| Heterogeneous | Oracle or SQL Server to Cloud SQL for PostgreSQL or AlloyDB for PostgreSQL. |

Sources: [Homogeneous migrations](https://docs.cloud.google.com/database-migration/docs/homogeneous-migrations), [Heterogeneous migrations](https://docs.cloud.google.com/database-migration/docs/heterogeneous-migrations).

Details that decide questions:

- MySQL sources include Amazon RDS, Amazon Aurora, Azure Database for MySQL, Cloud SQL, and self-managed MySQL. DMS is not compatible with MariaDB ([Supported source and destination databases](https://docs.cloud.google.com/database-migration/docs/mysql/migration-src-and-dest)).
- SQL Server to Cloud SQL uses backup and restore. For self-managed and Amazon RDS sources, you upload full backups and transaction log files to a Cloud Storage bucket, and DMS replicates from there ([Database Migration Service for SQL Server](https://docs.cloud.google.com/database-migration/docs/sqlserver/scenario-overview)).
- Heterogeneous migrations use a conversion workspace to convert the schema and code, with Gemini-assisted conversion ([Database Migration Service overview](https://docs.cloud.google.com/database-migration/docs/overview)).
- The cutover is called promotion. Stop all writes to the source, wait until the replication delay is zero, and then promote. You cannot undo a promotion ([Promote a migration](https://docs.cloud.google.com/database-migration/docs/mysql/promote-migration)).
- DMS does not support dual writes to the source and the destination ([Database Migration Service overview](https://docs.cloud.google.com/database-migration/docs/overview)).

Database configuration after the move is in [Configuring databases](note:2.2-database-config).

## Datastream

Datastream replicates changes from MySQL, Oracle, PostgreSQL, SQL Server, MongoDB, and Spanner into BigQuery. It can also write the change stream to Cloud Storage. Dataflow templates can then load the data into Cloud SQL or Spanner ([Datastream overview](https://docs.cloud.google.com/datastream/docs/overview)). It is serverless. Private connectivity configurations connect it to private sources through VPC peering ([Datastream overview](https://docs.cloud.google.com/datastream/docs/overview)).

Use DMS to move an operational database to a new primary database ([Database Migration Service overview](https://docs.cloud.google.com/database-migration/docs/overview)). Use Datastream to keep a copy of operational data in BigQuery for analytics, or to synchronize data during a hybrid period ([Datastream overview](https://docs.cloud.google.com/datastream/docs/overview)).

## Data warehouse migration

BigQuery Migration Service covers assessment, SQL translation, and data transfer. It supports Amazon Redshift, Hadoop and Hive, Apache Spark, IBM Netezza, Oracle, Snowflake, and Teradata. The Migration API has no charge ([Introduction to BigQuery migration](https://docs.cloud.google.com/bigquery/docs/migration-intro)).

- **SQL translation.** The batch SQL translator, the interactive SQL translator, and the translation API convert SQL into GoogleSQL ([Introduction to BigQuery migration](https://docs.cloud.google.com/bigquery/docs/migration-intro)). For new batch translations, Google recommends the BigQuery Migration API ([Batch SQL translator](https://docs.cloud.google.com/bigquery/docs/batch-sql-translator)).
- **Data transfer.** BigQuery Data Transfer Service loads data into BigQuery on a schedule. It cannot move data out of BigQuery ([BigQuery Data Transfer Service](https://docs.cloud.google.com/bigquery/docs/dts-introduction)).
- **Teradata.** A migration agent in your environment works with the BigQuery Data Transfer Service to copy schema and data ([Teradata migration overview](https://docs.cloud.google.com/bigquery/docs/migration/teradata-overview)).

Data processing choices are in [Choosing data processing solutions](note:1.3-data-processing).

## Moving files and objects

| Scenario | Recommendation |
|---|---|
| From another cloud storage provider | Storage Transfer Service |
| Less than 1 TB from on-premises | `gcloud storage` |
| More than 1 TB from on-premises | Storage Transfer Service or Transfer Appliance |
| Poor or no internet connectivity | Transfer Appliance |

Source: [Data transfer options](https://docs.cloud.google.com/storage-transfer/docs/transfer-options).

Transfer time is the deciding number. Ideally, 1 GB takes eight seconds over a 1 Gbps network. At 1 Gbps, 100 TB takes over 10 days online. At 100 Mbps, it takes over 100 days, and an offline transfer is worth considering ([Transfer your large datasets](https://docs.cloud.google.com/architecture/migration-to-google-cloud-transferring-your-large-datasets)). The docs show more sizes and bandwidths in a chart on the same page.

### Storage Transfer Service

- Sources include Amazon S3, Azure Blob Storage, Cloud Storage, file systems, HTTP and HTTPS URLs, and HDFS. It is optimized for more than 1 TiB ([Storage Transfer Service](https://docs.cloud.google.com/storage-transfer/docs/overview)).
- For file systems, you install agents in Docker containers on machines that mount the NFS data ([Data transfer options](https://docs.cloud.google.com/storage-transfer/docs/transfer-options)). More agents give more speed, and a bandwidth cap protects other workloads ([Transfer your large datasets](https://docs.cloud.google.com/architecture/migration-to-google-cloud-transferring-your-large-datasets)).
- Event-driven transfers copy new and updated objects from S3, Azure, or Cloud Storage in near real time. They do not copy deletions ([Event-driven transfers](https://docs.cloud.google.com/storage-transfer/docs/event-driven-transfers)).
- A Google-managed private network for S3 transfers removes AWS internet egress charges. You pay a per-GiB processing rate to Google instead ([Transfer over a Google-managed private network](https://docs.cloud.google.com/storage-transfer/docs/create-transfers/agentless/managed-private-network)).
- Storage Transfer Service has no SLA ([Storage Transfer Service](https://docs.cloud.google.com/storage-transfer/docs/overview)).

### Transfer Appliance

Google ships an appliance to you. You copy data to it over NFS (Linux and macOS) or SCP (Windows), and ship it back. Google uploads the data to Cloud Storage and then wipes the appliance. Data is encrypted with AES-256 and customer-managed keys. Online mode streams the copied data to Cloud Storage without waiting for shipment ([Transfer Appliance](https://docs.cloud.google.com/transfer-appliance/docs/4.0/overview)). One appliance holds up to 300 TB of encrypted data, and you can order several ([Transfer Appliance specifications](https://docs.cloud.google.com/transfer-appliance/docs/4.0/specifications), [Transfer Appliance](https://docs.cloud.google.com/transfer-appliance/docs/4.0/overview)).

### `gcloud storage`

`gcloud storage` is the standard tool for small to medium transfers. It suits on-demand transfers, a few files, and streamed program output ([Transfer your large datasets](https://docs.cloud.google.com/architecture/migration-to-google-cloud-transferring-your-large-datasets)). `gsutil` is the legacy tool ([gsutil tool](https://docs.cloud.google.com/storage/docs/gsutil)); see [Programmatic access](note:5.2-programmatic-access).

## Exam traps

- **Transfer Appliance when the network is fast enough.** It is a good fit when an online upload would take more than one week ([Transfer Appliance](https://docs.cloud.google.com/transfer-appliance/docs/4.0/overview)).
- **`gcloud storage` for hundreds of terabytes.** Above 1 TB from on-premises, use Storage Transfer Service or Transfer Appliance ([Data transfer options](https://docs.cloud.google.com/storage-transfer/docs/transfer-options)).
- **Storage Transfer Service for NFS without agents.** File system transfers need agents in your data center ([Data transfer options](https://docs.cloud.google.com/storage-transfer/docs/transfer-options)).
- **DMS for MariaDB.** DMS is not compatible with MariaDB ([Supported source and destination databases](https://docs.cloud.google.com/database-migration/docs/mysql/migration-src-and-dest)).
- **DMS into BigQuery or Spanner.** DMS targets Cloud SQL and AlloyDB for PostgreSQL. Datastream feeds BigQuery ([Database Migration Service overview](https://docs.cloud.google.com/database-migration/docs/overview), [Datastream overview](https://docs.cloud.google.com/datastream/docs/overview)).
- **Promotion before replication catches up.** Stop writes and wait for zero replication delay, or you can lose data ([Promote a migration](https://docs.cloud.google.com/database-migration/docs/mysql/promote-migration)).
- **Migrate to Containers for large in-memory databases or Windows apps that need GPUs.** These are not a good fit ([Migrate to Containers planning best practices](https://docs.cloud.google.com/migrate/containers/docs/planning-best-practices)).
- **Automatic rollback in Migrate to Virtual Machines.** Rollback is manual, and new data is not copied back ([VM migration process](https://docs.cloud.google.com/migrate/virtual-machines/docs/5.0/discover/lifecycle)).
- **Converting VMs when teams must keep VMware operations.** Use VMware Engine with HCX ([VMware Engine overview](https://docs.cloud.google.com/vmware-engine/docs/overview)).
