## Why it matters

A storage question gives you a workload and one or two hard constraints. Typical constraints are the access protocol, the data model, global writes, latency, and operational overhead. You must first choose the storage type (object, block, file, or database), and then the product. The wrong options are usually real products that break one stated constraint. Examples are Filestore for an SMB share, Cloud SQL for global writes, and Local SSD for data that must survive a VM stop.

## Key points

- For storage with unlimited scale and global availability, use Cloud Storage. Choose the storage class from the access frequency and the retention time ([Design an optimal storage strategy for your cloud workload](https://docs.cloud.google.com/architecture/storage-advisor)).
- Google recommends Hyperdisk for block storage. Persistent Disk is not available with the latest machine series ([Choose a disk type](https://docs.cloud.google.com/compute/docs/disks)).
- Hyperdisk performance is independent of the provisioned capacity. To get more Persistent Disk performance, you must increase the disk size ([Choose a disk type](https://docs.cloud.google.com/compute/docs/disks)).
- Local SSD is for scratch data and caches only. You cannot back it up with snapshots, clones, machine images, or images ([About Local SSD disks](https://docs.cloud.google.com/compute/docs/disks/local-ssd)).
- For NFS with regional availability, use Filestore Regional. For SMB, use NetApp Volumes. For a parallel file system for AI, ML, and HPC, use Managed Lustre ([Design an optimal storage strategy for your cloud workload](https://docs.cloud.google.com/architecture/storage-advisor)).
- AlloyDB is PostgreSQL-compatible. Its columnar engine runs analytical queries on live transactional data (HTAP) ([AlloyDB overview](https://docs.cloud.google.com/alloydb/docs/overview)).
- Spanner scales horizontally and gives external consistency by default. Multi-region configurations have a 99.999% SLA ([Spanner](https://cloud.google.com/spanner), [Regional, dual-region, and multi-region configurations](https://docs.cloud.google.com/spanner/docs/instance-configurations), [Spanner: TrueTime and external consistency](https://docs.cloud.google.com/spanner/docs/true-time-external-consistency)).
- Bigtable stores large amounts of single-keyed data with low latency. It is not a traditional relational database ([Bigtable overview](https://docs.cloud.google.com/bigtable/docs/overview)).
- For interactive queries in an online analytical processing (OLAP) system, use BigQuery ([Bigtable overview](https://docs.cloud.google.com/bigtable/docs/overview)).

## Step 1: choose the storage type

Start from how the application reads and writes data. The access method removes most options before you compare products.

| Access need | Storage type | Google recommendation |
|---|---|---|
| Unstructured objects of any size, read from anywhere | Object | Cloud Storage |
| Boot and data disks for a VM | Block | Hyperdisk; Persistent Disk on older machine series |
| Fast scratch disk or cache | Block (ephemeral) | Local SSD |
| Shared files over NFS | File | Filestore Zonal or Regional, or NetApp Volumes |
| Shared files over SMB | File | NetApp Volumes |
| Parallel file system for AI, ML, or HPC | File | Managed Lustre |
| Records that the application queries by key or by SQL | Database | See step 3 |

Sources: [Design an optimal storage strategy for your cloud workload](https://docs.cloud.google.com/architecture/storage-advisor), [Choose a disk type](https://docs.cloud.google.com/compute/docs/disks).

## Step 2a: object storage with Cloud Storage

Cloud Storage has no capacity limit and scales automatically ([Design an optimal storage strategy for your cloud workload](https://docs.cloud.google.com/architecture/storage-advisor)). Choose the class from the access pattern:

| Requirement | Recommendation |
|---|---|
| Access frequency varies, or the retention period is unknown | Autoclass |
| Frequent access: analytics, data lakes, websites, streaming video, mobile apps | Standard; add Cloud CDN for users far from the bucket |
| Infrequent access, kept at least 30 days (backups, long-tail media) | Nearline |
| Infrequent access, kept at least 90 days (disaster recovery) | Coldline |
| Lowest cost, kept at least 365 days (regulatory archives) | Archive |

Sources: [Design an optimal storage strategy for your cloud workload](https://docs.cloud.google.com/architecture/storage-advisor), [Storage classes](https://docs.cloud.google.com/storage/docs/storage-classes).

Locations, classes, lifecycle rules, and retention are on the [Configuring Cloud Storage](note:2.2-cloud-storage-config) page.

Three newer options change some AI and analytics answers:

- **Rapid Bucket.** A zonal bucket stores objects in the Rapid storage class, next to your compute. It gives lower latency and higher throughput than the other classes. The bucket needs hierarchical namespace and uniform bucket-level access ([Rapid Bucket](https://docs.cloud.google.com/storage/docs/rapid/rapid-bucket)).
- **Rapid Cache (formerly Anywhere Cache).** An SSD-backed zonal read cache for data that changes rarely and is read often, for example model training data ([Rapid Cache](https://docs.cloud.google.com/storage/docs/rapid/rapid-cache)).
- **Cloud Storage FUSE.** It mounts a bucket as a file system. It is not POSIX compliant, and it is not an NFS or CIFS file system on the backend ([Cloud Storage FUSE](https://docs.cloud.google.com/storage/docs/cloud-storage-fuse/overview)).

## Step 2b: block storage

### Hyperdisk or Persistent Disk

Choose Hyperdisk for new designs. Persistent Disk is not available on the newest machine series. For example, N4 does not support Persistent Disk or Local SSD ([Choose a disk type](https://docs.cloud.google.com/compute/docs/disks), [General-purpose machine family for Compute Engine](https://docs.cloud.google.com/compute/docs/general-purpose-machines)).

| Hyperdisk type | Use it for |
|---|---|
| Hyperdisk Balanced | Most enterprise applications, boot disks, PostgreSQL and MySQL |
| Hyperdisk Extreme | High I/O workloads such as high-performance databases |
| Hyperdisk Throughput | Scale-out analytics, data disks for cost-sensitive applications, cold storage |
| Hyperdisk ML | High read throughput to many VMs in read-only mode |
| Hyperdisk Balanced High Availability | Synchronous replication across two zones; multi-writer access from VMs in one region |

Sources: [Design an optimal storage strategy for your cloud workload](https://docs.cloud.google.com/architecture/storage-advisor), [Google Cloud Hyperdisk overview](https://docs.cloud.google.com/compute/docs/disks/hyperdisks).

Two details decide exam answers:

- You set Hyperdisk size and performance separately. The VM must support the provisioned performance level, or the disk does not reach it ([Google Cloud Hyperdisk overview](https://docs.cloud.google.com/compute/docs/disks/hyperdisks)).
- Google recommends Hyperdisk Storage Pools for 20 TiB or more of disk capacity in one project and zone. If an Advanced capacity pool is full, writes to all its disks fail ([Hyperdisk Storage Pools overview](https://docs.cloud.google.com/compute/docs/disks/storage-pools)).

### Zonal or replicated disks

A zonal disk survives a VM failure but not a zone outage. Choose the replication from the recovery point objective (RPO):

| Need | Option | Behavior |
|---|---|---|
| RPO zero for a zone outage | Regional Persistent Disk or Hyperdisk Balanced High Availability | Synchronous replication between two zones in one region. Force-attach to a standby VM takes less than one minute. Twice the cost of a zonal disk. |
| Cross-region disaster recovery | Asynchronous Replication | Target RPO of one minute, to a region on the same continent. You detect the outage and start the failover. |

Sources: [About synchronous disk replication](https://docs.cloud.google.com/compute/docs/disks/about-regional-persistent-disk), [Build HA services using synchronously replicated disks](https://docs.cloud.google.com/compute/docs/disks/high-availability-regional-persistent-disk), [About Asynchronous Replication](https://docs.cloud.google.com/compute/docs/disks/async-pd/about).

Regional Persistent Disk attaches only to E2, N1, N2, and N2D VMs ([About synchronous disk replication](https://docs.cloud.google.com/compute/docs/disks/about-regional-persistent-disk)). Replication does not protect against data corruption, user error, or attacks, so you still need backups ([Data protection options for disks and instances](https://docs.cloud.google.com/compute/docs/disks/data-protection)). Snapshots and machine images are on the [Data protection](note:2.2-data-protection) page.

### Local SSD

Local SSD gives the fastest block storage, but the data is temporary ([Choose a disk type](https://docs.cloud.google.com/compute/docs/disks), [About Local SSD disks](https://docs.cloud.google.com/compute/docs/disks/local-ssd)):

- Data stays during a live migration and a guest OS reboot.
- By default, data is lost when you stop or suspend the VM, and when a Spot VM or preemptible VM is preempted. An option to keep the data on stop or suspend is in Preview.
- You add Local SSD disks only when you create the VM.

Use it for scratch data, caches such as SQL Server `tempdb`, or flash-optimized databases ([Choose a disk type](https://docs.cloud.google.com/compute/docs/disks)).

## Step 2c: file storage

| Need | Recommendation |
|---|---|
| NFS, regional availability, performance that scales with capacity | Filestore Regional |
| NFS, zonal availability is enough, high performance | Filestore Zonal, or NetApp Volumes Premium or Extreme |
| SMB (Windows file shares) | NetApp Volumes |
| Many small shares for GKE through the Filestore CSI driver | Filestore Multishares for GKE (Enterprise) |
| Parallel file system for AI, ML, and HPC | Managed Lustre |

Sources: [Design an optimal storage strategy for your cloud workload](https://docs.cloud.google.com/architecture/storage-advisor), [About service tiers](https://docs.cloud.google.com/filestore/docs/service-tiers), [Filestore Multishares for GKE (Enterprise) service tier](https://docs.cloud.google.com/filestore/docs/service-tiers-enterprise).

**Filestore.** The primary tiers are Zonal, Regional, and Multishares for GKE (Enterprise). Basic HDD and Basic SSD are legacy tiers ([About service tiers](https://docs.cloud.google.com/filestore/docs/service-tiers)). The SLA is at least 99.99% for Regional and Enterprise (99.95% in Mexico and Stockholm), and at least 99.9% for Zonal and Basic ([Cloud Filestore Service Level Agreement](https://cloud.google.com/filestore/sla)). An older Architecture Center page recommends the Enterprise tier for resilience ([Disaster recovery building blocks](https://docs.cloud.google.com/architecture/dr-scenarios-building-blocks)). The current docs say to use Regional for all uses except multishares and the CSI driver ([Filestore Multishares for GKE (Enterprise) service tier](https://docs.cloud.google.com/filestore/docs/service-tiers-enterprise)).

**NetApp Volumes.** It supports NFSv3, NFSv4.1, NFSv4.2, SMB, iSCSI, and NVMe/TCP ([Google Cloud NetApp Volumes overview](https://docs.cloud.google.com/netapp/volumes/docs/discover/overview)). The service levels are Flex Unified, Flex File, Standard, Premium, and Extreme. From September 15, 2026, you cannot create new Flex File pools. Only the Flex levels offer regional pools ([Google Cloud NetApp Volumes service levels](https://docs.cloud.google.com/netapp/volumes/docs/discover/service-levels)).

**Managed Lustre.** It is a managed parallel file system for AI and HPC with up to 10 TBps of throughput ([Managed Lustre](https://docs.cloud.google.com/managed-lustre/docs/overview)). An instance is zonal. For more availability, deploy an instance in each zone ([Optimize AI and ML workloads with Google Cloud Managed Lustre](https://docs.cloud.google.com/architecture/optimize-ai-ml-workloads-managed-lustre)). For AI clusters, Google makes Cloud Storage Rapid Bucket the primary choice for training datasets, and Managed Lustre the primary choice for checkpoints ([About storage services for AI and ML workloads](https://docs.cloud.google.com/ai-hypercomputer/docs/storage)).

## Step 3: choose the database

Start with the data model and the workload type. Then check scale, consistency, and global reach.

| Product | Data model | Consistency | Scale | Global reach |
|---|---|---|---|---|
| Cloud SQL | Relational: MySQL, PostgreSQL, SQL Server | HA writes commit in two zones; cross-region replicas are asynchronous | Vertical; up to 64 TB of storage | One region; cross-region read replicas |
| AlloyDB | Relational, PostgreSQL-compatible | No data loss on HA failover; secondary clusters are asynchronous | One primary instance for writes; read pools of up to 20 nodes | One region; secondary clusters in other regions |
| Spanner | Relational (GoogleSQL or PostgreSQL interface), plus graph, key-value, and search | External consistency; strong reads by default | Horizontal: add compute capacity | Regional, dual-region, or multi-region |
| Bigtable | Key-value NoSQL in sparse tables with many columns | Strong in one cluster; eventual across clusters by default | Horizontal: add nodes; petabytes | Clusters in up to 8 regions |
| Firestore | Document NoSQL; MongoDB-compatible API | Strongly consistent queries; ACID transactions | Serverless; scales automatically | Regional or multi-region |
| Memorystore | In-memory key-value: Valkey, Redis Cluster, Redis | Asynchronous replicas; a failover can lose acknowledged writes | Shards and replicas, up to 250 nodes | Cross-region secondary instances (Valkey) |
| BigQuery | Columnar tables for SQL analytics | ACID transactions; built for analytics (OLAP) | Serverless; compute and storage scale separately | Region or multi-region location |

Sources: [About high availability](https://docs.cloud.google.com/sql/docs/postgres/high-availability), [Promote replicas for regional migration or disaster recovery](https://docs.cloud.google.com/sql/docs/postgres/replication/cross-region-replicas), [Compare AWS and Azure services to Google Cloud](https://docs.cloud.google.com/docs/get-started/aws-azure-gcp-service-comparison), [AlloyDB overview](https://docs.cloud.google.com/alloydb/docs/overview), [AlloyDB high availability overview](https://docs.cloud.google.com/alloydb/docs/high-availability), [Cross-region replication overview](https://docs.cloud.google.com/alloydb/docs/cross-region-replication/about-cross-region-replication), [Spanner](https://cloud.google.com/spanner), [Spanner: TrueTime and external consistency](https://docs.cloud.google.com/spanner/docs/true-time-external-consistency), [Bigtable overview](https://docs.cloud.google.com/bigtable/docs/overview), [Replication overview](https://docs.cloud.google.com/bigtable/docs/replication-overview), [Instances, clusters, and nodes](https://docs.cloud.google.com/bigtable/docs/instances-clusters-nodes), [Firestore overview](https://docs.cloud.google.com/firestore/native/docs/overview), [Memorystore](https://cloud.google.com/memorystore), [High availability and replicas](https://docs.cloud.google.com/memorystore/docs/valkey/ha-and-replicas), [About cross-region replication](https://docs.cloud.google.com/memorystore/docs/valkey/about-cross-region-replication), [BigQuery overview](https://docs.cloud.google.com/bigquery/docs/introduction).

| Product | Workload | Migration fit | Operational overhead |
|---|---|---|---|
| Cloud SQL | General-purpose OLTP: web frameworks, CRM, ERP, SaaS, and e-commerce | Existing MySQL, PostgreSQL, and SQL Server databases | You choose the machine size, HA, replicas, and a maintenance window |
| AlloyDB | Demanding PostgreSQL OLTP plus analytics on live data (HTAP) | PostgreSQL applications and tools such as psql and pgAdmin | You size the primary instance and the read pools |
| Spanner | OLTP at any scale, with global writes and up to 99.999% availability | Needs schema work; the PostgreSQL interface does not support extensions or stored procedures | You set compute capacity or use the managed autoscaler; no maintenance windows |
| Bigtable | High-throughput reads and writes: time series, IoT, financial, and marketing data | Apache HBase client for Java | You set nodes or autoscaling, and you design the row key |
| Firestore | Document data for applications; optional Firebase integration for mobile and web | MongoDB applications through the MongoDB-compatible API | Serverless; no capacity to provision |
| Memorystore | In-memory cache with sub-millisecond data access | Open source Valkey, Redis, and Memcached clients | You size shards and replicas; failover is managed |
| BigQuery | OLAP: data warehouse and interactive analytics | Data warehouse migrations (see [Migration tooling](note:5.1-migration-tooling)) | Serverless; no resources to provision or scale |

Sources: [Cloud SQL overview](https://docs.cloud.google.com/sql/docs/introduction), [Your Google Cloud database options, explained](https://cloud.google.com/blog/topics/developers-practitioners/your-google-cloud-database-options-explained), [Maintenance updates on Cloud SQL instances](https://docs.cloud.google.com/sql/docs/postgres/maintenance), [AlloyDB overview](https://docs.cloud.google.com/alloydb/docs/overview), [Compare AWS and Azure services to Google Cloud](https://docs.cloud.google.com/docs/get-started/aws-azure-gcp-service-comparison), [PostgreSQL interface](https://docs.cloud.google.com/spanner/docs/postgresql-interface), [Managed autoscaler](https://docs.cloud.google.com/spanner/docs/managed-autoscaler), [Bigtable overview](https://docs.cloud.google.com/bigtable/docs/overview), [Autoscaling](https://docs.cloud.google.com/bigtable/docs/autoscaling), [Firestore overview](https://docs.cloud.google.com/firestore/native/docs/overview), [Memorystore](https://cloud.google.com/memorystore), [BigQuery overview](https://docs.cloud.google.com/bigquery/docs/introduction).

### Relational: Cloud SQL, AlloyDB, or Spanner

- **Cloud SQL** fits general-purpose relational workloads in one region. It is managed MySQL, PostgreSQL, and SQL Server ([Cloud SQL overview](https://docs.cloud.google.com/sql/docs/introduction), [Your Google Cloud database options, explained](https://cloud.google.com/blog/topics/developers-practitioners/your-google-cloud-database-options-explained)).
- **AlloyDB** fits PostgreSQL workloads that need more performance or analytics on live data. The Cloud SQL recommender suggests AlloyDB for production instances with a low cache hit rate ([Improve performance with AlloyDB for PostgreSQL](https://docs.cloud.google.com/sql/docs/postgres/recommender-alloydb)).
- **Spanner** fits when one relational database must scale horizontally or write in several regions. Other relational databases scale vertically. Spanner scales horizontally ([Spanner](https://cloud.google.com/spanner)).

Dual-region and multi-region configurations need Enterprise Plus. Standard edition is regional only ([Spanner editions overview](https://docs.cloud.google.com/spanner/docs/editions-overview)). In a multi-region configuration, reads are faster from several regions, and writes have a small latency increase ([Regional, dual-region, and multi-region configurations](https://docs.cloud.google.com/spanner/docs/instance-configurations)). Configuration detail is on the [Configuring databases](note:2.2-database-config) page.

### NoSQL: Bigtable, Firestore, or Memorystore

- **Bigtable** is for large, single-keyed data with high throughput. Each value is typically no larger than 10 MB ([Bigtable overview](https://docs.cloud.google.com/bigtable/docs/overview)). Queries that do not use the row key, a key prefix, or a key range scan the whole table ([Schema design best practices](https://docs.cloud.google.com/bigtable/docs/schema-design)).
- **Firestore** is for document data with ACID transactions and SQL-like queries ([Bigtable overview](https://docs.cloud.google.com/bigtable/docs/overview)). Use Datastore compatibility only for applications that depend on the Datastore APIs ([Choose between Firestore APIs](https://docs.cloud.google.com/datastore/docs/firestore-or-datastore)).
- **Memorystore** keeps data in memory. Replication is asynchronous, so a failover can lose acknowledged writes ([High availability and replicas](https://docs.cloud.google.com/memorystore/docs/valkey/ha-and-replicas)). Memorystore for Memcached is deprecated. After February 1, 2027, you cannot create Memcached instances in new projects. Google recommends Memorystore for Valkey ([Memorystore for Memcached release notes](https://docs.cloud.google.com/memorystore/docs/memcached/release-notes)).

### Analytics: BigQuery

BigQuery separates compute and storage, so each layer scales without an effect on the other ([BigQuery overview](https://docs.cloud.google.com/bigquery/docs/introduction)). A multi-region dataset location does not give cross-region redundancy ([BigQuery locations](https://docs.cloud.google.com/bigquery/docs/locations)). Loading and transformation choices are on the [Choosing data processing solutions](note:1.3-data-processing) page.

## Exam traps

- **Filestore for Windows file shares.** Filestore serves NFS. For SMB, use NetApp Volumes ([Design an optimal storage strategy for your cloud workload](https://docs.cloud.google.com/architecture/storage-advisor)).
- **Filestore Basic or Enterprise for a new resilient NFS share.** Basic is a legacy tier. Use Regional unless you need multishares for GKE ([About service tiers](https://docs.cloud.google.com/filestore/docs/service-tiers), [Filestore Multishares for GKE (Enterprise) service tier](https://docs.cloud.google.com/filestore/docs/service-tiers-enterprise)).
- **Cloud Storage FUSE as a POSIX file system or a database disk.** It is not POSIX compliant ([Cloud Storage FUSE](https://docs.cloud.google.com/storage/docs/cloud-storage-fuse/overview)).
- **Local SSD for data that must survive a VM stop.** By default, a stop, suspend, or preemption discards the data, and snapshots do not work. An option to keep the data on stop or suspend is in Preview ([About Local SSD disks](https://docs.cloud.google.com/compute/docs/disks/local-ssd)).
- **Persistent Disk on a new C4 or N4 VM.** These series do not support Persistent Disk ([General-purpose machine family for Compute Engine](https://docs.cloud.google.com/compute/docs/general-purpose-machines)).
- **Cloud SQL for global, strongly consistent writes.** Cloud SQL cross-region replicas are asynchronous. Use a Spanner multi-region configuration ([Promote replicas for regional migration or disaster recovery](https://docs.cloud.google.com/sql/docs/postgres/replication/cross-region-replicas), [Regional, dual-region, and multi-region configurations](https://docs.cloud.google.com/spanner/docs/instance-configurations)).
- **Spanner Standard edition for a multi-region design.** Multi-region needs Enterprise Plus ([Spanner editions overview](https://docs.cloud.google.com/spanner/docs/editions-overview)).
- **Bigtable for joins or multi-row transactions.** Bigtable is not a traditional relational database. Keep data that you read atomically in one row ([Bigtable overview](https://docs.cloud.google.com/bigtable/docs/overview), [Schema design best practices](https://docs.cloud.google.com/bigtable/docs/schema-design)).
