## Why it matters

Cloud Run is often the first compute answer, but its settings decide cost, cold-start latency, and who can reach the service. The architect sets the scaling limits, the billing mode, the network ingress and egress path, and the invoker access. The exam also asks how VMware Engine private clouds connect to VPC networks and to on-premises sites.

## Key points

- A Cloud Run service answers requests at an HTTPS endpoint. A Cloud Run job runs its tasks to completion and does not serve requests ([Create jobs](https://docs.cloud.google.com/run/docs/create-jobs)).
- Revisions are immutable. You can split traffic between revisions, and a tag gives a revision its own URL for tests ([Deploy container images to Cloud Run services](https://docs.cloud.google.com/run/docs/deploying), [Rollbacks, gradual rollouts, and traffic migration](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration)).
- Request-based billing is the default for services. Instance-based billing keeps CPU for the whole instance lifecycle. All Cloud Run jobs use instance-based billing ([Billing settings for services](https://docs.cloud.google.com/run/docs/configuring/billing-settings)).
- Minimum instances reduce cold starts, and maximum instances limit cost and the connections to a backing database ([Set minimum instances](https://docs.cloud.google.com/run/docs/configuring/min-instances), [Set maximum instances](https://docs.cloud.google.com/run/docs/configuring/max-instances)).
- The ingress setting controls the network paths to a service: all, internal, or internal and Cloud Load Balancing. IAM authentication still applies on every path ([Restrict network endpoint ingress](https://docs.cloud.google.com/run/docs/securing/ingress)).
- To make a service public, Google recommends that you disable the Cloud Run Invoker IAM check ([Allowing public access](https://docs.cloud.google.com/run/docs/authenticating/public)).
- Direct VPC egress is the recommended way to reach a VPC network. It needs no Serverless VPC Access connector ([Compare Direct VPC egress and VPC connectors](https://docs.cloud.google.com/run/docs/configuring/connecting-vpc)).
- For a custom domain, Google recommends a global external Application Load Balancer. Cloud Run domain mapping is not recommended for production ([Mapping custom domains](https://docs.cloud.google.com/run/docs/mapping-custom-domains)).
- A Cloud Run function (formerly Cloud Functions) is a Cloud Run service that is deployed from source code. Event-driven functions use Eventarc triggers ([Compare Cloud Run functions](https://docs.cloud.google.com/run/docs/functions/comparison), [Cloud Run function triggers](https://docs.cloud.google.com/run/docs/function-triggers)).
- A Standard VMware Engine network is global. It connects to a VPC network through VPC Network Peering ([About VMware Engine networks](https://docs.cloud.google.com/vmware-engine/docs/networking/vmware-engine-network)).

## Services and jobs

| | Service | Job |
|---|---|---|
| Runs | A container that listens for requests | Tasks that run to completion and exit |
| Started by | HTTPS requests and events | Manually, on a schedule, or from a workflow |
| Time limit | Request timeout: default 5 minutes, maximum 60 minutes | Task timeout: default 10 minutes, maximum 168 hours (1 hour with GPUs) |
| Scale | Instance autoscaling, down to zero | Parallel tasks. Each task reads its index from `CLOUD_RUN_TASK_INDEX` |
| Billing | Request-based (default) or instance-based | Always instance-based |

Sources: [What is Cloud Run](https://docs.cloud.google.com/run/docs/overview/what-is-cloud-run), [Create jobs](https://docs.cloud.google.com/run/docs/create-jobs), [Configure request timeout for services](https://docs.cloud.google.com/run/docs/configuring/request-timeout), [Set task timeout for jobs](https://docs.cloud.google.com/run/docs/configuring/task-timeout), [Billing settings for services](https://docs.cloud.google.com/run/docs/configuring/billing-settings).

For a request timeout longer than 15 minutes, add retries and make the service tolerant of client reconnections ([Configure request timeout for services](https://docs.cloud.google.com/run/docs/configuring/request-timeout)). Google recommends retries for all jobs, especially jobs with long tasks ([Set task timeout for jobs](https://docs.cloud.google.com/run/docs/configuring/task-timeout)). For worker pools and instances, see [Mapping workloads to compute platforms](note:1.3-compute-choice).

## Revisions, traffic splitting, and tags

Each deployment creates a new revision, and revisions are immutable ([Deploy container images to Cloud Run services](https://docs.cloud.google.com/run/docs/deploying)). A gradual rollout with a tag has these steps ([Rollbacks, gradual rollouts, and traffic migration](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration)):

1. Deploy the new revision with no traffic and a tag: `gcloud run deploy SERVICE --image IMAGE --no-traffic --tag green`.
2. Test the revision at its tag URL, for example `https://green---SERVICE-abcdef.a.run.app`.
3. Move part of the traffic: `gcloud run services update-traffic SERVICE --to-tags green=10`.
4. Increase the percentage. To roll back, send 100% to the earlier revision with `--to-revisions`.

Traffic rules to remember ([Rollbacks, gradual rollouts, and traffic migration](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration)):

- **Splits persist.** After you split traffic, all later deployments keep that split. Use `--to-latest` to send all traffic to the newest revision again.
- **Tags can cost money.** Revision-level minimum instances also start instances for tagged revisions. Service-level minimum instances do not.

For canary and blue-green release processes, see [Deployment and release management](note:6.3-release-management).

## Scaling, performance, and billing

| Setting | What it does | Guidance |
|---|---|---|
| Maximum concurrent requests | Requests that one instance processes at the same time. Default 80 × vCPU with gcloud or Terraform, 80 in the console, maximum 1,000 | Keep the default. Set `1` if the code cannot process parallel requests, or if each request uses most of the CPU or memory |
| Minimum instances | Keeps idle instances ready, so requests avoid a cold start | Apply at the service level. Idle instances have a charge |
| Maximum instances | Upper limit on instances. Default 100 per revision. Traffic spikes can briefly exceed it | Apply at the service level. Use it to cap cost or database connections |
| Startup CPU boost | Extra CPU during startup and for 10 seconds after | Use it to reduce startup latency |

Sources: [Maximum concurrent requests for services](https://docs.cloud.google.com/run/docs/about-concurrency), [Set minimum instances](https://docs.cloud.google.com/run/docs/configuring/min-instances), [Set maximum instances](https://docs.cloud.google.com/run/docs/configuring/max-instances), [Configure CPU limits for services](https://docs.cloud.google.com/run/docs/configuring/services/cpu).

| | Request-based billing (default) | Instance-based billing |
|---|---|---|
| You pay for | Request processing, startup, and shutdown | The whole instance lifecycle |
| CPU outside requests | No | Yes, so background tasks can run after the response |
| Best traffic pattern | Sporadic, bursty, or spiky | Steady or slowly changing |
| Former name | CPU only allocated during request processing | CPU always allocated |

Source: [Billing settings for services](https://docs.cloud.google.com/run/docs/configuring/billing-settings).

Jobs always use instance-based billing, and services with GPUs require it ([Billing settings for services](https://docs.cloud.google.com/run/docs/configuring/billing-settings), [GPU support for services](https://docs.cloud.google.com/run/docs/configuring/services/gpu)). Idle instances can shut down at any time, even with instance-based billing. For asynchronous work that must finish, Google suggests Cloud Tasks, which retries failed tasks ([Billing settings for services](https://docs.cloud.google.com/run/docs/configuring/billing-settings)).

**GPUs.** A service can attach one NVIDIA L4 or RTX PRO 6000 GPU to each instance. No reservation is necessary, and the service can scale to zero. Each GPU type has minimum CPU and memory values ([GPU support for services](https://docs.cloud.google.com/run/docs/configuring/services/gpu)). For TPUs and large accelerator capacity, see [AI Hypercomputer](note:2.4-ai-hypercomputer).

## Ingress and access control

| Ingress setting | Allows | Use when |
|---|---|---|
| All (default) | All requests, including direct internet requests to the `run.app` URL | Public sites and APIs |
| Internal | Internal Application Load Balancers, VPC networks in the same project, the configured Shared VPC network, VPC Service Controls perimeters, and some Google services in the same project, such as Pub/Sub, Eventarc, and Cloud Scheduler | Internal-only services |
| Internal and Cloud Load Balancing | Internal sources, plus external Application Load Balancers | Internet traffic that must pass Cloud Armor, IAP, or Cloud CDN at the load balancer |

Source: [Restrict network endpoint ingress](https://docs.cloud.google.com/run/docs/securing/ingress).

- **On-premises clients.** Requests from on-premises networks over Cloud VPN or Cloud Interconnect count as internal ([Restrict network endpoint ingress](https://docs.cloud.google.com/run/docs/securing/ingress)).
- **Cloud Run callers.** A request from another Cloud Run service counts as internal only when it goes through a VPC network. The caller needs Direct VPC egress or a connector. For example, send all egress traffic to the VPC and turn on Private Google Access for the egress subnet. Or put an internal Application Load Balancer or Private Service Connect in front of the receiving service ([Private networking and Cloud Run](https://docs.cloud.google.com/run/docs/securing/private-networking)).
- **Blocked requests.** A request that fails the ingress setting gets HTTP 404. The error does not appear in the service's request logs ([Troubleshoot Cloud Run issues](https://docs.cloud.google.com/run/docs/troubleshooting)).
- **Default URL.** You can disable the `run.app` URL so that clients must use a load balancer or domain mapping ([Restrict network endpoint ingress](https://docs.cloud.google.com/run/docs/securing/ingress)).
- **Governance.** The `run.allowedIngress` organization policy limits the ingress settings that developers can select ([Restrict network endpoint ingress](https://docs.cloud.google.com/run/docs/securing/ingress)).

Identity controls:

- **Service-to-service calls.** Grant the caller's service account the Cloud Run Invoker role (`roles/run.invoker`) on the receiving service. The caller sends a Google-signed OpenID Connect ID token ([Authenticating service-to-service](https://docs.cloud.google.com/run/docs/authenticating/service-to-service)).
- **Public services.** Disable the Invoker IAM check. This works when the domain restricted sharing constraint blocks `allUsers` ([Allowing public access](https://docs.cloud.google.com/run/docs/authenticating/public)).
- **User sign-in.** You can enable IAP directly on a Cloud Run service, for all ingress paths. You cannot enable IAP on both the load balancer and the service ([Configure IAP for Cloud Run](https://docs.cloud.google.com/run/docs/securing/identity-aware-proxy-cloud-run)).
- **Service identity.** Use a user-managed service account with the minimum permissions. The default is the Compute Engine default service account, which can have the Editor role ([Introduction to service identity](https://docs.cloud.google.com/run/docs/securing/service-identity)).

## VPC egress: Direct VPC egress or a connector

| | Direct VPC egress (recommended) | Serverless VPC Access connector |
|---|---|---|
| Cost | Network egress only. Scales to zero with the service | Network egress plus the connector's Compute Engine VMs |
| Performance | Lower latency, higher throughput | Higher latency, lower throughput |
| IP addresses | Uses more: about 2× the instance count, in blocks of 16. The subnet must be /26 or larger | Uses fewer |
| Network tags | Per service or job, so firewall rules are more precise | Shared by all services that use the connector |
| Scaling | New instances start more slowly while Cloud Run creates network interfaces | Latency during surges while connector instances start |

Sources: [Compare Direct VPC egress and VPC connectors](https://docs.cloud.google.com/run/docs/configuring/connecting-vpc), [Direct VPC with a VPC network](https://docs.cloud.google.com/run/docs/configuring/vpc-direct-vpc).

- **Egress scope.** `--vpc-egress=private-ranges-only` is the default and sends only private IP traffic to the VPC. `all-traffic` sends everything ([gcloud run deploy](https://docs.cloud.google.com/sdk/gcloud/reference/run/deploy)).
- **Static outbound IP.** Route all traffic through a VPC network that has a Cloud NAT gateway with a static IP address ([Static outbound IP address](https://docs.cloud.google.com/run/docs/configuring/static-outbound-ip)).
- **Cloud NAT caveat.** Direct VPC egress with Cloud NAT can add cold-start delays of 30 seconds or more. For better startup, Google recommends a connector with Cloud NAT ([Direct VPC with a VPC network](https://docs.cloud.google.com/run/docs/configuring/vpc-direct-vpc)).
- **Subnet removal.** After services stop using a subnet, wait 1–2 hours before you delete it ([Direct VPC with a VPC network](https://docs.cloud.google.com/run/docs/configuring/vpc-direct-vpc)).

For Private Google Access and Cloud NAT design, see [Access to Google APIs, the internet, and cloud-adjacent services](note:2.1-vpc-access-patterns).

## Custom domains and multiple regions

| Option | Notes |
|---|---|
| Global external Application Load Balancer | Recommended. You can use your own TLS certificate, route URL paths, and add Cloud CDN and Cloud Armor |
| Cloud Run domain mapping | Limited availability and Preview. Not production-ready because of latency issues. No self-managed certificates |
| Firebase Hosting | Not covered by the Google Cloud Terms of Service |

Source: [Mapping custom domains](https://docs.cloud.google.com/run/docs/mapping-custom-domains).

To serve several regions, deploy the service in each region. Add a serverless network endpoint group (NEG) per region behind one global external Application Load Balancer ([Serve traffic from multiple regions](https://docs.cloud.google.com/run/docs/multiple-regions)). This setup alone does not fail over when a regional service returns errors. Add Cloud Run service health or outlier detection for automatic failover ([Serve traffic from multiple regions](https://docs.cloud.google.com/run/docs/multiple-regions)). For the load balancer choice, see [Choosing a load balancer](note:1.3-load-balancing).

## Cloud Run functions and Eventarc

| | Cloud Run functions | Cloud Run functions (1st gen) |
|---|---|---|
| Former name | Cloud Functions (2nd gen) | Cloud Functions (1st gen) |
| Resource model | A Cloud Run service deployed from source code | A function deployed from source code |
| Request timeout | Up to 60 minutes for HTTP functions | Up to 9 minutes |
| Concurrency | Up to 1,000 requests per instance | 1 request per instance |
| Traffic splitting | Supported | Not supported |
| Event types | Any event type that Eventarc supports | Events from 7 sources |

Source: [Compare Cloud Run functions](https://docs.cloud.google.com/run/docs/functions/comparison).

- **Trigger types.** HTTP functions answer HTTPS requests. Event-driven functions must use Eventarc triggers ([Cloud Run function triggers](https://docs.cloud.google.com/run/docs/function-triggers)).
- **Event sources.** Google events come directly from the source, such as Cloud Storage, or from Cloud Audit Logs entries. Eventarc uses Pub/Sub as the transport ([Eventarc Standard overview](https://docs.cloud.google.com/eventarc/standard/docs/overview)).
- **Editions.** Eventarc Standard routes events from providers to destinations with triggers. Eventarc Advanced adds a central bus, enrollments, and event transformation for complex, multi-team designs ([Eventarc overview](https://docs.cloud.google.com/eventarc/docs/overview)).
- **Retries.** For functions created with the Cloud Run Admin API, set the retry policy in Eventarc and a dead-letter topic in Pub/Sub ([Compare Cloud Run functions](https://docs.cloud.google.com/run/docs/functions/comparison)).

For event-driven integration patterns, see [Integration patterns and data movement](note:1.1-integration-and-data-movement).

## VMware Engine networking

A VMware Engine private cloud runs vSphere, vCenter, vSAN, NSX, and HCX on dedicated bare metal nodes. Google manages the infrastructure ([Google Cloud VMware Engine overview](https://docs.cloud.google.com/vmware-engine/docs/overview)). A single-node private cloud is for pilots and has no SLA. Expand it to at least three nodes for a standard private cloud ([About VMware Engine private clouds](https://docs.cloud.google.com/vmware-engine/docs/concepts-private-cloud)).

| | Standard VMware Engine network | Legacy VMware Engine network |
|---|---|---|
| Scope | Global | Regional. One per region that has a private cloud |
| Availability | The default | Only projects created before November 2023 |
| Connection to a VPC network | VPC Network Peering between the VPC and the VMware Engine network | Private services access and a private connection in each region |

Source: [About VMware Engine networks](https://docs.cloud.google.com/vmware-engine/docs/networking/vmware-engine-network).

- **Peering targets.** A VMware Engine network can peer with a VPC network in the same or another project, or with a Shared VPC network. It can also peer with another VMware Engine network, private services access (for example Cloud SQL), and NetApp Volumes ([Peer a VPC network](https://docs.cloud.google.com/vmware-engine/docs/networking/peer-vpc-network)).
- **Address planning.** The vSphere/vSAN subnets range must be /24 to /20. You cannot change it without deleting the private cloud. No range can overlap on-premises, VPC, or workload subnets ([Networking requirements](https://docs.cloud.google.com/vmware-engine/docs/quickstart-networking-requirements)).
- **DNS.** Each private cloud has a Cloud DNS zone for vCenter, NSX Manager, and HCX. A VPC peering creates the DNS binding for that zone automatically ([About VMware Engine networks](https://docs.cloud.google.com/vmware-engine/docs/networking/vmware-engine-network)).
- **HCX.** VMware Engine deploys HCX when it creates the private cloud. Connect the on-premises environment with Cloud VPN or Cloud Interconnect. HCX supports live, cold, and bulk migration ([Use VMware HCX to migrate VMware VMs](https://docs.cloud.google.com/vmware-engine/docs/workloads/howto-migrate-vms-using-hcx)).

For the migration plan and tools, see [Data and system migration tooling](note:5.1-migration-tooling).

## Exam traps

- **A connector for a new VPC egress design.** Direct VPC egress is recommended and has no connector VMs to pay for ([Compare Direct VPC egress and VPC connectors](https://docs.cloud.google.com/run/docs/configuring/connecting-vpc)).
- **Domain mapping for production.** Use a global external Application Load Balancer ([Mapping custom domains](https://docs.cloud.google.com/run/docs/mapping-custom-domains)).
- **Granting `allUsers` when an organization policy blocks it.** Disable the Invoker IAM check ([Allowing public access](https://docs.cloud.google.com/run/docs/authenticating/public)).
- **Ingress set to "internal" for a service behind an external load balancer.** Use "internal and Cloud Load Balancing" ([Restrict network endpoint ingress](https://docs.cloud.google.com/run/docs/securing/ingress)).
- **Background work after the response with request-based billing.** CPU is only allocated during requests. Use instance-based billing or Cloud Tasks ([Billing settings for services](https://docs.cloud.google.com/run/docs/configuring/billing-settings)).
- **Minimum instances to protect a database.** Maximum instances limit the connections ([Set maximum instances](https://docs.cloud.google.com/run/docs/configuring/max-instances)).
- **Expecting a new deployment to get all traffic after a split.** The split persists until you send all traffic to the latest revision ([Rollbacks, gradual rollouts, and traffic migration](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration)).
- **A static outbound IP with `private-ranges-only` egress.** Internet traffic must also go through the VPC to reach the Cloud NAT gateway ([Static outbound IP address](https://docs.cloud.google.com/run/docs/configuring/static-outbound-ip)).
- **A multi-region load balancer as automatic failover.** It does not fail over on errors without service health or outlier detection ([Serve traffic from multiple regions](https://docs.cloud.google.com/run/docs/multiple-regions)).
- **A small vSphere/vSAN range "to extend later".** You cannot change it without deleting the private cloud ([Networking requirements](https://docs.cloud.google.com/vmware-engine/docs/quickstart-networking-requirements)).
