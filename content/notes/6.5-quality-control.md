## Why it matters

Objective 6.5 asks you to evaluate quality control measures. The architect decides if a team's controls stop bad changes before users see them, and if the controls balance reliability with release speed. The exam describes a symptom, such as "releases often cause outages", "developers and SREs argue about each launch", or "the same incident happens again", and asks which control to add or change.

## Key points

- An SLI is the ratio of good events to total events. The SLO is the target for the SLI. The error budget is 100% minus the SLO ([Implementing SLOs](https://sre.google/workbook/implementing-slos/)).
- 100% is the wrong reliability target. Design systems to be just reliable enough for user happiness ([Set realistic targets for reliability](https://docs.cloud.google.com/architecture/framework/reliability/set-targets)).
- An error budget policy is a written policy. It states the actions to take when the service uses all of its error budget, and who takes them. The product manager, the developers, and the SREs must approve it ([Implementing SLOs](https://sre.google/workbook/implementing-slos/)).
- The error budget is an objective metric that removes politics from release decisions. While budget remains, releases continue ([Embracing Risk](https://sre.google/sre-book/embracing-risk/)).
- DORA measures software delivery performance with four metrics: change lead time, deployment frequency, change failure rate, and failed deployment recovery time ([Announcing the 2023 State of DevOps Report](https://cloud.google.com/blog/products/devops-sre/announcing-the-2023-state-of-devops-report)).
- DORA research recommends peer review instead of heavyweight change-approval processes ([DevOps capabilities](https://docs.cloud.google.com/architecture/devops)).
- Google Cloud's own change process uses presubmit tests, human code review, a qualification phase, and progressive rollouts with automated canary analysis ([Google Cloud's approach to change](https://docs.cloud.google.com/docs/cloud-approach-to-change)).
- Test organization policy changes before you enforce them: use Policy Simulator, then dry-run mode. Dry-run mode logs violations but does not deny them ([Create custom constraints](https://docs.cloud.google.com/organization-policy/create-custom-constraints)).
- A production readiness review (PRR) checks that a service meets production standards before an SRE team accepts responsibility for it ([The Evolving SRE Engagement Model](https://sre.google/sre-book/evolving-sre-engagement-model/)).
- Each postmortem action item needs an owner, a tracking number, a priority, and a verifiable end state ([Postmortem Culture: Learning from Failure](https://sre.google/workbook/postmortem-culture/)).

## SLOs, error budgets, and error budget policies

The SLO and burn-rate alert configuration in Cloud Monitoring is in [Google Cloud Observability](note:6.2-observability).

### Choose SLIs and targets

- Select a few SLIs that match what users care about. Serving systems care about availability, latency, and throughput. Storage systems emphasize latency, availability, and durability. Pipelines care about throughput and end-to-end latency ([Service Level Objectives](https://sre.google/sre-book/service-level-objectives/)).
- Have as few SLOs as possible. If an SLO never wins a discussion about priorities, it is probably not worth having ([Service Level Objectives](https://sre.google/sre-book/service-level-objectives/)).
- Keep a safety margin. Use an internal SLO that is tighter than the SLO that you publish ([Service Level Objectives](https://sre.google/sre-book/service-level-objectives/)).
- You can start from current performance if you have no other data and you iterate. Do not let current performance lock you into a target that needs heroic effort ([Implementing SLOs](https://sre.google/workbook/implementing-slos/), [Service Level Objectives](https://sre.google/sre-book/service-level-objectives/)).
- A four-week rolling window is a good general-purpose interval ([Implementing SLOs](https://sre.google/workbook/implementing-slos/)).
- The SLO owner must have the authority to trade feature velocity for reliability. This is normally the product owner, or the CTO in a small organization ([Implementing SLOs](https://sre.google/workbook/implementing-slos/)).

An SLA is a contract with consequences, such as a rebate. If a missed target has no explicit consequence, it is an SLO ([Service Level Objectives](https://sre.google/sre-book/service-level-objectives/)).

### The error budget policy

Three groups must agree. Product managers agree that the threshold is good enough for users. Developers agree to reduce risk when the budget is exhausted. The production team agrees that it can defend the SLO without excessive toil. If they do not all agree, change the SLIs and SLOs until they do ([Implementing SLOs](https://sre.google/workbook/implementing-slos/)).

| Part of the policy | Rule in the SRE workbook example |
|---|---|
| Goals | Protect customers from repeated SLO misses. Give an incentive to balance reliability with features. |
| Non-goal | The policy is not a punishment for missing SLOs. |
| SLO miss | If the service used more than its error budget in the preceding four-week window, halt all changes and releases except P0 issues and security fixes, until the service is back within its SLO. |
| The team must work on reliability when | A code bug or a procedural error caused the miss. A postmortem shows a hard dependency that the team can soften. Miscategorized errors hid a miss. |
| The team can continue feature work when | A company-wide network problem caused the outage. Another team's service caused it, and that team froze its own releases. Load tests or penetration testers used the budget. |
| Outage policy | A single incident that uses more than 20% of the four-week budget needs a postmortem with at least one P0 action item for the root cause. |
| Escalation | A disagreement about the calculation or the actions goes to the CTO. |

Source: [Example Error Budget Policy](https://sre.google/workbook/error-budget-policy/).

A halt is not the only response. A team can also slow down releases, or roll them back, when the budget is almost used up ([Embracing Risk](https://sre.google/sre-book/embracing-risk/)). Document the SLO and the policy with their approvers, the next review date, and the reasons for the numbers ([Implementing SLOs](https://sre.google/workbook/implementing-slos/)).

### Decide with the SLO decision matrix

| SLO | Toil | Customer satisfaction | Action |
|---|---|---|---|
| Met | Low | High | Relax release and deployment processes to increase velocity, or move engineering time to services that need more reliability. |
| Met | Low | Low | Tighten the SLO. |
| Met | High | High | If alerts give false positives, reduce sensitivity. Otherwise, loosen the SLOs for a time (or offload toil), and fix the product or improve automated fault mitigation. |
| Met | High | Low | Tighten the SLO. |
| Missed | Low | High | Loosen the SLO. |
| Missed | Low | Low | Increase alerting sensitivity. |
| Missed | High | High | Loosen the SLO. |
| Missed | High | Low | Offload toil, and fix the product or improve automated fault mitigation. |

Source: [Implementing SLOs](https://sre.google/workbook/implementing-slos/).

## Measure delivery performance with DORA metrics

| Metric | What it measures | Group |
|---|---|---|
| Change lead time | How long a code change takes to go from committed to deployed | Throughput |
| Deployment frequency | How frequently changes are pushed to production | Throughput |
| Change failure rate | How frequently a deployment introduces a failure that requires immediate intervention | Stability |
| Failed deployment recovery time | How long it takes to recover from a failed deployment | Stability |

Sources: [Announcing the 2023 State of DevOps Report](https://cloud.google.com/blog/products/devops-sre/announcing-the-2023-state-of-devops-report), [Use Four Keys metrics like change failure rate to measure your DevOps performance](https://cloud.google.com/blog/products/devops-sre/using-the-four-keys-to-measure-your-devops-performance).

Older questions use the names "Lead Time for Changes" and "Time to Restore Service". In 2021, DORA added reliability as a fifth metric ([Use Four Keys metrics like change failure rate to measure your DevOps performance](https://cloud.google.com/blog/products/devops-sre/using-the-four-keys-to-measure-your-devops-performance)).

Speed and stability are not a trade-off. Elite performers achieve both throughput and stability ([Announcing the 2023 State of DevOps Report](https://cloud.google.com/blog/products/devops-sre/announcing-the-2023-state-of-devops-report)).

Cloud Deploy shows Deployments, Deployment frequency, and Deployment failure rate for the production target of each pipeline. It counts a deployment as successful when the pods report a ready state ([Viewing metrics in Cloud Deploy](https://docs.cloud.google.com/deploy/docs/metrics)). DORA's change failure rate counts deployments that introduce a failure that needs immediate intervention. A ready deployment can still introduce such a failure, so link incident records to deployments ([Use Four Keys metrics like change failure rate to measure your DevOps performance](https://cloud.google.com/blog/products/devops-sre/using-the-four-keys-to-measure-your-devops-performance)).

## Quality gates in the delivery pipeline

| Stage | Quality control | Google Cloud feature |
|---|---|---|
| Before merge | Presubmit tests (unit, integration, static analysis). Peer code review with required approvers. | Cloud Build triggers on pull requests |
| Build | Fail the build when a test fails. Block an image that has vulnerabilities at a set severity level. | Cloud Build steps, On-Demand Scanning |
| Before deploy | Approval where a human decision adds value. Deploy only verified images. | Cloud Build approvals, Cloud Deploy approvals, Binary Authorization |
| Infrastructure change | Validate the Terraform plan against policy before apply. | Security Command Center IaC validation, `gcloud beta terraform vet` (Preview) |
| Runtime guardrails | Deny non-compliant configurations at the API or in the cluster. | Organization Policy custom constraints, Policy Controller |
| Rollout | Canary with automated analysis and bake time. Roll back on failure. | Cloud Deploy canary, verification, and analysis |
| After rollout | Alert on SLO burn rate. Compare new incidents with recent rollouts. | Cloud Monitoring |

Sources: [Google Cloud's approach to change](https://docs.cloud.google.com/docs/cloud-approach-to-change), [Create and manage build triggers](https://docs.cloud.google.com/build/docs/automating-builds/create-manage-triggers), [Use On-Demand Scanning in your Cloud Build pipeline](https://docs.cloud.google.com/artifact-analysis/docs/ods-cloudbuild), [Gate builds on approval](https://docs.cloud.google.com/build/docs/securing-builds/gate-builds-on-approval), [Promote your release and manage approvals](https://docs.cloud.google.com/deploy/docs/promote-release), [Implement shift-left security](https://docs.cloud.google.com/architecture/framework/security/implement-shift-left-security), [Validate your IaC against your Google Cloud organization's policies](https://docs.cloud.google.com/security-command-center/docs/validate-iac), [Policy validation](https://docs.cloud.google.com/docs/terraform/policy-validation), [Create custom constraints](https://docs.cloud.google.com/organization-policy/create-custom-constraints), [Policy Controller overview](https://docs.cloud.google.com/kubernetes-engine/policy-controller/docs/overview), [Run analysis jobs in Cloud Deploy](https://docs.cloud.google.com/deploy/docs/analysis), [Alerting on your burn rate](https://docs.cloud.google.com/stackdriver/docs/solutions/slo-monitoring/alerting-on-budget-burn-rate).

### Code review and change approval

- Replace heavyweight change-approval processes with peer review ([DevOps capabilities](https://docs.cloud.google.com/architecture/devops)).
- Work in small batches. Small batches give shorter lead times and faster feedback loops ([DevOps capabilities](https://docs.cloud.google.com/architecture/devops)).
- At Google, designated reviewers for each code directory must approve a change. They see the code, the tests, and the presubmit results. A substantial change after approval needs a new review ([Google Cloud's approach to change](https://docs.cloud.google.com/docs/cloud-approach-to-change)).
- Google admits a change to production only if a party distinct from the author reviewed and approved it. Google published these concepts as the SLSA framework ([Google Cloud's approach to change](https://docs.cloud.google.com/docs/cloud-approach-to-change)).

### Automated tests and analysis

Google moves tests to the start of development ("shift left") because the cost of a bug increases the later you find it ([Google Cloud's approach to change](https://docs.cloud.google.com/docs/cloud-approach-to-change)).

| Control | What it finds |
|---|---|
| Unit and integration tests | Wrong behavior. Google requires integration tests for every critical user journey. |
| Fuzzing | Hidden flaws, found with random inputs |
| Static analysis | Erroneous, inefficient, or deprecated code patterns. Google checks each change and scans the whole codebase when it adds a new check. |
| Dynamic analysis | Problems that occur only when code runs, such as memory violations and race conditions |
| Qualification tests | Large-scale functionality, business requirements (synthetic workloads), resistance to infrastructure failure (fault injection), serving capacity (load tests), and safe rollback |

Source: [Google Cloud's approach to change](https://docs.cloud.google.com/docs/cloud-approach-to-change).

Two Cloud Build details make a gate real. On-Demand Scanning in the pipeline can block a build when the image has vulnerabilities at a set severity ([Use On-Demand Scanning in your Cloud Build pipeline](https://docs.cloud.google.com/artifact-analysis/docs/ods-cloudbuild)). A step with `allowFailure: true` lets the build succeed when that step fails, so do not set it on a test that is a gate ([Build configuration file schema](https://docs.cloud.google.com/build/docs/build-config-file-schema)). Load and fault-injection testing are in [Reliability in production](note:6.6-production-reliability).

### Policy as code

| Tool | Where it checks | What to know |
|---|---|---|
| Organization Policy custom constraints | At the Google Cloud API, when a resource is created or updated | Defined in YAML with CEL conditions. Test with Policy Simulator, then with dry-run mode. |
| Security Command Center IaC validation | In CI, on a Terraform plan file | Checks the plan against the organization policies and Security Health Analytics detectors in your deployed postures. Available in the Premium, Standard-legacy, and Enterprise (deprecated) tiers, with activation at the organization level. Works with Cloud Build, Jenkins, and GitHub Actions. |
| `gcloud beta terraform vet` (Preview) | In CI, on a Terraform plan | Warns about violations or halts the deployment before production. Uses a central policy library. |
| Policy Controller | In GKE clusters, as admission control and audit | Based on Open Policy Agent Gatekeeper. Has prebuilt policy bundles. |

Sources: [Create custom constraints](https://docs.cloud.google.com/organization-policy/create-custom-constraints), [Validate your IaC against your Google Cloud organization's policies](https://docs.cloud.google.com/security-command-center/docs/validate-iac), [Policy validation](https://docs.cloud.google.com/docs/terraform/policy-validation), [Policy Controller overview](https://docs.cloud.google.com/kubernetes-engine/policy-controller/docs/overview).

Use both layers. The CI check gives fast feedback in the pull request. The constraint also stops changes that skip the pipeline. ## Production readiness reviews

A PRR is the usual first step when an SRE team takes on a service. It has two objectives. It verifies that the service meets the standards of production setup and operational readiness. It also improves reliability and reduces the number and severity of incidents ([The Evolving SRE Engagement Model](https://sre.google/sre-book/evolving-sre-engagement-model/)).

The simple PRR model has these phases ([The Evolving SRE Engagement Model](https://sre.google/sre-book/evolving-sre-engagement-model/)):

1. **Engagement.** Agree on an SLO or SLA, on disruptive design changes, and on training schedules.
2. **Analysis.** Use a PRR checklist. For example: does an update change an unreasonably large part of the system at once? Does the service report errors to central logging? Is every user-visible failure monitored, with alerting? Also check recent incidents, postmortems, and their follow-up tasks.
3. **Improvements and refactoring.** Prioritize fixes by their importance for reliability, and agree on a plan.
4. **Training.** Train the SRE team that takes over the service.
5. **Onboarding.** Transfer production responsibilities progressively.
6. **Continuous improvement.** Keep the standards while the service changes.

The operational readiness recommendations of the Well-Architected Framework are in [The operational excellence pillar](note:6.1-operational-excellence).

## Postmortem action items

A postmortem without action items is not effective. Good action items have these characteristics:

| Characteristic | Rule |
|---|---|
| Ownership | Each action item has an owner and a tracking number. Use one owner with several collaborators. |
| Prioritization | Each action item has a priority. |
| Measurability | Each action item has a verifiable end state, for example "Add an alert when more than X% of our machines have been taken away from us". |
| Preventive action | Each theme has items that prevent or mitigate a recurrence. |

Source: [Postmortem Culture: Learning from Failure](https://sre.google/workbook/postmortem-culture/).

More rules from the same chapter ([Postmortem Culture: Learning from Failure](https://sre.google/workbook/postmortem-culture/)):

- Change automated systems and processes. An action item that tries to change human behavior is less reliable.
- File action items as bugs in a central tracker, and monitor their closure.
- Reward the closure of action items, not only the writing of postmortems.
- If incidents repeat, ask if action items take too long to close, or if feature work always wins over reliability fixes.

Do not add complexity to fix a problem that is unlikely to happen again ([Conduct thorough postmortems](https://docs.cloud.google.com/architecture/framework/reliability/conduct-postmortems)). The error budget policy can force priority: a large incident needs at least one P0 action item ([Example Error Budget Policy](https://sre.google/workbook/error-budget-policy/)). The postmortem process itself is in [Testing, validation, and root cause analysis](note:4.1-testing-and-troubleshooting).

## Exam traps

- **A 100% SLO.** It is the wrong target. It leaves no error budget for change ([Set realistic targets for reliability](https://docs.cloud.google.com/architecture/framework/reliability/set-targets)).
- **An error budget policy as a punishment.** The example policy says that it is not a punishment for missing SLOs ([Example Error Budget Policy](https://sre.google/workbook/error-budget-policy/)).
- **A release freeze for someone else's outage.** If a company-wide network problem, or another team that froze its releases, used the budget, feature work can continue ([Example Error Budget Policy](https://sre.google/workbook/error-budget-policy/)).
- **An SRE team that sets the SLO alone.** The product manager, the developers, and the SREs must approve the error budget policy ([Implementing SLOs](https://sre.google/workbook/implementing-slos/)).
- **A heavyweight change-approval process.** DORA recommends peer review instead ([DevOps capabilities](https://docs.cloud.google.com/architecture/devops)).
- **Cloud Deploy's Deployment failure rate used as change failure rate.** Cloud Deploy counts a deployment as successful when the pods are ready ([Viewing metrics in Cloud Deploy](https://docs.cloud.google.com/deploy/docs/metrics)).
- **Action items like "Improve monitoring" with no owner.** Action items need an owner, a priority, a tracking number, and a verifiable end state ([Postmortem Culture: Learning from Failure](https://sre.google/workbook/postmortem-culture/)).
- **A new constraint enforced directly in production.** Test it with Policy Simulator and dry-run mode first ([Create custom constraints](https://docs.cloud.google.com/organization-policy/create-custom-constraints)).
