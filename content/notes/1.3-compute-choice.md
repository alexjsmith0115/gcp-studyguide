## Why it matters

The compute platform is the first decision in most designs, and it sets the operating model for years. The exam gives you a workload and one or two constraints: operational overhead, portability, scale to zero, run time, state, GPUs, licensing, or migration speed. You must pick the platform that Google recommends for that constraint. Google's default order is serverless first (Cloud Run), then GKE Autopilot, then GKE Standard or Compute Engine when you need more control.

## Key points

- Google recommends that you consider serverless first unless you need Kubernetes. If the workload does not fit serverless, Google recommends GKE Autopilot ([Select a managed container runtime environment](https://docs.cloud.google.com/architecture/select-managed-container-runtime-environment)).
- Cloud Run has four resource types. Services answer HTTP requests, jobs run tasks to completion, worker pools run non-HTTP background work, and instances (Preview) run one singleton ([What is Cloud Run](https://docs.cloud.google.com/run/docs/overview/what-is-cloud-run)).
- A Cloud Run service fits when the app serves HTTP, HTTP/2, WebSockets, or gRPC and keeps no local persistent files. It must also run as many instances and need no more than 8 CPU and 32 GiB per instance ([Is my app a good fit for a Cloud Run service?](https://docs.cloud.google.com/run/docs/fit-for-run)).
- A Cloud Run service request can run for up to 60 minutes (default 5 minutes). A Cloud Run job task can run for up to 168 hours (7 days), or 1 hour with GPUs ([Configure request timeout](https://docs.cloud.google.com/run/docs/configuring/request-timeout), [Set task timeout for jobs](https://docs.cloud.google.com/run/docs/configuring/task-timeout)).
- Cloud Run functions (formerly Cloud Functions 2nd gen) are Cloud Run services that Cloud Run builds from source code. Event-driven functions receive events through Eventarc ([Compare Cloud Run functions](https://docs.cloud.google.com/run/docs/functions/comparison), [Cloud Run function triggers](https://docs.cloud.google.com/run/docs/function-triggers)).
- Autopilot is the recommended GKE mode. Use Standard only when the workload needs privileges or configuration that Autopilot constraints do not allow ([About GKE modes of operation](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/choose-cluster-mode)).
- Autopilot bills general-purpose Pods by their resource requests. Pods that select specific hardware use node-based billing plus a node management premium ([GKE Autopilot overview](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/autopilot-overview)).
- Every GKE cluster pays a flat cluster management fee per hour, in any mode, size, or topology ([GKE pricing](https://cloud.google.com/kubernetes-engine/pricing)).
- For new users and new projects, Google recommends Cloud Run instead of App Engine ([Choose an App Engine environment](https://docs.cloud.google.com/appengine/docs/the-appengine-environments)).
- Google Cloud VMware Engine runs vSphere, vCenter, vSAN, NSX, and HCX on dedicated bare metal. Teams keep their VMware tools and processes ([VMware Engine overview](https://docs.cloud.google.com/vmware-engine/docs/overview)).
- Bare Metal Solution gives you dedicated bare-metal servers for specialized workloads under a bring-your-own-license model. You manage the OS and everything above it ([Bare Metal Solution overview](https://docs.cloud.google.com/bare-metal/docs/bms-overview)).
- Batch schedules and runs batch jobs on Compute Engine VMs that it creates and deletes for you. Batch itself has no additional cost ([Get started with Batch](https://docs.cloud.google.com/batch/docs/get-started)).

## Decision path

Use this order when a question asks which platform to choose. Stop at the first row that matches a hard requirement.

| Workload signal | Start with | Why |
|---|---|---|
| A VMware estate must leave the data center fast, with the same tools and processes | Google Cloud VMware Engine | It runs the full VMware stack and is compatible with existing VMware tools, skills, and processes. |
| Oracle or other specialized software that needs dedicated bare-metal servers or a third-party hypervisor | Bare Metal Solution | It provides bare-metal servers for third-party virtualization and apps that need low-level server access. |
| You need OS, kernel, or disk control, or a lift-and-shift of a VM | Compute Engine (with managed instance groups) | You choose the OS, machine type, and disks, and you control the VM lifecycle. |
| Stateless HTTP, gRPC, or event handling in a container, or code you can containerize | Cloud Run service (or Cloud Run function) | Least operational overhead, scale to zero, pay per use. |
| A script or parallel batch that runs to completion within 7 days | Cloud Run job | Tasks run to completion, in parallel as an array job. |
| Always-on pull consumer (Pub/Sub pull, Kafka) with no HTTP endpoint | Cloud Run worker pool | Designed for non-HTTP, pull-based background processing. |
| Needs the Kubernetes API, Helm, CRDs, persistent volumes, complex service networking, or RBAC multi-tenancy | GKE Autopilot | Kubernetes with Google-managed nodes and a workload SLA. |
| Needs privileged Pods or direct control of nodes | GKE Standard | You manage node pools, node settings, and autoscaling. |
| Large HPC or batch jobs on VMs, with a queue and scheduler | Batch | Batch provisions and deletes the VMs for each job. |

## Compare the main platforms

The exam criteria map to clear differences between the platforms.

| Criterion | Compute Engine | GKE Standard | GKE Autopilot | Cloud Run |
|---|---|---|---|---|
| Control vs operational overhead | You choose the OS, software, CPU, memory, disks, and GPUs. You operate and patch the OS (VM Manager helps). | You control node pools, node settings, security constraints, and scaling. | GKE manages nodes, scaling, and security defaults. | Limited control. You configure environment variables, concurrency, and network connections. |
| Scale to zero | A MIG can scale in to zero only with schedules or some Monitoring metrics, not with CPU. | The cluster management fee continues. | The cluster management fee continues. You pay for Pod requests. | Yes, by default. No charge when idle unless you set minimum instances. |
| Run time | You decide when to stop or delete a VM. | You choose node upgrade strategies to manage disruption. | Pods can run up to 7 days when protected from eviction. | 60 minutes per request; 7 days per job task. |
| State | Persistent disks; stateful MIGs keep disks, names, and IPs. | Full Kubernetes volume support. | Full Kubernetes volume support. | In-memory file system; use Cloud Storage or NFS for durable data. |
| GPUs | Accelerator-optimized A and G series, or GPUs attached to N1. | GPU node pools. | GPUs and TPUs, including reservations. | NVIDIA L4 or RTX PRO 6000; can scale to zero; needs instance-based billing. |
| Billing unit | Per second after a 1-minute minimum. | The nodes' Compute Engine VMs plus the cluster fee. | Pod resource requests (general-purpose) plus the cluster fee. | Per use, with 100 ms granularity. |

### Cloud Run or GKE Autopilot?

Both run containers, integrate with Cloud Load Balancing, and support VPC networking, IAP, and Google Cloud Armor. The selection guide lists the technical reasons to move from Cloud Run to Autopilot ([Select a managed container runtime environment](https://docs.cloud.google.com/architecture/select-managed-container-runtime-environment)):

- **Kubernetes dependency.** The app calls Kubernetes APIs, uses custom resources, or ships as a Helm chart. Cloud Run does not support Kubernetes.
- **Stateful workloads.** Autopilot supports Kubernetes volumes backed by Persistent Disk, including self-managed databases.
- **Long-lived work.** Autopilot Pods can run up to seven days when protected from eviction. Cloud Run has a maximum task timeout.
- **Complex service networking.** Autopilot adds namespaces, network policies, cluster DNS, and the Gateway API.
- **Multi-tenancy.** Complex organizations can use Kubernetes RBAC.
- **Large instances.** One Cloud Run instance has lower CPU and memory limits than an Autopilot Pod.

Organizational facts also count. A team with Kubernetes skills, tooling such as Argo CD or Helm, or a Kubernetes-first strategy may choose Autopilot. A small team may choose Cloud Run: it has no control plane to upgrade, and it can make hiring simpler ([Select a managed container runtime environment](https://docs.cloud.google.com/architecture/select-managed-container-runtime-environment), [Where should I run my stuff?](https://cloud.google.com/blog/topics/developers-practitioners/where-should-i-run-my-stuff-choosing-google-cloud-compute-option)).

For portability, GKE uses open source Kubernetes, and a fleet can include clusters outside Google Cloud ([Fleet management overview](https://docs.cloud.google.com/kubernetes-engine/fleet-management/docs)). GKE Enterprise no longer exists as a separate edition: its features are now part of GKE, or are separate products that you can use with GKE ([GKE Enterprise release notes](https://docs.cloud.google.com/kubernetes-engine/enterprise/docs/release-notes)).

## Cloud Run resource types

Pick the Cloud Run resource that matches how the code runs.

| Resource | Use it for | Key behavior |
|---|---|---|
| Service | Websites, APIs, microservices, Pub/Sub push and Eventarc targets, AI inference | Unique HTTPS endpoint, request-based autoscaling, traffic splitting between revisions. |
| Job | Scripts, database migrations, scheduled reports, array jobs over many files, batch inference | Runs tasks to completion, in parallel; you execute it manually, on a schedule, or from a workflow. |
| Worker pool | Pull-based consumers such as Kafka, Pub/Sub pull, and RabbitMQ | No endpoint or URL. No built-in autoscaling: you set the instance count manually, or you deploy CREMA to scale on external metrics such as Pub/Sub backlog. |
| Instance (Preview) | A long-lived singleton runtime | One instance only, with its own URL. |

Sources: [What is Cloud Run](https://docs.cloud.google.com/run/docs/overview/what-is-cloud-run), [Deployment options and resource model](https://docs.cloud.google.com/run/docs/resource-model), [Deploy worker pools to Cloud Run](https://docs.cloud.google.com/run/docs/deploy-worker-pools), [Autoscale worker pools with external metrics](https://docs.cloud.google.com/run/docs/configuring/workerpools/crema-autoscaling).

Worker pools do not scale automatically. To autoscale a worker pool, you deploy the CREMA autoscaler as a Cloud Run service. CREMA reads external metrics and updates the instance count of the worker pool ([What is Cloud Run](https://docs.cloud.google.com/run/docs/overview/what-is-cloud-run), [Autoscale worker pools with external metrics](https://docs.cloud.google.com/run/docs/configuring/workerpools/crema-autoscaling)).

Cloud Run services have two billing settings. Request-based billing (the default) charges only while an instance processes requests. Instance-based billing charges for the whole instance lifetime and lets code use CPU in the background after a response. All Cloud Run jobs use instance-based billing ([Billing settings for services](https://docs.cloud.google.com/run/docs/configuring/billing-settings)).

### Cloud Run functions

A Cloud Run function is a Cloud Run service that Cloud Run builds from your source code. You get the same controls as any service: Direct VPC egress, GPUs, volume mounts, and traffic splitting ([Compare Cloud Run functions](https://docs.cloud.google.com/run/docs/functions/comparison)).

| | Cloud Run functions | Cloud Run functions (1st gen) |
|---|---|---|
| Former name | Cloud Functions (2nd gen) | Cloud Functions (1st gen) |
| Request timeout | Up to 60 minutes for HTTP functions | Up to 9 minutes |
| Concurrency | Up to 1,000 requests per instance | 1 request per instance |
| Event sources | Any Eventarc event type, including 90+ sources through Cloud Audit Logs | 7 direct sources |
| Traffic splitting | Supported | Not supported |

Source: [Compare Cloud Run functions](https://docs.cloud.google.com/run/docs/functions/comparison).

All event-driven functions use Eventarc for event delivery. Pub/Sub and Cloud Storage triggers are types of Eventarc triggers ([Cloud Run function triggers](https://docs.cloud.google.com/run/docs/function-triggers)). Choose a function for single-purpose, event-driven code. Choose a service when you build and own the container image ([Deployment options and resource model](https://docs.cloud.google.com/run/docs/resource-model)).

## App Engine positioning

App Engine still runs, but Google now recommends Cloud Run for new projects and for modernizing existing apps ([Choose an App Engine environment](https://docs.cloud.google.com/appengine/docs/the-appengine-environments)). If an exam scenario already uses App Engine, know the two environments:

| | Standard environment | Flexible environment |
|---|---|---|
| Runs in | A language sandbox | Docker containers on Compute Engine VMs |
| Scale to zero | Yes | No, minimum 1 instance |
| Startup and deploy time | Seconds | Minutes |
| Good for | Spiky traffic, very low cost | Custom runtimes, native code, steady traffic |

Source: [Choose an App Engine environment](https://docs.cloud.google.com/appengine/docs/the-appengine-environments).

## Specialized platforms

| Platform | Use when | Watch out |
|---|---|---|
| Google Cloud VMware Engine | You must move vSphere workloads quickly and keep VMware tools, operations, and policies. Also for DR and virtual desktops on VMware. | You still run a VMware platform. Google suggests that you modernize the apps with Google Cloud services later, at your own pace. |
| Bare Metal Solution | Specialized workloads such as Oracle need dedicated servers, a third-party hypervisor, or low-level server access. | You own the OS, database, backups, patches, and licenses (BYOL). Google manages the infrastructure and the network. |
| Compute Engine bare metal instances | You need a Compute Engine machine type with no hypervisor (`-metal` machine types) in a normal VPC. | These instances are not related to Bare Metal Solution. |
| Batch | HPC, ML, or data-processing jobs need queuing and VM provisioning at scale. | Jobs use the Compute Engine default service account unless you choose another one, and that account has the Editor role by default. |

Sources: [VMware Engine overview](https://docs.cloud.google.com/vmware-engine/docs/overview), [Google Cloud VMware Engine](https://cloud.google.com/vmware-engine), [Bare Metal Solution overview](https://docs.cloud.google.com/bare-metal/docs/bms-overview), [Compare AWS and Azure services to Google Cloud](https://docs.cloud.google.com/docs/get-started/aws-azure-gcp-service-comparison), [Machine families resource and comparison guide](https://docs.cloud.google.com/compute/docs/machine-resource), [Get started with Batch](https://docs.cloud.google.com/batch/docs/get-started).

Migration speed matters here. VMware Engine deploys HCX automatically when it creates a private cloud. HCX supports live, cold, and bulk migration from your VMware environment ([Use VMware HCX to migrate VMware VMs](https://docs.cloud.google.com/vmware-engine/docs/workloads/howto-migrate-vms-using-hcx)). For VM-to-Compute Engine moves and other tools, see [Data and system migration tooling](note:5.1-migration-tooling). For licensing decisions such as BYOL, see [Licensing and financial impact of a migration](note:1.4-licensing-and-financials) and [Choosing compute resources](note:1.3-compute-resources).

## AWS mapping

| AWS | Google Cloud | Difference that matters |
|---|---|---|
| Amazon EC2 | Compute Engine | Custom machine types let you set vCPU and memory directly on N and E series. |
| EC2 Auto Scaling | Managed instance groups with the autoscaler | Regional MIGs spread VMs across three zones by default. |
| AWS Lambda | Cloud Run functions | A function is a Cloud Run service built from source; HTTP functions run up to 60 minutes and serve up to 1,000 concurrent requests per instance. |
| AWS Fargate, AWS App Runner | Cloud Run | No cluster to create; scale to zero by default. |
| Amazon EKS | GKE (Autopilot recommended) | Autopilot bills general-purpose Pods by resource requests, and GKE manages the nodes. |
| AWS Elastic Beanstalk | App Engine | Google recommends Cloud Run for new apps. |
| AWS Batch | Batch | Batch has no additional cost; you pay for the VMs. |
| VMware Cloud on AWS | Google Cloud VMware Engine | Standard VMware Engine networks are global and connect to your VPC networks through VPC Network Peering. |
| Amazon RDS for Oracle | Bare Metal Solution | Bare Metal Solution is BYOL and you run the database yourself; it is not a managed database. |

An AWS habit to drop: on AWS, a container service often means a cluster (ECS or EKS). On Google Cloud, the default container answer is Cloud Run, which needs no cluster ([What is Cloud Run](https://docs.cloud.google.com/run/docs/overview/what-is-cloud-run), [Select a managed container runtime environment](https://docs.cloud.google.com/architecture/select-managed-container-runtime-environment)).

## Exam traps

- **GKE for a simple stateless API.** A small team with a stateless HTTP service and no Kubernetes need gets Cloud Run. Google recommends serverless first ([Select a managed container runtime environment](https://docs.cloud.google.com/architecture/select-managed-container-runtime-environment)).
- **GKE Standard as the default GKE answer.** Autopilot is the recommended mode. Pick Standard only for privileged Pods or node-level control ([About GKE modes of operation](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/choose-cluster-mode)).
- **Cloud Run for a Helm-packaged app or an app that calls the Kubernetes API.** Cloud Run does not support Kubernetes. The answer is Autopilot ([Select a managed container runtime environment](https://docs.cloud.google.com/architecture/select-managed-container-runtime-environment)).
- **A Cloud Run service for multi-hour processing.** A service request stops at 60 minutes. Use a Cloud Run job (tasks up to 7 days) or Batch ([Configure request timeout](https://docs.cloud.google.com/run/docs/configuring/request-timeout), [Set task timeout for jobs](https://docs.cloud.google.com/run/docs/configuring/task-timeout), [Get started with Batch](https://docs.cloud.google.com/batch/docs/get-started)).
- **A worker pool for an HTTP API.** Worker pools have no load-balanced endpoint or URL. Use a Cloud Run service ([What is Cloud Run](https://docs.cloud.google.com/run/docs/overview/what-is-cloud-run)).
- **App Engine for a new application.** Google recommends Cloud Run for new projects ([Choose an App Engine environment](https://docs.cloud.google.com/appengine/docs/the-appengine-environments)).
- **Cloud Functions (1st gen) limits in a new design.** Current Cloud Run functions allow 60-minute HTTP requests and 1,000 concurrent requests per instance ([Compare Cloud Run functions](https://docs.cloud.google.com/run/docs/functions/comparison)).
- **Refactoring a large VMware estate under a tight deadline.** VMware Engine keeps tools and processes and moves VMs with HCX ([VMware Engine overview](https://docs.cloud.google.com/vmware-engine/docs/overview), [Use VMware HCX to migrate VMware VMs](https://docs.cloud.google.com/vmware-engine/docs/workloads/howto-migrate-vms-using-hcx)).
- **Bare Metal Solution as a managed Oracle service.** You own the OS, database, backups, patches, and licenses ([Bare Metal Solution overview](https://docs.cloud.google.com/bare-metal/docs/bms-overview)).
- **A "GKE Enterprise edition" answer.** GKE is now one offering without editions or tiers ([GKE Enterprise release notes](https://docs.cloud.google.com/kubernetes-engine/enterprise/docs/release-notes)).
