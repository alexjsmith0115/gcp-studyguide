## Why it matters

Objective 6.3 asks how you release changes with low risk, and how you go back when a release fails. The exam gives a requirement such as "limit the impact of a bad release", "test the new version with production traffic but no user impact", or "change the schema with no downtime". You choose a rollout strategy, the platform feature that implements it, and the gates and the rollback path around it.

## Key points

- Google Cloud rolls out all production changes in waves: binaries, configurations, schema updates, capacity changes, and access control lists. Each step has a bake time, and a typical rollout takes one week ([Google Cloud's approach to change](https://docs.cloud.google.com/docs/cloud-approach-to-change)).
- In an incident, Google's playbooks tell responders to roll back a recent rollout if they cannot rule it out as the cause ([Google Cloud's approach to change](https://docs.cloud.google.com/docs/cloud-approach-to-change)).
- A canary sends only part of the production traffic to a release. The cost to the error budget is in proportion to the traffic that the defect reaches ([Canarying Releases](https://sre.google/workbook/canarying-releases/)).
- Blue/green keeps two environments. The cutover and the rollback are router changes with no downtime, but the setup uses twice the resources ([Canarying Releases](https://sre.google/workbook/canarying-releases/)).
- The Application Load Balancer splits traffic by weight between backend services. It can also mirror requests to a test backend, and it does not wait for the mirror's response ([Traffic management overview](https://docs.cloud.google.com/load-balancing/docs/https/traffic-management-global), [Set up traffic management](https://docs.cloud.google.com/load-balancing/docs/https/setting-up-global-traffic-mgmt)).
- Cloud Deploy has two strategies, standard and canary. The canary strategy does not support Cloud Run jobs. A rollout to a target with `requireApproval: true` waits for an approver ([Use a deployment strategy](https://docs.cloud.google.com/deploy/docs/deployment-strategies), [Canary Deployments to Cloud Run](https://docs.cloud.google.com/deploy/docs/deployment-strategies/canary/cloud-run), [Overview of Cloud Deploy](https://docs.cloud.google.com/deploy/docs/overview)).
- A Cloud Deploy rollback is a new rollout of an earlier release. By default, it starts in the `stable` phase, so it restores 100% at once ([Overview of Cloud Deploy](https://docs.cloud.google.com/deploy/docs/overview), [rollbackTarget](https://docs.cloud.google.com/deploy/docs/api/reference/rest/v1/projects.locations.deliveryPipelines/rollbackTarget)).
- Cloud Run can deploy a revision with no traffic and a tag. You test the revision at its own URL, then move traffic to it ([Rollbacks, gradual rollouts, and traffic migration](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration)).
- A MIG canary update runs two instance templates at the same time. To roll back, you start a new update with the old template ([Automatically apply VM configuration updates in a MIG](https://docs.cloud.google.com/compute/docs/instance-groups/rolling-out-updates-to-managed-instance-groups)).
- A feature flag lets you turn off a feature without a new deployment ([Reliable Product Launches at Scale](https://sre.google/sre-book/reliable-product-launches/)).
- During a canary, the old revision and the new revision serve traffic at the same time. So a schema change must work with both versions ([Canary Deployments to Cloud Run](https://docs.cloud.google.com/deploy/docs/deployment-strategies/canary/cloud-run), [Schema update best practices](https://docs.cloud.google.com/spanner/docs/schema-updates-best-practices)).

## Choose a deployment strategy

| Strategy | What happens | Rollback | Extra cost | Choose it when |
|---|---|---|---|---|
| All at once (recreate) | Every instance changes to the new version at the same time. | Deploy the old version again. | None | You can detect and resolve defects quickly. |
| Rolling | Instances change in small batches. | Start a new update to the old version. | A few surge instances | Stateless services where two versions can run side by side. |
| Blue/green | Deploy to an idle copy, test it, then move all traffic at once. | Move the traffic back. | A second full environment | You need an instant, full rollback. |
| Canary | A small share of traffic goes to the new version. You compare it with the old version, then increase the share in steps. | Send all traffic back to the old version. | Small | The default for production services. |
| A/B test | Users are split by an attribute, such as a cookie or IP address, to compare two versions. | Remove the split. | Small | You measure whether a change improves the user experience. |
| Shadow (traffic teeing) | A copy of live requests goes to the new version. Its responses are discarded. | None needed: users never see it. | A second backend | You need realistic traffic before any user sees the version, and the copy cannot change shared state. |

Sources: [Canarying Releases](https://sre.google/workbook/canarying-releases/), [Automatically apply VM configuration updates in a MIG](https://docs.cloud.google.com/compute/docs/instance-groups/rolling-out-updates-to-managed-instance-groups), [Splitting traffic (App Engine)](https://docs.cloud.google.com/appengine/docs/standard/splitting-traffic), [Set up traffic management](https://docs.cloud.google.com/load-balancing/docs/https/setting-up-global-traffic-mgmt), [Reliable Product Launches at Scale](https://sre.google/sre-book/reliable-product-launches/), [Google Cloud's approach to change](https://docs.cloud.google.com/docs/cloud-approach-to-change).

Use these rules to pick between them:

- **Make the canary your default.** Tests do not cover every production case, so some defects reach production. A release that goes everywhere at once sends every defect to every user ([Canarying Releases](https://sre.google/workbook/canarying-releases/)). Google Cloud uses canaries in its rollout process for all types of production changes ([Google Cloud's approach to change](https://docs.cloud.google.com/docs/cloud-approach-to-change)).
- **Run one canary at a time.** Two canaries at the same time make the system state hard to reason about, and their signals can mix ([Canarying Releases](https://sre.google/workbook/canarying-releases/)).
- **Blue/green by itself is a before/after comparison.** To use it as a canary, send part of the traffic to each environment at the same time ([Canarying Releases](https://sre.google/workbook/canarying-releases/)).
- **Shadow testing is weak for stateful systems.** The copied traffic can change shared state. For example, a shared cache gives the shadow a false hit rate ([Canarying Releases](https://sre.google/workbook/canarying-releases/)).
- **Match the canary duration to the release rate.** If you release daily, a canary cannot last a week ([Canarying Releases](https://sre.google/workbook/canarying-releases/)).

How to evaluate a canary (control group, SLI metrics, bake time) is in [Testing, validation, and root cause analysis](note:4.1-testing-and-troubleshooting).

## Implement each strategy on Google Cloud

| Strategy | Compute Engine (MIG) | GKE | Cloud Run |
|---|---|---|---|
| Rolling | Proactive update with `maxSurge` and `maxUnavailable`. With `maxUnavailable=0` and `maxSurge` above 0, the MIG removes an old VM only after its new VM runs. | A Deployment rolling update replaces Pods step by step, with no downtime by design. | Not needed. Each deployment creates a new revision. |
| Blue/green | Two MIGs as two backend services. Change the URL map weights. | Two Deployments. Change the Gateway weights. | Deploy with `--no-traffic --tag green`, test the tag URL, then send 100% to the revision. |
| Canary | `--canary-version=template=NEW,target-size=10%` on `rolling-action start-update`. | Cloud Deploy canary: service networking (a share of Pods) or Gateway API (a share of traffic). | Cloud Deploy canary, or `gcloud run services update-traffic --to-revisions=REVISION=5`. |
| Rollback | A new update with the old template. `--max-unavailable=100%` is fastest. | `kubectl rollout undo`, or a Cloud Deploy rollback. | `update-traffic` to the old revision, or a Cloud Deploy rollback. |

Sources: [Automatically apply VM configuration updates in a MIG](https://docs.cloud.google.com/compute/docs/instance-groups/rolling-out-updates-to-managed-instance-groups), [Performing rolling updates](https://docs.cloud.google.com/kubernetes-engine/docs/archive/updating-apps), [Gateway traffic management](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/traffic-management), [Canary-deploy an application to a target](https://docs.cloud.google.com/deploy/docs/deploy-app-canary), [Rollbacks, gradual rollouts, and traffic migration](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration), [Deploy container images to Cloud Run services](https://docs.cloud.google.com/run/docs/deploying).

The load balancer gives these traffic controls across backend services:

| Need | Load balancer feature |
|---|---|
| Canary, blue/green, or A/B across backend services | `weightedBackendServices` in a URL map route rule, for example 95% and 5% |
| Send one group of users to a version, for example mobile clients | Traffic steering on request headers |
| Shadow test | `requestMirrorPolicy`, with `mirrorPercent` to mirror only a share of requests |

Sources: [Traffic management overview](https://docs.cloud.google.com/load-balancing/docs/https/traffic-management-global), [Set up traffic management](https://docs.cloud.google.com/load-balancing/docs/https/setting-up-global-traffic-mgmt).

Request mirroring works only when both backend services use managed instance groups, zonal NEGs, or hybrid NEGs. It does not support serverless NEGs, internet NEGs, or Private Service Connect backends ([Set up traffic management](https://docs.cloud.google.com/load-balancing/docs/https/setting-up-global-traffic-mgmt)).

App Engine has its own split. It splits traffic between versions by IP address or by cookie. A cookie split is more precise, which matters for an A/B test ([Splitting traffic](https://docs.cloud.google.com/appengine/docs/standard/splitting-traffic)).

Platform upgrades are releases too. For a GKE Standard node pool, a blue-green upgrade keeps the old nodes available for rollback while you validate the workloads. Autopilot clusters use surge upgrades ([Node upgrade strategies](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/node-pool-upgrade-strategies)). Cluster settings are in [Configuring GKE](note:2.3-gke).

## Cloud Deploy: the managed release process

Cloud Deploy delivers a release to a sequence of targets. Targets are GKE clusters, GKE attached clusters, or Cloud Run services and jobs. A custom target type deploys to other systems ([Overview of Cloud Deploy](https://docs.cloud.google.com/deploy/docs/overview), [About custom targets](https://docs.cloud.google.com/deploy/docs/custom-targets)).

| Resource or feature | What it does | Exam cue |
|---|---|---|
| Delivery pipeline | Defines the promotion sequence, for example dev, staging, prod. | "Same artifact through every environment" |
| Release | Your CI system creates it. It holds the rendered manifests for each target and the image references. | "Build once, deploy many times" |
| Rollout | Deploys one release to one target. A promotion creates a new rollout on the next target. | "Promote" |
| Approval | `requireApproval: true` on a target. Cloud Deploy publishes a Pub/Sub message, so a ticketing system can run the approval. Approvers need `roles/clouddeploy.approver`. | "Change board", "ServiceNow approval" |
| Canary strategy | Phases such as `canary-25`, `canary-50`, then `stable`. You advance each phase. The first deployment to a target skips the canary phases. | "Progressive rollout" |
| Verification | Runs your test containers after a deployment. A non-zero exit code fails the rollout. | "Automated smoke test" |
| Analysis | Watches Cloud Monitoring alerting policies (or another metrics system) during the rollout. | "Roll back on SLO breach" |
| Deploy hooks | `predeploy` and `postdeploy` jobs run your programs. Google assumes that they are idempotent. | "Run a migration before deploy" |
| Automation rules | `promoteReleaseRule`, `timedPromoteReleaseRule`, `advanceRolloutRule`, and `repairRolloutRule` (retry, then roll back). | "No manual steps" |
| Deploy policy | Blocks rollouts on a pipeline or target during time windows. `roles/clouddeploy.policyOverrider` can override. | "Change freeze" |
| Parallel deployment | A multi-target deploys to several child targets at the same time. | "Deploy to prod in 4 regions" |

Sources: [Overview of Cloud Deploy](https://docs.cloud.google.com/deploy/docs/overview), [Promote your release and manage approvals](https://docs.cloud.google.com/deploy/docs/promote-release), [Manage rollouts](https://docs.cloud.google.com/deploy/docs/deployment-strategies/manage-rollout), [Verify your deployment](https://docs.cloud.google.com/deploy/docs/verify-deployment), [Run analysis jobs](https://docs.cloud.google.com/deploy/docs/analysis), [Run hooks before and after deploying](https://docs.cloud.google.com/deploy/docs/hooks), [Using automation rules](https://docs.cloud.google.com/deploy/docs/automation-rules), [Restrict deploy behavior using policies](https://docs.cloud.google.com/deploy/docs/deploy-policy), [Deploy to multiple targets at the same time](https://docs.cloud.google.com/deploy/docs/parallel).

Three design points come up often:

- **Pin the image by digest.** Google recommends SHA-qualified image names when you create a release. Then every target runs exactly the image that the earlier target tested ([Canary-deploy an application to a target](https://docs.cloud.google.com/deploy/docs/deploy-app-canary)).
- **Replace the default execution service account.** By default, Cloud Deploy runs as the Compute Engine default service account, which can have broad permissions. Set a different service account for each target ([Cloud Deploy service accounts](https://docs.cloud.google.com/deploy/docs/cloud-deploy-service-account)).
- **Automate the gates, not only the steps.** An `advanceRolloutRule` moves a rollout to the next phase automatically. Add verification or analysis, so that a failed check fails the rollout. With analysis and a `repairRolloutRule`, a failed check can roll back the target automatically ([Using automation rules](https://docs.cloud.google.com/deploy/docs/automation-rules), [Verify your deployment](https://docs.cloud.google.com/deploy/docs/verify-deployment), [Run analysis jobs](https://docs.cloud.google.com/deploy/docs/analysis)).

Cloud Build approvals, triggers, and the CI half of the pipeline are in [SDLC, CI/CD, and service provisioning](note:4.1-sdlc-cicd). Image signing and deploy-time checks with Binary Authorization are in [Software supply chain security](note:3.1-supply-chain).

## Feature flags: separate deployment from release

A feature flag lets you deploy code in an inactive state, then turn the feature on for more users over time. If the feature causes problems, you turn it off at once, with no new build and no rollback. Then you fix it ([Reliable Product Launches at Scale](https://sre.google/sre-book/reliable-product-launches/)).

Google's feature flag frameworks usually do the following ([Reliable Product Launches at Scale](https://sre.google/sre-book/reliable-product-launches/)):

1. Roll out many changes in parallel, each to a few servers, users, or datacenters.
2. Increase each change to a limited group, usually 1 to 10 percent of users.
3. Revert each change immediately and independently.
4. Measure how much each change improves the user experience.

Google uses flags for user interface changes and for server-side business logic. A flag separates a feature launch from the binary release. Google still rolls out binaries, configurations, and schema updates in waves ([Canarying Releases](https://sre.google/workbook/canarying-releases/), [Google Cloud's approach to change](https://docs.cloud.google.com/docs/cloud-approach-to-change)). For software as a service (SaaS) providers, App Lifecycle Manager (Preview, formerly SaaS Runtime) automates rollouts and feature flag management across tenants ([App Lifecycle Manager overview](https://docs.cloud.google.com/app-lifecycle-manager/overview)).

## Database schema changes during a release

The schema must work with the old and the new application version at the same time. A canary, a rolling update, and a rollback all run two versions against one database. Use the expand and contract sequence:

1. **Expand.** Add the new table, column, or index. Do not remove or rename anything. In Spanner, a new non-key column cannot be `NOT NULL` ([Make schema updates](https://docs.cloud.google.com/spanner/docs/schema-updates)).
2. **Deploy code that works with both schemas.**
3. **Contract.** Drop the old column only when no version still writes to it or reads from it ([Schema update best practices](https://docs.cloud.google.com/spanner/docs/schema-updates-best-practices)).

Each step is a separate release. Protect the data before the contract step; backup and point-in-time recovery are in [Data protection](note:2.2-data-protection).

More rules from the docs:

- **Test on production-like data.** A schema update can succeed on a test database and fail on production, because some updates depend on the data ([Schema update best practices](https://docs.cloud.google.com/spanner/docs/schema-updates-best-practices)).
- **Expect long operations.** Spanner schema updates need no downtime, but updates that validate data or backfill an index can take a long time ([Make schema updates](https://docs.cloud.google.com/spanner/docs/schema-updates)).
- **Do not replay migrations on every deployment.** Google does not recommend tools that run long series of upgrade and downgrade schema updates on each deployment for Spanner ([Schema update best practices](https://docs.cloud.google.com/spanner/docs/schema-updates-best-practices)).
- **Run the migration as its own idempotent step.** A Cloud Deploy `predeploy` hook runs before the deploy job. For an automated canary, it runs only in the first phase ([Run hooks before and after deploying](https://docs.cloud.google.com/deploy/docs/hooks)).

## AWS mapping

| AWS | Google Cloud | Difference that matters |
|---|---|---|
| AWS CodeDeploy | Cloud Deploy | Cloud Deploy has standard and canary strategies only. For blue/green, use Cloud Run tags and traffic, or load balancer weights. |
| CodePipeline manual approval action | `requireApproval` on a Cloud Deploy target | The approval belongs to the target, and Cloud Deploy publishes a Pub/Sub message for external approval systems. |
| Lambda alias with weighted traffic | Cloud Run revisions with traffic splits and tags | A tag gives a revision its own URL, so you can test it without serving traffic. |
| EC2 Auto Scaling instance refresh | MIG proactive update with a canary version | A MIG canary runs two instance templates, and you set a target size for the canary template. |
| ALB weighted target groups | URL map `weightedBackendServices` | The Google load balancer can also mirror requests for a shadow test. |

## Exam traps

- **"Roll back Cloud Run, then deploy the fix."** After you move traffic to an earlier revision, later deployments keep that split. The fix gets no traffic until you send traffic to the latest revision ([Rollbacks, gradual rollouts, and traffic migration](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration)).
- **"Test the new revision with 1% of users."** If no user may see the version yet, deploy it with `--no-traffic` and a tag, and test the tag URL ([Rollbacks, gradual rollouts, and traffic migration](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration)).
- **"Blue/green costs nothing extra."** It runs two full environments, so it uses twice the resources ([Canarying Releases](https://sre.google/workbook/canarying-releases/)).
- **"Shadow the payment service with mirrored traffic."** Copied requests can change shared state, and extra requests to a billing system can charge real customers. Shadow tests suit read-only or isolated services ([Canarying Releases](https://sre.google/workbook/canarying-releases/)).
- **"Start a second MIG canary while the first one runs."** Roll back the first canary fully, then start again ([Automatically apply VM configuration updates in a MIG](https://docs.cloud.google.com/compute/docs/instance-groups/rolling-out-updates-to-managed-instance-groups)).
- **"The first canary rollout to prod exposes 25% of traffic."** There is no old version on a new target, so Cloud Deploy skips the canary phases and deploys to 100% ([Manage rollouts](https://docs.cloud.google.com/deploy/docs/deployment-strategies/manage-rollout)).
- **"Rename the column in the same release as the code change."** The old version still runs during the canary and after a rollback. Expand first, and drop only when nothing uses the column ([Schema update best practices](https://docs.cloud.google.com/spanner/docs/schema-updates-best-practices)).
- **"Enforce the holiday change freeze with an email to all teams."** A Cloud Deploy deploy policy blocks rollouts during the time window ([Restrict deploy behavior using policies](https://docs.cloud.google.com/deploy/docs/deploy-policy)).
- **"Weighted traffic split plus session affinity."** On the load balancer, do not combine them; the weights take precedence. On Cloud Run, session affinity takes precedence over the split ([Traffic management overview](https://docs.cloud.google.com/load-balancing/docs/https/traffic-management-global), [Set session affinity](https://docs.cloud.google.com/run/docs/configuring/session-affinity)).
