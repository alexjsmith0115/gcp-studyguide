## Why it matters

Most exam scenarios include a data center, a colocation facility, or another cloud that must connect to Google Cloud. The architect chooses the product, the topology that earns the SLA, the encryption layer, and the routing and DNS design. Many wrong answers use a product that Google does not recommend for the case (Classic VPN, Direct Peering), or the correct product in a topology that has no SLA ([Classic VPN dynamic routing deprecation](https://docs.cloud.google.com/network-connectivity/docs/vpn/deprecations/classic-vpn-deprecation), [Choosing a Network Connectivity product](https://docs.cloud.google.com/network-connectivity/docs/how-to/choose-product)).

## Key points

- Choose Cloud VPN for lower cost, lower bandwidth, or migration tests. Choose Dedicated Interconnect or Partner Interconnect for an enterprise-grade connection with higher throughput ([Choosing a Network Connectivity product](https://docs.cloud.google.com/network-connectivity/docs/how-to/choose-product)).
- Dedicated Interconnect uses 10-Gbps, 100-Gbps, or 400-Gbps circuits. The limits page gives 50 Mbps to 400 Gbps for each VLAN attachment. Some overview pages still say 50 Gbps ([Quotas and limits](https://docs.cloud.google.com/network-connectivity/docs/interconnect/quotas), [Create VLAN attachments](https://docs.cloud.google.com/network-connectivity/docs/interconnect/how-to/dedicated/creating-vlan-attachments), [Choosing a Network Connectivity product](https://docs.cloud.google.com/network-connectivity/docs/how-to/choose-product)).
- The multi-region 99.99% Cloud Interconnect topology needs four connections in two metropolitan areas (metros), VLAN attachments in two regions, and global dynamic routing ([Establish 99.99% availability for Dedicated Interconnect](https://docs.cloud.google.com/network-connectivity/docs/interconnect/tutorials/dedicated-creating-9999-availability)).
- HA VPN gives 99.99% only with a tunnel on each of its two interfaces. HA VPN supports only dynamic (BGP) routing ([HA VPN topologies](https://docs.cloud.google.com/network-connectivity/docs/vpn/concepts/topologies), [Cloud VPN overview](https://docs.cloud.google.com/network-connectivity/docs/vpn/concepts/overview)).
- You cannot create new Classic VPN tunnels that use BGP. Classic VPN keeps static routing and a 99.9% SLA ([Classic VPN dynamic routing deprecation](https://docs.cloud.google.com/network-connectivity/docs/vpn/deprecations/classic-vpn-deprecation), [Cloud VPN overview](https://docs.cloud.google.com/network-connectivity/docs/vpn/concepts/overview)).
- Cloud Interconnect does not encrypt traffic by default. Add MACsec, HA VPN over Cloud Interconnect, or both ([Cloud Interconnect overview](https://docs.cloud.google.com/network-connectivity/docs/interconnect/concepts/overview), [MACsec for Cloud Interconnect overview](https://docs.cloud.google.com/network-connectivity/docs/interconnect/concepts/macsec-overview)).
- Cloud Router manages the BGP sessions, and the Andromeda network stack forwards the packets ([Cloud Router overview](https://docs.cloud.google.com/network-connectivity/docs/router/concepts/overview)).
- Private Google Access for on-premises hosts and DNS forwarding zones need custom advertised routes on Cloud Router ([Cloud Interconnect overview](https://docs.cloud.google.com/network-connectivity/docs/interconnect/concepts/overview)).
- Network Connectivity Center (NCC) hybrid spokes let your sites exchange data over Google's network. This site-to-site data transfer is best effort ([Site-to-site data transfer overview](https://docs.cloud.google.com/network-connectivity/docs/network-connectivity-center/concepts/data-transfer)).
- Cross-Cloud Interconnect gives dedicated physical connections to AWS, Microsoft Azure, Oracle Cloud Infrastructure (OCI), and Alibaba Cloud ([Cross-Cloud Interconnect overview](https://docs.cloud.google.com/network-connectivity/docs/interconnect/concepts/cci-overview)).
- Choose `restricted.googleapis.com` for on-premises access to only the APIs that VPC Service Controls supports ([Configure Private Google Access for on-premises hosts](https://docs.cloud.google.com/vpc/docs/configure-private-google-access-hybrid)).

## Choose a connectivity option

Match the location, bandwidth, SLA, and encryption rule to one option.

| Option | Capacity | SLA | Encryption | Use when |
|---|---|---|---|---|
| HA VPN | 250,000 packets per second (1 to 3 Gbps) for each tunnel. Add tunnels for more. | 99.99% with the documented topology | IPsec | Lower cost, lower bandwidth, or migration tests |
| Classic VPN | One interface, static routing only | 99.9% | IPsec | Only when the peer device cannot run BGP |
| Dedicated Interconnect | 10, 100, or 400-Gbps circuits, up to 8 for each connection | End to end, for the Google-defined topologies | None by default | High bandwidth, and your routers can meet Google in a colocation facility |
| Partner Interconnect | 50 Mbps to 100 Gbps for each VLAN attachment on the limits page (50 Gbps on older pages). Not all providers offer all sizes. | Only between Google and the service provider | None by default | No colocation presence, or less than a full 10-Gbps connection |
| Cross-Cloud Interconnect | 10 or 100 Gbps; also 400 Gbps for AWS and OCI | 99.9% or 99.99% with the documented topology | MACsec supported | Dedicated capacity to another cloud |

Sources: [Cloud VPN overview](https://docs.cloud.google.com/network-connectivity/docs/vpn/concepts/overview), [Classic VPN dynamic routing deprecation](https://docs.cloud.google.com/network-connectivity/docs/vpn/deprecations/classic-vpn-deprecation), [Choosing a Network Connectivity product](https://docs.cloud.google.com/network-connectivity/docs/how-to/choose-product), [Cloud Interconnect overview](https://docs.cloud.google.com/network-connectivity/docs/interconnect/concepts/overview), [Partner Interconnect overview](https://docs.cloud.google.com/network-connectivity/docs/interconnect/concepts/partner-overview), [Quotas and limits](https://docs.cloud.google.com/network-connectivity/docs/interconnect/quotas), [Cross-Cloud Interconnect overview](https://docs.cloud.google.com/network-connectivity/docs/interconnect/concepts/cci-overview).

For Dedicated Interconnect, you order, give the Letter of Authorization and Connecting Facility Assignment (LOA-CFA) to your vendor, and test. For Partner Interconnect, you give a pairing key to the service provider ([Dedicated Interconnect overview](https://docs.cloud.google.com/network-connectivity/docs/interconnect/concepts/dedicated-overview), [Partner Interconnect overview](https://docs.cloud.google.com/network-connectivity/docs/interconnect/concepts/partner-overview)).

Cost also changes the answer. For high bandwidth needs, Dedicated Interconnect can be a cost-effective solution. Cloud VPN by itself does not reduce egress costs ([Choosing a Network Connectivity product](https://docs.cloud.google.com/network-connectivity/docs/how-to/choose-product), [Cloud Interconnect overview](https://docs.cloud.google.com/network-connectivity/docs/interconnect/concepts/overview)).

Do not use Direct Peering or Carrier Peering to reach VPC networks. They exist outside Google Cloud, give no access to internal IP addresses, and have no SLA ([Choosing a Network Connectivity product](https://docs.cloud.google.com/network-connectivity/docs/how-to/choose-product)).

## SLA topologies

An SLA applies only when you build the Google-defined topology. Extra hardware in another layout does not qualify.

| Target | Cloud Interconnect | HA VPN |
|---|---|---|
| 99.99% | Four connections: two in each of two metros, in both edge availability domains of each metro. Four VLAN attachments in two regions, a Cloud Router in each region, and global dynamic routing. | A tunnel on both gateway interfaces. Between two VPC networks, both HA VPN gateways in the same region. |
| 99.9% | Two connections in one metro, in different edge availability domains. Two VLAN attachments in one region. | Between two VPC networks, HA VPN gateways in different regions |

Sources: [Establish 99.99% availability for Dedicated Interconnect](https://docs.cloud.google.com/network-connectivity/docs/interconnect/tutorials/dedicated-creating-9999-availability), [Topology for non-critical applications overview](https://docs.cloud.google.com/network-connectivity/docs/interconnect/tutorials/non-critical-overview), [Establish 99.9% availability for Dedicated Interconnect](https://docs.cloud.google.com/network-connectivity/docs/interconnect/tutorials/dedicated-creating-999-availability), [HA VPN topologies](https://docs.cloud.google.com/network-connectivity/docs/vpn/concepts/topologies).

Details that decide exam answers:

- Google coordinates maintenance between the edge availability domains of one metro, but not between metros ([Establish 99.99% availability for Dedicated Interconnect](https://docs.cloud.google.com/network-connectivity/docs/interconnect/tutorials/dedicated-creating-9999-availability)).
- Partner Interconnect needs two regions for 99.99%, even when all VMs are in one region ([Establish 99.99% availability for Partner Interconnect](https://docs.cloud.google.com/network-connectivity/docs/interconnect/tutorials/partner-creating-9999-availability)).
- Dedicated Interconnect also has a single-region 99.99% topology. It uses four connections in one metro, ordered through a connection group with the `PRODUCTION_CRITICAL` capability ([Establish 99.99% availability for Dedicated Interconnect](https://docs.cloud.google.com/network-connectivity/docs/interconnect/tutorials/dedicated-creating-9999-availability)).
- Traffic leaves through the local region's VLAN attachments, even when they are overloaded. Each of the four connections needs capacity for all production traffic ([Best practices for Cloud Interconnect](https://docs.cloud.google.com/network-connectivity/docs/interconnect/concepts/best-practices)).
- Google recommends active-active VLAN attachments, with flow-based hashing on your routers ([Best practices for Cloud Interconnect](https://docs.cloud.google.com/network-connectivity/docs/interconnect/concepts/best-practices)).
- An HA VPN gateway with only one active interface has no SLA ([Choosing a Network Connectivity product](https://docs.cloud.google.com/network-connectivity/docs/how-to/choose-product)).
- `gcloud compute vpn-gateways get-status` shows `CONNECTION_REDUNDANCY_MET` when the tunnels cover both interfaces ([Check VPN status](https://docs.cloud.google.com/network-connectivity/docs/vpn/how-to/checking-vpn-status)).

## Encrypt hybrid traffic

Cloud Interconnect keeps traffic off the public internet, but it does not encrypt it. Choose the layer that the requirement names ([Cloud Interconnect overview](https://docs.cloud.google.com/network-connectivity/docs/interconnect/concepts/overview)).

| Method | What it protects | Limits | Use when |
|---|---|---|---|
| MACsec for Cloud Interconnect | Your router to Google's edge router (Layer 2). With Partner Interconnect, the provider's edge router to Google's edge router. | No encryption inside Google. 10-Gbps circuits need your account manager. With Partner Interconnect, the provider must also encrypt its own network. | Link encryption on Dedicated Interconnect, Partner Interconnect, or Cross-Cloud Interconnect |
| HA VPN over Cloud Interconnect | Your network to the VPC network (IPsec, Layer 3) | Select encryption when you create the VLAN attachment. Up to 50 Gbps for each encrypted attachment. | A rule requires IPsec, or traffic passes through a service provider |
| HA VPN over the internet | Your network to the VPC network (IPsec) | 1 to 3 Gbps for each tunnel | Lower cost or lower bandwidth |

Sources: [MACsec for Cloud Interconnect overview](https://docs.cloud.google.com/network-connectivity/docs/interconnect/concepts/macsec-overview), [HA VPN over Cloud Interconnect overview](https://docs.cloud.google.com/network-connectivity/docs/interconnect/concepts/ha-vpn-interconnect), [Cloud VPN overview](https://docs.cloud.google.com/network-connectivity/docs/vpn/concepts/overview), [Choosing a Network Connectivity product](https://docs.cloud.google.com/network-connectivity/docs/how-to/choose-product), [Cross-Cloud Interconnect overview](https://docs.cloud.google.com/network-connectivity/docs/interconnect/concepts/cci-overview).

Google recommends layers: MACsec at Layer 2, IPsec at Layer 3, and application-level protocols such as TLS ([MACsec for Cloud Interconnect overview](https://docs.cloud.google.com/network-connectivity/docs/interconnect/concepts/macsec-overview)). With Partner Interconnect, you must add IPsec to meet data security and compliance requirements ([Choosing a Network Connectivity product](https://docs.cloud.google.com/network-connectivity/docs/how-to/choose-product)). You cannot run Classic VPN over Cloud Interconnect ([HA VPN over Cloud Interconnect overview](https://docs.cloud.google.com/network-connectivity/docs/interconnect/concepts/ha-vpn-interconnect)).

## Cloud Router and BGP

- **ASNs.** Use a private ASN for HA VPN. You cannot change the ASN of a Cloud Router later. Partner Interconnect needs a Cloud Router with ASN `16550` ([Create HA VPN gateways to connect VPC networks](https://docs.cloud.google.com/network-connectivity/docs/vpn/how-to/creating-ha-vpn2), [Create VLAN attachments](https://docs.cloud.google.com/network-connectivity/docs/interconnect/how-to/partner/creating-vlan-attachments)).
- **Dynamic routing mode.** In regional mode, a Cloud Router advertises only subnets in its own region. Its learned routes have next hops only in that region. In global mode, both cover all regions ([Advertised routes](https://docs.cloud.google.com/network-connectivity/docs/router/concepts/advertised-routes), [Learned routes](https://docs.cloud.google.com/network-connectivity/docs/router/concepts/learned-routes)).
- **Peered VPC networks.** Default advertisement does not include peered subnet ranges. Use custom advertisement, and export and import custom routes on the peering ([VPC Network Peering](https://docs.cloud.google.com/vpc/docs/vpc-peering)).

| Advertise | Advertisement mode |
|---|---|
| Subnets of this VPC network | Default |
| Subnets plus the API VIPs, `35.199.192.0/19`, or peered subnet ranges | Custom: subnets plus custom ranges |
| Only ranges that you choose, such as `0.0.0.0/0` | Custom: custom ranges only |

Sources: [Advertised routes](https://docs.cloud.google.com/network-connectivity/docs/router/concepts/advertised-routes), [Cloud Interconnect overview](https://docs.cloud.google.com/network-connectivity/docs/interconnect/concepts/overview), [VPC Network Peering](https://docs.cloud.google.com/vpc/docs/vpc-peering).

## Network Connectivity Center for sites and clouds

- The NCC hub is global. Hybrid spokes hold HA VPN tunnels, VLAN attachments, or Router appliance VMs. One spoke holds one resource type and must be in the hub's project ([NCC overview](https://docs.cloud.google.com/network-connectivity/docs/network-connectivity-center/concepts/overview)).
- Site-to-site data transfer uses Google's network as a WAN between your sites and clouds. All spoke resources must be in one VPC network ([Site-to-site data transfer overview](https://docs.cloud.google.com/network-connectivity/docs/network-connectivity-center/concepts/data-transfer)).
- Data transfer between sites has no bandwidth or latency guarantee. It works only in supported locations ([Site-to-site data transfer overview](https://docs.cloud.google.com/network-connectivity/docs/network-connectivity-center/concepts/data-transfer)).
- To connect your sites to each other, use NCC, Router appliance, or Cross-Site Interconnect. First review Section 2 of the General Service Terms ([Cloud Interconnect overview](https://docs.cloud.google.com/network-connectivity/docs/interconnect/concepts/overview)).
- Router appliance runs a vendor image on VMs and peers with Cloud Router. Cross-Site Interconnect (Preview) gives Layer 2 links between your sites, and VPC networks cannot see that traffic ([Choosing a Network Connectivity product](https://docs.cloud.google.com/network-connectivity/docs/how-to/choose-product)).

## Multicloud and Google Cloud-to-Google Cloud connectivity

| Situation | Google-recommended option |
|---|---|
| Occasional, low-volume transfers that are not critical | The internet |
| Encryption, or small transfers | HA VPN to the other cloud's managed VPN |
| Larger volumes | Partner Interconnect with a multicloud-enabled partner |
| Your routers already connect to several clouds at 10 Gbps or more | Dedicated Interconnect through a common point of presence |
| You do not want to manage cross-connects and routers | Cross-Cloud Interconnect |

Sources: [Patterns for connecting other cloud service providers with Google Cloud](https://docs.cloud.google.com/architecture/patterns-for-connecting-other-csps-with-gcp).

- Google supports a Cross-Cloud Interconnect connection only up to the other provider's network ([Cross-Cloud Interconnect overview](https://docs.cloud.google.com/network-connectivity/docs/interconnect/concepts/cci-overview)).
- Partner Cross-Cloud Interconnect for AWS needs no physical provisioning, has built-in resiliency, and takes minutes to provision ([Cross-Cloud Interconnect overview](https://docs.cloud.google.com/network-connectivity/docs/interconnect/concepts/cci-overview)).
- HA VPN to an AWS peer gateway needs four tunnels for 99.99% availability ([Cloud VPN pricing](https://cloud.google.com/vpn/pricing)).
- For Cloud Storage or BigQuery from another cloud, use Private Service Connect or Private Google Access for on-premises hosts ([Patterns for connecting other cloud service providers with Google Cloud](https://docs.cloud.google.com/architecture/patterns-for-connecting-other-csps-with-gcp)).

Google Cloud-to-Google Cloud links connect VPC networks in different projects or organizations:

| Need | Option | Notes |
|---|---|---|
| Encrypted link between two VPC networks | An HA VPN gateway in each network | 99.99% when both gateways are in the same region. For another organization's gateway, request `compute.vpnGateways.use`. |
| The latency and throughput of one VPC network | VPC Network Peering | Works across organizations. Not transitive. Subnet ranges cannot overlap. |
| A hub network that routes between spokes | HA VPN from each spoke to a hub VPC network | Gives transitive routing |
| A mesh of many VPC networks | NCC VPC spokes | See [Cloud-native network design](note:1.3-network-design) |

Sources: [HA VPN topologies](https://docs.cloud.google.com/network-connectivity/docs/vpn/concepts/topologies), [Create HA VPN gateways to connect VPC networks](https://docs.cloud.google.com/network-connectivity/docs/vpn/how-to/creating-ha-vpn2), [VPC Network Peering](https://docs.cloud.google.com/vpc/docs/vpc-peering), [Hub-and-spoke network architecture](https://docs.cloud.google.com/architecture/deploy-hub-spoke-vpc-network-topology), [NCC overview](https://docs.cloud.google.com/network-connectivity/docs/network-connectivity-center/concepts/overview).

## Hybrid DNS

Google recommends two authoritative systems: Cloud DNS for your Google Cloud zones and your existing servers for on-premises zones ([Best practices for Cloud DNS](https://docs.cloud.google.com/dns/docs/best-practices)).

| Direction | Cloud DNS feature | Network requirement |
|---|---|---|
| Google Cloud to on-premises | A forwarding zone for the on-premises domain | Cloud DNS queries come from `35.199.192.0/19`. Advertise this range to on-premises, and send replies back through the same VPC network. |
| On-premises to Google Cloud | An inbound server policy. On-premises servers use conditional forwarding to its entry points. | Use the entry point in the region of the tunnel or VLAN attachment. |
| Other VPC networks to on-premises | A DNS peering zone that targets the VPC network with the forwarding zone | DNS forwarding cannot cross VPC Network Peering. |

Sources: [Best practices for Cloud DNS](https://docs.cloud.google.com/dns/docs/best-practices), [DNS server policies](https://docs.cloud.google.com/dns/docs/server-policies-overview), [Create a forwarding zone](https://docs.cloud.google.com/dns/docs/zones/forwarding-zones).

- Prefer a forwarding zone to an alternative name server. It keeps Compute Engine internal DNS names and resolves external names without an extra hop ([Best practices for Cloud DNS](https://docs.cloud.google.com/dns/docs/best-practices)).
- Put the inbound server policy in the VPC network that connects to on-premises. Its entry points are not reachable across VPC Network Peering or NCC ([DNS server policies](https://docs.cloud.google.com/dns/docs/server-policies-overview)).
- Cloud DNS does not support zone transfers. With Shared VPC, host the private zones in the host project ([Best practices for Cloud DNS](https://docs.cloud.google.com/dns/docs/best-practices)).

For private zones and response policies, see [Access to Google APIs, the internet, and cloud-adjacent services](note:2.1-vpc-access-patterns).

## Private Google Access for on-premises hosts

On-premises hosts reach Google APIs through your tunnels or VLAN attachments with special virtual IP addresses (VIPs). You do not enable Private Google Access on any subnet for this ([Private Google Access for on-premises hosts](https://docs.cloud.google.com/vpc/docs/private-google-access-hybrid)).

| Domain | IPv4 range | Allows |
|---|---|---|
| `private.googleapis.com` | `199.36.153.8/30` | Most Google APIs, whether or not VPC Service Controls supports them |
| `restricted.googleapis.com` | `199.36.153.4/30` | Only APIs that VPC Service Controls supports |

Sources: [Configure Private Google Access for on-premises hosts](https://docs.cloud.google.com/vpc/docs/configure-private-google-access-hybrid).

Configure four parts ([Configure Private Google Access for on-premises hosts](https://docs.cloud.google.com/vpc/docs/configure-private-google-access-hybrid)):

1. DNS: resolve the API domains to the chosen VIP. Use on-premises name servers, or Cloud DNS private zones with an inbound server policy. Do not mix the two VIPs.
2. VPC network: keep a route to the VIP range with the default internet gateway as the next hop.
3. Cloud Router: advertise the VIP range to on-premises with a custom advertisement.
4. On-premises firewall: allow traffic to the VIP range. VPC firewall rules have no effect on this API traffic from tunnels or VLAN attachments.

The VIPs support only HTTP-based protocols over TCP ([Configure Private Google Access for on-premises hosts](https://docs.cloud.google.com/vpc/docs/configure-private-google-access-hybrid)). A Private Service Connect endpoint for Google APIs can send on-premises traffic to IP addresses and regions that you choose ([Private Service Connect](https://docs.cloud.google.com/vpc/docs/private-service-connect)). For VPC Service Controls, see [Organization policy, VPC Service Controls, and audit logging](note:3.1-security-controls).

## AWS mapping

| AWS | Google Cloud | Difference that matters |
|---|---|---|
| AWS Direct Connect | Cloud Interconnect | 99.99% needs the four-connection topology. In global dynamic routing mode, routes learned in one region serve all regions. |
| AWS VPN | Cloud VPN (HA VPN) | HA VPN supports only BGP. An AWS peer gateway needs four tunnels for 99.99%. |
| AWS Transit Gateway, AWS Cloud WAN | Network Connectivity Center | The hub is global. Site-to-site data transfer is best effort. |
| Amazon Route 53 | Cloud DNS | Queries to on-premises come from `35.199.192.0/19`. |

Sources: [Compare AWS and Azure services to Google Cloud](https://docs.cloud.google.com/docs/get-started/aws-azure-gcp-service-comparison), [Establish 99.99% availability for Dedicated Interconnect](https://docs.cloud.google.com/network-connectivity/docs/interconnect/tutorials/dedicated-creating-9999-availability), [Learned routes](https://docs.cloud.google.com/network-connectivity/docs/router/concepts/learned-routes), [Cloud VPN overview](https://docs.cloud.google.com/network-connectivity/docs/vpn/concepts/overview), [Cloud VPN pricing](https://cloud.google.com/vpn/pricing), [NCC overview](https://docs.cloud.google.com/network-connectivity/docs/network-connectivity-center/concepts/overview), [Site-to-site data transfer overview](https://docs.cloud.google.com/network-connectivity/docs/network-connectivity-center/concepts/data-transfer), [Create a forwarding zone](https://docs.cloud.google.com/dns/docs/zones/forwarding-zones).

An AWS habit gives a wrong answer here. With Cloud Router in global dynamic routing mode, VPN tunnels to one region reach all regions of the VPC network. Other clouds can need VPN tunnels for each region ([Patterns for connecting other cloud service providers with Google Cloud](https://docs.cloud.google.com/architecture/patterns-for-connecting-other-csps-with-gcp)).

## Exam traps

- **Classic VPN with BGP.** You cannot create new Classic VPN tunnels that use BGP. Choose HA VPN ([Classic VPN dynamic routing deprecation](https://docs.cloud.google.com/network-connectivity/docs/vpn/deprecations/classic-vpn-deprecation)).
- **HA VPN gateways in different regions.** Between two VPC networks, this topology gives only 99.9% ([HA VPN topologies](https://docs.cloud.google.com/network-connectivity/docs/vpn/concepts/topologies)).
- **Two Interconnect connections for 99.99%.** Two connections in one metro give 99.9% ([Topology for non-critical applications overview](https://docs.cloud.google.com/network-connectivity/docs/interconnect/tutorials/non-critical-overview), [Establish 99.9% availability for Dedicated Interconnect](https://docs.cloud.google.com/network-connectivity/docs/interconnect/tutorials/dedicated-creating-999-availability)).
- **Regional dynamic routing in a multi-region design.** The multi-region 99.99% topology needs global dynamic routing ([Establish 99.99% availability for Partner Interconnect](https://docs.cloud.google.com/network-connectivity/docs/interconnect/tutorials/partner-creating-9999-availability)).
- **"Private means encrypted."** Cloud Interconnect is not encrypted by default, and MACsec does not encrypt traffic inside Google ([Cloud Interconnect overview](https://docs.cloud.google.com/network-connectivity/docs/interconnect/concepts/overview), [MACsec for Cloud Interconnect overview](https://docs.cloud.google.com/network-connectivity/docs/interconnect/concepts/macsec-overview)).
- **IPsec on an existing VLAN attachment.** You select encryption when you create the attachment. You cannot add it later ([HA VPN over Cloud Interconnect overview](https://docs.cloud.google.com/network-connectivity/docs/interconnect/concepts/ha-vpn-interconnect)).
- **Direct Peering for VPC access.** It gives no access to internal IP addresses and has no SLA ([Choosing a Network Connectivity product](https://docs.cloud.google.com/network-connectivity/docs/how-to/choose-product)).
- **Default advertisement for special ranges.** Cloud Router does not advertise peered subnet ranges in default mode. The API VIPs and DNS forwarding need custom advertisements ([VPC Network Peering](https://docs.cloud.google.com/vpc/docs/vpc-peering), [Cloud Interconnect overview](https://docs.cloud.google.com/network-connectivity/docs/interconnect/concepts/overview)).
- **VPC Network Peering for DNS.** Peering does not change name resolution. Use DNS peering zones ([Best practices for Cloud DNS](https://docs.cloud.google.com/dns/docs/best-practices)).
