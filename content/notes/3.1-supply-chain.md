## Why it matters

A supply chain attack changes your software before it runs in production. The attacker targets the code, the dependencies, the build system, the registry, or the deploy step. Exam scenarios give a threat or an audit requirement and ask which control stops it. They also ask how to prove where an image came from and how to block an image that fails a check.

## Key points

- A software supply chain is all the code, people, systems, and processes that develop and deliver your software, inside and outside your organization ([Software supply chain security](https://docs.cloud.google.com/software-supply-chain-security/docs/overview)).
- Google Cloud uses the Supply-chain Levels for Software Artifacts (SLSA) framework to describe threats from source to deployment ([Software supply chain threats](https://docs.cloud.google.com/software-supply-chain-security/docs/attack-vectors)).
- Cloud Build can generate build provenance that meets SLSA level 3. It does this only for artifacts that it stores in Artifact Registry ([Generate and validate build provenance](https://docs.cloud.google.com/build/docs/securing-builds/generate-validate-build-provenance)).
- Artifact Analysis (formerly Container Analysis) scans each new image when you push it to Artifact Registry. It keeps checking an image for new vulnerabilities while someone pulled it in the last 30 days ([Container scanning overview](https://docs.cloud.google.com/artifact-analysis/docs/container-scanning-overview), [Artifact Analysis overview](https://docs.cloud.google.com/artifact-analysis/docs/artifact-analysis)).
- On-Demand Scanning in a Cloud Build pipeline can block a build when the image has vulnerabilities of a set severity ([Use On-Demand Scanning in your Cloud Build pipeline](https://docs.cloud.google.com/artifact-analysis/docs/ods-cloudbuild)).
- Binary Authorization enforces a policy at deploy time on GKE and Cloud Run. An image that does not conform is not deployed ([Binary Authorization overview](https://docs.cloud.google.com/binary-authorization/docs/overview)).
- Cloud Build signs attestations at build time. The `built-by-cloud-build` attestor lets Binary Authorization allow only images that Cloud Build built ([Securing image deployments to Cloud Run and Google Kubernetes Engine](https://docs.cloud.google.com/build/docs/securing-builds/secure-deployments-to-run-gke)).
- On Cloud Run, developers can turn off Binary Authorization unless an organization policy requires it ([Enable Binary Authorization for Cloud Run](https://docs.cloud.google.com/binary-authorization/docs/run/enabling-binauthz-cloud-run)).
- A virtual repository in Artifact Registry can put your private packages before public ones. This reduces the risk of dependency confusion attacks ([Software supply chain security](https://docs.cloud.google.com/software-supply-chain-security/docs/overview)).
- Assured Open Source Software (Assured OSS) gives popular open source packages that Google builds, scans, and signs, with SLSA level 3 provenance and an SBOM ([Overview of Assured Open Source Software](https://docs.cloud.google.com/assured-open-source-software/docs/overview)).
- GKE no longer scans running workloads for vulnerabilities. Use Artifact Analysis or Security Command Center instead ([Vulnerability scanning removal from GKE](https://docs.cloud.google.com/kubernetes-engine/docs/deprecations/vulnerability-scanning-gkee)).

## Threats and controls by stage

Google Cloud calls this set of products "software supply chain security". The earlier name, Software Delivery Shield, no longer has its own documentation: its old overview URL goes to [Software supply chain security](https://docs.cloud.google.com/software-supply-chain-security/docs/overview). The products still work together:

| Stage | Threat | Google Cloud control |
|---|---|---|
| Develop | Insecure code from unmanaged developer machines | Cloud Workstations with VPC Service Controls and private ingress and egress. Local scans with On-Demand Scanning. |
| Source | Bad code in the repository, or a compromised source control system | Required human review, code scanning, restricted access, and multi-factor authentication |
| Dependencies | Vulnerable, malicious, or look-alike packages | Artifact Registry remote and virtual repositories, Assured OSS, pinned versions, and lock files |
| Build | A build from untrusted source, or a compromised build system | Cloud Build ephemeral builds, signed provenance, least privilege, and VPC Service Controls |
| Store | Tampered images, or images built outside the official process | Upload rights only for CI service accounts and repository administrators. Provenance checks. |
| Deploy | A compromised deploy process, or an image that failed checks | Cloud Deploy with approvals, and Binary Authorization |
| Run | New vulnerabilities and risky configuration | Artifact Analysis continuous analysis, Security Command Center, and the Cloud Run security panel |

Sources: [Software supply chain threats](https://docs.cloud.google.com/software-supply-chain-security/docs/attack-vectors), [Software supply chain security](https://docs.cloud.google.com/software-supply-chain-security/docs/overview), [Dependency management](https://docs.cloud.google.com/software-supply-chain-security/docs/dependencies), [Container scanning overview](https://docs.cloud.google.com/artifact-analysis/docs/container-scanning-overview), [Vulnerability scanning removal from GKE](https://docs.cloud.google.com/kubernetes-engine/docs/deprecations/vulnerability-scanning-gkee).

For source repository choices, see [SDLC, CI/CD, and service provisioning](note:4.1-sdlc-cicd).

## Build integrity with Cloud Build

Build provenance is verifiable data about a build. It records the digests of the built images, the source locations, the build arguments, and the build duration ([Generate and validate build provenance](https://docs.cloud.google.com/build/docs/securing-builds/generate-validate-build-provenance)). With provenance, you can prove that an image came from your trusted source and your trusted builder.

Rules for provenance ([Generate and validate build provenance](https://docs.cloud.google.com/build/docs/securing-builds/generate-validate-build-provenance)):

- List the image in the `images` field of the build config. Cloud Build cannot generate provenance if a build step runs `docker push`.
- Set `requestedVerifyOption: VERIFIED` in `options`. The build is then successful only if Cloud Build generates provenance.
- Validate the provenance with the open source SLSA verifier before you trust an image.

Cloud Build runs each build in a new VM environment and destroys it after the build ([Software supply chain threats](https://docs.cloud.google.com/software-supply-chain-security/docs/attack-vectors)). Build service accounts, secrets in builds, and private pools inside a VPC Service Controls perimeter are in [SDLC, CI/CD, and service provisioning](note:4.1-sdlc-cicd).

## Dependencies and artifacts

Many vulnerabilities come in through dependencies that you do not use directly. In December 2021, the Log4j vulnerability affected over 17,000 packages in Maven Central. Most of them did not use Log4j directly ([Software supply chain security](https://docs.cloud.google.com/software-supply-chain-security/docs/overview)).

| Control | What it does |
|---|---|
| Remote repository | Caches packages from Docker Hub, Maven Central, PyPI, and other upstream sources. The next request gets the cached copy. Scanning covers cached packages if you turn it on. |
| Virtual repository | Puts several repositories of one format behind one endpoint. A priority on each upstream repository decides the search order. |
| Assured OSS | Free tier: Python, Go, and Java packages. Premium tier, with Security Command Center Premium or Enterprise (deprecated), adds JavaScript (npm) packages and automated setup. |
| Version pinning | Fixes the version of a direct dependency, so that builds are reproducible. A lock file also fixes transitive dependencies. |
| Upload control | Only dedicated service accounts and repository administrators can upload to the release repositories. |

Sources: [Remote repositories overview](https://docs.cloud.google.com/artifact-registry/docs/repositories/remote-overview), [Virtual repositories overview](https://docs.cloud.google.com/artifact-registry/docs/repositories/virtual-overview), [Overview of Assured Open Source Software](https://docs.cloud.google.com/assured-open-source-software/docs/overview), [Dependency management](https://docs.cloud.google.com/software-supply-chain-security/docs/dependencies), [Software supply chain threats](https://docs.cloud.google.com/software-supply-chain-security/docs/attack-vectors), [Software supply chain security](https://docs.cloud.google.com/software-supply-chain-security/docs/overview), [Security Command Center service tiers](https://docs.cloud.google.com/security-command-center/docs/service-tiers).

A pinned version fixes only the dependency that you name. It also stops security fixes for that dependency until you update the pin ([Dependency management](https://docs.cloud.google.com/software-supply-chain-security/docs/dependencies)). A tag that is not permanently attached to one build lets a build resolve to a different version later ([Software supply chain threats](https://docs.cloud.google.com/software-supply-chain-security/docs/attack-vectors)). Deploy images by digest ([About container image digests](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/about-container-images)).

## Vulnerability scanning with Artifact Analysis

| | Automatic scanning | On-Demand Scanning |
|---|---|---|
| When it scans | When you push a new image to Artifact Registry. Then continuous analysis while someone pulled the image in the last 30 days. | When you run `gcloud artifacts docker images scan`, locally or in a build |
| Best use | Visibility and alerts for all images in the registry | Stop a build before the image reaches the registry |
| Price | $0.26 for the first scan of each image digest | $0.26 for each scanned image |

Sources: [Container scanning overview](https://docs.cloud.google.com/artifact-analysis/docs/container-scanning-overview), [Artifact Analysis pricing](https://cloud.google.com/artifact-analysis/pricing), [Use On-Demand Scanning in your Cloud Build pipeline](https://docs.cloud.google.com/artifact-analysis/docs/ods-cloudbuild).

More facts about scanning ([Container scanning overview](https://docs.cloud.google.com/artifact-analysis/docs/container-scanning-overview)):

- Artifact Analysis scans an image once, based on its digest. A new or changed tag does not start a new scan.
- It also reports malicious packages from the OpenSSF Malicious Packages Repository, as CRITICAL vulnerabilities.
- After 30 days without a pull, the results are stale. Pull the image to scan it again.
- Scanning for packages outside containers is off by default. You turn it on for each repository.

When you enable the Container Scanning API, Artifact Analysis does not scan the images that are already in the registry. You must push them again ([Artifact Analysis pricing](https://cloud.google.com/artifact-analysis/pricing)).

Artifact Analysis can also generate a software bill of materials (SBOM) in SPDX 2.3 format, and store it in Cloud Storage in your project ([SBOM overview](https://docs.cloud.google.com/artifact-analysis/docs/sbom-overview)).

## Deploy-time enforcement with Binary Authorization

A Binary Authorization policy is a set of rules. Each rule has an evaluation mode and an enforcement mode ([Binary Authorization concepts](https://docs.cloud.google.com/binary-authorization/docs/key-concepts)):

| Setting | Values |
|---|---|
| Evaluation mode | Allow all images, disallow all images, or require attestations |
| Enforcement mode | Block and audit log, or dry run (audit log only). Dry run lets you test a policy in production before it blocks anything. |
| Specific rules | GKE: per cluster, Kubernetes namespace, or Kubernetes service account. Cloud Run: the default rule only. |
| Exempt images | An allowlist by registry path. The setting that trusts Google-maintained system images keeps GKE system images working. |

Sources: [Binary Authorization concepts](https://docs.cloud.google.com/binary-authorization/docs/key-concepts).

An attestation certifies that an image finished a required stage, such as a build by your CI pipeline or a manual QA approval. A signer signs the image digest with a private key. At deploy time, an attestor verifies the signature ([Binary Authorization overview](https://docs.cloud.google.com/binary-authorization/docs/overview)). Keys can be in Cloud KMS ([Binary Authorization concepts](https://docs.cloud.google.com/binary-authorization/docs/key-concepts)).

Design rules:

- **Build verification.** Require the `built-by-cloud-build` attestor, so that only images from Cloud Build deploy ([Securing image deployments to Cloud Run and Google Kubernetes Engine](https://docs.cloud.google.com/build/docs/securing-builds/secure-deployments-to-run-gke)).
- **Vulnerability gate.** Create attestations only for images that pass the Artifact Analysis check. Binary Authorization then blocks images with known issues ([Container scanning overview](https://docs.cloud.google.com/artifact-analysis/docs/container-scanning-overview)).
- **Make it mandatory on Cloud Run.** Use the `constraints/run.allowedBinaryAuthorizationPolicies` constraint ([Organization policy constraints](https://docs.cloud.google.com/organization-policy/reference/org-policy-constraints)). Without it, developers can deploy with Binary Authorization turned off ([Enable Binary Authorization for Cloud Run](https://docs.cloud.google.com/binary-authorization/docs/run/enabling-binauthz-cloud-run)).
- **Plan for emergencies.** Breakglass deploys an image that the policy blocks. Cloud Audit Logs always records the breakglass event, so you can alert on it ([Use breakglass](https://docs.cloud.google.com/binary-authorization/docs/using-breakglass)).
- **Watch running Pods.** Continuous validation (Preview) checks the images of running Pods on GKE against check-based platform policies. It logs violations and does not stop Pods ([Continuous validation overview](https://docs.cloud.google.com/binary-authorization/docs/overview-cv)).

Binary Authorization protects container platforms. For VM images, use the trusted image projects constraint in [Organization policy, VPC Service Controls, and audit logging](note:3.1-security-controls).

## Runtime visibility

- GKE scans Kubernetes objects, such as Pod specifications, for configuration concerns. This scan is on by default in new clusters with GKE 1.27 or later ([About the security posture dashboard](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/about-security-posture-dashboard)).
- The GKE workload vulnerability scanning tiers are shut down. For running images, Security Command Center has Artifact Registry vulnerability assessment and Vulnerability Assessment for Google Cloud (Preview) ([Vulnerability scanning removal from GKE](https://docs.cloud.google.com/kubernetes-engine/docs/deprecations/vulnerability-scanning-gkee)).
- The Cloud Run security panel shows the SLSA build level, the build provenance, and vulnerabilities in running services ([Software supply chain security](https://docs.cloud.google.com/software-supply-chain-security/docs/overview)).

Release strategies, approvals, and rollbacks are in [Deployment and release management](note:6.3-release-management). GKE cluster hardening is in [Configuring GKE](note:2.3-gke).

## Exam traps

- **Scanning is not blocking.** Automatic scanning in Artifact Registry only reports vulnerabilities. To stop a deployment, add Binary Authorization. To stop a build, use On-Demand Scanning in the pipeline ([Container scanning overview](https://docs.cloud.google.com/artifact-analysis/docs/container-scanning-overview)).
- **Old images are not scanned.** After you enable the Container Scanning API, only new pushes are scanned ([Artifact Analysis pricing](https://cloud.google.com/artifact-analysis/pricing)).
- **Tags are not identities.** Scans, attestations, and provenance use the image digest. A tag can point to a different image later ([Container scanning overview](https://docs.cloud.google.com/artifact-analysis/docs/container-scanning-overview), [About container image digests](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/about-container-images)).
- **No provenance with `docker push`.** Cloud Build creates provenance only for images in the `images` field that go to Artifact Registry ([Generate and validate build provenance](https://docs.cloud.google.com/build/docs/securing-builds/generate-validate-build-provenance)).
- **Cloud Run needs the organization policy.** A Binary Authorization policy alone does not stop a developer who deploys without it ([Enable Binary Authorization for Cloud Run](https://docs.cloud.google.com/binary-authorization/docs/run/enabling-binauthz-cloud-run)).
- **Cloud Run rules are project-wide.** Cloud Run supports only the default rule, not specific rules ([Binary Authorization concepts](https://docs.cloud.google.com/binary-authorization/docs/key-concepts)).
- **Test before you block.** Use dry run mode to find images that a new policy would block ([Binary Authorization concepts](https://docs.cloud.google.com/binary-authorization/docs/key-concepts)).
- **GKE workload scanning is gone.** An answer that turns on GKE workload vulnerability scanning is out of date ([Vulnerability scanning removal from GKE](https://docs.cloud.google.com/kubernetes-engine/docs/deprecations/vulnerability-scanning-gkee)).
