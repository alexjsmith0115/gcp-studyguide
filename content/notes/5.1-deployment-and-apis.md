## Why it matters

In objective 5.1, you advise teams so that a design reaches production safely. The exam describes a team's situation and asks for the Google-recommended deployment practice, the right API management product, or the right type of test. Most wrong options are real products or practices used for the wrong job.

## Key points

- Google suggests Apigee first for complex, high-scale, or partner-facing API programs. API Gateway suits project-level APIs for serverless backends. Cloud Endpoints suits teams that want to run the gateway proxy themselves, most often for gRPC ([Choosing between Apigee, API Gateway, and Cloud Endpoints](https://cloud.google.com/blog/products/application-modernization/choosing-between-apigee-api-gateway-and-cloud-endpoints)).
- Apigee puts a proxy layer between clients and backends. Policies on the proxy add security, rate limiting, and mediation without backend changes ([What is Apigee?](https://docs.cloud.google.com/apigee/docs/api-platform/get-started/what-apigee)).
- In Apigee hybrid, Google runs the management plane and you run the runtime plane on your own Kubernetes clusters. All API traffic stays inside your network, and Pay-as-you-go pricing is not available ([What is Apigee hybrid?](https://docs.cloud.google.com/apigee/docs/hybrid/v1.17/what-is-hybrid), [Pay-as-you-go pricing FAQ](https://docs.cloud.google.com/apigee/docs/api-platform/reference/pay-as-you-go-updated-faq)).
- In Apigee, you provision API keys for API products, not for individual APIs ([Introduction to API products](https://docs.cloud.google.com/apigee/docs/api-platform/publish/what-api-product)).
- Use the SpikeArrest policy to protect against sudden traffic spikes. Use the Quota policy to enforce business contracts with developers and partners ([SpikeArrest policy](https://docs.cloud.google.com/apigee/docs/api-platform/reference/policies/spike-arrest-policy)).
- API Gateway is fully managed and pay-per-use. Each upload of an API definition creates a new API config, which you cannot modify ([API Gateway Architecture](https://docs.cloud.google.com/api-gateway/docs/architecture-overview), [API Gateway Deployment Model](https://docs.cloud.google.com/api-gateway/docs/deployment-model)).
- An API key identifies a project for quota, billing, and monitoring. Do not use API keys as the only credential when API calls carry sensitive data ([Use API Keys](https://docs.cloud.google.com/api-gateway/docs/authenticate-api-keys)).
- Immutable infrastructure means that you never modify a deployed resource. You change its configuration in source control, test the change, and redeploy ([Patterns for scalable and resilient apps](https://docs.cloud.google.com/architecture/scalable-and-resilient-apps)).
- Build each artifact once. Inject configuration and secrets at deployment time, and promote the same artifact from development to QA to production ([Migrate to automated, containerized deployments](https://docs.cloud.google.com/architecture/migration-to-google-cloud-automated-containerized-deployments)).
- Automate unit, integration, and end-to-end tests in the CI/CD pipeline. Add load and stress tests to find limits ([Automate and manage change](https://docs.cloud.google.com/architecture/framework/operational-excellence/automate-and-manage-change), [Ensure operational readiness and performance using CloudOps](https://docs.cloud.google.com/architecture/framework/operational-excellence/operational-readiness-and-performance-using-cloudops)).

## Advising on deployment

### Put every change through code and a pipeline

The operational excellence pillar recommends IaC, version control, CI/CD pipelines, configuration management tools, and automated testing ([Automate and manage change](https://docs.cloud.google.com/architecture/framework/operational-excellence/automate-and-manage-change)). Terraform details are in [Infrastructure as Code](note:5.2-infrastructure-as-code). CI/CD tools are in [SDLC, CI/CD, and service provisioning](note:4.1-sdlc-cicd).

For an organization with several teams, the enterprise foundations blueprint recommends a separate pipeline for each layer of the stack:

| Pipeline | What it deploys | Who owns it |
|---|---|---|
| Foundation pipeline | Shared folders and projects, organization policies, networks | One central team |
| Infrastructure pipeline | Workload projects and infrastructure, such as VMs and databases | One pipeline for each business unit, or one shared pipeline |
| Application pipeline | Workload artifacts, such as container images | Each application team |

Source: [Deployment methodology](https://docs.cloud.google.com/architecture/blueprints/security-foundations/deployment-methodology).

The blueprint builds these controls into its Cloud Build pipelines, and it recommends similar controls for other CI/CD tools ([Deployment methodology](https://docs.cloud.google.com/architecture/blueprints/security-foundations/deployment-methodology)):

- A pull request runs `terraform plan`, `terraform validate`, and policy checks. A merge runs `terraform apply`.
- Policy checks use Open Policy Agent constraints through the policy validation in the Google Cloud CLI. A build that fails a policy deploys nothing.
- Each pipeline stage runs as its own service account, with only the roles that the stage needs.
- Each infrastructure pipeline can deploy only to the projects of its own business unit.
- An optional manual approval step stops a build until a privileged user approves it.

### Prefer immutable infrastructure and immutable artifacts

Immutable infrastructure builds on IaC. Do not patch or tweak a deployed VM, cluster, or firewall rule. Update its configuration in the repository, test the change, and re-create the resource ([Patterns for scalable and resilient apps](https://docs.cloud.google.com/architecture/scalable-and-resilient-apps)). This approach makes deployments and rollbacks more predictable. It also reduces configuration drift and one-off "snowflake" servers.

The same idea applies to application artifacts ([Migrate to automated, containerized deployments](https://docs.cloud.google.com/architecture/migration-to-google-cloud-automated-containerized-deployments)):

1. Build the container image once. Tag a release with a semantic version, or tag work in progress with the Git commit hash.
2. Keep configuration files and secrets out of the image. Inject them when you deploy.
3. Deploy the image to development. After the tests pass, promote the same image to QA and then to production.
4. Use a dedicated service account for each runtime environment. Do not share one service account across environments.
5. Keep a break-glass process for emergencies.

### Promote changes through environments

| Layer | Promotion method that Google documents |
|---|---|
| Infrastructure (Terraform) | Persistent Git branches for development, non-production, and production. A pull request to the next branch promotes the change, and the merge applies it. |
| Applications | Cloud Deploy creates a release and delivers it to a series of targets in a defined promotion sequence. |
| Apigee API proxies | TargetServer resources keep backend URLs out of the proxy, so the proxy can move between environments. Deployed proxy revisions are immutable. |

Sources: [Deployment methodology](https://docs.cloud.google.com/architecture/blueprints/security-foundations/deployment-methodology), [Overview of Cloud Deploy](https://docs.cloud.google.com/deploy/docs/overview), [Best practices for API proxy design and development with Apigee](https://docs.cloud.google.com/apigee/docs/api-platform/fundamentals/best-practices-api-proxy-design-and-development), [Apigee technical feature overview](https://docs.cloud.google.com/apigee/docs/api-platform/get-started/apigee-feature-summary).

Canary, blue-green, and rollback strategies are in [Deployment and release management](note:6.3-release-management).

## API management: Apigee, API Gateway, or Cloud Endpoints

### Decision table

| Criterion | Apigee | API Gateway | Cloud Endpoints |
|---|---|---|---|
| Best fit | Complex or high-scale API programs; APIs for partners and third parties | Serverless backends on Google Cloud; APIs exposed at project level | You host the gateway on your own runtime with private networking; most often gRPC |
| Who runs the proxy | Google. With Apigee hybrid, you run the runtime plane. | Google. The service is fully managed and scales to zero. | You. ESP or ESPv2 runs next to the backend, or ESPv2 runs as a Cloud Run service. |
| API styles | REST, gRPC, SOAP, GraphQL | OpenAPI 2.0 and 3.x; gRPC services on Cloud Run | OpenAPI 2.0 and 3.x; gRPC |
| Developer portal | Integrated portal or Drupal portal | Not a fit when consumers need a portal | Endpoints Portal shut down in March 2023 |
| Controls | Many policies, API products, monetization, Advanced API Security add-on | API keys, Google ID tokens, JWT validation, quotas | User authentication, API keys, logging, monitoring |
| Pricing | Evaluation, Pay-as-you-go, or Subscription | Per call; the first 2 million calls each month for each billing account cost nothing | Consumption-based |

Sources: [Choosing between Apigee, API Gateway, and Cloud Endpoints](https://cloud.google.com/blog/products/application-modernization/choosing-between-apigee-api-gateway-and-cloud-endpoints), [What is Apigee?](https://docs.cloud.google.com/apigee/docs/api-platform/get-started/what-apigee), [Apigee architecture overview](https://docs.cloud.google.com/apigee/docs/api-platform/architecture/overview), [What is Apigee hybrid?](https://docs.cloud.google.com/apigee/docs/hybrid/v1.17/what-is-hybrid), [Publishing overview](https://docs.cloud.google.com/apigee/docs/api-platform/publish/publishing-overview), [Apigee pricing](https://cloud.google.com/apigee/pricing), [API Gateway Architecture](https://docs.cloud.google.com/api-gateway/docs/architecture-overview), [API Gateway OpenAPI overview](https://docs.cloud.google.com/api-gateway/docs/openapi-overview), [API Gateway Deployment Model](https://docs.cloud.google.com/api-gateway/docs/deployment-model), [Using Google ID tokens to authenticate users](https://docs.cloud.google.com/api-gateway/docs/authenticating-users-googleid), [About quotas](https://docs.cloud.google.com/api-gateway/docs/quotas-overview), [Choosing an Endpoints option](https://docs.cloud.google.com/endpoints/docs/choose-endpoints-option), [Cloud Endpoints release notes](https://docs.cloud.google.com/endpoints/docs/release-notes), [API Gateway pricing](https://cloud.google.com/api-gateway/pricing).

The blog post adds two rules. Keep a product that already meets your needs. For a serverless project without partner, scale, or governance needs yet, start with API Gateway. Consider Apigee later if the project grows or needs new features.

### Apigee features that an architect must know

| Feature | What it does | Advice |
|---|---|---|
| API proxy | Decouples clients from backend services | Change or move the backend without breaking clients. |
| Policies | Traffic management, security, mediation, extension, and AI workload logic on the proxy | Use built-in policies before custom JavaScript, Java, or Python. If a standard and an extensible policy both work, use the standard one. |
| Shared flows | Reusable policy sequences, called with FlowCallout or attached to flow hooks | A central team owns shared flows for security and logging. Line-of-business teams reuse them. |
| API products | Bundle operations with quotas, key approval, and access limits | Keep one OpenAPI spec, one proxy, and one API product for each API. |
| Developer portal | App registration, API key delivery, and interactive documentation | Use it for self-service onboarding of external developers. |
| Monetization | Rate plans on API products, with prepaid or postpaid billing | Use it when APIs are a revenue channel. |
| Advanced API Security | Detects malicious clients and API abuse, and assesses proxy configurations | It does not affect runtime traffic or performance. |
| API hub | A catalog of all APIs, with versions, dependencies, and specification linting | Use it for governance across many teams and gateways. |

Sources: [What is Apigee?](https://docs.cloud.google.com/apigee/docs/api-platform/get-started/what-apigee), [Policy reference overview](https://docs.cloud.google.com/apigee/docs/api-platform/reference/policies/reference-overview-policy), [Creating reusable shared flows](https://docs.cloud.google.com/apigee/docs/api-platform/fundamentals/shared-flows), [Introduction to API products](https://docs.cloud.google.com/apigee/docs/api-platform/publish/what-api-product), [Publishing overview](https://docs.cloud.google.com/apigee/docs/api-platform/publish/publishing-overview), [Overview of Apigee monetization](https://docs.cloud.google.com/apigee/docs/api-platform/monetization/overview), [Overview of Advanced API Security](https://docs.cloud.google.com/apigee/docs/api-security), [What is Apigee API hub?](https://docs.cloud.google.com/apigee/docs/apihub/what-is-api-hub), [API resources overview](https://docs.cloud.google.com/apigee/docs/apihub/apis-intro), [Best practices for API proxy design and development with Apigee](https://docs.cloud.google.com/apigee/docs/api-platform/fundamentals/best-practices-api-proxy-design-and-development).

### Apigee deployment models and pricing models

| Deployment model | Where the runtime runs | What to know |
|---|---|---|
| Apigee | In Google Cloud, managed by Apigee | Clients reach it through an external Application Load Balancer. It reaches your VPC network through VPC Network Peering or Private Service Connect. |
| Apigee hybrid | Management plane in Google Cloud; runtime plane on a supported Kubernetes platform that you operate, such as GKE, Google Distributed Cloud, EKS, or AKS | All API traffic stays inside your network. The runtime continues to work if its connection to the management plane fails. |

Sources: [Apigee architecture overview](https://docs.cloud.google.com/apigee/docs/api-platform/architecture/overview), [What is Apigee hybrid?](https://docs.cloud.google.com/apigee/docs/hybrid/v1.17/what-is-hybrid), [Apigee hybrid supported platforms and versions](https://docs.cloud.google.com/apigee/docs/hybrid/supported-platforms).

| Pricing model | Use it when | What to know |
|---|---|---|
| Evaluation | You want to try Apigee | No cost for 60 days, and no SLA. |
| Pay-as-you-go | You want to start small with no commitment | Not available for Apigee hybrid. You choose Base, Intermediate, or Comprehensive environments. API Analytics and Advanced API Security are add-ons. |
| Subscription | You want predictable costs at scale | Standard, Enterprise, and Enterprise Plus tiers. Hybrid entitlements are available. |

Sources: [Apigee pricing](https://cloud.google.com/apigee/pricing), [Pay-as-you-go pricing overview](https://docs.cloud.google.com/apigee/docs/api-platform/reference/pay-as-you-go-updated-overview), [Pay-as-you-go pricing FAQ](https://docs.cloud.google.com/apigee/docs/api-platform/reference/pay-as-you-go-updated-faq).

In Pay-as-you-go, a call to a standard API proxy costs one fifth of a call to an extensible API proxy. Extensible policies make a proxy extensible, and they work only in Intermediate and Comprehensive environments ([Pay-as-you-go pricing overview](https://docs.cloud.google.com/apigee/docs/api-platform/reference/pay-as-you-go-updated-overview), [Policy reference overview](https://docs.cloud.google.com/apigee/docs/api-platform/reference/policies/reference-overview-policy)). Only the Comprehensive environment type supports multiple regions ([Apigee Pay-as-you-go environment types](https://docs.cloud.google.com/apigee/docs/api-platform/reference/pay-as-you-go-environment-types)).

### API Gateway details

- An API has API configs and gateways. A gateway is an Envoy-based proxy in one region, and it hosts exactly one API config at a time ([API Gateway Deployment Model](https://docs.cloud.google.com/api-gateway/docs/deployment-model)).
- To change an API, you upload the edited definition as a new API config. Then you update the gateway to use the new config ([Create an API config](https://docs.cloud.google.com/api-gateway/docs/creating-api-config), [API Gateway Deployment Model](https://docs.cloud.google.com/api-gateway/docs/deployment-model)).
- The gateway calls the backend as the service account of the API config. Google recommends a separate service account with only the permissions that the backend needs, such as `roles/run.invoker` for Cloud Run ([Configure the development environment](https://docs.cloud.google.com/api-gateway/docs/configure-dev-env), [Securing backend services](https://docs.cloud.google.com/api-gateway/docs/securing-backend-services)).
- API Gateway cannot proxy to other Google Cloud APIs, such as `bigquery.googleapis.com`. It sends an ID token, and those APIs need an access token ([Securing backend services](https://docs.cloud.google.com/api-gateway/docs/securing-backend-services)).
- To serve an API from several regions, deploy a gateway in each region behind your own load balancer (Preview) ([API Gateway Deployment Model](https://docs.cloud.google.com/api-gateway/docs/deployment-model), [Creating multi-region deployments for API Gateway](https://docs.cloud.google.com/api-gateway/docs/multi-region-deployment)).
- Quota metrics and limits apply to the whole API, not to one config. Keep metric names the same across all active configs ([About quotas](https://docs.cloud.google.com/api-gateway/docs/quotas-overview)).

### Google API design guidance

Advise teams to adopt one design standard early. Google's API design guide covers REST and gRPC APIs, and its topics point to Google AIPs, such as AIP-121 for resource-oriented design ([API design guide](https://docs.cloud.google.com/apis/design)). Apigee API hub can lint specifications ([What is Apigee API hub?](https://docs.cloud.google.com/apigee/docs/apihub/what-is-api-hub)).

## Testing: what to recommend

### Test types

| Test type | What it checks | Where it runs |
|---|---|---|
| Unit test | One function or class, in isolation | On every commit, in CI |
| Integration test | Interactions between components, often with mocks for complex dependencies | In CI |
| System or end-to-end test | The whole application in realistic scenarios; includes smoke, performance, and regression tests | Before release, in a test environment |
| Load test | Behavior under realistic traffic patterns | In a test deployment of the service |
| Stress test | The limits and breaking points of the system | In production |
| Configuration test | That production uses the configuration in version control | In production |
| Canary | A new version on a small part of production, watched before full rollout | In production, during a rollout |

Sources: [Automate and manage change](https://docs.cloud.google.com/architecture/framework/operational-excellence/automate-and-manage-change), [Ensure operational readiness and performance using CloudOps](https://docs.cloud.google.com/architecture/framework/operational-excellence/operational-readiness-and-performance-using-cloudops), [Testing for Reliability](https://sre.google/sre-book/testing-reliability/), [Load testing best practices](https://docs.cloud.google.com/run/docs/about-load-testing).

Unit tests are cheap and usually finish in milliseconds. A full system test can take hours and need dedicated resources ([Testing for Reliability](https://sre.google/sre-book/testing-reliability/)). So advise many fast unit tests on every commit and fewer system tests before release. For integration tests, teams can use local emulators, such as the Pub/Sub emulator ([Testing apps locally with the emulator](https://docs.cloud.google.com/pubsub/docs/emulator)). Other emulators are in [Working with Google Cloud programmatically](note:5.2-programmatic-access).

### Load testing advice

The Cloud Run load-testing guidance gives this checklist ([Load testing best practices](https://docs.cloud.google.com/run/docs/about-load-testing)):

1. Fix concurrency and startup problems in a small environment first.
2. Test a service with realistic CPU use and startup time. A trivial "hello world" service gives misleading results.
3. Generate load with a harness that controls rate and concurrency, such as JMeter. Pub/Sub is a poor load generator because you cannot control its rate.
4. Check maximum instances and quotas before a large test.
5. Export logs to BigQuery for second-by-second analysis. Monitoring data is not fine-grained enough.
6. Repeat the test at several loads to confirm linear scale-out, and measure latency at the client too.

The reliability pillar adds load to failure tests, so that you see behavior during an outage at real traffic levels ([Perform testing for recovery from failures](https://docs.cloud.google.com/architecture/framework/reliability/perform-testing-for-recovery-from-failures)). Test processes and failure drills are in [Testing, validation, and root cause analysis](note:4.1-testing-and-troubleshooting) and [Reliability in production](note:6.6-production-reliability).

## Exam traps

- **API Gateway for a partner API program.** A developer portal, API products, or monetization points to Apigee ([Choosing between Apigee, API Gateway, and Cloud Endpoints](https://cloud.google.com/blog/products/application-modernization/choosing-between-apigee-api-gateway-and-cloud-endpoints)).
- **The Cloud Endpoints Portal as the developer portal.** It shut down on March 21, 2023 ([Cloud Endpoints release notes](https://docs.cloud.google.com/endpoints/docs/release-notes)).
- **Apigee hybrid on Pay-as-you-go.** Hybrid needs a Subscription or an Evaluation. Of the two Apigee deployment models, only hybrid keeps all API traffic inside your network ([Pay-as-you-go pricing FAQ](https://docs.cloud.google.com/apigee/docs/api-platform/reference/pay-as-you-go-updated-faq), [Apigee pricing](https://cloud.google.com/apigee/pricing), [What is Apigee hybrid?](https://docs.cloud.google.com/apigee/docs/hybrid/v1.17/what-is-hybrid), [Apigee architecture overview](https://docs.cloud.google.com/apigee/docs/api-platform/architecture/overview)).
- **Quota to protect a backend from bursts.** Quota enforces business contracts. SpikeArrest protects against sudden spikes ([SpikeArrest policy](https://docs.cloud.google.com/apigee/docs/api-platform/reference/policies/spike-arrest-policy)).
- **An API key as the only protection for sensitive data.** An API key identifies a project, not a user ([Use API Keys](https://docs.cloud.google.com/api-gateway/docs/authenticate-api-keys), [Why and when to use API keys](https://docs.cloud.google.com/endpoints/docs/openapi/when-why-api-key)).
- **API Gateway in front of a Google API such as BigQuery.** It is not supported; calls fail with `401` ([Securing backend services](https://docs.cloud.google.com/api-gateway/docs/securing-backend-services)).
- **"Update the API config."** API configs are immutable. Create a new config and update the gateway ([API Gateway Deployment Model](https://docs.cloud.google.com/api-gateway/docs/deployment-model)).
- **Rebuilding the image for each environment.** Promote the same immutable artifact and inject the configuration ([Migrate to automated, containerized deployments](https://docs.cloud.google.com/architecture/migration-to-google-cloud-automated-containerized-deployments)).
- **Pub/Sub as a load generator, or a hello-world service as the test target.** Use a harness with a controlled rate and a realistic service ([Load testing best practices](https://docs.cloud.google.com/run/docs/about-load-testing)).
