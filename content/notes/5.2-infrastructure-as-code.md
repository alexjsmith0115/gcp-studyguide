## Why it matters

An architect selects the Infrastructure as Code (IaC) tool, decides where Terraform state lives, and sets the guardrails that let many teams change infrastructure safely. The exam expects the Google-recommended defaults. Use Terraform with a Cloud Storage backend, and make changes through a pipeline with a service account identity. Use Infrastructure Manager when a team wants Google to run Terraform. The exam also tests the move away from Deployment Manager and the Kubernetes-based option, Config Connector.

## Key points

- For IaC on Google Cloud in general, Google recommends the Terraform provider for Google Cloud. Infrastructure Manager automates Terraform deployments. Config Connector and Config Controller manage resources through Kubernetes ([Infrastructure as Code on Google Cloud](https://docs.cloud.google.com/docs/terraform/iac-overview)).
- Infrastructure Manager (Infra Manager) runs `terraform init`, `validate`, and `apply` in an ephemeral Cloud Build environment. For each revision, it stores the logs, the configuration, the resource list, and the state file ([Infrastructure Manager overview](https://docs.cloud.google.com/infrastructure-manager/docs/overview)).
- Infra Manager deploys a Terraform root module. The configuration must not define backend blocks and must run on a supported Terraform version ([Terraform and Infrastructure Manager](https://docs.cloud.google.com/infrastructure-manager/docs/infra-manager-terraform)).
- Support for Deployment Manager stopped on April 1, 2026. Google turns the service down after June 30, 2027, and points customers to Infra Manager and the DM Convert tool ([Deployment Manager deprecation](https://docs.cloud.google.com/deployment-manager/docs/deprecations)).
- For team use, keep state in the Cloud Storage backend, which locks the state. Only the build system and highly privileged administrators get access to the bucket ([Best practices for security](https://docs.cloud.google.com/docs/terraform/best-practices/security)).
- Always create a plan first, save it to a file, and apply it after an owner approves it. Run Terraform from an automated pipeline ([Best practices for Terraform operations](https://docs.cloud.google.com/docs/terraform/best-practices/operations)).
- A pipeline on Google Cloud inherits its service account credentials. A pipeline outside Google Cloud uses Workload Identity Federation. Neither option needs a downloaded service account key ([Best practices for Terraform operations](https://docs.cloud.google.com/docs/terraform/best-practices/operations)).
- Avoid imports when you can recreate a resource through Terraform ([Best practices for Terraform operations](https://docs.cloud.google.com/docs/terraform/best-practices/operations)). When you must import, an `import` block (Terraform 1.5 and later) lets `terraform plan` show the import first ([Import your Google Cloud resources into Terraform state](https://docs.cloud.google.com/docs/terraform/resource-management/import)).
- `gcloud beta terraform vet` (Preview) checks a Terraform plan against a library of policy constraints before you apply it ([Policy validation](https://docs.cloud.google.com/docs/terraform/policy-validation)).
- Use the non-authoritative `google_*_iam_member` resources. The authoritative `google_*_iam_policy` and `google_*_iam_binding` resources can remove roles that Google Cloud manages ([Best practices when working with Google Cloud resources](https://docs.cloud.google.com/docs/terraform/best-practices/working-with-resources)).

## Choose an IaC tool

Terraform is the default. Each other tool answers a specific need.

| Situation | Recommended tool | Why |
|---|---|---|
| General IaC, with your own CI/CD system | Terraform CLI with the Cloud Storage backend, run by Cloud Build or your CI system | The provider covers all Google Cloud resources |
| Terraform without a Terraform toolchain to run | Infrastructure Manager | Google runs Terraform and keeps state, logs, and revisions |
| Terraform change management across the organization | Terraform Cloud or Terraform Enterprise | HashiCorp SaaS or self-hosted service that stores state and secrets |
| Infrastructure in a general-purpose language | Cloud Development Kit for Terraform (CDKTF) or Pulumi | Reuse the language toolchain for tests and dependencies |
| Teams that work in Kubernetes with GitOps | Config Connector, or Config Controller as the hosted version | Kubernetes objects describe Google Cloud resources |
| Existing Deployment Manager configurations | DM Convert, then Infra Manager | Deployment Manager is no longer supported |
| Application releases | Cloud Build, Cloud Deploy, or App Lifecycle Manager (Preview, formerly SaaS Runtime) | Infra Manager does not deploy applications |

Sources: [Infrastructure as Code on Google Cloud](https://docs.cloud.google.com/docs/terraform/iac-overview), [Overview of Terraform on Google Cloud](https://docs.cloud.google.com/docs/terraform/terraform-overview), [Best practices for security](https://docs.cloud.google.com/docs/terraform/best-practices/security), [Best practices for Terraform operations](https://docs.cloud.google.com/docs/terraform/best-practices/operations), [Infrastructure Manager overview](https://docs.cloud.google.com/infrastructure-manager/docs/overview), [App Lifecycle Manager overview](https://docs.cloud.google.com/app-lifecycle-manager/overview), [Deployment Manager deprecation](https://docs.cloud.google.com/deployment-manager/docs/deprecations).

### Terraform in your pipeline or Infrastructure Manager

Both options run the same Terraform code. The difference is who operates the runtime, the state, and the history.

| Concern | Terraform CLI in your pipeline | Infrastructure Manager |
|---|---|---|
| Runtime | Your build system | An ephemeral Cloud Build job with an image that Google maintains |
| State | A Cloud Storage backend that you configure | Stored by Infra Manager for each revision; no backend block |
| Plan review | `terraform plan -out` in the pipeline | A preview runs `terraform plan`; export it as a binary plan or JSON |
| History | Git history and object versions of the state | Revisions `r-0`, `r-1`, and so on, each with logs, configuration, resources, and state |
| Terraform version | The version that you choose | Supported versions only; you can upgrade a deployment but not downgrade it |
| Time limit | Set by your build system | Two hours to create or update; one hour for a preview |
| Cost | Your build system | Cloud Build and Cloud Storage charges only |

Sources: [Best practices for Terraform operations](https://docs.cloud.google.com/docs/terraform/best-practices/operations), [Store Terraform state in a Cloud Storage bucket](https://docs.cloud.google.com/docs/terraform/resource-management/store-state), [Infrastructure Manager overview](https://docs.cloud.google.com/infrastructure-manager/docs/overview), [Terraform and Infrastructure Manager](https://docs.cloud.google.com/infrastructure-manager/docs/infra-manager-terraform), [Deploy infrastructure using Infrastructure Manager](https://docs.cloud.google.com/infrastructure-manager/docs/deploy-resources), [Preview a deployment](https://docs.cloud.google.com/infrastructure-manager/docs/preview-deployment), [Export and view preview results](https://docs.cloud.google.com/infrastructure-manager/docs/export-view-preview-results), [Deployments, revisions, and previews overview](https://docs.cloud.google.com/infrastructure-manager/docs/deployments-revisions), [Infrastructure Manager pricing](https://cloud.google.com/infrastructure-manager/pricing).

## Terraform on Google Cloud: the recommended setup

### Authentication

Application Default Credentials (ADC) is the recommended way for Terraform to authenticate. The same configuration then works on a workstation and in production.

| Where Terraform runs | Recommended credentials |
|---|---|
| Developer workstation | User ADC from `gcloud auth application-default login` |
| Workstation, one service account for each environment | Impersonation: `--impersonate-service-account` on the ADC login, or `impersonate_service_account` in the provider block |
| Cloud Build, GKE, or Compute Engine | An attached user-managed service account, not the default service account |
| CI system on premises or in another cloud | Workload Identity Federation |
| No other option | A service account key, which you must secure yourself |

Sources: [Authentication for Terraform](https://docs.cloud.google.com/docs/terraform/authentication), [Best practices for Terraform operations](https://docs.cloud.google.com/docs/terraform/best-practices/operations).

Impersonation and Workload Identity Federation are covered in [Secure remote and workload access](note:3.1-secure-access).

### State

Terraform keeps state in a local `terraform.tfstate` file by default. This default can make team use difficult, because each machine has its own view of the infrastructure ([Store Terraform state in a Cloud Storage bucket](https://docs.cloud.google.com/docs/terraform/resource-management/store-state)). Configure state as follows:

- Use the Cloud Storage (`gcs`) backend. It locks the state so that a team can work together, and it keeps sensitive state data out of version control ([Best practices for security](https://docs.cloud.google.com/docs/terraform/best-practices/security)).
- On the bucket, turn on Object Versioning, enforce public access prevention, and use uniform bucket-level access. Lifecycle rules can delete old state versions ([Store Terraform state in a Cloud Storage bucket](https://docs.cloud.google.com/docs/terraform/resource-management/store-state)).
- Give bucket admin permissions to a small set of administrators. Other developers only read and write objects ([Store Terraform state in a Cloud Storage bucket](https://docs.cloud.google.com/docs/terraform/resource-management/store-state)).
- Keep secrets out of state. Some resources, such as `google_service_account_key`, store secret values in plaintext in state. Mark sensitive outputs as sensitive ([Best practices for security](https://docs.cloud.google.com/docs/terraform/best-practices/security)).
- Never edit the state file by hand. Use the `terraform state` commands ([Best practices for Terraform operations](https://docs.cloud.google.com/docs/terraform/best-practices/operations)).

### Structure of the code

| Topic | Google recommendation |
|---|---|
| Size of one state | No more than 100 resources, and ideally only a few dozen |
| Environments | A `modules/` directory for the service, and an `environments/` directory with one root configuration for each environment |
| Environment files | Each environment directory has its own `backend.tf` and a `main.tf` that calls the service module |
| Workspaces | Use only the default workspace; do not separate environments with CLI workspaces in one shared backend |
| Values from other configurations | Read their outputs through remote state; use data sources only for resources that Terraform does not manage |
| Versions | Pin providers to a minor version in root modules, and commit `.terraform.lock.hcl`; pin modules to a major version |
| Reusable modules | Do not configure providers or backends; release SemVer tags |
| Stateful resources | Turn on deletion protection, for example `prevent_destroy` |

Sources: [Best practices for root modules](https://docs.cloud.google.com/docs/terraform/best-practices/root-modules), [Best practices for reusable modules](https://docs.cloud.google.com/docs/terraform/best-practices/reusable-modules), [Best practices for cross-configuration communication](https://docs.cloud.google.com/docs/terraform/best-practices/cross-config-communication), [Best practices for general style and structure](https://docs.cloud.google.com/docs/terraform/best-practices/general-style-structure).

Organize repositories along team boundaries, which Google calls the best structure for most enterprises. When root configurations deploy directly, use a separate branch for each environment ([Best practices for version control](https://docs.cloud.google.com/docs/terraform/best-practices/version-control)).

### Modules and blueprints

A module is a reusable set of Terraform files. A blueprint packages deployable modules and policy for one opinionated solution. For example, the `example-foundation` blueprint composes Cloud Foundation Toolkit (CFT) modules into a secure foundation ([Terraform blueprints and modules for Google Cloud](https://docs.cloud.google.com/docs/terraform/blueprints/terraform-blueprints)). The enterprise foundations blueprint (formerly the security foundations blueprint) deploys its Terraform through a Cloud Build GitOps pipeline that also runs policy checks ([Enterprise foundations blueprint](https://docs.cloud.google.com/architecture/blueprints/security-foundations)).

## Run Terraform safely

Google's reference pipeline uses Cloud Build and Git branches:

1. A developer pushes to a feature branch. Cloud Build runs `terraform plan` and links the plan to the pull request.
2. After review, a merge to the `dev` branch applies the change to the development environment.
3. After tests pass, a merge from `dev` to `prod` applies the change to production.

Source: [Managing infrastructure as code with Terraform, Cloud Build, and GitOps](https://docs.cloud.google.com/docs/terraform/resource-management/managing-infrastructure-as-code).

Add these controls:

- **Pre-apply policy checks.** Convert the plan to JSON with `terraform show -json`, then run `gcloud beta terraform vet` with your policy library. It returns exit code 2 when it finds violations ([Validate policies](https://docs.cloud.google.com/docs/terraform/policy-validation/validate-policies)).
- **Continuous audits.** After `terraform apply`, run automated security checks such as Security Health Analytics ([Best practices for security](https://docs.cloud.google.com/docs/terraform/best-practices/security)).
- **Separation of duties.** Use this control if you cannot run Terraform from an automated system that no user can access. Limit each Terraform identity to its area, for example a network service account for the network project ([Best practices for security](https://docs.cloud.google.com/docs/terraform/best-practices/security)).
- **Tests, least expensive first.** Start with static analysis (`terraform validate`). Next, run module integration tests, for example with Google's blueprint testing framework or Terratest. Last, run end-to-end tests in a fresh project ([Best practices for testing](https://docs.cloud.google.com/docs/terraform/best-practices/testing)).

CI/CD design is in [SDLC, CI/CD, and service provisioning](note:4.1-sdlc-cicd). Release strategies are in [Deployment and release management](note:6.3-release-management).

## Infrastructure Manager in detail

Infra Manager runs each deployment as a Cloud Build job, streams the logs to a bucket that it creates, and retries some intermittent failures ([Infrastructure Manager overview](https://docs.cloud.google.com/infrastructure-manager/docs/overview)).

- **Sources.** A Cloud Storage bucket, a Git repository, or a local directory ([Deploy infrastructure using Infrastructure Manager](https://docs.cloud.google.com/infrastructure-manager/docs/deploy-resources)).
- **Revisions.** The first deployment is revision `r-0`. Each update creates the next revision ([Deployments, revisions, and previews overview](https://docs.cloud.google.com/infrastructure-manager/docs/deployments-revisions)).
- **Previews.** A preview runs `terraform plan` ([Preview a deployment](https://docs.cloud.google.com/infrastructure-manager/docs/preview-deployment)). You can export it and list resource changes and resource drift ([Export and view preview results](https://docs.cloud.google.com/infrastructure-manager/docs/export-view-preview-results)).
- **State.** To change state, lock the deployment, download the state file, change it with Terraform commands, upload it, and unlock ([Manage the Terraform state file](https://docs.cloud.google.com/infrastructure-manager/docs/state-file)).
- **Service account.** Infra Manager runs Terraform as the service account that you name. It needs `roles/config.agent` plus permissions for every resource in the configuration. The user needs the Service Account User role on it ([Configure the service account](https://docs.cloud.google.com/infrastructure-manager/docs/configure-service-account)).
- **Deletion.** Deleting a deployment deletes its resources by default. `--delete-policy=abandon` keeps the resources ([Delete a deployment](https://docs.cloud.google.com/infrastructure-manager/docs/delete-deployments)).
- **Automation.** The `im_cloudbuild_workspace` module creates Cloud Build triggers: a pull request creates a preview, and a merge updates the deployment ([Automate the deployment of Google Cloud resources](https://docs.cloud.google.com/infrastructure-manager/docs/automate-git)).
- **Data.** Infra Manager does not migrate data. If a revision deletes a database, applying the previous revision does not restore the data ([Automate the deployment of Google Cloud resources](https://docs.cloud.google.com/infrastructure-manager/docs/automate-git)).

## Config Connector and Config Controller

Config Connector is an open source Kubernetes add-on. Its custom resource definitions (CRDs) and controllers create and manage Google Cloud resources. It changes cloud resources with its own IAM service account. So, control who can create Config Connector objects, for example by applying them only from a trusted repository ([Config Connector overview](https://docs.cloud.google.com/config-connector/docs/overview)).

Config Controller is a hosted version of Config Connector. It includes Config Sync for GitOps and Policy Controller for guardrails, and it detects and repairs drift ([Config Controller overview](https://docs.cloud.google.com/kubernetes-engine/config-controller/docs/overview)).

| Concern | Terraform | Config Connector |
|---|---|---|
| Model | You run `plan` and `apply` when you want a change | Controllers reconcile each resource after an update and again at an interval |
| Order of creation | Terraform uses the dependencies between resources to create them in the correct order | You create resources in any order; the system becomes consistent over time |
| Drift | Found at the next `plan` or `apply` | Corrected at each reconciliation |
| Change to an immutable field | The execution plan shows the change before anything happens | An `UpdateFailed` event; you delete and recreate the resource |

Sources: [Overview of Terraform on Google Cloud](https://docs.cloud.google.com/docs/terraform/terraform-overview), [Best practices on dependency management](https://docs.cloud.google.com/docs/terraform/best-practices/dependency-management), [Reconciliation strategy](https://docs.cloud.google.com/config-connector/docs/concepts/reconciliation).

## Bring existing resources under IaC

Google's first choice is to create a new resource through Terraform and delete the old one. Import only when deleting the old resource causes significant toil, and get explicit approval. After the import, manage the resource only with Terraform ([Best practices for Terraform operations](https://docs.cloud.google.com/docs/terraform/best-practices/operations)).

| Method | Use it when | Notes |
|---|---|---|
| `terraform import ADDRESS ID` | You import one resource | Writes to state at once; import each resource in a module separately |
| `import` block | You import in bulk and want to preview the import | Terraform 1.5 or later; `plan` shows the import and `apply` runs it; `-generate-config-out` writes the resource blocks |
| `gcloud beta resource-config bulk-export --resource-format=terraform`, then `gcloud beta resource-config terraform generate-import` | You need code for a whole project, folder, or organization | Preview; needs the Config Connector CLI component and the Cloud Asset API; not all resource types |
| `gcloud infra-manager deployments apply --import-existing-resources` | An Infra Manager deployment meets existing resources | Imports supported resource types after a 409 conflict |

Sources: [Import your Google Cloud resources into Terraform state](https://docs.cloud.google.com/docs/terraform/resource-management/import), [Export your Google Cloud resources to Terraform format](https://docs.cloud.google.com/docs/terraform/resource-management/export), [gcloud infra-manager deployments apply](https://docs.cloud.google.com/sdk/gcloud/reference/infra-manager/deployments/apply).

## Migrate from Deployment Manager

| Date | Event |
|---|---|
| April 1, 2026 | Support for Deployment Manager stopped |
| June 30, 2026 | New users cannot enable the Deployment Manager V2 API or create a first deployment |
| March 31, 2027 | The maximum support extension ends |
| After June 30, 2027 | Google turns down the service and its APIs |

Source: [Deployment Manager deprecation](https://docs.cloud.google.com/deployment-manager/docs/deprecations).

Resources that Deployment Manager created keep working ([Deployment Manager deprecation](https://docs.cloud.google.com/deployment-manager/docs/deprecations)). To move to Infra Manager:

1. Convert the YAML configurations and Jinja or Python templates with DM Convert (Preview). It produces Terraform or Kubernetes Resource Model (KRM) files, but it does not convert composite types ([Using DM Convert to transition to Terraform or KRM](https://docs.cloud.google.com/deployment-manager/docs/dm-convert)).
2. Import the Terraform resources into Infra Manager ([Deployment Manager deprecation](https://docs.cloud.google.com/deployment-manager/docs/deprecations)).
3. Delete the Deployment Manager deployment with the abandon policy, so that the resources stay ([Deployment Manager deprecation](https://docs.cloud.google.com/deployment-manager/docs/deprecations)).

One behavior changes. Deployment Manager offered rollback to a previous deployment. In Infra Manager, you roll forward: you deploy the previous Terraform configuration as a new revision ([Deployment Manager deprecation](https://docs.cloud.google.com/deployment-manager/docs/deprecations), [Deployments, revisions, and previews overview](https://docs.cloud.google.com/infrastructure-manager/docs/deployments-revisions)).

## AWS mapping

| AWS | Google Cloud | Difference that matters |
|---|---|---|
| AWS CloudFormation | Infrastructure Manager | Infra Manager runs standard Terraform; to go back, you deploy an earlier configuration as a new revision |
| Terraform S3 backend | Terraform `gcs` backend | The Cloud Storage backend locks state; turn on Object Versioning to keep old state |
| AWS Controllers for Kubernetes (ACK) | Config Connector or Config Controller | Config Controller is hosted and includes Config Sync and Policy Controller |
| CloudFormation Guard | `gcloud beta terraform vet` (Preview) | Checks the JSON of a Terraform plan against a constraint library |
| IAM role that a CI system assumes through OIDC | Workload Identity Federation | Keyless access for pipelines outside Google Cloud |

Sources: [Deployment Manager deprecation](https://docs.cloud.google.com/deployment-manager/docs/deprecations), [Deployments, revisions, and previews overview](https://docs.cloud.google.com/infrastructure-manager/docs/deployments-revisions), [Best practices for security](https://docs.cloud.google.com/docs/terraform/best-practices/security), [Store Terraform state in a Cloud Storage bucket](https://docs.cloud.google.com/docs/terraform/resource-management/store-state), [Compare AWS and Azure services to Google Cloud](https://docs.cloud.google.com/docs/get-started/aws-azure-gcp-service-comparison), [Config Controller overview](https://docs.cloud.google.com/kubernetes-engine/config-controller/docs/overview), [Validate policies](https://docs.cloud.google.com/docs/terraform/policy-validation/validate-policies), [Best practices for Terraform operations](https://docs.cloud.google.com/docs/terraform/best-practices/operations).

## Exam traps

- **Deployment Manager for new work.** It has no support after April 1, 2026, and new users cannot enable its API ([Deployment Manager deprecation](https://docs.cloud.google.com/deployment-manager/docs/deprecations)).
- **A backend block in an Infra Manager configuration.** Infra Manager manages the state, so remove the backend block ([Terraform and Infrastructure Manager](https://docs.cloud.google.com/infrastructure-manager/docs/infra-manager-terraform), [Deployment Manager deprecation](https://docs.cloud.google.com/deployment-manager/docs/deprecations)).
- **Local state or state in Git for a team.** Use the Cloud Storage backend, and add state files to `.gitignore` ([Best practices for security](https://docs.cloud.google.com/docs/terraform/best-practices/security)).
- **`terraform validate` as a policy check.** It checks syntax and structure. Policy checks need a tool such as `gcloud beta terraform vet` ([Best practices for testing](https://docs.cloud.google.com/docs/terraform/best-practices/testing), [Validate policies](https://docs.cloud.google.com/docs/terraform/policy-validation/validate-policies)).
- **Authoritative IAM resources.** `google_project_iam_policy` can remove roles that Google Cloud manages and break services ([Best practices when working with Google Cloud resources](https://docs.cloud.google.com/docs/terraform/best-practices/working-with-resources)).
- **Service account keys in CI.** Use the attached service account on Google Cloud, or Workload Identity Federation outside it ([Best practices for Terraform operations](https://docs.cloud.google.com/docs/terraform/best-practices/operations)).
- **Infra Manager for application releases.** It does not deploy applications onto your resources ([Infrastructure Manager overview](https://docs.cloud.google.com/infrastructure-manager/docs/overview)).
- **"Rollback" restores data.** Applying an earlier revision again does not restore deleted data ([Automate the deployment of Google Cloud resources](https://docs.cloud.google.com/infrastructure-manager/docs/automate-git)).
- **CLI workspaces for environments.** Google recommends separate environment directories, each with its own backend ([Best practices for root modules](https://docs.cloud.google.com/docs/terraform/best-practices/root-modules)).
- **Continuous drift correction from Terraform.** Terraform compares the infrastructure with the code only when you run it ([Overview of Terraform on Google Cloud](https://docs.cloud.google.com/docs/terraform/terraform-overview)). Config Connector reconciles continuously ([Reconciliation strategy](https://docs.cloud.google.com/config-connector/docs/concepts/reconciliation)).
