## Why it matters

After you pick Compute Engine or GKE, you still choose the machine family, the machine shape, the provisioning model, and any isolation or security features. The exam tests these choices through cost, availability, licensing, and compliance constraints. Typical questions ask when to use Spot VMs and when a custom machine type saves money. Others ask when sole-tenant nodes are required, and how to secure capacity for a launch or a DR plan.

## Key points

- Compute Engine has six machine families: general-purpose, compute-optimized, memory-optimized, storage-optimized, network-optimized, and accelerator-optimized ([Machine families resource and comparison guide](https://docs.cloud.google.com/compute/docs/machine-resource)).
- Custom machine types are available for the N and E general-purpose series (N4, N4D, N4A, N2, N2D, E2, N1) and for G2. They cost 5% more than equivalent predefined types ([Create a VM with a custom machine type](https://docs.cloud.google.com/compute/docs/instances/creating-instance-with-custom-machine-type)).
- Extended memory adds memory beyond the normal per-vCPU range on N4, N4A, N4D, N2, N2D, and N1 custom types. E2 and predefined types do not support it ([Create a VM with a custom machine type](https://docs.cloud.google.com/compute/docs/instances/creating-instance-with-custom-machine-type)).
- Compute Engine has four provisioning models: standard (the default), Spot, flex-start, and reservation-bound ([Compute Engine instances provisioning models](https://docs.cloud.google.com/compute/docs/instances/provisioning-models)).
- Spot VMs give discounts of up to 91% and have no minimum or maximum runtime. Compute Engine can preempt them at any time, and no SLA covers them ([Spot VMs](https://docs.cloud.google.com/compute/docs/instances/spot)).
- Preemptible VMs are the older version of Spot VMs. They always stop after 24 hours, and Google recommends Spot VMs instead ([Preemptible VM instances](https://docs.cloud.google.com/compute/docs/instances/preemptible)).
- On preemption, a Spot VM stops by default. Set the termination action to `DELETE` to delete it instead ([Spot VMs](https://docs.cloud.google.com/compute/docs/instances/spot)).
- A reservation gives high assurance of capacity in one zone. You pay for reserved resources whether VMs use them or not ([About reservations](https://docs.cloud.google.com/compute/docs/instances/reservations-overview)).
- Sole-tenant nodes are physical servers dedicated to your project's VMs. Use them for physical isolation and for BYOL licenses that count physical cores or processors ([Sole-tenancy overview](https://docs.cloud.google.com/compute/docs/nodes/sole-tenant-nodes)).
- Shielded VM protects the boot chain with Secure Boot, a vTPM, and integrity monitoring. Confidential VM encrypts data in use with hardware-based memory encryption ([Shielded VM overview](https://docs.cloud.google.com/compute/shielded-vm/docs/shielded-vm), [Confidential VM overview](https://docs.cloud.google.com/confidential-computing/confidential-vm/docs/confidential-vm-overview)).
- VMs with attached GPUs cannot live migrate. Compute Engine stops them for host maintenance and gives a 1-hour notice ([Handle GPU host maintenance events](https://docs.cloud.google.com/compute/docs/gpus/gpu-host-maintenance)).

## Machine families

Pick the family from the workload profile first, then the series inside it.

| Family | Example series | Use it for |
|---|---|---|
| General-purpose | E2 (lowest cost), N4 / N4D / N4A / N2 / N2D (balanced), C4 / C4D / C4A / C3 / C3D (consistently high performance), Tau T2D / T2A (scale-out) | Web and app servers, microservices, dev and test, databases, most workloads |
| Compute-optimized | H4D, H3, C2, C2D | HPC, EDA, modeling and simulation, compute-bound workloads with high per-core performance |
| Memory-optimized | X4, M4, M4N, M3, M2, M1 | SAP HANA, in-memory data stores, memory-intensive HPC |
| Storage-optimized | Z3, Z4D | SQL, NoSQL, and vector databases, data warehouses, search, distributed file systems |
| Network-optimized | C4N, M4N | Network and security appliances, high-performance databases, I/O-intensive analytics |
| Accelerator-optimized | A4X Max, A4X, A4, A3, A2 (A series); G4, G2 (G series) | ML training and serving, HPC with GPUs (A series); graphics, video transcoding, virtual workstations, single-host inference (G series) |

Sources: [Machine families resource and comparison guide](https://docs.cloud.google.com/compute/docs/machine-resource), [GPU machine types](https://docs.cloud.google.com/compute/docs/gpus).

Other facts that the exam uses:

- **Shared-core types.** E2 offers `e2-micro`, `e2-small`, and `e2-medium`, which timeshare a physical core. They suit small, low-load apps ([Machine families resource and comparison guide](https://docs.cloud.google.com/compute/docs/machine-resource)).
- **Arm.** C4A and N4A run on Google Axion processors, and T2A runs on Ampere Altra. A vCPU on these series is a full physical core ([Machine families resource and comparison guide](https://docs.cloud.google.com/compute/docs/machine-resource)).
- **Bare metal machine types.** Types with `-metal` in the name have no hypervisor. They are not related to Bare Metal Solution ([Machine families resource and comparison guide](https://docs.cloud.google.com/compute/docs/machine-resource)).
- **Rightsizing.** After a VM runs, use machine type recommendations to adjust its size ([Machine families resource and comparison guide](https://docs.cloud.google.com/compute/docs/machine-resource)).

For TPUs and AI accelerator consumption options, see [AI Hypercomputer: accelerators and consumption models](note:2.4-ai-hypercomputer).

## Custom machine types and extended memory

A custom machine type lets you set the vCPU count and memory when no predefined shape fits. The price includes a 5% premium over predefined types, and the premium also applies when commitments cover the VM ([Create a VM with a custom machine type](https://docs.cloud.google.com/compute/docs/instances/creating-instance-with-custom-machine-type)).

| Option | Use when | Limits |
|---|---|---|
| Predefined machine type | A standard shape (`highcpu`, `standard`, `highmem`) fits the workload. | Fixed vCPU and memory. |
| Custom machine type | The workload needs a shape between predefined types, for example 6 vCPU with 20 GB. | N and E series and G2 only; each series has vCPU and memory-per-vCPU limits. |
| Custom type with extended memory | The workload needs more memory per vCPU than the default maximum of the series, for example an in-memory database or software licensed per vCPU. | N4, N4A, N4D, N2, N2D, and N1 only. Extended memory costs more per GB and does not qualify for resource-based CUDs. |

Source: [Create a VM with a custom machine type](https://docs.cloud.google.com/compute/docs/instances/creating-instance-with-custom-machine-type).

Extended memory is a licensing tool too. In-memory databases such as SQL Server, MongoDB, or Redis need more memory per vCPU. When software is licensed per vCPU, extended memory adds memory without adding licensed vCPUs ([Create a VM with a custom machine type](https://docs.cloud.google.com/compute/docs/instances/creating-instance-with-custom-machine-type)).

## Provisioning models

The provisioning model sets the availability, the lifespan, and the price of a VM. If you do not set one, Compute Engine uses standard ([Compute Engine instances provisioning models](https://docs.cloud.google.com/compute/docs/instances/provisioning-models)).

| Model | Use for | Availability and lifespan | Price |
|---|---|---|---|
| Standard | Web servers, databases, enterprise apps: work that needs stability | You decide when to stop or delete. Best-effort capacity, or high assurance through a reservation. | On-demand; committed use discounts apply |
| Spot | Batch, HPC, CI/CD, data analytics, media encoding, online inference: work that tolerates interruption | Compute Engine can preempt at any time. No minimum or maximum runtime. | Up to 91% off |
| Flex-start | Jobs of up to 7 days on GPUs, TPUs, or H4D, such as fine-tuning or batch inference | Dynamic Workload Scheduler obtains capacity; runs 10 minutes to 7 days. | Discounts for some machine types |
| Reservation-bound | Training or HPC with a fixed run time on reserved capacity | Capacity reserved for a future date; VMs stop or delete at the end of the period. | Charged for the reservation period |

Sources: [Compute Engine instances provisioning models](https://docs.cloud.google.com/compute/docs/instances/provisioning-models), [Spot VMs](https://docs.cloud.google.com/compute/docs/instances/spot), [Committed use discounts (CUDs) for Compute Engine](https://docs.cloud.google.com/compute/docs/instances/committed-use-discounts-overview).

Flex-start and reservation-bound VMs are mostly for AI and HPC capacity. The details belong to [AI Hypercomputer: accelerators and consumption models](note:2.4-ai-hypercomputer). For committed use discounts and sustained use discounts, see [Cost optimization and CapEx/OpEx](note:4.2-cost-optimization).

### How Spot VMs behave

Design a Spot workload for sudden loss of any VM. The preemption sequence has four steps ([Spot VMs](https://docs.cloud.google.com/compute/docs/instances/spot)):

1. Compute Engine sets the `preempted` metadata value to `TRUE`. Your workload can watch for this signal.
2. After the preemption notice duration, Compute Engine sends a soft-off signal. The default notice duration is 0 seconds; a 120-second notice is in Preview.
3. A shutdown script can run during the shutdown period, which is best effort and up to 30 seconds.
4. The VM stops (termination action `STOP`, the default) or is deleted (`DELETE`).

Rules that follow from this design:

- **Where it fits.** Spot VMs suit fault-tolerant batch work: if some VMs stop, the job slows but continues ([Spot VMs](https://docs.cloud.google.com/compute/docs/instances/spot)).
- **No SLA.** Spot VMs cannot live migrate or restart automatically after a host event, so the Compute Engine SLA excludes them ([Spot VMs](https://docs.cloud.google.com/compute/docs/instances/spot)).
- **MIGs.** You set the Spot model in the instance template. The MIG keeps trying to recreate preempted VMs when capacity returns ([Spot VMs](https://docs.cloud.google.com/compute/docs/instances/spot)).
- **Billing.** You pay nothing for a stopped Spot VM, but its disks still cost money. If Compute Engine preempts a Spot VM in its first minute, you pay nothing for that VM ([Spot VMs](https://docs.cloud.google.com/compute/docs/instances/spot)).
- **Capacity.** Reservations cannot supply capacity for Spot VMs or preemptible VMs ([Choose a reservation type](https://docs.cloud.google.com/compute/docs/instances/choose-reservation-type)).
- **GKE.** Keep a node pool of standard VMs next to Spot node pools, and use taints so that critical Pods avoid Spot nodes ([GKE Spot VMs](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/spot-vms)).

## Capacity: reservations and placement

Reservations and placement policies solve different problems. A reservation gives high assurance that capacity exists. A placement policy controls where VMs land relative to each other.

| Tool | What it does | Use it for |
|---|---|---|
| On-demand reservation | Reserves capacity in one zone now; you keep it until you delete it | Growth, planned spikes, large migrations, backup and DR capacity |
| Future reservation | Google reviews a request for capacity on a future date | Peak scale events or large migrations on a known date |
| Future reservation in calendar mode | Reserves GPUs, TPUs, or H4D for up to 90 days | Short training or HPC runs |
| Compact placement policy | Places VMs close together in a zone for low network latency | HPC, ML, and tightly coupled database servers |
| Spread placement policy | Places VMs on separate hardware in a zone | Replicated systems such as HDFS, Cassandra, or Kafka |

Sources: [Choose a reservation type](https://docs.cloud.google.com/compute/docs/instances/choose-reservation-type), [About reservations](https://docs.cloud.google.com/compute/docs/instances/reservations-overview), [About future reservation requests](https://docs.cloud.google.com/compute/docs/instances/future-reservations-overview), [About future reservation requests in calendar mode](https://docs.cloud.google.com/compute/docs/instances/future-reservations-calendar-mode-overview), [Placement policies overview](https://docs.cloud.google.com/compute/docs/instances/placement-policies-overview).

Reservation facts to know:

- **Billing.** A reservation bills at the on-demand rate of its resources while it exists. A VM that consumes it adds no second charge ([About reservations](https://docs.cloud.google.com/compute/docs/instances/reservations-overview)).
- **Matching.** A VM consumes a reservation only if its properties match the reservation exactly. The default consumption type is automatic; a specific reservation serves only VMs that target it by name ([About reservations](https://docs.cloud.google.com/compute/docs/instances/reservations-overview)).
- **Sharing.** A shared reservation serves several projects. The owner project must be on the allowlist of an organization policy constraint ([About reservations](https://docs.cloud.google.com/compute/docs/instances/reservations-overview)).
- **Discounts do not reserve.** Commitments do not reserve zonal capacity. For a discount and assured capacity, buy a commitment and also create reservations ([Combine reservations with committed use discounts](https://docs.cloud.google.com/compute/docs/instances/reservations-with-commitments)).

## Isolation and licensing: sole-tenant nodes

A sole-tenant node is a physical server that hosts only your project's VMs. You can share a node group with other projects or with the whole organization ([Sole-tenancy overview](https://docs.cloud.google.com/compute/docs/nodes/sole-tenant-nodes)).

Use sole-tenant nodes for these reasons:

- **Compliance.** Finance or healthcare rules can require physical separation from other customers' VMs ([Sole-tenancy overview](https://docs.cloud.google.com/compute/docs/nodes/sole-tenant-nodes)).
- **Per-core or per-processor BYOL.** Licenses with dedicated hardware terms need your own media on compliant hardware such as sole-tenant nodes. Compute Engine reports the physical server ID, so you can track core use in Cloud Logging ([Bringing your own licenses](https://docs.cloud.google.com/compute/docs/nodes/bringing-your-own-licenses), [Sole-tenancy overview](https://docs.cloud.google.com/compute/docs/nodes/sole-tenant-nodes)).
- **Not for every license.** RHEL or SLES BYOS and Microsoft applications such as SQL Server do not need sole-tenant nodes. Use Microsoft License Mobility for those applications ([Bringing your own licenses](https://docs.cloud.google.com/compute/docs/nodes/bringing-your-own-licenses)).

The host maintenance policy controls how many physical servers your VMs touch:

| Policy | Behavior | Use for |
|---|---|---|
| Default | VMs live migrate to a new sole-tenant node, with no fixed pool of physical servers. VMs that cannot live migrate restart on a new node. | General workloads; per-user or per-device licenses |
| Restart in place | VMs stop during host events and restart on the same physical server. | Licenses tied to physical cores; workloads that tolerate about one hour of downtime |
| Migrate within node group | VMs live migrate only inside a fixed set of servers. Google holds back 1 node per 20 nodes. | Highly available workloads with physical-core licenses |

Source: [Sole-tenancy overview](https://docs.cloud.google.com/compute/docs/nodes/sole-tenant-nodes).

You pay for the whole node plus a sole-tenancy premium, and the VMs on it cost nothing extra. The premium qualifies for flexible CUDs and SUDs, but not resource-based CUDs ([Sole-tenancy overview](https://docs.cloud.google.com/compute/docs/nodes/sole-tenant-nodes)). For the wider licensing picture in a migration, see [Licensing and financial impact of a migration](note:1.4-licensing-and-financials).

## Shielded VM and Confidential VM

These two features answer different threats.

| | Shielded VM | Confidential VM |
|---|---|---|
| Threat | Boot-level and kernel-level malware and rootkits | Reading or changing data in memory while it is in use |
| How | Secure Boot, vTPM with measured boot, integrity monitoring | Hardware memory encryption: AMD SEV, AMD SEV-SNP, Intel TDX, and NVIDIA Confidential Computing for GPUs |
| Enforce | Organization policy constraint `constraints/compute.requireShieldedVm` | Enable when you create the VM |
| Trade-off | vTPM and integrity monitoring are on by default; Google recommends Secure Boot when possible | Only AMD SEV on N2D and C3D supports live migration |

Sources: [Shielded VM overview](https://docs.cloud.google.com/compute/shielded-vm/docs/shielded-vm), [Confidential VM overview](https://docs.cloud.google.com/confidential-computing/confidential-vm/docs/confidential-vm-overview).

Confidential VM also backs Confidential GKE Nodes, Confidential Space, and Dataflow Confidential VM workers ([Confidential VM overview](https://docs.cloud.google.com/confidential-computing/confidential-vm/docs/confidential-vm-overview)). For encryption keys and data protection design, see [Encryption, Cloud KMS, and secrets](note:3.1-data-protection-kms).

## GPUs on Compute Engine

Choose the GPU family by workload. The A series targets large-scale training and serving. The G series targets graphics, video transcoding, virtual workstations, and single-host inference. N1 VMs accept attached T4, P4, or V100 GPUs, and T4 and P4 are near end of support ([GPU machine types](https://docs.cloud.google.com/compute/docs/gpus)).

Plan operations around GPU limits:

- **Host maintenance.** GPU VMs cannot live migrate, so they stop for host maintenance. Compute Engine sends a 1-hour notice through the metadata server ([Handle GPU host maintenance events](https://docs.cloud.google.com/compute/docs/gpus/gpu-host-maintenance)).
- **Zones.** Not every zone offers every GPU. A regional MIG with the `BALANCED`, `ANY`, or `ANY_SINGLE_ZONE` shape places VMs only in zones that have the hardware ([About regional MIGs](https://docs.cloud.google.com/compute/docs/instance-groups/regional-migs)).
- **Capacity.** For high assurance of GPU capacity, use a reservation. For serverless GPUs that scale to zero, consider Cloud Run ([Choose a reservation type](https://docs.cloud.google.com/compute/docs/instances/choose-reservation-type), [GPU support for services](https://docs.cloud.google.com/run/docs/configuring/services/gpu)).

A habit from fixed instance sizes: to get more memory, you move to a larger instance with more vCPUs. On Google Cloud, a custom machine type or extended memory can add memory without more vCPUs ([Create a VM with a custom machine type](https://docs.cloud.google.com/compute/docs/instances/creating-instance-with-custom-machine-type)).

## Exam traps

- **Preemptible VMs for a new design.** Spot VMs replace them and have no 24-hour limit ([Preemptible VM instances](https://docs.cloud.google.com/compute/docs/instances/preemptible)).
- **Spot VMs for a stateful database or a single-instance app with an SLA.** Spot VMs have no SLA and can stop at any time ([Spot VMs](https://docs.cloud.google.com/compute/docs/instances/spot)).
- **A reservation for Spot VMs.** Reservations cannot be used for Spot VMs or preemptible VMs ([Choose a reservation type](https://docs.cloud.google.com/compute/docs/instances/choose-reservation-type)).
- **A committed use discount to guarantee capacity.** Commitments do not reserve zonal capacity. Capacity comes from a reservation ([Combine reservations with committed use discounts](https://docs.cloud.google.com/compute/docs/instances/reservations-with-commitments)).
- **Sole-tenant nodes for every BYOL case.** SQL Server through License Mobility, and RHEL or SLES BYOS, do not need them ([Bringing your own licenses](https://docs.cloud.google.com/compute/docs/nodes/bringing-your-own-licenses)).
- **Extended memory on E2.** E2 custom types do not support extended memory. Use N4, N2, N2D, or another supported series ([Create a VM with a custom machine type](https://docs.cloud.google.com/compute/docs/instances/creating-instance-with-custom-machine-type)).
- **Shielded VM to protect data in memory.** Shielded VM protects boot integrity. Confidential VM protects data in use ([Shielded VM overview](https://docs.cloud.google.com/compute/shielded-vm/docs/shielded-vm), [Confidential VM overview](https://docs.cloud.google.com/confidential-computing/confidential-vm/docs/confidential-vm-overview)).
- **Live migration for GPU VMs.** GPU VMs stop during host maintenance, so design for restarts and watch for the 1-hour notice ([Handle GPU host maintenance events](https://docs.cloud.google.com/compute/docs/gpus/gpu-host-maintenance)).
