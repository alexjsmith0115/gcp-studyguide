## Why it matters

After you choose a database, you configure it for the availability target, the read and write load, and the expected growth. The exam tests the setting that meets a stated SLA, RPO, or scale need at the lowest cost. Examples are Cloud SQL HA against read replicas, a Spanner edition and configuration, a Bigtable app profile, and BigQuery partitioning. Product choice is on the [Choosing storage](note:1.3-storage-choice) page. Backups are on the [Data protection](note:2.2-data-protection) page.

## Key points

- A Cloud SQL HA (regional) instance has a primary and a standby in two zones. A write commits only after it reaches the disks in both zones ([About high availability](https://docs.cloud.google.com/sql/docs/postgres/high-availability)).
- Cloud SQL read replicas do not provide failover. Only a DR replica in Enterprise Plus edition supports failover. You can still promote a read replica to a standalone primary ([About replication in Cloud SQL](https://docs.cloud.google.com/sql/docs/postgres/replication), [Promote replicas for regional migration or disaster recovery](https://docs.cloud.google.com/sql/docs/postgres/replication/cross-region-replicas)).
- Cloud SQL Enterprise Plus has a 99.99% SLA that includes maintenance. Enterprise has 99.95% and excludes maintenance ([Cloud SQL editions overview](https://docs.cloud.google.com/sql/docs/postgres/editions-intro)).
- For private access from one VPC, use private services access. For access from several VPCs, projects, or organizations, use Private Service Connect ([Choose how to connect to Cloud SQL](https://docs.cloud.google.com/sql/docs/postgres/connection-options)).
- Spanner regional configurations have a 99.99% SLA (99.95% in Mexico and Stockholm). Dual-region and multi-region configurations have 99.999% and need Enterprise Plus ([Regional, dual-region, and multi-region configurations](https://docs.cloud.google.com/spanner/docs/instance-configurations), [Spanner editions overview](https://docs.cloud.google.com/spanner/docs/editions-overview), [Cloud Spanner Service Level Agreement](https://cloud.google.com/spanner/sla)).
- Do not start a Spanner primary key with a value that always increases or decreases, such as a timestamp ([Schema design best practices](https://docs.cloud.google.com/spanner/docs/schema-design)).
- Bigtable replication is eventually consistent by default. Single-cluster routing gives read-your-writes consistency ([Replication overview](https://docs.cloud.google.com/bigtable/docs/replication-overview)).
- A BigQuery multi-region location does not give cross-region redundancy ([BigQuery locations](https://docs.cloud.google.com/bigquery/docs/locations)).
- You cannot change the location of a Firestore database or a BigQuery dataset after creation ([Locations](https://docs.cloud.google.com/firestore/native/docs/locations), [Create datasets](https://docs.cloud.google.com/bigquery/docs/datasets)).

## Cloud SQL

### Editions

| Feature | Enterprise Plus | Enterprise |
|---|---|---|
| Availability SLA | 99.99%, includes maintenance | 99.95%, excludes maintenance |
| Planned maintenance downtime | Typically less than 1 second | Less than 30 seconds on average |
| Point-in-time log retention | Up to 35 days | Up to 7 days |
| Data cache and read pools | Yes | No |
| Advanced DR with a DR replica | Yes | No |

Sources: [Cloud SQL editions overview](https://docs.cloud.google.com/sql/docs/postgres/editions-intro), [Maintenance updates on Cloud SQL instances](https://docs.cloud.google.com/sql/docs/postgres/maintenance).

For PostgreSQL 16 and later, the default edition is Enterprise Plus. An in-place upgrade to Enterprise Plus has sub-second downtime ([Cloud SQL editions overview](https://docs.cloud.google.com/sql/docs/postgres/editions-intro)). Shared-core instances and single-zone instances are not covered by the SLA ([Cloud SQL Service Level Agreement](https://cloud.google.com/sql/sla)).

### High availability and replicas

| Option | What it gives | What it does not give |
|---|---|---|
| HA (regional instance) | Synchronous replication to a standby in a second zone. Automatic failover; the instance is unavailable for about 60 seconds. | Reads from the standby. Protection from a region outage. |
| Read replica | Read scaling in the same region. | Failover. |
| Cross-region read replica | Reads near remote users; asynchronous copy for regional DR and migration. | Zero data loss: recent transactions can be lost. |
| DR replica (Enterprise Plus) | Switchover with zero data loss, or replica failover after a region outage. | Automatic cross-region failover: you start the replica failover. |

Sources: [About high availability](https://docs.cloud.google.com/sql/docs/postgres/high-availability), [About high availability (MySQL)](https://docs.cloud.google.com/sql/docs/mysql/high-availability), [About replication in Cloud SQL](https://docs.cloud.google.com/sql/docs/postgres/replication), [Promote replicas for regional migration or disaster recovery](https://docs.cloud.google.com/sql/docs/postgres/replication/cross-region-replicas), [About disaster recovery (DR) in Cloud SQL](https://docs.cloud.google.com/sql/docs/postgres/intro-to-cloud-sql-disaster-recovery).

- An HA instance costs twice as much as a standalone instance. Cloud SQL does not recover a standalone instance from a zone outage automatically ([About high availability](https://docs.cloud.google.com/sql/docs/postgres/high-availability)).
- After a failover, the new primary stays primary, even when the original zone comes back ([About high availability](https://docs.cloud.google.com/sql/docs/postgres/high-availability)).
- Put read replicas in a different zone from the HA primary, so they keep working in a zone outage ([About replication in Cloud SQL](https://docs.cloud.google.com/sql/docs/postgres/replication)).
- Promoting a read replica stops replication and makes it a standalone primary ([Manage read replicas](https://docs.cloud.google.com/sql/docs/postgres/replication/manage-replicas)).
- A write endpoint is a global DNS name that resolves to the current primary. It needs the Cloud DNS API ([About disaster recovery (DR) in Cloud SQL](https://docs.cloud.google.com/sql/docs/postgres/intro-to-cloud-sql-disaster-recovery)). An instance that uses only Private Service Connect does not support it ([Choose how to connect to Cloud SQL](https://docs.cloud.google.com/sql/docs/postgres/connection-options)).

The DR runbook for a region outage is on the [Disaster recovery planning](note:4.1-disaster-recovery) page.

### Maintenance, connectivity, and storage

- **Maintenance.** A maintenance window is one hour on a day you choose. A deny maintenance period blocks maintenance for up to 90 days. Cloud SQL maintains read replicas before the primary ([Maintenance updates on Cloud SQL instances](https://docs.cloud.google.com/sql/docs/postgres/maintenance)).
- **Private IP.** Google recommends a private IP address. With private services access, only directly peered networks can connect, because transitive peering is not supported ([Choose how to connect to Cloud SQL](https://docs.cloud.google.com/sql/docs/postgres/connection-options), [Learn about using private IP](https://docs.cloud.google.com/sql/docs/postgres/private-ip)).
- **Public IP.** Connect through the Cloud SQL Auth Proxy or a Cloud SQL Language Connector. The Auth Proxy needs no authorized networks and no SSL configuration ([Choose how to connect to Cloud SQL](https://docs.cloud.google.com/sql/docs/postgres/connection-options), [About the Cloud SQL Auth Proxy](https://docs.cloud.google.com/sql/docs/postgres/sql-proxy)).
- **Authentication.** Use IAM database authentication when possible ([Choose how to connect to Cloud SQL](https://docs.cloud.google.com/sql/docs/postgres/connection-options)).
- **Storage growth.** Automatic storage increase is on by default and checks every 30 seconds. The automatic increase limit of 0 means no limit. An instance with a dedicated vCPU can have up to 64 TB. If storage runs out, the instance goes offline ([About instance settings](https://docs.cloud.google.com/sql/docs/postgres/instance-settings)).
- **Storage shrink.** Automatic increases are permanent. A manual storage shrink needs downtime ([About instance settings](https://docs.cloud.google.com/sql/docs/postgres/instance-settings), [About storage shrink](https://docs.cloud.google.com/sql/docs/postgres/about-storage-shrink)).

## AlloyDB for PostgreSQL

- An HA primary instance has an active node and a standby node in different zones ([AlloyDB overview](https://docs.cloud.google.com/alloydb/docs/overview)).
- AlloyDB writes the write-ahead log synchronously to a regional log persistor, so failover loses no data. Failure detection can take up to 30 seconds ([AlloyDB high availability overview](https://docs.cloud.google.com/alloydb/docs/high-availability)).
- Read pool instances scale reads, with up to 20 nodes across the cluster ([AlloyDB overview](https://docs.cloud.google.com/alloydb/docs/overview)).
- You can create up to five secondary clusters in other regions. They replicate asynchronously. Switchover reverses the roles with zero data loss. Cross-region failover is in Preview ([Cross-region replication overview](https://docs.cloud.google.com/alloydb/docs/cross-region-replication/about-cross-region-replication)).
- The columnar engine uses 30% of instance memory by default ([About the AlloyDB columnar engine](https://docs.cloud.google.com/alloydb/docs/columnar-engine/about)).

## Spanner

### Configuration and edition

| Configuration | SLA | Trade-off | Edition |
|---|---|---|---|
| Regional | 99.99% (99.95% in Mexico and Stockholm) | Lowest write latency in one region; lowest cost | All editions |
| Dual-region | 99.999% | Zero RPO in a region outage; only in Australia, Germany, India, and Japan | Enterprise Plus |
| Multi-region | 99.999% | Lower read latency in several regions; small write latency increase; higher cost | Enterprise Plus |

Sources: [Regional, dual-region, and multi-region configurations](https://docs.cloud.google.com/spanner/docs/instance-configurations), [Spanner editions overview](https://docs.cloud.google.com/spanner/docs/editions-overview), [Cloud Spanner Service Level Agreement](https://cloud.google.com/spanner/sla).

- Writes always go to the leader replica first. A read-write transaction from another region needs round trips to the leader region. Leader-aware routing, on by default, reduces them ([Replication](https://docs.cloud.google.com/spanner/docs/replication), [Leader-aware routing](https://docs.cloud.google.com/spanner/docs/leader-aware-routing)).
- Read-only replicas scale reads without a larger write quorum. Base multi-region configurations include them. To add optional read-only replicas, you need a custom configuration and Enterprise edition or higher ([Replication](https://docs.cloud.google.com/spanner/docs/replication), [Spanner editions overview](https://docs.cloud.google.com/spanner/docs/editions-overview)).
- Strong reads are the default. A read-only replica can serve stale reads locally when the staleness is at least 15 seconds ([Reads outside of transactions](https://docs.cloud.google.com/spanner/docs/reads), [Replication](https://docs.cloud.google.com/spanner/docs/replication)).
- An edition upgrade takes about 10 minutes, with no downtime and no data migration ([Spanner editions overview](https://docs.cloud.google.com/spanner/docs/editions-overview)).

### Compute capacity and growth

- Compute capacity is set in processing units (PUs) or nodes. 1,000 PUs equal 1 node. Spanner provides the full capacity in each zone that has a replica ([Compute capacity, nodes and processing units](https://docs.cloud.google.com/spanner/docs/compute-capacity)).
- Each node allows 10 TiB of data. If the database outgrows the capacity, Spanner might reject writes ([Compute capacity, nodes and processing units](https://docs.cloud.google.com/spanner/docs/compute-capacity)).
- Keep high-priority CPU below 65% for regional instances and 45% per region for dual-region and multi-region instances. These limits leave room to lose a zone or a region ([CPU utilization metrics](https://docs.cloud.google.com/spanner/docs/cpu-utilization)).
- The managed autoscaler needs Enterprise or Enterprise Plus. It uses the highest recommendation from the CPU and storage targets ([Managed autoscaler](https://docs.cloud.google.com/spanner/docs/managed-autoscaler)). The open source Autoscaler tool works with all editions, but you deploy and run it yourself ([Autoscaler tool overview](https://docs.cloud.google.com/spanner/docs/autoscaler-tool-overview)).

### Schema design

- Avoid hotspots: a key that starts with a timestamp or sequence sends all inserts to one server. Use UUID version 4, or a bit-reversed sequence ([Schema design best practices](https://docs.cloud.google.com/spanner/docs/schema-design)).
- Interleave child tables in parent tables to store related rows together ([Schemas overview](https://docs.cloud.google.com/spanner/docs/schema-and-data-model)).

## Bigtable

| Setting | Choice | Effect |
|---|---|---|
| Clusters | One cluster per zone, in up to 8 regions | Each cluster has a separate, independent copy of the data |
| App profile: single-cluster routing | One cluster serves the traffic | Read-your-writes consistency; optional single-row transactions; manual failover |
| App profile: multi-cluster routing | The nearest available cluster serves the traffic | Automatic failover; eventual consistency; no single-row transactions |
| Storage type | SSD or HDD, for all clusters | Permanent; when in doubt, choose SSD |
| Autoscaling | CPU target, storage target, and minimum and maximum nodes, per cluster | Uses the highest node recommendation |

Sources: [Instances, clusters, and nodes](https://docs.cloud.google.com/bigtable/docs/instances-clusters-nodes), [Choose between SSD and HDD storage](https://docs.cloud.google.com/bigtable/docs/choosing-ssd-hdd), [App profiles overview](https://docs.cloud.google.com/bigtable/docs/app-profiles), [Replication overview](https://docs.cloud.google.com/bigtable/docs/replication-overview), [Failovers](https://docs.cloud.google.com/bigtable/docs/failovers), [Autoscaling](https://docs.cloud.google.com/bigtable/docs/autoscaling).

- The SLA is 99.999% with multi-cluster routing across 3 or more regions, 99.99% for fewer regions (99.95% in Mexico and Stockholm), and 99.9% with single-cluster routing ([Cloud Bigtable Service Level Agreement](https://cloud.google.com/bigtable/sla)).
- At the maximum node count, a cluster that exceeds its storage limit rejects writes ([Autoscaling](https://docs.cloud.google.com/bigtable/docs/autoscaling)).
- Row keys: put a high-cardinality value, such as a user ID, before a timestamp. Reverse sequential numeric IDs. A hashed key loses the sort order that makes range reads efficient ([Schema design best practices](https://docs.cloud.google.com/bigtable/docs/schema-design)).
- For time series, no single schema fits every case. Time-bucket rows give better performance and compression. Single-timestamp rows, one row for each event, make tall and narrow tables ([Schema design for time series data](https://docs.cloud.google.com/bigtable/docs/schema-design-time-series)).
- Data Boost runs high-throughput read jobs on serverless compute, so analytics do not slow the application clusters ([Bigtable Data Boost overview](https://docs.cloud.google.com/bigtable/docs/data-boost-overview)).

## Firestore and Memorystore

**Firestore.** Choose a multi-region location to keep serving data after the loss of a region. Choose a regional location for lower cost and lower write latency ([Locations](https://docs.cloud.google.com/firestore/native/docs/locations)). The edition decides the data access mode: Standard supports the Native or Datastore API, and Enterprise supports MongoDB compatibility or Native mode. You cannot change the mode later ([Firestore editions overview](https://docs.cloud.google.com/firestore/native/docs/editions-overview)). A project can have several databases, for example to isolate test data or customers ([Create and manage databases](https://docs.cloud.google.com/firestore/native/docs/manage-databases)).

**Memorystore for Valkey.** Each shard has one primary node and up to five replicas, spread across zones. High availability needs at least one replica per shard ([Memorystore for Valkey overview](https://docs.cloud.google.com/memorystore/docs/valkey/product-overview), [High availability and replicas](https://docs.cloud.google.com/memorystore/docs/valkey/ha-and-replicas)). Replication is asynchronous, so a failover can lose acknowledged writes. For persistence, choose AOF or RDB, not both ([High availability and replicas](https://docs.cloud.google.com/memorystore/docs/valkey/ha-and-replicas), [Persistence overview](https://docs.cloud.google.com/memorystore/docs/valkey/persistence-overview)). For Memorystore for Redis, the Basic Tier is a cache only. The Standard Tier adds replication and automatic failover ([Redis tier capabilities](https://docs.cloud.google.com/memorystore/docs/redis/redis-tiers)).

## BigQuery storage configuration

| Setting | Rule |
|---|---|
| Dataset location | Set only at creation. A multi-region gives no cross-region redundancy. |
| Partitioning | One column only: time-unit column, ingestion time, or integer range. |
| Require partition filter | Every query must filter on the partitioning column. |
| Partition expiration | Deletes old partitions. With no table or dataset setting, partitions never expire. |
| Clustering | Up to four columns. Combine with partitioning for more. |
| Default table expiration on the dataset | Applies only to tables created after the change. |
| Storage billing model | Logical (uncompressed) bytes by default; physical (compressed) is an option. |

Sources: [Create datasets](https://docs.cloud.google.com/bigquery/docs/datasets), [BigQuery locations](https://docs.cloud.google.com/bigquery/docs/locations), [Introduction to partitioned tables](https://docs.cloud.google.com/bigquery/docs/partitioned-tables), [Manage partitioned tables](https://docs.cloud.google.com/bigquery/docs/managing-partitioned-tables), [Introduction to clustered tables](https://docs.cloud.google.com/bigquery/docs/clustered-tables), [Update dataset properties](https://docs.cloud.google.com/bigquery/docs/updating-datasets), [Introduction to datasets](https://docs.cloud.google.com/bigquery/docs/datasets-intro).

- Partitioning gives a cost estimate before the query runs. For clustered tables, the cost is known only after the query runs ([Introduction to clustered tables](https://docs.cloud.google.com/bigquery/docs/clustered-tables)).
- A dry run is free and shows the bytes that a query will process. A maximum bytes billed limit makes a query fail before it runs, at no charge. For a clustered table, the limit uses the upper-bound estimate ([Run a query](https://docs.cloud.google.com/bigquery/docs/running-queries), [Estimate and control costs](https://docs.cloud.google.com/bigquery/docs/best-practices-costs)).
- An authorized view lets users query a view without access to the source dataset. The view must be in a different dataset in the same location ([Authorized views](https://docs.cloud.google.com/bigquery/docs/authorized-views)).
- A table or partition that is not changed for 90 consecutive days moves to long-term storage, at about 50% lower price ([BigQuery pricing](https://cloud.google.com/bigquery/pricing)).
- Managed disaster recovery needs Enterprise Plus edition. It targets an RPO of 15 minutes ([Managed disaster recovery](https://docs.cloud.google.com/bigquery/docs/managed-disaster-recovery)).

## Plan for growth

| Product | Watch | Scale by |
|---|---|---|
| Cloud SQL | Storage, CPU, memory, read load | Automatic storage increase; a larger machine type; read replicas |
| AlloyDB | Read load | More read pool nodes |
| Spanner | High-priority CPU and storage per node | More compute capacity, or the managed autoscaler |
| Bigtable | CPU and storage utilization per cluster | Autoscaling with a maximum above the expected peak |
| Firestore | Nothing to size | Automatic |

## AWS mapping

| AWS | Google Cloud | Difference that matters |
|---|---|---|
| RDS Multi-AZ | Cloud SQL HA (regional instance) | The standby serves no reads. Use read replicas for reads. |
| RDS cross-region read replica | Cloud SQL cross-region replica, or an Enterprise Plus DR replica | Only a DR replica supports switchover and replica failover. |
| Aurora Global Database | AlloyDB secondary clusters, or Spanner multi-region | AlloyDB secondaries are asynchronous. Spanner multi-region commits each write to a quorum of replicas across regions. |
| DynamoDB on-demand capacity | Firestore | Serverless, with no capacity to set. |
| ElastiCache Multi-AZ | Memorystore for Valkey with replicas | Replication is asynchronous. |
| Redshift | BigQuery | Partition and cluster the tables. There is no cluster to size. |

## Exam traps

- **A Cloud SQL read replica as the failover target.** Read replicas cannot fail over. Use HA for zones and a DR replica for regions ([About replication in Cloud SQL](https://docs.cloud.google.com/sql/docs/postgres/replication)).
- **Send reads to the HA standby.** The standby cannot serve reads ([About high availability](https://docs.cloud.google.com/sql/docs/mysql/high-availability)).
- **VPC peering chains to reach Cloud SQL from many VPCs.** Transitive peering does not work. Use Private Service Connect ([Learn about using private IP](https://docs.cloud.google.com/sql/docs/postgres/private-ip), [Choose how to connect to Cloud SQL](https://docs.cloud.google.com/sql/docs/postgres/connection-options)).
- **Spanner multi-region on Standard edition.** It needs Enterprise Plus ([Spanner editions overview](https://docs.cloud.google.com/spanner/docs/editions-overview)).
- **A timestamp as the first Spanner or Bigtable key part.** It creates hotspots ([Schema design best practices](https://docs.cloud.google.com/spanner/docs/schema-design), [Schema design best practices](https://docs.cloud.google.com/bigtable/docs/schema-design)).
- **Multi-cluster routing for single-row transactions.** Use single-cluster routing ([App profiles overview](https://docs.cloud.google.com/bigtable/docs/app-profiles)).
- **Bigtable HDD for a latency-sensitive workload, to change later.** The storage type is permanent ([Instances, clusters, and nodes](https://docs.cloud.google.com/bigtable/docs/instances-clusters-nodes)).
- **A BigQuery multi-region dataset as regional DR.** It gives no cross-region redundancy ([BigQuery locations](https://docs.cloud.google.com/bigquery/docs/locations)).
- **A new dataset default expiration to clean up existing tables.** It applies only to new tables ([Update dataset properties](https://docs.cloud.google.com/bigquery/docs/updating-datasets)).
- **A `LIMIT` clause to cut the cost of `SELECT *`.** `LIMIT` does not reduce the bytes that the query reads. Select only the columns that you need ([Optimize query computation](https://docs.cloud.google.com/bigquery/docs/best-practices-performance-compute)).
