## Why it matters

Most exam designs put a load balancer at the front. Google Cloud lists 13 load balancer modes in three families. The correct mode depends on protocol, client location, scope, network tier, and edge services ([Choose a load balancer](https://docs.cloud.google.com/load-balancing/docs/choosing-load-balancer)). Wrong options usually name a real load balancer that fails one constraint: no UDP, no client IP, no Cloud CDN, or no Standard Tier.

## Key points

- Start with the traffic type. Application Load Balancers carry HTTP(S). Proxy Network Load Balancers carry TCP with optional SSL offload. Passthrough Network Load Balancers carry TCP, UDP, and other IP protocols ([Choose a load balancer](https://docs.cloud.google.com/load-balancing/docs/choosing-load-balancer)).
- Only external load balancers can be global. For internal load balancers with backends in several regions, choose a cross-region internal load balancer ([Choose a load balancer](https://docs.cloud.google.com/load-balancing/docs/choosing-load-balancer)).
- A global load balancer gives one anycast IP address and terminates TLS close to clients. A regional load balancer terminates TLS only in its own region ([Choose a load balancer](https://docs.cloud.google.com/load-balancing/docs/choosing-load-balancer)).
- The global external Application Load Balancer and the global external proxy Network Load Balancer work only in Premium Tier ([Network Service Tiers overview](https://docs.cloud.google.com/network-tiers/docs/overview)).
- Proxy load balancers do not preserve the client IP address in the packet. They supply it in the `X-Forwarded-For` header or with the PROXY protocol ([Load balancer feature comparison](https://docs.cloud.google.com/load-balancing/docs/features)).
- Google Cloud strongly recommends Certificate Manager for load balancer certificates. Google-managed wildcard certificates need Certificate Manager with DNS authorization ([SSL certificates overview](https://docs.cloud.google.com/load-balancing/docs/ssl-certificates)).
- With no SSL policy attached, the load balancer uses the `COMPATIBLE` profile with a minimum of TLS 1.0 ([SSL policies overview](https://docs.cloud.google.com/load-balancing/docs/ssl-policies-concepts)).
- Cloud CDN works only with the global external and the classic Application Load Balancer, and Cloud CDN is always Premium Tier ([Cloud CDN overview](https://docs.cloud.google.com/cdn/docs/overview), [Network Service Tiers overview](https://docs.cloud.google.com/network-tiers/docs/overview)).
- Google Cloud Armor (Cloud Armor) edge security policies apply before the CDN cache lookup. Backend security policies apply only to requests that go to the origin, such as cache misses ([Cloud CDN overview](https://docs.cloud.google.com/cdn/docs/overview)).

## The decision sequence

Answer these questions in order. Each answer removes options ([Choose a load balancer](https://docs.cloud.google.com/load-balancing/docs/choosing-load-balancer)).

1. **Traffic type.** HTTP(S): Application Load Balancer. TCP with optional SSL offload: proxy Network Load Balancer. UDP, ESP, GRE, ICMP, or an unchanged client packet: passthrough Network Load Balancer.
2. **Client location.** Internet clients need an external load balancer. Clients in the VPC network, a peered network, or on-premises over Cloud VPN or Cloud Interconnect use an internal one.
3. **Scope.** Users or backends in several regions: global (external) or cross-region (internal). TLS termination or resources that must stay in one region: regional.
4. **Network tier.** Premium Tier is the default and the only tier for global external load balancers. Standard Tier is a low-cost option when latency is not critical.
5. **Backend type.** VMs, GKE Pods, serverless, Cloud Storage, on-premises, or a published service ([Network endpoint groups overview](https://docs.cloud.google.com/load-balancing/docs/negs)).
6. **Edge services.** Certificates, SSL policies, Cloud CDN, Cloud Armor, and IAP each work only with some modes ([Load balancer feature comparison](https://docs.cloud.google.com/load-balancing/docs/features)).

## All load balancer modes

Application Load Balancers are Layer 7 proxies.

| Mode | Scope | Proxy | Network tier |
|---|---|---|---|
| Global external | Backends in many regions, one anycast IP | GFE, with Envoy traffic management | Premium only |
| Classic | Global in Premium Tier, regional in Standard Tier | GFE | Premium or Standard |
| Regional external | One region | Envoy in a proxy-only subnet | Premium or Standard |
| Regional internal | One region; optional global access for clients | Envoy in a proxy-only subnet | Premium |
| Cross-region internal | Backends in many regions; always globally accessible | Envoy in a proxy-only subnet | Premium |

Sources: [Choose a load balancer](https://docs.cloud.google.com/load-balancing/docs/choosing-load-balancer), [External Application Load Balancer overview](https://docs.cloud.google.com/load-balancing/docs/https), [Internal Application Load Balancer overview](https://docs.cloud.google.com/load-balancing/docs/l7-internal).

Network Load Balancers work at Layer 4.

| Mode | Type | Client protocols | Network tier | Client IP at the backend |
|---|---|---|---|---|
| Global external proxy | Proxy | TCP, optional SSL offload | Premium only | PROXY protocol |
| Classic proxy | Proxy | TCP, optional SSL offload | Premium (global) or Standard (regional) | PROXY protocol |
| Regional external proxy | Proxy | TCP | Premium or Standard | PROXY protocol |
| Regional internal proxy, cross-region internal proxy | Proxy | TCP without SSL offload | Premium | PROXY protocol |
| Global external passthrough (Preview) | Passthrough | TCP, UDP, ESP, GRE, ICMP, ICMPv6 | Premium | In the packet |
| Regional external passthrough | Passthrough | TCP, UDP, ESP, GRE, ICMP, ICMPv6 | Premium or Standard | In the packet |
| Internal passthrough | Passthrough | TCP, UDP, ICMP, ICMPv6, SCTP, ESP, AH, GRE | Premium | In the packet |

Sources: [Choose a load balancer](https://docs.cloud.google.com/load-balancing/docs/choosing-load-balancer), [Load balancer feature comparison](https://docs.cloud.google.com/load-balancing/docs/features).

Two older options remain supported:

- The classic modes use the `EXTERNAL` scheme. Google recommends that you migrate a classic Application Load Balancer to `EXTERNAL_MANAGED` to get the features of the global external Application Load Balancer ([Choose a load balancer](https://docs.cloud.google.com/load-balancing/docs/choosing-load-balancer)).
- A target pool is the legacy backend for the regional external passthrough Network Load Balancer. It supports only TCP or UDP and only IPv4 forwarding rules ([Passthrough Network Load Balancer overview](https://docs.cloud.google.com/load-balancing/docs/passthrough-network-load-balancer)).

## Global, cross-region, or regional

Resilience depends on the load balancer scope and on backend redundancy. A regional load balancer runs in several zones of one region, and an outage of that region affects it ([Choose a load balancer](https://docs.cloud.google.com/load-balancing/docs/choosing-load-balancer)).

| Choose | Use when | Do not use when |
|---|---|---|
| Global external | Users on several continents; backends in two or more regions; Cloud CDN | TLS must end in one jurisdiction; the design must use Standard Tier |
| Cross-region internal | Internal clients; the service must fail over to another region | Clients are on the internet |
| Regional (external or internal) | Backends and TLS termination must stay in one region | You need failover to another region |

Sources: [Choose a load balancer](https://docs.cloud.google.com/load-balancing/docs/choosing-load-balancer), [Internal Application Load Balancer overview](https://docs.cloud.google.com/load-balancing/docs/l7-internal), [Cloud CDN overview](https://docs.cloud.google.com/cdn/docs/overview).

The cross-region internal Application Load Balancer fails over automatically to healthy backends in other regions. Its VIPs are regional, so use DNS routing policies to send clients to the closest VIP ([Internal Application Load Balancer overview](https://docs.cloud.google.com/load-balancing/docs/l7-internal)).

## Proxy or passthrough

A proxy load balancer terminates the client connection and opens a new one to the backend. A passthrough load balancer delivers the packet unchanged, and the backend replies directly to the client (direct server return) ([Choose a load balancer](https://docs.cloud.google.com/load-balancing/docs/choosing-load-balancer)).

| Requirement | Proxy | Passthrough |
|---|---|---|
| Client source IP | `X-Forwarded-For` header or PROXY protocol | Unchanged in the packet |
| TLS termination and Google-managed certificates | Yes, except the regional external and the internal proxy Network Load Balancers | No; the backends decrypt TLS |
| Next hop of a static route for appliance VMs | No | Internal passthrough Network Load Balancer |

Sources: [Load balancer feature comparison](https://docs.cloud.google.com/load-balancing/docs/features), [Choose a load balancer](https://docs.cloud.google.com/load-balancing/docs/choosing-load-balancer), [Passthrough Network Load Balancer overview](https://docs.cloud.google.com/load-balancing/docs/passthrough-network-load-balancer), [Internal passthrough Network Load Balancers as next hops](https://docs.cloud.google.com/load-balancing/docs/internal/ilb-next-hop-overview).

If an application authenticates clients by source IP address, a proxy load balancer can break it. For Application Load Balancers, Google recommends Identity-Aware Proxy (IAP) as the authentication method instead ([Choose a load balancer](https://docs.cloud.google.com/load-balancing/docs/choosing-load-balancer)). IAP is covered in [secure access](note:3.1-secure-access).

## Network Service Tiers

You choose the tier per resource, such as the external IP address of a load balancer. In Premium Tier, packets enter Google's network as close as possible to the client. In Standard Tier, they enter near the load balancer's region ([Choose a load balancer](https://docs.cloud.google.com/load-balancing/docs/choosing-load-balancer)).

| Resource | Premium Tier | Standard Tier |
|---|---|---|
| Global external Application and proxy Network Load Balancers | Required | Not supported |
| Classic Application and proxy Network Load Balancers | Global IP address | Regional IP address |
| Cloud CDN | Always | Not supported |
| Internal load balancers | Always, with no internet egress charges | Not applicable |
| SLA | 99.99% uptime | 99.9% uptime |

Sources: [Network Service Tiers overview](https://docs.cloud.google.com/network-tiers/docs/overview), [Choose a load balancer](https://docs.cloud.google.com/load-balancing/docs/choosing-load-balancer).

Cloud Armor works with load balancers in either tier ([Security policy overview](https://docs.cloud.google.com/armor/docs/security-policy-overview)).

## Backends

Backend services hold instance groups or network endpoint groups (NEGs).

| Backend | Points to | Load balancers |
|---|---|---|
| Instance group | VMs in managed or unmanaged instance groups | Application, proxy Network, and passthrough Network |
| Zonal NEG, `GCE_VM_IP_PORT` | VM IP or alias IP, such as GKE Pod IPs | Application and proxy Network |
| Zonal NEG, `GCE_VM_IP` | Primary IP of a VM interface | Passthrough Network |
| Serverless NEG | Cloud Run, Cloud Run functions, App Engine, API Gateway (Preview) | Application only |
| Internet NEG | Endpoints outside Google Cloud: one in a global NEG, several in a regional NEG | Global: global external and classic Application. Regional: regional Application and proxy Network |
| Hybrid connectivity NEG | `IP:port` on-premises or in another cloud, over Cloud VPN, Cloud Interconnect, or Router appliance | Application and proxy Network |
| Private Service Connect NEG | A published service or a Google API | Application and proxy Network, except the classic modes |
| Backend bucket | Cloud Storage bucket | Application only |

Sources: [Network endpoint groups overview](https://docs.cloud.google.com/load-balancing/docs/negs), [Backend services overview](https://docs.cloud.google.com/load-balancing/docs/backend-service), [Internet NEGs overview](https://docs.cloud.google.com/load-balancing/docs/negs/internet-neg-concepts), [Backend buckets overview](https://docs.cloud.google.com/load-balancing/docs/backend-bucket), [External Application Load Balancer overview](https://docs.cloud.google.com/load-balancing/docs/https), [Internal passthrough Network Load Balancer overview](https://docs.cloud.google.com/load-balancing/docs/internal).

Rules to remember:

- All backends on one backend service are the same type. `GCE_VM_IP_PORT` zonal NEGs plus hybrid NEGs are the only mix, for hybrid designs ([External Application Load Balancer overview](https://docs.cloud.google.com/load-balancing/docs/https)).
- Serverless backends do not support health checks. The global external and cross-region internal Application Load Balancers offer optional outlier detection instead. The classic Application Load Balancer does not. With serverless NEGs in several regions, the load balancer sends traffic to the closest region ([Serverless NEGs overview](https://docs.cloud.google.com/load-balancing/docs/negs/serverless-neg-concepts)).
- A consumer load balancer with a PSC NEG enforces Cloud Armor policies, SSL policies, and URL maps in one place ([About Private Service Connect backends](https://docs.cloud.google.com/vpc/docs/private-service-connect-backends)). PSC design is in [network design](note:1.3-network-design).
- An external GKE Ingress always creates a classic Application Load Balancer. GKE Gateway can use any external Application Load Balancer mode ([External Application Load Balancer overview](https://docs.cloud.google.com/load-balancing/docs/https)). Cluster setup is in [GKE](note:2.3-gke).

## Certificates and TLS policy

A target HTTPS or SSL proxy gets certificates by one of three methods.

| Method | Scale per target proxy | Load balancers |
|---|---|---|
| Compute Engine SSL certificates | Up to 15 | All except cross-region internal; older, with notable limitations |
| Certificate Manager certificate map | Thousands of entries, can scale to millions | Global external and classic Application and proxy Network |
| Certificate Manager certificates, attached directly | Up to 100 | Regional Application; the only method for cross-region internal Application |

Sources: [SSL certificates overview](https://docs.cloud.google.com/load-balancing/docs/ssl-certificates).

Certificate Manager issues and renews Google-managed certificates automatically. It can provision them in advance for a zero-downtime migration, and it supports mutual TLS (mTLS) on the load balancer ([Certificate Manager overview](https://docs.cloud.google.com/certificate-manager/docs/overview)).

An SSL policy sets the minimum TLS version and features for connections between clients and the load balancer. It does not affect connections from the load balancer to the backends. The predefined profiles are `COMPATIBLE`, `MODERN`, `RESTRICTED`, and `FIPS_202205`, and `CUSTOM` lets you choose cipher suites. A minimum of TLS 1.3 needs `RESTRICTED` ([SSL policies overview](https://docs.cloud.google.com/load-balancing/docs/ssl-policies-concepts)).

HTTP to the backends can be acceptable. Google automatically encrypts traffic between GFEs and backends in VPC networks ([Set up a global external Application Load Balancer](https://docs.cloud.google.com/load-balancing/docs/https/setup-global-ext-https-compute)).

## Where Cloud CDN and Cloud Armor attach

Cloud CDN and most Cloud Armor policies attach to backend services or backend buckets, not to forwarding rules. Cloud Armor rules and features are in [network security](note:2.1-network-security).

| Feature | Attaches to | Load balancer modes |
|---|---|---|
| Cloud CDN | Backend service or backend bucket | Global external Application; classic Application in Premium Tier |
| Backend security policy | Backend service | Global external, classic, regional external, and regional internal Application; global external and classic proxy Network |
| Edge security policy | Backend service or backend bucket | Global external and classic Application |
| Network edge security policy | Regional backend service, target pool, target instance, or VM | Regional external passthrough Network, protocol forwarding, VMs with external IP addresses |

Sources: [Security policy overview](https://docs.cloud.google.com/armor/docs/security-policy-overview), [Cloud CDN overview](https://docs.cloud.google.com/cdn/docs/overview).

With both policy types on a CDN-enabled backend service, a request passes these checks in order ([Security policy overview](https://docs.cloud.google.com/armor/docs/security-policy-overview)):

1. The edge security policy, at the outer edge of Google's network.
2. The Cloud CDN cache, which answers cache hits.
3. The backend security policy, for cache misses that passed the edge policy.
4. The backend.

Edge security policies can only allow or deny. They filter only on `origin.asn`, `origin.ip`, `origin.region_code`, and request headers, method, path, query, and scheme ([Security policy overview](https://docs.cloud.google.com/armor/docs/security-policy-overview), [Custom rules language attributes](https://docs.cloud.google.com/armor/docs/rules-language-reference)). Put geography and IP blocks for cached content in the edge policy. Put WAF rules and rate limits in the backend policy.

More attachment facts:

- IAP and Cloud CDN cannot both be enabled on the same backend service ([External Application Load Balancer overview](https://docs.cloud.google.com/load-balancing/docs/https)). On a backend service with IAP, the edge security policy runs before IAP ([Security policy overview](https://docs.cloud.google.com/armor/docs/security-policy-overview)).
- Only edge security policies apply to backend buckets. A network edge security policy needs advanced network DDoS protection in its region ([Security policy overview](https://docs.cloud.google.com/armor/docs/security-policy-overview)).
- The default cache mode, `CACHE_ALL_STATIC`, caches static content. `FORCE_CACHE_ALL` overrides origin cache directives and can cache private, per-user content ([Caching overview](https://docs.cloud.google.com/cdn/docs/caching)).
- Media CDN complements Cloud CDN for streaming video and large file downloads ([Media CDN overview](https://docs.cloud.google.com/media-cdn/docs/overview)).

## Firewall and health checks

- For instance group and zonal NEG backends, the global external Application Load Balancer needs ingress rules from the GFE ranges `130.211.0.0/22` and `35.191.0.0/16`. Regional Envoy-based load balancers need a rule from the proxy-only subnet ([External Application Load Balancer overview](https://docs.cloud.google.com/load-balancing/docs/https)).
- Allow the full health check ranges. A partial range causes health check failures and HTTP `502` responses ([External Application Load Balancer overview](https://docs.cloud.google.com/load-balancing/docs/https)).

## Case study angles

| Case study | Requirement | Network design response |
|---|---|---|
| [EHR Healthcare](case:ehr) | "Provide a minimum 99.9% availability for all customer-facing systems" and "Reduce latency to all customers." | Global external Application Load Balancer with backends in two or more regions. TLS ends close to users, and traffic fails over between regions. |
| [Cymbal Retail](case:cymbal) | AI agents in the "website and mobile app"; customer data "handled securely". | Global external Application Load Balancer with Certificate Manager certificates, an SSL policy with a higher minimum TLS version, and Cloud Armor WAF rules. |
| [KnightMotives](case:knightmotives) | An ordering system "which is unreliable"; EU data protection "is critical". | If TLS must end in the EU, a regional external Application Load Balancer in an EU region. If not, a global one with backends in several regions. |
| [Altostrat Media](case:altostrat) | "Optimize cloud storage costs while maintaining high availability and scalability for media content." | Backend bucket with Cloud CDN, so cache hits reduce origin load. Media CDN for streaming video. |

## AWS mapping

| AWS | Google Cloud | Difference that matters |
|---|---|---|
| Application Load Balancer, one per region | Global external Application Load Balancer | One load balancer and one anycast IP serve backends in all regions. You do not join regional load balancers with DNS. |
| Network Load Balancer | Passthrough Network Load Balancer | Backends reply directly to clients (direct server return). |
| CloudFront | Cloud CDN or Media CDN | Cloud CDN is a setting on a backend service or backend bucket. |
| AWS WAF | Cloud Armor | Edge policies act before the cache; backend policies see only cache misses. |
| ELB pre-warming | Not needed | Autoscaling does not require pre-warming. |

Sources: [Compare AWS and Azure services to Google Cloud](https://docs.cloud.google.com/docs/get-started/aws-azure-gcp-service-comparison), [Cloud Load Balancing overview](https://docs.cloud.google.com/load-balancing/docs/load-balancing-overview), [Passthrough Network Load Balancer overview](https://docs.cloud.google.com/load-balancing/docs/passthrough-network-load-balancer), [Cloud CDN overview](https://docs.cloud.google.com/cdn/docs/overview).

## Exam traps

- **A proxy Network Load Balancer for HTTPS.** It can carry HTTPS, but Google says to use an external Application Load Balancer ([External proxy Network Load Balancer overview](https://docs.cloud.google.com/load-balancing/docs/tcp)).
- **A "global internal" load balancer.** Only external load balancers are global. The internal multi-region answer is cross-region internal ([Choose a load balancer](https://docs.cloud.google.com/load-balancing/docs/choosing-load-balancer)).
- **Standard Tier with a global load balancer or Cloud CDN.** Both need Premium Tier. With Standard Tier, use a regional external load balancer or a classic one in regional mode ([Network Service Tiers overview](https://docs.cloud.google.com/network-tiers/docs/overview)).
- **VPC firewall rules to block clients.** Firewall rules apply at the VMs, not at the GFEs. Use Cloud Armor ([External Application Load Balancer overview](https://docs.cloud.google.com/load-balancing/docs/https)).
- **A geography block in a backend security policy with Cloud CDN.** Cache hits never reach it. Use an edge security policy ([Security policy overview](https://docs.cloud.google.com/armor/docs/security-policy-overview)).
- **IAP and Cloud CDN on one backend service.** They are incompatible ([External Application Load Balancer overview](https://docs.cloud.google.com/load-balancing/docs/https)).
- **Google-managed certificates on a passthrough load balancer.** They are available only for proxy load balancers ([Passthrough Network Load Balancer overview](https://docs.cloud.google.com/load-balancing/docs/passthrough-network-load-balancer)).
- **No SSL policy means modern TLS.** The default accepts TLS 1.0 ([SSL policies overview](https://docs.cloud.google.com/load-balancing/docs/ssl-policies-concepts)).
- **Health checks on serverless NEGs.** They are not supported. Use outlier detection on a global external or cross-region internal Application Load Balancer. The classic Application Load Balancer does not support it ([Serverless NEGs overview](https://docs.cloud.google.com/load-balancing/docs/negs/serverless-neg-concepts)).
