## Why it matters

Objective 4.1 asks how teams test and validate software and infrastructure, and how they find the root cause of a failure. In a typical scenario, a release breaks production or a canary needs a pass or fail decision. Other scenarios need a guardrail for a Terraform change, or the right tool for an incident. The correct answer limits user impact first and catches the fault at the lowest cost. It uses the Google Cloud tool that is built for the question.

## Key points

- Tests are traditional (unit, integration, system) or production tests (configuration, stress). Production tests run against the live service. A canary is structured user acceptance, not a real test ([Testing for Reliability](https://sre.google/sre-book/testing-reliability/)).
- A test that blocks a push finds a bug with zero mean time to repair (MTTR). Such bugs never reach users ([Testing for Reliability](https://sre.google/sre-book/testing-reliability/)).
- Test Terraform with the least expensive method first: static analysis, then module integration tests, then end-to-end tests ([Best practices for testing](https://docs.cloud.google.com/docs/terraform/best-practices/testing)).
- `gcloud beta terraform vet` (Preview) checks a Terraform plan against policy constraints in an infrastructure CI/CD pipeline ([Policy validation](https://docs.cloud.google.com/docs/terraform/policy-validation)).
- A canary is a partial, time-limited deployment of a change and its evaluation. Compare the canary with the control, and start from your SLIs when you choose metrics ([Canarying Releases](https://sre.google/workbook/canarying-releases/)).
- Cloud Deploy verification runs your test containers after a deployment. Cloud Deploy analysis evaluates Cloud Monitoring alerting policies over time and can roll back automatically ([Verify your deployment](https://docs.cloud.google.com/deploy/docs/verify-deployment), [Run analysis jobs in Cloud Deploy](https://docs.cloud.google.com/deploy/docs/analysis)).
- In a major outage, stop the bleeding first. Find the root cause later, but keep evidence such as logs ([Effective Troubleshooting](https://sre.google/sre-book/effective-troubleshooting/)).
- Recent changes are a productive place to start a diagnosis ([Effective Troubleshooting](https://sre.google/sre-book/effective-troubleshooting/)).
- Postmortems are blameless. Define the postmortem criteria before an incident occurs ([Conduct thorough postmortems](https://docs.cloud.google.com/architecture/framework/reliability/conduct-postmortems)).
- Personalized Service Health is the primary channel for Google Cloud incidents that are relevant to your projects ([Personalized Service Health overview](https://docs.cloud.google.com/service-health/docs/overview)).
- Gemini Cloud Assist investigations (Preview) are a root-cause analysis tool. Since April 10, 2026, they need a Premium Support contract or access through the account team ([Troubleshoot issues with Gemini Cloud Assist investigations](https://docs.cloud.google.com/cloud-assist/investigations)).

## Test layers and what they prove

| Test | What it proves | Cost or scope |
|---|---|---|
| Unit | One function or class behaves as specified, in isolation | Very cheap; milliseconds on a laptop |
| Integration | Assembled components work together | Mocks replace complex dependencies, such as a stateful database |
| System | The undeployed system works end to end. Smoke, performance, and regression tests are system tests. | Minutes to hours; can need dedicated resources |
| Configuration (production) | The live binary uses the configuration that is in version control | Runs against production, outside the test sandbox |
| Stress (production) | The limits of the system, for example how many queries per second overload a server | Finds where a component fails instead of degrading |
| Canary (user acceptance) | A subset of servers runs the change with live traffic, then the rollout continues or reverts | Live users see the change, so revert quickly |

Sources: [Testing for Reliability](https://sre.google/sre-book/testing-reliability/).

A performance test keeps a system from slowly getting slower or more expensive between releases. A regression test turns each past bug into a test, so that the bug cannot come back. A canary exposes the change to less predictable live traffic, so it does not always catch new faults ([Testing for Reliability](https://sre.google/sre-book/testing-reliability/)).

Security tests belong in the same pipeline:

- Artifact Analysis scans container images when you push them to Artifact Registry. On-demand scanning runs from the gcloud CLI, so a CI step can check an image before it deploys ([Container scanning overview](https://docs.cloud.google.com/artifact-analysis/docs/container-scanning-overview)).
- Web Security Scanner crawls public App Engine, GKE, and Compute Engine web applications. It can affect application reliability and might not suit production, so scan a test deployment ([Overview of Web Security Scanner](https://docs.cloud.google.com/security-command-center/docs/concepts-web-security-scanner-overview)).

Load, chaos, and penetration testing in production are in [Reliability in production](note:6.6-production-reliability). ## Validate infrastructure changes

| Stage | Tool | What it catches | Cost |
|---|---|---|---|
| Static analysis | `terraform validate`, linters | Syntax and structure errors | No resources |
| Plan review | `terraform plan` saved to a file; an owner approves it before apply | Unexpected adds, changes, and deletes | No resources |
| Policy check | `gcloud beta terraform vet` (Preview) on the plan JSON | Violations of your constraint library | No resources |
| Module integration test | Blueprint testing framework, Terratest, Kitchen-Terraform | A module creates the expected resources | Real resources in a test environment |
| End-to-end test | All modules in a fresh test environment | Modules work together | Highest cost, highest confidence |

Sources: [Best practices for testing](https://docs.cloud.google.com/docs/terraform/best-practices/testing), [Best practices for Terraform operations](https://docs.cloud.google.com/docs/terraform/best-practices/operations), [Policy validation](https://docs.cloud.google.com/docs/terraform/policy-validation), [Validate policies](https://docs.cloud.google.com/docs/terraform/policy-validation/validate-policies).

Rules for infrastructure tests ([Best practices for testing](https://docs.cloud.google.com/docs/terraform/best-practices/testing)):

- Isolate tests from development and production. The best approach is a fresh project or folder for each test, with service accounts for each test run.
- Randomize project IDs and resource names to avoid conflicts.
- Clean up with `terraform destroy`, then delete the test projects. Do not use cleanup tools in production.
- Run small tests first and fail fast. Run tests in parallel and in stages to save time.

Terraform pipelines and Infrastructure Manager are in [Infrastructure as Code](note:5.2-infrastructure-as-code). After a network change, Connectivity Tests checks whether one endpoint can reach another. It simulates the forwarding path and, for some paths, sends live packets ([Connectivity Tests overview](https://docs.cloud.google.com/network-intelligence-center/docs/connectivity-tests/concepts/overview)).

## Canary analysis

The SRE workbook gives these rules for canary evaluation ([Canarying Releases](https://sre.google/workbook/canarying-releases/)):

- **Compare canary with control at the same time.** A before/after comparison is risky, because time is one of the biggest sources of change in metrics.
- **Start from SLIs.** HTTP error codes and response latency map to user impact. CPU usage can give a noisy canary that operators then ignore.
- **Keep the metric list short.** Rank metrics by how well they show user-visible problems, and use the top few, perhaps no more than a dozen.
- **Exclude 4xx codes.** A broken shared link can create 404s that have nothing to do with the release. Add black-box probes for specific URLs instead.
- **Use a gradual canary.** The first small stage uses the clearest signals, such as crashes and failed requests. Later stages are larger.
- **Pick the time with care.** Performance defects often show only under heavy load, so an off-peak canary can miss them.

Cloud Deploy automates both kinds of check:

| Check | Input | Pass or fail | Use it for |
|---|---|---|---|
| Verification | Your own test containers, run after the deployment | Exit code 0 passes; a failure fails the rollout | Tests, such as integration tests, that check that the new version works correctly |
| Analysis | Cloud Monitoring alerting policies, or a custom container for another metrics system | The alerting policy result over time | Canary evaluation; automatic rollback |

Sources: [Verify your deployment](https://docs.cloud.google.com/deploy/docs/verify-deployment), [Run analysis jobs in Cloud Deploy](https://docs.cloud.google.com/deploy/docs/analysis).

Release strategies and Cloud Deploy canaries are in [Deployment and release management](note:6.3-release-management).

## Root cause analysis

Google SRE troubleshooting is a loop of hypotheses and tests ([Effective Troubleshooting](https://sre.google/sre-book/effective-troubleshooting/)):

1. **Triage.** Assess the severity. In a major outage, make the system work as well as it can. For example, divert traffic from a broken cluster, drop traffic to prevent a cascading failure, or disable subsystems. Keep logs for the later analysis.
2. **Examine.** Use metrics, logs, and traces to see what each component does.
3. **Diagnose.** Inject known test data and check each component's output. Divide and conquer, or bisect a large system. Ask what the system does, where its resources go, and why. Check what touched it last: deployments and configuration changes.
4. **Test and treat.** Compare the observed state with each hypothesis, or change the system in a controlled way and watch the result.
5. **Cure.** Prove the cause if you can. Often you find several probable factors that together cause the failure. Then write a postmortem.

Common pitfalls are irrelevant symptoms, improbable theories, and past causes applied to a new problem. When you hear hoofbeats, think of horses, not zebras. Correlation is not causation ([Effective Troubleshooting](https://sre.google/sre-book/effective-troubleshooting/)).

### Postmortems

A postmortem is a written record of an incident: its impact, the mitigation, the root causes, and the follow-up actions ([Postmortem Culture: Learning from Failure](https://sre.google/sre-book/postmortem-culture/)). Write one after any of these events ([Conduct thorough postmortems](https://docs.cloud.google.com/architecture/framework/reliability/conduct-postmortems)):

- User-visible downtime or degradation beyond a threshold
- Data loss of any kind
- An on-call intervention, such as a release rollback or a traffic reroute
- A resolution time above a threshold
- A monitoring failure, which usually means that a person found the incident

Rules:

- Keep it blameless. Focus on processes, tools, and technology, not on individuals ([Conduct thorough postmortems](https://docs.cloud.google.com/architecture/framework/reliability/conduct-postmortems)).
- Identify both the immediate cause and the systemic issues ([Manage incidents and problems](https://docs.cloud.google.com/architecture/framework/operational-excellence/manage-incidents-and-problems)).
- Do not add complex fixes for problems that are unlikely to recur ([Conduct thorough postmortems](https://docs.cloud.google.com/architecture/framework/reliability/conduct-postmortems)).
- Review every postmortem and share it widely. An unreviewed postmortem might as well never have existed ([Postmortem Culture: Learning from Failure](https://sre.google/sre-book/postmortem-culture/)).

Incident roles are in [Supporting deployed solutions](note:6.4-support). Tracking of action items is in [Quality control measures](note:6.5-quality-control).

## Troubleshooting toolkit

| Question | Tool | Note |
|---|---|---|
| Does a Google Cloud incident affect my projects? | Personalized Service Health | Dashboard, API, and log-based alerts; organization view |
| Who changed which resource, and when? | Cloud Audit Logs, Admin Activity | Always written; you cannot disable them |
| Which errors are new, or which resolved errors came back? | Error Reporting | Groups errors by root cause and notifies on new errors and regressions. Cannot read CMEK-enabled log buckets. |
| Which service in the call chain is slow? | Cloud Trace | Latency across services |
| Which code uses the CPU or memory? | Cloud Profiler | Continuous, low-overhead profiling in production |
| Error rate per revision per minute, across many logs | Observability Analytics (formerly Log Analytics) | SQL on upgraded log buckets; joins with trace data. Logs Explorer cannot aggregate. |
| Can endpoint A reach endpoint B? Which rule drops the packet? | Connectivity Tests | Configuration analysis, plus live data plane analysis for some paths |
| Is it the network or my application? | Performance Dashboard | Performance of the Google Cloud network and of your project's resources |
| Which network misconfiguration causes this failure? | Network Analyzer | Correlates failures with recent configuration changes |
| Ranked hypotheses from logs, metrics, and configuration | Gemini Cloud Assist investigations (Preview) | One project or one App Hub application |

## Exam traps

- **Root cause first, mitigation later.** Stop the bleeding first, for example with a rollback or a traffic drain. Keep the logs ([Effective Troubleshooting](https://sre.google/sre-book/effective-troubleshooting/), [Incident Response](https://sre.google/workbook/incident-response/)).
- **A postmortem that names who is at fault.** Postmortems focus on systems and processes ([Conduct thorough postmortems](https://docs.cloud.google.com/architecture/framework/reliability/conduct-postmortems)).
- **`terraform validate` as a policy check.** It checks syntax and structure only. Use policy validation on the plan ([Best practices for testing](https://docs.cloud.google.com/docs/terraform/best-practices/testing), [Policy validation](https://docs.cloud.google.com/docs/terraform/policy-validation)).
- **Infrastructure tests in a shared or production project.** Give each test a fresh project or folder ([Best practices for testing](https://docs.cloud.google.com/docs/terraform/best-practices/testing)).
- **A before/after canary comparison.** Compare with a control population at the same time ([Canarying Releases](https://sre.google/workbook/canarying-releases/)).
- **Host CPU as the main canary metric.** Use SLI-based metrics such as error rate and latency ([Canarying Releases](https://sre.google/workbook/canarying-releases/)).
- **Web Security Scanner against production.** It can affect reliability. Scan a test deployment ([Overview of Web Security Scanner](https://docs.cloud.google.com/security-command-center/docs/concepts-web-security-scanner-overview)).
- **Data Access logs to find who changed a firewall rule.** Configuration changes are in Admin Activity logs ([Cloud Audit Logs overview](https://docs.cloud.google.com/logging/docs/audit)).
- **Logs Explorer to count errors by version.** It cannot aggregate. Use Observability Analytics ([Analyze logs using Logs Explorer and Observability Analytics](https://docs.cloud.google.com/logging/docs/log-analytics)).
- **Investigations for any team.** They are Preview and need Premium Support or account-team access ([Troubleshoot issues with Gemini Cloud Assist investigations](https://docs.cloud.google.com/cloud-assist/investigations)).
