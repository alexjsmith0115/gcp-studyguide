## Why it matters

People and workloads must reach Google Cloud resources from outside. The old answer was a VPN, a bastion host with a public IP address, and a service account key in the CI system. Google Cloud grants access by identity and context instead of by network location. The exam asks you to pick the right tool: Identity-Aware Proxy (IAP), service account impersonation, Workload Identity Federation, or Chrome Enterprise Premium (formerly BeyondCorp Enterprise). The wrong answers usually add an external IP address, open a firewall to the internet, or create a key.

## Key points

- IAP is a central authorization layer for applications that you reach over HTTPS. It checks IAM after it authenticates the user, so users do not need a VPN ([Identity-Aware Proxy overview](https://docs.cloud.google.com/iap/docs/concepts-overview)).
- IAP can sign in Google Accounts, users of an external identity provider (IdP) through Workforce Identity Federation, and customers through Identity Platform ([Identity-Aware Proxy overview](https://docs.cloud.google.com/iap/docs/concepts-overview)).
- IAP TCP forwarding gives SSH, RDP, and other TCP access to VMs that have no external IP address. The firewall must allow ingress from `35.235.240.0/20` ([Use IAP for TCP forwarding](https://docs.cloud.google.com/iap/docs/using-tcp-forwarding)).
- OS Login controls SSH access with IAM roles instead of SSH keys in metadata. When you remove a role, access to the VM stops ([About OS Login](https://docs.cloud.google.com/compute/docs/oslogin)).
- A user who connects to a VM can use all the IAM permissions of the service account that is attached to the VM ([About OS Login](https://docs.cloud.google.com/compute/docs/oslogin)).
- Service account impersonation always involves two identities: the caller and the service account. Most audit logs record both ([Service account impersonation](https://docs.cloud.google.com/iam/docs/service-account-impersonation)).
- To impersonate a service account, you need the Service Account Token Creator role on it. The Service Account User role only lets you attach the service account to a resource ([Roles for service account authentication](https://docs.cloud.google.com/iam/docs/service-account-permissions)).
- Workload Identity Federation lets a workload outside Google Cloud exchange its own credential for a short-lived Google token. It removes the need for service account keys ([Workload Identity Federation](https://docs.cloud.google.com/iam/docs/workload-identity-federation)).
- For federated workloads, Google recommends direct resource access. Use service account impersonation where an API has a limitation ([Workload Identity Federation](https://docs.cloud.google.com/iam/docs/workload-identity-federation)).
- GitHub, GitLab SaaS, and HCP Terraform use one issuer URL for all their customers. You must add an attribute condition that accepts only your organization's tokens ([Configure Workload Identity Federation with deployment pipelines](https://docs.cloud.google.com/iam/docs/workload-identity-federation-with-deployment-pipelines)).
- Workforce Identity Federation lets users of an external IdP use single sign-on (SSO) to Google Cloud, without syncing their accounts to Cloud Identity ([Workforce Identity Federation](https://docs.cloud.google.com/iam/docs/workforce-identity-federation)).
- Chrome Enterprise Premium adds context-aware access based on user, device, and location, plus data loss prevention and threat protection in Chrome ([Chrome Enterprise Premium overview](https://docs.cloud.google.com/chrome-enterprise-premium/docs/overview)).

## Choose the access pattern

| Need | Use | Avoid |
|---|---|---|
| Employees use an internal web app without a VPN | IAP on the load balancer, or directly on Cloud Run | A public app with only its own login page |
| Administrators use SSH or RDP on VMs with no external IP address | IAP TCP forwarding and OS Login | A bastion host with a public IP address, or SSH open to `0.0.0.0/0` |
| A person needs a service account's permissions for a short task | Service account impersonation | A downloaded service account key |
| A pipeline or app runs on AWS, Azure, GitHub, GitLab, or on-premises | Workload Identity Federation | A service account key stored as a CI secret |
| Employees sign in with Microsoft Entra ID or Okta, and the requirement says no account sync | Workforce Identity Federation | A sync to Cloud Identity with Google Cloud Directory Sync |
| Customers sign in to your app with email or a social login | Identity Platform, alone or with IAP | Cloud Identity accounts for customers |
| Access only from managed devices or from the corporate network | Access levels in IAP. Device attributes need Chrome Enterprise Premium. | A network allowlist as the only control |

Sources: [Identity-Aware Proxy overview](https://docs.cloud.google.com/iap/docs/concepts-overview), [Use IAP for TCP forwarding](https://docs.cloud.google.com/iap/docs/using-tcp-forwarding), [Service account impersonation](https://docs.cloud.google.com/iam/docs/service-account-impersonation), [Workload Identity Federation](https://docs.cloud.google.com/iam/docs/workload-identity-federation), [Workforce Identity Federation](https://docs.cloud.google.com/iam/docs/workforce-identity-federation), [Identity-Aware Proxy pricing](https://cloud.google.com/iap/pricing).

For workloads on GKE, use Workload Identity Federation for GKE, which [Configuring GKE](note:2.3-gke) covers.

## IAP for web applications

IAP handles each request in three steps ([Identity-Aware Proxy overview](https://docs.cloud.google.com/iap/docs/concepts-overview)):

1. The request reaches Cloud Run, App Engine, or an external or internal Application Load Balancer. The serving infrastructure checks if IAP is on for that app.
2. IAP authenticates the user. It sends a user who is not signed in to Google sign-in, to the external IdP, or to Identity Platform.
3. IAP checks IAM. The user needs the IAP-secured Web App User role (`roles/iap.httpsResourceAccessor`) on the app ([IAP roles](https://docs.cloud.google.com/iam/docs/roles-permissions/iap)).

Design rules:

- **Close the side doors.** IAP on a load balancer does not stop direct traffic to a VM backend. Use firewall rules. For Cloud Run, disable the `run.app` URL or use ingress controls ([Identity-Aware Proxy overview](https://docs.cloud.google.com/iap/docs/concepts-overview)).
- **On Cloud Run, choose one place.** IAP directly on the service protects all ingress paths. IAP on a load balancer suits many services behind one global load balancer. Do not enable it on both ([Identity-Aware Proxy overview](https://docs.cloud.google.com/iap/docs/concepts-overview)).
- **Verify the signed header.** The app checks the JWT in the `x-goog-iap-jwt-assertion` header. This protects the app if someone turns off IAP, misconfigures a firewall, or connects from inside the project ([Securing your app with signed headers](https://docs.cloud.google.com/iap/docs/signed-headers-howto)).
- **Add context.** A conditional role binding can check access levels, the URL host and path, and the date and time. IAP does not support scoped access policies. Its access levels must be in the organization-level access policy ([Setting up context-aware access with IAP](https://docs.cloud.google.com/iap/docs/cloud-iap-context-aware-access-howto)).
- **Know the cost.** IAP has no charge for Google Cloud resources, but you pay for the load balancer. Proxying non-Google Cloud resources, device attributes, and custom access levels are paid Chrome Enterprise Premium features ([Identity-Aware Proxy pricing](https://cloud.google.com/iap/pricing)).

## Administrative access to VMs

IAP TCP forwarding builds an encrypted tunnel to the VM. IAP connects to the primary internal IPv4 address of `nic0`, so the VM needs no external IP address ([Use IAP for TCP forwarding](https://docs.cloud.google.com/iap/docs/using-tcp-forwarding)).

| Layer | What to configure |
|---|---|
| Network | An ingress firewall rule from `35.235.240.0/20` (IPv6: `2600:2d00:1:7::/64`) to the ports that you need, such as 22 or 3389. Remove `default-allow-ssh` and `default-allow-rdp`, which allow all source addresses. |
| IAP | IAP-secured Tunnel User (`roles/iap.tunnelResourceAccessor`) on the project or on one VM. A condition can limit the port (`destination.port == 22`) or the destination IP address, or require an access level. You cannot grant it through tags. |
| VM login | OS Login: `enable-oslogin=TRUE` in project or instance metadata. Grant `roles/compute.osLogin` (no `sudo`) or `roles/compute.osAdminLogin` (with `sudo`). |
| VM identity | Service Account User on the VM's service account, if the VM has one. |
| Users from another organization | `roles/compute.osLoginExternalUser`, granted on the organization. |

Sources: [Use IAP for TCP forwarding](https://docs.cloud.google.com/iap/docs/using-tcp-forwarding), [Set up OS Login](https://docs.cloud.google.com/compute/docs/oslogin/set-up-oslogin).

More OS Login facts:

- When you set OS Login metadata, Compute Engine deletes the VM's `authorized_keys` files. The VM no longer accepts SSH keys from metadata ([Set up OS Login](https://docs.cloud.google.com/compute/docs/oslogin/set-up-oslogin)).
- For 2-step verification, set `enable-oslogin-2fa` to `TRUE` together with `enable-oslogin` ([Set up OS Login](https://docs.cloud.google.com/compute/docs/oslogin/set-up-oslogin)).
- To require OS Login in every project, use the Require OS Login constraint: `compute.managed.requireOsLogin`, or the legacy `compute.requireOsLogin` ([Organization policy constraints](https://docs.cloud.google.com/organization-policy/reference/org-policy-constraints)). See [Organization policy, VPC Service Controls, and audit logging](note:3.1-security-controls).
- Give the VM a minimal service account, or none. Every user who logs in can use its permissions ([About OS Login](https://docs.cloud.google.com/compute/docs/oslogin)).

The firewall design is in [Network security controls](note:2.1-network-security).

## Service account impersonation

The caller gets a short-lived token for the service account and uses it to authenticate. You can impersonate with the gcloud flag `--impersonate-service-account`, with Application Default Credentials, or with the Service Account Credentials API. The Google Cloud console always uses your user credentials ([Service account impersonation](https://docs.cloud.google.com/iam/docs/service-account-impersonation)). An access token lasts 1 hour by default. The `iam.allowServiceAccountCredentialLifetimeExtension` constraint can extend it to 12 hours for listed service accounts ([Restrict IAM service account usage](https://docs.cloud.google.com/organization-policy/restrict-service-accounts)).

| Role | What it allows |
|---|---|
| Service Account User (`roles/iam.serviceAccountUser`) | Attach the service account to a resource (`iam.serviceAccounts.actAs`). It does not allow impersonation. |
| Service Account Token Creator (`roles/iam.serviceAccountTokenCreator`) | Create access tokens, ID tokens, and signed JWTs and blobs. Use `--impersonate-service-account`. |
| Service Account OpenID Connect Identity Token Creator (`roles/iam.serviceAccountOpenIdTokenCreator`) | Create ID tokens only |
| Workload Identity User (`roles/iam.workloadIdentityUser`) | Let federated identities and GKE workloads impersonate the service account |

Sources: [Roles for service account authentication](https://docs.cloud.google.com/iam/docs/service-account-permissions), [Workload Identity Federation](https://docs.cloud.google.com/iam/docs/workload-identity-federation).

Design rules:

- **Grant Token Creator on one service account**, not on the project. See [IAM, resource hierarchy, and separation of duties](note:3.1-iam-and-hierarchy).
- **Watch `signBlob` and `signJwt`.** They also let a principal get access tokens and ID tokens for the service account ([Roles for service account authentication](https://docs.cloud.google.com/iam/docs/service-account-permissions)).
- **Prefer impersonation for accountability.** With a key, or with code that runs on a VM, the audit logs record only the service account. That creates privilege-escalation and non-repudiation risks ([Service account impersonation](https://docs.cloud.google.com/iam/docs/service-account-impersonation)).
- **Use it for** temporary elevated access, for testing a set of permissions, and for local development that needs a service account ([Service account impersonation](https://docs.cloud.google.com/iam/docs/service-account-impersonation)). For approvals and justifications, use Privileged Access Manager, which the IAM page covers.

## Workload Identity Federation

The flow ([Workload Identity Federation](https://docs.cloud.google.com/iam/docs/workload-identity-federation)):

1. The workload gets a credential from its environment. Examples are an AWS or Azure credential, a GitHub OIDC token, an X.509 certificate, or a SAML assertion.
2. It sends the credential to the Security Token Service. The service verifies the credential against a provider in a workload identity pool and returns a federated access token.
3. The workload uses the token on resources where its principal has roles. Or it impersonates a service account that grants Workload Identity User to that principal.

| Principal | Identifier |
|---|---|
| One identity | `principal://iam.googleapis.com/projects/PROJECT_NUMBER/locations/global/workloadIdentityPools/POOL_ID/subject/SUBJECT` |
| All identities in a group | `principalSet://iam.googleapis.com/projects/PROJECT_NUMBER/locations/global/workloadIdentityPools/POOL_ID/group/GROUP_ID` |
| All identities with an attribute value | `principalSet://iam.googleapis.com/projects/PROJECT_NUMBER/locations/global/workloadIdentityPools/POOL_ID/attribute.NAME/VALUE` |

Sources: [Workload Identity Federation](https://docs.cloud.google.com/iam/docs/workload-identity-federation).

An attribute mapping turns claims into `google.subject` (required, at most 127 characters), `google.groups`, and up to 50 custom `attribute.NAME` values. An attribute condition is a CEL expression. The provider rejects every credential for which it is false ([Workload Identity Federation](https://docs.cloud.google.com/iam/docs/workload-identity-federation)).

Design rules:

- **Separate environments.** Create one pool for each environment, such as development, staging, and production ([Workload Identity Federation](https://docs.cloud.google.com/iam/docs/workload-identity-federation)).
- **Centralize.** Manage pools and providers in a dedicated project. The `constraints/iam.workloadIdentityPoolProviders` constraint can deny new providers in other projects ([Best practices for using Workload Identity Federation](https://docs.cloud.google.com/iam/docs/best-practices-for-using-workload-identity-federation)).
- **Use immutable IDs.** Map numeric claims such as `repository_owner_id`. Someone can claim a deleted repository or organization name again ([Configure Workload Identity Federation with deployment pipelines](https://docs.cloud.google.com/iam/docs/workload-identity-federation-with-deployment-pipelines)).
- **Keep the default audience.** It is the provider URL, which reduces the risk of confused deputy attacks ([Best practices for using Workload Identity Federation](https://docs.cloud.google.com/iam/docs/best-practices-for-using-workload-identity-federation)).
- **Grant narrowly.** Do not grant a role to all members of a pool. Use attributes and conditions ([Workload Identity Federation](https://docs.cloud.google.com/iam/docs/workload-identity-federation)).
- **Check product limits.** Cloud Storage accepts federated identities only for buckets with uniform bucket-level access, and federated identities cannot create signed URLs ([Identity federation: products and limitations](https://docs.cloud.google.com/iam/docs/federated-identity-supported-services)).
- **No public OIDC endpoint?** Upload the JSON Web Key Set (JWKS) to the provider, up to 8 keys ([Configure Workload Identity Federation with other identity providers](https://docs.cloud.google.com/iam/docs/workload-identity-federation-with-other-providers)).

Pipelines that use federation are in [SDLC, CI/CD, and service provisioning](note:4.1-sdlc-cicd) and [Infrastructure as Code](note:5.2-infrastructure-as-code).

## Workforce Identity Federation

Workforce Identity Federation federates users, such as employees, partners, and contractors, from an OIDC or SAML 2.0 IdP. It stores no user accounts in Google Cloud, so you do not need Google Cloud Directory Sync. Pools belong to the organization, and a pool ID must be unique across Google Cloud. Users work in the console (federated), the gcloud CLI, and the APIs ([Workforce Identity Federation](https://docs.cloud.google.com/iam/docs/workforce-identity-federation)). Some products have limitations for federated users, so check the list before you choose it ([Identity federation: products and limitations](https://docs.cloud.google.com/iam/docs/federated-identity-supported-services)). The alternative is Cloud Identity with synced accounts and SAML SSO, which the IAM page covers.

## Chrome Enterprise Premium and context-aware access

Chrome Enterprise Premium (formerly BeyondCorp Enterprise) applies the zero trust model: access depends on the context of the request, not on the network. Access Context Manager defines access levels. VPC Service Controls, IAP, Context-Aware Access for Google Workspace, and IAM Conditions enforce them ([Access Context Manager overview](https://docs.cloud.google.com/access-context-manager/docs/overview), [Compare AWS and Azure services to Google Cloud](https://docs.cloud.google.com/docs/get-started/aws-azure-gcp-service-comparison)).

| Capability | Chrome Enterprise Core | Chrome Enterprise Premium |
|---|---|---|
| Access control to Google Cloud web apps, VMs (SSH, RDP, TCP), APIs, and the console | Yes | Yes |
| Access levels by user, IP address, and geographic location | Yes | Yes |
| Access control to web apps on-premises, on AWS, and on Azure | No | Yes |
| Access levels by device security posture, time and date, or advanced expressions | No | Yes |
| Data loss prevention, malware, and phishing protection in Chrome | No | Yes |

Sources: [Chrome Enterprise Premium overview](https://docs.cloud.google.com/chrome-enterprise-premium/docs/overview). Chrome Enterprise Core is included with Google Cloud at no additional cost.

## AWS mapping

| AWS | Google Cloud | Difference that matters |
|---|---|---|
| Application Load Balancer with Cognito, AWS Verified Access | IAP | IAP checks an IAM role on the app, and works directly on Cloud Run. |
| AWS Session Manager | IAP TCP forwarding | The VM needs a firewall rule for the IAP range and no external IP address. |
| Amazon EC2 Instance Connect | OS Login | IAM roles decide who can log in and who gets `sudo`. |
| AWS STS `AssumeRole` | Service account impersonation | The caller needs Token Creator on the service account. |
| AWS IAM Roles Anywhere | Workload Identity Federation | You can grant roles directly to federated principals. |
| Amazon Cognito | Identity Platform | IAP can use it to sign in customers. |

Sources: [Compare AWS and Azure services to Google Cloud](https://docs.cloud.google.com/docs/get-started/aws-azure-gcp-service-comparison), [Service account impersonation](https://docs.cloud.google.com/iam/docs/service-account-impersonation), [Identity-Aware Proxy overview](https://docs.cloud.google.com/iap/docs/concepts-overview), [Use IAP for TCP forwarding](https://docs.cloud.google.com/iap/docs/using-tcp-forwarding), [About OS Login](https://docs.cloud.google.com/compute/docs/oslogin), [Workload Identity Federation](https://docs.cloud.google.com/iam/docs/workload-identity-federation).

## Exam traps

- **"Store a service account key as a GitHub secret."** Use Workload Identity Federation with an attribute condition for your organization ([Configure Workload Identity Federation with deployment pipelines](https://docs.cloud.google.com/iam/docs/workload-identity-federation-with-deployment-pipelines)).
- **"Grant Service Account User so that the developer can use `--impersonate-service-account`."** That role only attaches service accounts. Impersonation needs Service Account Token Creator ([Roles for service account authentication](https://docs.cloud.google.com/iam/docs/service-account-permissions)).
- **"Allow port 22 from `0.0.0.0/0` so that IAP can connect."** Allow only `35.235.240.0/20` ([Use IAP for TCP forwarding](https://docs.cloud.google.com/iap/docs/using-tcp-forwarding)).
- **"IAP is on at the load balancer, so the VM backends are safe."** Direct access to a backend bypasses IAP. Add firewall rules and verify signed headers ([Identity-Aware Proxy overview](https://docs.cloud.google.com/iap/docs/concepts-overview)).
- **"Use a scoped access policy for the IAP access level."** IAP supports only the organization-level access policy ([Setting up context-aware access with IAP](https://docs.cloud.google.com/iap/docs/cloud-iap-context-aware-access-howto)).
- **"Turn on IAP on the load balancer and on the Cloud Run service."** Choose one of them ([Identity-Aware Proxy overview](https://docs.cloud.google.com/iap/docs/concepts-overview)).
- **"Grant the role to all identities in the pool."** Limit access with attributes and conditions ([Workload Identity Federation](https://docs.cloud.google.com/iam/docs/workload-identity-federation)).
- **"Impersonate the service account in the Google Cloud console."** The console always uses your user credentials ([Service account impersonation](https://docs.cloud.google.com/iam/docs/service-account-impersonation)).
