## Why it matters

A design is not finished when it goes to production. Business needs change, Google Cloud adds and retires services, and a first migration seldom reaches the target architecture. Objective 1.5 tests whether you can choose the next improvement that gives the most value at an acceptable risk. The Google-recommended answer is usually incremental: modernize in steps, prefer managed services, measure before you optimize, and plan for change from the start.

## Key points

- Cloud-first means that new workloads go to the public cloud and existing workloads stay where they are. Google suggests it only for selected workloads, because a strict cloud-first approach can increase complexity ([Hybrid adoption approaches](https://docs.cloud.google.com/architecture/hybrid-multicloud-patterns/adopt)).
- Cloud native is an approach to build and run scalable applications that take full advantage of cloud services. It is about how you build and deliver an application, not only where it runs ([What is cloud native?](https://cloud.google.com/learn/what-is-cloud-native)).
- Do not treat cloud native as a multi-year, "big-bang" project. Treat it as constant iteration ([What is cloud native?](https://cloud.google.com/learn/what-is-cloud-native)).
- Google defines six migration types: rehost, replatform, refactor, re-architect, rebuild, and repurchase ([Migrate to Google Cloud](https://docs.cloud.google.com/architecture/migration-to-gcp-getting-started)). A phased approach rehosts or replatforms first, and then refactors or re-architects ([Hybrid adoption approaches](https://docs.cloud.google.com/architecture/hybrid-multicloud-patterns/adopt)).
- "Design for change" is a core principle of the Well-Architected Framework: deliver small changes often, with fast feedback ([Well-Architected Framework](https://docs.cloud.google.com/architecture/framework)).
- Optimization is a continuous loop. Set measurable goals, such as SLOs, and stop when you meet them, because optimization has a cost ([Optimize your environment](https://docs.cloud.google.com/architecture/migration-to-google-cloud-optimizing-your-environment)).
- Preview offerings have no SLA or technical support commitments and are for test environments, unless Google states otherwise ([Product launch stages](https://cloud.google.com/products#product-launch-stages)).
- Google gives at least 12 months' notice before it discontinues a service or significantly changes a customer-facing API in a backwards-incompatible way, with some exceptions. Pre-GA offerings do not get this notice ([Terms of Service](https://cloud.google.com/terms)).
- Gemini models on Gemini Enterprise Agent Platform (Agent Platform, formerly Vertex AI) have retirement dates. Plan each model upgrade with evaluations and regression tests ([Model versions and lifecycle](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/model-versions), [Gemini model migration](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/migrate)).
- Active Assist recommenders sort recommendations into value categories, such as cost, security, performance, reliability, and manageability. A qualified reviewer must assess a recommendation before you apply it ([Recommenders](https://docs.cloud.google.com/recommender/docs/recommenders), [What is Active Assist](https://docs.cloud.google.com/recommender/docs/whatis-activeassist)).

## Cloud-first and cloud-native design

The two terms answer different questions. Cloud-first is an adoption approach: where do new workloads go? Cloud native is a design approach: how do you build and deliver them?

| Term | What Google means | What it means for a design |
|---|---|---|
| Cloud-first | Deploy new workloads to the public cloud, and keep existing workloads where they are. Use a private environment only if a public cloud deployment is impossible for technical or organizational reasons | Good for new workloads. It can miss larger savings from existing workloads, add cross-environment traffic, and conflict with data privacy laws |
| Cloud native | Build and run scalable applications that take full advantage of cloud services. Its pillars include microservices, containers and orchestration, DevOps, and CI/CD | Teams deploy and scale components independently. It needs new skills, cost oversight, and a change in culture |

Sources: [Hybrid adoption approaches](https://docs.cloud.google.com/architecture/hybrid-multicloud-patterns/adopt), [What is cloud native?](https://cloud.google.com/learn/what-is-cloud-native).

A common cloud-first hybrid case: legacy systems hold critical data that new cloud applications need. Put an API layer in front of the legacy services. Apigee does this with minimal application changes and adds security, analytics, and scalability ([Hybrid adoption approaches](https://docs.cloud.google.com/architecture/hybrid-multicloud-patterns/adopt)). Apigee API proxies decouple the app-facing API from the backend services. When you change the backend, apps continue to call the same API ([API proxies](https://docs.cloud.google.com/apigee/docs/api-platform/fundamentals/understanding-apis-and-api-proxies)). This gives you a safe path to replace the legacy backend later. See [Integration patterns and data movement](note:1.1-integration-and-data-movement) and [Advising teams: deployment, API management, and testing](note:5.1-deployment-and-apis).

A 2019 Google Cloud blog post calls the last of its five cloud-native principles "always be architecting." Refine, simplify, and improve the architecture as the organization, the IT landscape, and the cloud provider change ([5 principles for cloud-native architecture](https://cloud.google.com/blog/products/application-development/5-principles-for-cloud-native-architecture-what-it-is-and-how-to-master-it)). The current framework principles are in [The Google Cloud Well-Architected Framework](note:1.2-well-architected-framework).

## Modernization paths over time

Choose a migration type for each workload, not for the whole company. You can mix types across workloads, and even across the components of one application stack ([Hybrid adoption approaches](https://docs.cloud.google.com/architecture/hybrid-multicloud-patterns/adopt)).

| Type | What changes | Choose it when | Cost and risk |
|---|---|---|---|
| Rehost (lift and shift) | Only what the target environment needs | Few dependencies, third-party software, or code that you cannot change | Fastest, same skills. Does not take full advantage of horizontal scaling or managed services |
| Replatform (lift and optimize) | Parts are optimized for the cloud, for example containers in GKE | You want elasticity, redundancy, and performance without a rewrite | More work and testing than a rehost |
| Refactor (move and improve) | Code, to use cloud capabilities | Dependencies must be untangled, or the platform is not supported in the cloud | Slower than a rehost; needs new skills |
| Re-architect (continue to modernize) | How the code functions, for example a monolith into microservices | You need cloud-optimized scalability, security, and agility | More complex than a refactor; needs several rounds of testing |
| Rebuild (remove and replace) | You decommission the app and rewrite it | The app no longer meets requirements, costs too much to migrate, or uses end-of-life technology | Takes longer than a rehost or refactor; removes technical debt |
| Repurchase | You move to a SaaS equivalent, for example Google Workspace | A SaaS product covers the need | Can be easier, but can cost more and gives less control |

Sources: [Migrate to Google Cloud](https://docs.cloud.google.com/architecture/migration-to-gcp-getting-started), [Hybrid adoption approaches](https://docs.cloud.google.com/architecture/hybrid-multicloud-patterns/adopt).

Google's modernization path for .NET applications shows a typical sequence. Each step removes a limitation and opens the next phase ([.NET modernization path](https://docs.cloud.google.com/dotnet/docs/modernization-path-dotnet-applications-google-cloud)):

1. **Rehost.** Move the burden of server management to the cloud.
2. **Replatform.** Replace self-hosted software with managed services that need no code changes, such as Cloud SQL, Memorystore, and Managed Service for Microsoft Active Directory. The architecture does not change.
3. **Re-architect and rebuild.** Use Cloud Storage instead of network attached storage, Pub/Sub instead of a self-hosted message queue, and IAP instead of an authentication layer in the code. Move workloads to containers and serverless computing.

Do not rewrite everything at once. Write new services on the new platform, and break the monolith into smaller services as opportunities arise ([.NET modernization path](https://docs.cloud.google.com/dotnet/docs/modernization-path-dotnet-applications-google-cloud)). Modules with clear interfaces allow independent updates and future component separation, even inside a monolith. But communication between modules can add latency and overhead. When performance is critical, a more tightly coupled design can be the right choice ([Promote modular design](https://docs.cloud.google.com/architecture/framework/performance-optimization/promote-modular-design)).

For migration planning and tools, see [Planning a migration](note:1.4-migration-planning) and [Data and system migration tooling](note:5.1-migration-tooling). For the target platform, see [Mapping workloads to compute platforms](note:1.3-compute-choice).

## Design for change

The choices that you make today decide the cost of the next change. The Well-Architected Framework lists "design for change" first among its core principles. No system is static, so deliver small changes often, with fast feedback. DORA software delivery metrics show the speed, ease, and safety of change ([Well-Architected Framework](https://docs.cloud.google.com/architecture/framework)).

| Technique | What it protects against | Google Cloud example |
|---|---|---|
| Loose coupling through well-defined interfaces | A change in one component forces changes in others | APIs and message queues between modules |
| API facade | Backend changes break client apps | Apigee API proxies |
| Stateless components | A scale-out, restart, or replacement loses data | State in shared storage or cache services |
| Fully managed services | The team spends its time on patches, not on features | Cloud SQL; GKE Autopilot or Cloud Run for containers |
| Infrastructure as code (IaC) | You cannot test or roll back a change | Terraform: revert the code to roll back |
| Architecture decision records (ADRs) | Nobody knows why a design exists, so nobody changes it safely | Record the options, requirements, and decision. When a decision changes, keep the old one and the reason |
| Error budget | Fear of any failure stops all change | The gap between 100% and the SLO lets you take risks and innovate |

Sources: [Promote modular design](https://docs.cloud.google.com/architecture/framework/performance-optimization/promote-modular-design), [API proxies](https://docs.cloud.google.com/apigee/docs/api-platform/fundamentals/understanding-apis-and-api-proxies), [Well-Architected Framework](https://docs.cloud.google.com/architecture/framework), [Hybrid adoption approaches](https://docs.cloud.google.com/architecture/hybrid-multicloud-patterns/adopt), [Optimize your environment](https://docs.cloud.google.com/architecture/migration-to-google-cloud-optimizing-your-environment), [ADR overview](https://docs.cloud.google.com/architecture/architecture-decision-records), [Set realistic targets for reliability](https://docs.cloud.google.com/architecture/framework/reliability/set-targets).

An ADR history shows how the architecture changed as business needs evolved or new solutions appeared ([ADR overview](https://docs.cloud.google.com/architecture/architecture-decision-records)). For decision-making processes, see [Business processes](note:4.2-business-processes).

Change also needs governance: change governance, risk assessment, testing and validation, and controlled deployment with a way to roll back ([Automate and manage change](https://docs.cloud.google.com/architecture/framework/operational-excellence/automate-and-manage-change)). See [The operational excellence pillar](note:6.1-operational-excellence) and [Infrastructure as Code](note:5.2-infrastructure-as-code).

## Evolution of business needs

Treat improvement as a loop, not as a project. The optimization phase of Google's migration framework repeats these steps ([Optimize your environment](https://docs.cloud.google.com/architecture/migration-to-google-cloud-optimizing-your-environment)):

1. **Assess** the environment, the teams, and the loop. A new managed service can need skills that the team does not have.
2. **Set requirements.** Find the conflicts and prioritize. For example, more performance can conflict with lower operational cost.
3. **Set measurable goals** with SLIs and SLOs. If you cannot measure an SLI yet, your first goal is to extend monitoring.
4. **Measure, analyze, and optimize.** Compare the environment with the SLOs, with industry best practices, and with an environment that has no technical debt. Codify, automate, and monitor everything.
5. **Measure again, and tune the loop.** Stop when you meet the goals.

Feed the loop with feedback from users and stakeholders, and with KPIs in Cloud Monitoring and BigQuery ([Continuously improve and innovate](https://docs.cloud.google.com/architecture/framework/operational-excellence/continuously-improve-and-innovate)). Also use Cloud Billing data in BigQuery and findings from Recommender and Security Command Center ([Optimize your environment](https://docs.cloud.google.com/architecture/migration-to-google-cloud-optimizing-your-environment)).

| Business change | Architecture response | Read more |
|---|---|---|
| Fast growth in users or data | Stateless components that scale out quickly. Modules that scale independently | [HA and scalability](note:1.2-ha-scalability-performance) |
| More workloads move to the cloud | Grow the landing zone. Its first iteration is often not its final version | [Resource hierarchy](note:3.1-iam-and-hierarchy) |
| Pressure to cut cost | Act on cost recommendations, for example remove idle resources | [Cost optimization](note:4.2-cost-optimization) |
| A need for faster feature delivery | Decouple components, deliver small changes, and track DORA metrics | [SDLC and CI/CD](note:4.1-sdlc-cicd) |
| New regulations or data privacy laws | Check which workloads the rules restrict. They can block the move of sensitive data | [Compliance](note:3.2-compliance) |
| A new AI use case | Start with pre-trained models and small experiments. Define SMART objectives and ROI KPIs | [AI solutions](note:1.3-ai-solutions) |

Sources: [Well-Architected Framework](https://docs.cloud.google.com/architecture/framework), [Promote modular design](https://docs.cloud.google.com/architecture/framework/performance-optimization/promote-modular-design), [Landing zone design](https://docs.cloud.google.com/architecture/landing-zones), [Recommenders](https://docs.cloud.google.com/recommender/docs/recommenders), [Hybrid adoption approaches](https://docs.cloud.google.com/architecture/hybrid-multicloud-patterns/adopt), [AI cost perspective](https://docs.cloud.google.com/architecture/framework/perspectives/ai-ml/cost-optimization).

## Adopt new services and AI features safely

### Launch stages and deprecation

| Stage | SLA and support | Use it for |
|---|---|---|
| Preview | No SLA and no technical support commitments. Not necessarily feature-complete | Test environments, unless Google states otherwise |
| General Availability (GA) | Open to all customers. Covered by a Google Cloud SLA where applicable | Production |
| Deprecated | Scheduled for shutdown and removal | A plan to move off the feature |

Sources: [Product launch stages](https://cloud.google.com/products#product-launch-stages).

The 12-month discontinuation notice in the Terms of Service does not cover pre-GA offerings ([Terms of Service](https://cloud.google.com/terms)). Thus a Preview feature can change or disappear with less notice. When a scenario needs an SLA, choose the GA option.

Know what changes before it reaches you:

- **Release notes.** Filter them in the console, query them in BigQuery, or add their feed to a feed reader ([Google Cloud release notes](https://docs.cloud.google.com/release-notes)).
- **Deprecation recommender (Preview).** It identifies your resources that upcoming deprecations and breaking changes affect ([Deprecation recommender](https://docs.cloud.google.com/recommender/docs/deprecation-change-recommender)).
- **Managed upgrades.** GKE upgrades all clusters over time. Use a release channel; the default Regular channel suits most users. Upgrade pre-production first ([About release channels](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/release-channels)).
- **Deprecation insights.** When a GKE cluster uses a Kubernetes API that the next minor version removes, GKE pauses the automatic upgrade. GKE also creates an insight and a recommendation ([GKE deprecation insights](https://docs.cloud.google.com/kubernetes-engine/docs/deprecations/viewing-deprecation-insights-and-recommendations)).

### AI features

AI models and SDKs change fast. Plan for three things:

1. **Start small.** Start with pre-trained models and APIs, and with small models and datasets. Add complexity only when performance requirements need it ([AI cost perspective](https://docs.cloud.google.com/architecture/framework/perspectives/ai-ml/cost-optimization)).
2. **Define the value.** Set SMART objectives, and track ROI KPIs for costs and business value ([AI cost perspective](https://docs.cloud.google.com/architecture/framework/perspectives/ai-ml/cost-optimization)).
3. **Plan model upgrades.** Some models stay available for at least 12 months after release. Short-term models stay until Google announces a retirement date, with at least 45 days to migrate. Google does not move a retirement date earlier ([Model versions and lifecycle](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/model-versions)).

Before you switch models, get InfoSec, risk, and compliance approvals early. Repeat your evaluations, and run code, model quality, and load regression tests. If you use a fine-tuned model, first test the new model without fine-tuning. A tuned model does not move to a new Gemini version; you run a new tuning job. SDKs change too: Vertex AI SDK releases after June 2026 do not support Gemini ([Gemini model migration](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/migrate)). For model choice, see [Choosing AI and ML solutions](note:1.3-ai-solutions) and [End-to-end ML workflows on Agent Platform](note:2.4-ml-workflows).

## Active Assist as an input to improvements

Active Assist is the portfolio of Google Cloud tools that generate recommendations and insights to optimize your projects ([What is Active Assist](https://docs.cloud.google.com/recommender/docs/whatis-activeassist)). Each recommender belongs to a value category:

| Improvement goal | Example recommender | Value category |
|---|---|---|
| Right-size VMs | VM machine type recommender | Performance |
| Remove waste | Idle VM, idle persistent disk, and Cloud SQL idle instance recommenders | Cost |
| Remove excess permissions | Identity and Access Management recommender | Security |
| Reclaim unused projects | Unattended project recommender | Security |
| Increase availability | Cloud SQL reliability recommender (enable high availability) | Reliability |
| Avoid quota limits | Service limit (quota) recommender | Reliability |
| Prepare for deprecations | Deprecation and breaking changes recommender (Preview) | Manageability |

Sources: [Recommenders](https://docs.cloud.google.com/recommender/docs/recommenders), [Deprecation recommender](https://docs.cloud.google.com/recommender/docs/deprecation-change-recommender).

Use recommendations well:

- Find them in Active Assist, FinOps hub, and the Optimization page in Cloud Hub. You can also find them on the console page of a service, or through the gcloud CLI and the REST API ([What is Active Assist](https://docs.cloud.google.com/recommender/docs/whatis-activeassist)).
- Use the priority field (`P1` to `P4`) to decide what to do first ([Recommendations](https://docs.cloud.google.com/recommender/docs/key-concepts)).
- Review before you apply. A reviewer who knows the infrastructure and the business must assess the impact. To apply without human review, set up a rollback process first ([What is Active Assist](https://docs.cloud.google.com/recommender/docs/whatis-activeassist)).

For billing levers, see [Cost optimization and CapEx/OpEx](note:4.2-cost-optimization). For cost help in the console assistant, see [Gemini Cloud Assist](note:1.2-gemini-cloud-assist).

## Exam traps

- **A big-bang rewrite first.** Google recommends constant iteration. Prefer a phased path that rehosts or replatforms first ([What is cloud native?](https://cloud.google.com/learn/what-is-cloud-native), [Hybrid adoption approaches](https://docs.cloud.google.com/architecture/hybrid-multicloud-patterns/adopt)).
- **Rehost as the end state.** Rehosted workloads do not take full advantage of horizontal scaling or managed services. Plan the next steps. Google's .NET modernization path moves from rehost to replatform, and then to re-architect and rebuild ([Migrate to Google Cloud](https://docs.cloud.google.com/architecture/migration-to-gcp-getting-started), [.NET modernization path](https://docs.cloud.google.com/dotnet/docs/modernization-path-dotnet-applications-google-cloud)).
- **Cloud-first for everything.** A strict cloud-first approach can add complexity and cross-environment traffic, and regulations can block the move ([Hybrid adoption approaches](https://docs.cloud.google.com/architecture/hybrid-multicloud-patterns/adopt)).
- **Containers for every workload.** Some workloads cannot use containers for technical or licensing reasons. You can also stop at an earlier modernization step ([Containerized deployments](https://docs.cloud.google.com/architecture/migration-to-google-cloud-automated-containerized-deployments)).
- **Maximum modularity.** When performance is critical, a more tightly coupled design can be correct ([Promote modular design](https://docs.cloud.google.com/architecture/framework/performance-optimization/promote-modular-design)).
- **Preview in a production design that needs an SLA.** Preview has no SLA, and the 12-month notice does not cover it ([Product launch stages](https://cloud.google.com/products#product-launch-stages), [Terms of Service](https://cloud.google.com/terms)).
- **A model version as a permanent dependency.** Models retire, and tuned models do not carry over ([Model versions and lifecycle](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/model-versions), [Gemini model migration](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/migrate)).
- **Apply all recommendations automatically.** Unreviewed changes can hurt performance, reliability, or required permissions ([What is Active Assist](https://docs.cloud.google.com/recommender/docs/whatis-activeassist)).
- **Optimize without a goal.** Set measurable goals first ([Optimize your environment](https://docs.cloud.google.com/architecture/migration-to-google-cloud-optimizing-your-environment)).
