## Why it matters

IAM decides who can act. Other controls limit what anyone can configure, where requests can come from, and where data can go. Audit logs record what happened. The exam often offers an IAM change as the answer when the scenario needs a guardrail that applies to everyone, including owners.

## Key points

- Organization Policy focuses on what: it restricts how resources can be configured. IAM focuses on who can act ([Organization Policy overview](https://docs.cloud.google.com/organization-policy/overview)).
- An organization policy on an organization, folder, or project applies to that resource and to its descendants ([Organization Policy overview](https://docs.cloud.google.com/organization-policy/overview)).
- A new organization policy is usually not retroactive. Existing resources that violate it keep working, and you must fix them yourself ([Organization Policy overview](https://docs.cloud.google.com/organization-policy/overview)).
- An organization policy in dry-run mode logs violations but does not deny them. Dry-run mode works with custom constraints, managed constraints, and a few legacy constraints ([Test organization policies](https://docs.cloud.google.com/organization-policy/test-policies)).
- A VPC Service Controls perimeter protects Google-managed services such as Cloud Storage and BigQuery. It stops data from being copied out of the perimeter, even by clients with valid credentials ([Overview of VPC Service Controls](https://docs.cloud.google.com/vpc-service-controls/docs/overview)).
- Access from the internet to resources in a perimeter is denied by default. Ingress rules and access levels allow access by IP address, identity, device, or source project ([Overview of VPC Service Controls](https://docs.cloud.google.com/vpc-service-controls/docs/overview)).
- In dry-run mode, a perimeter logs requests that it would deny, but it does not deny them ([Dry run mode for service perimeters](https://docs.cloud.google.com/vpc-service-controls/docs/dry-run-mode)).
- Admin Activity and System Event audit logs are always written, and you cannot disable them ([Cloud Audit Logs overview](https://docs.cloud.google.com/logging/docs/audit)). Logging does not charge for logs in the `_Required` bucket ([Google Cloud Observability pricing](https://cloud.google.com/products/observability/pricing)).
- Data Access audit logs are off by default for all services except some BigQuery services ([Enable Data Access audit logs](https://docs.cloud.google.com/logging/docs/audit/configure-data-access)).
- The `_Required` bucket keeps logs for 400 days, and you cannot change it. The `_Default` bucket keeps logs for 30 days by default ([Quotas and limits](https://docs.cloud.google.com/logging/quotas)).
- Aggregated sinks route logs from all projects in an organization or folder to one central destination ([Aggregated sinks overview](https://docs.cloud.google.com/logging/docs/export/aggregated_sinks_overview)).
- Security Command Center finds misconfigurations, vulnerabilities, and threats. The Standard tier has no additional charge. Premium adds threat detection, attack paths, and compliance monitoring ([Security Command Center service tiers](https://docs.cloud.google.com/security-command-center/docs/service-tiers)).

## Pick the control for the risk

| Risk or requirement | Control | Why this control |
|---|---|---|
| Nobody may create VMs with external IPv4 addresses, whatever their roles. | Organization policy (`compute.vmExternalIpAccess`) | It restricts configuration for everyone, including project owners. |
| Some principals must lose a permission that other policies grant. | IAM deny policy | It removes permissions from principals, whatever their allow policies say. |
| Stolen credentials must not copy BigQuery data to another project. | VPC Service Controls perimeter | It blocks API requests that cross the perimeter, even when IAM allows them. |
| Only corporate networks or managed devices may reach the data. | Access level, used in an ingress rule or by IAP | An access level checks the IP address, device, region, or identity of the request. |
| Block network traffic between VMs in the whole organization. | Hierarchical firewall policy | It controls packets, not API requests. Lower levels cannot override it. |
| Record who changed what, and who read sensitive data. | Admin Activity and Data Access audit logs | Admin Activity logs are always on. Data Access logs need to be turned on. |
| Find misconfigurations and active threats across projects. | Security Command Center | Built-in detectors create findings. |

Sources: [Organization Policy overview](https://docs.cloud.google.com/organization-policy/overview), [Organization policy constraints](https://docs.cloud.google.com/organization-policy/reference/org-policy-constraints), [Deny policies](https://docs.cloud.google.com/iam/docs/deny-overview), [Overview of VPC Service Controls](https://docs.cloud.google.com/vpc-service-controls/docs/overview), [Access Context Manager overview](https://docs.cloud.google.com/access-context-manager/docs/overview), [Hierarchical firewall policies](https://docs.cloud.google.com/firewall/docs/firewall-policies), [Cloud Audit Logs overview](https://docs.cloud.google.com/logging/docs/audit), [Security Command Center overview](https://docs.cloud.google.com/security-command-center/docs/security-command-center-overview).

VPC Service Controls is a layer that is independent of IAM. Google recommends that you use both, for defense in depth ([Overview of VPC Service Controls](https://docs.cloud.google.com/vpc-service-controls/docs/overview)). For deny policies, see [IAM, resource hierarchy, and separation of duties](note:3.1-iam-and-hierarchy). For firewall policies and Cloud NGFW, see [Network security controls](note:2.1-network-security).

## Organization policy

A constraint is one type of restriction for one or more services. An organization policy sets one constraint on an organization, folder, or project ([Organization Policy overview](https://docs.cloud.google.com/organization-policy/overview)).

| Constraint type | What it is | Design notes |
|---|---|---|
| Managed constraint | Google defines it. It can take parameters, and it replaces an equivalent legacy constraint. | Supports Policy Simulator by default. A child resource does not merge an inherited managed constraint: it inherits it or overrides it. |
| Custom constraint | You define a condition on resource fields. It checks create and update requests. | Only for services that support custom constraints. |
| Legacy managed constraint | Formerly called a predefined constraint. List rules allow or deny values. Boolean rules enforce or do not enforce. | Policies for legacy constraints merge down the hierarchy by the hierarchy evaluation rules. |

Sources: [Organization Policy overview](https://docs.cloud.google.com/organization-policy/overview), [Create custom constraints](https://docs.cloud.google.com/organization-policy/create-custom-constraints).

Design rules:

- **Conditional enforcement.** Use tags to enforce a constraint only on some resources, for example resources tagged `environment=development` ([Organization Policy overview](https://docs.cloud.google.com/organization-policy/overview)).
- **Test first.** Put a new policy in dry-run mode, and read the violations in the audit logs before you enforce it ([Test organization policies](https://docs.cloud.google.com/organization-policy/test-policies)).
- **Existing resources.** Most constraints do not act on existing resources. `storage.publicAccessPrevention` is an exception: it revokes existing public access to buckets and objects ([Organization policy constraints](https://docs.cloud.google.com/organization-policy/reference/org-policy-constraints)).
- **Who can set policies.** You can grant the Organization Policy Administrator role only on the organization ([Organization Policy Service roles](https://docs.cloud.google.com/iam/docs/roles-permissions/orgpolicy)). To delegate, add a tag condition to the role binding ([Test organization policies](https://docs.cloud.google.com/organization-policy/test-policies)).

| Requirement in a scenario | Constraint |
|---|---|
| Only identities from our organization can get IAM roles. | `iam.allowedPolicyMemberDomains` (domain restricted sharing), or the managed `iam.managed.allowedPolicyMembers` |
| Create resources only in approved locations. | `gcp.resourceLocations` |
| No service account keys. | `iam.managed.disableServiceAccountKeyCreation` |
| No public buckets or objects. | `storage.publicAccessPrevention` |
| No object ACLs in Cloud Storage. | `storage.uniformBucketLevelAccess` |
| No external IPv4 addresses on VMs, except named VMs. | `compute.vmExternalIpAccess`, or the managed `compute.managed.vmExternalIpAccess` |
| VMs must use OS Login. | `compute.requireOsLogin`, or the managed `compute.managed.requireOsLogin` |
| Boot disks only from approved image projects. | `compute.trustedImageProjects`, or the managed `compute.managed.trustedImageProjects` (Preview) |
| Only approved Google Cloud services can be used. | `gcp.restrictServiceUsage` |
| No public IP addresses on Cloud SQL instances. | `sql.restrictPublicIp`, or the managed `sql.managed.restrictPublicIp` |
| CMEK is required, with keys from approved projects. | `gcp.restrictNonCmekServices` and `gcp.restrictCmekCryptoKeyProjects` |

Sources: [Organization policy constraints](https://docs.cloud.google.com/organization-policy/reference/org-policy-constraints).

## VPC Service Controls

A service perimeter is a security boundary around projects and their Google-managed services. Resources in the perimeter communicate freely. By default, the perimeter blocks requests that cross it ([Overview of VPC Service Controls](https://docs.cloud.google.com/vpc-service-controls/docs/overview)).

Know what a perimeter does not do:

- It works on Google Cloud APIs. It does not block third-party APIs or services on the internet ([Overview of VPC Service Controls](https://docs.cloud.google.com/vpc-service-controls/docs/overview)).
- It does not fully control the movement of metadata ([Overview of VPC Service Controls](https://docs.cloud.google.com/vpc-service-controls/docs/overview)).
- It does not need a VPC network. You can allow access from external IP ranges or from IAM principals ([Overview of VPC Service Controls](https://docs.cloud.google.com/vpc-service-controls/docs/overview)).

| Component | Purpose | Design notes |
|---|---|---|
| Access policy | Holds access levels and perimeters. One policy per organization, plus scoped policies for folders or projects. | A scoped policy delegates administration. It works only if an organization-level policy exists. |
| Service perimeter | The protected projects and the restricted services. | A project can be in only one perimeter. Use ingress and egress rules to cross perimeters. |
| Access level | Conditions on IP ranges, device policy, regions, or identities. | Basic levels combine conditions. Custom levels use Common Expression Language. |
| Ingress rule | Allows chosen clients outside the perimeter to reach resources inside. | Ingress and egress rules can replace use cases that needed perimeter bridges. |
| Egress rule | Allows clients or resources inside to reach resources outside. | For example, read a partner's dataset in another organization. |
| Dry-run configuration | Logs requests that the new configuration would deny. | Log entries have `metadata.dryRun` set to `True`. |

Sources: [Scoped policies](https://docs.cloud.google.com/access-context-manager/docs/scoped-policies), [Service perimeter details and configuration](https://docs.cloud.google.com/vpc-service-controls/docs/service-perimeters), [Access Context Manager overview](https://docs.cloud.google.com/access-context-manager/docs/overview), [Ingress and egress rules](https://docs.cloud.google.com/vpc-service-controls/docs/ingress-egress-rules), [Dry run mode for service perimeters](https://docs.cloud.google.com/vpc-service-controls/docs/dry-run-mode).

Private access and hybrid networks:

- VMs that use `restricted.googleapis.com` reach only the services that VPC Service Controls supports. Other Google APIs are blocked ([Configure Private Google Access](https://docs.cloud.google.com/vpc/docs/configure-private-google-access)).
- For private access from on-premises, the VPC network with the hybrid landing zone must be in the perimeter ([Overview of VPC Service Controls](https://docs.cloud.google.com/vpc-service-controls/docs/overview)). For Private Google Access and Private Service Connect, see [VPC access patterns](note:2.1-vpc-access-patterns).

Roll out a perimeter in three steps:

1. Create the perimeter in dry-run mode.
2. Read the Policy Denied audit logs where `protoPayload.metadata.dryRun="true"`. Add ingress rules, egress rules, or access levels for the legitimate flows.
3. Enforce the configuration.

Sources for the rollout: [Dry run mode for service perimeters](https://docs.cloud.google.com/vpc-service-controls/docs/dry-run-mode), [Manage dry run configurations](https://docs.cloud.google.com/vpc-service-controls/docs/manage-dry-run-configurations).

## Context-aware access

Access Context Manager defines access levels. VPC Service Controls, Identity-Aware Proxy (IAP), Context-Aware Access for Google Workspace, and IAM Conditions can enforce them. These checks apply in addition to IAM ([Access Context Manager overview](https://docs.cloud.google.com/access-context-manager/docs/overview)). For IAP and Chrome Enterprise Premium (formerly BeyondCorp Enterprise), see [Secure remote and workload access](note:3.1-secure-access).

## Audit logging

| Log type | Default | Can you turn it off? | Stored in | Log charges |
|---|---|---|---|---|
| Admin Activity | On | No | `_Required` bucket, 400 days | None |
| System Event | On | No | `_Required` bucket, 400 days | None |
| Data Access | Off, except some BigQuery services | Yes, except some BigQuery logs | `_Default` bucket, 30 days by default | Yes |
| Policy Denied | On | No, but you can exclude it from storage | `_Default` bucket, 30 days by default | Yes |

Sources: [Cloud Audit Logs overview](https://docs.cloud.google.com/logging/docs/audit), [Enable Data Access audit logs](https://docs.cloud.google.com/logging/docs/audit/configure-data-access), [Quotas and limits](https://docs.cloud.google.com/logging/quotas), [Google Cloud Observability pricing](https://cloud.google.com/products/observability/pricing).

Design rules for audit logs:

- Turn on Data Access audit logs at the organization or folder level. A project cannot turn off a Data Access log that a parent turned on. You can exempt principals, such as test accounts ([Enable Data Access audit logs](https://docs.cloud.google.com/logging/docs/audit/configure-data-access)).
- Route logs to a central logging project with an aggregated sink. An intercepting sink stops child sinks from also storing the entries, except the `_Required` sinks ([Aggregated sinks overview](https://docs.cloud.google.com/logging/docs/export/aggregated_sinks_overview)).
- `_Default` and user-defined buckets in projects can keep logs from 1 to 3650 days ([Quotas and limits](https://docs.cloud.google.com/logging/quotas)). Retention beyond 30 days costs $0.01 per GiB per month ([Google Cloud Observability pricing](https://cloud.google.com/products/observability/pricing)).
- If you lock a log bucket, you also lock its retention. You cannot delete a locked bucket until every entry has met the retention period ([Configure log buckets](https://docs.cloud.google.com/logging/docs/buckets)).

For audit evidence and Access Transparency, see [Designing for compliance](note:3.2-compliance).

## Exam traps

- **"Remove the Compute Admin role to stop external IP addresses everywhere."** Roles change who can act. Use the `compute.vmExternalIpAccess` constraint, which applies to everyone ([Organization Policy overview](https://docs.cloud.google.com/organization-policy/overview)).
- **"The new constraint stops the existing VMs that violate it."** Most policies are not retroactive. You must fix existing violations yourself ([Organization Policy overview](https://docs.cloud.google.com/organization-policy/overview)).
- **"Enforce the new perimeter in production at once."** Use dry-run mode first, and read the would-be denials in the logs ([Dry run mode for service perimeters](https://docs.cloud.google.com/vpc-service-controls/docs/dry-run-mode)).
- **"A perimeter makes IAM unnecessary."** VPC Service Controls is an extra layer. Use it with IAM ([Overview of VPC Service Controls](https://docs.cloud.google.com/vpc-service-controls/docs/overview)).
- **"Turn on Admin Activity audit logs."** They are always on, and you cannot turn them off ([Cloud Audit Logs overview](https://docs.cloud.google.com/logging/docs/audit)).
- **"Cloud Storage reads are logged by default."** Data Access audit logs are off by default, except for some BigQuery services ([Enable Data Access audit logs](https://docs.cloud.google.com/logging/docs/audit/configure-data-access)).
- **"Keep audit logs for seven years in the `_Required` bucket."** Its retention is fixed at 400 days. Route the logs to a bucket with custom retention ([Quotas and limits](https://docs.cloud.google.com/logging/quotas)).
- **"Use `private.googleapis.com` to block Google APIs that the perimeter does not support."** Use `restricted.googleapis.com` ([Configure Private Google Access](https://docs.cloud.google.com/vpc/docs/configure-private-google-access)).
