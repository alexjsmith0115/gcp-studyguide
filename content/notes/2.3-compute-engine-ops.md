## Why it matters

On Compute Engine, resilience and operations come from managed instance groups (MIGs), not from individual VMs. The architect decides between zonal and regional MIGs, the health check and autohealing policy, the autoscaling signals, and how updates roll out. The exam also tests fleet operations: images, patching with VM Manager, SSH access with OS Login, and startup configuration through metadata.

## Key points

- Instance templates cannot be changed after you create them. Google recommends regional instance templates unless you reuse a template across regions ([Instance templates](https://docs.cloud.google.com/compute/docs/instance-templates)).
- Google recommends regional MIGs over zonal MIGs. By default, a regional MIG spreads VMs evenly across three zones ([About regional MIGs](https://docs.cloud.google.com/compute/docs/instance-groups/regional-migs)).
- In a regional MIG across three zones, overprovision by at least 50%. Then the other two zones can carry all traffic if one zone fails ([About regional MIGs](https://docs.cloud.google.com/compute/docs/instance-groups/regional-migs)).
- Autohealing recreates VMs that fail an application-based health check. Use separate, more conservative health checks for autohealing than for load balancing ([Set up an application-based health check and autohealing](https://docs.cloud.google.com/compute/docs/instance-groups/autohealing-instances-in-migs)).
- The autoscaler scales on CPU utilization, load balancing serving capacity, Cloud Monitoring metrics, and schedules. With several signals, it uses the largest recommended size ([Autoscaling groups of instances](https://docs.cloud.google.com/compute/docs/autoscaler)).
- For an update with no capacity loss, set `maxUnavailable` to `0` and `maxSurge` above `0` ([Automatically apply VM configuration updates in a MIG](https://docs.cloud.google.com/compute/docs/instance-groups/rolling-out-updates-to-managed-instance-groups)).
- There is no rollback command. To roll back, start a new update with the previous instance template ([Automatically apply VM configuration updates in a MIG](https://docs.cloud.google.com/compute/docs/instance-groups/rolling-out-updates-to-managed-instance-groups)).
- Stateful MIGs keep instance names, disks, IP addresses, and metadata when VMs are recreated. They do not support autoscaling ([Stateful managed instance groups](https://docs.cloud.google.com/compute/docs/instance-groups/stateful-migs)).
- VM Manager provides Patch, OS inventory management, and OS policies. It needs the OS Config API, an active OS Config agent, and an attached service account on each VM ([Set up VM Manager](https://docs.cloud.google.com/compute/vm-manager/docs/setup)).
- By default, VM Manager does not patch VMs that are part of a MIG ([Create patch jobs](https://docs.cloud.google.com/compute/vm-manager/docs/patch/create-patch-job)).
- OS Login uses IAM to manage SSH access, so you do not create and manage individual SSH keys. It is the recommended way to manage many users across many VMs or projects ([About OS Login](https://docs.cloud.google.com/compute/docs/oslogin)).

## Instance templates and images

An instance template defines the machine type, image, disks, network, metadata, and provisioning model for every VM in a MIG. You cannot edit a template. To change the configuration, you create a new template and roll it out ([Instance templates](https://docs.cloud.google.com/compute/docs/instance-templates)).

| | Regional instance template | Global instance template |
|---|---|---|
| Scope | Only the template's region | Any region |
| Reliability | Hardware errors stay in one region | Hardware errors can affect every region that uses it |
| Use for | Less cross-region dependency; data residency | Reuse across regions for VMs, MIGs, and reservations |

Source: [Instance templates](https://docs.cloud.google.com/compute/docs/instance-templates).

Make templates deterministic. If a startup script installs software, pin the version, and use a specific container tag instead of `latest` ([Deterministic instance templates](https://docs.cloud.google.com/compute/docs/instance-templates/deterministic-instance-templates)).

### Images and image families

A custom image with your software already installed ("baking") is more efficient than a long startup script. Baking gives a shorter time to readiness, more reliable deployments, easier rollback, and identical software on every new VM ([Image management best practices](https://docs.cloud.google.com/compute/docs/images/image-management-best-practices)).

- **Image families.** An image family points to the latest image in the family. Automation can use the family name instead of an image name ([Image families best practices](https://docs.cloud.google.com/compute/docs/images/image-families-best-practices)).
- **Rollback.** To roll a family back, deprecate its newest image. The family then points to the previous image, if that image is not deprecated ([Image families best practices](https://docs.cloud.google.com/compute/docs/images/image-families-best-practices)).
- **Test first.** A new image in a family can break an application. Test the latest image in a separate environment before production ([Image families best practices](https://docs.cloud.google.com/compute/docs/images/image-families-best-practices)).
- **Deprecation states.** `DEPRECATED` images still launch with a warning. `OBSOLETE` and `DELETED` images cannot launch ([Image management best practices](https://docs.cloud.google.com/compute/docs/images/image-management-best-practices)).

## Zonal or regional MIGs

| | Zonal MIG | Regional MIG |
|---|---|---|
| Zones | One | Three by default; you can select more or fewer zones explicitly |
| Size limit | 1,000 VMs | 2,000 VMs (can increase to 4,000) |
| Zone failure | The whole group is down | The other zones keep serving |
| Default `maxSurge` and `maxUnavailable` | 1 | The number of zones (3 by default) |
| Zones after creation | — | You cannot change the zones; you can change the target distribution shape |

Sources: [About regional MIGs](https://docs.cloud.google.com/compute/docs/instance-groups/regional-migs), [Automatically apply VM configuration updates in a MIG](https://docs.cloud.google.com/compute/docs/instance-groups/rolling-out-updates-to-managed-instance-groups).

When a zone fails, the VMs in the other zones keep serving. The MIG does not add or move VMs unless autoscaling is on ([About regional MIGs](https://docs.cloud.google.com/compute/docs/instance-groups/regional-migs)). This is why you overprovision:

| Zones | Extra capacity | Group size |
|---|---|---|
| 2 | +100% | 200% |
| 3 | +50% | 150% |
| 4 | +33% | 133% |

Source: [About regional MIGs](https://docs.cloud.google.com/compute/docs/instance-groups/regional-migs).

The target distribution shape controls where a regional MIG puts VMs:

| Shape | Behavior | Use for |
|---|---|---|
| `EVEN` (default) | Same number of VMs in each zone, within 1 | Highly available serving |
| `BALANCED` | Prefers zones with resources, but stays as even as possible | Serving or batch that needs scarce hardware |
| `ANY` | Any zone with capacity; uses unused zonal reservations | Batch that does not need high availability |
| `ANY_SINGLE_ZONE` | All VMs in one zone | Tightly coupled work, with a compact placement policy |

Source: [About regional MIGs](https://docs.cloud.google.com/compute/docs/instance-groups/regional-migs).

## Health checks and autohealing

By default, a MIG repairs VMs that fail or that someone stops outside the MIG. Autohealing adds a repair for VMs whose application fails a health check ([About repairing VMs for high availability](https://docs.cloud.google.com/compute/docs/instance-groups/about-repair)).

Configure autohealing with care:

1. **Separate health checks.** A load balancer health check moves traffic away from unresponsive VMs. An autohealing health check recreates VMs, so make it more conservative ([Set up an application-based health check and autohealing](https://docs.cloud.google.com/compute/docs/instance-groups/autohealing-instances-in-migs)).
2. **Firewall.** Allow the health check probe ranges `130.211.0.0/22` and `35.191.0.0/16`. If the probes cannot reach the VMs, the MIG marks healthy VMs as unhealthy ([Set up an application-based health check and autohealing](https://docs.cloud.google.com/compute/docs/instance-groups/autohealing-instances-in-migs)).
3. **Initial delay.** The MIG ignores failed health checks while a new VM boots and runs its startup script. Set it to the real startup time (0 to 3600 seconds; the console default is 300) ([Set up an application-based health check and autohealing](https://docs.cloud.google.com/compute/docs/instance-groups/autohealing-instances-in-migs)).
4. **Repair template.** By default, a repair recreates the VM from the original instance template of that VM ([About repairing VMs for high availability](https://docs.cloud.google.com/compute/docs/instance-groups/about-repair)).

## Autoscaling

| Signal | Use when | Scale to zero? |
|---|---|---|
| Average CPU utilization | CPU tracks load | No |
| HTTP load balancing serving capacity | The MIG is a backend of an Application Load Balancer | No |
| Cloud Monitoring metrics | Load shows in another metric, for example queue depth | Only with metrics that do not come from the MIG's VMs |
| Schedules | Load is predictable, for example business hours or a known event | Yes, if no schedule is active and other signals allow it |

Sources: [Autoscaling groups of instances](https://docs.cloud.google.com/compute/docs/autoscaler), [Scaling based on load balancing serving capacity](https://docs.cloud.google.com/compute/docs/autoscaler/scaling-load-balancing), [Scale based on Monitoring metrics](https://docs.cloud.google.com/compute/docs/autoscaler/scaling-cloud-monitoring-metrics), [Scaling based on schedules](https://docs.cloud.google.com/compute/docs/autoscaler/scaling-schedules).

Tune these settings ([Autoscaling groups of instances](https://docs.cloud.google.com/compute/docs/autoscaler)):

- **Initialization period** (default 60 seconds). For scale-out decisions, the autoscaler ignores data from VMs that are still starting. Measure your real startup time.
- **Stabilization period** (default 10 minutes). The autoscaler keeps enough VMs for the peak in this window before it scales in.
- **Predictive autoscaling.** It scales out before forecast load. It works best when startup takes more than 2 minutes and load follows daily or weekly cycles.
- **Scale-in controls.** They limit how many VMs the group can lose in a time window. Use them for apps that start slowly and see load spikes after dips.

You cannot autoscale a stateful MIG ([Autoscaling groups of instances](https://docs.cloud.google.com/compute/docs/autoscaler)).

## Updating a MIG

MIG updates have two types. A proactive (automatic) update replaces VMs for you. An opportunistic (selective) update applies only when you act on selected VMs or when the MIG creates new VMs, for example during a scale-out ([Automatically apply VM configuration updates in a MIG](https://docs.cloud.google.com/compute/docs/instance-groups/rolling-out-updates-to-managed-instance-groups)).

| Setting | What it does | Key rule |
|---|---|---|
| `maxSurge` | Extra VMs above target size during the update | Needs quota; higher values update faster and cost more |
| `maxUnavailable` | VMs that can be offline at once | `0` together with `maxSurge` > 0 keeps full capacity |
| Regional fixed values | Surge and unavailable numbers | Must be `0` or at least the number of zones |
| Minimal action | The least action the MIG performs on each VM, for example a restart | Use a restart if the app reads metadata only at boot |
| Most disruptive allowed action | A ceiling on disruption | The update fails instead of doing more |
| Replacement method | `SUBSTITUTE` (default, new names, faster) or `RECREATE` (keeps names) | `RECREATE` requires `maxSurge` of `0` |
| Canary | Apply the new template to only part of the group | Roll back only that subset if the canary fails |

Source: [Automatically apply VM configuration updates in a MIG](https://docs.cloud.google.com/compute/docs/instance-groups/rolling-out-updates-to-managed-instance-groups).

For canary and blue/green as a release process, see [Deployment and release management](note:6.3-release-management).

## Stateful MIGs

A stateful MIG keeps each VM's unique state: name, persistent disks, IP addresses, and metadata. It keeps them through restart, recreation, autohealing, and update ([Stateful managed instance groups](https://docs.cloud.google.com/compute/docs/instance-groups/stateful-migs)).

- **Use for.** Databases such as Cassandra, Elasticsearch, and MongoDB, data processing such as Kafka, and legacy monoliths ([Stateful managed instance groups](https://docs.cloud.google.com/compute/docs/instance-groups/stateful-migs)).
- **You keep.** Autohealing, automated rolling updates, and multi-zone deployment ([Stateful managed instance groups](https://docs.cloud.google.com/compute/docs/instance-groups/stateful-migs)).
- **You lose.** Autoscaling ([Stateful managed instance groups](https://docs.cloud.google.com/compute/docs/instance-groups/stateful-migs)).
- **First consider managed services.** Google suggests Cloud SQL for MySQL and PostgreSQL, and Dataflow for data processing, before you run them on stateful MIGs ([Stateful managed instance groups](https://docs.cloud.google.com/compute/docs/instance-groups/stateful-migs)).

## Spot VMs in a MIG

You select Spot in the instance template with the provisioning model `SPOT`. The termination action is `STOP` (default) or `DELETE` ([Create and use Spot VMs](https://docs.cloud.google.com/compute/docs/instances/create-use-spot)). When Compute Engine preempts Spot VMs in a MIG, the MIG keeps trying to recreate them until capacity returns ([Spot VMs](https://docs.cloud.google.com/compute/docs/instances/spot)).

A Spot MIG can grow only when spare capacity exists. If the MIG uses instance flexibility with several machine types, it selects the types with the lowest observed preemption rates ([Spot VMs](https://docs.cloud.google.com/compute/docs/instances/spot)). For the Spot model itself, see [Choosing compute resources](note:1.3-compute-resources).

## Patch and configuration management with VM Manager

VM Manager has three services ([VM Manager](https://docs.cloud.google.com/compute/vm-manager/docs/overview)):

| Service | What it does |
|---|---|
| Patch | On-demand patch jobs, scheduled patch deployments, and patch compliance reports |
| OS inventory management | Collects OS details, installed packages, available updates, and vulnerability reports |
| OS policies | Installs, removes, and updates packages and files to a declared state |

Sources: [VM Manager](https://docs.cloud.google.com/compute/vm-manager/docs/overview), [OS inventory management](https://docs.cloud.google.com/compute/vm-manager/docs/os-inventory/os-inventory-management), [About OS policies](https://docs.cloud.google.com/compute/vm-manager/docs/os-policies).

Set it up in this order ([Set up VM Manager](https://docs.cloud.google.com/compute/vm-manager/docs/setup)):

1. Enable the OS Config API in the project.
2. Check that the OS Config agent is installed. Most images include it, but it stays inactive until you set the metadata.
3. Set `enable-osconfig=TRUE` in project or instance metadata. An organization policy can require it for new VMs.
4. Attach a service account to each VM. The service account needs no IAM roles.
5. For VMs without internet access, enable Private Google Access, and give the VMs a path to their package repositories ([VM Manager](https://docs.cloud.google.com/compute/vm-manager/docs/overview)).

The Patch service does not host packages. For full control of the patch baseline, Google recommends your own local repository or a Windows Server Update Service ([About Patch](https://docs.cloud.google.com/compute/vm-manager/docs/patch)).

A patch job gives you these controls ([Create patch jobs](https://docs.cloud.google.com/compute/vm-manager/docs/patch/create-patch-job)):

- **Targets.** Instance filters by name prefix, label, or zone. Patch in small batches instead of all VMs at once.
- **Rollout.** Patch one zone at a time or zones concurrently. A disruption budget limits how many VMs per zone are disrupted at once.
- **Maintenance window.** No new patching starts after the window ends.
- **Reboot.** `Default` (the agent decides), `Always`, or `Never`.
- **Scripts.** Pre-patch and post-patch scripts that run before and after the patch.
- **MIGs.** MIG VMs are skipped unless you set `migInstancesAllowed`.

OS policies suit agents and baseline configuration. VM Manager checks and enforces each OS policy every 60 minutes, and an OS policy assignment targets VMs by labels, OS family, and zone ([About OS policies](https://docs.cloud.google.com/compute/vm-manager/docs/os-policies)). The OS inventory scan runs every 10 minutes by default ([OS inventory management](https://docs.cloud.google.com/compute/vm-manager/docs/os-inventory/os-inventory-management)).

## OS Login, startup scripts, and metadata

OS Login ties Linux accounts to Google identities and checks IAM on every login ([About OS Login](https://docs.cloud.google.com/compute/docs/oslogin)):

- **Roles.** `roles/compute.osLogin` gives login without `sudo`. `roles/compute.osAdminLogin` gives login with `sudo`.
- **Enable.** Set `enable-oslogin=TRUE` in project or instance metadata. Compute Engine then ignores SSH keys stored in metadata ([Set up OS Login](https://docs.cloud.google.com/compute/docs/oslogin/set-up-oslogin)).
- **Extras.** OS Login supports 2-step verification and audit logging.

For IAP TCP forwarding and other access patterns, see [Secure remote and workload access](note:3.1-secure-access).

Startup scripts come from metadata ([Use startup scripts on Linux VMs](https://docs.cloud.google.com/compute/docs/instances/startup-scripts/linux)):

- **Scope.** A script can apply to one VM or to every VM in a project. VM-level metadata overrides project-level metadata.
- **Source.** Pass a script up to 256 KB directly with `startup-script`. Use `startup-script-url` for a larger script in Cloud Storage ([About startup scripts](https://docs.cloud.google.com/compute/docs/instances/startup-scripts)).
- **Every boot.** The script runs at each boot, so make it idempotent ([Image management best practices](https://docs.cloud.google.com/compute/docs/images/image-management-best-practices)).

Any process that can query the metadata server can read all metadata values. Google recommends caution when you write sensitive values to metadata ([About VM metadata](https://docs.cloud.google.com/compute/docs/metadata/overview)).

## AWS mapping

| AWS | Google Cloud | Difference that matters |
|---|---|---|
| EC2 launch template | Instance template | Templates cannot be edited; regional templates are recommended. |
| EC2 Auto Scaling group | Managed instance group with an autoscaler | A regional MIG spreads VMs across three zones by default. |
| Auto Scaling instance refresh | MIG rolling update | `maxSurge` and `maxUnavailable` control the pace; canary uses two templates. |
| AMI | Custom image and image family | A family always points to its latest image; deprecate to roll back. |
| AWS Systems Manager | VM Manager | Patch, OS inventory management, and OS policies. |
| EC2 Instance Connect | OS Login | IAM roles control SSH access, so you do not manage individual SSH keys. |
| EC2 user data | `startup-script` metadata | Runs at every boot, so the script must be idempotent. |

## Exam traps

- **A zonal MIG for high availability.** A zonal MIG runs in one zone, so it does not survive a zone failure. Google recommends regional MIGs ([About regional MIGs](https://docs.cloud.google.com/compute/docs/instance-groups/regional-migs)).
- **Sizing a regional MIG at exactly peak load.** Without overprovisioning, a zone failure removes a third of capacity. The MIG does not add VMs unless autoscaling is on ([About regional MIGs](https://docs.cloud.google.com/compute/docs/instance-groups/regional-migs)).
- **One aggressive health check for both load balancing and autohealing.** It recreates VMs that were only briefly slow ([Set up an application-based health check and autohealing](https://docs.cloud.google.com/compute/docs/instance-groups/autohealing-instances-in-migs)).
- **No firewall rule for health check ranges.** The MIG sees every VM as unhealthy and recreates them in a loop ([Set up an application-based health check and autohealing](https://docs.cloud.google.com/compute/docs/instance-groups/autohealing-instances-in-migs)).
- **Editing an instance template.** Templates cannot change. Create a new template and start a rolling update ([Instance templates](https://docs.cloud.google.com/compute/docs/instance-templates)).
- **Zero downtime with the default update settings.** Defaults allow unavailable VMs. Set `maxUnavailable=0` and `maxSurge` > 0 ([Automatically apply VM configuration updates in a MIG](https://docs.cloud.google.com/compute/docs/instance-groups/rolling-out-updates-to-managed-instance-groups)).
- **Autoscaling a stateful MIG.** Stateful MIGs cannot autoscale ([Autoscaling groups of instances](https://docs.cloud.google.com/compute/docs/autoscaler)).
- **CPU autoscaling to zero.** A CPU signal never scales a MIG to zero; use schedules or a suitable Monitoring metric ([Autoscaling groups of instances](https://docs.cloud.google.com/compute/docs/autoscaler)).
- **Patching VMs without an attached service account or without a route to packages.** VM Manager needs both ([Set up VM Manager](https://docs.cloud.google.com/compute/vm-manager/docs/setup), [About Patch](https://docs.cloud.google.com/compute/vm-manager/docs/patch)).
- **Expecting a patch job to patch MIG VMs.** It skips them unless you allow it ([Create patch jobs](https://docs.cloud.google.com/compute/vm-manager/docs/patch/create-patch-job)).
