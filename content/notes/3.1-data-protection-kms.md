## Why it matters

Google Cloud encrypts all customer data at rest by default, and it encrypts most traffic in transit. The architect decides when default encryption is not enough. Then the architect picks the key option for the requirement: key control, key location, hardware protection, or keys held outside Google. The exam also tests how applications get secrets, and what happens to data when you rotate, disable, or destroy a key.

## Key points

- Google encrypts all customer content at rest with AES-256, with no action from you ([Default encryption at rest](https://docs.cloud.google.com/docs/security/encryption/default-encryption)).
- With default encryption, you cannot view or manage the keys or review key usage logs. Data from multiple customers might use the same key encryption key ([Cloud KMS overview](https://docs.cloud.google.com/kms/docs/key-management-service)).
- With a customer-managed encryption key (CMEK), your Cloud KMS key wraps the data encryption keys of a Google Cloud service. This is envelope encryption ([Cloud KMS overview](https://docs.cloud.google.com/kms/docs/key-management-service)).
- The service agent of the CMEK-integrated service uses the key. The principal that creates or reads the resource does not need a role on the key ([CMEK](https://docs.cloud.google.com/kms/docs/cmek)).
- For a CMEK integration, the key must be in the same location as the resource. Key rings and keys cannot move to another location ([Cloud KMS locations](https://docs.cloud.google.com/kms/docs/locations)).
- The protection level of a key (software, HSM, or external) is fixed when you create the key ([Cloud KMS resources](https://docs.cloud.google.com/kms/docs/resource-hierarchy)).
- Key rotation creates a new key version. It does not re-encrypt data, and it does not disable or delete old versions ([Key rotation](https://docs.cloud.google.com/kms/docs/key-rotation)).
- A key version stays scheduled for destruction for 30 days by default. After that, the key material is gone, and data encrypted with it cannot be recovered ([Delete Cloud KMS resources](https://docs.cloud.google.com/kms/docs/delete-kms-resources), [Create a key](https://docs.cloud.google.com/kms/docs/create-key)).
- Cloud EKM keeps key material in an external key manager. Google does not store or cache these keys and cannot recover data if you lose them ([Cloud EKM](https://docs.cloud.google.com/kms/docs/ekm)).
- Autokey creates Cloud HSM keys on demand when developers create resources. Google recommends it if its keys meet all of your requirements ([CMEK](https://docs.cloud.google.com/kms/docs/cmek)).
- Store passwords, API keys, and certificates in Secret Manager. Cloud KMS stores keys, and you cannot view or export the key material ([Secret Manager overview](https://docs.cloud.google.com/secret-manager/docs/overview)).
- VM-to-VM traffic on internal IP addresses in VPC networks is encrypted by default. Traffic between external IP addresses is not encrypted automatically ([Encryption in transit](https://docs.cloud.google.com/docs/security/encryption-in-transit)).

## Choose the encryption option

Start with the requirement, then pick the simplest option that meets it. You can mix options, for example software keys for less sensitive data and HSM or external keys for the most sensitive data ([Cloud KMS overview](https://docs.cloud.google.com/kms/docs/key-management-service)).

| Option | Where the key is and who controls it | Use it when | Trade-off |
|---|---|---|---|
| Google default encryption | Google's internal Keystore. Google manages everything. | No requirement to control, log, or revoke keys. | No key usage logs. You cannot disable access to the data through the key. |
| CMEK, software key | Cloud KMS. You control rotation, IAM, location, and the key version state. | You must control keys, prove key use in logs, or crypto-shred data. | About $0.06 per key version per month. If you disable or destroy the key, the service cannot read the data. |
| CMEK, Cloud HSM key | FIPS 140-2 Level 3 HSMs that Google manages. Same Cloud KMS API. | A requirement names hardware protection or FIPS 140-2 Level 3. | $1.00 to $2.50 per key version per month. |
| CMEK with Autokey | Cloud HSM keys that Autokey creates when a developer creates a resource. | You want CMEK everywhere without a manual key request process. | Autokey chooses the key settings. You cannot delete keys that Autokey created. |
| Single-tenant Cloud HSM | Dedicated HSM partitions. A quorum of your administrators controls the instance. | You need cryptographic isolation and administrative control of the HSMs. | Flat monthly fee for each instance. Available in fewer locations. |
| Cloud EKM | A supported external key manager, outside Google Cloud. | Key material must never be in Google, and you must be able to deny access from outside. | $3.00 per key version per month. If the external key manager is unavailable, the data is unavailable. |
| Customer-supplied encryption key (CSEK) | You. You send the key with each request, and Google does not store it. | Cloud Storage only, when policy requires you to supply raw key material. | Google keeps only a hash of the key, so you must back up each key. CSEK for Compute Engine is deprecated. |
| Confidential Computing | A hardware trusted execution environment (TEE). | Data must stay encrypted while it is in use (in memory). | Additional cost for each confidential VM. |

Sources: [Cloud KMS overview](https://docs.cloud.google.com/kms/docs/key-management-service), [Cloud HSM](https://docs.cloud.google.com/kms/docs/hsm), [Single-tenant Cloud HSM overview](https://docs.cloud.google.com/kms/docs/single-tenant-hsm), [CMEK](https://docs.cloud.google.com/kms/docs/cmek), [Autokey overview](https://docs.cloud.google.com/kms/docs/autokey-overview), [Delete Cloud KMS resources](https://docs.cloud.google.com/kms/docs/delete-kms-resources), [Cloud KMS pricing](https://cloud.google.com/kms/pricing), [Cloud Storage customer-supplied encryption keys](https://docs.cloud.google.com/storage/docs/encryption/customer-supplied-keys).

CSEK for Compute Engine is being removed. Since July 20, 2026, you cannot use a CSEK to encrypt new disks, images, or snapshots. Google recommends CMEK instead ([Deprecation of CSEK in Compute Engine](https://docs.cloud.google.com/compute/docs/deprecations/csek-deprecation-in-compute-engine)).

## How Cloud KMS organizes keys

| Resource | What it is | Design rule |
|---|---|---|
| Key ring | A group of keys in one location. | Create it in the location of the data that its keys protect. You cannot move it later. |
| Key | Has a purpose, a protection level, and an optional rotation schedule. | IAM on a key applies to all of its versions. You cannot grant access to one version only. |
| Key version | The key material. States: enabled, disabled, scheduled for destruction, destroyed. | A symmetric key encrypts new data with its primary version. Old versions still decrypt old data. |

Sources: [Cloud KMS resources](https://docs.cloud.google.com/kms/docs/resource-hierarchy), [Cloud KMS locations](https://docs.cloud.google.com/kms/docs/locations).

Location rules decide many exam answers:

- A CMEK must be in the same exact location as the resource that it protects. Some CMEK integrations do not support the `global` location ([Cloud KMS locations](https://docs.cloud.google.com/kms/docs/locations)).
- Use `global` only when the application is globally distributed, the keys have no residency requirement, and you do not use external keys ([Cloud KMS locations](https://docs.cloud.google.com/kms/docs/locations)).
- For Cloud Storage, a bucket in `US-EAST1` needs a key ring in `US-EAST1` ([Cloud Storage CMEK](https://docs.cloud.google.com/storage/docs/encryption/customer-managed-keys)).

Separate the people who manage keys from the people and services who use them. The Cloud KMS Admin role manages keys but does not include cryptographic operations. Legacy basic roles do not separate the two, so do not use them for keys ([Cloud KMS permissions and roles](https://docs.cloud.google.com/kms/docs/reference/permissions-and-roles)). For key projects and governance models, see [IAM, resource hierarchy, and separation of duties](note:3.1-iam-and-hierarchy).

## Design CMEK for a platform

1. **Grant the key to the service agent.** Each CMEK-integrated service has a service agent in your project. Grant it the CryptoKey Encrypter/Decrypter role on the key. If you revoke the role or disable the key, the data cannot be accessed ([CMEK](https://docs.cloud.google.com/kms/docs/cmek)).
2. **Choose where keys live.** A dedicated key project separates key managers from key users. Cloud KMS bills all key charges to the project that owns the key ([Separation of duties](https://docs.cloud.google.com/kms/docs/separation-of-duties), [Cloud KMS pricing](https://cloud.google.com/kms/pricing)).
3. **Enforce CMEK with organization policy.** `constraints/gcp.restrictNonCmekServices` requires CMEK for the services that you list. `constraints/gcp.restrictCmekCryptoKeyProjects` limits which projects keys can come from. Use both to require keys from approved projects ([CMEK organization policies](https://docs.cloud.google.com/kms/docs/cmek-org-policy)).
4. **Automate with Autokey.** Developers request a key as part of resource creation, and Autokey grants the service agent access. Dedicated-project key storage needs an organization with a folder. Same-project key storage works on a folder or a project ([Autokey overview](https://docs.cloud.google.com/kms/docs/autokey-overview)).
5. **Log key use.** Encrypt and decrypt calls create Data Access audit logs. Admin changes create Admin Activity audit logs ([Cloud KMS audit logging](https://docs.cloud.google.com/kms/docs/audit-logging)). Data Access audit logs are off by default for most services ([Enable Data Access audit logs](https://docs.cloud.google.com/logging/docs/audit/configure-data-access)).

## Rotate, disable, destroy, and delete

| Action | Effect on data | Undo and cost |
|---|---|---|
| Rotate (new primary version) | New data uses the new version. Old data still decrypts with old versions. Nothing is re-encrypted. | Old versions stay enabled and are billed until you destroy them. |
| Re-encrypt | You rewrite the data, and the service encrypts it with the current primary version. Then you can destroy old versions. | Each rewrite is billed as cryptographic operations. |
| Disable a version | Data encrypted with that version cannot be decrypted. This is eventually consistent: typically up to 1 minute, sometimes hours. | Enable the version again to undo. Still billed. |
| Schedule destruction | The version cannot be used. It stays in this state for 30 days by default. | Restore the version before the period ends to undo. Still billed. |
| Destroyed | The key material is gone. Data encrypted with it is crypto-shredded. | You cannot undo it. No charge. |
| Delete | Removes destroyed versions, empty keys, and empty key rings from lists. Deleted key names cannot be reused. | You cannot undo it. |

Sources: [Key rotation](https://docs.cloud.google.com/kms/docs/key-rotation), [Cloud KMS resource consistency](https://docs.cloud.google.com/kms/docs/consistency), [Key version states](https://docs.cloud.google.com/kms/docs/key-states), [Create a key](https://docs.cloud.google.com/kms/docs/create-key), [Delete Cloud KMS resources](https://docs.cloud.google.com/kms/docs/delete-kms-resources), [Cloud KMS pricing](https://cloud.google.com/kms/pricing).

More rules for the key lifecycle:

- Disabling a key version is not immediate. The consistency page says to also remove the IAM role on the key, to stop a user during that time. IAM changes also take time to apply. For the times, see the cited pages ([Cloud KMS resource consistency](https://docs.cloud.google.com/kms/docs/consistency), [Access change propagation](https://docs.cloud.google.com/iam/docs/access-change-propagation)).
- You set the scheduled-destruction duration only when you create the key. It can be 24 hours to 120 days, and an organization policy can set a minimum ([Create a key](https://docs.cloud.google.com/kms/docs/create-key)).
- Cloud KMS does not rotate asymmetric keys automatically. Some standards, such as PCI DSS, require regular key rotation ([Key rotation](https://docs.cloud.google.com/kms/docs/key-rotation)).
- Cloud Storage encrypts the object data with the CMEK, but not most metadata. You can still list and delete objects after you disable or destroy the key ([Cloud Storage CMEK](https://docs.cloud.google.com/storage/docs/encryption/customer-managed-keys)).

You can delete key versions, keys, and key rings only when some conditions are met. For the conditions, see the cited page ([Delete Cloud KMS resources](https://docs.cloud.google.com/kms/docs/delete-kms-resources)). Key rings and keys have no charge. Cloud KMS bills active key versions and operations ([Cloud KMS pricing](https://cloud.google.com/kms/pricing)).

## External keys and access justifications

Use Cloud EKM when a regulation or policy says that key material must stay outside Google. Each request goes from Cloud KMS to your external key manager partner, over the internet or over a VPC network ([Cloud EKM](https://docs.cloud.google.com/kms/docs/ekm)).

The trade-off is availability. If the external key is unavailable, Cloud KMS returns a `FAILED_PRECONDITION` error. Some services lose data permanently: Spanner deletes a database if its CMEK stays unavailable for more than 30 consecutive days. For better availability, Google suggests Cloud EKM over VPC or Cloud HSM keys ([Cloud EKM](https://docs.cloud.google.com/kms/docs/ekm)).

Key Access Justifications adds a reason code to each request to use an enrolled key. With some control packages, you can approve or deny requests by reason code. It works only with Assured Workloads ([Key Access Justifications overview](https://docs.cloud.google.com/assured-workloads/key-access-justifications/docs/overview)). For sovereignty designs, see [Designing for compliance](note:3.2-compliance).

## Encryption in transit and in use

| Path | Default protection | What you add |
|---|---|---|
| Client to a Google Cloud API | TLS at the Google Front End (GFE). | Private access, so that traffic does not use external IP addresses. |
| User to your app through an external Application Load Balancer | TLS from the client to the load balancer, with Google-managed or self-managed certificates. | Encryption from the load balancer to the backends. mTLS if clients must present certificates. |
| VM to VM on internal IP addresses (same or peered VPC network) | Authenticated and encrypted. | Nothing for encryption. Traffic between external IP addresses is not encrypted automatically. |
| Service to service inside Google | ALTS, with PSP on SmartNICs. | Nothing. |
| GKE or Compute Engine workloads that must authenticate each other | The VM-to-VM encryption in the row above. | Cloud Service Mesh for mTLS, with certificates that you manage. |
| Your data center to Google over Cloud Interconnect | Google's encryption in transit paper does not cover this link. | MACsec for Cloud Interconnect, or HA VPN over Cloud Interconnect for IPsec. |

Sources: [Encryption in transit](https://docs.cloud.google.com/docs/security/encryption-in-transit), [MACsec for Cloud Interconnect overview](https://docs.cloud.google.com/network-connectivity/docs/interconnect/concepts/macsec-overview).

For network design, see [Hybrid and multicloud connectivity](note:2.1-hybrid-multicloud) and [Load balancing](note:1.3-load-balancing).

Encryption in use protects data while a CPU processes it. Confidential Computing uses a hardware trusted execution environment ([Confidential Computing overview](https://docs.cloud.google.com/confidential-computing/docs/confidential-computing-overview)).

- **Confidential VM** runs a VM in a trusted execution environment. It is also available in GKE, Dataflow, and Managed Service for Apache Spark (formerly Dataproc) ([Confidential Computing overview](https://docs.cloud.google.com/confidential-computing/docs/confidential-computing-overview)).
- **Confidential Space** lets parties process shared sensitive data with an agreed workload. The workload operator cannot access the data ([Confidential Space overview](https://docs.cloud.google.com/confidential-computing/confidential-space/docs/confidential-space-overview)).
- **Certificate Authority Service** runs private CAs for internal certificates, such as mTLS between services. It can keep CA keys in Cloud HSM ([CA Service overview](https://docs.cloud.google.com/certificate-authority-service/docs/ca-service-overview)).

## Secrets: Secret Manager

| | Secret Manager | Cloud KMS |
|---|---|---|
| Stores | The secret value. A principal with access can read it. | Keys. You cannot view, extract, or export the key material. |
| Typical use | Database passwords, API keys, and TLS certificates that an application needs at runtime. | Encrypt data, sign data, and protect CMEK resources. |

Sources: [Secret Manager overview](https://docs.cloud.google.com/secret-manager/docs/overview), [CMEK](https://docs.cloud.google.com/kms/docs/cmek).

Design rules for secrets:

- Grant the Secret Manager Secret Accessor role on each secret, not on the project, when one project holds secrets for many services ([Secret Manager best practices](https://docs.cloud.google.com/secret-manager/docs/best-practices)).
- Pin a version number instead of the `latest` alias. Then you can validate and roll back a secret change with your release process ([Secret Manager best practices](https://docs.cloud.google.com/secret-manager/docs/best-practices)).
- Choose the replication policy at creation, because you cannot change its locations later. Automatic replication is billed as one location. User-managed replication is billed for each location ([Choose a secret replication policy](https://docs.cloud.google.com/secret-manager/docs/choosing-replication), [Secret Manager pricing](https://cloud.google.com/secret-manager/pricing)).
- Automatic replication needs `global` to be allowed by the resource locations organization policy. For strict data residency, use regional secrets ([Choose a secret replication policy](https://docs.cloud.google.com/secret-manager/docs/choosing-replication), [Secret Manager best practices](https://docs.cloud.google.com/secret-manager/docs/best-practices)).
- A rotation schedule only sends `SECRET_ROTATE` messages to Pub/Sub. You must build the subscriber that creates the new version ([Create rotation schedules](https://docs.cloud.google.com/secret-manager/docs/secret-rotation)).
- Enable Data Access audit logs to record `AccessSecretVersion` calls ([Secret Manager best practices](https://docs.cloud.google.com/secret-manager/docs/best-practices)).
- Let workloads read secrets with an attached service account or Workload Identity Federation. Google prefers these methods over an exported service account key ([Secret Manager best practices](https://docs.cloud.google.com/secret-manager/docs/best-practices)).

## AWS mapping

| AWS | Google Cloud | Difference that matters |
|---|---|---|
| AWS Key Management Service (KMS) | Cloud KMS, with Cloud HSM for hardware keys | A CMEK must be in the same location as the resource. HSM keys use the same Cloud KMS API, and Google manages the HSM cluster. |
| AWS KMS External Key Store (XKS), AWS CloudHSM with custom key store | Cloud EKM | Key Access Justifications can add a reason code to each request, with Assured Workloads. |
| AWS Secrets Manager, AWS Systems Manager Parameter Store | Secret Manager | A rotation schedule only sends Pub/Sub messages. You write the rotation code. |
| AWS Private Certificate Authority | Certificate Authority Service | CA keys can be in Cloud HSM. |
| AWS Nitro Enclaves | Confidential Computing (Confidential VM, Confidential Space) | Confidential VM protects a whole VM. Confidential Space supports multi-party data sharing. |

Sources: [Compare AWS and Azure services to Google Cloud](https://docs.cloud.google.com/docs/get-started/aws-azure-gcp-service-comparison), [Cloud KMS locations](https://docs.cloud.google.com/kms/docs/locations), [Cloud HSM](https://docs.cloud.google.com/kms/docs/hsm), [Create rotation schedules](https://docs.cloud.google.com/secret-manager/docs/secret-rotation), [Key Access Justifications overview](https://docs.cloud.google.com/assured-workloads/key-access-justifications/docs/overview), [CA Service overview](https://docs.cloud.google.com/certificate-authority-service/docs/ca-service-overview), [Confidential Space overview](https://docs.cloud.google.com/confidential-computing/confidential-space/docs/confidential-space-overview).

## Exam traps

- **"Rotate the key to re-encrypt the old data."** Rotation only adds a new primary version. You must rewrite the data to re-encrypt it ([Key rotation](https://docs.cloud.google.com/kms/docs/key-rotation)).
- **"Disable the key version to stop access immediately."** Disabling is eventually consistent. The consistency page says to also remove the IAM role on the key ([Cloud KMS resource consistency](https://docs.cloud.google.com/kms/docs/consistency)).
- **"Grant the developers the Encrypter/Decrypter role on the key."** The service agent needs the role. People who create or read the resource do not ([CMEK](https://docs.cloud.google.com/kms/docs/cmek)).
- **"Use a key in the `global` location for a regional bucket."** A CMEK must be in the same exact location as the resource ([Cloud KMS locations](https://docs.cloud.google.com/kms/docs/locations)).
- **"Use CSEK for new Compute Engine disks."** CSEK for Compute Engine is deprecated and blocked for new resources. Use CMEK ([Deprecation of CSEK in Compute Engine](https://docs.cloud.google.com/compute/docs/deprecations/csek-deprecation-in-compute-engine)).
- **"Store the database password in Cloud KMS."** Cloud KMS does not return key material. Store the password in Secret Manager ([Secret Manager overview](https://docs.cloud.google.com/secret-manager/docs/overview)).
- **"Set only `restrictCmekCryptoKeyProjects` to require CMEK."** That constraint alone does not require CMEK. Also set `restrictNonCmekServices` ([CMEK organization policies](https://docs.cloud.google.com/kms/docs/cmek-org-policy)).
- **"Cloud EKM caches the key, so an outage of the key manager does not matter."** External keys are never cached in Google Cloud. An outage blocks decryption ([Cloud EKM](https://docs.cloud.google.com/kms/docs/ekm)).
