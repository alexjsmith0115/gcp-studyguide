## Why it matters

By default, a VM without an external IP address can reach only its own VPC network. The architect chooses how each workload reaches Google APIs, the internet, managed services such as Cloud SQL, and VPC resources from serverless code. The exam tests this choice, and the DNS, route, and firewall details that make each path work.

## Key points

- The private options for services are Private Service Connect (PSC), Private Google Access, private services access, and VPC Network Peering. They operate independently of each other ([Private access options for services](https://docs.cloud.google.com/vpc/docs/private-access-options)).
- Private Google Access is a per-subnet setting. It lets VMs without external IP addresses reach Google APIs and services ([Private Google Access](https://docs.cloud.google.com/vpc/docs/private-google-access)).
- Traffic to Google APIs uses routes with the default internet gateway as next hop, but it stays in Google's network. Routing it through VMs or custom next hops isn't supported ([Configure Private Google Access](https://docs.cloud.google.com/vpc/docs/configure-private-google-access)).
- `restricted.googleapis.com` and the PSC `vpc-sc` bundle allow only APIs that support VPC Service Controls. `private.googleapis.com` and the `all-apis` bundle allow most Google APIs ([About accessing global Google APIs through endpoints](https://docs.cloud.google.com/vpc/docs/about-accessing-google-apis-endpoints)).
- A PSC endpoint for Google APIs is one internal IPv4 address that you choose. On-premises hosts can use it, but peered VPC networks can't ([Access global Google APIs through endpoints](https://docs.cloud.google.com/vpc/docs/configure-private-service-connect-apis)).
- Cloud NAT is software-defined, not a proxy VM. Public NAT serves the internet. Private NAT serves private networks, also with overlapping ranges. Neither allows unsolicited inbound connections ([Cloud NAT overview](https://docs.cloud.google.com/nat/docs/overview)).
- Private services access connects your VPC network to a producer VPC network through VPC Network Peering. Peered VPC networks can't use the connection, because peering isn't transitive ([Private services access](https://docs.cloud.google.com/vpc/docs/private-services-access)).
- Cloud SQL offers private services access for one VPC network, and PSC for many VPC networks, projects, or organizations ([Choose how to connect to Cloud SQL](https://docs.cloud.google.com/sql/docs/mysql/connection-options)).
- Direct VPC egress is the recommended way for Cloud Run to reach a VPC network. Compared with a connector, it has lower latency, higher throughput, and no VM charges ([Compare Direct VPC egress and VPC connectors](https://docs.cloud.google.com/run/docs/configuring/connecting-vpc)).
- Connectivity Tests checks the configuration between two endpoints. Performance Dashboard shows packet loss and latency over time ([Connectivity Tests overview](https://docs.cloud.google.com/network-intelligence-center/docs/connectivity-tests/concepts/overview), [Performance Dashboard overview](https://docs.cloud.google.com/network-intelligence-center/docs/performance-dashboard/concepts/overview)).

## Choose the access path

Start from the destination. Then check the security constraint in the scenario.

| The workload must reach | Use | Not this |
|---|---|---|
| Google APIs, from VMs without external IP addresses | Private Google Access | Cloud NAT. API traffic uses Private Google Access even with Public NAT. |
| Google APIs, through an internal address that you choose | PSC endpoint for Google APIs | The public API addresses |
| Only APIs that VPC Service Controls supports | `restricted.googleapis.com` or the `vpc-sc` bundle | `private.googleapis.com` or `all-apis` |
| Regional endpoints (`*.rep.googleapis.com`) | PSC endpoint for regional Google APIs | Private Google Access |
| The internet, outbound only | Public NAT | An external IP address on each VM |
| The internet, with hostname or URL rules | Secure Web Proxy ([network security](note:2.1-network-security)) | Cloud NAT alone |
| A private network with overlapping ranges | Private NAT | Public NAT |
| Cloud SQL, AlloyDB, or Memorystore, from one VPC network | Private services access or PSC | A public IP address |
| A managed service, from many VPC networks | PSC endpoints, often created by a service connection policy | Private services access |
| A third-party service published with PSC | PSC endpoint or backend ([network design](note:1.3-network-design)) | The public internet |
| VPC resources, from Cloud Run | Direct VPC egress | A Serverless VPC Access connector as the default |

Sources: [Private access options for services](https://docs.cloud.google.com/vpc/docs/private-access-options), [Private Google Access](https://docs.cloud.google.com/vpc/docs/private-google-access), [About accessing global Google APIs through endpoints](https://docs.cloud.google.com/vpc/docs/about-accessing-google-apis-endpoints), [Cloud NAT overview](https://docs.cloud.google.com/nat/docs/overview), [Access regional and multi-regional Google APIs through endpoints](https://docs.cloud.google.com/vpc/docs/access-regional-google-apis-endpoints), [Secure Web Proxy overview](https://docs.cloud.google.com/secure-web-proxy/docs/overview), [Private services access](https://docs.cloud.google.com/vpc/docs/private-services-access), [Choose how to connect to Cloud SQL](https://docs.cloud.google.com/sql/docs/mysql/connection-options), [Compare Direct VPC egress and VPC connectors](https://docs.cloud.google.com/run/docs/configuring/connecting-vpc).

## Private Google Access

Private Google Access needs the subnet setting and an interface without an external IP address. Routes and egress rules must also allow the traffic ([Configure Private Google Access](https://docs.cloud.google.com/vpc/docs/configure-private-google-access)).

| Domain | Addresses | APIs | Choose it when |
|---|---|---|---|
| Default domains | Various public ranges | Most Google APIs, plus Google Workspace web apps | You want no DNS changes |
| `private.googleapis.com` | `199.36.153.8/30` | Most Google APIs | You don't use VPC Service Controls, or you also need APIs that it doesn't support |
| `restricted.googleapis.com` | `199.36.153.4/30` | Only APIs that support VPC Service Controls | You want extra protection against data exfiltration |

Sources: [Configure Private Google Access](https://docs.cloud.google.com/vpc/docs/configure-private-google-access).

Rules for the two VIP domains ([Configure Private Google Access](https://docs.cloud.google.com/vpc/docs/configure-private-google-access)):

- Create a private DNS zone for `googleapis.com`, with `A` records for the VIP and a `CNAME` for `*.googleapis.com`. Do the same for other domains, such as `*.gcr.io` and `*.pkg.dev` for GKE.
- Don't mix `private` and `restricted` addresses. The mix can cause intermittent failures.
- The VIPs support only HTTP-based protocols over TCP.
- If you replace the default route, add routes for the VIP range with the default internet gateway as next hop. Routes and egress rules must also allow `34.126.0.0/18`, which some services use for direct connectivity.

VPC Service Controls enforces its perimeter for supported services on every domain. `restricted.googleapis.com` adds protection because it blocks the other services ([Set up private connectivity to Google APIs and services](https://docs.cloud.google.com/vpc-service-controls/docs/set-up-private-connectivity)). The perimeter design is on the [security controls](note:3.1-security-controls) page. On-premises hosts can use the VIPs over hybrid links; see [hybrid connectivity](note:2.1-hybrid-multicloud).

## PSC endpoints for Google APIs

A PSC endpoint for Google APIs is a global forwarding rule with one internal IPv4 address outside your subnet ranges. Service Directory creates DNS names such as `storage-xyz.p.googleapis.com` for an endpoint named `xyz`. For default names such as `storage.googleapis.com`, you create the DNS records ([About accessing global Google APIs through endpoints](https://docs.cloud.google.com/vpc/docs/about-accessing-google-apis-endpoints); [Access global Google APIs through endpoints](https://docs.cloud.google.com/vpc/docs/configure-private-service-connect-apis)).

| Need | Private Google Access | PSC endpoint |
|---|---|---|
| Traffic control from on-premises | One VIP range for all APIs | Several endpoints, each advertised over a different VLAN attachment |
| Peered VPC networks | Each network turns on its own subnets | Peered networks can't reach the endpoint |

Sources: [About accessing global Google APIs through endpoints](https://docs.cloud.google.com/vpc/docs/about-accessing-google-apis-endpoints), [Access global Google APIs through endpoints](https://docs.cloud.google.com/vpc/docs/configure-private-service-connect-apis), [Private Google Access](https://docs.cloud.google.com/vpc/docs/private-google-access), [Configure Private Google Access](https://docs.cloud.google.com/vpc/docs/configure-private-google-access).

A VM without an external IP address still needs Private Google Access on its subnet to use an endpoint. A firewall rule that denies all internet egress doesn't block traffic to the endpoint ([Access global Google APIs through endpoints](https://docs.cloud.google.com/vpc/docs/configure-private-service-connect-apis); [About accessing global Google APIs through endpoints](https://docs.cloud.google.com/vpc/docs/about-accessing-google-apis-endpoints)).

## Cloud NAT

| | Public NAT | Private NAT |
|---|---|---|
| Destinations | The internet | NCC VPC spokes, and on-premises or other clouds (Hybrid NAT) |
| Source addresses after NAT | External IP addresses, allocated automatically or assigned manually | Addresses from a subnet with purpose `PRIVATE_NAT` |
| Typical reason | Updates and third-party APIs; fixed addresses for partner allowlists | Overlapping subnet ranges |

Sources: [Cloud NAT overview](https://docs.cloud.google.com/nat/docs/overview), [Private NAT](https://docs.cloud.google.com/nat/docs/private-nat).

Design rules:

- A gateway serves one VPC network and region, through one Cloud Router. Packets don't pass through the gateway or the router ([Public NAT](https://docs.cloud.google.com/nat/docs/public-nat)).
- A gateway can't serve VMs in a peered VPC network. For Shared VPC, create gateways in the host project ([Cloud NAT product interactions](https://docs.cloud.google.com/nat/docs/nat-product-interactions)).
- When Public NAT serves a subnet range, Private Google Access is on for that range, and you can't turn it off ([Cloud NAT product interactions](https://docs.cloud.google.com/nat/docs/nat-product-interactions)).
- Public NAT uses only routes with the default internet gateway as next hop. It can't use a `0.0.0.0/0` route learned from on-premises ([Cloud NAT product interactions](https://docs.cloud.google.com/nat/docs/nat-product-interactions)).
- For a private GKE cluster, the gateway must cover the node, Pod, and Service ranges of the subnet ([Cloud NAT product interactions](https://docs.cloud.google.com/nat/docs/nat-product-interactions)).
- With Private NAT, a VM can reach only the non-overlapping subnets of the connected network ([Private NAT](https://docs.cloud.google.com/nat/docs/private-nat)).

## Managed services in producer networks

Many managed services run in a producer VPC network that Google or a vendor manages. With private services access, you allocate a range, and the producer network peers with your network. Only one consumer VPC network can connect to a service instance ([Private services access](https://docs.cloud.google.com/vpc/docs/private-services-access)). With PSC service connectivity automation, a service connection policy lets the service create PSC endpoints in your subnet ([About service connection policies](https://docs.cloud.google.com/vpc/docs/about-service-connection-policies)).

Plan private services access with care:

- For Google services, the minimum allocated range is `/24`, and Google recommends `/16`. You can't change an allocated range later, but you can add other ranges to the connection ([Configure private services access](https://docs.cloud.google.com/vpc/docs/configure-private-services-access); [Private services access](https://docs.cloud.google.com/vpc/docs/private-services-access)).
- With Shared VPC, create the allocated range and the connection in the host project ([Private services access](https://docs.cloud.google.com/vpc/docs/private-services-access)).
- On-premises hosts can't reach the producer network by default. Export custom routes on the peering, and advertise the allocated range to on-premises ([Configure private services access](https://docs.cloud.google.com/vpc/docs/configure-private-services-access)).
- Cloud SQL doesn't support DNS peering over private services access ([Configure private services access](https://docs.cloud.google.com/vpc/docs/configure-private-services-access)).

| Service | Private options | What decides |
|---|---|---|
| Cloud SQL | Private services access, PSC, or both | PSC-only instances don't support external replicas, the write endpoint, or client IP visibility. PSC reaches many VPC networks, projects, or organizations. |
| Memorystore for Redis | Direct peering (default) or private services access | Shared VPC and on-premises access over VPN need private services access. |
| Memorystore for Valkey, Memorystore for Redis Cluster | PSC only: a service connection policy (recommended) or user-registered PSC connections | No peering option. |
| AlloyDB for PostgreSQL | Private services access or PSC | Both models are supported. |

Sources: [Choose how to connect to Cloud SQL](https://docs.cloud.google.com/sql/docs/mysql/connection-options), [Memorystore for Redis networking](https://docs.cloud.google.com/memorystore/docs/redis/networking), [Memorystore for Valkey networking](https://docs.cloud.google.com/memorystore/docs/valkey/networking), [Memorystore for Redis Cluster networking](https://docs.cloud.google.com/memorystore/docs/cluster/networking), [Private services access](https://docs.cloud.google.com/vpc/docs/private-services-access), [Private Service Connect compatibility](https://docs.cloud.google.com/vpc/docs/private-service-connect-compatibility).

The PSC producer and consumer model is on the [network design](note:1.3-network-design) page. Database settings are on the [database configuration](note:2.2-database-config) page.

## Cloud DNS in the access path

Every private path depends on DNS. Choose the zone type by its job.

| Zone or policy | What it does | Use it for |
|---|---|---|
| Private zone | Serves records only to the VPC networks that you authorize | Internal names; `googleapis.com` records for the VIPs |
| Forwarding zone | Sends queries for a domain to other name servers | Names that other DNS servers own |
| Peering zone | Sends queries to the Cloud DNS zones of another VPC network | Hub-and-spoke DNS |
| Response policy | Rules that change the answers for matching names; at most one policy per network | Overriding selected names, including wildcards, with passthru rules for exceptions |

Sources: [DNS zones overview](https://docs.cloud.google.com/dns/docs/zones/zones-overview), [Cloud DNS overview](https://docs.cloud.google.com/dns/docs/overview), [Configure Private Google Access](https://docs.cloud.google.com/vpc/docs/configure-private-google-access), [Best practices for Cloud DNS](https://docs.cloud.google.com/dns/docs/best-practices), [Manage response policies and rules](https://docs.cloud.google.com/dns/docs/zones/manage-response-policies).

Design rules:

- DNS peering is one-way, and it is separate from VPC Network Peering. It allows only one transitive hop ([DNS zones overview](https://docs.cloud.google.com/dns/docs/zones/zones-overview)).
- Cloud DNS can't use transitive routing to reach a forwarding target in a peered network. Use a peering zone to the network that has the route ([DNS zones overview](https://docs.cloud.google.com/dns/docs/zones/zones-overview)).
- For Shared VPC, create zones in the host project ([Cloud DNS overview](https://docs.cloud.google.com/dns/docs/overview)).

For on-premises names, Google recommends one VPC network that forwards to on-premises, and peering zones to it from the other networks ([Best practices for Cloud DNS](https://docs.cloud.google.com/dns/docs/best-practices)). Inbound server policies and the full hybrid design are on the [hybrid connectivity](note:2.1-hybrid-multicloud) page.

## Serverless egress to a VPC network

| | Direct VPC egress | Serverless VPC Access connector |
|---|---|---|
| Performance | Lower latency, higher throughput | Higher latency, lower throughput |
| Cost | Network traffic charges only | Connector instances are billed as VMs |
| IP addresses | About 2 per instance; subnet `/26` or larger | A `/28` range; 2 to 10 instances that don't scale in |

Sources: [Compare Direct VPC egress and VPC connectors](https://docs.cloud.google.com/run/docs/configuring/connecting-vpc), [Direct VPC with a VPC network](https://docs.cloud.google.com/run/docs/configuring/vpc-direct-vpc), [Send serverless traffic to a VPC network](https://docs.cloud.google.com/vpc/docs/serverless-vpc-access).

To use Public NAT, set egress to `all-traffic`. The `private-ranges-only` setting sends only traffic to internal addresses through the VPC network ([Direct VPC with a VPC network](https://docs.cloud.google.com/run/docs/configuring/vpc-direct-vpc); [Cloud NAT product interactions](https://docs.cloud.google.com/nat/docs/nat-product-interactions)). With Cloud NAT, Direct VPC egress can add 30 seconds or more to cold starts. For better startup performance in that case, the docs recommend a connector ([Direct VPC with a VPC network](https://docs.cloud.google.com/run/docs/configuring/vpc-direct-vpc)). Configuration details are on the [serverless](note:2.3-serverless) page.

## Troubleshoot with Network Intelligence Center

| Question | Tool |
|---|---|
| Does the configuration let A reach B? Which rule or route drops the packet? | Connectivity Tests |
| Is the problem in my application or in the network? | Performance Dashboard |
| What connects to what, and with what throughput? | Network Topology |
| Which configurations are wrong or suboptimal? | Network Analyzer |
| Which flows carry my traffic, without SQL queries? | Flow Analyzer, which reads VPC Flow Logs |

Sources: [Network Intelligence Center overview](https://docs.cloud.google.com/network-intelligence-center/docs/overview), [Performance Dashboard overview](https://docs.cloud.google.com/network-intelligence-center/docs/performance-dashboard/concepts/overview).

Connectivity Tests simulates the packet path through VPC networks, Cloud VPN tunnels, and VLAN attachments. For Google-managed services such as Cloud SQL, it gives only an overall result. A "could be delivered" result doesn't guarantee delivery on the data plane. For continuous monitoring, use Performance Dashboard ([Connectivity Tests overview](https://docs.cloud.google.com/network-intelligence-center/docs/connectivity-tests/concepts/overview)).

## Exam traps

- **"Turn on Private Google Access so that VMs can download packages from the internet."** Private Google Access reaches only Google APIs and services. Use Cloud NAT for the internet ([Private access options for services](https://docs.cloud.google.com/vpc/docs/private-access-options), [Cloud NAT overview](https://docs.cloud.google.com/nat/docs/overview)).
- **Private Google Access for VMs with external IP addresses.** It has no effect on them ([Private Google Access](https://docs.cloud.google.com/vpc/docs/private-google-access)).
- **A PSC endpoint without Private Google Access.** VMs without external IP addresses still need Private Google Access on their subnet ([Access global Google APIs through endpoints](https://docs.cloud.google.com/vpc/docs/configure-private-service-connect-apis)).
- **One PSC endpoint in a hub for all peered spokes.** Peered VPC networks can't reach the endpoint ([Access global Google APIs through endpoints](https://docs.cloud.google.com/vpc/docs/configure-private-service-connect-apis)).
- **`restricted.googleapis.com` for a workload that also needs unsupported APIs.** The restricted VIP blocks them. Use `private.googleapis.com` ([Configure Private Google Access](https://docs.cloud.google.com/vpc/docs/configure-private-google-access)).
- **One Cloud NAT gateway for peered networks.** A gateway serves only its own VPC network ([Cloud NAT product interactions](https://docs.cloud.google.com/nat/docs/nat-product-interactions)).
- **Cloud NAT for inbound traffic.** Cloud NAT allows only responses to outbound connections. Use a [load balancer](note:1.3-load-balancing) for inbound traffic ([Cloud NAT overview](https://docs.cloud.google.com/nat/docs/overview), [Cloud NAT product interactions](https://docs.cloud.google.com/nat/docs/nat-product-interactions)).
- **Cloud SQL from a peered network or from on-premises "just works".** Private services access isn't transitive. On-premises access needs exported custom routes and an advertised allocated range ([Configure private services access](https://docs.cloud.google.com/vpc/docs/configure-private-services-access)).
- **A small allocated range "to save addresses".** Google recommends `/16`. You can't change an allocated range later. You can add other ranges to the connection ([Configure private services access](https://docs.cloud.google.com/vpc/docs/configure-private-services-access), [Private services access](https://docs.cloud.google.com/vpc/docs/private-services-access)).
- **A Serverless VPC Access connector that scales down after a peak.** Connectors don't scale in ([Send serverless traffic to a VPC network](https://docs.cloud.google.com/vpc/docs/serverless-vpc-access)).
