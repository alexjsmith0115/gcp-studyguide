## Why it matters

The architect decides how many failure domains a workload uses. More failure domains cost more and add operational complexity. Exam scenarios give an availability target, a latency need, a budget, or a residency rule. The correct answer meets the target with the least cost and complexity, not with the most redundancy.

## Key points

- A zone is a single failure domain inside a region. A region has three or more zones. Deploy across zones for high availability, and across regions for region outages ([Geography and regions](https://docs.cloud.google.com/docs/geography-and-regions)).
- Google Cloud infrastructure targets 99.9% availability in one zone, 99.99% across zones, and 99.999% across regions. These are platform targets, not product SLAs ([Building blocks of reliability](https://docs.cloud.google.com/architecture/infra-reliability-guide/building-blocks)).
- The Architecture Center defines six deployment archetypes: zonal, regional, multi-regional, global, hybrid, and multicloud. Hybrid and multicloud contain one of the four basic archetypes ([Google Cloud deployment archetypes](https://docs.cloud.google.com/architecture/deployment-archetypes)).
- Tiers in series multiply. Three interdependent tiers at 99.9% each give about 99.7% ([Building blocks of reliability](https://docs.cloud.google.com/architecture/infra-reliability-guide/building-blocks)).
- Redundant copies in separate failure domains increase availability, but the target of the deployment location caps the result ([Building blocks of reliability](https://docs.cloud.google.com/architecture/infra-reliability-guide/building-blocks)).
- A global resource survives zone and region outages. A configuration error can still make it a single point of failure (SPOF) ([Building blocks of reliability](https://docs.cloud.google.com/architecture/infra-reliability-guide/building-blocks)).
- Autoscaling needs stateless instances. The Compute Engine autoscaler does not work with managed instance groups (MIGs) that have a stateful configuration ([Autoscaling groups of instances](https://docs.cloud.google.com/compute/docs/autoscaler)).
- Premium Tier is the default network tier, and global load balancers and Cloud CDN need it. Standard Tier costs less and suits regional, latency-tolerant workloads ([Network Service Tiers overview](https://docs.cloud.google.com/network-tiers/docs/overview)).
- A cache in the load balancer decreases latency. Users can also get cached content when the origin servers are down ([Assess reliability requirements](https://docs.cloud.google.com/architecture/infra-reliability-guide/requirements)).
- High availability does not replace backups. Set the backup frequency from the recovery point objective (RPO), and test restores ([Perform testing for recovery from data loss](https://docs.cloud.google.com/architecture/framework/reliability/perform-testing-for-recovery-from-data-loss)).

## Failure domains and location scopes

The location scope of a resource tells you which failure can affect it ([Building blocks of reliability](https://docs.cloud.google.com/architecture/infra-reliability-guide/building-blocks)).

| Location scope | Examples | Resilience | How to reduce outage impact |
|---|---|---|---|
| Zonal | Compute Engine VMs, zonal MIGs, Hyperdisk volumes, Cloud SQL instances | Low | Deploy redundantly in multiple zones or regions |
| Regional | Regional MIGs, regional buckets, regional GKE clusters, VPC subnets, Cloud Run services | Medium | Deploy redundantly in multiple regions |
| Multi-region | Dual-region and multi-region buckets, multi-region Spanner | High | Manage changes carefully; add defense-in-depth fallbacks |
| Global | VPC networks, Cloud DNS zones, global external Application Load Balancers, Pub/Sub topics | High | Manage changes carefully; add defense-in-depth fallbacks |

Sources: [Building blocks of reliability](https://docs.cloud.google.com/architecture/infra-reliability-guide/building-blocks).

An archetype is not a location scope. A VM is zonal, but VMs in several zones give a regional architecture ([Google Cloud deployment archetypes](https://docs.cloud.google.com/architecture/deployment-archetypes)). Some regions, such as Stockholm and Osaka, have three zones in only one or two physical data centers ([Geography and regions](https://docs.cloud.google.com/docs/geography-and-regions)).

## Choose a deployment archetype

Choose the archetype first, because it simplifies later product decisions. For example, the regional archetype points to a regional GKE cluster ([Google Cloud deployment archetypes](https://docs.cloud.google.com/architecture/deployment-archetypes)).

| Design consideration | Zonal | Regional | Multi-regional | Global |
|---|---|---|---|---|
| Infrastructure availability target | 99.9% | 99.99% | 99.999% | 99.999% |
| Zone outage | RTO of hours or days | Near-zero RTO* | Near-zero RTO* | Near-zero RTO* |
| Region outage | RTO of hours or days | RTO of hours or days | Near-zero RTO* | Near-zero RTO* |
| Cost of resources | Low | Medium | High | Medium |
| Operational complexity | Lowest | More than zonal | More than regional | Can be less than multi-regional |

\* If data replication is synchronous. Sources: [Comparative analysis of deployment archetypes](https://docs.cloud.google.com/architecture/deployment-archetypes/comparison).

| Archetype | Use it when | Watch for |
|---|---|---|
| Zonal | Development and test; apps that tolerate downtime; batch jobs that need low-latency links; license-restricted software | Downtime in a zone outage; keep a passive replica in a second zone |
| Regional | High availability for users in one geographic area; data residency | Downtime in a region outage; back up to another region |
| Multi-regional | Business-critical apps; users across a continent; residency through a geofenced DNS policy | Cross-region transfer and replication cost; complexity |
| Global | Users worldwide; fewer resources with a global load balancer and database | Transfer cost; careful change control of global resources |
| Hybrid | DR site for on-premises apps; progressive migration; cloud bursting | Setup effort; network connection; redundant resources |
| Multicloud | Another cloud as the DR site; Google Cloud analytics or AI for apps in another cloud | Redundant data; cross-cloud traffic; different security tools |

Sources: [Google Cloud deployment archetypes](https://docs.cloud.google.com/architecture/deployment-archetypes), [Zonal](https://docs.cloud.google.com/architecture/deployment-archetypes/zonal), [Regional](https://docs.cloud.google.com/architecture/deployment-archetypes/regional), [Multi-regional](https://docs.cloud.google.com/architecture/deployment-archetypes/multiregional), [Global](https://docs.cloud.google.com/architecture/deployment-archetypes/global), [Hybrid](https://docs.cloud.google.com/architecture/deployment-archetypes/hybrid), [Multicloud](https://docs.cloud.google.com/architecture/deployment-archetypes/multicloud).

Decision rules for exam scenarios:

- "A zone outage must not stop the app" → regional or higher.
- "A region outage must not stop the app" with a near-zero RTO → multi-regional or global, with synchronous replication.
- "Users worldwide" → global, with a global anycast load balancer.
- "Data must stay in one country" → regional in that country, or multi-regional with a geofenced DNS routing policy.
- "Internal app for employees in one area" → regional is often enough when cost has priority over availability ([Google Cloud deployment archetypes](https://docs.cloud.google.com/architecture/deployment-archetypes)).
- Hybrid or multicloud with critical cross-environment dependencies → availability is below the least available component in any environment ([Comparative analysis of deployment archetypes](https://docs.cloud.google.com/architecture/deployment-archetypes/comparison)).

## Composite availability

Use two rules and one cap ([Building blocks of reliability](https://docs.cloud.google.com/architecture/infra-reliability-guide/building-blocks)):

1. **Tiers in series:** multiply the availability of each tier. The stack is less available than its weakest tier.
2. **Redundant copies in parallel:** multiply the failure probabilities. Two 99.9% copies in separate failure domains give 1 − (0.001 × 0.001) = 99.9999% in theory.
3. **Location cap:** the result cannot exceed 99.9% for one zone, 99.99% for multiple zones, or 99.999% for multiple regions.

The reliability guide calculates four versions of one three-tier stack:

| Design | Calculation | Aggregate | Maximum downtime per 30 days |
|---|---|---|---|
| One zone: regional external Application Load Balancer, zonal MIGs, internal load balancer, Cloud SQL (Enterprise edition, HA) | 0.9999 × 0.999 × 0.9999 × 0.999 × 0.9995 | 99.73% | About 1 hour 57 minutes |
| Multiple zones: the same stack on regional MIGs | 0.9999 × 0.9999 × 0.9999 × 0.9999 × 0.9995 | 99.91% | About 39 minutes |
| Two regions: regional load balancers, Cloud DNS routing policy, multi-region Spanner | 0.99999 × 1 × 0.99999 | 99.998% | About 52 seconds |
| Two regions: global external Application Load Balancer, multi-region Spanner | 0.99999 × 0.9999 × 0.99999 | 99.988% | About 5 minutes 11 seconds |

Sources: [Design reliable infrastructure](https://docs.cloud.google.com/architecture/infra-reliability-guide/design).

In two-region rows, the first factor is the compute stack after the 99.999% cap. Lessons:

- The weakest serial component limits the stack. In the multi-zone row, Cloud SQL at 99.95% keeps the stack below 99.95%. For a higher target, choose Cloud SQL Enterprise Plus edition (99.99%), AlloyDB with HA (99.99%), or multi-region Spanner (99.999%) ([Building blocks of reliability](https://docs.cloud.google.com/architecture/infra-reliability-guide/building-blocks), [Cloud SQL editions overview](https://docs.cloud.google.com/sql/docs/postgres/editions-intro)).
- Fewer interdependent tiers give higher availability ([Building blocks of reliability](https://docs.cloud.google.com/architecture/infra-reliability-guide/building-blocks)).
- The numbers cover infrastructure only; app design and processes also count ([Design reliable infrastructure](https://docs.cloud.google.com/architecture/infra-reliability-guide/design)).

## Failover design

Failover works only when every tier has redundancy, health checks detect the failure, and the surviving location has enough capacity.

| Failure | Mechanism | Failover |
|---|---|---|
| The app on a VM stops responding | Health checks stop traffic to it; MIG autohealing re-creates the VM | Automatic |
| Zone outage, compute | A regional MIG keeps VMs in the other zones | Automatic |
| Zone outage, Cloud SQL with HA | Cloud SQL fails over to the standby in another zone | Automatic |
| Zone outage, zonal archetype | You promote the failover-zone database and update the load balancer | Manual |
| Region outage, regional load balancers | A Cloud DNS routing policy with health checks sends traffic to the other region | Automatic (DNS) |
| Region outage, global external Application Load Balancer | The load balancer sends requests to the healthy region | Automatic |
| Global load balancer outage or configuration error | Cloud DNS sends traffic to regional external Application Load Balancers | Automatic (DNS) |

Sources: [Manage traffic and load](https://docs.cloud.google.com/architecture/infra-reliability-guide/traffic-load), [Design reliable infrastructure](https://docs.cloud.google.com/architecture/infra-reliability-guide/design), [Zonal deployment archetype](https://docs.cloud.google.com/architecture/deployment-archetypes/zonal), [Failover for global external Application Load Balancers](https://docs.cloud.google.com/load-balancing/docs/https/global-applb-failover-overview).

Design rules:

- **Plan spare capacity.** For N+1 redundancy, each component needs at least one instance more than the forecast load requires ([Manage traffic and load](https://docs.cloud.google.com/architecture/infra-reliability-guide/traffic-load)). In multi-region designs, reserve capacity in all regions, or accept the risk of emergency autoscaling ([Design reliable infrastructure](https://docs.cloud.google.com/architecture/infra-reliability-guide/design)). To save cost, run a passive failover region with fewer resources ([Regional deployment archetype](https://docs.cloud.google.com/architecture/deployment-archetypes/regional)).
- **Protect global resources.** Manage their configuration changes carefully. For exceptionally high availability, add regional load balancers as defense-in-depth fallbacks ([Building blocks of reliability](https://docs.cloud.google.com/architecture/infra-reliability-guide/building-blocks)). The failover guide recommends the active-active (bypass) strategy unless the app needs capacity-based global backend load balancing ([Failover for global external Application Load Balancers](https://docs.cloud.google.com/load-balancing/docs/https/global-applb-failover-overview)).
- **Know the geofence trade-off.** With a geofenced geolocation policy, Cloud DNS does not fail over to the next closest geolocation ([DNS routing policies and health checks](https://docs.cloud.google.com/dns/docs/routing-policies-overview)).
- **Test failover.** Simulate failures regularly ([Build highly available systems through resource redundancy](https://docs.cloud.google.com/architecture/framework/reliability/build-highly-available-systems)).

## Scalability and elasticity

Scale horizontally. Vertical scaling has hard limits, costs more for large machines, and a large VM can become a SPOF ([Take advantage of horizontal scalability](https://docs.cloud.google.com/architecture/framework/reliability/horizontal-scalability)).

**Stateless design comes first.** A stateless service keeps no local persistent data, so the autoscaler can create and destroy instances without data loss. Separate the services that must keep state from the stateless ones ([Patterns for scalable and resilient apps](https://docs.cloud.google.com/architecture/scalable-and-resilient-apps)). Memorystore lists session management as a common caching use ([Memorystore for Redis overview](https://docs.cloud.google.com/memorystore/docs/redis/memorystore-for-redis-overview)).

| Autoscaler feature | Use it for | Note |
|---|---|---|
| Utilization signals: CPU, load balancer serving capacity, Cloud Monitoring metrics | Unpredictable load | With several signals, the largest recommended size wins |
| Schedules | Known, recurring peaks | Sets a minimum number of VMs for a time window |
| Predictive autoscaling | Daily or weekly cycles; initialization longer than 2 minutes | Scales out before the forecast load |
| Scale-in controls | Spikes that follow soon after drops | Limits how fast the group shrinks |

Sources: [Autoscaling groups of instances](https://docs.cloud.google.com/compute/docs/autoscaler), [Take advantage of elasticity](https://docs.cloud.google.com/architecture/framework/performance-optimization/elasticity).

The autoscaler does not work with unmanaged instance groups, stateful MIGs, or MIGs with VM repairs turned off ([Autoscaling groups of instances](https://docs.cloud.google.com/compute/docs/autoscaler)). For a known peak, such as a seasonal sale, scale up before the event. Reactive scaling can take several minutes ([Take advantage of elasticity](https://docs.cloud.google.com/architecture/framework/performance-optimization/elasticity)).

Managed services scale for you. Cloud Run scales in to zero, and GKE Autopilot scales nodes automatically ([Manage traffic and load](https://docs.cloud.google.com/architecture/infra-reliability-guide/traffic-load)). VMs and GKE nodes take time to start, so keep a baseline of them and use pre-baked images or containers ([Patterns for scalable and resilient apps](https://docs.cloud.google.com/architecture/scalable-and-resilient-apps)).

Capacity planning is part of scalability. Forecast the load and run load tests. Check quotas. Use reservations for assured Compute Engine capacity in a zone ([Manage traffic and load](https://docs.cloud.google.com/architecture/infra-reliability-guide/traffic-load)).

## Performance and latency

Put resources close to users. Keep the serving path on Google's network with Premium Tier, Cloud Load Balancing, Cloud CDN, and caches ([Best practices for Compute Engine regions selection](https://docs.cloud.google.com/solutions/best-practices-compute-engine-region-selection)).

| Deployment pattern | User latency | Complexity | Use when |
|---|---|---|---|
| One region, with Cloud CDN and global load balancing | Lower with edge caching and edge termination | Lowest | The gain from more regions does not justify the complexity |
| Frontends in several regions, backend in one region | Low when a request needs few backend calls | Medium | Frontend caching or asynchronous writes |
| Frontends and backends in several regions | Lowest; each region answers locally | High; all data replicated to every region | Global low latency, for example with multi-region Spanner |
| Parallel apps per geography | Low | Medium; little shared data | Country sites, game rooms, SaaS with a data location per account |

Sources: [Best practices for Compute Engine regions selection](https://docs.cloud.google.com/solutions/best-practices-compute-engine-region-selection).

| | Premium Tier | Standard Tier |
|---|---|---|
| Internet routing | Enters and exits Google's network at the point of presence (PoP) closest to the user | Uses ISP and transit networks near the region of the resource |
| Global IP addresses, global external Application Load Balancer, Cloud CDN | Supported | Not supported |
| Uptime SLA for VMs | 99.99% | 99.9% |
| Best for | Global users; backends in more than one region | Latency-tolerant apps in one region, at lower cost |

Sources: [Network Service Tiers overview](https://docs.cloud.google.com/network-tiers/docs/overview).

You choose the tier per resource, such as the external IP address of a load balancer. One project can use both tiers. If you are not sure, use Premium Tier ([Network Service Tiers overview](https://docs.cloud.google.com/network-tiers/docs/overview)).

| | Cloud CDN | Memorystore |
|---|---|---|
| Where it caches | At the Google edge, with a global external or classic Application Load Balancer | In memory, inside your VPC network |
| What to cache | Static and cacheable HTTP responses, never user-specific content | Sessions, frequent query results, leaderboards |
| Main design choices | Cache mode (`CACHE_ALL_STATIC` is the default); custom cache keys; versioned URLs instead of invalidation | Memorystore for Valkey, Redis Cluster, or Redis (Memcached is deprecated); replicas across zones |

Sources: [Cloud CDN overview](https://docs.cloud.google.com/cdn/docs/overview), [Content delivery best practices](https://docs.cloud.google.com/cdn/docs/best-practices), [Memorystore](https://docs.cloud.google.com/memorystore/docs), [Memorystore for Valkey overview](https://docs.cloud.google.com/memorystore/docs/valkey/product-overview), [Memorystore for Redis overview](https://docs.cloud.google.com/memorystore/docs/redis/memorystore-for-redis-overview).

A cache also adds resilience. If the storage layer is overloaded or unavailable, the cache can continue to serve requests ([Patterns for scalable and resilient apps](https://docs.cloud.google.com/architecture/scalable-and-resilient-apps)).

## Backup and recovery overview

Redundancy protects against infrastructure failure. Backups protect against data loss and corruption, for example from a software bug ([Perform testing for recovery from data loss](https://docs.cloud.google.com/architecture/framework/reliability/perform-testing-for-recovery-from-data-loss)).

- The recovery time objective (RTO) is the maximum acceptable time offline. The RPO is the maximum acceptable period of data loss. Smaller values cost more ([Disaster recovery planning guide](https://docs.cloud.google.com/architecture/dr-scenarios-planning-guide)).
- Back up at least as often as the RPO. Use point-in-time recovery for critical Cloud SQL data. Test restores in a non-production environment ([Perform testing for recovery from data loss](https://docs.cloud.google.com/architecture/framework/reliability/perform-testing-for-recovery-from-data-loss)).
- For zonal or regional storage, replicate data to another region or snapshot it to a multi-region location ([Geography and regions](https://docs.cloud.google.com/docs/geography-and-regions)).
- Backup and DR Service manages backups centrally. Its backup vault enforces write once, read many (WORM) immutability ([Backup and DR overview](https://docs.cloud.google.com/backup-disaster-recovery/docs/concepts/backup-dr)).

Detail lives in [Data protection](note:2.2-data-protection), [DR planning](note:4.1-disaster-recovery), [Database configuration](note:2.2-database-config), [Load balancers](note:1.3-load-balancing), [Compute platforms](note:1.3-compute-choice), and [the Well-Architected Framework](note:1.2-well-architected-framework).

## Exam traps

- **"Each tier has a 99.9% SLA, so the app has 99.9%."** Tiers in series multiply ([Building blocks of reliability](https://docs.cloud.google.com/architecture/infra-reliability-guide/building-blocks)).
- **"Add VMs in the same zone to reach 99.99%."** Redundancy inside one zone stays capped at the 99.9% zone target ([Building blocks of reliability](https://docs.cloud.google.com/architecture/infra-reliability-guide/building-blocks)).
- **"A global load balancer cannot be a SPOF."** A configuration error, such as a deleted forwarding rule, can stop it for all users ([Design reliable infrastructure](https://docs.cloud.google.com/architecture/infra-reliability-guide/design)).
- **"Use Standard Tier to cut the cost of a global load balancer or Cloud CDN."** Standard Tier supports neither ([Network Service Tiers overview](https://docs.cloud.google.com/network-tiers/docs/overview)).
- **"Session affinity makes a stateful app safe to autoscale."** Affinity is best effort. Adding or removing backends can break it ([Backend services overview](https://docs.cloud.google.com/load-balancing/docs/backend-service)).
- **"Autoscaling covers the Black Friday peak."** For known peaks, scale up in advance ([Take advantage of elasticity](https://docs.cloud.google.com/architecture/framework/performance-optimization/elasticity)).
- **"Multi-regional is always the best answer."** The archetype is a trade-off of availability, cost, and complexity ([Google Cloud deployment archetypes](https://docs.cloud.google.com/architecture/deployment-archetypes)).
- **"Replicas are my backup."** Recovery from data loss or corruption needs tested backups ([Perform testing for recovery from data loss](https://docs.cloud.google.com/architecture/framework/reliability/perform-testing-for-recovery-from-data-loss)).
