## Why it matters

Objective 4.1 asks how a team builds, tests, and ships software, and how it provisions new services. The exam describes a delivery problem, such as slow releases, a leaked credential, or a build that cannot reach a private server. You pick the Google-recommended practice and the correct Cloud Build, Artifact Registry, or provisioning configuration. Many wrong options use products that Google no longer offers to new customers.

## Key points

- DORA identifies the capabilities that improve software delivery. The technical capabilities include continuous integration, continuous delivery, trunk-based development, deployment automation, and test automation ([DevOps capabilities](https://docs.cloud.google.com/architecture/devops)).
- Cloud Source Repositories is not available to new customers since June 17, 2024. Connect GitHub, GitLab, or Bitbucket through Developer Connect or Cloud Build repositories (2nd gen) ([Cloud Build repositories](https://docs.cloud.google.com/build/docs/repositories)).
- Private pools are dedicated, fully managed build workers that can reach resources in a private network. The `constraints/cloudbuild.allowedWorkerPools` constraint stops builds from using the default pool ([Private pools overview](https://docs.cloud.google.com/build/docs/private-pools/private-pools-overview), [Using Cloud Build in a private network](https://docs.cloud.google.com/build/docs/private-pools/use-in-private-network)).
- New projects run builds as the Compute Engine default service account. The most secure option is a user-specified service account for manual and triggered builds ([Cloud Build default service account change](https://docs.cloud.google.com/build/docs/cloud-build-service-account-updates)).
- Secret Manager is the recommended way to give a build passwords and API keys. For new projects, do not use Cloud KMS encrypted credentials ([Use encrypted credentials from Cloud KMS](https://docs.cloud.google.com/build/docs/securing-builds/use-encrypted-credentials)).
- Artifact Registry is the recommended registry. Container Registry shut down on March 18, 2025 ([Transition from Container Registry](https://docs.cloud.google.com/artifact-registry/docs/transition/transition-from-gcr)).
- Application Design Center is generally available since December 5, 2025. Platform teams publish approved templates, and App Hub registers each deployed application automatically ([Application Design Center release notes](https://docs.cloud.google.com/application-design-center/docs/release-notes), [Application Design Center overview](https://docs.cloud.google.com/application-design-center/docs/overview), [Deploy applications](https://docs.cloud.google.com/application-design-center/docs/deploy-applications)).

## SDLC practices that Google documents

### DORA capabilities

These DORA capabilities appear most often in delivery scenarios.

| Capability | What it gives you | Google Cloud support |
|---|---|---|
| Trunk-based development | Fewer merge conflicts | Triggers on pushes and pull requests to the main branch |
| Continuous integration | Early detection of integration problems | Cloud Build runs unit tests, static analysis, and integration tests |
| Deployment automation | Less manual work in the release process | Cloud Deploy promotion and rollback |
| Continuous delivery | Low-risk deployment on demand, at any time | Cloud Deploy approvals and notifications |
| Shifting left on security | Security in the lifecycle without slower delivery | Artifact Analysis scanning and build provenance |
| Streamlining change approval | Peer review instead of heavyweight change approval | Pull request review, build approvals |

Sources: [DevOps capabilities](https://docs.cloud.google.com/architecture/devops), [Automate and manage change](https://docs.cloud.google.com/architecture/framework/operational-excellence/automate-and-manage-change), [Overview of Cloud Build](https://docs.cloud.google.com/build/docs/overview), [Overview of Cloud Deploy](https://docs.cloud.google.com/deploy/docs/overview), [Artifact Registry overview](https://docs.cloud.google.com/artifact-registry/docs/overview), [Gate builds on approval](https://docs.cloud.google.com/build/docs/securing-builds/gate-builds-on-approval).

The DORA metrics are in [Quality control measures](note:6.5-quality-control). Database change management, also a DORA capability, is in [Deployment and release management](note:6.3-release-management).

### Trunk-based development and release branches

DORA names trunk-based development as the way to prevent merge-conflict problems ([DevOps capabilities](https://docs.cloud.google.com/architecture/devops)). The SRE book describes how Google applies the model ([Release Engineering (SRE book)](https://sre.google/sre-book/release-engineering/)):

1. Developers check in all code to the main branch, which Google calls the mainline.
2. A continuous test system runs the unit tests on each change. These tests match the tests that gate a release.
3. For a release, the team branches from a mainline revision that passed all tests. It never merges the release branch back.
4. A bug fix goes to the mainline first. The team then cherry-picks the fix into the release branch and tests the branch again.

Builds are hermetic: they use known versions of tools and libraries, not what is installed on the build machine ([Release Engineering (SRE book)](https://sre.google/sre-book/release-engineering/)).

Foundation infrastructure code uses a different model: one persistent branch for each environment, with feature branches merged through approved pull requests ([Deployment methodology](https://docs.cloud.google.com/architecture/blueprints/security-foundations/deployment-methodology)). For application code, build one artifact and promote it ([Advising teams: deployment, API management, and testing](note:5.1-deployment-and-apis)).

## The CI/CD toolchain on Google Cloud

| Stage | Google Cloud service | Decision for the architect |
|---|---|---|
| Source | GitHub, GitLab, or Bitbucket through Developer Connect, or Secure Source Manager | Where code lives and how Google Cloud connects to it |
| Build and test (CI) | Cloud Build | Trigger type, worker pool, service account, secrets |
| Artifacts | Artifact Registry | Repository mode, location, cleanup, scanning |
| Delivery (CD) | Cloud Deploy | Promotion sequence, approvals, rollout strategy |
| Infrastructure | Terraform in Cloud Build, or Infrastructure Manager | Plan review and policy checks |
| Supply chain | Build provenance, Artifact Analysis, Binary Authorization | Which images a runtime accepts |

Sources: [CI/CD pipeline for developing and delivering containerized apps](https://docs.cloud.google.com/architecture/app-development-and-delivery-with-cloud-code-gcb-cd-and-gke), [Deployment methodology (enterprise application blueprint)](https://docs.cloud.google.com/architecture/blueprints/enterprise-application-blueprint/deployment-methodology), [Cloud Build repositories](https://docs.cloud.google.com/build/docs/repositories), [Infrastructure Manager overview](https://docs.cloud.google.com/infrastructure-manager/docs/overview).

In the enterprise application blueprint, a commit starts Cloud Build. Cloud Build builds, tests, and scans the image, pushes it to Artifact Registry, and creates a Cloud Deploy release. Cloud Deploy rolls the same immutable image out to each environment in order, with a manual approval at each stage ([Deployment methodology (enterprise application blueprint)](https://docs.cloud.google.com/architecture/blueprints/enterprise-application-blueprint/deployment-methodology)).

Cloud Deploy targets can be GKE clusters, GKE attached clusters, or Cloud Run services and jobs. Any CI tool can create a Cloud Deploy release if it produces container images ([Overview of Cloud Deploy](https://docs.cloud.google.com/deploy/docs/overview)). Promotion, canary rollouts, and rollback are in [Deployment and release management](note:6.3-release-management).

## Connect source code

| Option | Use it when | Notes |
|---|---|---|
| Developer Connect | One connection must serve several products, such as Cloud Build, Cloud Run, and Gemini Code Assist | Cloud Build cannot create manual, Pub/Sub, or webhook triggers for these repositories |
| Cloud Build repositories (2nd gen) | You need manual, Pub/Sub, or webhook triggers, or connections managed with Terraform | Supersedes 1st gen, which is now a legacy option |
| Secure Source Manager | Code must stay in a regional, single-tenant Git service that Google Cloud hosts | Built-in pull requests and issues. A triggers file starts Cloud Build builds |
| Cloud Source Repositories | Only organizations that used it before June 17, 2024 | Not available to new customers |

Sources: [Cloud Build repositories](https://docs.cloud.google.com/build/docs/repositories), [Developer Connect overview](https://docs.cloud.google.com/developer-connect/docs/overview), [Secure Source Manager overview](https://docs.cloud.google.com/secure-source-manager/docs/overview).

## Cloud Build decisions

### Triggers

| Trigger | Starts a build when | Note |
|---|---|---|
| Repository event | A push to a branch, a new tag, or a pull request | Included and ignored file filters work only for push and tag events |
| Manual | A person runs it, or Cloud Scheduler runs it on a schedule | The caller can override substitution values |
| Pub/Sub | A message arrives, for example after an image push to Artifact Registry | Not supported with VPC Service Controls |
| Webhook | An external system calls the trigger URL | The build config can be inline in the trigger |

Sources: [Cloud Build triggers](https://docs.cloud.google.com/build/docs/triggers), [Create and manage build triggers](https://docs.cloud.google.com/build/docs/automating-builds/create-manage-triggers).

In a repository with many services, use included and ignored files, so that a change starts only the builds that it affects. Cloud Build sends build status to the `cloud-builds` Pub/Sub topic, and notifiers forward it to Slack, SMTP, HTTP, or BigQuery ([Cloud Build triggers](https://docs.cloud.google.com/build/docs/triggers)).

### Approvals and outside contributors

A trigger can require approval. The build waits until a user with the Cloud Build Approver role (`roles/cloudbuild.builds.approver`) approves it ([Gate builds on approval](https://docs.cloud.google.com/build/docs/securing-builds/gate-builds-on-approval), [IAM roles and permissions](https://docs.cloud.google.com/build/docs/iam-roles-permissions)). The `constraints/cloudbuild.allowedIntegrations` constraint controls which external services can invoke triggers, and it overrides an approval ([Gate builds on organization policy](https://docs.cloud.google.com/build/docs/securing-builds/gate-builds-organization-policy), [Gate builds on approval](https://docs.cloud.google.com/build/docs/securing-builds/gate-builds-on-approval)).

GitHub pull request triggers have comment control. With "Required except for owners and collaborators", a build for an external contributor starts only after an owner or collaborator comments `/gcbrun`. Builds for owners and collaborators still start automatically ([Building repositories from GitHub](https://docs.cloud.google.com/build/docs/automating-builds/github/build-repos-from-github)).

### Default pool or private pool

The default pool runs each build on an isolated worker that can reach the public internet, but private network access is limited. Private pools are dedicated to you, but Cloud Build still manages them and scales them to zero ([Private pools overview](https://docs.cloud.google.com/build/docs/private-pools/private-pools-overview)).

| Requirement | Private pool feature |
|---|---|
| Builds must reach a server that has only a private IP address | Peer the pool's service producer network with your VPC network |
| Builds must run inside a VPC Service Controls perimeter | Create the private pool inside the perimeter |
| Builds must not reach the internet | Set `egressOption` to `NO_PUBLIC_EGRESS` |
| A service allowlists calls from a defined IP range | Define a static internal IP range for the pool. You cannot control the pool's external IP addresses, so for a reserved external IP address, route traffic through a proxy VM |
| No build in the organization may use the default pool | Enforce `constraints/cloudbuild.allowedWorkerPools` |

Sources: [Private pools overview](https://docs.cloud.google.com/build/docs/private-pools/private-pools-overview), [Using Cloud Build in a private network](https://docs.cloud.google.com/build/docs/private-pools/use-in-private-network).

### Service accounts

Since May and June 2024, new projects run builds as the Compute Engine default service account. Projects that ran their first build earlier keep the Cloud Build legacy service account. A trigger must name a service account, unless the project default is the legacy account. The most secure option is a user-specified service account for both manual and triggered builds ([Cloud Build default service account change](https://docs.cloud.google.com/build/docs/cloud-build-service-account-updates)).

With a user-specified service account, store build logs in Cloud Logging or in a Cloud Storage bucket that you own ([Create and manage build triggers](https://docs.cloud.google.com/build/docs/automating-builds/create-manage-triggers)).

### Secrets in builds

Store passwords and API keys in Secret Manager. Grant the Secret Manager Secret Accessor role on the secret to the build's service account. In the build config, list the secret under `availableSecrets`, and expose it to a step with `secretEnv`. Do not grant the Secret Accessor role to the legacy Cloud Build service account. Any user who can run a trigger with that account could then read the secret through a build ([Use secrets from Secret Manager](https://docs.cloud.google.com/build/docs/securing-builds/use-secrets)).

### Provenance and supply chain

Cloud Build can generate build provenance that meets SLSA level 3 ([Generate and validate build provenance](https://docs.cloud.google.com/build/docs/securing-builds/generate-validate-build-provenance)). Binary Authorization can then block images that Cloud Build did not build ([Securing image deployments to Cloud Run and Google Kubernetes Engine](https://docs.cloud.google.com/build/docs/securing-builds/secure-deployments-to-run-gke)). The design of these controls is in [Software supply chain security](note:3.1-supply-chain).

## Artifact Registry decisions

| Decision | Choice | Why |
|---|---|---|
| Repository mode | Standard, remote, virtual, or connector (Preview) | You cannot change the mode after you create the repository |
| Third-party dependencies | Remote repository for Docker Hub, Maven Central, and other upstream sources | Caches upstream artifacts, reduces latency, and improves availability |
| One endpoint for many repositories | Virtual repository | Sets a priority for each repository behind the endpoint |
| Location | Region or multi-region | Balance latency, availability, egress cost, and compliance |
| Old versions | Cleanup policies | Delete policies and keep policies control what stays |

Sources: [Repository overview](https://docs.cloud.google.com/artifact-registry/docs/repositories), [Artifact Registry overview](https://docs.cloud.google.com/artifact-registry/docs/overview), [Configure cleanup policies](https://docs.cloud.google.com/artifact-registry/docs/repositories/cleanup-policy).

Since March 18, 2025, you cannot write images to Container Registry. `gcr.io` URLs that Artifact Registry hosts are not affected ([Transition from Container Registry](https://docs.cloud.google.com/artifact-registry/docs/transition/transition-from-gcr)).

## Secure and resilient pipelines

Treat a pipeline that deploys to production as a production system ([Design secure deployment pipelines](https://docs.cloud.google.com/architecture/design-secure-deployment-pipelines-bp)):

- Apply the same access control, security, and quality standards to the pipeline as to production.
- Grant the pipeline access to individual resources, not to whole projects. Split a pipeline into stages when it needs several projects.
- Keep an emergency access procedure for times when the pipeline does not work.
- Keep a cache of input artifacts, so that an outage at an outside source does not stop deployments.

Plan business continuity for the toolchain. Source control and Artifact Registry have the highest developer and operations impact, so they need the lowest RTO and RPO. An Artifact Registry outage can stop deployments and autoscaling. Use multi-region Artifact Registry storage, and cache third-party libraries in your registry ([Business continuity with CI/CD on Google Cloud](https://docs.cloud.google.com/architecture/business-continuity-with-cicd-on-google-cloud)). General DR design is in [Disaster recovery planning](note:4.1-disaster-recovery).

## Infrastructure as code in CI

In Google's GitOps example, a push to a feature branch runs only `terraform plan`. A push to the `dev` or `prod` branch runs `terraform apply` for that environment. The Cloud Build GitHub app links the plan to the pull request, so reviewers see the change before the merge. Branch protection requires a successful Cloud Build run before a merge ([Managing infrastructure as code with Terraform, Cloud Build, and GitOps](https://docs.cloud.google.com/docs/terraform/resource-management/managing-infrastructure-as-code)).

`gcloud beta terraform vet` (Preview) checks a plan against policy constraints, and it can stop a deployment before production ([Policy validation](https://docs.cloud.google.com/docs/terraform/policy-validation)). State, modules, and Infrastructure Manager are in [Infrastructure as Code](note:5.2-infrastructure-as-code).

## Environment and project strategy

The enterprise foundations blueprint separates environments with folders and projects:

| Element | Blueprint pattern |
|---|---|
| Folders | `development`, `nonproduction`, and `production`, plus `common` and `networking` for shared resources |
| Workload projects | One project for each environment and workload, named `prj-{env}-{workload}` |
| Pipeline projects | A dedicated project holds the CI/CD pipeline. The application blueprint creates one for each application |
| Pipeline identities | Each stage or business unit uses its own service account, with access only to its own projects |

Sources: [Organization structure](https://docs.cloud.google.com/architecture/blueprints/security-foundations/organization-structure), [Deployment methodology](https://docs.cloud.google.com/architecture/blueprints/security-foundations/deployment-methodology), [Deployment methodology (enterprise application blueprint)](https://docs.cloud.google.com/architecture/blueprints/enterprise-application-blueprint/deployment-methodology).

Environment folders let you give production stricter policies and different IAM roles ([Decide a resource hierarchy for your Google Cloud landing zone](https://docs.cloud.google.com/architecture/landing-zones/decide-resource-hierarchy)). The `nonproduction` folder holds a copy of production for tests before promotion ([Organization structure](https://docs.cloud.google.com/architecture/blueprints/security-foundations/organization-structure)). Hierarchy design is in [IAM, resource hierarchy, and separation of duties](note:3.1-iam-and-hierarchy).

## Service catalog and provisioning

Three products solve different provisioning problems.

| Product | What it does | Status and fit |
|---|---|---|
| Service Catalog (formerly Private Catalog) | Cloud admins share curated solutions with folders and projects. A solution is a Terraform configuration, a Deployment Manager template, or a link | Still documented. Deployment Manager support stopped on April 1, 2026, so do not build new solutions on its templates |
| Application Design Center | Platform teams build templates from Google components and imported Terraform components (Preview), and share them through catalogs. Developers customize and deploy them | GA since December 5, 2025. App Hub registers each deployed application. You can export the Terraform code |
| App Hub | A registry that groups existing services and workloads from many projects into applications, with owners, criticality, and environment | Gives application context to Cloud Hub, Gemini Cloud Assist, and Google Cloud Observability |

Sources: [Overview of Service Catalog](https://docs.cloud.google.com/service-catalog/docs/overview), [Creating a Terraform configuration](https://docs.cloud.google.com/service-catalog/docs/terraform-configuration), [Service Catalog release notes](https://docs.cloud.google.com/service-catalog/docs/release-notes), [Deployment Manager deprecation](https://docs.cloud.google.com/deployment-manager/docs/deprecations), [Application Design Center release notes](https://docs.cloud.google.com/application-design-center/docs/release-notes), [App Hub overview](https://docs.cloud.google.com/app-hub/docs/overview).

Google's application-centric model uses Application Design Center to design and deploy applications, and App Hub to organize existing resources into applications ([Application-centric Google Cloud](https://docs.cloud.google.com/application-design-center/docs/application-centric-google-cloud)). Use this logic:

- Developers need self-service deployment of approved patterns with standards built in: use Application Design Center templates in a catalog.
- Resources already exist, and teams need an application view with owners and dependencies: use App Hub.
- An organization already shares Terraform solutions in Service Catalog: it can keep them, but it must replace Deployment Manager templates.

## Exam traps

- **Cloud Source Repositories for a new company.** It is not available to new customers since June 17, 2024. Use Secure Source Manager or connect external Git ([Cloud Build triggers](https://docs.cloud.google.com/build/docs/triggers)).
- **The default pool for a build that calls a private IP address.** Use a private pool with VPC peering ([Private pools overview](https://docs.cloud.google.com/build/docs/private-pools/private-pools-overview)).
- **`allowedIntegrations` to force private pools.** That constraint controls which external services invoke triggers. `allowedWorkerPools` forces private pools ([Gate builds on organization policy](https://docs.cloud.google.com/build/docs/securing-builds/gate-builds-organization-policy), [Using Cloud Build in a private network](https://docs.cloud.google.com/build/docs/private-pools/use-in-private-network)).
- **Secret access for the legacy Cloud Build service account.** Any user who runs a trigger with that account can then read the secret. Grant access to a user-specified service account ([Use secrets from Secret Manager](https://docs.cloud.google.com/build/docs/securing-builds/use-secrets)).
- **Pub/Sub triggers inside a VPC Service Controls perimeter.** Cloud Build does not support them there ([Cloud Build triggers](https://docs.cloud.google.com/build/docs/triggers)).
- **A weekly change advisory board to lower risk.** DORA replaces heavyweight change approval with peer review ([DevOps capabilities](https://docs.cloud.google.com/architecture/devops)).
- **A new image build for each environment.** Build one immutable image and promote it ([Deployment methodology (enterprise application blueprint)](https://docs.cloud.google.com/architecture/blueprints/enterprise-application-blueprint/deployment-methodology)).
- **App Hub to deploy a new application.** App Hub organizes existing resources. Application Design Center deploys templates ([Application-centric Google Cloud](https://docs.cloud.google.com/application-design-center/docs/application-centric-google-cloud)).
