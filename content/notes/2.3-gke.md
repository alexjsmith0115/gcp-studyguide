## Why it matters

When a design uses GKE, the architect sets the cluster mode, availability, upgrade policy, scaling layers, network isolation, and workload identity. These settings decide the SLA, the security posture, and how much work the platform team does. Exam questions often give a GKE requirement and ask for the Google-recommended setting. Typical requirements are least privilege, controlled upgrades, a private control plane, multi-cluster traffic, and cost.

## Key points

- Autopilot is the recommended mode of operation. GKE manages the nodes, scaling, and security defaults ([About GKE modes of operation](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/choose-cluster-mode)).
- Autopilot clusters are always regional. Google recommends regional clusters for production workloads ([Regional clusters](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/regional-clusters)).
- The control plane SLA is 99.95% for Autopilot and regional Standard clusters, and 99.5% for zonal Standard clusters ([GKE pricing](https://cloud.google.com/kubernetes-engine/pricing)).
- Google recommends enrolling every cluster in a release channel. Regular is the default. Extended keeps a minor version for up to 24 months ([About release channels](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/release-channels)).
- A cluster has one recurring maintenance window and can have several maintenance exclusions. GKE can override both for critical security patches ([Maintenance windows and exclusions](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/maintenance-windows-and-exclusions)).
- The cluster autoscaler adds and removes nodes based on Pod resource requests, not on actual utilization ([About GKE cluster autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/cluster-autoscaler)).
- Do not use the Horizontal Pod Autoscaler and the Vertical Pod Autoscaler together on CPU or memory ([Horizontal Pod autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/horizontalpodautoscaler)).
- VPC-native is the default network mode for all new clusters, and Autopilot cannot turn it off. Pod IP addresses come from subnet secondary ranges and are routable in the VPC ([VPC-native clusters](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/alias-ips), [Create a VPC-native cluster](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/alias-ips)).
- Use the DNS-based endpoint for control plane access. Private nodes have only internal IP addresses ([About network isolation in GKE](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/network-isolation)).
- Workload Identity Federation for GKE is the recommended way for workloads to call Google Cloud APIs. It is always enabled in Autopilot ([About Workload Identity Federation for GKE](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/workload-identity), [Authenticate to Google Cloud APIs from GKE workloads](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/workload-identity)).
- A multi-cluster Gateway gives one entry point for Services in several clusters. All the clusters must be registered to one fleet ([About multi-cluster Gateways](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/multi-cluster-gateways)).
- Backup for GKE backs up Kubernetes resources and persistent volumes. It can restore them into another cluster ([Backup for GKE overview](https://docs.cloud.google.com/kubernetes-engine/docs/add-on/backup-for-gke/concepts/backup-for-gke)).

## Autopilot or Standard

| | Autopilot | Standard |
|---|---|---|
| Nodes | GKE creates and manages them from your Pod specs | You create and manage node pools |
| Bin-packing | GKE bin-packs Pods onto nodes | You plan node sizes and bin-packing to avoid waste |
| Security defaults | Best-practice constraints, for example no privileged Pods | You can configure Pods in any way, including privileged mode |
| Billing | General-purpose Pods: Pod resource requests. Specific hardware: the whole node plus a management premium | The Compute Engine VMs of the nodes |
| Cluster location | Always regional | Regional or zonal |

Sources: [About GKE modes of operation](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/choose-cluster-mode), [GKE pricing](https://cloud.google.com/kubernetes-engine/pricing), [Regional clusters](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/regional-clusters).

- **Autopilot workloads in Standard.** A Standard cluster can run Autopilot workloads through a compute class. GKE then manages bin-packing, scaling, and infrastructure for those workloads ([About GKE modes of operation](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/choose-cluster-mode)).
- **Hardware choice.** Autopilot runs general-purpose Pods on the container-optimized compute platform. Pods that need specific hardware, such as GPUs, request a ComputeClass, and GKE configures nodes to match ([GKE Autopilot overview](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/autopilot-overview)).
- **Right-size requests.** In Pod-based billing, the node size and node count do not matter. You pay for Pod requests, so set requests to what the workload needs ([GKE pricing](https://cloud.google.com/kubernetes-engine/pricing)).
- **Management fee.** Every cluster pays the same flat fee per hour, in all modes. The free tier covers one Autopilot or zonal Standard cluster per billing account each month ([GKE pricing](https://cloud.google.com/kubernetes-engine/pricing)).

## Availability: regional and zonal clusters

A regional cluster replicates the control plane and nodes across zones in one region. The control plane is not affected when a single zone becomes unavailable. You can also use the Kubernetes API during control plane upgrades ([Regional clusters](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/regional-clusters)).

- **Zonal limits.** A Standard zonal cluster has a single control plane. During control plane changes and maintenance, you cannot modify the cluster, and this includes deploying workloads ([Maintenance windows and exclusions](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/maintenance-windows-and-exclusions)).
- **Node count.** The default node pool of a regional Standard cluster has nine nodes, three per zone. You can reduce this to one node per zone ([Regional clusters](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/regional-clusters)).
- **Zone outage.** Autopilot rebalances nodes automatically. In Standard, you rebalance nodes manually or with the cluster autoscaler ([Regional clusters](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/regional-clusters)).
- **Overprovisioning.** To keep full capacity after a zone loss, set the autoscaling limits of a three-zone cluster to 150% ([Regional clusters](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/regional-clusters)).
- **Cost.** Node-to-node traffic across zones has a charge ([Regional clusters](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/regional-clusters)).

## Upgrades: release channels, windows, and exclusions

| Channel | Behavior | Use for |
|---|---|---|
| Rapid | Newest versions. They are excluded from the GKE SLA | Testing new versions in pre-production |
| Regular (default) | Balance of feature availability and stability | Most clusters (Google recommendation) |
| Stable | New versions arrive last, after validation in Rapid and Regular | Clusters that put stability before new features |
| Extended | Stay on a minor version for up to 24 months. An extra fee applies in the extended support period | Long-term support: keep a minor version as long as possible |
| No channel | Deprecated. Removal on June 14, 2027 | Do not use for new clusters |

Sources: [About release channels](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/release-channels), [GKE pricing](https://cloud.google.com/kubernetes-engine/pricing).

Maintenance exclusions have three scopes:

| Scope | Blocks | Maximum length |
|---|---|---|
| No upgrades (default) | All automatic upgrades | 90 days. Google recommends less than 30 days |
| No minor upgrades | Minor version upgrades. Patch upgrades continue | Up to the end of support for the minor version |
| No minor or node upgrades | Minor upgrades and node upgrades, so no Pod eviction from upgrades. Control plane patches continue | Up to the end of support for the minor version |

Source: [Maintenance windows and exclusions](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/maintenance-windows-and-exclusions).

- **Hold a version.** To keep a cluster on a version while you test, Google recommends a maintenance exclusion. Do not leave the release channel ([About release channels](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/release-channels)).
- **End of support.** At the end of support, GKE upgrades node pools anyway ([Maintenance windows and exclusions](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/maintenance-windows-and-exclusions)).
- **Node upgrade strategy.** Standard node pools use surge upgrades or blue-green upgrades. Blue-green upgrades keep the old nodes available for rollback while you validate the workloads. Autopilot uses surge upgrades ([Node upgrade strategies](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/node-pool-upgrade-strategies)).

## Scaling layers

| Layer | Scales | Based on | Notes |
|---|---|---|---|
| Horizontal Pod Autoscaler (HPA) | Number of Pods | CPU, memory, custom metrics, or external metrics such as a Pub/Sub queue size | Fast response to load changes |
| Vertical Pod Autoscaler (VPA) | Pod CPU and memory requests | Resource usage over time, including historical data | `Auto` (`Recreate`) mode evicts Pods to change requests. `InPlaceOrRecreate` is in Preview |
| Cluster autoscaler (Standard) | Nodes in a node pool, between a minimum and a maximum | Pods that cannot be scheduled, and resource requests | Not based on actual utilization |
| Node pool auto-creation (Standard) | New node pools | Hardware needs and requests of pending Pods | Enable per workload with ComputeClasses (recommended), or for the whole cluster with node auto-provisioning |
| Autopilot | Nodes and node pools | Pod specs | GKE always does it. Nothing to configure |

Sources: [Horizontal Pod autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/horizontalpodautoscaler), [Vertical Pod autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/verticalpodautoscaler), [About GKE cluster autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/cluster-autoscaler), [About node pool auto-creation](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/node-auto-provisioning).

The cluster autoscaler does not fix Pods that request too few resources. Make explicit resource requests for all workloads ([About GKE cluster autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/cluster-autoscaler)). To scale horizontally on CPU and vertically on memory at the same time, use multidimensional Pod autoscaling, which is in beta ([Horizontal Pod autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/horizontalpodautoscaler)).

## Networking

### VPC-native clusters

A VPC-native cluster uses alias IP address ranges ([VPC-native clusters](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/alias-ips)):

- **Routing.** Pod IP addresses are routable in the cluster's VPC and in VPCs connected by VPC Network Peering. On-premises networks reach them over Cloud VPN or Cloud Interconnect.
- **Planning.** GKE reserves Pod IP addresses in the VPC before it creates the Pods, so they do not conflict with other resources.
- **Routes quota.** Pod ranges do not use custom static routes or their quota.
- **Features.** Some features, such as network endpoint groups (NEGs), work only with VPC-native clusters.

For subnet and IP address planning, see [Cloud-native network design](note:1.3-network-design).

### Control plane access and private nodes

| Control | What it does |
|---|---|
| DNS-based endpoint (recommended) | A stable DNS name for the control plane. It is reachable from any network that can reach Google Cloud APIs. IAM controls access, and VPC Service Controls can add a second layer. No bastion host is necessary |
| IP-based endpoints with authorized networks | Limit control plane access to trusted IP ranges. Google strongly recommends at least one authorized network. If you disable the external endpoint, remote access needs a bastion host |
| Private nodes | Nodes get only internal IP addresses. Internet egress needs Cloud NAT or another NAT solution. Set it per cluster, per node pool (Standard), or per workload (Autopilot) |

Source: [About network isolation in GKE](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/network-isolation).

VPC Service Controls does not directly support a control plane with a public IP address. The cluster gets VPC Service Controls protection when clients use the DNS-based endpoint ([About network isolation in GKE](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/network-isolation)). New Autopilot clusters have a publicly accessible IP address, so customize the network isolation when the design needs a private cluster ([GKE Autopilot overview](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/autopilot-overview)).

### Traffic into the cluster

| Need | Use |
|---|---|
| External HTTP(S) traffic to many Services, by host or path | Gateway API or Ingress, with an external Application Load Balancer |
| Internal HTTP(S) traffic to many Services | Gateway API or Ingress, with an internal Application Load Balancer |
| Traffic to one Service, for example an email server | A `LoadBalancer` Service, which creates an external or internal passthrough Network Load Balancer |
| One entry point for Services in several clusters | A multi-cluster Gateway |
| Service discovery and calls between clusters | Multi-cluster Services (MCS) |
| Rules for Pod-to-Pod traffic | Network policies. GKE Dataplane V2 enforces them and is on by default in Autopilot |

Sources: [GKE Autopilot overview](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/autopilot-overview), [About Gateway API](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/gateway-api), [About multi-cluster Gateways](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/multi-cluster-gateways).

Gateway API evolves the Ingress resource ([About Gateway API](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/gateway-api)):

- **Role-oriented.** Cluster operators define the shared Gateway. Application developers create HTTPRoutes to expose their applications.
- **Expressive.** Header-based matching and traffic weighting are built in. Ingress needs custom annotations for them.
- **Portable.** Gateway API is an open source standard with many implementations.

A multi-cluster Gateway has one config cluster. You deploy all the Gateway and HTTPRoute resources only to that cluster, so choose a regional cluster for it ([About multi-cluster Gateways](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/multi-cluster-gateways)). For the load balancer choice, see [Choosing a load balancer](note:1.3-load-balancing).

## Workload identity

Workload Identity Federation for GKE lets IAM treat a Kubernetes ServiceAccount as a principal. You grant IAM roles directly to a principal identifier like this one ([About Workload Identity Federation for GKE](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/workload-identity)):

```
principal://iam.googleapis.com/projects/PROJECT_NUMBER/locations/global/workloadIdentityPools/PROJECT_ID.svc.id.goog/subject/ns/NAMESPACE/sa/SERVICEACCOUNT
```

- **No automatic access.** Enabling the feature grants no IAM permissions. You grant each role on purpose ([About Workload Identity Federation for GKE](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/workload-identity)).
- **Identity sameness.** All clusters in one project share one workload identity pool. IAM treats the same namespace and ServiceAccount in two clusters as one identity. To separate an untrusted cluster, put it in a different project, use distinct namespace names, or use conditional IAM policies ([About Workload Identity Federation for GKE](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/workload-identity)).
- **Weaker alternatives.** All workloads on a node share the node service account, which violates least privilege. Exported service account keys are a security risk ([About Workload Identity Federation for GKE](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/workload-identity)).

For access from outside Google Cloud, see [Secure remote and workload access](note:3.1-secure-access).

## Fleets, Config Sync, and Policy Controller

A fleet is a logical group of Kubernetes clusters that you manage together from one fleet host project. A fleet can include clusters outside Google Cloud ([Fleet management overview](https://docs.cloud.google.com/kubernetes-engine/fleet-management/docs)).

| Tool | What it does | Use for |
|---|---|---|
| Config Sync | GitOps service. Syncs configuration and policies from a central source, such as Git, to any number of clusters, and prevents drift | The same configuration across environments and teams |
| Policy Controller | Programmable policies, based on Open Policy Agent Gatekeeper. Audit and admission control, with a library of prebuilt policies | Security and compliance guardrails across a fleet |

Sources: [Config Sync overview](https://docs.cloud.google.com/kubernetes-engine/config-sync/docs/overview), [Policy Controller overview](https://docs.cloud.google.com/kubernetes-engine/policy-controller/docs/overview).

These features were part of GKE Enterprise. GKE is now a single offering without editions or tiers ([GKE Enterprise release notes](https://docs.cloud.google.com/kubernetes-engine/enterprise/docs/release-notes)). For image signing and deploy-time checks, see [Software supply chain security](note:3.1-supply-chain).

## Backup for GKE

Backup for GKE is a managed service with two parts: a control plane API and an agent in each cluster ([Backup for GKE overview](https://docs.cloud.google.com/kubernetes-engine/docs/add-on/backup-for-gke/concepts/backup-for-gke)).

- **Contents.** A configuration backup holds the Kubernetes resource manifests. A volume backup holds snapshots of the persistent volumes.
- **Scope.** Back up all workloads in a cluster, or select workloads by namespace or by application.
- **Restore.** Restore into the same cluster or into another cluster. The target cluster must already exist and have the agent enabled.
- **Changes during restore.** Transformation rules can change resources, for example a zonal persistent disk to a regional persistent disk.
- **Schedules.** Automated backups on a recurring schedule help you meet your RPO.

For DR design across services, see [Disaster recovery planning](note:4.1-disaster-recovery).

## Spot capacity on GKE

| | Autopilot | Standard |
|---|---|---|
| How | Spot Pods: use the `cloud.google.com/gke-spot=true` label in a nodeSelector or node affinity | Node pools of Spot VMs |
| Shutdown time | A grace period of 15 seconds at most | 30 seconds by default: 15 for regular Pods, then 15 for critical system Pods |
| Design | Stateless, batch, or fault-tolerant Pods | Also keep node pools of standard VMs. Taint the Spot node pools so critical Pods do not run there |

Sources: [Run fault-tolerant workloads at lower costs in Spot Pods](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/autopilot-spot-pods), [Spot VMs](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/spot-vms).

## Exam traps

- **A zonal cluster for production.** A zonal control plane has a lower SLA, and you cannot deploy during its maintenance. Use a regional cluster ([Regional clusters](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/regional-clusters), [Maintenance windows and exclusions](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/maintenance-windows-and-exclusions), [GKE pricing](https://cloud.google.com/kubernetes-engine/pricing)).
- **Leaving the release channel to stop upgrades.** "No channel" is deprecated. Stay in a channel and use a maintenance exclusion ([About release channels](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/release-channels)).
- **The Rapid channel for production.** Rapid versions are excluded from the GKE SLA ([About release channels](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/release-channels)).
- **A "No upgrades" exclusion for six months.** That scope allows 90 days at most. Use "No minor upgrades" to hold a minor version longer ([Maintenance windows and exclusions](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/maintenance-windows-and-exclusions)).
- **HPA and VPA both on CPU.** They conflict. Use multidimensional Pod autoscaling, or scale on different metrics ([Horizontal Pod autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/horizontalpodautoscaler)).
- **Expecting the cluster autoscaler to react to high node CPU.** It reacts to Pods that cannot be scheduled, based on requests ([About GKE cluster autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/cluster-autoscaler)).
- **Service account keys in Kubernetes Secrets.** Use Workload Identity Federation for GKE ([About Workload Identity Federation for GKE](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/workload-identity)).
- **Trusted and untrusted clusters in one project.** Identity sameness gives the same namespace and ServiceAccount the same access in every cluster of the project ([About Workload Identity Federation for GKE](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/workload-identity)).
- **A bastion host to reach a private control plane.** The DNS-based endpoint removes the need for one. It also works with VPC Service Controls ([About network isolation in GKE](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/network-isolation)).
- **Only Spot capacity for critical Pods.** Keep node pools of standard VMs, and taint the Spot node pools ([Spot VMs](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/spot-vms)).
