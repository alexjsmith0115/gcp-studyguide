## Why it matters

Objective 6.2 covers monitoring and logging, profiling and benchmarking, and alerting strategies. The exam gives you a requirement such as "one view of 40 projects", "keep audit logs for seven years at low cost", or "stop alert fatigue", and asks for the correct Google Cloud Observability (formerly the Cloud operations suite, or Stackdriver) configuration. Most wrong answers use a real tool for the wrong job, for example Cloud Trace to find a CPU hot spot or a log exclusion to cut API calls.

## Key points

- Cloud Monitoring, Cloud Logging, and Cloud Trace are on by default in each project. They collect telemetry and audit logs for most Google Cloud services automatically ([Observability in Google Cloud](https://docs.cloud.google.com/stackdriver/docs)).
- A metrics scope lets one scoping project chart and alert on metrics from many projects. Use a project without resources as the scoping project ([Metrics scopes overview](https://docs.cloud.google.com/monitoring/settings)).
- Every log entry passes the Log Router. Sinks route entries to log buckets, BigQuery, Cloud Storage, Pub/Sub, or another project ([Route log entries](https://docs.cloud.google.com/logging/docs/routing/overview)).
- The `_Required` bucket keeps Admin Activity, System Event, and Access Transparency logs for 400 days, and you cannot change it. `_Default` and user-defined buckets in a project keep logs for 30 days by default, configurable from 1 to 3650 days ([Logging quotas and limits](https://docs.cloud.google.com/logging/quotas), [Route log entries](https://docs.cloud.google.com/logging/docs/routing/overview)).
- Exclusion filters on sinks reduce Cloud Logging storage costs. Routing to Cloud Storage, BigQuery, or Pub/Sub has no Cloud Logging storage charge ([Optimize and monitor Google Cloud Observability costs](https://docs.cloud.google.com/stackdriver/docs/observability/pricing-optimize-and-monitor)).
- Observability Analytics (formerly Log Analytics) runs SQL on log buckets that you upgrade. It can join log and trace data ([Analyze logs using Logs Explorer and Observability Analytics](https://docs.cloud.google.com/logging/docs/log-analytics)).
- For SLO alerts, start with a fast-burn policy (10x burn rate, 1- or 2-hour lookback) and a slow-burn policy (2x burn rate, 24-hour lookback) ([Alerting on your burn rate](https://docs.cloud.google.com/stackdriver/docs/solutions/slo-monitoring/alerting-on-budget-burn-rate)).

## Which tool answers which question

| Question in the scenario | Tool | Why |
|---|---|---|
| Is the service up for users? What is its error rate or latency? | Cloud Monitoring (metrics, uptime checks, SLOs) | Time series, alerting, and SLO tracking. |
| Can a user log in and check out? | Synthetic monitor | Runs a scripted test on a schedule. |
| What happened, in detail, at 02:14? | Cloud Logging (Logs Explorer) | Search and troubleshoot individual log entries. |
| How many 5xx errors per customer per hour last month? | Observability Analytics | SQL aggregation. Logs Explorer cannot aggregate. |
| Which service in the call chain adds the latency? | Cloud Trace | Follows one request across services as spans. |
| Which function uses the most CPU or heap in production? | Cloud Profiler | Continuous, low-overhead profiling tied to source code. |
| Which exceptions are new since the last release? | Error Reporting | Groups error events by root cause. |
| Kubernetes teams already use PromQL and Grafana | Google Cloud Managed Service for Prometheus | Managed Prometheus backend on the Cloud Monitoring datastore. |

Sources: [Synthetic monitoring overview](https://docs.cloud.google.com/monitoring/uptime-checks/introduction), [Analyze logs using Logs Explorer and Observability Analytics](https://docs.cloud.google.com/logging/docs/log-analytics), [Cloud Trace overview](https://docs.cloud.google.com/trace/docs/overview), [Cloud Profiler overview](https://docs.cloud.google.com/profiler/docs/about-profiler), [Error Reporting overview](https://docs.cloud.google.com/error-reporting/docs/grouping-errors), [Google Cloud Managed Service for Prometheus](https://docs.cloud.google.com/stackdriver/docs/managed-prometheus).

## Cloud Monitoring

### Multi-project monitoring: metrics scopes and observability scopes

A **scoping project** hosts a metrics scope. It also stores the alerting policies, uptime checks, dashboards, and other monitoring configuration. By default, a metrics scope contains only its own project ([Metrics scopes overview](https://docs.cloud.google.com/monitoring/settings)).

Design rules from the docs:

- Use a new project, or one without resources, as the scoping project. Otherwise, a chart or alert on the scoping project's own resources needs filters to exclude the monitored projects, which invites errors ([Metrics scopes overview](https://docs.cloud.google.com/monitoring/settings)).
- Use several scoping projects to control what each team sees ([Metrics scopes overview](https://docs.cloud.google.com/monitoring/settings)).
- Monitoring Viewer on the scoping project is enough to see metrics from all monitored projects. To change the scope, you need Monitoring Admin on the scoping project and on each project you add ([Metrics scopes overview](https://docs.cloud.google.com/monitoring/settings)).

Scopes do not move data. Metric and trace data stays in the project where it originates. Log data can be routed elsewhere, so you configure a **log scope**, preferably with log views. The **observability scope** sets the default log and trace scopes for the Logs Explorer and Trace Explorer ([Configure observability scopes](https://docs.cloud.google.com/stackdriver/docs/observability/scopes)).

Monitoring checks your IAM role on the scoping project only. Logging and Trace check your permissions on each resource that the query reads ([Configure observability scopes](https://docs.cloud.google.com/stackdriver/docs/observability/scopes)).

### Uptime checks and synthetic monitors

| Type | What it does | Use it for |
|---|---|---|
| Public uptime check | Sends HTTP, HTTPS, or TCP requests from checkers in several regions to a public URL or resource | External availability, from the user's side |
| Private uptime check | Sends requests over a private network to internal IPs, such as a VM or an L4 internal load balancer | Internal services without a public endpoint |
| Synthetic monitor | Deploys a 2nd gen Cloud Run function (formerly Cloud Functions) in Node.js. Custom and Mocha monitors run your tests. A broken-link checker tests the links at a URI | User journeys, such as login or checkout, and broken links |

Source: [Synthetic monitoring overview](https://docs.cloud.google.com/monitoring/uptime-checks/introduction).

To get notified when a check fails, create an alerting policy on the check ([Synthetic monitoring overview](https://docs.cloud.google.com/monitoring/uptime-checks/introduction)).

### SLO monitoring

Cloud Monitoring can track SLOs for a **service**. Basic service types (App Engine, Cloud Endpoints, Istio, Cloud Run) get a basic availability or latency SLI automatically. GKE services and custom services need an SLI that you define. A request-based SLI counts good events against total events, for example 2xx responses against all responses. A windows-based SLI counts good time windows against total windows ([Constructs in the API](https://docs.cloud.google.com/stackdriver/docs/solutions/slo-monitoring/api/api-structures)).

The compliance period is a calendar period (for example, a week) or a rolling window of 1 to 30 days. The error budget is (1 − SLO goal) × eligible events ([Concepts in service monitoring](https://docs.cloud.google.com/stackdriver/docs/solutions/slo-monitoring)). Error budget policy is in [Quality control measures](note:6.5-quality-control).

### Google Cloud Managed Service for Prometheus

Managed Service for Prometheus stores Prometheus and OpenTelemetry metrics in Monarch, the same datastore as Cloud Monitoring. You keep PromQL, Grafana dashboards, and PromQL alerts. Data is kept for 24 months at no additional cost ([Google Cloud Managed Service for Prometheus](https://docs.cloud.google.com/stackdriver/docs/managed-prometheus)).

- Managed collection is Google's recommended approach for all Kubernetes environments ([Google Cloud Managed Service for Prometheus](https://docs.cloud.google.com/stackdriver/docs/managed-prometheus)).
- The Ops Agent can scrape Prometheus metrics on Compute Engine. Cloud Run uses a Prometheus or OpenTelemetry sidecar ([Google Cloud Managed Service for Prometheus](https://docs.cloud.google.com/stackdriver/docs/managed-prometheus)).
- It is billed per sample. A longer scrape interval (for example, 60 seconds instead of 15) and filtering reduce cost ([Optimize and monitor Google Cloud Observability costs](https://docs.cloud.google.com/stackdriver/docs/observability/pricing-optimize-and-monitor)).

### Agents and instrumentation

The **Ops Agent** is the primary agent for Compute Engine ([Ops Agent overview](https://docs.cloud.google.com/stackdriver/docs/solutions/agents/ops-agent)). Without it, you get basic VM metrics such as CPU and network, and basic process data. Memory metrics need the Ops Agent, and the agent adds deeper process metrics ([Observe and monitor VMs](https://docs.cloud.google.com/compute/docs/instances/observe-monitor-vms)).

For application code, Google recommends OpenTelemetry. Cloud Run and Cloud Run functions send latency data for incoming and outgoing HTTP requests to Trace automatically ([Cloud Trace overview](https://docs.cloud.google.com/trace/docs/overview)).

## Cloud Logging

### Log Router, sinks, and buckets

Each project, folder, organization, and billing account has a Log Router. Each sink has one inclusion filter and optional exclusion filters. Every sink evaluates every entry, so several sinks can route the same entry ([Route log entries](https://docs.cloud.google.com/logging/docs/routing/overview)).

| Destination | Choose it when |
|---|---|
| Log bucket | You want Logs Explorer, Observability Analytics, and Error Reporting. |
| BigQuery dataset | You want to join logs with business data. |
| Cloud Storage bucket | You want low-cost, long-term storage. Entries are JSON files. |
| Pub/Sub topic | You want to export to a third-party tool such as Splunk or Datadog. |
| Another Google Cloud project | You want the sinks in that project to route the entries again. |

Sources: [Route log entries](https://docs.cloud.google.com/logging/docs/routing/overview), [Storage classes](https://docs.cloud.google.com/storage/docs/storage-classes).

Rules that exam questions test:

- A new sink routes only entries that arrive after you create it. To move old logs, copy them from a log bucket to Cloud Storage ([Route log entries](https://docs.cloud.google.com/logging/docs/routing/overview)).
- You cannot modify or delete the `_Required` sink. You can modify or disable the `_Default` sink ([Route log entries](https://docs.cloud.google.com/logging/docs/routing/overview)).
- **Aggregated sinks** at a folder or organization route logs of all child resources. An intercepting aggregated sink stops child sinks from routing the matched entries, except the `_Required` sink ([Route log entries](https://docs.cloud.google.com/logging/docs/routing/overview)).
- You cannot create user-defined buckets in folders or organizations. To keep folder or organization logs longer than 30 days, route them to a bucket in a project ([Route log entries](https://docs.cloud.google.com/logging/docs/routing/overview), [Logging quotas and limits](https://docs.cloud.google.com/logging/quotas)).
- You cannot change a log bucket's region after you create it ([Configure log buckets](https://docs.cloud.google.com/logging/docs/buckets)).

### Retention

| Bucket | Retention | Configurable |
|---|---|---|
| `_Required` | 400 days | No |
| `_Default` or user-defined, in a project | 30 days | Yes, 1 to 3650 days |
| `_Default` in a folder or organization | 30 days | No |

Source: [Logging quotas and limits](https://docs.cloud.google.com/logging/quotas).

Retention past the default period costs extra ([Logging quotas and limits](https://docs.cloud.google.com/logging/quotas)). For seven-year audit retention at low cost, a sink to Cloud Storage is the usual pattern ([Detective controls](https://docs.cloud.google.com/architecture/blueprints/security-foundations/detective-controls), [Storage classes](https://docs.cloud.google.com/storage/docs/storage-classes)). Retention locks and compliance storage are in [Organization policy, VPC Service Controls, and audit logging](note:3.1-security-controls).

### Cost levers

- Add exclusion filters to sinks for low-value entries. You can exclude all matches or a percentage (sampling). Excluded entries are not stored and not charged ([Optimize and monitor Google Cloud Observability costs](https://docs.cloud.google.com/stackdriver/docs/observability/pricing-optimize-and-monitor)).
- Exclusions do not reduce `entries.write` API calls or quota, because the Logging API applies them after it receives the entries ([Route log entries](https://docs.cloud.google.com/logging/docs/routing/overview)). To cut volume at the source, change the application or agent configuration.
- Cloud Logging storage charges apply only to log buckets. Routing to Cloud Storage, BigQuery, or Pub/Sub has no Cloud Logging charge, but the destination bills you ([Optimize and monitor Google Cloud Observability costs](https://docs.cloud.google.com/stackdriver/docs/observability/pricing-optimize-and-monitor)).
- User-defined log-based metrics count both included and excluded entries. You can drop the entries from storage and still count them ([Log-based metrics overview](https://docs.cloud.google.com/logging/docs/logs-based-metrics)).

### Log-based metrics and Observability Analytics

Log-based metrics turn log entries into Cloud Monitoring metrics. **Counter** metrics count matching entries. **Distribution** metrics extract values such as latency into histogram buckets. A new metric counts only entries that arrive after you create it. All user-defined log-based metrics are billable custom metrics ([Log-based metrics overview](https://docs.cloud.google.com/logging/docs/logs-based-metrics)).

Use the Logs Explorer to troubleshoot single entries. Use **Observability Analytics** (formerly Log Analytics) for SQL grouping and aggregation, joins of log and trace data, and a linked BigQuery dataset that queries logs without export ([Analyze logs using Logs Explorer and Observability Analytics](https://docs.cloud.google.com/logging/docs/log-analytics)).

## Profiling and benchmarking

**Cloud Profiler** is a statistical, low-overhead profiler for production. It continuously collects CPU and memory-allocation data and maps it to source code. The overhead is usually less than 0.5% when amortized across replicas, so you can leave it on in production ([Cloud Profiler overview](https://docs.cloud.google.com/profiler/docs/about-profiler)).

**Cloud Trace** shows where a request spends time across services. Spans in the `_Trace` bucket are kept for 30 days. For high-traffic systems, a sample rate of 1 in 1,000 or 1 in 10,000 requests is usually enough ([Cloud Trace overview](https://docs.cloud.google.com/trace/docs/overview), [Optimize and monitor Google Cloud Observability costs](https://docs.cloud.google.com/stackdriver/docs/observability/pricing-optimize-and-monitor)).

**Error Reporting** groups error events by root cause and needs no setup. It does not analyze log entries in CMEK-enabled buckets or in a bucket in another project that receives them directly from a sink ([Error Reporting overview](https://docs.cloud.google.com/error-reporting/docs/grouping-errors)).

**Benchmarking** gives a repeatable baseline before a change. Google creates Compute Engine benchmark scores with PerfKit Benchmarker ([Benchmark scores for compute instances](https://docs.cloud.google.com/compute/docs/coremark-scores-of-vm-instances)). For disks, use FIO, not `dd`, because `dd` uses a very low I/O queue depth ([Benchmark Persistent Disk performance](https://docs.cloud.google.com/compute/docs/disks/benchmarking-pd-performance-linux)). For network throughput, use iPerf version 2 ([Benchmark higher network bandwidth](https://docs.cloud.google.com/compute/docs/networking/benchmarking-higher-bandwidth-vms)). Load testing is in [Reliability in production](note:6.6-production-reliability).

## Alerting strategies

### Alert on symptoms, not causes

The SRE book separates "what is broken" (the symptom) from "why" (the cause). Page on symptoms that users feel. Use the four golden signals: latency, traffic, errors, and saturation. Every page must be actionable and must need human judgment. If a page needs only a robotic response, it must not be a page ([Monitoring Distributed Systems](https://sre.google/sre-book/monitoring-distributed-systems/)). Automate that response instead.

### Alerting policy types

| Condition | Use it when |
|---|---|
| Metric threshold | A metric is above or below a value for a retest window. |
| Metric absence | A time series has no data for a retest window. The maximum window is 24 hours. |
| Forecasted metric value | A metric will cross a threshold within a forecast window (1 hour to 7 days), for example disk space. |
| PromQL | You need ratios, dynamic thresholds, or existing Prometheus rules. |
| Log-based | A specific message appears in a log entry. |

Source: [Alerting overview](https://docs.cloud.google.com/monitoring/alerts).

Each policy has conditions, notification channels, and documentation. Put runbook links in the documentation field. To silence a policy during a planned window, create a **snooze** ([Alerting overview](https://docs.cloud.google.com/monitoring/alerts)).

### SLO burn-rate alerts

The **burn rate** is how fast you use the error budget. A burn rate above 1 means the budget runs out before the compliance period ends ([Alerting on your burn rate](https://docs.cloud.google.com/stackdriver/docs/solutions/slo-monitoring/alerting-on-budget-burn-rate)).

| Policy | Starting point in Cloud Monitoring | Purpose |
|---|---|---|
| Fast burn | 10x burn rate, 1- or 2-hour lookback | A sudden outage that burns the budget in hours or days. Page. |
| Slow burn | 2x burn rate, 24-hour lookback | A small, sustained problem. Less urgent. |

Sources: [Alerting on your burn rate](https://docs.cloud.google.com/stackdriver/docs/solutions/slo-monitoring/alerting-on-budget-burn-rate), [Alerting on SLOs](https://sre.google/workbook/alerting-on-slos/).

In Cloud Monitoring, the lookback period for a burn-rate alert cannot exceed 24 hours ([Alerting on your burn rate](https://docs.cloud.google.com/stackdriver/docs/solutions/slo-monitoring/alerting-on-budget-burn-rate)). The SRE workbook's recommended design is the **multiwindow, multi-burn-rate alert**. A long window catches significant budget use. A short window (1/12 of the long one) confirms that the burn continues, so the alert resets quickly ([Alerting on SLOs](https://sre.google/workbook/alerting-on-slos/)).

| Severity | Long window | Short window | Burn rate |
|---|---|---|---|
| Page | 1 hour | 5 minutes | 14.4 |
| Page | 6 hours | 30 minutes | 6 |
| Ticket | 3 days | 6 hours | 1 |

Source: [Alerting on SLOs](https://sre.google/workbook/alerting-on-slos/) (parameters for a 99.9% SLO).

### Notification channels

- Use more than one channel type. Mobile App, PagerDuty, webhook, and Slack share one Google internal delivery service. Add email or Pub/Sub as the redundant channel ([Create and manage notification channels](https://docs.cloud.google.com/monitoring/support/notification-options)).
- For automation that reads or acts on alerts, use Pub/Sub or webhooks. Other formats can change ([Create and manage notification channels](https://docs.cloud.google.com/monitoring/support/notification-options)).

### Alert fatigue

The SRE book describes the signs: pages that you learn to ignore, pages without action, and more urgent pages than a person can handle in a day ([Monitoring Distributed Systems](https://sre.google/sre-book/monitoring-distributed-systems/)). The fixes are symptom-based conditions, SLO burn-rate alerts instead of raw thresholds, ticket-level severity for slow problems, and automation for robotic responses ([Alerting on SLOs](https://sre.google/workbook/alerting-on-slos/), [Monitoring Distributed Systems](https://sre.google/sre-book/monitoring-distributed-systems/)).

## AWS mapping

| AWS | Google Cloud | Difference that matters |
|---|---|---|
| Amazon CloudWatch (metrics, alarms) | Cloud Monitoring | Multi-project views come from a metrics scope in a scoping project. |
| CloudWatch Logs | Cloud Logging | Routing is a separate layer (Log Router and sinks). `_Required` audit logs are always kept for 400 days. |
| CloudWatch Logs Insights | Observability Analytics | SQL on upgraded log buckets, with joins to trace data and a linked BigQuery dataset. |
| AWS X-Ray | Cloud Trace | Cloud Run sends request latency to Trace automatically. |
| CloudWatch Synthetics | Synthetic monitors | Tests run as a Node.js Cloud Run function. |
| CloudWatch agent | Ops Agent | Needed for VM memory metrics and deeper process metrics. |
| AWS CloudTrail | Cloud Audit Logs | Admin Activity logs go to the `_Required` bucket. |

Sources: [Compare AWS and Azure services to Google Cloud](https://docs.cloud.google.com/docs/get-started/aws-azure-gcp-service-comparison), [Metrics scopes overview](https://docs.cloud.google.com/monitoring/settings), [Route log entries](https://docs.cloud.google.com/logging/docs/routing/overview), [Logging quotas and limits](https://docs.cloud.google.com/logging/quotas), [Analyze logs using Logs Explorer and Observability Analytics](https://docs.cloud.google.com/logging/docs/log-analytics), [Cloud Trace overview](https://docs.cloud.google.com/trace/docs/overview), [Synthetic monitoring overview](https://docs.cloud.google.com/monitoring/uptime-checks/introduction), [Observe and monitor VMs](https://docs.cloud.google.com/compute/docs/instances/observe-monitor-vms).

## Exam traps

- **Exclusions to cut API quota.** Exclusion filters reduce storage cost, not `entries.write` calls ([Route log entries](https://docs.cloud.google.com/logging/docs/routing/overview)).
- **A new sink for old logs.** Sinks are not retroactive. Copy existing logs from the bucket instead ([Route log entries](https://docs.cloud.google.com/logging/docs/routing/overview)).
- **Longer `_Default` retention for audit compliance.** Long retention in log buckets costs extra. For years of low-cost storage, route to Cloud Storage ([Logging quotas and limits](https://docs.cloud.google.com/logging/quotas), [Route log entries](https://docs.cloud.google.com/logging/docs/routing/overview), [Storage classes](https://docs.cloud.google.com/storage/docs/storage-classes)).
- **A production project as the scoping project.** Google recommends a project without resources ([Metrics scopes overview](https://docs.cloud.google.com/monitoring/settings)).
- **Trace for CPU hot spots.** Trace shows latency between services. Profiler shows which code uses CPU and memory ([Cloud Profiler overview](https://docs.cloud.google.com/profiler/docs/about-profiler)).
- **Missing VM memory data.** Install the Ops Agent. More dashboards do not help ([Observe and monitor VMs](https://docs.cloud.google.com/compute/docs/instances/observe-monitor-vms)).
- **Paging on CPU utilization.** High CPU is a cause, not a symptom. Page on user-visible symptoms or SLO burn rate ([Monitoring Distributed Systems](https://sre.google/sre-book/monitoring-distributed-systems/)).
- **One alert on a 30-day burn window.** Cloud Monitoring burn-rate lookbacks stop at 24 hours. Use fast-burn and slow-burn policies ([Alerting on your burn rate](https://docs.cloud.google.com/stackdriver/docs/solutions/slo-monitoring/alerting-on-budget-burn-rate)).
- **Only Slack or PagerDuty.** They share one delivery path. Add email or Pub/Sub ([Create and manage notification channels](https://docs.cloud.google.com/monitoring/support/notification-options)).
