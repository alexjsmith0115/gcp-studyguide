## Why it matters

Google Cloud has a separate security control for each traffic layer. Cloud Next Generation Firewall (Cloud NGFW) protects VMs, Google Cloud Armor protects load balancers, and Secure Web Proxy controls outbound web traffic. The architect picks the control that fits the threat: block or detect, inbound or outbound, IP address or workload identity. Many exam distractors name a real product at the wrong layer.

## Key points

- Cloud NGFW is a distributed, stateful firewall service. It applies rules to VMs and to supported load balancers in a VPC network ([Cloud NGFW overview](https://docs.cloud.google.com/firewall/docs/about-firewalls)).
- You don't subscribe to a Cloud NGFW tier. Google Cloud bills traffic at the tier of the features that the evaluating rule uses ([Cloud NGFW tiers](https://docs.cloud.google.com/firewall/docs/ngfw_tiers)).
- By default, hierarchical firewall policies come first, then VPC firewall rules, then network firewall policies. `BEFORE_CLASSIC_FIREWALL` moves network firewall policies ahead of VPC firewall rules ([Rule evaluation order](https://docs.cloud.google.com/firewall/docs/firewall-policies-rule-eval-order)).
- When no rule matches, ingress to a VM is denied and egress is allowed. Rules are stateful, so return traffic of an allowed connection is allowed ([Rule evaluation order](https://docs.cloud.google.com/firewall/docs/firewall-policies-rule-eval-order), [VPC firewall rules](https://docs.cloud.google.com/firewall/docs/firewalls)).
- Only firewall policies can use secure tags, which IAM controls. VPC firewall rules use network tags, which have no access control ([Secure tags for firewalls](https://docs.cloud.google.com/firewall/docs/tags-firewalls-overview)).
- Cloud NGFW Enterprise (formerly Cloud Firewall Plus) blocks threats inline through zonal firewall endpoints. Cloud IDS detects threats and alerts, but doesn't block ([Intrusion prevention](https://docs.cloud.google.com/firewall/docs/about-intrusion-prevention), [Cloud IDS](https://docs.cloud.google.com/intrusion-detection-system/docs/overview), [Announcing Next Gen Firewall Enterprise, now in GA](https://cloud.google.com/blog/products/identity-security/announcing-next-gen-firewall-enterprise-now-in-ga-next24)).
- Cloud Armor security policies attach to load balancer backend services. They add WAF rules, rate limiting, and geography rules ([Cloud Armor policies](https://docs.cloud.google.com/armor/docs/security-policy-overview)).
- Secure Web Proxy is a managed proxy for outbound HTTP and HTTPS. It denies all traffic by default and allows it by source identity and destination ([Secure Web Proxy](https://docs.cloud.google.com/secure-web-proxy/docs/overview)).
- VPC Flow Logs record sampled flows. Packet Mirroring copies full packets. Firewall rules logging records the rule that allowed or denied each connection ([VPC Flow Logs](https://docs.cloud.google.com/vpc/docs/flow-logs), [Packet Mirroring](https://docs.cloud.google.com/vpc/docs/packet-mirroring), [Rules logging](https://docs.cloud.google.com/firewall/docs/firewall-policy-rules-logging-overview)).

## Choose the control

| Requirement | Use | Not this |
|---|---|---|
| Allow or deny VM traffic by IP range, port, and protocol | Rules in a global network firewall policy | Cloud Armor. It works at load balancers and public IP addresses. |
| App teams choose which approved rules apply to their VMs | Secure tags in firewall policy rules | Network tags. Anyone who can edit a VM can change them. |
| Egress only to named domains, or deny known bad IP addresses | Cloud NGFW Standard: FQDN objects, geolocation, threat intelligence | Cloud NAT alone. Only egress firewall rules filter its traffic. |
| Block exploits and command-and-control traffic inline, also east-west | Cloud NGFW Enterprise intrusion prevention | Cloud IDS. It only alerts. |
| Detect threats in a copy of the traffic, for example for PCI 11.4 or HIPAA | Cloud IDS | VPC Flow Logs. They hold only sampled connection data. |
| Protect a public web app from SQL injection and cross-site scripting | Cloud Armor preconfigured WAF rules | Backend firewall rules. They control only the traffic from the load balancer proxies. |
| Limit or ban clients that send too many requests | Cloud Armor throttle or rate-based ban rules | Adaptive Protection alone. It models anomalies, not a fixed limit for each client. |
| Control outbound HTTP(S) by workload identity and URL | Secure Web Proxy | Cloud NAT. Use it when you don't need identity controls. |
| Rules that no project can override | Hierarchical firewall policy ([security controls](note:3.1-security-controls)) | VPC firewall rules in each project |

Sources: [Cloud NGFW tiers](https://docs.cloud.google.com/firewall/docs/ngfw_tiers), [Secure tags](https://docs.cloud.google.com/firewall/docs/tags-firewalls-overview), [Cloud NAT](https://docs.cloud.google.com/nat/docs/overview), [Cloud IDS](https://docs.cloud.google.com/intrusion-detection-system/docs/overview), [VPC firewall rules](https://docs.cloud.google.com/firewall/docs/firewalls), [Cloud Armor](https://docs.cloud.google.com/armor/docs/cloud-armor-overview), [Rate limiting](https://docs.cloud.google.com/armor/docs/rate-limiting-overview), [External Application Load Balancer overview](https://docs.cloud.google.com/load-balancing/docs/https), [VPC Flow Logs](https://docs.cloud.google.com/vpc/docs/flow-logs), [VPC design](https://docs.cloud.google.com/architecture/best-practices-vpc-design), [Hierarchical firewall policies](https://docs.cloud.google.com/firewall/docs/firewall-policies).

## Cloud NGFW: where rules live

A firewall policy groups rules into one object that IAM roles control, and you can apply it to several networks. VPC firewall rules belong to one VPC network. You can't share them with other networks, including peered networks ([Firewall policies](https://docs.cloud.google.com/firewall/docs/firewall-policies-overview), [VPC firewall rules](https://docs.cloud.google.com/firewall/docs/firewalls)).

| Container | Scope | Targets | Layer 7 inspection | Notes |
|---|---|---|---|---|
| VPC firewall rules | One VPC network | All instances, network tags, or service accounts | No | `allow` and `deny` only |
| Global network firewall policy | All regions of VPC networks in the same project. One policy for each network. | Service accounts, secure tags, internal load balancer forwarding rules | Yes | `goto_next` passes to the next step |
| Regional network firewall policy | One region of VPC networks in the same project | Service accounts, secure tags, internal load balancer forwarding rules | No | No `apply_security_profile_group` action |
| Hierarchical firewall policy | An organization or a folder | VPC networks, service accounts, organization-scoped secure tags | Yes | Lower levels can't override it. `goto_next` delegates to them. |

Sources: [Global network firewall policies](https://docs.cloud.google.com/firewall/docs/network-firewall-policies), [Regional network firewall policies](https://docs.cloud.google.com/firewall/docs/regional-firewall-policies), [Hierarchical firewall policies](https://docs.cloud.google.com/firewall/docs/firewall-policies), [Rule components](https://docs.cloud.google.com/firewall/docs/firewall-policies-rule-details).

### Evaluation order

With the default `AFTER_CLASSIC_FIREWALL` order, Cloud NGFW evaluates in these steps ([Rule evaluation order](https://docs.cloud.google.com/firewall/docs/firewall-policies-rule-eval-order)):

1. Hierarchical firewall policies: the organization, then folders from the top down.
2. Regional system firewall policies.
3. VPC firewall rules.
4. The global network firewall policy.
5. Regional network firewall policies.
6. The implied action: deny ingress to VM interfaces, allow all egress.

`BEFORE_CLASSIC_FIREWALL` moves steps 4 and 5 ahead of step 3. You set it with `gcloud compute networks update --network-firewall-policy-enforcement-order`. In each step, rules are checked from the highest priority to the lowest. `allow` and `deny` stop all evaluation, and `goto_next` goes to the next step. So a priority number orders rules only inside one step.

For internal Application Load Balancers and internal proxy Network Load Balancers, the implied ingress action is `allow`, not `deny` ([Rule evaluation order](https://docs.cloud.google.com/firewall/docs/firewall-policies-rule-eval-order)).

By default, Google Cloud blocks egress to TCP port 25 of external IP addresses. The default network has rules that allow SSH and RDP from `0.0.0.0/0` ([VPC firewall rules](https://docs.cloud.google.com/firewall/docs/firewalls)). For IAP TCP forwarding, allow ingress from `35.235.240.0/20` ([IAP TCP forwarding](https://docs.cloud.google.com/iap/docs/using-tcp-forwarding), [secure access](note:3.1-secure-access)).

## Targets: secure tags, service accounts, and network tags

The target decides who can change which rules apply to a VM. Google recommends secure tags or service accounts over network tags ([VPC design](https://docs.cloud.google.com/architecture/best-practices-vpc-design)).

| Attribute | Network tags | Service accounts | Secure tags |
|---|---|---|---|
| Who controls the binding | Anyone who can edit the VM | Holders of the Service Account User role | Holders of the Tag User role |
| Rules that use it | VPC firewall rules | VPC firewall rules, firewall policies | Firewall policies only |
| Number for each VM | Many | One. A change needs a VM restart. | One value for each tag key |
| Works across VPC Network Peering and NCC VPC spokes | No | No | Only as the source of an ingress rule |

Sources: [VPC firewall rules](https://docs.cloud.google.com/firewall/docs/firewalls), [Secure tags](https://docs.cloud.google.com/firewall/docs/tags-firewalls-overview), [VPC design](https://docs.cloud.google.com/architecture/best-practices-vpc-design).

Secure tags split duties. A Tag Administrator creates tag keys and values. App teams get the Tag User role to bind values to their VMs, without the Compute Security Admin role that changes rules. The parent of a tag key can be a project, so secure tags work without an organization ([Secure tags](https://docs.cloud.google.com/firewall/docs/tags-firewalls-overview)).

## Cloud NGFW tiers

| Tier | Features | Charges |
|---|---|---|
| Essentials | Stateful inspection, secure tags, address groups, VPC firewall rules | No cost |
| Standard | FQDN objects, geolocation objects, Google Threat Intelligence lists | North-south traffic that Standard features evaluate |
| Enterprise | Intrusion detection and prevention, URL filtering, TLS inspection, Advanced malware sandbox (WildFire) (Preview) | Each firewall endpoint hour, plus each GB inspected, north-south and east-west |

Sources: [Cloud NGFW tiers](https://docs.cloud.google.com/firewall/docs/ngfw_tiers), [Cloud NGFW pricing](https://cloud.google.com/firewall/pricing).

FQDN objects match the resolved IP address at the network layer. URL filtering works at the application layer. Without TLS inspection, it sees only the SNI of HTTPS traffic ([Cloud NGFW tiers](https://docs.cloud.google.com/firewall/docs/ngfw_tiers), [URL filtering](https://docs.cloud.google.com/firewall/docs/about-url-filtering)). Enterprise Layer 7 inspection doesn't cover serverless egress, through Direct VPC egress or connectors ([Intrusion prevention](https://docs.cloud.google.com/firewall/docs/about-intrusion-prevention)).

## Intrusion prevention or intrusion detection

| Attribute | Cloud NGFW Enterprise intrusion prevention | Cloud IDS |
|---|---|---|
| Result | Detects and blocks inline | Detects and alerts only |
| Traffic path | Firewall policy rules with `apply_security_profile_group` intercept traffic to a firewall endpoint | Packet Mirroring sends a copy to an IDS endpoint |
| Location | Zonal endpoint for workloads in the same zone. One endpoint for each zone of a VPC network. | Zonal endpoint that inspects traffic from all zones of its region |

Sources: [Intrusion prevention](https://docs.cloud.google.com/firewall/docs/about-intrusion-prevention), [Firewall endpoints](https://docs.cloud.google.com/firewall/docs/about-firewall-endpoints), [Cloud IDS](https://docs.cloud.google.com/intrusion-detection-system/docs/overview).

- Enterprise features work only through firewall policies, never VPC firewall rules. A project can own a firewall endpoint, so you don't need organization permissions ([Intrusion prevention](https://docs.cloud.google.com/firewall/docs/about-intrusion-prevention), [Firewall endpoints](https://docs.cloud.google.com/firewall/docs/about-firewall-endpoints)).
- If a Layer 7 rule and a Cloud IDS policy match the same traffic, the Layer 7 rule wins and the traffic isn't mirrored ([Cloud IDS](https://docs.cloud.google.com/intrusion-detection-system/docs/overview)).
- For your own third-party appliances, Network Security Integration in-band integration inserts them through firewall policy rules, without route changes ([In-band integration](https://docs.cloud.google.com/network-security-integration/docs/in-band/in-band-integration-overview)).

## Cloud Armor for internet-facing apps

Cloud Armor automatically gives DDoS protection to global external Application Load Balancers, classic Application Load Balancers, and external proxy Network Load Balancers, in all tiers. Layer 7 protection needs a security policy that you configure ([Cloud Armor](https://docs.cloud.google.com/armor/docs/cloud-armor-overview), [load balancers](note:1.3-load-balancing)).

| Policy type | Attaches to | Evaluated | Actions and notes |
|---|---|---|---|
| Backend security policy | Backend services of external Application Load Balancers, regional internal Application Load Balancers, and global external and classic proxy Network Load Balancers | For requests that go to the origin. With Cloud CDN, only cache misses and dynamic content. | Allow, deny, throttle, rate-based ban. Redirect only on global external and classic Application Load Balancers. |
| Edge security policy | Backend services and backend buckets of global external and classic Application Load Balancers | At the edge, before the Cloud CDN cache and before IAP | Allow and deny only |
| Network edge security policy | Regional external passthrough Network Load Balancers, protocol forwarding, VMs with public IP addresses | At the edge of Google's network | Needs advanced network DDoS protection (Cloud Armor Enterprise, formerly Managed Protection Plus) |

Sources: [Cloud Armor policies](https://docs.cloud.google.com/armor/docs/security-policy-overview), [Cloud CDN](https://docs.cloud.google.com/cdn/docs/overview), [Cloud Armor Enterprise](https://docs.cloud.google.com/armor/docs/armor-enterprise-overview), [Cloud Armor release notes](https://docs.cloud.google.com/armor/docs/release-notes).

**WAF rules.** Preconfigured WAF rules use the OWASP Core Rule Set. Google recommends CRS 4.22, with rule names such as `sqli-v422-stable`. Sensitivity level 1 has the highest-confidence signatures and the fewest false positives. By default, a rule runs at level 4 with all signatures. Start at level 1 in preview mode, then tune ([Cloud Armor](https://docs.cloud.google.com/armor/docs/cloud-armor-overview), [WAF rules](https://docs.cloud.google.com/armor/docs/waf-rules)).

**Rate limiting.** A `throttle` rule caps each client at a threshold. A `rate_based_ban` rule blocks a client for a set time after it exceeds the threshold. Keys include the client IP address, the `X-Forwarded-For` address, a header, a cookie, and the region. The threshold applies to each backend service. Google recommends status `429` for the exceed action ([Rate limiting](https://docs.cloud.google.com/armor/docs/rate-limiting-overview)).

**Adaptive Protection.** Machine-learning models detect Layer 7 DDoS attacks, write an attack signature, and suggest a WAF rule. A model trains for at least one hour. A new security policy discards the baseline, so don't create policies during an attack ([Adaptive Protection](https://docs.cloud.google.com/armor/docs/adaptive-protection-overview)).

Rules can also match client geography and named IP address lists. Preview mode shows the effect of a rule without enforcing it ([Cloud Armor policies](https://docs.cloud.google.com/armor/docs/security-policy-overview)).

| Feature | Cloud Armor Standard | Cloud Armor Enterprise |
|---|---|---|
| Billing | Per policy, per rule, per request | Paygo, or Annual with a 12-month commitment. WAF usage included. |
| Adaptive Protection | Basic alerts only | Full alerts with signatures and suggested rules |
| Google Threat Intelligence, third-party named IP address lists | No | Yes |
| Advanced network DDoS protection | No | Yes |
| DDoS response support, DDoS bill protection | No | Annual only |

Sources: [Cloud Armor Enterprise](https://docs.cloud.google.com/armor/docs/armor-enterprise-overview), [Adaptive Protection](https://docs.cloud.google.com/armor/docs/adaptive-protection-overview).

## Egress control

Cloud NAT gives VMs without external IP addresses a path to the internet, subject to egress firewall rules. Google recommends Secure Web Proxy when the traffic is HTTP(S) and you need identity controls ([Cloud NAT](https://docs.cloud.google.com/nat/docs/overview), [VPC design](https://docs.cloud.google.com/architecture/best-practices-vpc-design)).

| Option | What it checks | Client change | Use when |
|---|---|---|---|
| Firewall policy egress rules | IP ranges and ports. FQDN and geolocation objects with Standard. | None | A short allowlist of destinations |
| Cloud NGFW Enterprise URL filtering | Domain and SNI. The host header with TLS inspection. | None | Transparent domain filtering with intrusion prevention |
| Secure Web Proxy | Source service account or secure tag, destination host, port. URL path, method, and headers with TLS inspection. | Proxy settings, or next hop routing | Central HTTP(S) egress with identity rules and a log of each request |
| Cloud NAT | No filtering of its own | None | Internet egress without identity controls |

Sources: [Secure Web Proxy](https://docs.cloud.google.com/secure-web-proxy/docs/overview), [Secure Web Proxy rules](https://docs.cloud.google.com/secure-web-proxy/docs/policies-and-rules-overview), [URL filtering](https://docs.cloud.google.com/firewall/docs/about-url-filtering), [Cloud NAT](https://docs.cloud.google.com/nat/docs/overview).

Secure Web Proxy has three modes: explicit proxy, Private Service Connect service attachment for multi-VPC designs, and next hop. With Shared VPC, it runs only in the host project ([Secure Web Proxy](https://docs.cloud.google.com/secure-web-proxy/docs/overview)). Cloud NAT design is on the [access patterns](note:2.1-vpc-access-patterns) page.

## Visibility: logs, mirroring, and insights

| Tool | What it records | Use it for | Limits |
|---|---|---|---|
| VPC Flow Logs | Sampled 5-tuple flow records for a network, subnet, VLAN attachment, or VPN tunnel | Monitoring, forensics, cost analysis | Sampled connection data only |
| Firewall rules logging | One record for each allowed or denied connection, with the rule | Proof of what a rule does | TCP and UDP only. Not for implied rules. |
| Packet Mirroring | Full packets, payloads included, from VMs selected by subnet, network tag, or name | Third-party IDS, deep forensics | Uses VM bandwidth. Collectors sit behind an internal passthrough Network Load Balancer. |
| Firewall Insights | Shadowed rules, rules with no hits, overly permissive allow rules | Rule cleanup | Metrics need firewall rules logging |

Sources: [VPC Flow Logs](https://docs.cloud.google.com/vpc/docs/flow-logs), [Rules logging](https://docs.cloud.google.com/firewall/docs/firewall-policy-rules-logging-overview), [Packet Mirroring](https://docs.cloud.google.com/vpc/docs/packet-mirroring), [Firewall Insights](https://docs.cloud.google.com/network-intelligence-center/docs/firewall-insights/concepts/overview).

For new mirroring deployments, Google recommends Network Security Integration Packet Mirroring ([Packet Mirroring](https://docs.cloud.google.com/vpc/docs/packet-mirroring)). Its mirroring rules live in a global network firewall policy, and collectors can be in another project or organization ([Out-of-band integration](https://docs.cloud.google.com/network-security-integration/docs/out-of-band/out-of-band-integration-overview)).

## Exam traps

- **Cloud IDS to block attacks.** Cloud IDS only detects and alerts. Use Cloud NGFW Enterprise to block ([Cloud IDS](https://docs.cloud.google.com/intrusion-detection-system/docs/overview)).
- **Network tags as a security boundary.** Anyone who can edit a VM can change its tags, and with them its rules ([VPC firewall rules](https://docs.cloud.google.com/firewall/docs/firewalls)).
- **Secure tags or intrusion prevention in VPC firewall rules.** VPC firewall rules support neither. Use a firewall policy ([Secure tags](https://docs.cloud.google.com/firewall/docs/tags-firewalls-overview), [Intrusion prevention](https://docs.cloud.google.com/firewall/docs/about-intrusion-prevention)).
- **A priority number to beat an earlier step.** A network firewall policy deny at priority 1 still loses to a VPC firewall rule that allows first, unless the network uses `BEFORE_CLASSIC_FIREWALL` ([Rule evaluation order](https://docs.cloud.google.com/firewall/docs/firewall-policies-rule-eval-order)).
- **Flow logs for payloads.** VPC Flow Logs sample packets and aggregate them by connection. Packet Mirroring captures payloads ([VPC Flow Logs](https://docs.cloud.google.com/vpc/docs/flow-logs), [Packet Mirroring](https://docs.cloud.google.com/vpc/docs/packet-mirroring)).
- **A geography block in a backend security policy with Cloud CDN.** Cache hits never reach it. Use an edge security policy ([Cloud CDN](https://docs.cloud.google.com/cdn/docs/overview)).
- **One firewall endpoint for a whole region.** An endpoint inspects only workloads in its own zone ([Firewall endpoints](https://docs.cloud.google.com/firewall/docs/about-firewall-endpoints)).
