## Why it matters

A disaster recovery (DR) question gives you a recovery time objective (RTO), a recovery point objective (RPO), a budget, and the location of production. You must choose a cold, warm, or hot pattern and the Google Cloud building blocks for it. The exam rewards the least expensive design that meets the numbers. It punishes designs that assume a product survives a region outage when it does not.

## Key points

- RTO is the maximum acceptable time that an application can be offline. RPO is the maximum acceptable length of time during which data can be lost. A business impact analysis defines both ([Disaster recovery planning guide](https://docs.cloud.google.com/architecture/dr-scenarios-planning-guide)).
- Smaller RTO and RPO values cost more and add administrative overhead ([Disaster recovery planning guide](https://docs.cloud.google.com/architecture/dr-scenarios-planning-guide)).
- Google names three DR patterns: cold, warm, and hot. One application can mix them, for example a hot purchase path and a warm or cold notification service ([Disaster recovery scenarios for applications](https://docs.cloud.google.com/architecture/dr-scenarios-for-applications)).
- On Google Cloud, define RTO and RPO per outage scope. The scopes are a zonal outage, a regional outage, and the very unlikely outage of multiple regions ([Architecting disaster recovery for cloud infrastructure outages](https://docs.cloud.google.com/architecture/disaster-recovery)).
- RPO zero usually needs synchronous replication. Many products replicate synchronously across zones, but only a few do it across regions ([Architecting disaster recovery for cloud infrastructure outages](https://docs.cloud.google.com/architecture/disaster-recovery)).
- Business-critical operations must depend only on the data plane. Do not make recovery depend on a VM-creation API call or an IAM change ([Architecting disaster recovery for cloud infrastructure outages](https://docs.cloud.google.com/architecture/disaster-recovery)).
- Create reservations in the DR target zones. Without them, on-demand capacity might not be available within your RTO ([Disaster recovery building blocks](https://docs.cloud.google.com/architecture/dr-scenarios-building-blocks)).
- Test recovery regularly: regional failover, release rollback, and restore from backup. Measure the result against RTO and RPO ([Perform testing for recovery from failures](https://docs.cloud.google.com/architecture/framework/reliability/perform-testing-for-recovery-from-failures)).
- Backup and DR Service gives central, policy-based backups. Its backup vault keeps backups immutable and indelible ([Backup and DR overview](https://docs.cloud.google.com/backup-disaster-recovery/docs/concepts/backup-dr)).

## RTO, RPO, and the plan

DR is a subset of business continuity planning. RPO measures time only. It does not describe the amount or quality of lost data. Treat RTO and RPO as service level objectives (SLOs) ([Disaster recovery planning guide](https://docs.cloud.google.com/architecture/dr-scenarios-planning-guide)).

High availability (HA) and DR overlap, but HA does not replace DR. DR also covers software bugs and data corruption, not only infrastructure failures ([Architecting disaster recovery for cloud infrastructure outages](https://docs.cloud.google.com/architecture/disaster-recovery)). HA design is in [High availability, scalability, and performance](note:1.2-ha-scalability-performance). Per-service backups are in [Data protection](note:2.2-data-protection).

A DR plan from the planning guide has these parts ([Disaster recovery planning guide](https://docs.cloud.google.com/architecture/dr-scenarios-planning-guide)):

1. Recovery goals: an RTO, an RPO, and a pattern for each workload.
2. End-to-end recovery: backup, restore, and cleanup. A backup alone is not a plan.
3. Specific tasks: each step is a concrete command, not "run the restore script."
4. Control measures: for example, an alert when a deletion pipeline deletes too much.
5. Software readiness: images, licenses, and reserved capacity.
6. Continuous deployment for recovery: CD tools and artifacts must work during the disaster.
7. Security and compliance controls, and regular tests.

## Cold, warm, and hot patterns

| Pattern | What runs in the DR location before the disaster | Failover | Fits |
|---|---|---|---|
| Cold | Minimal resources: backups in Cloud Storage, custom images, IaC templates | Create the environment, restore the latest backup and transaction logs, test, then point Cloud DNS to it | RTO over a day; archive and compliance data |
| Warm | Part of the stack, for example a database replica on the smallest machine type that can accept replication | Resize the database, create web and app servers from snapshots, test, switch DNS | RTO between an hour and a day |
| Hot | Both environments serve production traffic | No move of data or processing; DNS or the load balancer stops sending traffic to the failed side | RTO of minutes, for a small set of critical services |

Sources: [Disaster recovery scenarios for applications](https://docs.cloud.google.com/architecture/dr-scenarios-for-applications), [Architecting disaster recovery for cloud infrastructure outages](https://docs.cloud.google.com/architecture/disaster-recovery), [Disaster recovery planning guide](https://docs.cloud.google.com/architecture/dr-scenarios-planning-guide).

A warm pattern is a good trade-off between budget and availability ([Disaster recovery scenarios for applications](https://docs.cloud.google.com/architecture/dr-scenarios-for-applications)). Automate its scale-out steps. A hot pattern across regions is complicated and expensive, and only a very small fraction of critical services warrant it ([Architecting disaster recovery for cloud infrastructure outages](https://docs.cloud.google.com/architecture/disaster-recovery)).

Examples when production already runs on Google Cloud ([Disaster recovery scenarios for applications](https://docs.cloud.google.com/architecture/dr-scenarios-for-applications)):

- **Cold, recoverable application server.** A MIG with a target size of one uses a startup script that creates a disk from the latest snapshot. The MIG re-creates a failed VM in the same zone. A zone failure needs manual action. The snapshot frequency sets the RPO.
- **Warm, static site failover.** A Cloud Storage static site waits on standby. If the MIG backends fail, you point Cloud DNS to the static site.
- **Hot, HA web application.** A regional MIG across three zones, global load balancing, and Cloud SQL. Failover is automatic.

Failback to the repaired primary reverses the steps. The application is down from the time you stop connections to the DR site until DNS points back to production ([Disaster recovery scenarios for applications](https://docs.cloud.google.com/architecture/dr-scenarios-for-applications)).

## Design for cloud infrastructure outages

Google Cloud products are zonal, regional, or multi-regional. Google Cloud offers few zonal resources, namely Compute Engine VMs and Persistent Disk. You compose them yourself, for example with MIGs across zones and regional Persistent Disk ([Architecting disaster recovery for cloud infrastructure outages](https://docs.cloud.google.com/architecture/disaster-recovery)).

| Product scope | Component failure in a zone | Zone outage | Region outage |
|---|---|---|---|
| All products | Covered | Not covered | Not covered |
| Regional, with automatic replication across zones | Covered | Covered | Not covered |
| Multi-regional or global, with automatic replication across regions | Covered | Covered | Covered |

Sources: [Architecting disaster recovery for cloud infrastructure outages](https://docs.cloud.google.com/architecture/disaster-recovery).

The design goal is 99.9% for zonal resources (8.75 hours of downtime per year) and 99.99% for regional resources (52 minutes per year). If an hour of regional downtime per year is not acceptable, the application needs a multi-region DR plan ([Architecting disaster recovery for cloud infrastructure outages](https://docs.cloud.google.com/architecture/disaster-recovery)).

What some products do in an outage:

| Product | Zone outage | Region outage |
|---|---|---|
| Compute Engine | VMs in the zone are unavailable; MIGs across zones keep serving | Use more than one regional MIG for stateless apps |
| Cloud Run | Traffic goes to other zones | Data is never replicated across regions, and Cloud Run never routes traffic to another region. Deploy to several regions behind Cloud Load Balancing. |
| Cloud Storage | Regional buckets serve from other zones with no lost writes | Dual-region and multi-region buckets keep serving. Data replicates asynchronously; turbo replication on a dual-region targets 15 minutes. |
| Cloud SQL | The HA configuration fails over to a standby in another zone | Cross-region replicas are asynchronous. Promotion is a manual decision because of split-brain risk. Without a write endpoint (Enterprise Plus edition), you redirect clients yourself. |
| Spanner | A regional instance keeps a quorum across three zones | A multi-region instance keeps a quorum across five replicas in three regions |
| BigQuery | Data is written synchronously to two zones | Not covered by default. A multi-region dataset still stores data in one region. Managed disaster recovery (Enterprise Plus edition) adds failover to a secondary region. |
| Cloud Build and Cloud Deploy | New builds go to healthy zones; running builds can be lost | Triggers and worker pools are not replicated, and release data is lost. Prepare triggers and pools in several regions; keep pipeline definitions in source control. |

Sources: [Architecting disaster recovery for cloud infrastructure outages](https://docs.cloud.google.com/architecture/disaster-recovery), [About disaster recovery (DR) in Cloud SQL](https://docs.cloud.google.com/sql/docs/mysql/intro-to-cloud-sql-disaster-recovery), [Connect to an instance using a write endpoint](https://docs.cloud.google.com/sql/docs/mysql/connect-to-instance-using-write-endpoint), [BigQuery managed disaster recovery](https://docs.cloud.google.com/bigquery/docs/managed-disaster-recovery).

Decision rules from the guide ([Architecting disaster recovery for cloud infrastructure outages](https://docs.cloud.google.com/architecture/disaster-recovery)):

- Group applications into criticality tiers. Give each tier one RTO and RPO per outage scope.
- Ask whether you really need RPO zero, and whether only a subset of the data needs it. RPO zero means mostly regional products, which do not survive a region outage.
- An RTO in minutes means automatic recovery, with no human steps or a single failover button.
- Plan for partial outages in the same way as full outages.
- Use a load balancer even when the RTO is long. Manual changes to IP addresses or DNS can take longer than expected.
- A "golden source" can lower the RPO of a whole service. For example, raw files in Cloud Storage let you re-ingest data into BigQuery after an outage.

For each scope and outage length, ask what customers see, how you detect the outage, what happens to data, and who recovers ([Architecting disaster recovery for cloud infrastructure outages](https://docs.cloud.google.com/architecture/disaster-recovery)).

## DR scenarios by production location

| Production runs on | Data | Databases |
|---|---|---|
| On-premises | Scheduled `gcloud storage rsync` to Cloud Storage for a lower RPO, Storage Transfer Service file system transfers (formerly Transfer service for on-premises data), or a partner gateway | Copy backups and transaction logs to Cloud Storage and restore to a recovery server, or replicate to a standby server on Compute Engine |
| Google Cloud | Tiered storage: move older backups to Nearline, Coldline, or Archive with Object Lifecycle Management | Managed database features, Backup and DR Service, or a self-managed database on a MIG of size one with snapshots |
| Another cloud | Storage Transfer Service, the recommended way to copy from Amazon S3. Schedule jobs at intervals no longer than the RPO. | The provider's HA features, or Cloud Storage as cold storage for backup files |

Sources: [Disaster recovery scenarios for data](https://docs.cloud.google.com/architecture/dr-scenarios-for-data), [Disaster recovery building blocks](https://docs.cloud.google.com/architecture/dr-scenarios-building-blocks), [Data transfer options](https://docs.cloud.google.com/storage-transfer/docs/transfer-options).

For a hybrid DR site, the connection to Google Cloud can fail too. Keep an alternative access path and test it regularly ([Disaster recovery planning guide](https://docs.cloud.google.com/architecture/dr-scenarios-planning-guide)).

For locality-restricted workloads, ask whether encryption with Cloud External Key Manager meets the requirement. If yes, dual-region and multi-region services are an option. If not, restrict locations with the resource locations organization policy constraint ([Architecting disaster recovery for locality-restricted workloads](https://docs.cloud.google.com/architecture/architecting-disaster-recovery-for-locality-restricted-workloads)).

## Building blocks

| Need | Building block |
|---|---|
| Identical replacement VMs | Custom images, instance templates, and MIGs with autohealing |
| Capacity at failover | Compute Engine reservations in the DR zones |
| Disk recovery in another zone or region | Snapshots copied across regions; regional Persistent Disk (force-attach in the other zone); Persistent Disk Asynchronous Replication for cross-region active-passive DR |
| Protection from deletion | Cloud Storage soft delete and object holds; VM deletion protection |
| Traffic switch | Cloud Load Balancing health checks and one anycast IP; Cloud DNS routing policies with failover |
| Rebuild of the environment | Terraform and Infrastructure Manager; configuration management tools; containers in Artifact Registry |
| Kubernetes | Regional clusters, Multi-cluster Gateway, Backup for GKE |
| Detection | Cloud Monitoring uptime checks and alerts |

Sources: [Disaster recovery building blocks](https://docs.cloud.google.com/architecture/dr-scenarios-building-blocks), [Disaster recovery scenarios for applications](https://docs.cloud.google.com/architecture/dr-scenarios-for-applications).

The DR guide examples still use Deployment Manager templates. Google discontinued support for Deployment Manager on April 1, 2026. Use Terraform or Infrastructure Manager instead ([Deployment Manager deprecation](https://docs.cloud.google.com/deployment-manager/docs/deprecations), [Infrastructure as Code](note:5.2-infrastructure-as-code)).

## Backup and DR Service

Backup and DR Service manages backups for Compute Engine, Persistent Disk, Filestore, and VMware Engine VMs. It also protects Cloud SQL, AlloyDB, and self-managed databases such as Oracle and SAP HANA ([Backup and DR overview](https://docs.cloud.google.com/backup-disaster-recovery/docs/concepts/backup-dr)).

- A **backup vault** enforces write once, read many (WORM) immutability, so backups stay recoverable after ransomware attacks or accidental deletion. A vault can also enforce a minimum retention of up to 99 years ([Backup and DR overview](https://docs.cloud.google.com/backup-disaster-recovery/docs/concepts/backup-dr)).
- A **backup plan** links workloads to a vault. Its **backup rules** set frequency, backup windows, and retention ([Backup and DR overview](https://docs.cloud.google.com/backup-disaster-recovery/docs/concepts/backup-dr)).
- Cross-region and cross-project clones support DR drills ([Backup and DR overview](https://docs.cloud.google.com/backup-disaster-recovery/docs/concepts/backup-dr)).

## Security and compliance in the DR environment

- Apply the same network separation and firewall controls as production. Deploy IAM policies to both environments with IaC ([Disaster recovery planning guide](https://docs.cloud.google.com/architecture/dr-scenarios-planning-guide)).
- Make users sign in to the DR environment during regular DR tests, and fix access problems before a disaster ([Disaster recovery planning guide](https://docs.cloud.google.com/architecture/dr-scenarios-planning-guide)).
- Include the DR environment in penetration tests. Backfill DR logs into the production log archive ([Disaster recovery planning guide](https://docs.cloud.google.com/architecture/dr-scenarios-planning-guide)).
- Treat recovered data like production data: same permissions, encryption, and audit. Record who restored what ([Disaster recovery planning guide](https://docs.cloud.google.com/architecture/dr-scenarios-planning-guide)).

## Test the DR plan

The reliability pillar gives this test cycle ([Perform testing for recovery from failures](https://docs.cloud.google.com/architecture/framework/reliability/perform-testing-for-recovery-from-failures)):

1. Define objectives and scope, for example "validate RTO and RPO" and "test automated failover."
2. Prepare a staging or sandbox environment that replicates production. Back up critical data first and inform stakeholders.
3. Simulate failures with scripts. Firewall rules or API restrictions can simulate a region-wide outage. Also test misconfigurations, such as wrong DNS failover settings. Add load during the test.
4. Monitor load balancers, health checks, latency, and errors with Cloud Monitoring and Cloud Logging.
5. Measure the recovery time and data loss, and compare them with RTO and RPO.
6. Document the results and present a postmortem.
7. Repeat on a schedule, for example quarterly. Automate failover tests in CI/CD pipelines.

For data restore tests, judge success by data integrity, RTO, and RPO. Restore in a non-production environment and test the whole application stack with the restored data. Set backup frequency from the RPO, and alert in Cloud Monitoring when a backup interval exceeds it ([Perform testing for recovery from data loss](https://docs.cloud.google.com/architecture/framework/reliability/perform-testing-for-recovery-from-data-loss)). Fault injection and chaos testing are in [Reliability in production](note:6.6-production-reliability).

## Cost trade-offs

| Choice | Saves | Costs |
|---|---|---|
| Cold instead of warm | No compute runs in the DR location | Longer RTO; manual restores can need a database administrator who is not available |
| Warm database on the smallest machine type that accepts replication | Low standing cost; sustained use discounts apply | You resize it during failover |
| Reservations in DR zones | Capacity is there when you fail over | You pay the on-demand rate for reserved resources while the reservation exists |
| Regional Persistent Disk instead of snapshots | No restore step, so a shorter RTO | Twice the storage |
| Nearline, Coldline, or Archive for backups | Lower storage cost; Nearline fits monthly DR tests | Retrieval costs and minimum storage durations |
| Hot across regions | Near-zero RTO | Complex and expensive; keep it for a few critical services |

Sources: [Disaster recovery building blocks](https://docs.cloud.google.com/architecture/dr-scenarios-building-blocks), [Disaster recovery scenarios for applications](https://docs.cloud.google.com/architecture/dr-scenarios-for-applications), [Architecting disaster recovery for cloud infrastructure outages](https://docs.cloud.google.com/architecture/disaster-recovery), [About reservations](https://docs.cloud.google.com/compute/docs/instances/reservations-overview).

## AWS mapping

| AWS | Google Cloud | Difference that matters |
|---|---|---|
| AWS Backup | Backup and DR Service | Backup vaults are immutable and indelible, with enforced retention of up to 99 years. |
| Amazon Route 53 | Cloud DNS routing policies with health checks | Resolvers can cache DNS answers until the TTL expires, and DNS changes can take longer than expected. Prefer a load balancer where it fits. |
| Amazon Relational Database Service (RDS) | Cloud SQL with cross-region replicas | Replication is asynchronous. You decide on promotion. Without a write endpoint (Enterprise Plus edition), you redirect clients yourself. |
| Amazon Aurora or Amazon DynamoDB | Spanner multi-region | Writes are acknowledged only after a quorum across regions commits them, so a region outage loses no acknowledged writes. |
| AWS Simple Storage Service (S3) | Cloud Storage dual-region or multi-region | One bucket with no separate primary and secondary, active-active in both regions. Turbo replication targets a 15-minute RPO. |

Sources: [Compare AWS and Azure services to Google Cloud](https://docs.cloud.google.com/docs/get-started/aws-azure-gcp-service-comparison), [Architecting disaster recovery for cloud infrastructure outages](https://docs.cloud.google.com/architecture/disaster-recovery), [Backup and DR overview](https://docs.cloud.google.com/backup-disaster-recovery/docs/concepts/backup-dr), [DNS routing policies and health checks](https://docs.cloud.google.com/dns/docs/routing-policies-overview), [Connect to an instance using a write endpoint](https://docs.cloud.google.com/sql/docs/mysql/connect-to-instance-using-write-endpoint).

## Exam traps

- **"BigQuery multi-region protects against a region outage."** It stores data in one region within the location. For cross-region redundancy, use managed disaster recovery (Enterprise Plus edition) or copy datasets to another region ([Architecting disaster recovery for cloud infrastructure outages](https://docs.cloud.google.com/architecture/disaster-recovery), [BigQuery locations](https://docs.cloud.google.com/bigquery/docs/locations), [BigQuery managed disaster recovery](https://docs.cloud.google.com/bigquery/docs/managed-disaster-recovery), [Disaster recovery scenarios for data](https://docs.cloud.google.com/architecture/dr-scenarios-for-data)).
- **"Cloud SQL HA covers a region outage."** HA uses two zones in one region. Add a cross-region replica and a promotion runbook ([Architecting disaster recovery for cloud infrastructure outages](https://docs.cloud.google.com/architecture/disaster-recovery)).
- **"Cloud Run moves traffic to another region."** It never does. Deploy to several regions behind a load balancer ([Architecting disaster recovery for cloud infrastructure outages](https://docs.cloud.google.com/architecture/disaster-recovery)).
- **"Create the VMs when the disaster happens" for a tight RTO.** That depends on the management plane and on-demand capacity. Pre-provision capacity or use reservations ([Architecting disaster recovery for cloud infrastructure outages](https://docs.cloud.google.com/architecture/disaster-recovery), [Disaster recovery building blocks](https://docs.cloud.google.com/architecture/dr-scenarios-building-blocks)).
- **Hot active-active for every application.** Tier the portfolio. Most applications fit a warm or cold pattern ([Architecting disaster recovery for cloud infrastructure outages](https://docs.cloud.google.com/architecture/disaster-recovery)).
- **Daily backups for a one-hour RPO.** Back up at least as often as the RPO ([Perform testing for recovery from data loss](https://docs.cloud.google.com/architecture/framework/reliability/perform-testing-for-recovery-from-data-loss)).
- **Relaxed security in the DR site to speed up recovery.** The same controls apply to the recovered environment ([Disaster recovery planning guide](https://docs.cloud.google.com/architecture/dr-scenarios-planning-guide)).
- **One Interconnect as the only path to the DR site.** Keep a second path and test it ([Disaster recovery planning guide](https://docs.cloud.google.com/architecture/dr-scenarios-planning-guide)).
- **Deployment Manager templates to rebuild the DR site.** Support ended on April 1, 2026 ([Deployment Manager deprecation](https://docs.cloud.google.com/deployment-manager/docs/deprecations)).
